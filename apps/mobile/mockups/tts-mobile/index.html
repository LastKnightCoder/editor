推荐架构：同 WebView 直接调用

抽提桌面纯 JS 的 TTS 注册/会话核心，移动端每个 runtime 持有一份实例。无需 Electron relay，也无需为两个厂商各写 Rust。

设置 / 测试 UI→移动 TTS service→共享 TTS registry→插件实例→context.fetch
  • 账号配置与模型在 open 时冻结，取消与插件停用统一处理。
  • 音频直接 Blob 试听，不经过主进程复制完整字节。
  • Qwen 复刻继续使用现有 context.upload.uploadRemote。

配置：沿用桌面数据形状

  • ttsProviders[]：账号实例 ID、插件 ID、名称、私有 config、models。
  • ttsUsageSettings.default：当前账号、模型、音色。
  • 新增原生 TTS mutation，复用 mutate_setting_value 的串行原子落盘。
  • 校验窗口、工作区、账号归属、模型非空与去重；成功返回快照后再更新 UI。
  • preserve_managed_fields 同步保护 TTS 字段，防止陈旧全量写覆盖。

实施顺序与验收

阶段改动通过判据
1. 共享核心抽桌面 registry，移动注入 tts；开放 target:"tts"注册、账号/模型冻结、取消、停用、切库与桌面回归
2. 配置与 UI原生 TTS 配置 mutation；语音入口、账号/模型/当前服务页面保存重开、多账号不串值、失败不发布、旧快照不覆盖

5. 发行真机通过后更新 manifest、版本、兼容文档和中心选版同一 portable ZIP 支持 desktop/android/ios，最低版本指向新宿主

需要你决策的 4 件事

以下选项是推荐默认值；确认后再进入业务实现。

D1 · 本次是否包含音色复刻？ 推荐包含

方案 A：合成 + 音色 + 复刻一次完成，才能称为两个插件完整支持移动端。

精简方案 先不做复刻，可缩小首轮范围，但 Qwen/MiniMax 都属于能力不完整，manifest 与兼容说明必须明确。

D2 · 设置入口是否按 mockup？ 推荐统一入口

我的 → 语音 → 语音合成，插件详情也跳到这里；账号与当前服务集中管理。

备选 只在插件详情配置，入口更深，多账号与当前音色还要继续跳转，不建议。

D3 · 测试能否改当前服务？ 推荐不改

任意账号都可独立测试；只有显式“设为当前语音服务”才修改默认账号、模型与音色。

备选 只允许测试默认服务，实现略少，但新账号必须先启用才能验证，容易误切。

D4 · 旧配置如何处理？ 推荐保守迁移

已有同形 ttsProviders 直接保留；仅对非空旧 MiniMax 凭据做带备份迁移，不从空默认值创建账号。

Doubao 没有本次对应插件，不伪造迁移。也可选择本期完全不迁旧 MiniMax，但要明确告知用户重新配置。

明确不在本次范围

  • 编辑器工具栏“文本转语音”与生成后插入音频附件。
