实现要点
  • 编辑器 kit 已按 mobileContentPlugins.extensions 快照重建；插件就绪后让打开中的编辑器重新取 kit 即可（订阅 runtime 快照）。

异步化的技术路径（供评估，不在本轮实现）

  1. MobilePluginProvider 去掉「未就绪就不渲染 children」，改为 status: "starting" | "ready" | "safe" | "failed" 放进 context，children 立即渲染。
  2. 中心状态刷新（网络）移出启动关键路径：先用本地缓存的撤回状态启动，联网结果回来后再按现有 blockFromCenter 逻辑处置——这本来就是前台刷新已在做的事。
  3. 消费方按需等待：usePluginManager 的「插件会话未就绪」、PluginPageView 的不可用文案、工具栏插入项，在 starting 时显示加载态。
  4. 风险点：插件启动前已打开的编辑器里含插件节点 → 需要「占位只读 → 就绪后换 kit」的机制，这是工作量最大的一步。

顶栏换成全站 PageHeader：左 ChevronLeft、标题居中、右上角搜索图标，点击后横向展开成搜索框（与任务中心同款交互）。商店/已安装改为文字标签（替代 Segmented）。列表有两种形态，都是全宽，彻底消除宽度随描述变化的问题。

「待生效」之后怎么办（需要你决策）

方案 ①：提示「下次打开应用生效」（现状语义）——实现最省，但用户装完插件立刻想用会落空，体验断裂。

方案 ②：提供「立即生效」推荐——applyPendingMobilePlugins() 本就在插件会话启动时执行；异步加载改造后，重建插件会话（不重启应用、不刷新页面）即可让待生效包上线。

  • 首装：可以在下载完成后自动重载会话，用户无感直接可用；按钮从环 → 「已安装」。
  • 更新 / 回退：已有旧版在运行，正文可能正在编辑 → 走横幅「立即生效」，由用户点。
  • 风险：重载期间插件块短暂回到占位态；插件页若正打开会显示「插件重新加载中」。

商店详情与已安装管理合一（同桌面端）：一个页面按「是什么 → 能不能用/在不在运行 → 怎么用 → 细节」披露。头部回答前两个问题，下方分段 Tab 承载桌面端的全部能力，Tab 随状态出现：未安装只有 介绍 · 版本 · 评论，已安装再加 设置 · 权限。
