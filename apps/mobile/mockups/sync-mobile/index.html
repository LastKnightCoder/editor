问题归纳

  1. 最高频动作埋得最深：用户来这里 90% 是「同步一下 / 看看同步了没」，却要进第二层、点一个文字行。
  2. 手势语义反直觉：iOS/Android 设置里「点行 = 进入详情」，这里点行会直接切换同步服务（还会立刻持久化），想看配置却误切服务。
  3. 状态用技术语言：「本地领先 / 远端领先 / v127」需要用户理解版本模型；用户真正关心的是「我的改动传上去没有」「有没有别处的新内容」「上次是什么时候」。
  4. 危险操作没有降级：整库覆盖与日常同步同屏同形。
  5. 配置流程断裂：凭证、参数、启用分散在三个页面；没有连接测试；显式「保存」按钮在移动端容易漏。
  6. 不利于插件化：服务列表是硬编码数组 SYNC_PROVIDERS，每个服务一个手写 Section 组件、一个模块路由（sync-s3…），而桌面端已经是 tau.sync-* 插件。

一页看懂、一键完成：把「数据库同步」做成单页同步中心——顶部大状态卡回答「同步了没」，拇指区一个主按钮，按钮文案随状态变化（上传改动 / 下载更新 / 立即同步）；下拉 = 检查云端（替代「检查远端更新」按钮）。服务、数据库、整库覆盖下沉为普通行，点行一律进入。版本号降为卡片底部小字，给排查问题用。

同步不是一个设置，而是一个随手动作：首页标题旁放常驻同步状态胶囊，点开是同步抽屉（状态 + 主按钮），设置里只留服务配置。优点是最快；代价是首页多一个元素，并且要和首页现有布局协调。可与方案 A 叠加：A 做设置页，B 的胶囊作为快捷入口。

方案 B 的取舍

  • 好处：一次点击完成同步；状态持续可见，用户不用记得去设置里看。
  • 代价：首页加常驻元素；需要定义「何时自动检查云端」（打开 App / 回到前台），会产生额外网络请求。
  • 与插件化的关系：胶囊与抽屉都是宿主组件，只读宿主统一的同步状态，不随服务变化，插件化无额外成本。
  • 建议：先做 A；B 的胶囊作为后续增强，单独确认是否要放首页。

与桌面端同步插件对齐：桌面端 tau.sync-* 插件用 sync.register({ id, name, create(config) }) 提供字节读写，用 settings.register({ target: "sync", component }) 提供自己的设置面板；宿主只负责「选哪个服务 + 挂载面板」。移动端按同一形态组织：宿主外壳 + 服务面板插槽，内置四个服务先以面板形式实现。

谁负责什么

宿主（同步中心 · 永远不变）

状态卡、主按钮、进入时检查云端、版本比较与方向判断、服务抽屉、连接测试、切换前探测与确认、整库覆盖、上次同步时间。

服务（内置或插件）

名称、图标、一句话描述、是否已配置、「同步到」行摘要，以及一个设置面板（账号卡 + 存储位置字段，失焦即保存）。

凭证

内置服务的凭证仍在集成账号，与资源存储共用；面板里就地展示并跳转更换。

注册表条目

{
  id: "s3",                 // = setting.json 的 sync.active
  name: "S3 兼容存储",
  description: "AWS、Cloudflare R2、MinIO…",
  tile: { letter: "S", className: "bg-tag-2-soft text-tag-2" },
  isConfigured: setting => …,
  summary: setting => "tau-sync · ap-southeast-1",
  Panel: S3Panel,           // 设置面板插槽
}

将来移动端支持插件时，插件服务以同样的条目接入同一个注册表，面板来自插件的 target: "sync" 设置组件，宿主页面不变。

需要你拍板的几件事

  1. 方向：先做 A？B 的首页胶囊要不要做、何时做？
  2. 服务选择：抽屉（3-1）还是独立列表页？
  3. 数据库切换：下沉到「更多 › 数据库」可以吗？（现在常驻首屏）
  4. 上次同步时间：本机记录一次成功时间，可以加吗？
  5. 整库覆盖：长按确认 OK，还是保留现在的二次确认弹窗？
  6. 范围：「资源同步」页是否一起按同一套样式改？（本稿只覆盖数据库同步）
