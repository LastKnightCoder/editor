问题归纳

  1. 概念错位：「上传位置」与「资源文件同步」是两件事，后端也是两套配置（imageBed vs sync），界面却放在一页，用户会以为切换存储目标会改变资源同步去向。
  2. 手势反直觉：同数据库同步旧版——点行即切换且立即落盘，可切到未配置的目标。
  3. 没有「传得上去吗」的反馈：没有测试上传，看不到最终地址；上传失败只在编辑器里一闪而过，设置页毫无痕迹。
  4. 状态不可信：资源同步页的计数、「已完成」都是上一轮结果；没有失败文件列表，「重试失败文件」不知道在重试谁。
  5. 假开关：WebView 对 >300KB 的图片总是先转 webp（长边 2048），「上传前压缩」只影响 Rust 端二次压缩。
  6. 不利于插件化：RESOURCE_TARGETS 硬编码 + 每个目标一个手写 Section 和模块路由（resource-github…），而桌面端已是「本地 | 上传插件」两档，插件经 upload.register + settings.register({ target: "upload" }) 接入。

一件事一个地方：设置里的「资源与存储」改名为「图片与附件」，只回答一个问题——新插入的图片和附件存到哪里。资源文件同步（resources 目录 ↔ 云端）本来就跟着数据库同步服务走，挪进同步中心成为第二张卡（见 5）。这与桌面端「资源存储页只管上传目标、资源同步在同步页」一致。

方案 B 的取舍

  • 好处：入口不变，同步中心不用改；改动集中在一个页面。
  • 代价：概念错位还在；用户在两个地方都看到「S3 / GitHub」会混。
  • 与插件化的关系：上传服务的注册表、服务页与 A 完全相同（3 的页面可直接复用），差别只在资源同步放哪。
  • 建议：做 A。资源同步页（5-2/3/4）本身两案通用，B 只是挂载点不同。

与桌面端上传插件对齐：桌面端插件用 upload.register({ id, name, upload(file, config, signal) → url }) 提供上传能力，用 settings.register({ target: "upload", component }) 提供设置面板，宿主只有「本地 | 上传插件」两档。移动端按同一形态组织：宿主外壳 + 上传服务注册表，与同步服务注册表 SYNC_PROVIDERS 同构。

谁负责什么

宿主（图片与附件页 · 编辑器上传管线 · 永远不变）

「本机」选项、目的地卡、最近上传结果、服务抽屉、示例地址框、上传测试（真传 + 回读）、设为上传位置、压缩、编辑器内进度/失败/重试、错误翻译。

上传服务（内置或插件）

名称、图标、一句话描述、是否已配置、副文案摘要、示例地址、一个设置面板，以及一个上传函数：给文件，返回可直接引用的 http(s) 地址。

凭证

内置服务的凭证仍在集成账号，与同步共用；面板里就地展示并跳转更换。插件服务的配置存在插件自己的 configurations[pluginId]（同桌面 imageBed.plugin）。

不是插件点：资源文件同步

它跟随同步服务。将来的同步插件（sync.register）提供字节读写后，资源同步自动可用，不需要另开扩展点。

注册表条目

{
  id: "github",              // = setting.json 的 imageBed.active
  name: "GitHub 仓库",
  description: "公开仓库，免费",
  tile: { icon: "github", className: "bg-tag-3-soft text-tag-3" },
  isConfigured: setting => …,
  summary: setting => "tau-assets · main",
  sampleUrl: setting => "https://…/uploads/2026/10/…",
  Panel: GithubUploadPanel,  // 设置面板插槽
  // 内置服务：宿主调 Rust upload_resource
  // 插件服务：宿主调插件的 upload(file, config, signal)
}

「本机」不进注册表——它是宿主内置的离线选项（同桌面 EImageBed.Local）。编辑器上传管线只依赖「当前目的地 → 上传函数」，所以插件接入时编辑器零改动；测试上传也复用同一个上传函数，插件不需要实现额外的 test 接口。
