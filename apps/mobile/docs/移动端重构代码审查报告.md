## 1. 总体评价

**结论先行：架构方向正确且完成度高，分层设计明显优于旧 navigation 实现；但 `navigator.popTo` 与
`navigator.replace` 存在两个已复现的正确性缺陷（P0），生命周期文档与运行时行为有一处事实性偏差（P1），
`keepAlive: "data"/"fresh"` 策略未实现（P1）。建议修复 P0 后再合入。**

## 2. 架构分层逐层评审

### 2.1 L1 栈机（`src/router/core/stackMachine.ts`）——优秀

纯函数、无 React、不可变更新，`pushEntry/popEntry/replaceTop/popToKey/popToTop/removeEntryById`
全部可单测。`markTop` 维护 `lastActiveAt` 支撑 LRU。match 三态（single/params/multi）的语义
集中在 `pushEntry` 一处，等价于 Android launchMode 的宿主声明式，合理。

细节问题：

- `pushEntry` 去重复用时 `{ ...entry, createdAt: 原.createdAt }` 保留了旧 `createdAt` 但
  `lastActiveAt` 由 `markTop` 刷新。对 screen 层无影响，但 overlay 层的可见性依赖
  `createdAt`（见 D-6），single overlay 复用时会出问题。
- `popToKey` 的目标定位条件 `index < entries.length - 1`（必须是"非栈顶"实例）在单栈内合理，
  但被 `popTo` 跨层使用时语义不完整（见 D-1 分析）。

### 2.2 L1 history 适配器（`core/historyAdapter.ts`）——良好

双栈快照序列化进 `window.history.state`，带 `mark + version` 的版本校验；恢复时 schema 净化
（非法条目丢弃）+ 按位置对齐保留 entry id（避免整栈 remount 丢保活状态），两道防线设计到位。

细节问题：

- `restoreStack` 的兜底匹配用 `JSON.stringify(entry.params) === JSON.stringify(params)`，
  键序敏感。当前因 `sanitizeFields` 按 schema 固定顺序构建结果而恰好安全，但这是一个**隐式
  耦合**，建议加注释说明"依赖 sanitize 的字段顺序稳定"，或改用逐字段比较。
- `restoreStack` 把所有条目的 `lastActiveAt` 统一刷成 `now`，LRU 顺序在恢复后失真（轻微）。

### 2.3 L2 paramsSchema（`core/paramsSchema.ts`）——优秀

类型推导（`InferFields` 将 optional 描述子映射为可选键）与运行时净化（丢弃 schema 外字段、
类型不符回退 default、必填缺失整体拒绝）分离，DSL 只覆盖可 JSON 序列化的标量/嵌套对象，
边界克制。`number/string/boolean` 等工厂函数名与 TS 内置类型重名，通过 `index.ts` 重命名为
`paramNumber/paramString/...` 导出，处理得当。

一处冗余：`sanitizeDesc` 对 `object` 描述子在 `value === undefined` 时返回 `undefined`，
嵌套 object 无 default 语义——若未来需要"可选对象带默认值"需要扩展，当前够用（YAGNI）。

### 2.4 L2 definePage + registry（`definePage.ts` / `registry.ts`）——良好

单文件声明页面全部（身份/匹配/转场/参数/数据/守卫/组件），元数据与组件分别注册进
core（无 React）与 React 侧注册表，两个 registry 均有 `clearForTest` 钩子。默认值
（screen→slideRight、overlay→sheetUp、match→single、keepAlive→keep）选取合理。

问题：

- **类型擦除后 `data` 的 `as` 断言链**（`args.data as PageDataDefinition<ParamFields>`）
  使 `PageDefinition` 上的 `data` 失去强类型，`RouterProvider.preload` 里不得不另建
  `PreloadableDataEntry` 类型重复描述同一结构（DRY 违背，见 5.9）。
- `definePage` 在模块副作用中执行注册（`pages.ts` glob eager），HMR 下重复注册是幂等的
  （Map.set 覆盖），无碍；但 `definePage` 返回值 `export default` 未被任何地方消费，
  `pages.ts` 也只利用副作用——建议注释说明这是刻意为之。

### 2.5 L3 RouterProvider（`RouterProvider.tsx`）——核心枢纽，问题集中地

**设计正确的部分：**

- navigator 命令对象经 `useMemo([])` 引用稳定，全部经由 refs + setState 闭包访问最新状态，
  `getNavigator()` 模块单例供组件外使用（模块赋值在渲染期执行，StrictMode 双渲染无害，
  但并发模式被丢弃的渲染也会赋值，建议移入 `useEffect`，见 5.11）。
- 结果通道（`pushForResult/finish/cancel` + `settleResults`）的三态结算（fulfilled/rejected/
  dismissed/caller-dismissed）覆盖完整，`settleResults` 在每次栈变化时对账，能兜住各种异常路径。
- history 同步契约（增长 setState+pushState、缩短 history.go 驱动 popstate 恢复）保证浏览器
  历史与内部栈一致，是系统能用返回键的正确做法。
- Android `onBackButtonPress` 注册有 disposed 竞态防护（异步 import 完成后若已卸载则立即
  unregister），细节处理成熟。

**问题（详见第 3、4 节）：** `popTo` 深度计算（D-1）、`replace` history 语义（D-2）、
settle 残留（D-7）、降级分支 no-op（D-8）、关闭拦截（D-9）。

### 2.6 L3 PageHost / PageLayer（`PageHost.tsx`）——良好，两处实现缺口

转场编排（surface 状态机 + `useAnimationControls` 手动驱动、双页同动视差、AnimatePresence
exit）集中在此，页面组件零 motion 代码，职责分配正确。LRU 淘汰（`MAX_LIVE_SCREENS = 10`）
带 top/underlay 保护与引用相等去重，实现干净。

问题：

- **keepAlive 只有 `"keep"` 生效**（D-4）：LRU effect 里 `keepAlive === "keep"` 是该字段
  唯一读取点；`PageLayer` 对所有页面一律渲染 `<Activity>`。声明 `"data"`/`"fresh"` 的页面
  实际仍保活。当前所有页面用默认 keep 所以未暴露，但这是 API 承诺与实现不符的**事实性缺口**。
- LRU 淘汰时 `evicted ? null : <PageStoreScope>` 连页面私有 store 一起卸载（D-10），
  与注释"数据仍在 query 缓存"并不矛盾（query 是全局的），但**页面 UI 态会静默丢失**，
  需要在文档中写明取舍。
- `PageLayer` 内 `instanceValue` 每次渲染新建对象且未 memo，栈内每个存活页面在每次栈变化时
  都会触发 `PageInstanceContext` 消费者重渲染（性能，见 5.5）。
- `useRouterContext().navigator` 写在 JSX 表达式中间（`PageHost.tsx:179` 附近），合法但
  违反 hooks "顶层调用" 的惯例，可读性差（见 5.6）。
- `AnimatePresence` 的直接子元素是 `PageLayer`（普通组件，根为 `<Activity>`），exit 动画依赖
  `motion.div` 通过 PresenceContext 感知卸载。当前集成测试（jsdom）证明可行，但
  `Activity` 与 `AnimatePresence` 组合属于两个库的边缘交叠，React 升级时需回归验证。

### 2.7 L3 OverlayHost（`OverlayHost.tsx`）——设计巧，实现薄

`createdAt` 新旧判定可见性：`entry.id === topOverlayId && entry.createdAt > topScreenCreatedAt`。
"预览打开详情时浮层自动隐藏、返回自动恢复"确实零恢复代码，是这次重构里最亮眼的设计之一。

问题：

- **single overlay 重 push 不更新 createdAt**（D-6）：`pushEntry` 去重复用保留原 `createdAt`。
  场景：`preview(t1) → 下钻 detail(t2) → 不返回、在 detail 层再 push cardPreview(新 cardId)`
  ——entry 移到 overlay 栈顶且 params 已更新，但 `createdAt(t1) < topScreenCreatedAt(t2)`，
  `isActive=false`，**用户点击无任何反应**。当前 UI 里 detail 层没有预览入口所以未暴露，
  但这是规则与 match 策略的组合缺陷，加页面时会踩。修复：去重复用时刷新 `createdAt`
  （screen 层无此约束，或统一改为"复用时更新 createdAt"——需评估对下钻隐藏语义的影响，
  screen 层 `createdAt` 不参与可见性，统一刷新是安全的）。
- `AnimatePresence` 包裹的子树内没有任何 `motion` 组件（overlay 组件自带容器形态），
  该 AnimatePresence **不产生任何退出动画**，纯冗余（D-12）；若期望 overlay 有退出转场，
  需要在 PageStoreScope 外再包 motion 层或删除 AnimatePresence。
- overlay 的转场配置（`transition: sheetUp` 默认）在 overlay 层**完全没有被消费**——
  `definePage` 里 overlay 的 `transition/presentation` 声明了但渲染层未读取（`presentation`
  同样无消费方）。属于"协议先行、实现未跟上"，与 D-4 同类。

### 2.8 L3 生命周期（`pageLifecycle.tsx`）——分层思路好，存在级语义存疑

三层事件（存在级/显示级/恢复级）对齐 Android/iOS 的意图明确；`transition.seq` 递增触发
effect 的手法规避了闭包陷阱；`useBackHandler/usePageGuard` 用 ref 保最新 handler、
按 entryId 注册注销，实现干净。

**核心问题（D-3，已复现）**："存在级" `onInit/onDestroy` 挂在普通 `useEffect` 上，而页面
进入 `deeper`（第三层及以下）时 `<Activity mode="hidden">` 会卸载 effect：

- `home → a → b → c` push 到 c 时，a 触发 `A:destroy`（实验输出：`["A:init","B:init","A:destroy","C:init"]`）；
- 返回 `c → b` 时 a 的 effect 重挂，`A:init` 再次触发。

因此 `onInit/onDestroy` 实际语义是**"可见性级"而非"存在级"**——与代码注释和文档
"实例创建/pop 销毁（keep-alive 下仅一次）"矛盾。两层含义（pop 销毁 vs 压深隐藏）在
当前实现下不可区分。需要二选一：

1. 修正语义：`onInit/onDestroy` 更名或改文档为"首次渲染/不可见"，另设真正的存在级钩子
   （例如由 PageHost 在 entries 数组增删时经 context 显式分发，不受 Activity 影响）；
2. 或在 `usePageLifecycle` 内部用"该实例是否曾出现在栈里"的外部登记表判断真实销毁。

**注**：与 `onPause/onResume`（phase 驱动）的关系也需理清——phase paused 包含"被覆盖"
（underlay，effect 未卸载）与"压深"（deeper，effect 已卸载）两种情形，`onPause` 只在
前者触发（phase 变化），后者靠 `onDestroy` 表达，事件矩阵比文档表格复杂。建议文档补一张
"页面位置 × 事件"真值表。

### 2.9 L3 手势（`gesture.ts`）——实现质量好，一个交互缺口

28px 边缘判定、8px 横向意图锁定（与纵向滚动冲突避免）、40% 位移或 0.5px/ms 速度提交、
`configRef` 保持最新配置、capture 阶段挂载 passive 策略正确（move 用 non-passive 以便
preventDefault）。**问题（D-5）**：`finish()` 达到提交阈值后先 `start({x:"100%"})` 把页面
动画飞出，再调 `onBack()` → `goBack("gesture")` → `historyBack` 异步询问守卫。若守卫返回
false，栈不变，但页面已停在 100% 处（不可见），**没有回弹**，界面假死。修复：`onBack` 改为
带回滚回调（`onBack(): Promise<boolean>` 或提交前先同步问守卫），拒绝时 `springBack()`。

另外 velocity 只取正向（`Math.max(0, ...)`），手指先右快滑再左回移的"甩动"场景速度被
钳为 0，判定偏保守，属可接受取舍。

### 2.10 L3 转场（`transition.ts`）与 `useRootScrollLock`——无问题

转场目标值结构与 motion 解耦（便于测试），`shouldParallaxUnderlay` 只对 slideRight 视差。
`useRootScrollLock` 引用计数 + body fixed（iOS）/class（Android）双策略 + jsdom 降级，
实现严谨。建议补充：该锁目前只由 HomeScreen 以 `topKey !== "home"` 驱动，语义是
"非根页时锁根滚动"；overlay 打开时（topKey 仍为 home）不锁——依赖 SnapSheet 自身处理
滚动穿透，当前可用，但规则分散在两处。

### 2.11 L4 数据层（`query/PageQueryProvider.tsx` / `store/PageStoreScope.tsx`）——方向正确

- `usePageQuery`：queryKey `[...entry.key(params), pageKey, dataKey]` 参数化 + phase
  paused→active 时按 `refetchOnResume` 策略重取，实现"返回时刷新"声明化，好评。
- `PageStoreScope`：`useState(createStore)` 惰性建店、随实例卸载 GC，简洁。
  但 `usePageStore(selector)` 的 state 类型是 `Record<string, unknown>`，selector 手动断言
  每个字段（`s.draft as string`），类型安全弱于 zustand 惯例（泛型 store 工厂
  `createStore<T>()` 可以在 definePage 的 `store` 声明处携带类型），可演进。
- `getQueryClient()` 模块级单例：AppShell 与 store（todo/diary）跨 React 访问需要它，
  取舍合理；但单例无重置入口，测试间需手动 `clear()`（文档已提醒），HMR 下缓存跨代残留，
  建议增加 `__resetQueryClientForTest()`。

### 2.12 L5 开发者 hooks（`hooks.ts`）——最小可用

`usePage<P>()` 的泛型由调用方手动传（`usePage<TodoDetailParams>()`），页面定义处的
schema 类型信息没有传导到组件（definePage 的 component 与 params 类型是断开的）。
文档说"迁移期由 pages.ts 的类型映射统一收窄"，但 `pages.ts` 现在只是 glob 副作用入口，
**该类型映射尚不存在**——每处 `usePage<XXX>()` 手写一遍参数类型，与 schema 漂移无编译期
防护（例如 `contentDetail.page.tsx` 手写 `ContentDetailParams` 与 schema 各自维护）。
建议：`definePage` 返回带类型的组件工厂，或提供 `defineTypedPage` 让 `usePage()` 从
context 取到 `InferFields<F>`（把泛型存进 component 的 props/context 类型上）。

### 2.13 app 层（`AppShell.tsx` / `AppContext.ts` / `HomeScreen.tsx`）——瘦身显著，过渡态明显

- AppShell 从 1465 行瘦身（UPDATE_LOG 口径），职责收敛为"Provider 组装 + 全局数据编排 +
  跨页面操作"，quickCapture 控制器下沉（`useQuickCaptureController` 注释"原先寄生在 AppShell
  的约 300 行逻辑下沉"，验证属实）。
- `AppContextValue` 仍承载 15+ 个命令式 handler（handleSyncUpload/handleResourceSyncStart/
  handleDeleteCard...），本质是把旧的 props drilling 换成 context drilling——SettingsPage
  不再收 21 个 props 改为页面自取，是进步；但"操作定义在 AppShell、页面经 context 取用"
  的模式仍是中心化编排。长期方向：同步/资源操作收敛进独立 service hooks（如
  `useSyncActions()`），AppContext 只留真正的全局只读态 + presentError。
- Provider 嵌套 11 层（AntdApp→KeyboardViewport→Editor→4×Deps→Dnd→PageQuery→AppContext→
  Router），可读性一般但组织有序，各 DepsProvider 是 @tau/shared 的接口注入，可接受。
- `useEffect` 依赖数组缺 `handleCheckVersions` 等的 `appContextValue` memo 手列 17 项，
  `useMemoizedFn` 本身引用稳定，可直接依赖整组或拆分 context（轻微）。
- HomeScreen 以 `rootContent` 常驻渲染：root 页也走 Activity（visible/deeper），返回根页时
  不重渲染内容（保活语义正确）。`isPreviewOpen` 用 `overlays.some` 判定，但 overlay 被
  更新 screen 盖住时仍为 true，语义应为"overlay 栈中有 preview 且当前可见"——现用途
  （传给 CardsPage）影响极小，提一句。

## 3. 已验证缺陷（附复现证据）

以下三个缺陷通过临时集成测试在 jsdom + 真实 RouterProvider/PageHost/OverlayHost 下复现
（测试代码见附录 A，跑完已删除）。

### D-1（P0）`popTo` 回退深度计算错误 —— 混栈时回退步数不对

**位置**：`RouterProvider.tsx` `navigator.popTo`：

```ts
const depth =
  before -
  preview.entries.length -
  (meta.layer === "overlay" ? 0 : overlaysRef.current.entries.length);
```

**根因**：history 链中每条记录对应一次 push（screen 与 overlay 交织），从栈深 D1 回到
栈深 D2 需要 `go(-(D1-D2))`，即 `depth = 当前总深度 − 目标态总深度`。而公式对两个分支
各错一个方向：

- 目标层是 **screen**：目标态 = `preview.entries`（screens 截断）+ overlays 清空（overlay
  必在目标 screen 之上，已被弹掉）。正确 `depth = before − preview.length`；公式额外减了
  `overlays.length` → **回退步数不足，中间页残留**。
- 目标层是 **overlay**：目标态 = screens 全保留 + overlay 截到目标。正确
  `depth = before − screens.length − preview.length`；公式漏减 `screens.length` →
  **回退步数过多，连深层 screen 一起误弹**。

**复现 1a（screen 目标）**：`screens=[home,a,b,c] overlays=[ox]`，`popTo("a")` 期望
`screens=[home,a]`，实测 `screens=[home,a,b] overlays=[]` —— b 残留，用户"回到 a"停在 b。

**复现 1b（overlay 目标）**：`screens=[home,a,c] overlays=[ox]`，`popTo("ox")` 期望
`screens=[home,a,c] overlays=[ox]`（ox 已是 overlay 栈顶，最多只应弹掉其上的 c），实测
`screens=[home] overlays=[]` —— ox、a、c 全部被弹掉，直接回到根页。

**附带发现**：`popToKey` 只在"目标是非栈顶实例"时定位（`index < length-1`），目标恰为该层
栈顶时返回原栈。叠加错误公式后即复现 1b 的灾难性回退。另外若目标是**被 overlay 盖住的
screen 栈顶**（`screens=[home,b] overlays=[X]`，`popTo("B")`），preview 不变、depth=0、
静默无动作——"弹到 B 露出它"的语义未被覆盖，建议明确并测试。

**修复建议**：

```ts
popTo: key => {
  const meta = getPageMeta(key);
  if (!meta) return;
  const screensNow = screensRef.current.entries;
  const overlaysNow = overlaysRef.current.entries;
  let targetTotal: number;
  if (meta.layer === "overlay") {
    const idx = findLastIndex(overlaysNow, e => e.key === key);
    if (idx < 0) return;
    // 其上 createdAt 更晚的 screen 也必须弹掉（否则浮层不可见）
    const keepScreens = screensNow.filter(s => s.createdAt <= overlaysNow[idx].createdAt).length;
    targetTotal = keepScreens + (idx + 1);
  } else {
    const idx = findLastIndex(screensNow, e => e.key === key);
    if (idx < 0) return;
    targetTotal = idx + 1; // overlays 一律清空
  }
  const depth = totalDepth() - targetTotal;
  if (depth > 0) void historyBack("code", depth);
};
```

并补齐集成测试：screen 目标含 overlay、overlay 目标含覆盖 screen、目标即栈顶、目标不存在
四个用例。

### D-2（P0）`replace` 的 history 语义错误 —— 被替换页"复活"

**位置**：`RouterProvider.tsx` `navigator.replace` 末尾 `historyModeRef.current = "push"`。

**根因**：replace 替换栈顶后，浏览器历史里被替换页的快照记录仍在（replace 动作却做了
pushState），返回时 popstate 恢复出被替换的页面。文件顶部注释"增长/替换动作直接 setState +
pushState/replaceState"表明本意是 replace 用 replaceState，且 `HistoryWriteMode` 已含
`"replace"` 分支（栈变化 effect 中 `else replaceHistoryState(state)`），只是 replace 动作
设错了 mode。

**复现**：`push("a") → replace("b") → goBack("ui")`，栈变为 `screens=[home,a]` —— 已被
替换掉的 a 页复活。

**修复**：`historyModeRef.current = "replace"`（一行）。补集成测试：replace 后返回应回到
replace 之前的上一页（home），且 `history.length` 不增长。

### D-3（P1）`onInit/onDestroy` 并非"仅一次" —— Activity hidden 卸载 effect

**位置**：`pageLifecycle.tsx` 存在级 effect + `PageHost` 的 `<Activity mode="hidden">`
（surface === "deeper" 时）。

**复现**：`push a → push b → push c`，事件流实测 `["A:init","B:init","A:destroy","C:init"]`
—— a 被压入第三层（deeper）时 `A:destroy` 触发；随后返回 `c→b` 时 a 的 effect 重挂，
`A:init` 将再次触发。

**影响**：

1. 文档《移动端页面栈与返回策略.md》生命周期表格"onInit/onDestroy：实例创建/pop 销毁
   （keep-alive 下仅一次）"与运行时行为不符——**这是事实性错误**；
2. 业务方若在 `onDestroy` 里做"离开页面清理"（如上报、落盘），会在页面仅被压深时误触发；
3. 反过来，页面组件内一切 `useEffect`（订阅、定时器、事件监听）在压深时都会被卸载、
   回浅时重挂。文档"常见陷阱"里只针对 `usePageQuery` 提了一句，应升级为通用约定。

**建议**：短期先修文档与注释（把 onInit/onDestroy 描述改为"组件可见性挂载/卸载"，
并给出与 phase 的真值表）；中期由 PageHost 基于栈 entries 增删显式分发真正的
存在级事件（例如在 context 中增加 `existenceSeq`，仅当 entry 进入/离开 entries 数组时递增）。

### D-4（P1）`keepAlive: "data" / "fresh"` 未实现

**位置**：`PageHost.tsx`（LRU effect 只读 `=== "keep"`；PageLayer 无 keepAlive 分支）、
`OverlayHost.tsx`（同样未读取）。

**证据**：全仓库 `keepAlive` 的读取点仅 `PageHost.tsx:240` 一处（LRU 候选过滤）；
渲染层对所有页面一律 `<Activity>` 保活。声明 `"data"`（文档承诺"pop 即卸载组件；数据留在
query 缓存"）或 `"fresh"`（"每次全新"）的页面实际仍会保活。

**当前影响**：所有 11 个页面均使用默认 `"keep"`，未暴露；但这是 API 协议已发布、实现缺失
的缺口（同类问题：overlay 的 `transition` 与 `presentation` 字段同样无消费方）。
**建议**：要么在 PageLayer 按 keepAlive 分支（`"data"/"fresh"` 不渲染 Activity、直接条件
卸载），要么先从 `PageMeta`/文档中摘除未实现字段（YAGNI），二选一保持承诺与实现一致。

## 4. 高风险设计问题（推理充分、未动态复现）

### D-5（P1）手势提交后守卫拒绝，页面无回弹

`gesture.ts` `finish()`：达到提交阈值后先播放"飞出"动画再调 `onBack()`；
`onBack → goBack("gesture") → historyBack` 异步询问 `useBackHandler`/`usePageGuard`/
`canLeave`，任一拒绝则栈不变——但动画已把 active 页移到 x:100%，无回弹，界面停留在
下层页面之上（栈顶不可见）。当前业务层零守卫（grep 证实 `canLeave/usePageGuard` 无使用），
所以**现在不会发生**；一旦某页接入守卫（quickCapture 就是天然候选，见 D-11），手势路径
即触发。修复：提交前先同步/异步询问守卫，或 `onBack` 返回 Promise<boolean> 拒绝时
`springBack()`。

### D-6（P1）single overlay 重 push 不刷新 createdAt → 浮层"打不开"

`stackMachine.pushEntry` 去重复用保留原 `createdAt`；`OverlayHost.isActive` 要求
`entry.createdAt > topScreenCreatedAt`。组合场景：overlay X(t1) 被 screen D(t2) 盖住
（X paused 但保留），此时再 `push("X")`（如换一组 params）——X 移到 overlay 栈顶、params
已更新，但 `t1 < t2`，isActive=false，**点击无反应且无报错**。当前 UI 无该路径（preview
入口只在 home/search，其上无下钻），属潜伏缺陷。修复：`pushEntry` 复用时刷新 `createdAt`
（screen 层 createdAt 不参与任何可见性判定，统一刷新安全）。

### D-7（P1）settle 先于守卫写入，拒绝时残留

`pop(result)/finish/cancel` 均先 `settlesRef.set(target.id, ...)` 再 `historyBack("code")`；
若守卫拒绝，栈不变、settle 残留。之后该页面被**任何方式**真正弹掉时（包括无 result 的
手势返回），`settleResults` 会把当时的旧 result resolve 给 caller——`pushForResult` 的
调用方收到一次"已经被取消过"的结果。低概率但语义错。修复：settle 的写入移到守卫通过
之后（`historyBack` 返回是否执行了回退，或把 settle 作为参数传入 historyBack 在 go(-n)
前落账）。

### D-8（P2）`historyBack` 降级分支是 no-op

`window.history.length <= 1` 时读**当前** `history.state` 并 `restoreStack` —— 当前 state
即当前栈快照，恢复结果与现状相同，pop 无效果。该分支本意是"测试/降级环境无历史可驱退，
直接按快照恢复"，但恢复源选错（应使用"上一条记录"的快照，而该环境没有）。jsdom 中因为
push 后 length 增长，测试都走 `go(-1)` 分支，此降级分支实际只在"挂载后从未 push 就 pop"
（根页 pop，`totalDepth()<=1` 已拦截）或极端 WebView 下触达，影响面小。建议：改注释说明
"该分支按当前快照恢复（等同 no-op），仅保持状态一致性"，或直接移除。

### D-9（P2）Tauri `onCloseRequested` 拦截关闭 → 桌面端窗口无法关闭

`getCurrentWindow().onCloseRequested(event => { event.preventDefault(); goBack("android"); })`
——用户点窗口 X：栈深>1 时变成"返回上一页"；根页时走"双击缩小应用"（minimize）。
**窗口永远无法真正关闭**（除非任务管理器）。移动端 App 生命周期模型下"返回键代替关闭"
是合理的，但 Android 实体返回键已有 `onBackButtonPress`，此处的 close 拦截建议改为：
栈深>1 时 goBack、根页时放行 `event.none()` 真正关闭（桌面行为）；或至少在文档记录这是
刻意的产品决策。

### D-10（P2）LRU 淘汰静默丢页面私有 store / UI 态

`evicted` 时卸载 `PageStoreScope`（页面 store 销毁）与组件 state；注释只承诺"数据仍在
query 缓存"。栈深超过 10（root 之外 keepAlive keep 的页面）后最久未访问页被逐出，返回
该页时 store 重置（`definePage({ store })` 工厂重跑）。取舍可以接受，但：

1. `MAX_LIVE_SCREENS = 10` 与"用户连续下钻 todoDetail（multi）"场景的距离不远，建议在
   文档标注该常量与行为；
2. `collectKeepAliveEvictionCandidates` 的 `protectedIds`（top/underlay）正确，但
   popstate 恢复后 `lastActiveAt` 全部刷新为 now（见 2.2），LRU 顺序失真可能逐出"其实
   刚用过"的页面。

### D-11（P2）quickCapture 未接返回守卫，系统返回绕过 flush

关闭路径有两条：UI 关闭按钮 → `requestClose()`（flush 队列→空内容删卡→复位）→ goBack；
系统返回键/浏览器返回 → `goBack("android"/"popstate")` → 无 backHandler/守卫 → **直接弹栈**。
防抖（600ms）内未落库的内容：编辑器 onChange 每次都 `writeQuickCaptureDraft`（localStorage
兜底，数据不丢），但卡片未创建，下次打开需手动点"恢复草稿"——体验断裂。修复建议
（一石二鸟）：quickCapture 页注册 `useBackHandler(() => { void requestCloseRef.current().then(closed => closed && navigator.goBack("ui")); return true; })`，
把系统返回也收进 flush 流程；顺带验证 D-5 的手势路径（quickCapture 是 overlay，
`useEdgeBackGesture` 在 overlay 存在时 disabled，手势路径不涉及）。

### D-12（P2）OverlayHost 无退出动画

外层 `AnimatePresence` 的子树无 motion 组件，overlay 弹出栈即刻消失（无 sheet 下滑过渡）。
要么删除 AnimatePresence（诚实），要么给 overlay 容器包一层 `motion.div` 按 `isActive`/
卸载驱动 exit——与 D-4 的 `transition/presentation` 实现一并考虑。

## 5. 中低风险与规范性问题

1. **router → components/toast 的反向依赖**：`RouterProvider.tsx` `import { toast as uiToast }
from "../components/toast"`。框架层依赖业务组件层，破坏分层方向（L3 依赖了组件库层）。
   建议：`RouterProvider` 接受 `onRootBackHint?: (text: string) => void` prop 由 AppShell
   注入 toast，router 保持零业务依赖。
2. **`navigator.popTo` 的 `popToKey(..., Date.now())` 预览调用**：纯函数无副作用，但语义上
   "为算长度而跑一遍迁移"可读性一般；建议 stackMachine 增加 `countToKey(stack, key): number`
   语义化辅助函数（与 D-1 修复一起做）。
3. **`PageLayer` 的 zIndex 体系不统一**：screen 层 inline `zIndex = totalLayers + 2`（动态小
   数值），overlay/弹层组件用 tailwind 固定值（SnapSheet z-50、ActionSheet z-70/80、Toast
   z-80、DevTools 9999）。两套体系靠"screen 栈永远达不到 48 深"这一隐式假设共存。建议统一
   常量表（如 `Z.SCREEN_BASE/OVERLAY/TOAST/DEVTOOLS`），screen 层用 `Z.SCREEN_BASE + index`。
4. **`usePageQuery` 的 `refetchOnResume` 在 disabled query 上仍会 refetch**：`enabled:false`
   的 entry，phase 恢复时 `query.refetch()` 会绕过 enabled 发起请求。建议 effect 内补
   `if (!query.isEnabled) return`（或以 enabled 函数重算）。当前无 enabled 声明使用方，未暴露。
5. **`PageInstanceContextValue` 每渲染新建**：`PageHost`/`OverlayHost` 直接内联构造
   instanceValue，栈内每个存活页面在每次栈变化时重渲染所有 context 消费者。当前页面数
   少无感；建议 `useMemo` 按 `[entry.id, phase, transitionSeq, navigator]` 记忆化。
6. **hooks 调用位置不规范**：`PageLayer` 中 `navigator: useRouterContext().navigator` 位于
   JSX 对象字面量中间（约 179 行）。合法（无条件分支）但易被误改坏，建议上移组件顶部。
7. **`seedRootStack` 的 `params: {}` 未走 schema**：root 页 schema 为空无碍；若未来根页
   带必填 params 会静默绕过校验，建议复用 `sanitizePageParams` 防御。
8. **`historyBack` 中 `window.history?.state`**：`typeof window === "undefined"` 已在前一
   条件短路，此处 `?.` 冗余（极小）。
9. **类型重复**：`RouterProvider.PreloadableDataEntry` 与 `definePage.PageDataEntry` 结构
   重复（preload 手写了一份窄化版）；根因是 `PageDefinition.data` 擦除泛型（见 2.4）。
   建议 `PageDefinition` 携带 `data` 的已擦除但完整类型（含 refetchOnResume），preload 复用。
10. **`useCardsQuery.refreshCards` 兼容层返回旧值**：`invalidateQueries` / 条件切换分支
    `return cards`（触发前的闭包值），与旧实现"返回本次拉取结果"不同。现调用方
    （CardsPage/refreshCardsSafe）不消费返回值的具体内容，无实际影响；若未来有调用方依赖
    返回值会拿到过期数据，建议返回 Promise 化的最新缓存或 void。
11. **`moduleNavigator` 渲染期赋值**：并发渲染被丢弃时模块仍被赋值（对象内容一致，无害）。
    移入 `useEffect` 更符合 React 语义；注意 `getNavigator()` 的消费者都在挂载后调用，
    effect 时序（子组件 effect 先于父组件）需验证——页面组件 effect 里调用是安全的，
    但 `AppShell` 的事件回调（handleDeleteCard）在挂载后任意时刻调用也安全。改动低风险。
12. **useTodoStore / useDiaryStore 成为 query 缓存的镜像**：读路径 `fetchQuery` 后 `set`
    进 zustand，两处状态源（query cache + store state），mutation 后靠
    `invalidateQueries + 重新 fetchQuery` 对齐，存在短暂不一致窗口。这是合理的过渡态
    （文档"数据层现状"已如实描述），长期建议组件侧直接 `useQuery` 订阅、store 只留
    UI 态与编排——与 router 数据层（usePageQuery）的设计意图对齐。
13. **空目录残留**：`src/app/__tests__/`（previewOverlayUi.test.ts 删除后）为空目录，
    建议 `git clean` 或删除。
14. **`cardPreview.page.tsx` 的 `p.cardId as number` 冗余断言**：schema 推导下 `p.cardId`
    已是 number；同类手写 `as` 会掩盖未来 schema 改动导致的类型不匹配，建议删除断言
    （tsc 可通过即证明安全）。

## 6. 工程架构与可扩展性评估

### 6.1 依赖方向

```
app/AppShell ─┬─→ router（Provider/Host/navigator）   ✅
              ├─→ features/*（页面组件）              ✅
              └─→ hooks/services                      ✅
features/* ─┬─→ router（definePage/usePage/...）      ✅（基础设施向下依赖）
            └─→ services/tauri、@tau/*               ✅
router ─┬─→ react / motion / zustand / @tanstack     ✅
```

### 6.3 双栈 + createdAt 可见性模型的评估

screen/overlay 分栈 + "overlay 仅在最新 screen 之上可见"是对"浮层下钻"交互的准确建模，
比旧的 previewOverlayUi 快照机制优雅得多。但该模型有一条隐式公理：**overlay 的 createdAt
必须反映"最后一次被打开"的时间**——D-6 正是这条公理被 `pushEntry` 去重逻辑破坏的例子。
建议在 `stackMachine`/`OverlayHost` 注释中把这个不变式（invariant）写明，并加一条单测
固定行为（"single overlay 重新 push 后必须可见"）。

## 附录 A：缺陷复现步骤

临时测试文件 `src/router/__tests__/audit-probe.test.tsx`（已删除）在 jsdom 下挂载真实的
`RouterProvider + PageHost + OverlayHost`，注册 home/a/b/c（multi screen）与 ox（multi
overlay）页面，核心工具：

```tsx
function stackKeys(): string {
  const screens = getNavigator()
    .getScreenStack()
    .entries.map(e => e.key)
    .join(",");
  const overlays = getNavigator()
    .getOverlayStack()
    .entries.map(e => e.key)
    .join(",");
  return `screens=[${screens}] overlays=[${overlays}]`;
}
```

**D-1 复现 1a**：`push a → push b → push ox → push c`（得 `screens=[home,a,b,c]
overlays=[ox]`）→ `popTo("a")` → 轮询后打印 `screens=[home,a,b] overlays=[]`（期望
`screens=[home,a]`）。

**D-1 复现 1b**：`push a → push ox → push c`（得 `screens=[home,a,c] overlays=[ox]`）→
`popTo("ox")` → 打印 `screens=[home] overlays=[]`（期望 ox 保留在 overlay 栈顶）。

**D-2 复现**：`push a → replace b`（栈 `[home,b]`）→ `goBack("ui")` → 打印
`screens=[home,a]`（被替换的 a 复活；期望 `[home]`）。

**D-3 复现**：页面组件挂 `usePageLifecycle({ onInit: () => events.push("A:init"),
onDestroy: () => events.push("A:destroy") })`；`push a → push b` 事件流
`["A:init","B:init"]`（a 为 underlay，effect 未卸载）；再 `push c`（a 变 deeper/hidden）
事件流变为 `["A:init","B:init","A:destroy","C:init"]` —— `A:destroy` 在页面仍在栈内时触发。

> 注意：D-1/D-2 的复现依赖 jsdom `window.history`（pushState 会使 `history.length` 增长，
> `historyBack` 走 `go(-n)` 分支），与浏览器/Tauri WebView 行为一致，结论可迁移。
