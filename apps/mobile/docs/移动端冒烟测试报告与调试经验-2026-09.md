## 已修复的 P0 缺陷（2 个）

### P0-1 首屏渲染崩溃：QueryClientProvider 挂载在消费方内部

**现象**：应用启动白屏，报 `Error: No QueryClient set, use QueryClientProvider to set one`。

**根因**：`AppShell` 组件函数体顶层调用 `useCardsQuery()`（内部 `useQueryClient()`），
而 `PageQueryProvider`（内含 `QueryClientProvider`）挂在 AppShell 自己的 render 输出
内部——组件自身位于 Provider 之外。属于"数据层接入 query 缓存"重写时的 Provider 层级疏漏。

**修复**：函数体抽为 `AppShellInner`，外层用 `PageQueryProvider` 包裹后再渲染
（`src/app/AppShell.tsx`）。

**预防**：凡是"组件顶层消费 Context/hook 且 Provider 由该组件自己提供"的写法都必然踩坑，
Provider 必须先于消费方挂载。

### P0-2 页面注册表为空：vite 7 中 `../` 开头的 glob 模式失效

**现象**：console 报 `[pages] 未发现任何页面定义文件`、`[router] 根页 home 未注册`；
主界面能显示（rootContent 直接渲染，不查注册表），但**所有 push 导航静默失效**——
任务/日记/设置/搜索全部点不开，RouterDevTools 悬浮球显示 `⌗ 0`（栈里连 root 都没有）。

**根因**：`src/pages.ts` 使用
`import.meta.glob("../features/**/pages/*.page.{ts,tsx}", { eager: true })`。
经探针文件对比验证：**vite 7.3 中 `../` 开头的 glob 模式匹配 0 个文件**（无论 `**`
还是 `*`），`/src/...` 绝对路径与正确的 `./...` 相对路径均正常（10 个页面全命中）。

**修复**：改为 `/src/features/**/pages/*.page.{ts,tsx}`（`src/pages.ts`），dev 与
production 构建均验证生效。

**教训**：

- `import.meta.glob` 返回空对象**不会报任何错**，靠"注册数为 0 时 console.warn"这类
  自检兜底才能发现（本次正是这个警告立了功，值得保留并考虑升级为 dev 模式 throw）；
- vitest 对 `import.meta.glob` 的路径解析行为与 vite dev server 不同——**单测全绿不代表
  dev 构建可用**，入口装配层（pages.ts / AppShell）是单测盲区，必须真机冒烟覆盖。

### 归因校准记录：`sync_check_versions` 不背"首启慢"的锅

排查过程中一度将首启卡顿归因于同步检查超时（前端 `SYNC_CHECK_TIMEOUT_MS = 35s`），
深入代码与实测后修正：

- `sync_check_versions` 只读远端版本文件 `database_<库名>.json` 的 `version` 字段与本地
  比对，用于设置页展示本地/远端版本、提示上传或下载，**只读不写**；
- 全新安装默认配置为 `sync.active = "aliOSS"` 且凭证全空，
  `parse_sync_provider` 在发起任何网络请求之前就立即返回 `SYNC_CONFIG_MISSING`
  （毫秒级），前端 `catch` 后放行——**不会挂起**；
- 两个超时常量（前端 35s / Rust `SYNC_CHECK_TIMEOUT_SECS = 30`）仅对**已配置同步**时的
  真实网络请求生效；
- 实测首启耗时分布（独立 APK、logcat 时间戳）：Rust 侧建库+索引迁移 ~2s，页面资源加载
  DCL ~1.2s，其余为 debug 前端包（36MB assets）解析执行与首屏渲染。

## 调试方法论沉淀

### 1. WebView 应用的 CDP 直连诊断（强烈推荐）

`adb shell` + screencap 只能看表象，CDP 才能看真相。dev 与 debug 构建均可连：

```bash
ADB=~/Library/Android/sdk/platform-tools/adb
PID=$($ADB shell pidof com.txiong.tau_mobile | tr -d '\r')
$ADB forward tcp:9222 localabstract:webview_devtools_remote_$PID
curl -s http://127.0.0.1:9222/json   # 取 webSocketDebuggerUrl，用 ws 库直连
```

高频用法（Runtime.evaluate）：

- `document.body.innerText` / `#root` innerHTML —— DOM 真实状态（**innerText 只含可见
  文本，元素被隐藏时查 outerHTML**）；
- 直接 `window.__TAURI_INTERNALS__.invoke("bootstrap_app")` —— 绕过 UI 测 Rust 命令
  耗时与返回值，快速区分前端/后端问题；
- 遍历 `document.querySelectorAll("button")` 取 `getBoundingClientRect()` 中心坐标 ×
  `devicePixelRatio` 换算物理坐标，再 `adb shell input tap` —— 比"看截图估坐标"可靠得多。

**注意**：CDP attach 本身可能影响被测进程（S1 的 3/4 次死亡紧随 attach 之后），对内存
敏感场景要用"无 CDP 的对照轮"交叉验证。

### 2. 截图分析的坑：帧 ≠ 真相

`screencap` 抓的是合成帧。本次多次出现"截图显示 A、DOM 实际是 B"（过渡动画帧、首帧
合成缺失、渲染进程卡死时的最后合成帧）。**图像分析结论必须与 DOM/console 交叉印证**，
单独采信任何一侧都会误判。

### 3. 环境变量先于代码归因

两次"应用死亡"最终都与代码无关：第一次是模拟器存储不足（`INSTALL_FAILED_INSUFFICIENT_
STORAGE`，452MB debug APK），第二次是 2GB 内存被 lmk 连环击杀（渲染进程 OOM 2.7GB）。
模拟器上跑 debug 构建的准备工作：

- `adb shell df -h /data` 确认空间（不足时卸旧包 + `pm trim-caches`）；
- 用 `-memory 4096` 启动模拟器（默认 2GB 对 452MB debug APK + WebView 太小）；
- 模拟器是共享环境，Google 系后台应用也在抢内存，"间歇性死亡"先查
  `logcat -b all | grep -iE "lowmemorykiller|Render process"`。

### 4. 归因要用数据闭环，警惕"常数巧合"

"卡了 ~35 秒"与代码里 `SYNC_CHECK_TIMEOUT_MS = 35_000` 的巧合极具迷惑性。最终靠
logcat 时间戳把启动耗时拆解到各阶段（Rust 2s / DCL 1.2s / 其余为前端执行）才完成
修正。**看到"数值对得上"先当作假设，用分阶段计时验证。**

### 5. 对照实验设计：dev 依赖剥离

dev 模式混入了 vite HMR、CDP、React DevTools 等变量。排查"疑似应用 bug"时，构建
`build:android:test` 独立 APK 跑同一操作序列，是一次性剥离全部 dev 工具链变量的最干净
对照实验。

## 冒烟测试操作手册（可复用）

1. **静态**：`pnpm --filter mobile exec tsc --noEmit` + `pnpm --filter mobile test`；
2. **部署**：`pnpm dev:android`（迭代期）或 `build:android:test` 独立 APK（终验）；
3. **启动自检**：console 无 `[pages]`/`[router]` 警告；RouterDevTools 悬浮球 `⌗ ≥ 1`；
4. **核心链路**（每步确认进程存活 + 截图留档）：
   - 卡片首页列表/空状态；
   - 页面栈：任务/日记/设置 push → root 层交互隔离（底部工具栏在非根页应失效）→
     系统返回键逐层 pop；
   - 待办：创建 → 完成切换 → 列表实时刷新（query 订阅化 store）；
   - 日记：月历 → SnapSheet → Slate 编辑器输入 → 返回后"最近记录"更新
     （验证 refetchOnResume）；
   - 设置：渲染 + 主题切换（深色）；
   - 卡片：快速捕获输入 → 保存 → 列表更新。
5. **验收基线**（独立 APK，4GB 模拟器）：全新安装首启主界面 ~15s、二次启动 ~3s、
   连续操作 12 分钟无崩溃。
