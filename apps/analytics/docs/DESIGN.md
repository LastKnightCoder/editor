# Tau 应用版本与下载统计

## 范围

统计只回答两个问题：用户使用哪些应用版本，以及通过官网下载入口发起了多少次安装包下载。不采集启动耗时、使用时长、页面访问、会话、崩溃和功能行为；后台不提供这些指标、留存或事件明细。

独立 Worker `tau-analytics`、D1 `tau-analytics` 和同域管理后台位于 `analytics.taunote.app`。安装包仍由 R2 桶 `tau-release` 的原下载域名分发。插件门户数据库、用户主动提交的反馈与本机性能诊断不属于本统计服务，不随本次收敛移除。

## 版本上报

`POST /v1/versions` 仅接收不超过 2KiB 的 JSON：

```json
{
  "schema_version": 1,
  "product": "tau-desktop",
  "environment": "production",
  "installation_id": "954953c5-8e48-45b7-9b6a-5222f33c7702",
  "app_version": "0.59.2",
  "reported_at": "2026-10-24T12:00:00.000Z"
}
```

环境只允许 production/development；安装 ID 是随机 UUID，不是硬件标识。版本须为有效版本号，时间只接受七天内至未来五分钟的 UTC 观测。未知字段直接拒绝，不收集系统、架构、语言、页面、正文或错误堆栈。限流在解析正文前执行，生产绑定缺失时拒绝放行。

回执 `data` 回显 `app_version`、`reported_at`；数据库提交后才确认。以 `(product, environment, day, installation_id)` 为主键，单条 UPSERT 仅允许更晚的观测覆盖。重试与乱序补报不增加安装数，不把当前时间或版本补造到旧观测上。

旧 `POST /v1/events/batch` 已退役，返回 410，不读取请求正文或访问数据库。没有旧事件解析或投影兼容层。尚未升级的旧二进制仍可能发送请求，但服务端不再接收这些行为；需要发布并安装新客户端才能停止旧端发送。

## 桌面端

版本模块随 BACKGROUND 启动，无渲染端 IPC 和页面接线。正式包默认启用，开发构建默认停用；显式开发上报使用 `TAU_TELEMETRY_DEBUG=1`，全局停用使用 `TAU_TELEMETRY_DISABLED=1`。调试地址 `TAU_ANALYTICS_ENDPOINT` 需指向版本接口。

同一安装每天首次启动上报；当天版本变化重新上报，不持续发送心跳。失败仅按 20 秒、60 秒、300 秒补报，之后等下次启动。版本客户端合并并发请求，先原子保存状态再发送，确认落盘失败仍保留待补报观测；服务器按观测时间幂等处理。

本机格式 2 状态只包含安装 ID、已确认和待确认版本，文件权限 0600，通过临时文件 rename 原子替换。当前版本将原 `analytics.json` 格式 1 状态转换为格式 2，仅保留合法安装 ID、丢弃全部旧行为队列；转换失败停止上报，不覆盖为新安装。不再读取更早的 `telemetry.json`。损坏或未来格式明确报错，不假造成功。

## 下载口径

`GET /v1/downloads/:filename?channel=website` 仅允许正式 Tau 安装包名，通过 R2 HEAD 验证存在后 302 跳转至固定下载域名。不代理大文件，不修改自动更新源。

统计为“下载发起”，不是下载完成、安装成功或真实人数。同一天、同安装包按服务端秘密、上海日期、IP 与 UA 的摘要近似去重；不保存原始 IP。HEAD、Range、预取、明显机器人、缺少真实 IP 或摘要秘密时不计数；统计数据库故障不阻断跳转。自动更新与 R2 直链不计入官网指标。保留已有下载维度与去重存储结构，不重新解释历史下载数。

## 数据模型与历史边界

| 表                    | 当前用途                                         | 保留范围 |
| --------------------- | ------------------------------------------------ | -------- |
| installation_versions | 每个安装每天的最后一次版本观测，仅保存版本与时间 | 400 天   |
| download_receipts     | 下载短期摘要去重                                 | 7 天     |
| daily_downloads       | 日期、安装包、渠道等下载聚合                     | 400 天   |

追加迁移 `0003_minimal_versions.sql` 从已有 daily_activity 回填版本观测，并移除旧事件投影触发器；不修改已执行的迁移、不主动删除既有行为数据。历史 events/sessions/daily_activity/daily_events 不再接收业务写入，继续按原定 30/400 天清理，installations 历史表冻结保留。它们不参与当前管理查询，不恢复旧采集逻辑。

版本分布对所选日期内的每个安装只取最后一次观测，不能直接相加每日版本数；升级过的安装在窗口中只计最新观测版本。上报安装数不等于经过验证的真实人数。日期固定上海自然日，时间存 UTC 毫秒，正式与开发环境隔离。

## 管理后台

管理员使用高熵凭据交换 HttpOnly/Secure/SameSite=Strict Cookie，或用 bearer 做运维读取；凭据不进 URL、前端包或浏览器持久存储。后台仅“应用版本”和“下载统计”两个页签，react-query 管理请求、刷新和错误，不回退模拟数据。

保留 `/v1/admin/overview`、`timeseries`、`breakdown`，指标版本为 2；维度仅 versions/downloads/channels。原 retention/events 查询和行为维度返回不存在或不支持。查询 product/environment/from/to，默认最近七天、最多九十天；版本以所选时间段的最新观测归组，下载显示所选时间段内的发起数。失败不显示为零。

## 部署与验证

顺序为：备份 D1 → 应用 0003 → 部署 Worker 与同域后台 → 运行独立 development 标识的远端验证 → 发布桌面新版。仅合并代码不会改变线上采集，旧安装包也不会因 Worker 更新自动替换自身代码。

远端验证只写独立测试安装及下载标记，finally 定向清理；不读取真实用户明细。历史触发器已退役，不能通过回退至旧行为采集 Worker 来恢复新协议；修复应基于最小版本上报实现向前发布。

本地验证覆盖版本去重、升级、乱序、迁移、正文边界、旧接口退役、认证、下载计数与故障不阻断下载、清理、客户端落盘和有界重试；同时执行类型检查和构建。视觉由用户验收。当前部署记录为 Workers Free，不新增付费专属 CPU 配置或订阅。
