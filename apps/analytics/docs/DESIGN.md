# Tau Analytics 第一版设计

## 1. 范围与决策

独立应用 `apps/analytics` 使用 Cloudflare Workers、独立 D1 数据库和同域静态管理后台。迁移桌面端现有六类埋点，增加 R2 安装包下载发起、省份分布、功能排行、趋势、留存与事件诊断。UI 使用现有 React、react-query、Tailwind 和 `@tau/themes` / `@tau/ui`。

安装包仍存 `tau-release` 桶的 `desktop/`，仍由 `https://dl.taunote.app/desktop` 分发。统计服务只 HEAD 校验对象与返回跳转，不代理大文件、不改自动更新源。不修改插件市场数据库。

新服务使用 `https://analytics.taunote.app`，不接管旧 Umami 域名；旧客户端升级前仍向旧服务上报。代码切换与云端部署分开，先发布新 API，再发布官网和桌面版本；确认旧版本退出后才人工停用旧服务。

## 2. 非破坏性扩展契约

1. `/v1` 的必填字段、字段含义、时间与去重口径固定；新增字段只能可选，客户端忽略未知响应字段。
2. 事件信封版本 `schema_version` 与业务事件版本 `event_version` 分开。改变既有事件含义必须追加事件版本，不能重解释旧数据；不兼容信封使用 `/v2`。
3. 事件规则在 `contracts/events.ts` 集中登记：事件名、版本、允许属性与类型。新增事件只追加规则；禁止开放任意属性收集笔记正文、路径等内容。
4. 原始事件与查询投影分离。新增分析优先增加独立查询模块；需要索引或新投影时追加 SQL 迁移与回填，不修改已经执行的迁移。
5. 指标口径另有 `metric_version`。改变已有指标时追加新指标/版本，不悄悄改变旧查询响应。
6. 新增分析能使用已保留的事实；从未采集的属性、过期明细不能事后恢复。新增属性需先发服务端规则，再发采集端；历史缺失显示未知，不推断填充。
7. 兼容性测试固定 v1 请求/响应、旧事件版本、新增可选字段、重试幂等与顺序迁移。独立数据库、产品/环境命名空间避免污染其他系统。

### 后续扩展的具体路径

- 已有事实的新分析，例如按应用版本分析启动耗时：追加查询模块和后台视图，使用已采集的 app_ready/startup_ms；不要求修改客户端或既有 overview 响应。超过明细保留窗口的分位数需要提前新增投影，不能从事件总数反推。
- 新业务行为，例如导出完成：在事件定义中追加新事件及允许属性，先部署服务端，再发布调用该事件的新客户端；旧六类事件和旧客户端请求保持原样工作。
- 新索引或投影：追加 `0002_*.sql` 等迁移，在保留范围内分批回填；先让旧代码可继续运行，再部署读取新投影的代码，不删除旧表或改写 0001。
- 已有事件语义变化：追加 `event_version` 对应规则，旧版本规则继续保留；查询按事件版本选择解释方式。已有指标计算方式变化则追加指标版本或新接口，保持旧指标可用。

这里保证的是已发布协议与统计口径的兼容，新增分析仍需相应实现、测试和部署；不把“可扩展”理解为自动支持未定义的所有分析。

## 3. 采集 API

`POST /v1/events/batch`：JSON 不超过 64KiB，1–50 个事件。信封包含 `schema_version: 1`、`product`、`environment`、`installation_id`、`events`。

每个事件包含 `event_id`、`session_id`、`name`、`event_version: 1`、`occurred_at`（UTC ISO）、`context`（app_version/os/arch/locale）和 `properties`。上下文在生成事件时冻结，不能在补报时改成当前应用版本。ID 是随机 UUID，不是硬件标识；安装实例与真实人数区分。

服务端增加 `received_at`、国家、省份编码与来源。地域来自 Worker `request.cf`，忽略客户端同名值。不保存原始 IP；地域表示补报时的网络出口，不能证明事件发生时或用户常住地。

响应 `data` 包含 `accepted: string[]`、`rejected: { index, event_id, code, retryable }[]` 和 `received_at`。accepted 包含已存在的事件，按 `(product, environment, event_id)` 去重；只有 D1 原子提交后才确认。批内坏事件独立拒绝，其他事件照常写入。未知事件/版本允许重试，不阻塞同批其他事件。过期、超界时间、非法属性为永久错误。

仅接受过去七天至未来五分钟的事件。正式/开发环境分开存储，管理后台默认 production；开发构建仍默认关闭采集。公开采集不能用客户端内置秘密证明可信来源，使用边缘限流、大小限制与服务端校验降低垃圾数据；管理员认证与采集完全分离。

## 4. 桌面迁移与可靠性

保留 `trackEvent(name, data)` IPC 调用方式与 BACKGROUND 模块归属；渲染端经 `withModule` 等待就绪。六类事件 session_start/app_ready/heartbeat/session_end/screen_view/crash 名称保留，另支持 feature_used。

离线队列改存带协议版本的 `analytics.json`，写入串行、临时文件 rename 原子替换，成功落盘后才能发送。旧 `telemetry.json` 只读取安装 ID；旧队列缺少会话、版本等原始上下文，不伪造后迁入新统计。旧文件保留供排查，一次迁移完成后新文件是唯一事实源。

每批按条确认并删除；确认后落盘失败时下次重发，由服务端幂等吸收。网络错误、429、5xx 指数退避；永久坏事件移除，未知事件保留重试。队列有条数与七天期限上限，异常落盘失败不能影响产品使用。退出事件立即请求保存与发送，不承诺 native 崩溃前异步写盘必定成功。

会话 UUID 每次启动重新生成；既有安装 ID 迁移保持稳定。`first_run=false` 的旧安装不能记成新安装。开发环境和退出门控必须测试。

## 5. R2 下载

`GET /v1/downloads/:filename?channel=website`：仅允许 Tau 正式安装包文件名，禁止任意 URL、路径穿越和更新元数据。通过 RELEASES 绑定 HEAD `desktop/:filename`，存在才 302 到固定下载域名；自身响应 no-store，R2 文件缓存不受影响。

下载不依赖统计数据库可用：数据库或摘要生成失败仍跳转，并记录不包含请求内容的故障标识。HEAD、Range、预取及明显机器人不计数。它统计“安装包下载发起”，不是下载完成或安装成功；自动更新仍直连 R2，不混入官网指标。

同一天、同安装包按短期摘要去重：服务端秘密 + 上海日期 + IP + UA，经 SHA-256 后只保存摘要，七天后清理。相同 NAT 出口与 UA 可能合并，代理变化可能重复，因此只称近似去重发起，不能称独立用户。缺少真实 IP 或摘要秘密时跳过计数，不保存可逆替代值。

channel 是短标识白名单格式，默认 direct；文件名提供版本、平台、可选架构，当前不含架构的文件标为 unknown，不猜测。

## 6. D1 数据模型与口径

| 表                | 职责                                      | 保留  |
| ----------------- | ----------------------------------------- | ----- |
| events            | 原始合法事件、时点上下文、事件版本、地域  | 30天  |
| installations     | 首次观测、最后观测、明确的首次启动时间    | 长期  |
| sessions          | 每个会话累计时长的最大确认值              | 400天 |
| daily_activity    | 每安装每天一行，准确跨日去重与留存        | 400天 |
| daily_events      | 日期/事件/业务键/版本/平台/地域的可加计数 | 400天 |
| download_receipts | 短期下载去重事实                          | 7天   |
| daily_downloads   | 下载版本/平台/渠道/地域的可加计数         | 400天 |

日期固定 Asia/Shanghai，时间戳存 UTC 毫秒；避免本地时区及 UTC 混算。原始插入和投影由 SQLite AFTER INSERT 触发器在同一事务维护，重试 INSERT OR IGNORE 不触发二次计数。时长取会话累计最大值，乱序心跳/退出不重复累加。

`0002_versioned_projections.sql` 将安装/时长的属性解释固定在已有 v1 生命周期事件；以后其他事件或新版本复用同名属性，不会自动改变当前指标。新版本需要显式追加对应投影解释，不能靠属性名碰巧相同就参与计算。

活跃安装按 daily_activity 的 installation_id 去重，月活不累加日活。省份按窗口内地区/安装去重，一个跨省安装可以出现于多个分组，各组之和不保证等于总活跃。前台时长表示窗口聚焦，不表示实际操作；按会话开始日归属，不宣称跨午夜精确分摊。

留存以明确 first_run=true 的 installed_at 为 cohort，N日留存分母排除尚未观察满 N 日的 cohort；旧安装首次接入只计首次观测，不混入新安装 cohort。原始明细清理不扣减聚合；定时分批清理，单次工作量有上限。

## 7. 管理查询与 UI

同域后台登录：管理员输入服务端随机高熵 token，交换带 HMAC 签名、短期有效的 HttpOnly/Secure/SameSite=Strict Cookie；token 不进入 URL、前端包或浏览器持久存储。接口支持 bearer 供运维使用。无配置时拒绝管理访问；生产只使用 HTTPS，登录与采集配置独立边缘限流。

接口 `/v1/admin/overview`、`timeseries`、`breakdown`、`retention`、`events` 使用统一 product/environment/from/to 查询，from/to 为上海自然日（含两端），默认最近7天、最多90天；分组维度与SQL表达式固定映射，不接受客户端SQL。响应保留 metadata：时区、指标版本、保留范围。

第一版简单 UI：筛选栏、概览卡、每日表格、功能/页面排行、省份/系统/版本分布、下载表、留存表、最近事件。react-query 管理请求、错误、刷新及过期登录；不使用模拟数据，不把请求失败展示成零。UI样式后续可单独替换，不改变 API。

## 8. 交付与验证

先完成本设计，再依次实现后端/投影与安全边界、客户端/官网迁移、后台和部署说明。验证包括类型检查、行为测试、真实 SQLite 事务/触发器、Worker本地 D1/R2 冒烟和构建。视觉验收由用户完成。

云端使用独立 D1 ID 与新的 Worker，自行备份后应用增量迁移。正式部署必须配置管理员 token、下载摘要秘密和域名；本地使用 .dev.vars（不入库）。不自动删除 Umami/Postgres，不迁移无法对齐口径的旧统计总量。

后续量大时再引入 Queues/R2 归档或独立分析库；采集端保持 v1，替换只发生在持久化/投影内部。D1 单库10GB限制通过保留策略、容量监控与后续存储演进应对，不承诺单库无限增长。
