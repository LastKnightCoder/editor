侧边栏响应式设计探索

背景：侧边栏现有 21 个条目 / 5 组，窗口较小（尤其矮窗口）时纵向溢出出现滚动条。下面四个方案都能在这个目录里打开对应 HTML 实际拖动浏览器边缘感受——每个页面右下角有实时尺寸读数。

2026-09-16 · 视觉与数据均对齐当前 navigation.ts（cream 主题实测色值）· 纯静态可离线打开

四个方案

PLAN 1 基础层

优雅滚动

Notion · Figma · Apple 系统设置

不减少入口：sticky 组头 + 上下边缘渐隐 + hover 细滚动条 + 底部设置钉住。把滚动做到无感。

零信息损失、成本最低矮窗口仍要滚动
 PLAN 2 推荐主方案

分组折叠

VS Code · Obsidian · Discord · Slack

组头点击折叠收纳，折叠处显示条目数，状态记忆。21 项日常可压到 10 行以内，溢出时退化为方案一滚动。

用户自主可控、业界最主流找折叠项多一跳
 PLAN 3 窄窗兜底

响应式图标栏

VS Code activity bar · Arc · Slack 窄窗

窗口宽度低于阈值自动收成 58px 图标栏（与现有手动折叠同形态），组头变小点、徽标变角标、hover 出 tooltip。

横向省 160px、复用现有折叠态牺牲文字可读性
 PLAN 4 不推荐

组级双层导航

Apple 系统设置 · iOS 设置

一级只放今日 + 5 组 + 设置（7 项），结构性不溢出；点组推入二级面板。直达性损失大，适合设置类 app 而非高频工具。

一级永不溢出所有功能多一跳

对比

维度① 优雅滚动② 分组折叠③ 图标栏④ 双层导航
解决「矮窗口溢出」 接受滚动，优化体验 收纳后大概率放下 图标也多，仍可能滚 一级恒定 7 项
解决「窄窗口拥挤」 不处理横向 不处理横向 218px → 58px 侧栏可做窄，未本质解决
高频功能直达 全部一跳 展开组内一跳 一跳但需认图标 组内功能两跳
实现成本（对现有代码） 低：sticky + 复用 useEdgeFade 低：组头改 button + shellStore 存状态 低：现有折叠态 + 自动触发断点 高：侧栏改双层栈 + 导航语义变化
信息可发现性 全量可见 折叠项靠组名 + 数量提示 纯图标，新用户不友好 组内条目进二级才可见

业界结论TL;DR

桌面端侧边栏条目超过一屏时，业界几乎无一例外选择「滚动 + 可折叠分组」，而不是减少或隐藏入口。Notion/Figma/Apple 设置走纯滚动优化；VS Code/Obsidian/Discord/Slack 在滚动之上加分组折叠；横向空间不足时收成图标栏（VS Code activity bar、Arc）。把一级功能藏进「更多…」菜单的做法只存在于移动端 bottom-nav 场景，桌面端没有主流产品这样做。

对本项目的推荐：① + ② 叠加为基底，③ 作为窄窗自动兜底（三者不互斥，成本都不高）。

  1. 先做方案一（一次性打底）：组头 sticky、边缘渐隐直接复用 useEdgeFade、hover 细滚动条、设置钉底——无论后面选什么，这层都有价值；
  2. 主方案二：组头可折叠 + 条目数 + shellStore 持久化（与侧栏宽度/折叠态同店）；默认全展开，让用户自己养出收纳习惯；
  3. 窄窗兜底方案三：现有 58px 折叠态已存在，只差一个宽度断点自动触发 + 手动优先（用户手动选过就不自动切）；
  4. 不做方案四：本产品是高频直达型 PKM 工具，「卡片库 → 待办」这类跨组切换是常态，两跳成本不可接受；双层导航适合设置类低频浏览场景。

另一个值得考虑的补充：Ctrl+K 命令面板（03 指南 §9 任务 3）落地后，侧边栏的「全量可达性」压力会显著下降——键盘用户根本不依赖侧边栏找功能，届时侧边栏只需服务高频入口 + 视觉定位。
