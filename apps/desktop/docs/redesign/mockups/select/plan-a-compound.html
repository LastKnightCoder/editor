暗账 · 本方案绕不开的三件事

① 搜索过滤要解析树：searchable 时组件得遍历 children、 抽取每个 Option 的文本做 includes——「可编程的数据」在 A 里是「要解析的 JSX 树」。
// 方案 B 是一行：options.filter(o => labelOf(o).includes(q)) // 方案 A：React.Children.forEach + isValidElement + 读 props.children… const text = extractText(children) // 每个 Option 都要走一遍
② 异步 / 大列表先数组化：远程选项拿到的是数组，还得 map 回 Option JSX 再喂给组件—— 绕一圈回到 B 的形态；选项上千时 children 语法无法切片（M1 虚拟化受阻）。
③ value 类型推断弱：selected 值从 children 收集是运行时行为，TS 只能宽泛为 string； M1 多选（value: V[]）时 Option 协议要跟着动，属破坏性改动。
Tau v2 · 重构中方案 A · 复合组件 · 与 B/C 共皮

选项即标签

结构写在 JSX：<Select.Option> 里直接写富内容（图标 / 双行 / 徽章）， antd JSX 老用法几乎零成本迁移，分组用 OptGroup。 代价：搜索要解析树、异步/大列表要先数组化、value 类型推断弱——见页底「暗账」。
试试：全部下拉均可键盘操作（↑↓ Enter Esc Home/End 敲字跳匹配）； 贴底边那个看 flip 向上展开；右上角切 cream / cocoa 双主题验对比度。
