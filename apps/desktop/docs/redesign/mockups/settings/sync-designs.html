同步子页 · 设计探讨

核心问题先摆出来：legacy 里数据同步（阿里云 OSS / S3 / WebDAV / GitHub 四家 + 自动同步节奏）和资源存储（local / GitHub / S3 / WebDAV——没有 OSS、多一个纯本地） 是两个子页，提供商高度重叠——同一家 WebDAV 服务器要在两页各配一遍。 三案不画整页，只聚焦「同步区」的核心形态：状态怎么读、远端怎么选、数据库与资源怎么组织。 设计语言沿用外观页定稿的行流（hairline 行 / Switch / Select / 状态点）。

案 1 · 合并一页：双通道 数据为中心

一页两节——「数据库」与「资源」各自选远端、各自配置。 保留双远端灵活性（数据库走 NAS 的 WebDAV、图片走 S3 的人有福），但两份配置仍在—— 单远端用户（绝大多数）依旧要配两遍，只是不用切页了。

案 2 · 合并一页：远端为中心 推荐基底

先选一家远端（四卡平铺），下面是一份配置，再由两个开关决定这家远端承载什么： 「同步数据库」与「同步资源」。配置一次两用——单远端用户（绝大多数人）成本直接减半； 资源关掉远端开关即回「仅本地」。这是 Obsidian Sync / Notion 的心智：「我的东西放在哪」 是一个问题，不是两个。

案 3 · 保持拆分：两页各自独立 现状延续

「同步」页只管数据库（本片段）；「资源存储」独立子页（legacy 语义： local 可为 active、含压缩选项）。拆分的理由是资源语义独立演化（大文件、CDN、 压缩策略），但代价是同远端双份配置的原样保留。

对比与建议

案 1 · 双通道案 2 · 远端为中心案 3 · 拆分两页
单远端用户成本配两遍（跟随可减一遍）配一遍，两用配两遍
双远端灵活性支持不支持（可后置为高级能力）支持
「我的东西在哪」心智两节分开读一屏一个答案两页两问
存储迁移成本中（合并页 + 跟随映射）中高（sync/imageBed 配置合并）零
左栏入口1 个（同步）1 个（同步）2 个（同步 + 资源存储）
  1. 建议以案 2 为基底：单远端是绝对主流，配置一次两用是这次重组的最大红利；「这台远端承载什么」的开关句式让数据库与资源的关系第一次被明说（legacy 里两者关系是隐式的）。
  2. 拆分问题随之消解：不拆页（左栏仍一个「同步」入口），但「同步资源」开关关闭 = 仅本地，覆盖了资源独立性的最小诉求；双远端作为高级能力后置（若真有需求，允许资源区单独切换远端即可，形态回到案 1 的资源节）。
  3. 状态读感：一份连接状态行（远端鉴权 + 上次同步）服务两类数据，比两节各一条状态行更整体；冲突/版本信息进状态行的右侧时间位（展开明细可后续设计）。
  4. 迁移注意：案 2 需要 imageBed（local/github/s3/webdav）与 sync（oss/s3/webdav/github）的配置合并映射（同提供商字段对齐 + 「资源是否启用」从 active!=local 推导）；OSS 补齐资源能力属增量。
