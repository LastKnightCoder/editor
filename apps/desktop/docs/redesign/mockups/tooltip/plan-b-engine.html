Tooltip 设计稿 · 方案 B

9 月 17 日 周四 · JS 定位引擎：与方案 A 同视觉同行为，只换引擎（Portal + mini floating-ui）

位置矩阵 · 12 PLACEMENT

placement 由引擎的 computePosition 计算（数学同方案 A 的 position-area，行为一致）； flip / shift 是引擎里的两个中间件，策略可编程 —— 这是本方案的核心卖点。

边缘 FALLBACK · 按住拖我到窗口四角

托盘只管起点——抓起后可拖到窗口任意角落（双击回位） 建议先开「常显模式」↗ ↙ 拖到顶缘看 flip 换边 + 箭头换向 拖到左/右缘看 shift 夹回视口 ↘
引擎链：offset → flip → shift → arrow

滚动跟随 · AUTO-UPDATE（scroll + resize 监听 → rAF）

悬停任意行后滚动列表 —— 引擎监听 scroll(capture) 事件逐次重算； 方案 A 同一场景零监听器（浏览器内建跟随）。监视器里 update 次数可见差异。

内容形态（与方案 A 通用，不随引擎变化）

Tau v2 · 重构中引擎 update：0 次

引擎监视器 · ENGINE MONITOR

update 调用0
scroll 监听2
resize 监听1
最近一次耗时— ms
方案 A（原生锚定）同样交互下这四行全是 0 —— 差别即本方案的代价。

策略可编程的引擎

与 A 同视觉、同 12 位、同 fallback 行为；不同在于定位是 JS 中间件链 （offset → flip → shift → arrow），Menu / Select 需要更复杂策略时在这里扩展， 且 箭头坐标由引擎顺手算出（A 需要 show 后读一次边向）。 代价：scroll/resize 监听 + 每次布局变化都跑 JS + 自己管 z-index 与 Portal。
试试：开常显模式 → 抓起按钮拖到窗口四角（flip 换边、shift 夹回、箭头换向全可验；双击回位）；滚动列表看跟随； chips 切 12 个位置对比方案 A —— 应该看不出任何区别（这正是「视觉与引擎解耦」的意义）。
