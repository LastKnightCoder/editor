Tooltip 基础件 · 方案导览

已定稿：方案 B · JS 定位引擎（Portal + 自研 mini floating-ui，2026-09-17，用户裁决，D-004）——实测中方案 A 的 position-try 候选语义保守、safe anchor-center 布局异常、UA popover 样式需重置三连，使用户倾向策略可编程的 B；A 留档备用。与 Toast 的三方案不同，Tooltip 的分歧不在视觉（业界共识：反相小标签 + 12 位 + 箭头可关），而在技术路线——承载用不用 HTML popover、定位用不用 CSS Anchor Positioning、还是传统 JS 引擎。三份演示页共用 tau 双主题与同一套视觉，其中方案 B 刻意与 A 同皮（只换引擎），证明视觉与引擎解耦。02 规范 §5.2 已裁定 Tooltip / Popover / Menu / Select 共享同一浮层定位引擎——本页的裁决即是引擎选型。

三条技术路线

方案 A · 原生锚定（留档）

popover + CSS Anchor Positioning — 零定位 JS
让浏览器当定位引擎。承载 = popover=manual（top layer：免 z-index、免 Portal、不受祖先裁剪、不抢焦点）；定位 = 锚定 + position-try（12 位、flip 换位链、滚动 resize 跟随全内建）。JS 只剩驱动层：hover 延迟、focus-visible、aria、show 后读一次边向供箭头。
  • 定位代码 ~0 行：滚动/resize 跟随、边缘换位零监听器零每帧计算
  • 箭头对齐触发器中心 = anchor-center 一行（JS 方案要手算投影）
  • Electron 43（Chromium ~150）单环境，无 web 兼容包袱（popover 114+ / 锚定 125+）
  • anchor-name 须全文档唯一（useId 生成 + 内联 style，Tailwind 词表外）
  • position-try 策略是声明式，表达不了的需求要退 JS（Menu/Select 复杂场景的保底 = 方案 B）
适用：Tooltip 全部需求 + Menu/Select 的常规对齐（anchor-size() 还能让下拉与触发器同宽）。02 §5.2 引擎投入最小化。

方案 B · JS 定位引擎 已定稿

Portal + 自研 mini floating-ui — 策略可编程
中间件链换策略。Portal + fixed + 自研 ~100 行引擎（offset → flip → shift → arrow），行为与 A 完全同形；演示页的引擎可直接移植为 primitives 参考。策略是代码：Menu/Select 需要多花的行为时改链路，不动 CSS。
  • 箭头坐标引擎顺手算出（A 需 show 后读一次 rect）；当前边向 JS 天然知道
  • 策略可编程、可单测（注入 rect）；或直接引 floating-ui（~5KB gzip）省自研
  • scroll(capture)/resize 监听 + 每次布局变化都跑 JS（演示页「引擎监视器」可视化了这个代价）
  • z-index / Portal 生命周期自管；自研则有维护面（引 floating-ui 则多一个依赖）
适用：作为 A 的保底与增量——position-try 表达不了的组件（虚拟锚点、动态 size 中间件）仅对该组件换 JS 定位，承载仍 popover，A→B 是渐进不是推翻。

方案 C · 伪元素 / title

::after 与原生 title — 零 JS 凑合（反面教材）
省 20 行 JS，赔四张底牌。被 overflow:hidden 裁剪、无 fallback、transform 祖先下漂移、title 延迟 ~1s 不可控、读屏盲区。单独成页是为了把「为什么不凑合」变成可体验的证据。
  • 零 JS、零依赖，一次性 debug 脚本可用
  • 滚动容器里基本必死（桌面应用到处是滚动容器）
  • 无 aria 语义、无主题、无延迟控制、无富内容
裁定：产品代码禁用；仅作决策对照留档。

决策建议与 API 草案

怎么选

  1. 推荐定稿方案 A：桌面端是单 Chromium 环境，anchor positioning 的唯一短板（兼容性）不存在；定位 JS 归零意味着 02 §5.2「浮层定位引擎是 M0 最重投入」直接降到最轻；top layer 免掉 z-index 与 Portal 两套心智。JS 驱动层（hover intent / focus-visible / aria / 读边向）预计 ~60 行，纯逻辑可测。
  2. 方案 B 不是落选，是保底与增量：Menu / Select / Popover 迁移中若遇到 position-try 表达不了的策略（虚拟锚点、动态尺寸中间件、跨容器吸附），仅对该组件引入 JS 定位（演示页 mini 引擎即参考实现），承载仍走 popover——A 与 B 组合而非互斥。是否引入 floating-ui 届时再裁（当前零依赖）。
  3. 方案 C 禁入产品代码：省 20 行驱动层的代价是裁剪、fallback、可达性、主题四张底牌全赔。title 仅保留给纯文本兜底场景。
  4. 实现提交的两处同步义务：① anchor-name / position-area / position-try 不在 Tailwind 词表且 anchor-name 为动态值——需在 03 指南 §4 CSS 白名单扩一类「浮层锚定 CSS（含内联 anchor-name）」，DECISIONS.md 记一条；② Tooltip 不接 Esc、不进浮层退场注册表（瞬态非阻断，同 Toast 的 D-003 口径）。

ui/primitives/Tooltip API 草案

<Tooltip content="复制" placement="top">        // children 克隆注入事件 + aria-describedby
  <IconButton icon={<Copy />} />                    // disabled 子元素自动包 wrapper span（pointer 事件被吞）
</Tooltip>

interface TooltipProps {
  content: React.ReactNode;                 // string 或含 <Kbd /> 的富内容
  placement?: Side | `${Side}-${Align}`;    // 12 位，默认 "top"
  arrow?: boolean;                          // 默认 true（视觉定稿可全局关）
  delay?: number | { show?: number; hide?: number };   // 默认 { show: 450, hide: 0 }；快速划过不闪
  open?: boolean;                           // 受控（对齐 §5.3 浮层 open/onOpenChange 契约）
  onOpenChange?: (open: boolean) => void;
  children: ReactElement;
}
// 内建行为（不做成 props）：
// - focus-visible 显示（键盘可达）· 移出即隐 · 相邻 Tooltip 切换零延迟（组联动）
// - fallback 链与视口 padding(8px) 固定；箭头随 flip 换边（show 后读一次边向）
// - anchor-name 用 useId 生成全文档唯一；承载 popover="manual"（不抢焦点、不 light-dismiss）
// - 不接 Esc、不进浮层退场注册表（瞬态非阻断）；不含交互元素（可点的说明浮层是 Popover/Menu）
// - 不导出命令式 API（tooltip.show() 之类不做——无障碍语义要求声明式）
实现映射：plan-a 的驱动层 JS（hover intent / focus-visible / aria-describedby / readRealSide）与进出场 CSS（@starting-style + allow-discrete）可直接移植；plan-b 的 mini 引擎留作 Menu/Select 保底参考。实测备注（Chromium 146 / Electron 41 内核）：popover、锚定、flip 链、safe anchor-center 均验证生效；CSS 无 floating-ui 式任意 shift，且 position-try 候选「整块放得下才启用、全失败回首选位」——极端小空间行为需在实现期用真实用例回归（这也是 B 保底价值的一部分）。Tooltip 属 ui/primitives 基础件（03 指南 §9 任务 2 清单内），选型落定后在实现提交中同步 03 §4 白名单与 DECISIONS.md。
