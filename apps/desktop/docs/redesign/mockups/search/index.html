标题栏搜索框（新壳层）目前是死按钮，等待方案定稿后接线。本页把「内容搜索 + 命令/页面跳转」合入一个窗口的四种设计铺开对比，每份方案都有完整可操作的交互演示（双主题、键盘导航、类型限定全流程）。

现状盘点：老代码的两套搜索

内容搜索（全库检索）

Ctrl+K · ContentLayout/components/Search + useCommandPanelStore
  • 5 类实体：card / article / project-item / document-item / diary-daily
  • 全文（FTS）+ 向量混合检索，回车触发（非即时）
  • 结果虚拟列表，点击按类型打开对应详情 Tab
  • 侧栏 SearchBox 点击打开的也是它

命令 / 页面跳转

Ctrl+P · components/CommandPanel（@tmikeladze/react-cmdk）
  • 空态：最近访问 + 常用（useNavigationHistoryStore）
  • 全部页面按「通用 / 内容 / 工具 / 效率 / 设置」分组
  • 输入即时过滤，仅页面导航，无内容结果
  • 与内容搜索完全割裂：入口、交互、视觉三套
两个待决设计问题：① 两种搜索如何合一个窗口？（混排 / 分模 / 分栏 / 分层）　② 只搜某一类（如卡片）怎么交互？（chips / 前缀 / tabs / 预设入口）——四个方案分别给出不同答案，可单选，也可组合。

决策建议

单层 or 两层？

  1. 如果只做一个窗口：选 A（统一混合）。学习成本最低、与老 Ctrl+P「最近 + 常用」语义连续，scope 四条路（chips 单选/多选、前缀、查看全部、徽章移除）已覆盖「只搜卡片 / 卡片+文章」诉求；A 里的「卡片:」前缀本质上就是 B 的轻量版，未来可无痛升级。
  2. 如果内容判读需求强（卡片正文长、常需确认再打开）：在 A 基础上引入 C 的预览栏（C 可视为 A 的「宽面板」变体，同构同数据，只是渲染层不同）。
  3. 长期形态（Notion / Slack 同构）：快速层 + 深度层两层分工——
    A 快速面板Ctrl K 跳一个地方 → D 搜索中心Ctrl ⇧ F / A 的「查看全部」找一批东西
    两层共用一套检索数据协议（searchContent 5 类 + 命令源），UI 独立演进。
实现映射（无论选哪个）：数据＝内容源复用 searchContent（FTS 可即时、向量重排建议防抖 300ms）＋ 命令源 app/navigation.ts ＋ 最近/常用 useNavigationHistoryStore； 快捷键＝Ctrl+K 主入口、Ctrl+P 作为别名保留老习惯； 架构＝搜索面板是 dialog 浮层，不经 definePage 协议（D-016），承载方式（建议 ui 层通用 Dialog 容器 + 全局 SearchProvider）需先在 DECISIONS.md 裁决后再动工。
