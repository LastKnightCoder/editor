# Tab 导航残留审计

审计日期：2026-09-23。范围：桌面端 `apps/desktop/src`。下方清单保留修复前的静态审计快照。

## 修复状态（2026-09-23）

已修复下表 8 组新架构可触达入口，并补齐网页、内嵌白板、内容预览的 Page 承载；知识库文档列表及正文链接复用独立窗口。MCP 创建后打开、当前页面查询、编辑目标解析及 AI RPC 导航改接真实 Page 栈，未实现类型明确返回错误。旧 pages/layouts 不做兼容处理。

注意：`useItemUpdateListener` 实际挂在包裹路由的 App，亦会在新壳层运行；其旧 Tab 标题更新不是导航入口。下方“挂于旧 App”的表述是初次审计的归类偏差，此处更正。

## 结论与口径

- 56 个生产文件直接导入旧 Tab store 或旧导航包装器：54 个导入 useTabStore，2 个消费 utils/navigation。排除测试、注释中的名字和仅引用 TabType 的类型协议；56 不是故障数量，也不是跳转次数。
- 新项目工作台及其共享组件中，7 个文件存在 8 组可触达的旧导航路径，详见下表。同一个更多菜单文件包含删除后的返回与新 Tab 打开两组。
- 前两轮已修复的项目文档卡片列表、项目思维导图不再导入旧 Tab store，不计入残留。
- Page 实际注册为 home、stats、cards、card-detail、articles、article-detail、projects、project-detail。知识库、白板、日记等入口目前仍为 legacy 占位；没有 WebView 或白板详情 Page。不能只把 TabType 换成猜测的 page key。

## 不应计入当前故障的名字残留

- `features/projects/views/ProjectDetailView.tsx` 的 useTabStore 只在历史注释中。
- `useRegisterActiveEditingContext`、`services/content-editing/*` 的 tabType/tabId 等部分是编辑上下文协议字段；只改名字不会修复导航。
- 项目 shared/hooks 下的 `createRootVideoStrategy/createRootAudioStrategy/createRootPdfStrategy/createRootEpubStrategy` 仍保留旧 navigateTo 注入协议，但已无生产调用方（Audio 有测试调用）。项目根节点新增现走 ProjectList 的 targetAwareAddStrategy 与 navigator.push，子节点走 child strategy。
- `utils/navigation.ts` 本身是旧 store 的包装层，不是 Page 适配器。当前两个消费者是内嵌白板卡片和旧白板面包屑。

## 建议处理顺序

1. 修复已有 Page 可承载的普通导航：项目切换、删除后返回、转卡片／文章、正文内容链接中的已迁移类型。
2. 明确“新 Tab／另一分栏”在 Page 栈下的产品语义；为网页、白板详情、知识库补承载，或复用既有独立窗口能力，避免导航到不存在的 key。
3. 将 MCP 当前页面读取、创建后打开及外部服务导航接入新栈；服务层需要可注入的导航入口，不能在普通函数里直接调用 React hook。
4. 旧 pages/layouts 按既定迁移锚点清理；加依赖约束防止 features 和已迁移共享入口重新引入 useTabStore。保留必要的 legacy 白名单。
