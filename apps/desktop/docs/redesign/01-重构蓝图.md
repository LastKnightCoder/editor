## 0. 一句话诊断

桌面端的根本问题不是"Tab 不好"，而是**导航、状态、渲染三个关注点全部纠缠在一个 1183 行的 useTabStore 里**：切换 Tab 即卸载组件（无保活）、33 种 TabType 靠 switch 分发（无页面自治）、UI 靠 antd 三层 token 补丁链糊在一个 ConfigProvider 上（无设计语言）。
解法是把移动端已验证的 **defineXxx 声明式页面协议 + 纯函数栈机 + Activity 保活** 同构移植到桌面，Tab 降级为"导航方案之一"而不是架构本身，UI 则从零建立自有设计系统、彻底退场 antd。

## 1. 现状判断

### 1.1 架构层：导航与状态、渲染三位一体

**双轨路由**。主窗口完全不走 react-router：`src/router.tsx` 的 14 条 hash 路由只服务于辅助窗口（单条编辑窗、番茄钟、快捷卡片等）；主界面由自研的 "Pane → TabGroup → Tab" 三层模型驱动，两套导航体系并行，语义互不相通。

**Tab 系统本身是个巨型上帝 store**。`src/stores/useTabStore.ts`（1183 行，zustand + persist + immer）同时承担：Tab 增删改查、查重（`findTab` 用 `JSON.stringify` 深比较 params）、相邻补位、pane 上限管理（硬编码 2 个）、localStorage 持久化与手写迁移（version 6，还要清理已删除的 goals/slides/badgeCenter 类型）。UI 侧 `TitlebarWithTabs/index.tsx`（1049 行）再承接拖拽排序/分组/关闭。一个导航关注点扩散在 2200+ 行里。

**切 Tab 丢状态的机制性根因**：`PanesLayout/index.tsx:223` 起是 `{activeTab && <TabContent tab={activeTab} />}` —— 只有激活 Tab 被挂载，切换即卸载。组件内部 state、滚动位置、编辑器现场全部丢失，唯一幸存的是 store 持久化和 query 缓存。**这不是 bug，是当前架构的默认行为**，修不动，只能换。

**33 种 TabType 的 switch 分发**。`TabContent.tsx:56-179` 一个 switch 映射 33 个分支到 30 个懒加载页面。页面没有自治权：身份（单例还是多例）、保活策略、参数校验、离开守卫，全部无处声明，只能靠调用方约定。

### 1.2 架构层：分层混乱

- **聊天系统寄生在布局层**：`layouts/ContentLayout/components/ChatSidebar/` 下藏着 2372 行的 ChatContainer、MarkdownRenderer、messageQueue 等，ContentLayout 还在布局层做 `initAiServer()` 和数据库初始化。"布局"目录承担了业务域的全部职责。
- **components/ 是两个巨型子系统的坟场**：116 个目录中 WhiteBoard 独占 48737 行、Database 13892 行——它们是 feature，不是组件。
- **Settings 是一座 18651 行 / 93 文件的山**，15 个子设置页挤在一个页面域里。
- **46 个 store 平铺**，19 个各自 persist 到 localStorage，无统一迁移策略；`useSettingStore.ts` 1436 行。
- **命令层样板海**：`src/commands/` 92 个文件几乎全是 `return xxxCommands.yyy.call(args)` 手写包装，且契约化只完成一半。
- **主进程 304 处 ****`ipcMain.handle`**** 散布**在 modules/ 里无集中注册（这部分本次重构不动，但要知道它在那）。

### 1.3 UI 层：antd 补丁链 + 样式三轨

- **361 个文件 import antd**，遍布所有层。
- 主题决策散落三处：`App.tsx:216-399` 的 10 个组件 token 覆盖，每处都是 `isSolid ? (isDark ? … : …) : …` 三层嵌套三元硬编码色值；`useAntdThemeToken.ts` 从 accent 预设派生；`themes/overlay.less` 用 `!important` 给浮层打毛玻璃补丁。**同一个视觉决策改一处要同步三处**。
- 样式三轨并行：约 447 个 tsx 用 Tailwind 原子类、144 个 CSS Modules（.less）、297 个用 classnames 拼接，同一文件混用是常态。
- 交互无一致语言：组件行为跟着 antd 走，没有自己的规范，"没有个人特色"的直接原因。

### 1.4 值得保留的资产（不是推倒一切）

| ------------------------ | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## 2. 目标与原则

1. **切页面零丢失**：任何导航动作不丢组件状态、滚动位置、编辑器现场。
2. **页面自治**：一个页面的身份、参数、保活、守卫、数据、转场，在一个文件里声明完毕（defineXxx 精神）。
3. **渐进式**：新旧页面长期共存，任何时刻可发布；升级进度可感知、可管理。
4. **UI 完全自有**：antd 彻底退场（含 @ant-design/icons），token → 组件 → 模式 → 页面四层自建，支持多主题；审美以 PREFERENCES.md 为唯一事实源，不引用任何遗留文档（原 PRODUCT.md 已按裁决删除）。
5. **架构与移动端同构**：同一个心智模型（声明式页面协议 + 栈机 + 保活 + 结果通道），桌面适配（多面板、快捷键、高信息密度）。两端代码不共享，但**设计共享、范式共享**，降低维护心智。
6. **依赖向前看**：M0 基建时统一升级到最新稳定版（React 19.2.3+，与移动端版本对齐；`<Activity>` 保活、`<ViewTransition>` 浮层转场按实际可用性启用，实验期 motion 兜底）；迁移期间冻结大版本、只走补丁；新代码一律按新 API 写，不留旧版兼容层。

## 3. 新架构：Page 协议

### 3.1 心智模型：从 "Tab" 到 "Page"

Tab 是浏览器隐喻，隐含"每个 Tab 是独立文档"。但本产品的 33 种 TabType 里，绝大多数是**功能页**（卡片库、日历、设置…），少数是**参数化详情**（某张卡片、某个项目）。真正需要浏览器式并行的场景很少。

新模型把"可导航的东西"统一为 **Page（页面）**，一个 Page 就是一块有身份、有参数、有生命周期的界面：

```
主窗口
├── Sidebar（一级导航，常驻）
├── PageHost × N（每个 pane 一个，承载 page 栈）
│     └── page 栈：cards → card-detail(cardId=42) → …（<Activity> 保活 + LRU）
├── 浮层（dialog/drawer）——不经 definePage，承载方式待裁决（D-002）
└── ChatPanel / Inspector 等可停靠面板（dockable panel，未来）
独立窗口（quick-card、编辑器窗…）：复用同一 Page 协议，由 WindowManager 按 key 开窗
```

与移动端的对应关系：

| 移动端                             | 桌面端                           | 差异                                             |
| ---------------------------------- | -------------------------------- | ------------------------------------------------ |
| `definePage({ layer: "screen" })`  | `definePage`（无 layer 字段）    | 同名同构；桌面 page 栈默认无转场动画（即时切换） |
| `definePage({ layer: "overlay" })` | ——（浮层不经 definePage，D-002） | 桌面浮层承载方式另行裁决，不进页面协议           |
| 底部 Dock Tab                      | 侧边栏                           | 一级导航的桌面化                                 |
| 单栈 + LRU                         | 每 pane 一条栈 + LRU             | 分屏 = 多 PageHost 实例，栈机纯函数天然可多实例  |
| 无                                 | 独立窗口 `window: "auxiliary"`   | 桌面特有：同一协议，宿主换成 BrowserWindow       |

### 3.2 definePage：一个文件声明一个 Page 的全部

与移动端 definePage 同名同构（泛型只在边界、双注册表、params schema 编译期推导 + 运行时净化、默认值分流）。桌面化调整：**协议只承载页面**——dialog/drawer 等浮层不经 definePage，如需浮层导航另行裁决（D-002）。

```TypeScript
// src/page/definePage.ts
export function definePage<F extends ParamFields>(args: PageDefinitionArgs<F>): PageDefinition

export type PageDefinitionArgs<F extends ParamFields> = {
  key: string;
  match?: "single" | "params" | "multi";         // 宿主声明流（对齐 Android launchMode）
  getId?: (params: InferFields<F>) => string;    // match: "params" 的身份函数
  keepAlive?: "keep" | "data";                   // keep=Activity 保活；data=卸载内容靠 query 缓存恢复
  window?: "auxiliary";                          // 声明为独立窗口（quick-card、单条编辑器…）
  params: F;                                     // 参数 schema：编译期推导 + 恢复会话时运行时净化
  canLeave?: (ctx) => boolean | Promise<boolean>;
  data?: PageDataDefinition<F>;                  // 页面级 query 声明（key 参数化/staleTime/refetchOnFocus）
  store?: (params) => Record<string, unknown>;   // 实例级 zustand store 工厂（随实例 GC）
  status?: "new" | "migrating" | "legacy";       // 升级状态机（见 §5，迁移期专用字段）
  component: ComponentType;
};
```

配套（全部从移动端平移，仅改名）：

| 移动端文件                                | 桌面端对应                              | 职责                                                                       |
| ----------------------------------------- | --------------------------------------- | -------------------------------------------------------------------------- |
| `router/core/stackMachine.ts`             | `page/core/stackMachine.ts`             | 纯函数栈机：push/pop/popTo/removeById/LRU 候选，无 React 可单测            |
| `router/core/paramsSchema.ts`             | `page/core/paramsSchema.ts`             | `createPageSchema` + `number()/string()/oneOf()/optional()` DSL            |
| `router/core/pageMeta.ts`                 | `page/core/pageMeta.ts`                 | 纯数据注册表（无 React）                                                   |
| `router/registry.ts`                      | `page/registry.ts`                      | React 侧组件注册表                                                         |
| `router/RouterProvider.tsx`               | `page/PageProvider.tsx`                 | 运行时枢纽：栈状态、navigator 命令对象、结果通道、守卫                     |
| `router/PageHost.tsx` / `OverlayHost.tsx` | `page/PageHost.tsx` / `OverlayHost.tsx` | 渲染层：`<Activity>` 保活；OverlayHost 承载浮层（不经 definePage，待裁决） |
| `router/useSheetBackDismiss.ts`           | `page/useEscapeDismiss.ts`              | 浮层 Escape 拦截（桌面等价物：Esc 先关浮层，LIFO 仲裁）                    |
| `router/query/` `router/store/`           | `page/query/` `page/store/`             | 页面级 query 声明 + 实例级 store                                           |
| `src/pages.ts`（Vite glob）               | `src/pages.ts`                          | `import.meta.glob("/src/features/**/pages/*.page.tsx")` 副作用注册         |

**导航 API**（保留移动端全套语义，桌面补充分屏）：

```TypeScript
type Navigator = {
  push(key, params?); replace(key, params?); pop(result?); popTo(key); popToTop();
  back(): boolean; forward(): boolean;         // 桌面新增：标题栏按钮 + Alt+←/→；push/replace 清空 forward buffer（浏览器语义）
  canBack(): boolean; canForward(): boolean;   // 按钮禁用态（禁用而非隐藏，用户对"能否返回"要有稳定预期）
  pushForResult<R>(key, params?): Promise<R>;  // finish(result) resolve / cancel() reject / Esc reject("dismissed")
  finish(result?); cancel();
  openInSplit(key, params?): boolean;          // 桌面新增：在右侧 pane 打开（无右侧 pane 时创建，上限 2）
  preload(key, params?): Promise<void>;        // 按页面 data 声明预取
  // Esc = 移动端 goBack 的桌面对应物（backHandler 问栈顶 → 守卫 → back()；根页 Esc 无操作）
  // 关键差异：主窗口不做 window.history 同步——桌面没有系统返回键约束，栈机是唯一真相源，
  // 移动端的 historyAdapter 整层丢弃（取舍清单见 §3.7）
};
```

### 3.3 状态不丢的三道防线

1. **`<Activity>`**** 保活（React 19）**：page 栈内页面切换不卸载，DOM/state/滚动全保留，effect 自动停驻；LRU 上限（建议 12）超出才卸载最久未访问的页面 DOM。
2. **状态外置**：凡是跨导航要活下来的状态，按归属放三层——URL 化 params（可恢复、可深链）、实例级 store（`definePage({ store })`，随实例生命周期）、query 缓存（服务端状态单一事实源）。组件内部 state 只放"丢了也无所谓"的瞬态。
3. **会话恢复**：主栈序列化进 localStorage（走 schema 净化，天然免疫脏数据），启动时恢复——替代现在的 tab-store v6 手写迁移。

### 3.5 与现有代码共存：Legacy 兼容层

迁移期的核心机关——**旧 Tab 系统整体降级为 legacy 数据源**：

```
新 Sidebar/Navigator
   └─ push("vibe-learning") ──→ page registry 查 status
                                  ├─ status: "new"/"migrating" → 渲染新组件
                                  └─ status: "legacy" → <LegacyTabPage type="vibe-learning" params/>
                                                          └─ 内部复用旧 TabContent switch 渲染旧页面
```

- `LEGACY_TAB_MAP.ts`：33 个 TabType → page key 的映射表（含已废弃类型的丢弃/重定向），一次性写好；
- 旧 `navigateTo/openInNewTab` 调用点改写为新 `navigator.push`（openInNewTab 语义映射为 `openInSplit` 或普通 push，视页面而定）；
- 兼容层让**新 shell（侧边栏 + PageHost + 保活）先上线**，所有旧页面零改动继续跑，然后一个一个迁移。这也顺带解决了"切页面丢状态"——legacy 页面同样被 `<Activity>` 包住，保活立竿见影。

### 3.7 移动端概念的取舍清单（不乱抄）

移植不是照抄——每个移动端概念都要过一遍"平台语义是否成立"。已裁决清单（后续新特性同样按此裁决，新条目追加进来）：

| 移动端概念                                                                                 | 桌面端裁决                  | 理由                                                                                        |
| ------------------------------------------------------------------------------------------ | --------------------------- | ------------------------------------------------------------------------------------------- |
| historyAdapter（history 驱动弹栈）                                                         | **丢弃**                    | 它为 Android 系统返回键服务；桌面主窗口无此约束，栈机即唯一真相源，省掉整层同步复杂度       |
| 边缘返回手势 / 双击根页退出                                                                | **丢弃**                    | 桌面 = Esc + 标题栏后退/前进按钮 + Alt+←/→；根页 Esc 无操作即可                             |
| BottomSheet / ActionSheet / SnapSheet 生态                                                 | **丢弃**                    | 桌面浮层 = 居中 Dialog、右侧 Drawer、Menu/Popover；形变转场走 View Transitions API（D-106） |

| refetchOnResume                                                                            | **改造** → refetchOnFocus   | "恢复"的桌面语义是窗口/pane 聚焦                                                            |
| 触控命中区 28px / 安全区 env                                                               | **丢弃**                    | 键盘焦点优先，命中区 24px，无安全区概念                                                     |
| params schema / match 声明流 / keepAlive 两策略 / 结果通道 / 双注册表 / TAB_ORDER 顺序契约 | **照搬**                    | 协议核心，平台无关                                                                          |
| `<Activity>` 保活 + LRU                                                                    | **照搬**（LRU 上限 10→12）  | 桌面内存宽裕                                                                                |
| useSheetBackDismiss（手势浮层拦截）                                                        | **改造** → useEscapeDismiss | 仲裁语义（LIFO、注册时序、退场缓冲）原样保留，触发器从返回手势换成 Esc                      |

## 4. 导航方案对比

多方案并列，供决策（样板间 `mockups/index.html` 内有线框对比）：

### 方案 0：维持浏览器式 Tab（现状）

多窗口心智，每个 Tab 独立"文档"。33 种 TabType 已证明会失控：标题栏拥挤、Tab 管理成本高（分组/拖拽/查重）、且用户实际高频使用的固定功能页只有十来个。
**适合**：重度多任务、需要同时开 10+ 个详情页比对的工作流。**成本**：即使上了保活，Tab 条仍是信息噪音；分组/关闭交互复杂度居高不下。

### 方案 1：固定侧边栏 + 单主视图（Notion / Linear 式）

左侧栏常驻一级导航（卡片库、文章、知识库、项目、学习、日历、聊天、设置…），可折叠为图标栏；主区域一次显示一个 page，栈内可返回。
**优点**：导航零管理成本；切换 = 保活切换，零成本零丢失；信息架构一目了然；键盘/鼠标的工作流连续。
**缺点**：不能同时看两个页面（靠方案 4 的分屏补）。

### 方案 2：侧边栏 + 列表详情同屏（master-detail，邮件客户端式）

一级导航进列表页，点条目**不跳转**而是在右侧展开详情（卡片库、文章列表天然适合）。
**优点**：浏览-阅读工作流最高效；详情即浮层即栈，Esc 逐层退回。
**缺点**：只适合"列表+详情"型内容；编辑器/白板等沉浸型内容不适合挤在半栏里。
**注**：这不是全局导航方案，而是**方案 1 内特定页面的布局模式**——详情作为右侧 drawer 浮层即可实现（浮层承载方式待裁决，D-002）。

### 方案 3：多面板自由工作台（IDE / Obsidian 式）

任意 page 可拖拽拆分为多 pane、多列布局可保存。
**优点**：天花板最高。**缺点**：实现与维护成本最高，且 pane 布局管理会重演 Tab 管理的复杂度——把今天的 Tab 问题换个形态请回来。

### 方案 4（推荐）：侧边栏骨架 + 页内 master-detail + 受控分屏逃生舱

- **一级导航**：方案 1 的侧边栏（可折叠、支持用户排序/隐藏，学移动端 `TAB_ORDER` 顺序契约）；
- **详情浏览**：列表类页面内部用方案 2 的 master-detail（详情 = drawer 浮层）；
- **并排对比的强需求**：保留 `openInSplit`（右侧开一个新 pane，上限 2，沿用现有习惯），这是方案 3 的 10% 成本拿到 80% 价值；
- **命令面板**（Ctrl+K / Ctrl+P）：所有 page 可搜索直达——键盘用户的真正"多任务"入口，补齐侧边栏的可达性。

**推荐理由**：与移动端栈模型同构度最高（侧边栏 = dock 的桌面化，分屏 = 多栈机实例）；架构上它只是"PageHost 的实例数问题"，从方案 4 走到方案 3 是渐进演化而非重构；先不做 pane 自由拖拽，留到确有需求再加。

## 5. 渐进式升级管理

### 5.1 升级状态机：status 字段 + Legacy 兼容层

每个 page 在 definePage 里带 `status`（§3.5）：

| status      | 含义                          | 渲染                          |
| ----------- | ----------------------------- | ----------------------------- |
| `legacy`    | 未迁移，仍在 legacy/          | LegacyTabPage → 旧 TabContent |
| `migrating` | 迁移中，新旧并存可切换（dev） | 新组件 + dev 开关回退旧版     |
| `new`       | 迁移完成或全新页面            | 新组件                        |

**规则：status 只进不退（migrating→new），回退要走 DECISIONS.md 记录原因。**

### 5.2 升级进度的感知（四层）

1. **注册表自身**：`listPageMetas()` 可编程枚举全部 page 及 status——进度是数据，不是文档；
2. **DevTools 面板**（学移动端 RouterDevTools，仅 dev 构建加载）：可视化各 pane 的 page 栈、Activity 保活数、query 缓存，外加"重构进度"页：legacy/migrating/new 三色清单 + 占比；
3. **CI 棘轮**：脚本断言——antd import 白名单长度只减不增；`src/pages/`（旧目录）文件数只减不增；`features/**/pages/*.page.tsx` 里 status 统计输出进 PR 注释；
4. **里程碑燃尽图**：`docs/redesign/DECISIONS.md` 附 page 清单表，每迁移一页勾一行（人工但可见）。

### 5.3 页面的合并、拆分与消亡

33 个 TabType 迁移时趁机重整信息架构（映射表 `LEGACY_TAB_MAP.ts` 是唯一事实源）：

| 现状                                                     | 走向                                                                                              |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| DocumentsView + DocumentView + PdfView + VecDocumentView | 合并为 `library` 域（列表/详情/阅读器为子 page）                                                  |
| VibeLearningView + FlashcardCenter                       | 归入 `learning` 域                                                                                |
| Calendar + TimeRecordView + 番茄钟                       | 归入 `schedule` 域（番茄钟独立窗口保留）                                                          |
| Settings 15 子页                                         | 拆为 settings 域下的搜索式设置中心（子 page）                                                     |
| DiaryView、WeRead、WhiteBoard…                           | 原样逐页迁移；ResourceManagement 已退役（D-037）；FeedView、RSS、稍后读及博客 RSS 已退役（D-042） |
| 已废弃 TabType（goals/slides/badgeCenter…）              | 映射为 redirect 或丢弃，映射表里留痕                                                              |

映射表里的每个 key 都有注释行标注"合并自/替代/废弃于"，保证旧入口（快捷键、收藏、深链）不断链。

### 5.4 偏好沉淀机制（本节回答"我的偏好如何沉淀、方便后续吸收参考"）

重构是长期工程，审美决策会持续产生。沉淀分三层，**每次设计评审后必须更新**（这是流程要求，不是可选项）：

1. **`PREFERENCES.md`********（偏好清单——最重要的资产）**：结构化记录"我喜欢什么 / 我讨厌什么 / 在什么场景"。每次评审（包括本次三套样板间的取舍）把新发现的偏好追加进去，写清**正例、反例、一句话理由**。它越厚，后续页面设计越不需要你反复解释口味，AI/协作者吸收它作为设计输入。
2. **`DECISIONS.md`********（轻量 ADR）**：每个已裁决的决策一行：背景 → 选项 → 选择 → 理由 → 影响。导航方案、设计方向、token 命名、组件 API 风格，全部落这里。回看时能知道"当时为什么这么定"，避免半年后无意识推翻。
3. **`mockups/`********（视觉存档）**：落选方案移入 `mockups/archive/` 不删除——它们是偏好的负样本证据，与 PREFERENCES.md 的反例条目互相引用。

时机成熟时（大约 M2 后），把稳定下来的硬规则（禁 antd、page 协议用法、样式写法）固化进 **AGENTS.md 专节**，学移动端"浮层与返回手势规范"的做法——这个仓库已经证明这是最有效的防腐化手段。

| 阶段                    | 内容                                                                                                                                                                                     | 验收                                                                             |

## 6. 风险与对策

| 风险                                                                               | 对策                                                                                                    |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `<Activity>` 在 Electron/React 19 桌面场景的边角问题（焦点恢复、webview 保活内存） | M0 做专项 spike；keepAlive: "data" 作为每个页面的降级逃生舱；LRU 上限兜底内存                           |
| 迁移期双 UI 并存造成风格割裂                                                       | 接受割裂（legacy 页面维持 antd 原样），但新壳（侧边栏/标题栏/浮层）先行统一——壳先于页                   |
| 合并页面破坏用户肌肉记忆                                                           | 映射表 + 旧 key redirect；高频入口（侧边栏顺序、快捷键）迁移前后保持一致                                |
| 33 TabType 里有隐藏的跨 tab 副作用依赖                                             | M1 前 grep 全库 `useTabStore` 消费点，列出副作用清单逐一接管（预计集中在 navigateTo/openInNewTab 调用） |
| 重构期间业务需求并行                                                               | CI 棘轮保证增量不恶化；legacy 页面允许修 bug 但禁止新功能（新增功能必须走新架构）                       |
