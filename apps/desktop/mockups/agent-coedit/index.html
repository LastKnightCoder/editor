Agent 协同编辑 · 设计方向

目标：让 Agent 在文档里像一个真正的同事。它有名字和颜色，你看得见它在哪、在干什么；它的改动落在原文上，可以讨论、可以退回；你和它可以同时写，人永远优先。

现在的问题

  • 改动在对话里审，不在文档里审。确认入口是聊天流里的工具卡（ContentEditProposalRenderer），要在卡里切「改动高亮 / 完整内容」看一份只读副本。文档只多了一个浅色底和顶部一排「AI · 拟修改正文」标签。
  • Agent 没有身份。标记统一用 bg-accent-soft，名字默认「AI」，多个 Agent 同时改分不清谁是谁，hover 时只有 title 提示。
  • 过程不可见。提案出现之前看不到它在读哪、做到哪；提交后的标记 12 秒就消失，回来时看不出谁改过什么。
  • 交互是审批，不是协作。「确认应用 / 提修改意见 / 拒绝」三个按钮针对整次提案；你想只要其中一处、或对某一句说话，都要回到对话里重来。
  • 权限是对话级开关。review_required / auto_apply_allowed 跟着会话走，没有「这个 Agent 我信得过」这一层。

三个方向

A 建议模式 推荐先做

像 Google Docs 的「建议」。Agent 的改动以作者色修订痕迹落在正文，右栏按条接受 / 退回 / 回复；选中文字 @Agent 派活。最贴近现有提案 + 范围锚点的模型，改造量最小。

B 批注对话

页边批注线程是主场。Agent 会反问、给选项、@另一个 Agent 交接；改法是线程里的一条回复。适合核对、调研这类需要来回商量的活，以及「派完活走开」的异步节奏。

C 放手改 + 回看

受信任的 Agent 拥有直接编辑权，像另一台在线设备实时打字；人一碰它就让。事后在动态里按次回看、撤销。按 Agent 给权限，和真人协作者同一个面板。

建议的组合

  1. 共同底座（三个方案都要）：Agent 身份（名字 / 颜色 / ✦ 角标 / 一句职责）、标题栏在场头像、正文里的 Agent 光标与「正在看这段」、按作者着色的痕迹。
  2. 默认交互用 A：改动落在原文、按条处理，审阅从对话卡迁到文档里。对话里的工具卡只保留一行摘要 +「在文档中查看」。
  3. B 的反问与线程作为 A 的「回复」延伸：先做「Agent 在批注里问你、给选项」，Agent 之间 @ 交接放后。
  4. C 作为权限升级：某个 Agent 在某篇文档被设为「直接改」后才走实时落地 + 事后回看；默认仍是建议。

已定

  • 审阅不迁出对话。用户不一定打开文章，所以同一份建议有两个视图：对话里按条的紧凑卡片，文章里的修订痕迹，状态同步（见 A 场景「文章没打开时」）。
  • Agent 名字由 AI 生成：派发时按任务起一个职责名（「校对」「调研员」），颜色按名字固定分配。
  • 实时打字要做（方案 C 的直接改）。
  • 推进方向：A 为主，B 的反问作为回复的延伸，C 作为权限升级。
  • 支持按条接受：一次修改里的每处改动是一条独立建议，各自带锚点和原文前提，可以单独接受、退回、回复；「全部接受」只是批量操作。提交按条校验，一条过期不影响其他条。

文章开关时怎么保证同步

原则：界面不持有任何状态，只是数据的投影。文章开着还是关着、在哪个窗口打开，都读同一份数据，所以随时开关都不会错位。

  • 中途关闭：什么都不用做。Agent 的写入和建议都不经编辑器，关掉只是少了一个观察者。
  • 中途打开：先加载正文，再取该文档的未处理建议，用锚点解析回当前位置。解析不到、或原文前提已变的，标「已过期」而不是画错位置。
  • 两边同时操作：接受和退回都是对记录的条件更新（只允许「待处理 → 已接受 / 已退回」）。对话里先点了，正文那边就收到状态变更、痕迹消失；后点的一方得到「已处理」，不会重复应用。
  • 多个窗口：独立编辑器窗口和主窗口都从主进程订阅，规则相同。

和现状的差别：现在提案存在渲染进程的 localStorage（content-edit-review-session），正文标记存在内存 store，提交后 12 秒消失。别的窗口看不到，重启也就没了。这次要把建议记录和变更广播移到主进程。
