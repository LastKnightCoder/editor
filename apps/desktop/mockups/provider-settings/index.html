问题清单

  • 1职责混在一起：宿主设置页同时承担「选服务 + 看状态 + 填配置」，配置字段让同步页最长的部分变成了别人的表单。
  • 2样式无约束：插件拿 SettingRow / Input / Button 自由拼，说明有无、按钮文案（保存同步配置 / 保存并使用）、提示字号（tau-body / tau-sm）、字段顺序、「可选」写法（标题括号 / 说明 / placeholder）各不相同。
  • 3归属反转：插件详情 › 设置 对 sync / upload / tts / publish 都只放跳转按钮。
  • 4保存语义不一：桌面显式「保存」；移动端位置字段失焦即存、账号却要在 Dialog 里点「保存账号」。
  • 5移动端交互是桌面的：账号 Dialog、远程选项 Dialog + ghost Button 列表、枚举用 Select 下拉浮层；无全屏推入、无勾选列表、无键盘让位。
  • 6字号排版：插件面板用 text-tau-*，宿主外壳用 text-[14.5px]/[11.5px]；两套卡片皮（shadow-card vs setting-group）上下拼接。
  • 7双份维护：每个插件两套 UI；S3 / OSS / GitHub 的同步插件与上传插件分家，同一把密钥要填两次。

核心原则一句话：设置页回答「用哪个、现在怎样」，插件页回答「怎么连」。宿主设置页只放与服务无关的东西（当前服务、同步状态与操作、压缩等宿主策略）；连接参数（账号、桶、仓库、路径）属于插件，住在插件详情 › 设置。两个页面互相只放一行「入口」。

设置 › 同步 / 资源存储（宿主）

  • 状态：数据库版本、资源文件、上次同步、错误
  • 操作：同步 / 拉取 / 检查 / 整库覆盖
  • 服务选择：已安装且具备该能力的插件列表，单选；每行显示「已配置 · bucket/仓库摘要」或「未配置」
  • 每行尾部「配置 ›」→ 插件页；底部「添加服务 ›」→ 插件中心
  • 宿主策略：上传压缩、本地存储目录

插件详情 › 设置（插件）

  • 能力卡：此插件可用于「同步」「资源存储」，各显示「当前使用 / 设为当前」
  • 连接表单：账号 → 存储位置 → 测试连接，由宿主统一渲染
  • 保存即测试；保存成功且尚无当前服务时提示「设为同步服务」
  • 从设置页进入时顶部带「← 返回同步设置」

首次配置路径

设置 › 同步选择 S3（未配置）插件页 › 设置填账号/位置 → 保存并测试「设为同步服务」返回同步设置，立即同步

往返成本靠两处抵消：插件页能力卡可直接「设为当前」；返回条一键回到来源设置分区。移动端本来就是推入栈，返回即回到同步中心。

桌面端跳转承载（待决策 Q2）

  • N1 跳插件页推荐：设置是全窗口浮层，点「配置 ›」关闭设置、push 插件详情 settings 标签（参数 from=sync），页顶返回条重新打开设置并定位到同步分区。插件页是唯一配置位置，心智最干净。
  • N2 设置内抽屉：在设置页右侧拉出抽屉渲染同一份表单，不离开设置；插件页也渲染同一份。改动小、无往返，但「配置在哪」又变成两处可见（数据仍是一份）。

同一原则可推广到的目标

插件设置 target 现有 sync / upload / tts / asr / images / video / publish。本轮建议只做 sync + upload（问题最集中、字段最规整）；tts（模型、音色克隆等多页）与 publish（发布页自有工作台）结构不同，验证后再评估（Q5）。

「样式不一」的根因是插件在写 UI。只要插件还能自由拼组件，规范就会漂移；把配置表单改成插件声明字段、宿主按平台渲染，一份声明在桌面是 SettingRow + Input，在手机是分组行 + 推入选择页，插件不再写 mobile-settings.tsx。

方案 A：声明式字段推荐

插件注册 fields（分组 + 类型 + 校验 + 远程选项），可选 prepare（换取用户信息）与 test（连接测试）钩子；宿主负责布局、文案、保存、错误、加载态、键盘与平台差异。

  • ✅ 一致性由结构保证，无需评审兜底
  • ✅ 每插件少一套 UI（约 60–140 行/插件）
  • ✅ 移动端交互一次改对，所有插件受益
  • ⚠️ 需要设计字段类型集；极少数特殊配置（OAuth 登录）留 custom 逃生口

方案 B：自适应组件套件

@tau/ui 提供 ProviderForm / ProviderField，内部按平台切换渲染；插件仍写 JSX 但只能用这套。

  • ✅ 插件 API 不变，迁移是换组件
  • ⚠️ 插件仍能在中间夹 <p>、自定义类名，漂移可能复发
  • ⚠️ 保存 / 测试 / 错误展示仍各写各的

方案 C：保持现状 + 规范

只做位置迁移（表单搬到插件页），出一份插件 UI 规范与 lint 规则。

  • ✅ 成本最低
  • ❌ 不解决两套 UI 与移动端交互
  • ❌ 第三方插件不受约束

方案 A 的声明长什么样（以 S3 为例）

context.settings.register({
  id: "sync",
  title: "S3",
  target: "sync",
  form: {
    groups: [
      { key: "account", title: "账号", fields: [

        { key: "bucket", label: "Bucket", type: "text", required: true },
        { key: "region", label: "区域", type: "text", placeholder: "us-east-1", required: true },
        { key: "pathPrefix", label: "目录", type: "text", placeholder: "sync", optional: true },
