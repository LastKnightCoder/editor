问

SQLite 开启 WAL 后，为什么读不再阻塞写？

桌面端把数据库切到 WAL 后，后台同步写入时界面查询不再卡顿。我知道「WAL 提升并发」这个结论，但说不清它到底让谁不必等谁，也不确定代价是什么。

● 结论速览

写只往 WAL 末尾追加，读只看自己开始时的 end mark 之前——各看各的快照，所以互不等待。代价是单写者，以及长读事务会让 WAL 无限变大。

第 9 天10月9日 周五

写下结论，标为已解决

解 2026年10月9日

关键在于：写操作不再原地修改数据库文件。WAL 模式下，提交只是把被修改的整页追加到 -wal 文件末尾，主文件在 checkpoint 之前保持不变。

读事务开始时会记下 WAL 中最后一个有效 frame 的位置（end mark），之后只读取这个位置之前的内容。于是读者看到的是一份一致的快照，写者可以继续往后追加，两者互不等待。这就是快照隔离的思路——只不过以「页」为粒度、靠 WAL 位置实现。

代价：同一时刻仍只能有一个写者；长读事务会挡住 checkpoint 回收 WAL。

方案 C 设计说明

研究日志：问 → 结论速览 → 径（主体）→ 解 → 据。过程即正文，读者跟着走一遍你的研究。

  • 顶部「结论速览」先给赶时间的读者一句话答案，再提供两条路：读完整解答 / 从第一天看起。
  • 日志按天组织，资料以引文卡直接嵌在发生的那一天，摘录原文 + 去原处的链接，引用和出处同处一地。
  • 「弯路」「想通了」是手写笔记的标记，是这类页面最有价值、也最难在别处读到的部分。
  • 空档天折叠成「— 1 天没有记录 —」，保留节奏感而不占篇幅。右侧日志目录随滚动高亮。
  • 「解」里的 [n] 点击跳回日志中的那张引文卡——资料只出现一次，不重复。
  • 优点：最强调研究过程、最有可读性；缺点：依赖你在探究时写笔记，只有自动轨迹的问题会显得空。
