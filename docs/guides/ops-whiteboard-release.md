# 白板协作发布前检查

此清单只用于发布准备。执行真实迁移、SDK 发布或服务部署须另获明确授权。

## 最低兼容组合的确定

| 对象 | 放行前核对                                                                                                                  | 不能作为替代证据                                                          |
| ---- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| SDK  | 下载固定发行版本的 tarball，验证 integrity；在仓库外编译白板作者夹具及示例，确认身份命令、dataVersion、文本绑定与受控写入口 | workspace alias、本地同号包或 npm latest 标签                             |
| 桌面 | 固定包含公共契约与白板完整接线的提交、版本和原生安装包；以首个通过组合验收的发行版作为插件最低宿主版本                      | package.json 版本、源码构建成功或仅能安装插件                             |
| 插件 | 每个插件单独确定适配版本；核对 ZIP 摘要、desktop 最低版本、元素数据契约、文本/资源声明与宿主历史                            | apiVersion 1、formatVersion 3、web-v1、插件中心 compatible 或仅提高包版本 |
| 服务 | 固定实际服务构建摘要及部署版本对应；验证文档协议 3、契约格式 2、whiteboard-w1-v1、因果/epoch、回执和资源保留                | 健康检查成功、通用 build 标签、/v1 URL 或 Node/Worker 包版本号            |

按上述四项记录一个明确的已验证组合，再填写正式最低版本；未知更高版本不能自动视为经过验收。新插件的 minAppVersion 只能阻止它进入旧宿主，不能证明旧插件适合新宿主。缺少新白板数据声明的旧插件仍须单独适配，不能由安装成功推断可编辑。

SDK 是作者类型依赖，用户无需安装；插件运行时由宿主提供。没有第三方插件的白板不依赖作者插件包；含缺失插件元素的文档只承诺已有保真占位和通用操作，不承诺专属编辑。

## 检查步骤

1. 固定待发布提交及模板子模块提交，确认公共编辑器契约、白板模型与服务端门禁来自同一套已验证源码；工作区混合改动不能直接充当发行物。
2. 核对版本与门禁：契约格式 2、白板 profile whiteboard-w1-v1、正文协议 2、白板协议 3。dataVersion、扩展 apiVersion、SDK 版本及 epoch 分别核对，不原位修改历史契约摘要。确定新的 SDK/客户端发行版本与实际最低宿主版本，不能用相同版本号覆盖旧包。
3. 运行联合回归、类型检查、`pnpm check:whiteboard-boundaries`、`pnpm check:plugin-process-boundaries` 与 `pnpm check:docs`。保留明确的跳过原因；禁止用宽松断言、减少数据规模或丢弃分支换取通过。
4. 在协作包执行 `pnpm test:whiteboard-capacity`，记录机器、Node 版本、测试参数、编码字节和延迟分位数。以操作轮数描述加速长会话，不把它称作真实数小时在线验收；进程 RSS 不等于单文档堆占用。
5. 分别执行 `pnpm --filter @tau/whiteboard bench:hit`、`bench:render`。Profiler 是脚本测量，不替代真实设备的视觉/交互验收。存储上限不等于可用容量；对高负载延迟未达预期的版本不得承诺满额流畅编辑。
6. 本地打包 SDK，在仓库外编译作者示例与负向类型夹具，再构建模板。使用 `node scripts/plugins/verify-stickman-collaboration.mjs` 验证火柴人候选、宿主绑定与实际本地 Node 服务构建；检查脚本输出的产物摘要和原依赖/锁文件未改写断言。确认白板仅声明 desktop，旧路径 API、schemaVersion/migrate、Y.Doc 与通用 CAS 不出现在当前作者写入口中。
7. 核对普通界面的真实调用链：共享（白板状态行「共享」→ publish）、续做/取消（「继续共享 / 取消共享」→ publish-resume/publish-cancel）、成员打开（协作页侧栏白板 → remote-install）、网络收发（WhiteboardRemoteSync → remote-open/remote-sync）、保存失败与重试。运行 `collaboration-flow.test.ts`（真实服务端路由的两设备流程）与渲染端 remote/DocumentBoardCanvas 测试；交互功能须有真实界面消费者，不能只验证孤立 handler。
8. 使用隔离测试库和本地服务验证同源身份、旧快照拒绝、隐藏页与多窗口、回执丢失及各存储失败重试。旧增量留在原日志/outbox，未确认分支不能被新 epoch 接纳。本步骤不生成恢复包，不自动清理历史资源。
9. 在目标桌面系统完成由用户负责的中文输入、选择、拖动、缩放、媒体、插件缺失、关闭与重新打开验收。容量/长会话、产品入口、版本及设备任一门禁未满足时记录阻断，不以本地构建成功替代。
10. 所有门禁满足且另获授权后，才进入真实发行流程；本清单不包含自动发布、部署或真实数据迁移命令。

## 实时同步排查与验收

1. 两端运行包含实时接线的桌面构建，打开同一共享白板的同一页；在当前 `~/.editor/logs/session-*.log` 中检索 `[whiteboard-sync]`。
2. 确认两端出现「推送连接就绪」；持续输入与拖动时，发送端应有「本机耐久保存完成 / 实时增量发送」，确认对账另有「HTTP 完成」，接收端应有「推送应用完成 / 渲染端应用增量」，无需等到补偿轮询。对比同文档的修订与各阶段 elapsedMs；HTTP 失败先查 code/status/cause，不用两台机器墙钟计算延迟。
3. 由用户验收光标名字、选区、拖动预览、缩放后的坐标与中文输入。切到另一页不应显示原页光标；失焦、隐藏或关闭画布后在线标记应清除；拖动与松手后等待正式内容期间，选框与元素保持同位；本机也选中同一元素时亦如此。取消实时拖动会广播回滚，双方应恢复开始前的位置；一次撤销还原整次拖动，远端不产生本机撤销项。
4. 在隔离测试环境断开连接、继续编辑、恢复连接，确认缺失内容补齐且不重复写入；检查断线日志与重试间隔。运行桌面 `whiteboard-documents/__tests__/realtime.test.ts`、`collaboration-flow.test.ts`、渲染端 `remote.test.ts` 和白板包 `presence.test.tsx`。
5. 日志只有阶段与耗时，不能单独证明真实网络条件下的端到端延迟或视觉体验；完成目标设备验收后再判断是否达到产品要求。

真实拖动回归执行 `pnpm --filter desktop exec vitest run src/services/whiteboard-documents/__tests__/drag-realtime.test.tsx`：挂载两个真实画布，从 pointerdown/move/up/cancel 经渲染 outbox、SQLite 文档会话、本地真实 WebSocket 服务回到另一画布，分别断言未松手时的文档坐标与元素/选框 DOM 坐标。覆盖先选中/直接拖动、跨撤销捕获时间窗的长拖动、一次撤销与重做、取消/隐藏回滚，以及远端冲突后迟到松手；不以只更新临时预览作为内容实时同步通过。
