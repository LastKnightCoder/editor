# 现有业务的架构迁移

用于在现有应用里用端口与适配器收口长期演变的业务。以一个能从正式入口读写并重开的用例为最小迁移单位。正文是可对照实例。 [正文架构与持久化](/docs/architecture/content-storage.md)

## 1. 画出实际调用和数据边界

1. 从用户操作或宿主命令往下追到存储与通知，也从底层写入口往上反查消费者。逐一登记正式 IPC、表直调、后台任务、脚本、插件、跨端读写与恢复入口。
2. 对每条路径记录 `入口 → 权限和身份 → 业务行为 → 写入位置 → 提交后的结果 → 重开行为`。把业务调用与测试专用入口标清。
3. 盘点稳定身份、当前连接或租约、修订及幂等凭据。逐个写明生成者、生命周期、比较位置和变化后的处理。正文实例中，业务 `contentId`、稳定正文 ID、会话基线与远端序号分别用于不同边界。

交付物为调用方清单和事务范围。至少能从清单解释一次创建、复用、复制、删除以及一次失败重试。能指出两个业务对象引用同一数据时谁拥有修改权和回收权。

## 2. 先用独立判据锁定行为

1. 将每条关键路径写成“已知输入和操作 → 用户可见结果 → 持久结果 → 重开结果”。选择会区分行为的合成数据，例如同一正文有两个拥有者、目录多挂载、未知契约、异库同编号。
2. 从用户已确认的语义和业务不变量写期望，再记录旧实现的实际输出。旧实现与预期有差异时记录触发方式和处理结论。
3. 对数据直接从存储读节点身份、关系差集、计数与流水；对消息直接比较收到的回执或事件。回滚检查同时看目标与旁路数据。候选与基准使用同一输入和判定器。
4. 记录执行入口、环境、版本、实际依赖、替身、随机种子、负载和产物摘要。回归前后都保留失败原因与通过证据。

正文的独立判据包括“建卡再次共用同一正文只保留一份持有”“从项目条目每派生一张新卡就多一份持有”“解除目录最后一处时才释放条目的持有”。逐条将数量与身份写进测试预期。

## 3. 让端口表达用例所需的保证

1. 将模型校验、用例编排和宿主接线定位到能单独评审的代码。用例先声明实际需要的原子操作、输入校验、回执与失败形式，存储和网络适配器实现这些语义。
2. 聚合同一个 SQLite 事务内的正文、关系、计数和流水。异步转换先准备候选，落地前复核发起时记录的连接、身份、权限与修订。事务内发生故障时核对所有连带表；异步期间到达的新数据进入下一次保存。
3. 跨存储时写清每次状态更新的权威来源和允许的重试。记录原操作身份及输入指纹，未知结果按旧 ID 查询，确认终态后才执行不可逆的清理或解绑。
4. 将工厂、配置、存储和连接放到宿主组合根。共享逻辑经显式接口接入自己的运行时，生命周期由拥有对应依赖的代码控制。启动或关闭失败时核对已接纳数据、活动订阅和下一次重试入口。

评审端口时验证一个真实替换点和一个失败点。例如正文投影端口接受“带观察修订的提交”，调用方不需要直接更新块、关系和计数三个表。共享发布与退出还要确认只释放实际交接的会话。

## 4. 按可交付切片迁移

1. 先贯通一个本地读写、落盘和重开的生产入口，再迁移相邻的业务持有、替换和条件操作。先明确共同入口与实际顺序，再确定能无冲突并行的独立切片。
2. 每步沿用已确认的行为夹具和外部命令。每个切片完成后检查实际调用已指向新用例，复核短路、过期修订和失败回滚。删除旧路径前用 `rg` 核对消费者清零。
3. 多 Agent 并行时明确文件所有者、接口、可更改范围、独立测试输出和合并人。合并人验证同一个候选构建，统一对账文档、数据格式和真实入口。阶段内只维护一份执行状态。

## 5. 用已知故障反查设计

| 评审问题                                     | 可重放的检查                                                                               |
| -------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 异步完成后是否仍写原意图？                   | 在资源准备中插入另一笔提交或切库，复核原修订失败且不覆盖新数据                             |
| “保存成功”指哪次提交？                       | 分别在日志提交前后、主库事务前后强退，独立读取存储并重开核对                               |
| 重试会不会重复效果？                         | 丢弃已处理的提交响应和查询响应，重开按同一 ID 查终态，核对业务行、流水或远端序号只变化一次 |
| 主库提交了，另一个存储还没来得及更新怎么办？ | 在真实事务返回与下一份日志安装之间强退，按主库身份和已保存的候选继续交接                   |
| 派生数据漏了事件怎么办？                     | 核对事件路由使用实际登记的连接。投递旧索引文件或删掉派生库，再从主库重建并通过正式查询核验 |

## 6. 放行与沉淀

1. 对受影响路径补定向回归、正式构建与真实入口。跨端验证明确哪一层用了替身。性能比较固定机器、输入、负载和阈值，快速正确性结果与正式容量、长稳分别记录。
2. 将用户操作、实际设备、输入法、焦点、视觉及真实服务配置单列，写明步骤与通过条件。正在进行的验收记录具体门槛和最近证据。
3. 将现状写入对应架构文档，将可执行验证写入指南，将可复用夹具和故障驱动留在代码旁。更新文档索引并运行 `pnpm check:docs`。仅保留仍有退出条件的任务条目。
