# 知识库合并到项目实施记录

## 已确定的约束

- 统一为文档树项目，不保留知识库业务入口或旧协议。
- 保留正文身份、标签、树顺序、多父关系、时间及置顶；根正文并入项目描述。
- 桌面、CLI 和移动端均支持独立升级，映射规则跨端一致。
- 沿用同步目录；发布前必须停用全部旧端，迁移不自动上传。
- 旧博客地址不兼容；发布范围不扩大，旧文件在新文件上传成功后清理。
- 真实用户数据库不用于开发验证；测试仅使用临时库。

## 当前发现

- 桌面普通重连不执行表的 upgradeTable，迁移必须放在两种开库模式的公共入口。
- 项目 upgradeTable 会删除无归属节点，迁移必须在清理前完整建立关系。
- CLI DataAccess 直接打开 SQLite，需要单独接入迁移。
- 协作服务器的 documents 是房间表，不属于删除范围。
- 真实历史库存在三类旧版删除残留，迁移按确定性规则处理而不是拒绝开库：悬空 children 引用（删子节点未清父引用）剔除并计入 `repairedDanglingRefs`；从任何知识库根不可达的孤儿节点收拢进新建的「未挂载文档」项目（`recoveredOrphans`/`rescueProjectId`），正文与内部关系保留、引用正常映射，孤儿子树不经拓扑传播、其内部成环不阻塞；指向已删除知识库的 publish_selections 行直接清除（区别于 publish_history 的置空保留）。可达子图的循环、缺失正文、悬空的 JSON/发布节点引用仍然失败回滚。

## 实现入口与运行约定

- Node 核心：`packages/db-schema/src/knowledge-migration.ts`；桌面所有开库模式及 CLI DataAccess 共用 `upgradeKnowledgeDatabase`。Rust 核心为 `apps/mobile/src-tauri/src/database/knowledge_migration.rs`，移动端主库结构版本升为 3。
- 模型版本为 1，写入 `migration_meta.data-model-version` 和远端同步元信息 `dataModelVersion`。完整报告保存在 `migration_meta` 的 `knowledge-to-project:v1` 键，包含根、节点映射和修复的派生关系数量。不含任何业务表的空库文件（旧版 CLI 可能创建）只登记模型版本，不进入建列流程。
- Node 备份为数据库相邻的 `.pre-knowledge-v1-<uuid>.bak`，同库已存在备份时复用首份（迁移失败重试不膨胀）；移动端沿用 `.pre-schema-v3-<uuid>.bak`，同样复用。同步下载的临时验证库不产生备份。桌面独立协作缓存升级前另建快照。备份不自动删除。不含知识库数据的库（全新库、仅用过项目的库或旧版 CLI 空壳）只补齐项目列、包装旧版纯文本描述并登记模型版本，不产生备份，也不登记迁移映射。
- 原正文 ID、创建时间、引用计数不变；源节点一对一搬迁，不按正文或名称合并。已删除实体的操作历史保留为 retired 类型，避免旧 ID 被误解释为现有项目；旧版本删除知识库节点时遗留的协作绑定按正文存活性处理：正文仍在的降级为 `retired-document-item` 来源，正文已删的死行直接清除。
- 正文、项目描述、聊天消息和运行快照、白板、数据表格、闪卡数据、学习资源来源及待办关联均处理历史引用。代码围栏、行内代码及普通文字不做实体名称替换。
- 主库映射也用于索引身份迁移；已有向量直接复用，不因改实体类型重算全部嵌入。协作通过 Yjs 属性事务转换引用，多端转换后合并不重复正文。
- 旧 `content_link.source_type=document` 的来源语义无法可靠判定时拒绝迁移；循环、缺失正文、悬空引用等也会明确失败并回滚，不猜测或静默丢弃。
- 桌面与移动端下载先验证并迁移临时数据库，成功后再替换本地文件；即使跳过即时重连也必须经过验证。替换主库后本地索引的 ID 空间整体失效，桌面经 `reset-content-index`、CLI 直接删除索引文件、移动端在替换后重置索引（删除前先把索引重建状态标记为 pending，文件删除失败时残留索引也会在下次开库触发全量重建），均改为按需全量重建，不做旧索引增量转换。移动端索引连接与升级事务均带 busy_timeout，升级事务以 BEGIN IMMEDIATE 立即取写锁，避免与后台写入并发时以裸 BUSY 失败。已迁移库的映射在移动端按库路径缓存，随连接失效一并清空。CLI 同步关闭自身缓存连接，拉取后在启用和更新版本前迁移，失败恢复备份；拉取路径的迁移跳过额外备份（本地副本已由 pull 自身的备份承担）。CLI 构建和类型检查同时修复了既有的 JSON 配置项、RPC 泛型、stdout 回调类型和缺失的 OSS 类型依赖。

## 发布与回滚

1. 所有桌面、移动端及 CLI 停用旧版；保留各端尚未同步的数据副本。
2. 升级后各端可独立开库迁移，但不自动上传；选定最新完整数据库作为首次同步基线。
3. 同一旧快照产生一致映射；不同设备已分叉的数据仍按整库同步冲突处理，不承诺自动合并。
4. 博客重新发布后使用项目地址；旧地址允许失效，上传失败时旧产物和历史保留以便重试。
5. 回滚使用迁移前主库及协作缓存备份。已有迁移后编辑时先另行保全，不直接用旧库覆盖新内容。
