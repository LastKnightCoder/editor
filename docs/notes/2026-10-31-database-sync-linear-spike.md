# 线性数据库同步与完整冲突副本验证

2026 年 10 月 31 日，分支 `codex/database-sync-spike`。本次采用简化方案：线性事务增量、快照兜底、完整资料库冲突副本；能证明独立的修改自动接续，不逐表实现语义合并。

电脑修改已有笔记 A、手机修改已有笔记 B，可以自动得到两边的新内容。完整副本是冲突或证据不足时的保底，不要求所有双端修改都人工选择。21 个专项用例通过；前几轮实验代码保留对照，不作为新方案的处理器依赖。

## 自动处理的边界

| 场景                               | 处理                                         |
| ---------------------------------- | -------------------------------------------- |
| 共同版本之后仅一端编辑             | 沿主线顺序复制完整事务                       |
| 两端写入不同记录且读取依据未变化   | 在当前主线重放并生成新的线性提交             |
| 两端修改同一条正文记录             | 保留整库副本，不逐字猜测合并                 |
| 写入不同但查询、父级或计算依据改变 | 保留整库副本                                 |
| 不同记录竞争唯一业务键             | SQLite 拒绝候选事务，整体回滚并保留副本      |
| 同一整数主键被两端用于不同新内容   | 识别为冲突，分别保留，不混淆实体             |
| 不知道业务依赖的任意 SQL           | 只沿原主线复制，分叉时不自动重放             |
| 主线旧日志已经回收                 | 使用当前行版本判定独立；返回快照而非缺失增量 |
| 本机也丢弃了待发送增量证据         | 主线未变可整库快照接续；主线已变则保留副本   |

自动处理以完整的读写依赖为前提。两行不同不代表业务互不影响：例如删除分组与另端新增其下待办、两个对象竞争唯一键、两个事务分别读取对方状态后修改自己。

## 通用事务入口

[线性副本实现](/scripts/spikes/database-sync/linear-replica.mjs) 只按当前 SQLite Schema 发现字段、主键、可用的非空唯一键及外键，不导入先前的领域契约、逐行 LWW 或恢复代次模型。

所有 98 张表安装通用变更捕获，保留事务内的操作顺序及每次写入的前后值。任意业务 SQL 只要来自共同主线，就能按事务结果复制；新路径没有前一方案的 70 表门禁。

记录的内容包括父提交、资料库代次、原操作身份、读行版本、查询范围的表版本和写入结果。它们用于判断能否接续，不解释“金额”“循环日程”或“复习排程”的业务含义。

两类入口互相配合：

- 原 SQL 入口默认保守，只能沿相同基线复制，不在分叉后自行合并。
- 已确认能完整记录依据的入口，可使用 `transaction(fn, { scoped: true })`。`read` 记录读行，`expect` 检查缓存中的观察版本，`scan` 保守记录表级范围，`insert`、`update`、`remove` 记录写入。`exec` 会退回保守模式。

任何来自编辑器缓存或其他查询结果的依据，都必须刷新读取或携带观察版本。未遵守这个约定的业务代码不能安全启用自动接续。原型没有证明任意 SQL 的完整读集，也没有自动分析应用内存中的依赖。

业务代码需要配合的重点是统一写入口、保留已有的修订检查，并把公共统计、搜索索引和本机维护与共享事实分开。若每次保存正文都更新同一条每日计数，两个不同笔记仍会因共同写集而冲突；不应通过同步层猜测如何累加来掩盖它。

`scan` 只用于实验中的范围守卫验证。正式查询应继续使用 LIMIT 和索引，以表版本保护查询范围，不照搬全表读取。

## 安装结果而非重跑业务

接收端安装来源事务已经完成的行结果，不再次执行业务动作或外部副作用。普通业务 SQL 触发器在安装期间统一停用并在同一事务恢复，避免重复计算。

SQLite 自身的外键级联仍可能改变更多记录，因此接收端继续审计实际写集及最终行值。若级联碰到来源事务没有声明的行，整次候选回滚，随后保存完整副本。验证中覆盖了父级删除可能误删另一端后来新增子项的情况。

完整库安装按外键依赖顺序处理，先删除子表，再装父表；使用真实的 RESTRICT 外键和白板 BLOB 验证，避免只在空表上证明快照可用。Schema 跨表依赖环没有额外处理策略，遇到不支持结构时拒绝安装。

同一记录删除后重建，即使数据值完全相同，行版本也已经改变，旧写入不会通过比较。这里使用通用行版本及整库代次，不维护每个业务对象专用的删除恢复协议。

## 线性增量与快照兜底

正常请求只携带待提交事务及状态摘要，响应只携带主线的有序后继事务。双方正常同步不上传完整库体。

若本机已有未确认事务，接收确认后的主线时，先在本地事务内恢复最后确认状态，再安装主线后继。所有本机提交必须已被发布者确认，或已作为完整副本保全，才能清掉待发送记录。

主线日志被回收后，仍保留轻量回执和行、表版本。旧设备保留了依赖证据时，不同记录仍可自动接续；下载侧改用快照，不假装旧增量仍然存在。

本机也可压缩待发送日志，保留当前完整库和未确认身份。此时证据不足，不再尝试通用事务重放：主线没有变化就快照接续；主线已有修改就保存完整冲突副本。这个保守降级避免为了减少日志而丢失编辑。

同步响应到达期间若用户又有输入，安装前的本机头版本检查会拒绝覆盖，下一轮重新提交。安装、待发送状态、版本元数据和确认状态共同提交；异常或进程退出时共同回滚。

## 完整副本与主版本选择

冲突时先在发布者的 SQLite 事务中持久保存来源完整快照与真实数据库副本，才允许来源对齐当前主线。它不是一段差异文本，也不只包含冲突记录。

副本包含当前主库 Schema 的全部 98 张业务表、索引、约束、触发器与 BLOB，可通过 `exportBranch()` 导出为独立 `.db` 文件。它不包含库外图片附件、AI JSONL、设置文件或此前的备份目录；正式资料库副本仍需配套文件清单。

用户可以继续保留当前主线，也可以选择某个完整副本作为新主线。选择副本时：

1. 检查选择界面观察到的主线头版本，期间有新修改则拒绝旧选择。
2. 将当前完整主库另存，保留未选版本。
3. 原子安装所选副本并生成新的资料库代次。
4. 干净设备通过快照对齐；旧代设备的未确认修改再次保全，不写进新选择。

选择是整个资料库级别的决定，不会自动从两份库中挑选各自更好的笔记。选择前后两份完整副本都保留，可以再次选择。原型提供回环 HTTP 的副本列表和选择接口，没有制作界面。

## 验证结果

21 个专项用例覆盖：独立笔记自动接续、读依赖与范围变化、唯一键冲突、新内容 ID 碰撞、删除重建、SQLite 额外级联写入、真实外键及二进制备份、双向增量、长期离线与双端日志压缩、安装中断、进程直接退出、选择期间版本变化，以及选择后的继续同步。

一次 HTTP 探针的资料库快照为 1194205 字节。电脑和手机分别修改不同笔记时，请求为 1521 字节、响应为 3374 字节，未上传整库。主线日志清理到 0 后，离线修改仍可接续，返回路径使用快照。发生冲突后生成两份可导出的 SQLite 副本，选择手机版本后继续编辑与同步通过。

上述数字是固定小样本的协议载荷，不是性能承诺。原型仍计算全库摘要、维护本地确认快照，存在明显本地开销；完整副本也需要相应磁盘空间。

## 适用边界

本次只操作临时数据库，未接入实际桌面或移动业务命令。不同笔记真实自动接续还依赖写入口正确记录依据，以及剥离共享统计和本机派生写入，不能用这组存储探针宣称完整应用已验收。

要求相同的 Schema 和协议。版本不匹配时拒绝互传，不自动把旧库按新列解释。配对鉴权、移动后台、Rust 协议 4、真实应用中的缓存释放和查询刷新尚未接入。此前 Rust 协议 2、3 的验证不等于已经支持协议 4。

完整快照当前上限 64 MiB，HTTP 请求上限 16 MiB；大库应复用分块传输。未测试任意体量、磁盘不足或断电设备。冲突副本不自动删除，轻量操作回执与删除后的行版本仍会增长。

运行说明见[实验入口](/scripts/spikes/database-sync/README.md)。使用 `node scripts/spikes/database-sync/verify-linear.mjs --keep` 可保留演示副本并得到路径，供独立 SQLite 工具检查。
