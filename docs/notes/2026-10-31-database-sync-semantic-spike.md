# 数据库同步约束恢复与大字段差量方案验证

2026 年 10 月 31 日。分支 `codex/database-sync-spike`。本次在真实主库 Schema 上扩展实验协议，解决原始行复制暴露的唯一键冲突、孤儿关系、删除后恢复与大字段日志放大问题。

这四类问题都有可落地的处理方式：保存全部修改事实，再按显式领域规则生成活动数据；恢复引用具体删除并切换代次；大字段按已知版本生成差量，并将历史状态保存为可复用的压缩内容块。26 个用例全部通过，包含上一轮 17 个验证及反例。

## 方案与取舍

| 问题                           | 本次选择                                                                 | 代价与边界                                                     |
| ------------------------------ | ------------------------------------------------------------------------ | -------------------------------------------------------------- |
| 两个不同对象竞争同一业务唯一键 | 按逻辑时钟和来源身份选出一个活动对象，完整保留另一个对象及其关联到冲突区 | 不自动合并不同对象的内容；改名或显式处理后可恢复活动状态       |
| 父对象缺失或删除               | 未知父对象的子项暂存；已知父对象已删除时，将子项投影到待整理，保留原父级 | 按关系类型声明，不能用统一级联删除代替所有业务语义             |
| 删除后恢复                     | 恢复指向已观察到的具体删除，在原 ID 上开启新一代；旧代操作只进入历史     | 需要明确的恢复命令与代次元数据，不能用普通 INSERT 或时间戳模拟 |
| 大字段重复记录                 | 只记录变化字段，大值使用带基线摘要的字节差量；历史行复用压缩内容块       | 增加编解码 CPU；差量依赖的历史暂不回收，不自动合并并发文本意图 |

直接合并两个竞争唯一键的对象，会混淆原身份与引用；静默改名则会改变插件的业务键。冲突区让系统继续同步，同时保全需要用户或领域代码裁决的材料。

孤儿对象直接级联删除可能丢失另一台设备离线新增的内容；自动复活原父级则会推翻删除意图。待整理保留子对象，允许用户重新归类。恢复父级只收回仍保持原归属的子对象。

恢复不是撤销墓碑本身，而是一个新的、可验证的业务事件。删除只压制同一代的旧修改；已恢复的新代不会被迟到的旧代编辑或删除覆盖。

## 实现

[共享捕获与提交管道](/scripts/spikes/database-sync/replica.mjs) 继续为真实主库的 98 张表安装捕获；[协议 2 实验](/scripts/spikes/database-sync/semantic-replica.mjs) 复用其事务、日志、来源进度、传输与回滚流程，增加领域投影和恢复协议。[字段编解码](/scripts/spikes/database-sync/field-codec.mjs) 处理大字段。没有修改正式 Schema 或应用入口。

协议 1 保留，用于复现原始方案的失败模式。协议 2 的信封、基线与副本都有版本标记，双方不能混用。原生 Rust 探针仍只支持协议 1，已增加格式检查，防止误写协议 2 副本；本次没有实现 Rust 版的协议 2。

### 唯一键与关联

对 `plugin_entities(plugin_id, kind, key)` 和 `plugin_links(from_id, to_kind, to_id, role)` 声明唯一键策略。每条原始修改先保存到不可变日志及版本记录，再从已知事实确定活动记录。

未采用的实体进入冲突区；以其为来源的关联也进入冲突区，不留下指向不可见来源的活动关联。不同设备依据相同事实集得到相同活动对象和冲突区，后续无关事务可以继续确认。

对冲突对象执行 `editPreserved()` 改名后，原 ID 和关联可重新出现。删除当前活动对象时保留该唯一键的删除声明，已知的较旧竞争对象不会仅因位置空出就自动顶替；更晚的显式修改仍可按版本规则重新竞争。

这些规则没有扩展到所有索引、金额累加、唯一性范围或对象合并。未声明策略的 SQL 约束仍可能拒绝提交。

### 孤儿与待整理

`todo_item.group_id` 使用以下规则：父分组正常存在则按原归属呈现；从未出现的父级使子项暂存，父级到达后自动呈现；父级有删除事实时，子项暂时显示在待整理。

待整理是本机确定性投影，不写成新的原始归属。用户仅修改标题时，原分组引用保持；用户显式改到另一分组时，新的归属进入日志。父分组恢复后，前一类回到原分组，后一类保留用户的新选择。

实验使用 `-1` 作为待整理组的保留编号，正式接入须为该系统组分配同步组内稳定身份。父子环、项目树、正文持有关系与全部插件引用仍需各自声明策略。

### 删除代次与原子恢复

每个行版本增加代次和恢复来源。普通写入沿用其基线版本的代次；删除在同一代优先。恢复必须引用已观察到的删除事件，保留原主键，并将代次加一。

恢复材料取自该删除明确引用的前一版本，不采用删除后才到达的旧代编辑。再次删除和恢复继续推进代次；并发恢复进入同一新代，按稳定版本顺序收敛。过期的恢复凭据或没有观察到目标删除的操作会被拒绝。

`restoreMany()` 将一个业务对象的多张表放进同一事务恢复。实验使用真实有外键的 `contents` 与 `content_documents`，连同 `cards` 验证：本机发现任一删除凭据过期时不恢复任何一行；接收时中断也不留下半个对象。

正式业务还需将最近删除、撤销凭据、稳定实体身份和引用计数纳入对应聚合。不能据此将任意单行恢复直接接入现有界面。

### 字段差量与内容分块

普通修改只发送变化字段。大文本和 BLOB 使用原行版本作为基线，按 UTF-8 或原始字节计算前缀与后缀之间的替换区间；同时携带基线摘要、结果摘要与长度。接收端验证摘要后才能安装。

大字段创建或无法有效生成差量时，使用 Brotli 压缩快照。编解码会比较快照与差量的信封大小，选择较小者；单字段结果上限为 16 MiB。

历史行不重复保存大值全文，而保存内容块引用。分块边界由滚动内容指纹确定，最小 2 KiB、最大 16 KiB；块用 SHA-256 寻址并独立压缩。这样在文本中间插入内容时，后面的分块可重新对齐，不会因固定偏移整体移动而全部失效。

内容块、版本、事务日志、活动投影和确认进度在同一 SQLite 事务提交。损坏差量或投影中断不会推进进度，也不会留下这次写入的新块。

字节差量只优化传输与历史存储，不负责合并并发文字。正文和白板正式接入时仍须遵守现有 Yjs 基线与内容协议，避免两套通道相互覆盖。

## 验证结果

完整运行 26 个用例，26 个通过、0 个跳过；原生协议 1 互通用例继续通过。新增场景覆盖如下。

| 场景                                                             | 结果                                                         |
| ---------------------------------------------------------------- | ------------------------------------------------------------ |
| 三台设备离线创建同业务键实体，各自附带关联，再产生后续事务       | 一个活动对象，其余实体与关联保全，后续事务继续确认，三端相同 |
| 冲突对象改名                                                     | 原 ID 与关联重新呈现                                         |
| 删除活动对象                                                     | 较旧冲突对象未自动顶替                                       |
| 删除分组与离线新增子项并发                                       | 子项进入待整理，不丢失                                       |
| 待整理中只改标题或显式重新归类，再恢复父级                       | 前者回到原归属，后者保持新归属                               |
| 子项引用尚未出现的父级，父级稍后到达                             | 子项先暂存，随后正常呈现                                     |
| 恢复后才收到更高逻辑时钟的旧编辑和旧删除                         | 新代保持，旧操作不覆盖                                       |
| 重启后再次删除、恢复，以及并发恢复                               | 正确推进代次并收敛                                           |
| 三表恢复凭据过期或接收一半失败                                   | 行、日志及确认共同回滚，合法重试成功                         |
| 不易压缩文本连续局部修改，差量损坏、写块后中断、重启经 HTTP 追赶 | 损坏不确认，失败无新增块残留，重启后精确补齐                 |
| 随机二进制只改一个字节                                           | 按差量还原全部原始字节                                       |
| 协议 1 收到协议 2 信封                                           | 明确拒绝                                                     |

随机文本样本约 96 KiB，中间连续插入 30 次。本次测试的网络信封合计 18657 字节，新增压缩块合计 467860 字节；整列前后值重复记录的量级为 5907240 字节。随机内容影响分块边界，因此新增块大小会随样本变化。

## 本机对比测量

Node.js 24.21.0、SQLite 3.53.4，真实 98 表 Schema，WAL 与 `synchronous=FULL`，回环 HTTP。两种协议各预热一次，再交替顺序运行三轮，耗时取中位数。大字段样本与第一轮实验相同，为 98304 字节的重复中文文本，连续保存 30 次。

| 项目                           | 原始行复制   | 协议 2      |
| ------------------------------ | ------------ | ----------- |
| 1000 次独立小记录事务          | 129.49 ms    | 325.89 ms   |
| HTTP 追赶 1000 个事务          | 216.14 ms    | 266.91 ms   |
| 小记录事务的传输载荷           | 476336 字节  | 589336 字节 |
| 30 次大字段修改的写入时间      | 95.41 ms     | 179.53 ms   |
| 30 次大字段修改的网络增量      | 5912499 字节 | 16453 字节  |
| 正文历史行中的前后状态或块引用 | 6001339 字节 | 20331 字节  |
| 压缩内容块总量                 | 无独立块     | 215 字节    |

重复文本极易压缩，不能将这一比例推广到任意正文。上面的随机文本验证同时证明，差量收益不只来自重复文本的压缩。存储数字是表内载荷字节数，不是 SQLite 物理文件大小，也没有扣除需要保留的初始基线。

新协议对小记录增加代次、基线和字段编码元数据，写入及验证更慢，载荷也更大。收益主要来自大字段变化与历史复用；正式实现应对小值减少重复验证与封装，按适当边界合批。以上没有给出移动设备性能承诺。

三轮小记录写入分别为：协议 1 的 129.49、127.03、134.26 ms；协议 2 的 307.25、332.95、325.89 ms。HTTP 追赶分别为 213.90、216.14、222.64 ms 和 266.91、301.15、260.22 ms。

## 后续接入边界

这次验证解决的是可复用机制及代表领域，没有为全部 98 张表完成裁决。正式实现仍须列清每个领域的自然键、拥有关系、删除聚合、恢复聚合与派生数据，不直接把所有表按原始行复制。

约束投影目前重建受影响的代表表，便于检验到达顺序无关和事务回滚。正式版本应按冲突键及关系组件增量更新，并维护稳定身份、引用持有与应用缓存，避免整表重建和错误回收。

差量依赖的行版本、删除代次和内容块全部保留。本次没有实现检查点、成员确认水位、设备退役或安全回收；长期离线设备仍依赖完整历史追赶。后续回收必须先建立包含代次与业务状态的共同检查点，并让落后设备重新安装检查点后重放其未上传修改，不能直接按保存天数删日志。

Rust 协议 2、真实移动端与 Electron 接入、局域网配对、后台生命周期和对用户可见的冲突处理仍属于后续范围。复现命令见[实验说明](/scripts/spikes/database-sync/README.md)。
