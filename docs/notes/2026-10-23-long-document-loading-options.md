# 长文档打开的轻量方案评估

本次只评估，不修改业务代码。视口级挂载按用户要求暂缓，未排期。

## 实测依据

现有实现的同文档开发版实机基线：正文完全就绪 16.46 秒；单次完整解析约 2.18 秒，约占 13%；正文与格内输入中位数分别为 72ms、64ms。剩余时间包含其它初始化、React 挂载和浏览器布局，不能全部归为解析。

以下数值是工程估计和原型验证目标，不是新一轮实测。

## 解析隔离

主要收益是将约两秒解析计算移出文档界面线程，让这段时间里的窗口和加载反馈更容易响应。解析仍需计算，完整编辑器仍依赖结果；单纯更换执行进程通常不能把 16.5 秒直接减去 2.2 秒。只有与独立初始化重叠或提前解析时，才可能缩短对应的关键路径；理论上完全覆盖这次解析，也只是约 13% 的当前耗时。

代价包括进程通信、节点结果复制、额外内存、冷启动，以及同步流程异步化后的取消、文件修订、迟到结果和插件快照一致性。首次可见与可编辑时间可能基本持平或略增，不应承诺打开显著提速；稳态输入延迟也不会由此直接下降。

仓库已有 ContentExecutor 和 parse 操作，可以借用隔离能力，但当前执行器串行排队；与后台内容任务共用时，需要避免交互打开排在长任务后面。主进程在没有插件时采用的内置同步转换也不能直接视为界面解析的合适替代方案。

投入判断：中等。收益偏界面响应，异步数据协议的回归面较大。

## 先显示只读首屏

主要收益是提早看见真实内容。按当前约 0.84 秒页面资源加载和 2.18 秒解析计算，首屏首次可见可将 **4–6 秒**作为原型验证目标，相比当前有望提前约十秒；复杂首屏和资源仍可能超出，必须实际复测。文章详情已有只读首屏模式可借鉴，Markdown 文件应使用自己的 kit 与文档生命周期，不能直接带入文章业务装配。

完整可编辑时间仍预计在当前十几秒量级，额外预览与交接也可能略增成本。它不直接降低全文 React/DOM 挂载总量或现有输入延迟；后台准备完整编辑器时，界面仍可能出现主线程停顿，不能承诺预览阶段始终流畅。

主要损失是过渡阶段只能阅读首屏，完整编辑、全文查找与远处目录跳转需等编辑就绪。需按渲染成本限制首屏，防止单个巨大表格撑爆预算。交接必须保留阅读位置、控制选择和焦点，避免抢焦点与滚动跳动；只读预览不参与正文保存、Y.Doc 或撤销历史，不能通过部分正文覆盖完整文件。

投入判断：低到中等。主要是展示层和挂载调度，已有模式可参考；仍需完整的关闭保存、切换文件、源码、外部更新和交接回归。

## 建议

针对“Loading 很久才看见正文”，优先验证只读首屏；解析隔离后续按界面长任务与响应问题决定。两者可以组合，但收益不能简单相加。视口级挂载保留为后续方向，本次不启动。
