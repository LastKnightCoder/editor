通用升级提示能力 · 设计与抽象说明

1. 为什么要提取成「通用升级提示能力」？

目前仓库中已有 5 类「旧版遇到新版数据或能力，需要升级 Tau」的真实场景，却各自散落成不同形态（有的只弹一句「保存失败」红条、有的是死锁标签无入口、开库失败则是裸文本按钮）。提取为统一能力后，任何业务域只需声明「为什么需要升级 + 数据是否安全」，升级检查、进度、重启安装、官网兜底、移动端 Android/iOS 分流全部由宿主闭环承接。

2. 三方案核心差异

方案呈现形式最适合
方案 A（推荐） 标准 Dialog + 安心保护条 + 内嵌 useUpdateStore 状态卡（+ 可折叠原因对照） 全场景通吃、零跳转一步完成更新；非阻断入口配轻量 UpgradeInlineNotice 点击唤起同弹窗
方案 B Dialog 内默认展开「旧版 vs 保护」情景对照块，更新态收进 footer 状态微行 偏重向用户解释技术差异，但在下载进度/报错/非字段类场景略局促
方案 C 表单内非模态暖底横幅（带「还原时间」继续存标题），拖拽/后台走右上角通知卡 轻打断，但多载体心智分散、无表单容器时需二次跳转

3. 跨端共享契约（@tau/shared/upgrade-prompt）

export type UpgradePromptReason = | "calendar-timezone-write" | "whiteboard-readonly" | "collaboration-incompatible" | "plugin-min-version" | "db-model-incompatible" | "content-source-unsupported"; export interface UpgradePromptRequest { reason: UpgradePromptReason; title?: string; // 缺省按 reason 取 i18n 预设 description?: string; context?: string; // 对象徽标，如「产品评审」「v0.63.0+」 dataSafety?: string; // 数据保护承诺，消除焦虑 minAppVersion?: string; // 最低所需版本 explanation?: { // 可选「了解原因」对照 triggerLabel: string; rows: { label: string; text: string; tone?: "warn" | "ok" }[]; }; secondaryAction?: { // 可选业务脱困动作（如还原时间） label: string; onClick: () => void; }; critical?: boolean; // 启动门禁不可关闭 }

4. 两端宿主与错误识别分层

• 错误分类器：parseUpgradeRequiredError(err) 集中识别 CALENDAR_TIMEZONE_UPGRADE_REQUIRED（兼容现有 trigger 文案）、DB_MODEL_INCOMPATIBLE、WHITEBOARD_DOC_VERSION_TOO_NEW、UNSUPPORTED_CONTENT_SOURCE 及统一前缀 UPGRADE_REQUIRED:<reason>。

• 桌面宿主：app/upgradePromptStore.ts（遵循 features 域禁止互引 store）+ UpgradePromptHost（与 ReleaseNotesDialog 同挂 AppShell，直连 useUpdateStore）；开库 BootState 复用同一内容体 embedded 渲染。

• 移动宿主：复用同一 UpgradePromptRequest 契约，以 BottomSheet 承载；Android 直连 useAppUpdate 展示下载进度与系统安装器，iOS 隐藏应用内下载改为「前往 App Store 更新」。
