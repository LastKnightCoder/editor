# 长文本正文编辑性能定位

日期：2026-10-23。

## 范围与结论

用户确认卡顿发生在 Markdown 文件窗口的正文富文本编辑，源码模式尚未测试。本次没有读取参考文档正文，也没有编辑用户文件；使用五万字合成内容复现输入链路。

已证实的共性问题是：局部编辑触发大量无关段落更新、选区变化也做全文 JSON 比较、Markdown 读取反复生成整篇正文、正文输入重置隐藏源码视图。已对这四处落地优化。尚未采集用户真实窗口的 CPU/渲染轨迹，因此不能声称已解释真实文档全部卡顿，或将测试耗时等同于实际输入到绘制的延迟。

## 可复现证据

测试环境为当前工作区依赖、React 开发运行时和 Vitest/jsdom。段落测试通过 React Profiler 记录真实段落子树的提交，未替换编辑器行为；文档会话测试运行真实 Y.Doc/Slate 绑定与 Markdown 转换。时间仅为诊断样本，未作为测试通过阈值；调用次数和更新范围有行为断言。

| 场景                                    | 优化前         | 优化后               |
| --------------------------------------- | -------------- | -------------------- |
| 500 段 × 每段 100 字，移动一次光标      | 500 次段落提交 | 0 次                 |
| 同一文档输入一个字                      | 500 次段落提交 | 1 次                 |
| 上述每次选区变化/输入的全文 JSON 序列化 | 各 2 次        | 各 0 次              |
| 无正文变更，连续读取 Markdown 10 次     | 10 次全文转换  | 0 次                 |
| 正文输入两次时隐藏源码编辑器 setValue   | 每次输入同步   | 0 次，进入源码时同步 |

未同时运行构建的首次诊断样本：段落选区操作约 25.0ms、输入约 21.1ms；第一轮优化后约 7.6ms、7.0ms。重复读取 Markdown 十次约 14.9ms，优化后约 0.03ms。并行构建和测试时采样会波动，不能由此推算真实窗口提速倍数。

## 原因与实现

### 全局订阅穿透组件 memo

段落、普通列表项使用 `useSlate()`，整份编辑器状态变化会通知所有实例。即使外层元素和段落组件有 memo，内部 Context 订阅仍会导致更新；现有 chunking 也不能屏蔽这类订阅。

段落改为静态取得 editor，只订阅“是否为同级末尾”的布尔值；列表项只订阅“父列表是否为无序列表”。使用 `findPath` 的 selector 设置 `deferred: true`，避免容器移动时读取 Slate 渲染前的旧索引。保留了插入、删除、移动、父列表类型切换后的正确显示。

对应代码：[Paragraph](/packages/editor/src/core/extensions/paragraph/components/Paragraph/index.tsx)、[ListItem](/packages/editor/src/extensions/list/src/extensions/list-item/components/ListItem/index.tsx)。这也符合 [Slate 官方性能指南](https://docs.slatejs.org/walkthroughs/09-performance) 对精确订阅的建议。

### 全文比较进入光标操作路径

CoreEditor 的通用 onChange 在选区变化时同样执行，对新旧正文各做一次 JSON.stringify；工作量随全文大小增长，还分配大字符串。

改用 Slate 不可变 `children` 引用区分内容更新，选区通知独立保留。此判断依赖 Slate 的更新契约，节点修改仍必须经 Slate 操作完成。

对应代码：[CoreEditor](/packages/editor/src/core/CoreEditor.tsx)。

### 正文快照与保存读取重复投影

Markdown 会话每次事务先读取一次正文用于快照，再读取一次用于序列化；getText 每调用一次又重新读取、转换全文。自动保存即使最终发现文本未改变，每 500ms 的轮询也已经付出了转换成本。

现在每次事务只读取一次正文、生成一次 Markdown 快照；getText 先 flush 尚未提交的 Slate 操作，再返回该快照。原文格式保留、转换失败时保留原文、撤销与磁盘冲突语义维持原协议。

对应代码：[markdownDocument](/apps/desktop/src/features/markdown-window/markdown/markdownDocument.ts)。

### 隐藏视图仍同步全文

源码编辑器常驻挂载，原先每次正文变化都向其 setValue。CodeMirror 同时配置了 `viewportMargin: Infinity`；由此产生的全文重设工作并不因界面隐藏而自动消失。真实耗时仍需浏览器采样，此次只对是否发生重设作了行为验证。

现在正文模式不更新隐藏源码编辑器，进入源码模式时再同步最新文本；源码模式下的撤销、重做和外部修改继续同步。

对应代码：[MarkdownFileView](/apps/desktop/src/features/markdown-window/markdown/MarkdownFileView.tsx)。

## 后续方案与取舍

| 优先级   | 方案                                                                     | 收益与成本                                                                           | 进入条件                                   |
| -------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ | ------------------------------------------ |
| 优先验证 | 对真实窗口采集输入 CPU、长任务、布局和绘制轨迹                           | 区分剩余时间究竟在 Slate、转换还是浏览器布局；不改变文档协议                         | 用户重测后仍有明显卡顿，或需量化端到端收益 |
| 下一阶段 | 按变更块缓存 Markdown、字数和大纲；转换脱离逐键输入路径                  | 继续减少与全文规模相关的同步计算；需处理外部修改、撤销和插件 codec 变化的失效        | 轨迹显示转换/投影仍占主要开销              |
| 下一阶段 | 对 100/200/500/1000 节点 chunk 做实机对照，复杂块内部按视口延迟高亮/预览 | 当前 1000 节点 chunk 对不足千块文档可能只有一个大绘制单元；复杂表格/代码需要单独测量 | 轨迹显示布局、绘制或复杂块初始化占主导     |
| 按需     | 复用现有独立内容运行时处理重转换，带修订号丢弃过时结果                   | 防止长任务阻塞输入；增加异步一致性和错误处理成本，数据传输也有开销                   | 增量缓存后转换仍显著阻塞主线程             |
| 后置     | 正文完整虚拟化                                                           | 能降低 DOM 规模，但需解决选区、输入法、跨屏选择、查找、拖拽和滚动定位                | 前几项不足以支持更大文档时再评估           |

首轮不更换编辑器框架，也不把已有 chunking 误当作完整虚拟化。复杂块的延迟优化应保留 Slate 负责选区的节点，只延迟块内部的高亮/预览等重组件。
