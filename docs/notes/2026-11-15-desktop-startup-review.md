# 桌面启动依赖与发布检查审查

目标：解释 0.63.5 偶发启动失败的系统原因，明确依赖、构建与验证各自需要治理的边界。

## 已确认事实

- 本机 `session-2026-11-15_11-49-37-6c80.log` 中，三个窗口的启动均在生产 `DesktopWhiteboard` 分包读取 `paddingY` 时失败；后台数据库连接成功。不能由这条日志推断用户数据损坏。
- `main.tsx` 并行加载应用、工具、内容编辑与插件等模块，然后装配宿主编辑器扩展和内容插件，最后提交应用 React 树。正文支持白板块，因此没有打开白板页面也会加载相关依赖。
- 把白板默认内边距改为调用时读取后，强化后的启动检查又捕获 `Class extends value undefined`，位置是 `RichTextPlugin extends CommonPlugin`。这证明只处理一个提前读取的位置不能覆盖生产分包的初始化问题；白板代码实验已撤回。
- 当前 Rolldown 的 `output.strictExecutionOrder` 默认关闭。类型声明明确说明，该选项可保留跨分包的源码模块执行顺序，代价是增加模块初始化包装及产物体积。开启该选项后的生产构建与隔离启动检查通过；这不证明源码依赖已经合理，也不代表真实用户工作区与全部窗口已验收。

## 源码依赖边界

以下链路根据真实源码导入关系核对，排除纯类型导入。

已有回环：

```text
EditorKit
  → editor-extensions/index
  → content-link
  → ContentLink / Content 预览
  → ContentEditor
  → useCollaborationKit
  → EditorKit
```

聊天引用新增的回环：

```text
editor-extensions/index
  → chat-ref
  → operations
  → content-editing/index
  → review-session
  → scoped-plan
  → EditorKit
  → editor-extensions/index
```

`operations` 只需获取当前编辑目标，却从整个内容编辑桶入口导入。桶入口同时导出审阅与方案模块，扩大了初始化依赖范围。`EditorKit` 的源码注释也已承认扩展组件会绕回装配层，现状靠延迟创建 kit 避免部分提前读取，尚未消除回环。

聊天引用预览还静态引入聊天 Markdown 渲染及代码块注册表；后者以 eager glob 收集全部块渲染器。悬停时才显示预览，不等于这些依赖在悬停时才加载。

因此，聊天引用提交 `c4a03ac9c` 确实增加了启动期依赖；目前没有完成该提交前后的同环境产物对照，不能把它写成已独立证实的唯一故障引入点。

## 发布检查为何漏报

- `9b262d2a9`（10 月 25 日）切换 Vite 8 / Rolldown 构建链。
- `146b8f24f`（10 月 26 日）修复过生产启动白屏，通过单独拆出 loadable 分包规避当时的初始化问题，并新增生产启动检查。检查成功条件是 `root.childElementCount > 0`。
- `cccd70f12`（10 月 29 日）改为先渲染启动提示，再异步加载业务模块，但未同步调整启动检查。检查此后可能在异步模块完成前退出。
- 启动失败由 `bootstrap().catch` 捕获后使用普通错误日志和错误提示展示；旧检查主要匹配 `Uncaught`，也没有可靠识别这类已捕获的失败。
- 当前 `startup:renderer-ready` 在 `root.render` 调用之后上报，能证明 bootstrap 执行完毕，但不能单独证明 React 已提交业务壳层、设置与数据库已就绪。

问题是启动语义变化后，验收判据没有随之更新；类型检查、功能测试和一次手动重启也不能替代生产启动验收。

## 建议治理方案

### 依赖层

- 先围绕启动入口、EditorKit、宿主扩展、内容编辑服务与聊天预览列出运行时依赖及模块顶层副作用，标出已知回环与实际消费者。
- 获取编辑目标等轻量操作直接依赖对应叶子模块，避免通过桶入口顺带加载审阅、方案与装配层。
- 把扩展声明、编辑操作与重型预览的依赖分清；需要时延迟加载预览，保留既有扩展注册和编辑行为。装配层不应通过声明模块再静态拉回自己。
- 对治理后的具体边界增加结构检查，阻止新代码恢复这些回环；不以全仓所有循环一次性清零扩大任务。

### 构建层

- 使用打包器提供的执行顺序保障，不再依次为常量、基类或第三方库添加分包特例。
- 对比启用前后的资源大小和启动耗时，明确包装开销；不把构建选项当作源码解耦的替代品。

### 启动与验收层

- 在现有 bootstrap 与壳层上明确区分模块加载、扩展装配、React 提交和主窗口业务就绪，避免再造一套导航或初始化框架。
- 隔离检查覆盖完整 bootstrap，任何阶段失败均非零退出；成功不能只依赖根节点非空。
- 主窗口业务就绪另按现有设置和数据库就绪协议验证；内容转换窗口与插件窗口按各自入口验证，不用主窗口信号代替。
- 对已知的加载顺序问题做有限次独立冷启动，并核对失败日志；真实安装包与开发产物的验证范围明确区分。
- 保留现有相关行为测试，新增检查仅服务真实回归与结构边界，不以测试数量为交付标准。

建议顺序：先修正生产启动验收判据并验证构建顺序保障，再按真实依赖图切断启动相关回环，最后检查多入口和安装包。涉及模块职责调整的实现，应先确认上述方案方向。

## 实施与验证快照

用户已确认上述方向。EditorKit、基础扩展、内容链接与聊天引用入口的传递静态回环已切断，并通过结构检查；引用插入改用编辑会话叶子模块，两类引用的重型预览按需加载。生产分包启用执行顺序保障，移除 loadable 初始化顺序特例。

启动检查分别确认 bootstrap、React 提交、设置初始化、当前库连接和业务壳层提交，另验证内容转换契约准备与插件窗口挂载握手。故障注入的数据库连接失败以退出码 1 被拒绝。

验证结果：桌面类型检查通过；相关现有行为测试 42 项通过，其中编辑器 void 行为在允许网络后复核通过；代码质量工具回归 94 项通过；桌面启动、白板和插件进程边界检查通过。三个生产入口在独立冷启动中连续通过，主窗口耗时为 902、1038、944 毫秒；本地 Windows 目录包内 ASAR 的相同检查通过，主窗口耗时 906 毫秒。上述后端响应为隔离夹具，未执行真实用户数据库维护或视觉验收，未发布或覆盖安装。
