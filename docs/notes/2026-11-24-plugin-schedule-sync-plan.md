# 待办与日程插件同步：方案与第一期交付记录

状态：用户批准第一期，已实施；第二、三期保留为未实施的设计参考。

本文件为一次性方案记录。第一期当前事实已沉淀至架构与插件作者文档；正文中的“本轮不写代码”等表述保留原方案评审上下文，不表示当前交付状态。

目标：为插件补齐待办、日程的完整读写、目录发现、可靠增量与条件写入，使 Tau 待办可推送到 TickTick，日程可通过插件与外部日历双向同步。

## 1. 需求与范围

用户已验证网络请求、凭据保存、OAuth 本机回调和插件记录存储可用。本任务聚焦宿主业务接口，不改网络桥、后台授权或凭据体系，不实现 TickTick 或 CalDAV 插件。

同步方向按原始反馈确定：待办为 Tau → TickTick；日程为双向。TickTick 完成状态回写、外部清单自动创建都不是默认需求。

宿主负责数据表达、身份、权限、条件写入、删除识别和变更恢复。插件负责远端协议、远端账号及清单映射、外部版本令牌、冲突策略、网络重试与同步进度。宿主不解释远端版本令牌，也不以内置第三方字段污染待办和日程表。

本方案建议三期交付，每期同时交付对应的版本正确性与验证；不先发布字段，再补冲突保护。

## 3. 插件接口草案

以下为评审用签名与语义，不是已经可用的 SDK，也不在本轮编写实现。

### 3.1 目录发现与按 ID 读取

| 建议入口                                               | 输入                   | 输出/语义                             | 权限            |
| ------------------------------------------------------ | ---------------------- | ------------------------------------- | --------------- |
| `data.todoLists.query({ archived?, limit?, cursor? })` | 可选归档过滤，默认全部 | 分页返回待办清单                      | `todos:read`    |
| `data.todoLists.get(id)`                               | 清单 ID                | 单项或 null                           | `todos:read`    |
| `data.calendars.query({ archived?, limit?, cursor? })` | 同上                   | 分页返回日历，包括系统/不可写项并标记 | `calendar:read` |
| `data.calendars.get(id)`                               | 日历 ID                | 单项或 null                           | `calendar:read` |
| `data.todos.get(id)`                                   | 现有不透明待办/实例 ID | 当前完整对象或 null                   | `todos:read`    |
| `data.calendar.get(id)`                                | 现有不透明日程 ID      | 当前完整对象或 null                   | `calendar:read` |

清单和日历最小返回：`id / revision / title / archived / writable / readonlyReason?`；日历增加 `color / visible`。`visible` 仅表示 Tau 视图是否展示，不表示是否允许同步。ID 与任务的 `listId`、日程的 `calendarId` 一致；插件不解析、不猜测、不按名称当身份。

第一期只开放目录读取和选择已有目标，不开放清单/日历创建、删除和改名。需要“把远端日历自动建到 Tau”时再扩展目录写权限及删除契约，不借日程写权限隐式创建目录。

### 3.2 待办字段

在 `PluginTodo` 增加：

| 字段                                                     | 语义                                                                       |
| -------------------------------------------------------- | -------------------------------------------------------------------------- |
| `listId: string \| null`                                 | 独立待办所属清单；正文勾选项没有独立清单，返回 null                        |
| `reminders: { offsetMs: number }[]`                      | 完整提醒列表；基准时刻减提醒时刻，沿用现有毫秒口径                         |
| `recurrence: { segments: …[] } \| null`                  | 使用现有规则字段与分段语义；系列 ID 为不透明字符串                         |
| `occurrence?: { taskId, seriesId, originalDate, state }` | 明确所属根任务、系列、原始实例日期与完成/跳过/改期状态；改期不改变实例身份 |
| `writable / readonlyReason?`                             | 将领域层的可写性传给插件                                                   |

普通独立待办的 `create`、`update` 增加 `listId / reminders`；`query` 增加 `listId / archived`。完成仍经 `setCompleted`，不把 completed 混入任意 patch。

提醒边界：普通待办基于截止时刻，定时日程基于开始时刻，全天日程基于当天零点；全天当天 9 点允许负 offset。无基准时刻时不能新增相对提醒。读到的空列表为无提醒；patch 省略表示保留，`[]` 表示清空；无效数字、超上限或宿主不支持的提醒形态明确报错。重复待办提醒的基准和正文待办单提醒模型在第三期定义并实现，不提前把单次绝对时间冒充系列提醒。

第一期返回重复规则供识别和展示，但对重复任务的新增字段写入先拒绝；第三期开放下述独立操作：

- `todos.setRecurrence(taskId, { rule, effectiveFrom }, options)`：从某个原始日期起调整规则或停止重复，宿主管理历史分段和系列 ID。
- `todos.setOccurrenceState(instanceId, { completed?, skipped?, scheduledAt? }, options)`：只修改一例的状态；不暗中修改整个系列。
- `todos.occurrenceStates.query({ taskId, limit?, cursor? })`：分页列出持久化的实例完成/跳过/改期状态，返回实例 ID、系列 ID、原始日期和状态；不要求日期窗口，也不展开无限重复序列。根待办变化后，插件可重读此集合并对账已清除的状态。现有 `todos.query({ view: "occurrences", start, end })` 继续负责窗口内实例展开。
- 第三期为 `todos.create` 增加可选重复规则；普通 `update` 对实例的标题/清单/规则修改继续拒绝，除非该字段已有明确的单次覆盖模型。

复用现有 `TaskRecurrenceRule` 的 daily / weekdays / weekly / monthly / yearly / custom、interval、起止日期、次数和节假日规则。插件只能写宿主支持的规则；不能靠传入任意 RRULE 绕过校验。首期第三方映射是否支持某条规则由插件判断，不静默降级。

### 3.3 日程字段与备注

在 `PluginCalendarEvent` 增加 `reminders / notesRef / writable / readonlyReason? / kind`：

- `kind` 区分普通日程、待办的一次安排、只读虚拟标记；具体枚举与现有来源投影对齐。
- `notesRef: PluginContentRef | null` 是备注正文句柄，不暴露 contentId。通过 `context.content.read` 读取 markdown 或 nodes，通过 `context.content.edit` 按正文 revision 编辑。
- `calendar.create` 增加可选 `notes: PluginContentInput` 和 `reminders`；`calendar.update` 增加 `reminders`，保留已有 `calendarId` 移动能力。
- `calendar.query` 增加 `calendarIds` 与 `view: "display" | "stored"`。缺省 display，维持现有必须给日期窗口的展示行为；stored 只枚举真实持久日程，日期窗口可省略，使用稳定 ID 键集分页，供第一期全量同步及第二期 bootstrap 复用。系统日历和虚拟标记不能通过修改 calendarId 绕过只读限制。

备注复用正文 API，需要将 `calendar-event` 纳入正文 owner 权限解析：读取备注要求 `calendar:read`，写入要求 `calendar:write`，不顺带授权任何无关卡片/文档。引用失效、日程已删除或目标不可写时拒绝。

日程元数据/提醒更新是一笔领域事务；备注编辑是独立的正文条件操作。跨这两个调用不承诺整体原子性。插件记录操作进度，全部成功后才推进同步检查点；后一步冲突时重读并协调，不反向覆盖用户的新修改。备注变更必须使日程聚合 revision 改变，并进入日程变更流。

备注不自动执行富文本 → Markdown → 富文本的循环写回。远端未改备注时保留 Tau 原正文；远端有改动时，插件选择宿主支持的正文输入形式并处理格式能力差异。

### 3.4 条件写入与创建重试

继续使用 `PluginWriteOptions.expectedRevision`，不另设时间戳比较参数。过期版本沿用 `PluginConflictError`；版本只能比较相等，不用于排序或挑选“更新的一方”。时间戳可以用于展示，不承担正确性判断。

为 `todos.create` 和 `calendar.create` 增加可选第二参数 `{ requestId: string }`。插件先持久化请求 ID，再发起创建；重试必须复用同一个 ID 与输入。

宿主按“资料库身份 + 插件 ID + requestId”隔离回执；插件 ID 从宿主上下文取得，不信任调用参数。相同请求返回原结果/原身份，不重复创建；同 ID 不同输入拒绝；原对象已删除或已撤销时返回明确的目标失效错误，不再次创建。

这只保证 Tau 侧创建可安全重试。TickTick 等远端创建是否可重试由插件按远端能力处理；宿主不能承诺跨网络事务。

### 3.5 可靠全量与增量

建议统一入口：

```ts
data.changes.query({
  domains: ("todo" | "todo-list" | "event" | "calendar")[],
  todoSource?: "todo" | "document" | "all",
  cursor?: string,
  limit?: number,
}) => {
  mode: "snapshot" | "changes",
  items: { domain, id, operation: "upsert" | "delete" }[],
  cursor: string,
  hasMore: boolean,
  checkpoint?: string,
}
```

不传 cursor 开始全量；分页 cursor 用于继续当前一轮，checkpoint 只在这一轮全部完成后给出，用于下一轮增量。两个值均不透明，绑定域集合、插件权限范围、本机资料库代次和协议版本。默认每页 50、上限 100，空结果仍返回有效 checkpoint。

`todoSource` 缺省为 `todo`，只含独立待办，是固定的数据来源范围，不是完成/日期等动态过滤。前两期明确拒绝 document/all，第三期才开放；选择来源范围后绑定进 cursor，变更范围必须重新全量，不能把不完整的正文待办增量伪装为成功。全量和增量使用完全相同的来源范围。

变更条目只指明对象；插件用 `get` 读当前完整对象。`upsert` 后读取为 null，按对象已删除处理。接口承诺可重放、最终收敛，不承诺读取每个历史版本；读取时比该变更更晚的状态允许提前看到，后续变更仍会重放，不因此跳过。

此入口不接收日期范围、完成状态、清单 ID 等动态过滤。否则日程移出日期范围、任务完成、跨清单移动会悄悄消失。插件在拿到变更后按映射处理；已同步对象移出选定范围时，同样要撤销或调整远端映射。

每个请求按域校验现有读取权限；缺一项就拒绝整个请求，不能无声省略某个域。游标跨资料库/设备、筛选域改变、权限范围改变、保留窗口已过、资料库被替换，返回建议新增的类型化 `PluginSyncResetRequiredError` 及 reason。它与数据冲突是不同错误。

不开放跨域历史审计、任意 SQL 或业务批量事务。`data.changes` 是宿主数据变化读取，与现有对象存储提供方 `context.sync` 无关。

## 5. 底层机制

### 5.1 版本：比较业务状态，覆盖所有可写字段

为待办和日程建立共享的语义 revision 投影，仍由同一领域读写入口使用。与“撤销要恢复哪些行”的快照分开，避免版本算法被备份材料或无关更新时间牵动。

- 待办覆盖标题、完成/归档、截止、所属清单、完整提醒、重复分段和相关实例状态；实例 revision 覆盖本例状态与实际生效规则。
- 日程覆盖标题、时段、全天、所属日历、完整提醒、备注正文的权威 revision 和改变可编辑行为的关联身份。
- 清单/日历版本覆盖公开属性与可写性；相关目录失效时，写入事务重新确认目标存在且可写。
- 仅排序、查看状态、写入相同业务值等不应制造业务冲突；所有集合输入先按业务语义规范化，再计算 hash。
- 备注正文的当前 revision 通过正文服务取得；不能仅 hash `detail_content_id`，也不能把尚未投影的会话正文当作不存在。CAS 接线须使用现有正文写入协调/保存屏障复验，不能只在 UI 预检时算一次。

日程元数据/提醒的 expectedRevision 比较、目标校验、写入、回执及持久变更必须在同一 SQLite 事务中完成。正文有自身耐久日志事务；聚合 revision 的复验需与正文协调边界配合，不能声称跨两库天然原子。

同一毫秒两次写入、时钟回拨，都不影响版本比较。内容改回完全相同状态可得到相同 hash，这是状态比较的允许行为；如果必须知道“中间曾改过”，使用变更流，不用 revision 代替历史。

撤销也要覆盖新增字段。提醒要加入操作快照与恢复；新建备注持有、删除、恢复和延迟回收沿用内容层。备注独立编辑沿用正文历史，不把它伪装成元数据事务的同一笔撤销。不能通过扩充 hash 就宣称撤销已经完整。

### 5.2 持久变更：随业务事务提交、回滚

建议在主库增加两个职责明确的对象：

| 对象                    | 最小字段/索引                                                                               | 作用                                             |
| ----------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `schedule_change_log`   | `seq INTEGER PRIMARY KEY AUTOINCREMENT`、domain、entity_id、operation；索引 `(domain, seq)` | 不可变的变更身份与删除墓碑；不保存备注正文/密钥  |
| `schedule_change_state` | 协议版本、已清理到的序号边界                                                                | 区分有效旧游标与已被裁剪的历史；重启后不忘记边界 |

序号代表本库事务提交序列中的位置，不依赖系统时间，不在设备间比较。条目时间可以用于运维，清理和正确性不依赖用户时钟。

持久 SQLite 触发器写日志，不能通过现有 `tau_domain_change` 内存回调事后补日志。事务回滚同时回滚日志；所有写入口都覆盖，不只记录插件自己写的修改。触发器不得依赖手机或离线维护连接不存在的 Node 自定义函数。

捕获表与归属：

| 来源变化                                     | 对插件的变化                                                    |
| -------------------------------------------- | --------------------------------------------------------------- |
| `todo_item`                                  | 对应根待办 upsert/delete                                        |
| `todo_group`                                 | todo-list upsert/delete                                         |
| `calendar_event`                             | 真实 event upsert/delete                                        |
| `calendar` 及影响子日历可写性的分组          | calendar 变化，必要时使受影响日程重新投影                       |
| `item_reminder`                              | 对应待办/日程 upsert；删除主对象后的附带触发可合并为最终 delete |
| `todo_recurrence`、历史分段、完成与 override | 根待办 upsert；第三期按原始实例身份补查状态                     |
| 待办安排、关联关系                           | 受影响的待办/日程变化，不能把解除关联视为日程删除               |
| 备注正文耐久投影                             | 根据当前持有者反查所有相关日程，分别 upsert                     |

备注变更的捕获接在正文当前结构的耐久投影/持有关系上，不能沿用旧 `contents.content` 假设。投影若晚于正文耐久提交，先发出失效唤醒；投影事务随后写入日志。重启必须先恢复未投影输入，随后继续产生日程变化，不能只靠退出时刷新。

第一期所有新增字段可用后，第二期才启用日志；首次启用不需要伪造历史，初始全量就是基线。

### 5.3 首次全量与分页不漏变更

全量不用长期打开的数据库事务，也不把当前展示查询的 OFFSET 分页作为一致性保证：

1. 先完成必要的正文恢复/投影准备，记录日志水位 `W0`。
2. 按 domain 与稳定实体 ID 做键集扫描，枚举所有受支持的持久对象；分页期间允许重复，不按日期窗口裁剪。
3. 扫描完固定补偿终点 `W1`，继续读取 `(W0, W1]` 的变化。扫描期间新增、删除、改动因此均能补齐。
4. 补偿读完才给出 checkpoint=`W1`。`W1` 之后的提交留给下一轮。

增量同样在一轮开始固定上界 `U`，按序号分页读取 `(checkpoint, U]`。每页在短读事务内取条目与必要身份；同一对象重复变化可在该页合并。不得因为合并结果或无匹配域的区间为空而丢失扫描位置。

如果全量/分页期间历史被清理到起点之后，立即返回 reset-required，不交付假的完成检查点。插件全量重建先收集这一轮见过的身份，只在全量及补偿成功结束后对旧映射做缺失对账；失败半途不能批量删除远端数据。

### 5.4 游标代次、保留与多设备

游标绑定本机工作区及本机“资料库替换代次”。该代次放宿主本机登记中，不能只存会随整库同步搬运的主库，也不能直接复用当前 workspaceId——当前 workspaceId 在同名库替换后不变。

整库下载替换、恢复备份、重建库、不可证明连续性的重新连接，须在重新对外提供读取前原子切换代次。进程启动无法确认替换是否完成时宁可使旧游标失效；正常重启且库未替换则保留游标。已有 `workspace.reset` 是通知，同时还必须有持久代次检查，以覆盖插件不在线的情况。

日志建议以条数做有界保留，初始预算为每库最近 100,000 条、按批裁剪；这是待容量验证的实现默认值，不写入 SDK 契约。清理边界和日志删除同事务提交；插件过慢就重新全量，不以无限日志换取无限离线保证。

插件将 cursor 与本机工作区标识一起保存；即使记录随 Tau 整库同步到了另一台设备，宿主也会拒绝跨设备 cursor。远端映射可以保存在 `context.records`，但这不提供多设备同步执行互斥。本轮不增加分布式租约：同一远端账号/映射建议只指定一个执行设备，不能声称本机 requestId 能防住两台设备同时在外部创建。

### 5.5 回执生命周期与来源信息

复用现有 task-assistant 请求 hash 与回执核对思路，但不能依赖仅为撤销保留的短期操作记录：建议增加 `plugin_schedule_create_receipts`，以本库内 `(plugin_id, request_id)` 为唯一键，存输入摘要、实体类型、不透明结果身份与最终状态，和创建同事务提交。正文创建准备在事务前完成，失败按内容层回收，不留下已成功的假回执。重放时先核对输入摘要和结果身份；对象仍存在则返回该对象的当前投影，已经失效则报错，不返回可用于覆盖新状态的旧 revision。

回执保留至插件清除其数据；对象删除后保留“目标已失效”结果，不让旧请求复活。这个寿命与可恢复删除的七天窗口、增量日志保留预算分别管理。插件请求应按账号/远端对象生成稳定操作身份，不每次重试都生成新 ID。

第一版 changes 不承诺精确来源，也不新增依赖来源的防回环协议。插件用映射中“最后成功同步的业务状态/版本”判断自身回声，不比较 hash 大小，也不跳过“自己发起期间”的所有变化。现有集合事件继续允许重复唤醒。

## 6. 主流程

[同步主流程图](./2026-11-24-plugin-schedule-sync-flow.html) 使用 Diagram Design 默认样式，文档内 960×600 画布；图只展开游标失效与同步冲突两个结果分支，逐条字段校验见正文。

```text
同步启动或收到集合变化通知：
  验证读取权限，加载插件映射和上次完成的 checkpoint
  page = data.changes.query(domains, cursor = checkpoint 或已保存的分页 cursor)
  如果 reset-required：丢弃游标，保留映射，重新开始全量及补偿

  对 page 中每个身份：
    upsert → get 当前对象；若已经不存在，转为删除处理
    根据已选清单、映射和最后成功同步状态决定外部动作
    双方都改过 → 进入插件冲突策略，不能按 Tau 时钟直接覆盖
    外部变更写 Tau → 使用最新 revision；创建复用事先存下的 requestId
    条件冲突 → 重读并保留待处理项；不自动覆盖，不推进本页
    网络失败/备注步骤失败 → 保存操作进度，留待安全重试
    成功 → 保存映射和本项结果

  本页全部成功后保存分页 cursor
  hasMore → 继续下一页
  收到 checkpoint 且本轮全部成功 → 完成缺失对账并保存 checkpoint
```

插件记录更新可以用现有 `context.transaction` 原子保存映射与 cursor，但不能把远端网络请求塞进宿主 SQLite 事务。宿主返回 cursor 不代表插件已经消费；推进责任属于插件。

每期按桌面先验证、手机实现/核验后更新公共支持矩阵的顺序交付。候选开发可仅桌面，但公开标为支持的新签名必须有对应最低宿主版本。旧宿主的可选 adapter 方法缺失时，新 SDK 明确拒绝；不能传参后被忽略。已有旧签名继续服务原范围，不保留两套新旧领域实现。
