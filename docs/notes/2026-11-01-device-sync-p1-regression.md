# 设备同步三个 P1 修复验证

范围：`codex/database-sync-spike`，审查基线 `b4eb4c25f`。只修复旧 JSON 保存任务越过覆盖边界、首次正文准备漏传版本、本机版本表损坏三个问题及直接回归。当前事实见 `/docs/architecture/device-sync.md`，复现步骤见 `/docs/guides/ops-device-sync-spike.md`。

## P1-1：旧保存队列重新领取版本

根因：节流、串行队列及失败重试只保留正文；实际执行时才取得当前 generation，相同 revision 不能区分覆盖前后的任务。

改动：输入产生时绑定库身份与原始版本，队列及重试沿用它；覆盖清退旧任务并重建编辑上下文。普通刷新仅在库与版本均相同的条件下保留本机未保存输入。JSON 保存和耐久正文保存均在原生最终事务检查版本，JSON 分支同时核对实际库名。

实际验证：真实 `useEditContent` 与生产 `updateContent` 接入临时 Rust SQLite。分别覆盖有检查点与无检查点分支；覆盖前后 revision 相同，旧节流、旧排队及旧失败重试均不能改变新正文。新会话、覆盖失败后的编辑及其他库覆盖期间的当前库保存正常；当前保存失败返回 false 并显示保存错误。直接向原生提交旧版本的 JSON/Yjs 请求也被拒绝。普通刷新仍可保存保留的本地输入。

未覆盖：完整页面导航、真实触屏输入和真机 IPC 调度。无检查点场景从临时快照基线移除设备正文检查点，使实际保存进入普通 JSON 分支；不代表验收了云端文件下载界面。

## P1-2：首次正文准备漏传 generation

根因：生产 `prepareMissing` 未传版本，验证桥却自动补当前版本，掩盖了覆盖后原生守卫的稳定拒绝。

改动：准备开始即捕获 generation，保存时显式传入；桥原样转发参数，手动构造的测试保存请求自行声明上下文。Rust 守卫保持拒绝旧版本的语义。

实际验证：明确覆盖后向临时库插入只有 `contents/content_documents` 的正文，调用生产 `startDeviceSync`，成功建立检查点并经固定证书 HTTPS 同步到临时桌面库。另在准备结果提交前执行真实 Rust 快照覆盖，原请求保留旧 generation，返回 `DEVICE_SYNC_REPLACED`，旧正文没有落库。

未覆盖：真机导入页面、系统后台创建入口与操作系统挂起调度；这里直接构造相同数据库状态并运行生产同步编排。

## P1-3：本机版本表未纳入恢复

根因：健康检查和恢复边界都遗漏版本表，且无列名 INSERT 对额外列敏感。

改动：两端共用独立结构及健康 SQL，检查精确列、唯一记录和版本值；仅归档并重建版本表。可确认的有效版本继续保留，无法确认时生成 UUID 新命名空间。初始化、版本读取和移动云端下载候选库走相同边界。结构识别不接纳锁忙、只读、空间及 I/O 故障；事务失败保留原错误，不通过空版本冒充成功。

实际验证：Electron SQLite 与 Rust SQLite 分别注入列缺失、额外列、记录缺失、异常值和表缺失，共 10 组。业务正文、正文身份、健康二进制、未确认日志及有效 JSON 转换意图逐项比对不变；有原表时保留隔离材料；旧版本请求被拒绝，新版本可以保存。另组合生产 JSON 入口验证版本表恢复后的旧上下文拒绝及新会话保存。

使用真实只读连接、SQLite 写锁和 `max_page_count` 配额耗尽验证两端失败返回，未新增隔离材料、未改变有效数据；解除限制后可恢复。配额测试不代表物理磁盘已经写满。

未覆盖：操作系统级磁盘 I/O 故障、权限故障的完整平台组合及真机缓存页面恢复；错误分类对此保留原错误，不宣称进行了物理故障注入。
