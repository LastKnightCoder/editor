# 白板协作与插件接入调研

调研日期：2026-10-24。类型：一次性调研快照，可随时删除；不作为架构事实、已确认裁决或实施任务引用。本次只新增此报告，不修改产品代码。

## 结论

建议保留现有白板内核，复用 Yjs、身份与房间管理、WebSocket、持久化和附件基础设施，新增白板文档模型及绑定层。插件通过宿主管理的文档数据接口加入协作，不各自连接协作服务器。

当前已有较好的基础：稳定元素 ID、统一操作入口、静态插件定义、数据校验和迁移、未知元素保真，以及成熟于正文场景的协作服务。主要缺口是白板的数据与并发语义，不是缺少网络连接。

不能把整页 children 或整元素 JSON 放进 Y.Map 就宣称支持完整协作，也不能把当前基于数组路径的 Operation 原样广播。可保留它们作为本地交互表示，但持久化协作层必须围绕稳定身份、明确合并单位、结构约束及本地撤销重新设计。

仓库已有编辑器节点契约任务，明确了契约随文档保存、插件更新不自动迁移旧数据、外部实体保持引用语义等约定。该任务仍是方案，尚未实现；本报告建议与其共用契约基础，但不把“正文支持白板引用”视为“白板本身已经支持协作”。

## 3. 候选路线

| 路线                             | 优点                                                     | 成本与限制                                                                                 | 适用性                                                   |
| -------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| A. 整板租约锁 + 快照同步         | 最快形成共同查看、轮流编辑；改动相对小                   | 同一时刻一个写者；需服务端租约和 fencing token，断网不能继续冒充持锁写者；不是自由多人编辑 | 若业务急需演示/评审，可作为独立范围的过渡能力            |
| B. 自有白板 + Yjs 文档绑定       | 最大化复用现有白板、编辑器协作、宿主与插件；利于离线合并 | 需要新模型、绑定、树约束、撤销及协议演进；不是几个事件监听器                               | **推荐主线**                                             |
| C. 自有白板 + 服务器权威记录同步 | 树约束、规则验证、权限与操作裁决集中                     | 自建乐观重放、冲突变换、重连和撤销；维护第二套同步引擎                                     | 如果强结构约束优先、长期离线不是重点，可重新评估         |
| D. 迁移至 tldraw 并采用其 sync   | 可使用现成图形编辑/同步体系                              | 现有脑图、分栏、文档卡、手绘、插件 API 均需适配或迁移；需另行确认当期许可证及商业条件      | 更适合同时计划替换白板内核的项目，不建议仅为协作而换内核 |

以上为相对成本判断，未做开发工期承诺。当前没有证据支持“换 tldraw 总成本更低”，也没有必要为保留 Yjs 而忽略树合并的复杂性。

## 4. 推荐架构与数据边界

### 4.1 分层与文档归属

建议新增 `@tau/whiteboard-collab`（拟议包名）：负责白板共享数据、操作映射、远端投影、手势来源、撤销、在线状态；保持 `@tau/whiteboard` 不依赖桌面业务和服务端。桌面宿主负责会话、存储、身份、资源及主进程接线。

底层共用现有协作传输与持久化；协议新增文档种类后，正文与白板分别提供初始化、校验、摘要、资源扫描及本地投影适配器。`SourceBinding.contentId`、`SharedContent`、`validateDocument`、`readSharedContent` 等当前正文假设都要检查，不能只增加一个 sourceType 字符串。

产品边界建议为“一份多页白板，一个权限/分享对象”。首版可将该白板的页目录与页面数据放进同一 Y.Doc，简化跨页移动、撤销和权限一致性，但必须服从文档大小预算；这只是起步方案，不声称支持无限页。需要大板或按页加载时再拆根目录文档与页文档，并明确跨文档移动没有单个 Yjs 原子事务。独立的内嵌白板内容页也需要稳定共享身份，不必伪造 white_boards 记录。

建议的逻辑模型（不是现有 API 或最终字段命名）：

- 板元数据、页面清单与排序：共享内容。
- 元素：按稳定 elementId 索引，独立保存属性、位置、层级与数据契约。
- 板内文字：以 pageId/elementId/field 稳定寻址的共享富文本或共享字符串。
- 契约与附件声明：随文档保存的不可变数据。
- 光标、当前页、选中元素 ID、临时拖动预览：Awareness，短暂且可丢弃。
- 本机缩放、视口、工具、弹窗、阅读纸停靠：本机状态；跟随演示者通过单独的显式模式实现。

### 4.2 稳定身份和合并单位

元素已有 ID，应继续使用；运行时可以保留树形 children，协作层以 ID 寻址并投影成树。路径只在提交时按当前树解析，不传给远端当永久地址，也不让异步任务缓存路径。

推荐按语义选择合并单位：

| 内容                               | 推荐语义                                                                  |
| ---------------------------------- | ------------------------------------------------------------------------- |
| 颜色、显示名称、独立开关           | 独立共享属性；不同属性修改可以同时保留                                    |
| 一次移动/缩放的几何状态            | 按业务选定 transform 原子属性，避免并发结果拼出没有任何人提交过的几何组合 |
| 父节点与同级排序位置               | 一个 placement 原子属性；排序采用可并发插入的顺序键并定义同键决胜规则     |
| 正文、脑图文字、箭头文字、插件源码 | 对应共享富文本/文本绑定，不反复整段写入 JSON                              |
| 插件普通对象、数组                 | 默认明确为整属性替换，不宣传深层自动合并                                  |
| 投票等独立贡献                     | 按稳定参与者/贡献 ID 的共享映射；是否允许多次投票由业务决定               |

`Y.transact` 可以批量通知和组织事务，但不把多个独立键变成不可拆分的并发胜负单元。要求一起变化的数据必须在表示上拥有相应原子边界。同一字段的并发赋值按 Yjs 的确定性规则解决，不承诺真实世界时钟上的“最后操作必胜”。

整元素 Y.Map 值若是普通 JSON，并不会自动把内部字段变成 CRDT。应维护稳定的嵌套共享对象，不在每次渲染或更新时新建并替换它。

### 4.3 树、连线和自动布局

至少明确以下规则：

- A 挂到 B、B 同时挂到 A 时如何得到无环视图；Yjs 的收敛不保证业务树无环。
- 两人把同一节点移入不同容器，只能产生一个父归属；同级排序冲突需稳定决胜。
- 父节点删除与子节点移出并发时保留哪一方；删除后迟到的属性更新不得无意复活节点。
- 连线目标被删时，端点如何解绑、悬空或保留恢复信息；恢复与撤销的行为必须一致。
- frame、column、脑图的布局是用户意图还是派生结果；不能每台客户端收到远端变化后各算一遍布局，再把各自结果广播。

可用确定性投影消解非法结构，或引入服务端权威结构操作；第一阶段必须用对抗测试选定并固定一种协议，不能依赖客户端随意“修复”共享树。服务端拒绝非法增量后，要保留本地未确认改动，并从已确认状态恢复/重建会话；不允许客户端静默丢弃某个远端更新后继续宣称已同步。

### 4.4 撤销和交互

协作会话使用选择性撤销，按本机编辑会话 origin 追踪；插件主动写入和内置操作进入同一语义通道，远端同步、投影与迁移不计为用户操作。跨窗口来源是否共享历史要明确，不能把“本机进程收到的消息”都算成本人编辑。origin 是本地追踪标记，不是服务器可信身份。

移动手势可采用本地 60fps 预览、限频 Awareness 预览、结束时持久提交一次。持续笔迹可另设受预算控制的分段提交，避免崩溃损失整个长手势。两人同时拖同一元素时，提示占用并定义提交冲突规则；Awareness 提示不是强制锁。

文本编辑时撤销当前文本，退出文本后撤销画布；若要求同一撤销步同时覆盖“新建元素 + 初始文字”，优先让板内文字与元素处于同一文档和历史作用域。外部引用文章属于独立文档，不承诺跨文档原子撤销。

### 4.5 内嵌文字、外部实体与资源

区分三件事：

1. 白板自有文字：富文本框、脑图文字、图形/连线标签应由白板共享会话拥有。现有富文本服务可以复用，但需接入板内共享根；不能原样传播本地数字 contentId。
2. 外部文档卡：继续引用原文章/卡片/日记。白板权限不自动授予文章权限；无权访问时显示明确状态，可申请权限；不自动复制正文。已有标题/预览快照是否随板共享，也要有明确的公开边界。
3. 图片、音视频和插件素材：按稳定资产 ID 与资源声明上传/解析，服务端进行成员鉴权和配额管理。本机路径或私有凭据不进入共享字段；当前正文的本地视频策略不能被误当作已实现共享视频。

白板内引用另一个白板同样不递归自动授权。共享引用、共享目标内容、编辑目标内容是三个不同权限判断。

资源与外部正文的释放应依据共享引用差集、幂等账务及撤销保留窗口；不要让每个客户端重放同一次删除时都减少本地引用计数。生命周期与编辑器节点契约方案共用原则，归属白板的数据另行接线。

## 5. 插件如何接入

### 5.1 三类插件分别处理

| 类型                       | 接入方式                                                                         |
| -------------------------- | -------------------------------------------------------------------------------- |
| 工具/命令插件              | 通过受控 API 修改已有元素，宿主记录一个事务并同步；插件无需网络代码              |
| 自定义元素插件             | 声明静态数据契约，通过共享属性、文本句柄、映射等宿主接口读写；渲染函数只消费投影 |
| AI、网络请求、后台任务插件 | 发起者执行有副作用的命令，完成后提交结果；其他参与者同步结果，不重执行任务       |

目前 `IPluginStorage` 是插件/工作区作用域的存储接口，不是白板房间共享状态。它不应因接入协作而整体上传，也不能承载多人投票等共享事实。凭据、个人配置、缓存与共享元素数据需要保持不同归属。

### 5.2 建议新增的最小契约能力

下列是拟议能力名和行为，尚非可直接调用的 SDK：

- 普通属性的按键 patch；插件 data 的字段级更新入口，避免先读整个 data 再整体写回。
- 声明文本字段，并提供文本/富文本绑定句柄；对已声明文本禁止绕过绑定做延迟整段覆盖。
- 需要时提供有限的共享 map；投票优先记录独立贡献而非暴露无保证的 `count + 1`。
- 声明资源槽和外部实体引用，以便缺少插件代码时仍可扫描、保存和导出。
- 事务来源、撤销分组、当前权限、连接/冻结状态与订阅接口。
- AI 改写、自动排版等长任务携带读取时的修订依据；内容已变时返回冲突，保留结果供处理。

不向插件暴露原始 Y.Doc、provider、整个协作数据库或任意顶层共享 map。由宿主绑定 pluginId、elementId、契约与房间上下文；这些受控入口用于维持协议正确性，但当前同运行时插件没有完整安全沙箱，不能夸大为能阻止恶意插件的安全边界。

### 5.3 与编辑器契约统一，避免两套作者规则

共用不可变契约格式、摘要算法、版本支持、文本/资源/引用声明与迁移语义；白板额外扩展几何、父子关系和排序。不要复用仅适用于 Slate 的节点结构，也不要为白板建立另一套私有字段黑名单。

服务器不能运行任意插件的 React render、Standard Schema 的 JS 函数或 migrate 回调。第一期可以只执行平台定义的可序列化契约校验，插件业务 schema 在可信作者运行环境中校验；这不等于服务端保证了全部插件业务不变量。确需强业务约束的能力必须由受控服务或可验证的受限规则承载。

### 5.4 缺失插件和不同版本

| 状态                 | 推荐行为                                                                         |
| -------------------- | -------------------------------------------------------------------------------- |
| 对方没安装插件       | 保留完整元素、契约和资源引用，显示占位；不自动下载执行代码，不影响其它可编辑元素 |
| 插件不支持该数据版本 | 私有数据不可写；宿主能够安全理解的公共外壳操作按明确规则开放                     |
| 插件仅升级代码       | 不自动改旧元素的数据版本或契约                                                   |
| 主动升级共享数据     | 走共享迁移屏障、修订校验及持久回执；旧客户端不得继续提交旧语义增量               |
| 插件卸载             | 保留文档中的共享数据与必要资源，不因卸载删除所有协作者的内容                     |

当前白板在装配和插入时会自动调用 migrate；共享模式不能直接沿用“本机加载后迁移、下次保存带出去”的行为。必须先与编辑器契约任务中的旧数据升级、epoch 和恢复机制对齐。

### 5.5 副作用只执行一次

AI 生成图片、调用第三方 API、付费编译等不能挂在“收到共享数据变化就执行”的观察器上。由显式命令发起，使用 requestId 幂等重试，结果提交前检查当前权限、目标存活与字段修订。任务失败不写成成功状态，接收端只显示已提交的结果。

共享后台任务如确需接管，要有服务端租约及幂等回执；不能靠 Awareness 推选一个人就声称严格恰好一次。对于不可撤销外部服务，画布撤销只撤内容，不承诺撤销已经发生的调用或费用。

## 6. 缺口与优先级

| 优先级 | 缺口                         | 完成判据                                                         |
| ------ | ---------------------------- | ---------------------------------------------------------------- |
| P0     | 文档类型、稳定身份与共享边界 | 正文/白板路由及校验明确；多页、独立页和引用身份不会串库          |
| P0     | 元素合并、树与删除语义       | 并发插入、移动、删除、换父、排序和连线在乱序重放后收敛且结构合法 |
| P0     | 单一文档绑定与持久化         | 本机多窗口、远端、离线恢复走同一状态源；快照保存不会覆盖远端增量 |
| P0     | 选择性撤销和文本绑定         | 本人撤销不抹掉他人独立修改；同文本并发输入和 IME 正常            |
| P0     | 插件契约与版本保护           | 无插件、不兼容插件、迁移和撤权不会静默丢数据或继续非法写入       |
| P0     | 资源及外部实体               | 不误读对方本地 ID；附件可鉴权恢复；引用权限和回收正确            |
| P1     | 在线交互                     | 光标、选区、当前页、拖动预览；过期清理、限流与高延迟处理         |
| P1     | 容量与性能                   | 大板、手写、多成员和长会话下的带宽、内存、校验 CPU、日志增长实测 |
| P2     | 产品增强                     | 跟随演示、评论、历史版本、只读访客、按页加载等按需求增加         |

“只读访客”不能只设置画布 readonly：当前成员角色只有 owner/editor；若首版需要访客，服务端角色、票据、逐消息授权与 UI 必须一起纳入 P0。

## 7. 服务端的具体约束

已检查 [服务入口](/apps/collaboration-cloudflare/src/index.ts) 和 [存储实现](/apps/collaboration-cloudflare/src/store.ts)：

- 当前一个正式 DO 承载所有房间；文档上限 8MiB，活动文档编码状态合计预算 12MiB，另有活动房间和连接数量限制。白板手写和嵌入文本必须压测；编码状态预算也不等于实际内存占用。
- 每个同步增量会构造候选 Y.Doc、编码/校验，再事务落盘。高频拖动持久化将放大整文档处理成本，不能从文本协作的可用性直接推导白板吞吐。
- 在线状态每 socket 每分钟最多 600 次，约为持续平均 10 次/秒，且光标、选区、心跳等共用预算。建议先合批、留余量，以总发送频率约 5–8 次/秒进行交互试验；这是待测参数，不是已验证最佳值。若提高频率，必须同时调整服务限流、字节预算及压测。
- 首版不必立即改成每房间一个 DO；达到瓶颈后再分片，届时补齐跨 DO 权限传播、撤权及时性和元数据一致性。
- 服务端当前资源扫描与校验以正文为输入；白板和未知插件资源必须由新的文档适配器覆盖，不能只复用 R2 上传接口。

## 8. 建议实施顺序与验收

1. **确定协议并做双端数据原型。** 明确实体身份、字段粒度、placement、删除策略、树无环及白板文字归属。先证明数据正确，不急于做协作光标 UI。
2. **打通本地白板会话。** 新绑定支撑两视图同步、增量投影、选择性撤销、快照导出、崩溃恢复；保留现有交互与渲染实现，切换时只有一个写入真源。
3. **接入远端共享闭环。** 扩展文档协议、身份/绑定、校验和资源扫描，复用邀请与成员管理。先支持几何、文字、连线和图片，验证断网与撤权。
4. **完成插件与复杂结构。** 使用现有简单自定义元素插件验证通用几何和属性，再用一个带文本或独立贡献映射的测试插件验证合并；覆盖缺失、旧版、迁移与异步任务。脑图、分栏、多页移动按同样标准验证。

每阶段只扩展必要能力，不先建设任意深层字段 DSL、通用跨文档事务或所有插件的服务器执行环境。

最低行为验收矩阵：

- 两人修改不同元素；同一元素不同属性；同一属性竞争。
- 同一文本并发输入、删除与 IME；文本编辑与几何移动同时发生。
- 删除与修改、父删与子移、相互嵌套、同级重排、连线端点删除。
- 一人撤销时另一人已编辑；拖动中的远端删除；异步插件结果迟到。
- 多窗口、断网重连、重复和乱序消息、崩溃重启、被撤权后待发送更新。
- 无插件、旧插件、新契约、显式迁移、资源丢失、外部实体无权限。
- 带笔迹与插件的大板性能、长时间编辑日志增长及断线恢复时间。

视觉验收按项目约定由用户完成；实施阶段需完成类型、行为测试、构建和边界检查。

## 9. 本次验证与限制

完成仓库代码和文档核查、官方资料检索，并使用仓库现有 Yjs 运行内存双端实验：从共同初始状态分叉，一端改 color，另一端改 size，再双向交换更新。整元素 JSON 两端最终一致，但只保留一端属性修改；嵌套 Y.Map 的独立字段最终同时保留 red 和 size=20。这验证了“收敛不代表保留所有独立编辑”，不代表白板协作实现已通过测试。

没有连接正式房间、修改真实数据库、发布服务或运行白板视觉验收；未进行网络压力测试及端到端协作验收。工期、性能目标及最终协议需要原型结果支持。
