# 数据库多设备同步 Spike 验证记录

2026 年 10 月 31 日。目标是在设备大部分时间各自编辑的条件下，验证资料库的自动增量同步、离线补齐与最终一致性。基线提交为 `c05aa844f9f09a381c079bcba41fccaa9cab4958`，分支为 `codex/database-sync-spike`。

数据库层捕获和持久补传可行：离线双向修改、稍后打开设备、跨表原子接收、重试、进程退出恢复、第三设备转发均通过。通用行级复制还不能直接成为正式全库同步功能：跨记录唯一约束会阻断进度，没有数据库外键的业务关系可能形成孤儿，大字段整列记录会放大传输量。

## 实现范围

实现位于 [scripts/spikes/database-sync](/scripts/spikes/database-sync/README.md)，与正式应用入口隔离，没有修改共享 Schema、桌面代码或移动代码。

临时副本加载完整的主库 SQL，实际创建 98 张业务与管理表，为其生成 294 个增删改捕获触发器。97 张表使用声明主键，`content_links` 使用现有唯一索引对应的二元键。BLOB 以带类型标记的十六进制载荷传输。

场景实际写入 11 张代表表：`contents`、`content_documents`、`cards`、`todo_group`、`todo_item`、`plugin_kv`、`plugin_records`、`content_links`、`whiteboard_documents`、`plugin_entities`、`entity_identities`。用例对全部 98 张表的最终行快照进行比较；没有穷举每张表的业务操作。

网络验证使用真实回环 HTTP，请求中的事务经 JSON 编码后由另一 SQLite 副本接收。自动轮询用于验证设备稍后连接的追赶流程，不依赖手工逐条触发同步。没有验证真实 Wi-Fi、mDNS、移动后台、TLS 配对或界面刷新。

## 数据与提交协议

- 第一次加入从同一份业务行快照初始化，基线摘要、资料库身份和 Schema 指纹进入每个变更信封。
- 每个来源持有持久单调序号；事务信封携带逻辑时钟和已观察到的各来源进度。
- 触发器在原 SQLite 事务内捕获行的前后状态，业务行、待发送日志与来源序号共同提交。
- 接收端在一个 SQLite 事务内写入行版本、业务投影、耐久日志和确认进度。失败共同回滚，不提前确认。
- 来源进度只在连续依赖齐备后推进；重复事务不重复执行，同一操作身份携带不同内容则拒绝。
- 更新按逻辑时钟、设备身份和来源序号确定主版本，与到达顺序无关。并发分支保留；观察全部分支后的新编辑可使冲突视图收敛。
- 删除在同一记录身份上永久优先，阻止离线旧修改复活。原型不支持在同一身份上撤销删除；正式接入必须兼容现有最近删除、恢复和撤销语义。
- 所有设备保留已接纳的原始来源日志，可向第三台设备转发；转发不生成新的本机操作身份。

普通记录采用整行裁决。两台设备分别修改同一行的不同字段时也可能保留为两个分支，没有实现字段级合并、正文 Yjs 合并或语义合并。

## 原生互通

Node 使用 `node:sqlite` 的 SQLite 3.53.4。原生探针使用与移动端相同版本的 `rusqlite 0.29.0`，本机编译出的 SQLite 为 3.41.2。

原生探针在已安装捕获触发器的临时库中，通过普通 SQL 写入待办分组、待办、插件记录和白板 BLOB，并在同一事务保存完整同步信封。退出后由 Node 重开该库、发送到另一副本，全部业务表比较一致，二进制字节保持不变。

原生构建的 `sqlite_compileoption_used('ENABLE_SESSION')` 返回 false。因此，本次选择普通 SQLite 触发器，不依赖 Session Extension 或额外的 SQLite 编译选项。

该结果证明两种 SQLite 版本与 JSON 编码的互通；正式 Electron `better-sqlite3`、Tauri 生命周期、移动打包与真机仍需接入验证。Rust 示例只包含固定的四项写入，没有实现完整的原生接收、冲突处理或自动调度。

## 场景结果

完整命令运行 17 个用例，17 个通过、0 个跳过。测试中包含主动复现的不安全行为，不能把反例通过解释为相关问题已经解决。

| 场景                                                   | 结果                                             |
| ------------------------------------------------------ | ------------------------------------------------ |
| 同一基线下，电脑和手机离线新增不同记录、修改多个业务域 | 重连后双向补齐，全部业务表一致                   |
| 手机未连接时电脑修改，手机稍后启动同步循环             | 自动追赶，并可向电脑反向发送                     |
| 同记录并发编辑及三设备不同连接顺序                     | 主版本与冲突视图一致，分支保留                   |
| 删除遇到离线旧编辑，旧编辑逻辑时钟更高                 | 删除不复活，旧修改仍可查                         |
| 乱序、重复、操作身份被篡改、资料库或 Schema 不匹配     | 缺依赖或身份不匹配时拒绝，重复幂等               |
| 三表事务只接收第一项后注入失败                         | 行、日志、确认进度全部回滚，重启后重试成功       |
| 服务端提交后连接断开，客户端未收到响应                 | 重试不产生重复行或回声操作                       |
| 子进程在提交前或提交后直接退出，不关闭连接             | 未提交事务回滚，已提交数据与日志可恢复           |
| 原设备退出后，经第二台设备向第三台转发                 | 原始来源修改可以继续传播                         |
| 白板 BLOB、组合主键与真实身份退役触发器                | 字节、键和触发器副作用随事务传播                 |
| 原生 Rust 写入后由 Node 重开并发送                     | 四项写入与二进制状态一致                         |
| 两条不同 ID 的记录竞争业务唯一键                       | 整批拒绝，确认进度不推进；尚无自动裁决           |

| SQLite changeset 遇到主键碰撞并一律采用远端            | 两端最终不同，不能直接采用该策略                 |

## 重要发现

### 初始基线必须显式传递

主库建库 SQL 会写入带当前时间的默认 `excerpt_provider`。两端各自建库，即使 Schema 完全相同，也会得到不同初始行。直接从后续增量开始复制无法修复这些未记录的差异。

原型让加入设备继承同一份初始快照，并校验基线摘要。重开副本不重新执行建库 SQL，避免把已删除的默认记录重新插入。已有正式资料库的原子快照导出、首次安装和长期离线后的重新建立基线仍需单独实现。

### 稳定身份与业务约束需要统一规则

主库有 69 张表声明整数主键。原型显式为设备分配互不重叠的整数编号段，证明独立新增可以互不覆盖；没有实现设备编号的配对分配、旧 ID 迁移或现有所有写入口的编号接入。

`plugin_entities(plugin_id, kind, key)` 这样的唯一性跨越不同记录 ID。仅靠每行的版本优先级不能解决此类冲突；原型选择整批回滚并停止确认该来源，保留处理机会。正式方案需要按业务定义合并、重命名或保留冲突对象。

`todo_item.group_id` 的业务关系没有数据库外键。数据库能完全一致，业务却可能失去父级。因此必须同时验证领域不变量，不能只比较数据库行或执行 `PRAGMA foreign_key_check`。

### 大字段整列复制需要优化

正文 JSON 和白板状态存放在大字段中。通用捕获会为每次更新保留整列前后状态；它适合捕获变更事实，但不宜直接作为每次输入的网络载荷。正式方案应对短时间连续保存合批，正文与白板复用既有增量协议，避免重复维护两套相互覆盖的状态。

## 正式实现的边界

完整产品需要覆盖所有业务写入口及所有数据库连接，并协调现有整库云同步、内容会话缓存和资料库替换。业务事务必须与日志共同提交，不能依赖进程内回调补日志。

98 张表不能全部按原始行原样搬运：资料库身份、授权、缓存、引用计数、派生数据和本机状态应逐表定义归属；未知插件 JSON 不能自动推断业务合并语义。Schema 不同的副本需要明确的升级与同步门禁。

日志与墓碑当前永久保留，传输不做压缩或分页；接收请求限制为 16 MiB。长期离线设备的快照追赶、日志回收、过期设备退役与大包续传都属于后续工作。图片附件和 AI JSONL 会话文件没有纳入本次数据库实验。

后续接入应先完成表与约束清单，并用真实业务命令验证带关系的创建、删除、恢复和插件写入。网络发现和配对可以复用成熟方案，但不能替代上述数据一致性工作。
