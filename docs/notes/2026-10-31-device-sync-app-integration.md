# 混合设备同步的应用接入验证

目标：把正文 Yjs、线性数据库事务和快照补齐接入真实桌面与移动宿主，验证配对、恢复与图片同步，库选择仅作极端兜底。

## 实施方案与结果

采用单个桌面排序点，移动端主动连接。先建立耐久正文，再接可信传输与恢复调度，最后接图片和异常副本。没有逐表领域合并器，没有新建自动选主协议，也没有把完整库选择作为普通正文冲突的处理界面。

真实接入最关键的修正是业务连带结果：正文会改变实体引用数、待回收队列和操作统计，不能让 Rust 与 TypeScript 各自猜测同一确认结果。因此通用日志区分显式元数据与本机投影，排序设备合并正文后捕获既有业务方法产生的完整行结果；手机撤回未确认投影，再重放确认事务，只安装正文标量投影。

正文二进制、投影、待确认标记和本机结果同事务保存。业务入口的 JSON 修改先保留原基线及目标，再转换成原节点树上的操作。整数编码保持 i64；正文规范 JSON 字节由共享层生成，规避 JavaScript 与 Rust 在字段排序和整数/浮点表示上的差异。标题保持在线性元数据中，正文投影不回写旧标题。

配对使用短期秘密与固定证书 HTTPS，移动原生客户端不关闭 TLS 校验。图片使用内容地址、分块校验、完整摘要和原子安装。手机前台恢复与原生恢复事件只负责唤醒同一个串行对账任务，不依赖后台定时器持续存活。

## 自动化证据

验证加载真实主库 98 表，并运行 Electron better-sqlite3、移动 Rust 的真实 SQLite/投影/HTTPS 代码和移动恢复调度。临时库用于所有实验，未连接个人正式资料库。

相关既有行为测试：桌面 56 项、移动 28 项通过；原独立混合原型 88 项回归通过。两端生产构建、共享层和客户端类型检查、Rust 构建、数据库结构及三项架构边界检查通过；定向静态检查无错误，仍有类型断言和空函数等警告。完整复现入口见操作指南；具体判据以当前脚本的断言为准。

## 审查结论

**总体：实验范围可继续验收，不能据此批准完整产品发行。** 审查覆盖共享状态机、SQL 事务、旧 JSON 转换、信任、附件、回收保全与恢复调度。

已处理的高优先级问题包括：两端独立投影导致跨记录不一致、数字精度与 Unicode 排序误判、旧标题回写、关闭/撤销后的迟到提交，以及确认缓存保留整篇 JSON 的内存增长。启动串行化，已发布排序头在库外耐久保存，设备凭据不进入资料库。

预算内的安全补齐通过自动验证。未覆盖真实 iOS/Android 挂起与杀进程、路由器隔离/权限拒绝、Windows 防火墙及持续大库性能；生命周期验证使用模拟事件，不是完整真机 UI 联调。入口默认关闭并标注实验。

剩余边界：固定桌面排序；没有自建 mDNS；检查点 64 MiB、正文 8 MiB、附件 25 MiB；聊天记录文件和独立 PDF 原件不搬运；主库指纹不一致会拒绝；完整正文检查点的磁盘写入与正文大小有关。不能读到的源图片保留引用，恢复原始文件定位的异常链路不能替代重新上传。

没有删除仍在使用的云端同步或旧协议实验，也没有自动发布、打包安装或合并此 worktree。
