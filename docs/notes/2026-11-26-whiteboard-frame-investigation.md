# 画框准入与交互性能摸底

目标：回答哪些元素不能真正归入画框，以及哪些画框操作会停顿、回弹或失败。本次仅新增独立基准与调查记录，没有修改产品行为。

实测已确认：空画框能创建，但只圈住一个已有矩形就触发“白板身份不能复用”；把同一个矩形拖入已有画框则成功。新建收纳的通用故障比元素类型限制影响更广。

## 元素准入盘点

“视觉上重叠”不等于“已经成为画框子元素”；以文档父子关系及拖动后是否随框移动为准。

下表的“允许”指元素准入规则；当前“新建画框圈住已有内容”还存在通用的身份冲突故障，不能把准入允许当作该入口已经可用，详见后文。

| 元素                                   | 新建画框圈住                 | 拖入已有画框                         | 扩大已有画框收纳       | 依据与限制                                                                                     |
| -------------------------------------- | ---------------------------- | ------------------------------------ | ---------------------- | ---------------------------------------------------------------------------------------------- |
| 图形、富文本、手写、图片、视频、音频   | 允许                         | 允许                                 | 允许                   | 能力系统允许；还要满足几何相交条件                                                             |
| 文档卡（含 PDF）、摘录、白板引用、网页 | 允许                         | 允许                                 | 允许                   | 文档/摘录/白板引用显式允许；网页使用默认允许能力。这里是代码规则核对，未逐一加载真实媒体验证   |
| 箭头/连线                              | 不允许                       | 不允许                               | 不允许                 | ArrowPlugin 的 canBeContained=false；连线仍可在视觉上位于画框内部                              |
| 另一个画框                             | 不允许                       | 不允许                               | 不允许                 | FramePlugin 禁止嵌套；创建手势也显式排除 frame                                                 |
| 分栏                                   | 前端会尝试收纳，文档模型禁止 | 不允许                               | 不允许                 | 创建手势对 column 特判放行；ColumnPlugin 和文档契约均声明 canBeContained=false，入口与模型冲突 |
| 思维导图                               | 允许                         | 独立导图根的专用拖动未走画框归属提交 | 不允许                 | 创建准入允许；MindPlugin 接管指针手势；FramePlugin.onResize 排除了所有容器，包含 mind-node     |
| 第三方插件元素                         | 由声明决定                   | 由声明及手势决定                     | 由声明及是否为容器决定 | 默认可收纳；插件可用 containment.canBeContained=false 禁止，专用手势可能影响实际拖入           |

准入判断的关键位置：

- `/packages/whiteboard/src/services/CapabilityService.ts`：canContain 统一能力查询。
- `/packages/whiteboard/src/extensions/creators/frame.ts`：collectFrameChildren，仅扫描根层，column 特判。
- `/packages/whiteboard/src/plugins/FramePlugin.tsx`：onResize 过滤所有容器；创建与扩大入口不一致。
- `/packages/whiteboard/src/plugins/MindPlugin.tsx`：claimPointerGesture / finishDrag / commitDrop，只处理导图自身的专用拖放。
- `/packages/whiteboard/src/collaboration/builtins.ts` 与 `/packages/collaboration/src/whiteboard-projection.ts`：文档模型的分栏准入禁令。

几何规则也会造成“放不进去”的感觉：当前默认要求元素矩形与画框（向外扩 padding，默认 20）的交集**严格超过元素面积的 50%**；只把鼠标拖到框内或刚好压住一半并不足够。创建只收纳根层元素，不会拆散已有容器。几何判断用 x/y/width/height，而非所有插件的实际可见包围盒；导图按根节点矩形判断，不按整棵子树。

## 采样方法与边界

独立 Vite 生产构建、真实 Whiteboard + Yjs WhiteboardModel + createWhiteboardBinding，本机手势合并开启，与桌面本机文档路径一致。使用临时文档及浏览器会话，不接入用户资料库。夹具按生产单批预算分批插入，不放宽限制。

环境：Apple M3 Pro、36 GiB 内存、Node 24.21.0、Playwright CLI 使用本机 Chrome，视口 1000×700。画框内容为具有真实几何和渲染的矩形，正常布局容纳子元素，较大内容自然延伸到视口外。输入共 48 步，移动时按 Alt 禁用吸附以隔离基本移动成本；创建手势因此使用 Alt 的中心扩张约束。本次数值采样使用 `--rounds=3`：每场景预热一次，再测两次；脚本默认预热一次、正式三次。4 倍 CPU 降速只覆盖大画框拖动。

记录 requestAnimationFrame 帧间隔 P95、最大值、≥50 ms 的帧数、Chromium TaskDuration 差值、pointerup 到下一动画帧的延迟、最终元素坐标和归属。函数阶段计时会嵌套，不能相加；它包含插桩成本。帧指标不是实际屏幕位移次数，不能据此宣称每个输入事件都显示了一帧。

本次不包含真实 PDF/图片解码、视频播放、网页嵌入、SQLite 保存、跨窗口与网络协作，也不做视觉验收。结果是内核与文档链路基线，不能替代用户原始大白板的现场采样。

共保留 23 个场景、69 条采样（每场景一次预热、两次正式），以及 6 条临界数量复核。原始数据在 [画框操作采样](./2026-11-26-whiteboard-frame-samples.json)。首轮整框移动通过画布 API 准备数据，后续从模型分批准备相同结构，以避免夹具准备阶段重复编译；数据中用 preparation 标明。255/256 临界点经两种准备方式复核一致。准备超时、定位器歧义等基准自身失败均已排除并补跑，不计作产品失败或性能数值。

## 整框移动的实测

以下数值来自两次正式采样；所有时间单位为 ms。子元素数为普通矩形数量，另有画框自身一条更新。

| 子元素数 | 帧间隔 P95   | 最大帧间隔    | 松手到下一帧 | 实际结果                               |
| -------- | ------------ | ------------- | ------------ | -------------------------------------- |
| 100      | 16.8         | 16.8 / 33.4   | 23.8 / 25.3  | 成功移动 220，模型与画布落点一致       |
| 255      | 16.8         | 33.3 / 33.4   | 52.7 / 52.6  | 成功移动；松手已有约 53 ms 停顿        |
| 256      | 16.8         | 33.3 / 16.8   | 14.0 / 14.6  | 预算超限，画框和子元素都回到原位       |
| 500      | 49.9 / 33.3  | 50.1 / 83.4   | 13.2 / 13.5  | 预算超限，未成功移动                   |
| 1000     | 49.9 / 133.3 | 283.3 / 150.1 | 14.3 / 13.5  | 尝试期间出现明显长帧，最终预算超限回弹 |

256 及以上样本的松手延迟较低，是因为手势此前已经被取消，不能据此判断操作流畅。4 倍 CPU 降速同样触发取消，因此不作为成功拖动的设备能力对比。

100 个子元素正式样本中 `board.apply` 累计约 48–51 ms；255 个时约 488–518 ms；1000 个失败样本中约 558–665 ms，而 `board.moveElement` 仅约 10–11 ms。不同数量的失败样本在不同时间取消，累计耗时不可直接作线性缩放比较；但同步更新链路是明确的主要成本。

## 其余操作与归因

下表列两次正式样本；菜单操作的延迟不能使用起始右键的 pointerup 计时，因此只报告整个菜单交互内的帧间隔与累计任务时间。

| 场景                                                   | 松手到下一帧   | 最大帧间隔    | 结果                                                        |
| ------------------------------------------------------ | -------------- | ------------- | ----------------------------------------------------------- |
| 1000 个子元素的画框，内部移动一个矩形                  | 105.1 / 93.1   | 100 / 100     | 正确移动，松手明显停顿                                      |
| 根层 1000 个矩形，移动一个                             | 87.8 / 91.2    | 99.9 / 100.1  | 同样停顿，说明通用文档提交已是瓶颈                          |
| 100 个画框，其中一个有 1000 个子元素，移动其中一个矩形 | 102.9 / 104.9  | 116.7 / 116.7 | 成功；其余 99 个为空框且在视口外，不代表 100 个复杂画框同屏 |
| 1000 个子元素，向外扩画框左上边界，不改变归属          | 82.5 / 81.4    | 66.6 / 66.6   | 正确修改画框边界，子元素位置不变                            |
| 从 1000 个子元素的画框拖出一个                         | 232.4 / 223.8  | 216.6 / 200   | 正确变为根层元素；跨容器比框内移动更慢                      |
| 单个矩形拖入空画框                                     | 12.9 / 13.1    | 约一帧        | 成功归入画框                                                |
| 1000 个子元素，自适应内容                              | 菜单动作不适用 | 66.8 / 66.7   | 成功收紧边界；累计主线程任务 124.5 / 120.3                  |
| 1000 个子元素，解散画框                                | 菜单动作不适用 | 83.3 / 83.3   | 预算超限，仍保留完整画框；累计主线程任务 131.3 / 130.4      |
| 新建空画框                                             | 13.1 / 12.9    | 约一帧        | 成功                                                        |
| 圈住一个已有矩形新建画框                               | 14.5 / 13.7    | 约一帧        | 身份重复，创建失败，原元素仍在根层                          |
| 1000 个根层矩形中圈住部分新建画框                      | 62.5 / 63.0    | 50.0 / 50.0   | 同样身份重复，原有 1000 个元素均保留                        |

平移与缩放的正式样本 P95 均约 16.7 ms，最大帧间隔不超过 16.8 ms；平移实际到达 (-180, -40)，缩放实际达到约 2.59 倍。本场景下未复现与内容提交同等级的卡顿。

根层与框内的单元素松手都在 90 ms 左右，不能把这部分耗时全部归因于画框绘制。跨容器操作还包含结构变更和容器回调，需优先关注绑定层的候选校验与投影刷新。代码中 `commands.submit` 对纯几何更新跳过扩展预检，而结构变更还会进入额外的 preflight；这解释了值得继续精确剖析的链路，不代表本次已完成各内部阶段的独立 CPU 归因。

另一个代码层面的差异：`gesture.commitPreview` 的本机平移快路只命中 `board.children` 中的单个根层文档卡。画框内的文档卡无法命中该分支，会走通用提交。本次没有加载真实文档/PDF 卡面，实际影响应补做现场测量。

## 已定位的机制

### 新建画框收纳已有内容的身份冲突

frameCreateGesture.end 返回「从根层 remove_node，再插入带原 children 的新画框」。文档绑定将前者编译为 remove_nodes，将后者的整棵子树编译为 create。WhiteboardModel 不允许重用已经出现过的元素身份，即使旧记录已经被删除。因此这条旧式收纳方式与现在的文档模型不兼容：前端能预览收纳，提交时仍失败。

分栏另有第二层冲突：即使改成保留身份的 move_node，分栏契约 canBeContained=false 仍会禁止其进入画框。需要同时确定并对齐产品规则。

### 大画框移动的提交上限冲突

FrameUtil.moveAll 递归复制并平移整棵子树，CapabilityService.buildElementMoveOps 经 BoardUtil.buildTranslateSubtreeOps 为画框自身及每个有坐标的后代生成 set_node。拖动预览进入绑定层，gesture.compact 合并同一元素的重复更新，但不同元素仍各占一条命令。

WhiteboardModel 单批上限是 256 条命令。一个画框加 256 个普通子元素需要至少 257 条，超过上限。手势中定期 flush 或松手提交都会碰到同一限制；定期提交失败会取消交互并恢复权威投影，表现为拖着拖着停止、回弹，而不仅是帧率低。包含嵌套分支时应计算有坐标的整个后代数，不能只看直接子元素数。

### 整框拖动的同步工作随子树放大

`/packages/whiteboard/src/collaboration/operations.ts` 的 compile 先整批规范化，再对每条 prepared 操作调用一次 BoardOperations.applyOperations 生成下一份 children。整框移动的每个输入步均展开子树，再逐条更新不可变结构，存在重复遍历和数组复制。应优先优化操作编译/投影的整批应用；只减少绘制细节并不能消除这段同步计算。

### 画框边界与松手的附加工作

调整画框大小会在手势中扫描根层候选和现有 children，并生成结构迁移。拖入、拖出及框内移动在松手时还会触发 notifyChildInserted/Removed；autoResize 随后重新计算所有子元素包围盒并提交画框边界。其成本需要和拖动过程分开观察。

## 复现与验证

```bash
node apps/desktop/scripts/bench-whiteboard-frame.mjs --output=/tmp/whiteboard-frame.json
node apps/desktop/scripts/bench-whiteboard-frame.mjs --only=entry:column,create:mind --output=/tmp/whiteboard-frame-admission.json
pnpm --filter @tau/whiteboard test src/utils/__tests__/FrameUtil.test.ts src/utils/__tests__/BoardOperations.frame.test.ts
```

基准保留失败操作的 outcome、failure 与 errors。只有最终效果正确的样本才可评价该操作是否流畅；预算失败的耗时不能作为性能通过结果。

既有 FrameUtil 与 BoardOperations.frame 两组测试共 20 条通过。夹具构建、定向静态检查、文档检查与白板公开入口边界检查均按本次改动验证。

## 修复优先次序

1. 先修复新建收纳的身份冲突：创建空画框后以结构移动保留已有元素身份，并维持同次撤销与失败原子性。
2. 解决整棵子树移动与单批预算的冲突，保留原子性、单次撤销与失败回滚；不应直接去掉预算，也不应把多批提交当作天然安全。
3. 将手势内同一批几何更新整批编译和应用，减少重复不可变树复制，再测单步与松手耗时。
4. 对齐新建、拖入和调整边界的收纳规则，以及文档模型准入；为导图专用手势明确画框归属提交。
5. 在内核基线修复后，用用户原始白板补测真实媒体、正文编辑、吸附、持久化及共享状态，确认剩余卡顿来源。
