# 密集白板手写压测

## 局部提交后的桌面结果

本机 Apple M3 Pro，Electron 生产构建，真实前台窗口、隔离资料库，通过窗口接收 CDP 模拟笔输入。两版使用相同主屏、笔压、历史笔迹和手势。初始有 800 笔，每笔 64 个点。每组先预热一轮，再测三轮。每轮在笔尖移动到抬笔后的第二个动画帧之间采样。测试包括渲染进程、主进程、数据库和保存回执，离页时等待正式保存屏障。模拟笔没有经过物理数位板驱动。

| ------------------------------------------ | ---------------: | ---------: | ---------: |
| Electron 连写 5 笔，每轮最长帧中位数       |         516.7 ms |    33.7 ms | 缩短 93.5% |
| 同场景，每轮 ≥49.9 ms 的帧数中位数         |               44 |          0 | 三轮均为 0 |
| 独立画布，240 笔背景，6 次同步分段提交合计 |           313 ms |       7 ms | 缩短 97.8% |
| 独立画布，800 笔背景，6 次同步分段提交合计 |         1,020 ms |       9 ms | 缩短 99.1% |

短笔组每轮写 13、13、73、13、13 点。分别在两组退出画布后，通过主进程重新打开文档，核对短笔组新增 20 笔及长笔组新增 4 笔的分段点数。长笔组只在本轮测量。帧间隔包含合成与调度波动，仍可见超过一个刷新周期的帧。后台耐久保存涉及整文档校验和数据库提交，其回执可能落后笔尖数百毫秒。桌面基准的隔离环境限制外部插件服务与非必要子进程，双端同步另以真实 WebSocket 回归测试验证。

### 桌面停顿来源

- 分段提交与抬笔在输入线程反复复制、校验、投影整份文档。局部候选复用命令校验器，在已验证的文档上核对身份、页和剩余容量。画布缓存只替换该笔及页面快照。容量临界、恢复区或并发附加写入有完整路径兜底。
- 主进程收到增量后做整文档接纳、编码和投影序列化。大检查点改在工作线程完成，数据库事务与保存回执继续由主进程控制。
- 真实窗口的 CPU 采样还记录到了元素树中大量菜单、图标的 React 更新，以及查询缓存对整份采样点的深比较。收起的元素树按需挂载并停订，已打开的树复用旧笔行，菜单项在首次打开时挂载。页面入口读取文档映射，列表读取缩略图数据，发起写入的视图按回播来源确认修订。

## 上轮基线与编解码优化

在本机重现了持续写字时周期性的停顿。画布已有 240 笔时，新写 5 笔产生 6 次分段提交，最长帧从空白板的 16.8 ms 增至 83.3 ms。优化后降至 50.0 ms。已有 800 笔时，优化后仍有明显卡顿。

### 上轮独立画布结果

每项取三轮中位数。「最长帧」先取每轮最大的动画帧间隔。慢帧以 49.9 ms 为界，容纳 Chromium 帧时间戳在 50 ms 附近的舍入。提交耗时为 6 次同步 appendStroke 的合计，包含模型写入与画布投影。模型列单列其中的 submit 耗时。

| 初始笔数 | 分段提交合计，前 → 后 | 其中模型提交，前 → 后 |  最长帧，前 → 后 | 慢帧数，前 → 后 |
| -------: | --------------------: | --------------------: | ---------------: | --------------: |
|        0 |            21 → 13 ms |            17 → 11 ms |   16.8 → 16.8 ms |           0 → 0 |
|      240 |          437 → 313 ms |          301 → 238 ms |   83.3 → 50.0 ms |           6 → 2 |
|      800 |      1,452 → 1,020 ms |          990 → 768 ms | 300.0 → 166.7 ms |           6 → 6 |

三个场景的 P95 帧间隔中位数均在 16.7–16.8 ms。卡顿集中在少数帧，单看 P95 会漏掉用户能感受到的停顿。

### 独立画布条件与复跑

Apple M3 Pro，Chromium 153.0.8010.12，无头生产构建，1000 × 700，未设置 CPU 降速。使用桌面白板同款 React 画布、Yjs 模型、文档绑定及本机手势配置。使用一次性内存文档。数据覆盖渲染进程中的交互与提交，Electron 主进程、资料库落盘、真实数位笔和跨设备同步未纳入计时。

每轮在新页面预置固定波形，每条历史笔迹 64 点，均位于初始视口。预热写 1 笔后，通过 Chromium 指针输入接口以 pen 类型、固定 0.5 压力写 4 条短笔和 1 条长笔。检查新笔在画布模型中分别保留 13、13、73、13、13 个点，并收到全部 6 次分段提交。计时起于正式输入，持续至抬笔后两个动画帧。基线取工作区优化前的实现，投影代码对应 dfca002ba，编解码使用未打补丁的 lib0 0.2.117。优化前后共用场景和输入。

从仓库根目录运行默认的空白板与 240 笔场景，或运行 800 笔场景。

```sh
node apps/desktop/scripts/bench-whiteboard-ink.mjs
node apps/desktop/scripts/bench-whiteboard-ink.mjs --large
```

### 上轮耗时来源与改动

1. 写到第 64 个采样点会同步提交，抬笔时提交余点。模型在隔离的文档副本中执行和验证命令，并编码文档核算容量。历史点越多，同一次新笔提交需要处理的字节越多。CPU 采样中出现了大量短字段名的 UTF-8 编解码调用。给渲染端使用的 lib0 ESM 实现增加最多 16 字节的 ASCII 快速路径后，常见采样点字段名可以直接读写。容量核算、隔离预检及 Unicode 路径沿用原有逻辑。
2. 提交后，画布曾给历史分段创建临时投影，重新拟合每条笔迹，再序列化比较整个结果。现在只投影可见子节点，并比较笔迹输入。历史笔迹的输入一致时直接复用已有轮廓和画布元素。单独开启这项优化时，240 笔场景下，6 次 appendStroke 中扣除模型提交后的耗时从约 136 ms 降到 86 ms，仍有 6 个慢帧。
3. 在 800 笔场景中，模型提交仍占优化后同步提交耗时的约四分之三。剩余瓶颈集中在分段和抬笔时的整文档工作。完整桌面应用中的绝对耗时还受主进程、其他窗口和实际资料库影响。
