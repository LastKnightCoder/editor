# 画框性能修复与实测

结论：整框拖动有显著改善，1000 个带文字元素在 1×、2×、4× CPU 降速的正式 4 秒样本中均达到逐帧位移门槛。**全部操作保持 60 FPS 的目标尚未完成**：4× 长拖动仍出现输入延迟尖峰，大批量新建、解散和拖出元素仍有同步提交长帧。

功能修复基线为 `2f2a2edf9`。本报告是本轮性能工作的快照，原始数据与失败样本见 [采样数据](./2026-11-26-whiteboard-frame-performance.json)。

## 测量口径

使用白板内核的 Vite 生产构建、Chrome 158.0.8127.37、1000×700 视口，通过 CDP 设置 1× / 2× / 4× CPU 降速。降速不模拟 GPU、磁盘或网络变慢。标签场景使用真实非空段落，仍有视口裁剪，并非 1000 个元素全部同屏。

正式拖动按浏览器 rAF 发出真实 CDP 指针输入，不插值伪造位置。每帧读取画框矩形的 SVG 屏幕矩阵，记录实际位置变化、帧间隔、输入到画面延迟与松手延迟；松手后继续采样 500ms。4 秒场景有 240 步输入，前 5 步未越过既有 5px 拖动阈值，因此应显示 235 次有效位移；8 秒场景应显示 470 次。

门控要求：帧间隔与实际位移间隔均不超过 20ms，全部有效位移有显示，最大输入到画面延迟不超过 34ms。20ms 是计时抖动容差，不能放过 33ms 的漏帧。预热显式标记，失败记录保留；最终坐标、模型提交及单次撤销/重做另行核对。松手延迟单列，门控通过不意味着这项延迟消失。

## 改善程度

同一 1000 个普通矩形、48 步原生输入的诊断对比：

| CPU 降速 | 修复前帧间隔 P95 | 修复后帧间隔 P95 | 修复前累计任务时间 | 修复后累计任务时间 |
| -------- | ---------------: | ---------------: | -----------------: | -----------------: |
| 1×       |          366.8ms |           16.8ms |          10631.5ms |            168.3ms |
| 2×       |          933.3ms |           16.8ms |          29191.1ms |            103.0ms |
| 4×       |         2166.6ms |           16.8ms |          77817.5ms |            297.0ms |

这组诊断启用了 CPU profile，输入按浏览器处理速度推进，累计任务时间不是同等时长吞吐量。profile 停止本身可能影响最大帧间隔，因此它只作前后诊断，不用作 60 FPS 放行证据。下面的正式采样不启用 profile。

1000 个带文字元素，预先选中画框，每档一次预热、两次正式 4 秒拖动：

| CPU 降速 | 正式样本数 | 位移间隔 P95 / 最大值 | 每轮实际位移 | 最大输入到画面延迟 | 松手延迟    |
| -------- | ---------: | --------------------- | ------------ | ------------------ | ----------- |
| 1×       |          2 | 16.8 / 16.8ms         | 235 / 235    | 19.5–19.7ms        | 20.2–21.0ms |
| 2×       |          2 | 16.8 / 16.8ms         | 235 / 235    | 19.3–19.7ms        | 19.2–19.4ms |
| 4×       |          2 | 16.8 / 16.8ms         | 235 / 235    | 27.6–29.7ms        | 40.1–40.2ms |

九条记录（含预热）均通过逐帧门控，全部撤销与重做正确。

8 秒长拖动的 1× / 2× 两轮均显示全部 470 次有效位移，最大间隔 16.8ms。4× 的两轮正式样本也显示全部 470 次，帧间隔和位移间隔最大 16.8ms，但最大输入到画面延迟分别为 **37.8ms、31.2ms**，第一轮超过门槛，因此长拖动验收失败。4× 松手延迟为 39.3–42.3ms。其预热样本还有 33.4ms 帧间隔和 39.1ms 输入延迟，不承诺冷启动全程 60 FPS。

## 尚未达标的操作

三档降速共 60 条操作记录，覆盖框内单元素移动、画布平移与缩放、调整框边界、圈住既有内容新建框、分栏/导图拖入、拖出、自适应、解散，全部最终结果及适用的撤销/重做正确。这些场景记录 rAF 间隔；只有整框拖动另有逐帧屏幕位移门控，不能把其他场景的静止帧当作已通过的位移证据。

最终 4× 大操作复测：

| 操作                                | 最大帧间隔（两轮） | 判断   |
| ----------------------------------- | ------------------ | ------ |
| 1000 个根层元素中圈住一部分新建画框 | 616.6 / 583.2ms    | 未达标 |
| 从含 1000 个元素的框拖出一个        | 283.4 / 283.3ms    | 未达标 |
| 1000 个元素的框自适应内容           | 50 / 50ms          | 未达标 |
| 解散含 1000 个子元素的框            | 400 / 400ms        | 未达标 |

解散的最大长帧由优化前的约 2843ms 降至约 400ms，新建由约 1900ms 降至约 617ms，拖出由约 683ms 降至约 283ms；改善仍不足以达到一帧预算。4× 扩框场景也有 33.3ms 帧。

剩余主要成本是同步候选复制、完整协议校验、合入和全量快照读取。它们需要继续从交互关键路径拆出；不能通过删除容量限制、跳过完整校验或拆成部分成功来换取数字。

## 已实现的修复

- 整批规范化几何操作，按不可变快照建立 ID 索引，避免每个子元素再次遍历和复制整树。
- 已验证基线上的几何更新保留有限数值、可见目标、容量上界、单事务和观察者隔离检查；无法证明时仍走完整候选。
- 复用模型的同一候选进行扩展资源与数据校验，只读取本批目标。分批候选不再为每小批重建整个文档，仍完整验证后一次合入。
- 解散使用逐步路径；历史保护范围按有序区间相减，避免平方级路径变换与区间扣除。
- 空标签不挂载只读编辑器；移动与选区布尔值按需订阅，消除全树 Context 通知。
- 画框用显示组平移跟随指针，逻辑投影合并更新；公开查询返回当前实际位移，读取不写文档。连线和裁剪使用移动后的坐标。
- 松手先保留终点显示，把最终模型事务与子树坐标归位错开；下一次交互前完成归位，取消、撤销和卸载清理显示状态。

## 验证与复现

定向白板测试 157 条通过（3 条环境门控用例未运行），模型及历史测试 39 条通过，真实 SQLite / WebSocket 测试 7 条通过，官网 69 条与发布验证 5 条通过；白板和协作包类型检查通过。复杂场景使用 909 个元素、旧分栏升级、嵌套分栏、跨容器、连线、20 轮 / 121 次真实拖放、撤销重做及 Esc 取消，另核对撤销后屏幕坐标与模型一致。

```bash
node apps/desktop/scripts/bench-whiteboard-frame.mjs --rounds=3 --warmup=1 --rates=1,2,4 --raf-input --preselect --labels --steps=240 --settle-ms=500 --verify --assert-60fps --only=drag:frame:1000 --output=/tmp/frame-acceptance.json
node apps/desktop/scripts/bench-whiteboard-frame.mjs --rounds=3 --warmup=1 --rates=4 --raf-input --preselect --labels --steps=480 --settle-ms=500 --verify --assert-60fps --only=drag:frame:1000 --output=/tmp/frame-long.json
node apps/desktop/scripts/bench-whiteboard-frame.mjs --stress --stress-rate=4 --output=/tmp/frame-stress.json
```

长拖动门控失败时脚本应非零退出，不能把它改为无条件通过。本次不做视觉验收；未将真实媒体解码、完整桌面保存链路或共享端性能作为 60 FPS 已通过的场景。
