## 确认的问题

### P1 联系线组件在单节点变化时仍重复扫描整张画布

位置：[ArrowElementComponent](/packages/whiteboard/src/components/ArrowElementComponent/index.tsx) 第 285–341 行，尤其是第 289–291 行与第 332 行。

新增的 `followsMind` 回退使任一导图节点变化都会为所有联系线取得两个端点。即使端点坐标完全没变，每条线也先调用 `PathUtil.getPathByElement`，之后才通过 diff 判断无需写入。该路径查询从白板根开始 DFS；联系线位于顶层导图之后时，每条线都会重新遍历整棵导图。批量变化时，两次 `elements.find` 还会反复扫描变化数组。

复现挂载真实 `ArrowElementComponent`，安装真实导图与箭头扩展，不 mock 几何、路径查询或事件处理。通过真实 `Board.apply(set_node)` 仅修改一个节点的 `textColor`，端点坐标不变；对原节点的身份 getter 计数，得到以下读取次数。计数包含该操作的其他工作，增长趋势与源码里的逐线 DFS 一致。

| 普通节点数 | 联系线数 | 单节点真实编辑的身份读取次数 | 批量事件的变化数组身份读取次数 | 普通对象批量事件中位数 ms |
| ---------- | -------: | ---------------------------: | -----------------------------: | ------------------------: |
| 100        |       50 |                       10,000 |                          5,150 |                      1.26 |
| 500        |      250 |                      250,000 |                        125,750 |                     23.54 |
| 1000       |      500 |                    1,000,000 |                        501,500 |                     84.89 |

批量事件计时使用普通属性对象，三次采样，窗口为 `element:change` 分发及 React `act` 收尾；变化数组计数另用 Proxy，单节点真实编辑计数另用 getter，插桩耗时不作为产品计时。组件挂载和样本构造在计时外。没有挂载导图节点正文，也没有真实浏览器绘制，因此这些数值不是桌面帧率。500 节点加 250 条线已超过一帧的常见时间量级；1000 节点加 500 条线是本机组件压力规模，不能据此突破协作文档的独立富文本根预算。

现有 `bench:mind` 直接查询透明度和绑定点，1000 节点、500 条线约 0.25 ms，但没有走组件事件与逐线查路径。这解释了为何现有性能守护通过，真实组件仍有二次方成本。批量数组扫描是相关存量问题；本批新增的全联系线回退进一步把单节点变化也扩大为整批路径查询。

建议先在查路径和提交之前比较实际端点变化，避免无变化的查询与写入；再按变化批次或不可变快照共享身份、路径索引，或复用统一箭头投影批次。验收应覆盖真实单节点编辑、折叠和整图移动的组件事件，而不只调用绑定点工具函数；行为断言继续保证折叠改接与预览位移正确。

### P2 并发删节点与新建联系线会持久保留悬空联系线

位置：[MindPlugin](/packages/whiteboard/src/plugins/MindPlugin.tsx) 第 922–938 行的联系线创建，以及 [mindRelation](/packages/whiteboard/src/utils/mindRelation.ts) 第 93–99、119–125 行的识别与删除。

两端从同一真实 Yjs 文档初始化，导图含 a、b。A 用 `deleteBoardElements` 删除 a；未同步的 B 用 `createMindRelation` 和真实画布插入操作创建 a→b。通过两端 `model.receive` 交换状态后，模型一致，a 已不存在，但箭头仍保存 `source.bindId = a`。二进制编码后重新创建模型与绑定，残留箭头仍存在。随后再删除 b，箭头依然没有清理。

删除操作只能收集当时已知的联系线，无法处理远端尚未到达的新增。合并后的 `isMindRelation` 又要求两个端点都在当前活树中；缺失 a 后，这条线失去联系线身份，后续删除 b 也跳过它。未挂载箭头组件的夹具证明这是已存入文档的残留，不能依赖某个渲染订阅最终清理。

建议明确并发合并后的有效性规则，在投影或合并边界按端点存活状态处理联系线，保留足以识别联系线及其原端点类型的事实，避免只依赖当前活树。需同时验证单端撤销删除后是否恢复、两端删除、乱序接收与二进制重开；新增联系线身份字段或改变删除语义前应先确认数据与撤销方案。
