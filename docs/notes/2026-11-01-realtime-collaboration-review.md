# 实时协作架构与代码质量调研报告

日期：2026-11-01。基于 `master`、HEAD `7ba64663e` 及调研时工作区；仓库已有未提交修改，包含设备同步相关文件。本轮只新增报告，不修改实现、测试或既有文档。

**结论：共享模型与协议层已有可保留的基础，最需要整理的是宿主编排层的职责与生命周期。** 目前的复杂度，一部分来自离线编辑、稳定节点身份、撤销、多窗口和跨存储提交的真实需求，另一部分来自这些需求持续汇入管理器、状态字段和入口适配。适合先修复已确认的问题，再按责任逐步拆分；没有证据支持推倒 CRDT 模型或统一重写两端运行时。

本报告记录 2 项 P1 生命周期问题、6 项 P2 行为或契约问题，以及独立的架构整理建议。P1 表示应优先修复的功能错误；P2 表示边界条件错误或维护风险。架构整理顺序不等同于故障严重程度。

## 2. 现状如何运转

### 2.1 四条需要区分的链路

| 链路         | 数据流                                                                                     | 真相与确认边界                                                                                    |
| ------------ | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| 桌面普通正文 | Slate 绑定 → 渲染端 Y.Doc → IPC → 主进程候选校验与缓存 → 主库投影                          | 即使没有共享，也进入名为 collaboration 的会话模块；主库保留正文身份与契约，活跃会话保留 CRDT 状态 |
| 桌面共享正文 | 上述本机会话 + Hocuspocus `/ws` + `/events` + 附件服务                                     | 服务端在同步消息继续处理前持久化；本机缓存和主库投影仍由宿主维护                                  |
| 移动共享正文 | Slate 直接绑定 WebView 会话的 Y.Doc → provider；文档更新另经串行队列写 Rust 缓存           | 编辑器和运行时共用文档对象；本机缓存写入是异步的，不能照搬桌面 IPC 副本结构                       |
| 桌面共享白板 | 画布文档绑定 → IndexedDB outbox → 主进程日志与投影；WebSocket 实时收发 + HTTP 操作回执对账 | 实时到达、本机耐久保存、主库投影、远端确认是不同事实；双通道分别承担延迟与结果确认                |

白板看起来“多了一套”，但其中日志、outbox、操作回执各有不同故障边界。不能因为层数多就合并成一次 `save()`，也不能将 WebSocket 已连接当成业务提交完成。

### 2.2 已经做对的抽象

- **模型和宿主总体分开。** `NodeTree`、`WhiteboardModel` 不直接依赖 Electron、Tauri、数据库连接或业务页面；宿主负责持久化、资源与投影。
- **稳定身份与编辑器投影分开。** 移动节点通过位置引用，正文与声明文本字段保留共享身份；拆分、合并及撤销的复杂性有实际并发语义支撑，不能用整篇 JSON 覆盖替代。
- **候选验证和正式安装分开。** [document-adapter](/packages/collaboration/src/document-adapter.ts) 统一正文和白板的校验入口；[DocumentWriteQueue](/packages/collaboration/src/document-write-queue.ts) 限制逐文档并发与排队预算。
- **提交回执是独立概念。** [DocumentOperationLedger](/packages/collaboration/src/document-operations.ts) 管幂等与终态，[DocumentSyncSession](/packages/collaboration/src/document-sync.ts) 管待确认分支、未知结果和隔离；存储、传输通过小接口注入。这是当前较好的抽象样板。
- **资源共享有角色边界。** 作者资源、成员上传、本机不透明引用和结束共享前的补存有不同规则。这些规则应集中命名，而不应在清理中删除。

共享包对正文与白板两个固定协议使用显式分支是合理的。当前没有必要再为它们引入可插拔策略注册器、通用事务框架或第三套事件总线。

## 3. 已确认的问题

### R1 · P1 · 单篇重连销毁其他文档共用的传输

位置：[移动管理器 `reconnect()`](/apps/mobile/src/features/collaboration/core/manager.ts#L320)、[传输池](/apps/mobile/src/features/collaboration/core/manager.ts#L1304)。

传输按服务器地址缓存，多篇文档的 provider 共用同一 `HocuspocusProviderWebsocket`。重连 A 时却销毁这个共享传输、从池里删除，再仅为 A 创建 provider。B 的 provider 仍引用旧传输，且 `attach()` 会因 B 已有 provider 而直接返回。

使用当前安装的 Hocuspocus 4.6.0 做了不联网最小复现：销毁旧传输并为 A 重建后，B 仍指向旧传输、新传输不含 B，旧传输 `shouldConnect=false`。这不是命名或风格问题，而是资源所有权与操作范围不一致。

**整理方向：** 服务器级传输由传输池独占生命周期。单文档重连只处理该文档租约；若确需重建整条连接，传输池必须负责重绑全部消费者，不能由单文档方法直接销毁。

### R2 · P1 · provider 销毁后继续复用已销毁的 Awareness

位置：[重连](/apps/mobile/src/features/collaboration/core/manager.ts#L333)、[缓存写入失败处理](/apps/mobile/src/features/collaboration/core/manager.ts#L1020)、[重新挂载 provider](/apps/mobile/src/features/collaboration/core/manager.ts#L1317)。

会话创建一次 `Awareness`，重连或保存失败时调用 `provider.destroy()`，恢复时将同一个 `session.awareness` 再传给新 provider。当前依赖的 `HocuspocusProvider.destroy()` 会销毁调用方传入的 Awareness；后者会清除观察者和保活计时器。

最小复现确认：provider 销毁触发一次 Awareness destroy；重新挂载并设置活动状态后，原视图的 change 订阅收到 0 次事件。光标层依赖这些订阅，重连后可能失去更新；实例的状态保活也不会因重新传入 provider 自动恢复。

**整理方向：** 先明确会话、provider、Awareness 的所有者。若重建 provider，就同时创建新 Awareness 并让视图明确换绑；若保留会话 Awareness，则使用经过核实、不会销毁它的断开方式。不要只将 `destroy` 改名为 `disconnect` 而不核对依赖语义。

现有移动缓存测试在 fixture 中替换了 `attach()`，因此 26 项缓存测试通过仍不能证明这两个真实 provider 生命周期正确。

### R3 · P2 · 隐藏的共享面板仍启动协作运行时

位置：[useContentCollabEntry 的 `shareSheet`](/apps/mobile/src/features/collaboration/useContentCollabEntry.tsx#L64)、[ShareContentSheet](/apps/mobile/src/features/collaboration/ShareContentSheet.tsx#L37)、[useCollaborationRuntime](/apps/mobile/src/features/collaboration/hooks/useCollaborationRuntime.ts#L17)。

`shareSheet` 无条件渲染 lazy 组件，只将 `open=false` 传进去；组件挂载后无条件调用运行时 hook。因而普通详情页渲染该入口时，即使用户没有打开发起面板，仍会加载面板、retain/start 协作，并可能注册设备身份及拉取列表。lazy 延迟的是首次渲染时的模块加载，不是等 `open=true` 才加载。

**整理方向：** 让运行时的持有与真实业务需求一致，选择只在面板打开时挂载，或给运行时 hook 明确的启用条件。还需检查 Activity 保活下的显示、隐藏与卸载语义。

### R4 · P2 · 正文条件写入仍用客户端墙钟生成期限

位置：[replaceContentSnapshot](/apps/desktop/src-electron/main/modules/collaboration/index.ts#L1493)、[服务端期限校验](/packages/collaboration/src/document-operations.ts#L136)。

正文条件写入使用 `Date.now() + 4 分钟`，服务端只接受不超过服务端当前时间 5 分钟的期限。客户端快两分钟会被判定期限过长；慢五分钟会立即过期。调用实际 `DocumentOperationLedger` 验证，三种偏移分别得到 `INVALID_OPERATION`、`EXPIRED` 和正常的 `PENDING`。

白板传输已经通过 [serverTime](/apps/desktop/src-electron/main/modules/collaboration/client.ts#L18) 与 [whiteboardRemoteTransport](/apps/desktop/src-electron/main/modules/whiteboard-documents/remote.ts#L173) 使用服务端 Date。两条提交链路对同一协议的时间语义发生了漂移。

**整理方向：** 复用服务端时间来源，并统一条件操作的请求、期限、未知结果查询策略。正文已保存候选副本，但尚未像白板一样完整使用耐久操作日志，不能简单认为二者恢复能力相同。

### R5 · P2 · Worker 在活动文档达到上限时拒绝已有文档的新连接

位置：[Worker `onAuthenticate`](/apps/collaboration-cloudflare/src/index.ts#L152)、[Node 对应逻辑](/apps/collaboration-server/src/server.ts#L128)。

Worker 的 20 文档上限判断仅检查总数，没有排除目标已经加载的情况。达到 20 份小文档时，给其中现有文档新增或恢复连接也会被拒绝。Node 实现先判断目标是否已存在，语义不同。此项由代码分支确认，未另做 20 文档的负载复现。

**整理方向：** 把“新增文档准入”和“向已有文档建立连接”分开；在共享业务判据中保留平台各自的资源预算实现。

### R6 · P2 · 两套服务的成员活动聚合已经不同

位置：[Worker `members()`](/apps/collaboration-cloudflare/src/index.ts#L115)、[Node `onlineActivities()`](/apps/collaboration-server/src/server.ts#L89)。

同一设备有多个视图，一个 editing、另一个 viewing 时，Worker 按遍历顺序覆盖结果；Node 保留 editing 的优先级。因此成员状态可能因服务实现或 Awareness 插入顺序不同而变化。

**整理方向：** 将 `editing > viewing > background` 这类纯规则提取为共享函数，HTTP/WebSocket 与存储继续由各服务适配。这是值得抽取的真实重复规则。

### R7 · P2 · IPC 声明与主进程注册没有形成类型闭环

位置：[命令声明](/apps/desktop/src/commands/contracts/collaboration.ts#L49)、[调用包装](/apps/desktop/src/commands/collaboration.ts#L52)、[主进程参数校验](/apps/desktop/src-electron/main/modules/collaboration/ipc-controller.ts#L140)。

`createSharedContent` 允许 `number | string` 的内容及来源 ID、任意 string 的来源类型；主进程实际只接受正整数与 `SOURCE_TYPES`。合法通过调用端编译的参数会在执行端被拒绝。`join` 声明返回 void，主进程实际返回申请结果，目前 UI 忽略了结果。

主进程自行拼接 channel 并用泛型包装 `ipcMain.handle`，没有通过已有 `CommandRef.register()` 约束参数和返回值，因此双方都能通过类型检查，却彼此不一致。

**整理方向：** 使用现有命令契约做类型化注册；先将类型与实际产品语义对齐，再替换注册入口。仍保留运行时输入校验，不把 TypeScript 类型当作鉴权与数据校验。

### R8 · P2 · 导出实现、测试与说明不同步

位置：[导出器](/apps/collaboration-cloudflare/scripts/export-node.mjs#L67)、[失败测试](/apps/collaboration-server/src/document-protocol.test.ts#L70)、[Node README](/apps/collaboration-server/README.md)。

导出器生成格式 6，并保留历史账本；测试仍期待格式 5 且没有历史账本，README 也仍写格式 5。当前协作架构与裁决已要求保留历史账本。选定测试实际失败于 `expected 6 to be 5`。

**整理方向：** 保留实现中的历史保全语义，更新直接相关测试与说明。不能为恢复绿色测试而将导出器降回格式 5，也不能仅删除失败测试。

## 4. 架构上应如何整理

### 4.1 首要问题是责任归属，不是文件数量

| 位置                                                                                         | 观察                                                                                | 为什么值得拆                                                                           |
| -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| [桌面 CollaborationManager](/apps/desktop/src-electron/main/modules/collaboration/index.ts)  | 2322 行；同时处理本机正文、云端共享、设备同步准备与接收、缓存、投影、窗口关闭和退出 | 普通正文、网络协议或窗口策略任一变化都要进入同一对象，状态和依赖相互扩散               |
| [白板主进程模块](/apps/desktop/src-electron/main/modules/whiteboard-documents/index.ts#L373) | 1582 行；`init()` 含 886 行装配、IPC handler 和业务流程                             | 初始化承担运行期编排；虽然已有 installation/transitions/sessions，入口仍持续承接新规则 |
| [移动 CollaborationManager](/apps/mobile/src/features/collaboration/core/manager.ts)         | 1503 行；身份、发现、发布、缓存、资源、投影、连接和页面运行时保活集中               | 资源所有权靠调用顺序维持，R1/R2 就发生在这些边界交汇处                                 |
| [桌面 useCollaborationDocument](/apps/desktop/src/hooks/useCollaborationDocument.ts#L31)     | 285 行函数，其中一个 effect 约 270 行                                               | React hook 同时充当 IPC 会话客户端、重试队列、草稿保全、冻结协议和资源适配器           |

建议先在现有目录内移动责任，不急着建立新 npm 包。拆出类之后若仍接收原管理器整个 `this`、一堆可变 Map 或几十个回调，依赖关系并没有改善。[CollaborationIpcContext](/apps/desktop/src-electron/main/modules/collaboration/types.ts#L42) 已有这种倾向：controller 同时取得存储、资源、客户端、会话表和一组生命周期操作。

### 4.2 先确立中立的正文会话，再挂载共享与设备同步

当前模块名使人误以为 collaboration 只在联网协作时使用，实际普通正文持久化也离不开它。建议按所有权建立下列边界，名称可随实现调整：

| 责任               | 独占内容                                           | 不应知道的内容                                            |
| ------------------ | -------------------------------------------------- | --------------------------------------------------------- |
| 正文会话           | 活跃 Y.Doc、身份、写入准入、本机保存状态、视图租约 | BrowserWindow、HTTP 路由、Tauri invoke、具体文章/项目表名 |
| 主库投影适配器     | 正文身份和修订比对、事务写回、关系及标题投影       | WebSocket 重连与 UI 状态                                  |
| 云端共享协调器     | 发布、成员、加入、结束共享、远端确认               | 本机窗口事件、设备同步内部表                              |
| 服务器连接池       | 同服务器传输与事件连接、消费者租约、重连           | 正文投影、资源文件写入                                    |
| 资源服务           | 准备、上传、解析、作者持久副本及队列               | UI 页面与编辑器生命周期                                   |
| 桌面生命周期适配器 | 关窗、退出、切库时的排空与回执仲裁                 | CRDT 内部布局、上传实现                                   |
| 移动运行时适配器   | 前后台、页面持有、Rust 缓存与宿主事件              | 桌面 IPC 副本结构                                         |

设备同步通过正文会话的有限接口准备、接收或排空内容，不再要求正文管理器直接解释设备同步内部 SQL。白板首次共享和退出的跨存储安装仍由已有 installation/transitions 边界承担。

最有价值的接口问题是“谁有权改变它，何时确认成功”，而不是“能否给所有保存方式套一个泛型接口”。例如提交返回应明确代表内存接纳、本机耐久或远端确认，不能让调用方从 `pending=false` 猜测。

### 4.3 将生命周期状态和连接状态分开

[CollaborationSession](/packages/collaboration/src/protocol.ts#L94) 同时混合服务端成员元数据、本机模式、连接态、pending、frozen、leaving 和 error；RuntimeSession 又增加保存错误、资源任务、dirty、projectionDirty 等字段。当前不是完全没有守卫，而是守卫分散，必须记住多字段组合才能判断可写。

建议保留独立的几个维度：

- 业务生命周期：打开、发布、活跃、关闭结果未知、已结束。
- 访问权限：可写、只读或已撤权。
- 本机耐久状态：待保存、已确认、失败。
- 远端确认状态：待发送、结果未知、已确认。
- 连接状态：连接中、在线、离线。

只对有明确迁移约束的生命周期使用小型判别联合或纯转换函数；其他维度保持独立。先统一 `canWrite` 与关闭放行判据，不建立覆盖全部组合的巨型状态机，也不必引入新状态机依赖。

### 4.4 服务端共享业务规则，平台实现继续分开

Node 与 Worker 的 store 分别约 903、1160 行，重复的不只是 SQL，还包括发布、成员权限、票据、候选接纳、资产持有与操作提交。R5/R6 说明相似代码已经产生行为差异。

推荐先共享已出现差异的纯规则，再考虑将“授权复核 → 候选验证 → 修订条件 → 原子提交”的公共用例收口，沿用现有 `DocumentSql` 与回执抽象。Node 的文件存储、Fastify，Worker 的 chunk、Durable Object 事务、R2 不强行统一。正式入口只使用 Worker，也不意味着 Node 可删除：它仍是开发服务、行为测试宿主、自托管参考和导出工具。

### 4.5 主进程应从无 React 的入口消费正文差分

[桌面管理器](/apps/desktop/src-electron/main/modules/collaboration/index.ts#L28) 通过 `@tau/editor-collab` 根入口消费 `applyNodeTreeContent`，它与 React 文档装配、光标组件放在 [同一模块](/packages/editor-collab/src/nodeTreeDocument.ts#L1)，实现还复用 `withNodeTree` 和 Slate。

复用同一套差分语义有价值，但它不需要依赖 React 光标与文档 UI 装配。建议建立明确的无 React 差分子入口，必要时保留无界面的 Slate 适配。先分离入口和模块依赖，再判断是否能进一步下沉到纯 NodeTree 操作；不要另写一套不一致的正文 diff。

共享包也存在公共入口不明确的问题：[根入口](/packages/collaboration/src/index.ts) 广泛导出模型、协议与存储相关能力，消费者又大量深引 `src/view`、`src/encoding`、`src/device-sync/*`。可在现有包内定义少量用途明确的子入口，逐步禁止业务方直接依赖 `src/`。其中 `view.ts` 实际导入 React，文件注释中的“无 UI 框架依赖”应纠正。

### 4.6 整理方案的取舍

| 方案                                       | 收益                                               | 成本与风险                                                                     | 建议                                   |
| ------------------------------------------ | -------------------------------------------------- | ------------------------------------------------------------------------------ | -------------------------------------- |
| 现有模块内按所有权拆分，再提取已重复的规则 | 保留现有协议与故障保全，逐步降低耦合，每批容易审查 | 需要明确接口和状态所有者，不能只移动文件                                       | 优先采用                               |
| 立即建立桌面与移动共用的完整运行时         | 未来可能统一更多流程                               | IPC 副本与同进程文档、同步 SQLite 与异步 Rust 持久化不同，容易形成大量平台开关 | 先等局部边界稳定，再以实际重复用例评估 |
| 重写 CRDT 模型及整个协作栈                 | 可重新设计全部接口                                 | 要重新证明节点身份、并发拆并、撤销、旧状态读取与资源保全，风险和验证成本最高   | 当前证据不足以支持                     |

## 5. 函数、导入与动态导入的具体整理建议

### 5.1 函数位置：按依赖与业务阅读顺序，不按语法偏好

扫描没有发现顶层可执行声明之后又出现静态 import 的情况；不能据此说“导入散落在函数中”。模块中确实混用声明函数、箭头函数和类方法，但这不是主要缺陷。

推荐顺序为：导入 → 类型和协议常量 → 小型纯辅助函数 → 公开入口 → 按打开、写入、同步、关闭组织的内部操作 → 单例导出。类的字段声明集中放置；当前白板模块和移动管理器有字段穿插于方法之间，增加寻找全部状态的成本。

无捕获、无副作用且描述独立概念的辅助函数可提升到模块级；依赖一份视图或会话生命周期的闭包留在拥有者内。`withNodeTree()` 约 524 行，但它的大量内部函数共享编辑器状态，不能机械拆成几十个携带大上下文的工具函数。应优先分离剪贴板、选区映射、文本字段和操作转换等完整责任。

白板 `init()` 则应优先整理：它可以只装配服务与注册类型化 handler，将共享、远端同步、租约、排空等业务操作移回对应服务。

### 5.2 静态导入：先去重复和明确边界

结构扫描发现 16 个文件有重复模块导入，共 18 组。例如桌面管理器从 `@tau/collaboration` 导入三次，移动管理器与两套服务端也有重复。部分来自单独的类型导入，不是运行错误；同一来源能清晰合并时可合并，类型使用 `type` 标记。

建议在所整理模块统一为系统依赖、第三方依赖、工作区公共入口、宿主服务、当前目录的顺序。长类型的 `import("包").Type` 在重复使用或核心接口中改为顶部 `import type`；它是类型查询，不是运行时懒加载，不能纳入“动态导入过多”的指控。

仓库 Oxfmt 明确 `sortImports=false`。如果要自动排序，应作为独立规则变更评估，不在架构重构里顺带全仓洗牌。优先保持移动责任后的文件可读和 diff 可审查。

### 5.3 动态导入：分别检查分包、启动副作用与依赖方向

统计范围内生产 TS/TSX 共有 12 个运行时 `import()` 调用，数量本身不多。

| 用途                                       | 判断与处理                                                                            |
| ------------------------------------------ | ------------------------------------------------------------------------------------- |
| 页面、成员面板、加入面板的 `React.lazy`    | 合理的 UI 加载边界，保留                                                              |
| 移动运行时的按需加载                       | 目标合理，但 R3 的无条件挂载破坏了业务按需；应先修挂载条件                            |
| 已静态依赖运行时的模块再次动态取 manager   | 不能据此承诺独立分包；移动插件宿主已有静态 manager 消费者，应核对完整导入图和构建产物 |
| 主进程动态获取 windows 或 Whiteboard table | 需核实是否为规避初始化依赖；优先注入确需的查询能力，未核实前不直接改静态导入          |

“代码没有首屏加载”和“没有启动网络/注册身份”是两件事。性能和副作用都需要各自的证据，不能用看到 `import()` 替代判断。

### 5.4 错误与类型：不要把所有告警当同一类问题

针对性 Oxlint 扫描为 0 error、509 warning，其中生产代码告警 172 项：100 项非空断言、33 项空函数、18 项未使用变量、18 项混合导出、2 项 hook 依赖、1 项 any。未使用变量里有用于剔除字段的解构，空 catch 也有已保全并交后台重试的分支，不能按数量批量“修复”。

建议先区分：错误已转成会话状态且有重试入口、刻意保留材料的降级、真正没有可观察结果的吞错。错误码在共享核心中保持结构化，Electron/Tauri 边界再编码；当前 Rust 字符串前缀和白板错误文本解析体现了传输层适配差异，应集中到边界。

移动 hook 的 `canWrite` 使用 ref 读取最新配置，不能机械将每次新建的函数加进 effect 依赖。先确定稳定回调和绑定生命周期，再处理告警。

Oxfmt 检查扫描 202 个文件，有 5 个文件需要格式化：桌面 `types.ts`，移动 `CollaborationUI.tsx`、`invitation-cache.ts`、`leaveCollab.ts`、`useContentCollabBinding.ts`。本轮未格式化。可见纯排版问题规模有限，不应作为大规模重构的理由。

## 6. 可清理内容与必须保留的边界

| 内容                                                        | 结论               | 前提                                                                                                       |
| ----------------------------------------------------------- | ------------------ | ---------------------------------------------------------------------------------------------------------- |
| `rekeySession` 注释、设计稿方案编号、历史任务编号等过程注释 | 可直接修正或删除   | 当前源码已无 `rekeySession` 实现；注释改写为当前行为事实                                                   |
| 重复导入、重复导入后再导出的组织、5 个文件的格式问题        | 低风险整理         | 独立小提交，避免与行为修复混杂                                                                             |
| `remoteVersionAvailable`                                    | 待退役候选         | 生产源码只初始化为 false，移动保存失败恢复仍读取；先统一当前版本冲突判据，再核对旧缓存读取和相关测试后删除 |
| 名叫 `migrations` 的本机记录及 installation                 | 不能按名称直接删除 | 仍用于当前白板首次共享、退出等跨存储安装，需要逐个核对消费者与记录语义                                     |
| Node 服务与旧备份格式读取                                   | 保留               | 仍有真实开发、测试、导出和历史保全消费者                                                                   |
| 两种编辑绑定：NodeTree 与本地 slate-yjs                     | 保留               | 前者承担结构化共享正文；后者仍用于 Markdown 文件等本机编辑，不是已失效的重复实现                           |
| tombstone、初始化保护、拒绝分支、回执和草稿保全             | 保留               | 承担撤销、迟到更新和未知结果恢复，不因“看起来像补丁”删除                                                   |

另一个需单独评估的边界是 Yjs 内部结构依赖：历史裁剪及白板历史预检读取 StackItem、时钟、结构存储等内部对象。当前固定依赖版本并有专门回归，是有理由的工程取舍。建议集中封装这些假设、保留升级检查入口，不在风格整理时顺带更换算法或 Yjs 版本。

性能方面存在值得测量的热点：正文单批更新会多次完整编码与候选复制，实体持有会扫描节点，白板 outbox 读取后在内存筛选。代码足以说明工作量随文档/积压增长，但本轮没有延迟或堆内存基准，不能宣称它们已造成用户卡顿。先固定大文档与积压场景测量，再决定索引、增量维护或缓存策略。

## 7. 推荐整理顺序与完成判据

| 批次                  | 范围                                                                     | 完成判据                                                                                               |
| --------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| 1. 修正具体行为       | R1/R2 的所有权、R3 启动条件、R4 时间来源、R5/R6 服务语义；R7/R8 分开维护 | 单篇重连不影响其他房间；重连后光标继续更新；普通详情页不因隐藏面板注册协作身份；备份测试与保全规则一致 |
| 2. 拆宿主责任         | 先整理桌面正文会话、投影、窗口排空；再收窄白板 init 与 IPC 上下文        | 改网络连接不需要修改正文投影；改关窗策略不需要理解协议内存布局；每份可释放资源只有明确拥有者           |
| 3. 收口共用规则与入口 | 活动聚合、准入判据、条件操作语义；无 React 差分入口；公共子入口          | 一个规则只维护一次；平台存储仍各自实现；主进程不从 UI 文档装配模块取无界面能力                         |
| 4. 风格和文档收尾     | 函数组织、导入、命名、过程注释、过期字段                                 | 静态检查与格式检查通过；架构文档描述新现状；移除实现前消费者已清零                                     |

每批只处理一个责任迁移或一组紧密相关问题。行为修复与纯移动/格式化分开提交；不同时升级协议、改持久化格式、升级依赖或重写 UI。新增测试限于已确认严重回归和复杂生命周期边界，其余优先维护直接相关现有测试并完成类型、静态、构建检查。

后续验收不以“拆成多少文件、减少多少行、增加多少测试”为标准。应检验：新规则能否放到唯一位置；资源释放是否可从一个拥有者追踪；本机耐久、投影与远端确认是否可区分；同一错误是否还需要在多个端打同样的补丁。
