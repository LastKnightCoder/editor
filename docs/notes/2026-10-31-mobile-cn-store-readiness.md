# Tau 移动端国内应用商店上架整改清单

结论：当前移动端已有可用的双端构建基础，但尚不具备直接向国内商店提交正式审核的条件。优先处理隐私告知与授权、APP 备案材料、AI 功能的合规边界和 iOS 插件分发方案，再生成正式候选包与提审材料。

本次按用户确认的**个人主体**审查苹果中国大陆区、小米、OPPO、vivo、应用宝。原生鸿蒙仅列为可选范围。审查日期为 2026-10-31，代码基线为 `09ad7ddda` 加当前工作区未提交改动；当前移动版本为 `0.2.15`，iOS 配置构建号为 `4`。这些是本次快照，不能替代未来候选版本的复验。

## 结论如何使用

- **P0**：提交前必须完成，或先决定该渠道实际提供哪些功能；含资格待核验项，不代表已经确认违法或必然被拒。
- **P1**：正式候选包放行前完成，部分与 P0 并行。
- **P2**：后续加固，不作为本次已证实的硬性上架门槛。
- **已确认缺口**：代码或本地构建产物能够证明。
- **待核验**：依赖外部证照、商店后台、服务地域或设备行为；仓库未保存材料不能推断材料不存在。
- **渠道方案待决定**：需要选定满足规则的实现方式，本报告不代替用户关闭功能或提交审核。

这是一次性审查快照，唯一位置为本文件。按仓库文档规则，不从架构、指南或索引文档引用它；未来启动整改时，将选定范围转入自含任务文档，完成后按实际代码更新架构与操作指南，本快照可删除。

## P0 提交前必须处理

### P0-01 核验主体与材料，补 APP 备案展示

**现状与证据**

- 用户选择个人主体；本轮没有登录任何商店后台，也没有查验身份证明、备案证照或软著原件，不能判断这些材料是否已经办理。
- [关于页](/apps/mobile/src/features/settings/about/AboutSection.tsx#L33)目前仅有官网、文档和源代码链接，未发现 APP 备案号及查询入口。
- 正式 Android 合并 Manifest 与输出元数据里的包名是 `com.txiong.tau_mobile`；[Tauri 配置](/apps/mobile/src-tauri/tauri.conf.json)及检查的 iOS 归档里 Bundle ID 是 `com.txiong.tau-mobile`。这是平台实际标识差异，不应直接当作包名错误修复；备案必须按各平台最终包信息填写。

**整改与验收**

- [ ] 完成首发商店的个人账号资格核验，记录实际可提交类别；OPPO、应用宝没有确认前保留渠道不确定性。
- [ ] 核实有效 APP 备案、主体、名称、域名及 Android／iOS 特征信息；若未办理，通过接入商或分发平台办理。网站已有备案不能替代补充 APP 信息。
- [ ] 从最终签名包提取公钥与**证书** MD5，避免误填 APK 文件 MD5；更换证书或包标识时重新核对备案信息。
- [ ] 准备本人持有或合法授权的版权材料，按商店接受范围提交；软件名称、主体及授权关系可对应。小米明确列出软著或 APP 电子版权认证材料，不据此推定其他商店都接受相同替代材料。
- [ ] 在应用显著位置展示有效备案号并提供查询入口，商店信息与备案记录一致。

依据：[工信部 APP 备案解读](https://www.miit.gov.cn/jgsj/xgj/hlwgl/art/2023/art_564bf0759d7e41d5b4aa8ce4996b9e84.html)、[APP 特征信息获取](https://help.aliyun.com/zh/icp-filing/basic-icp-service/user-guide/fill-in-app-feature-information)、[小米版权要求](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=1321)、[苹果中国大陆供应信息](https://developer.apple.com/help/app-store-connect/reference/app-information/app-information/)。APP 备案、网站备案、经营性电信许可按实际业务分别判断，不因应用收费就直接判定需要 ICP 许可证。

### P0-02 补移动端隐私文档与授权生命周期

**现状与证据**

- 检索移动端源码、原生源码和网站内容，未发现移动端专用隐私政策、用户协议、政策版本记录或统一隐私同意状态。网站的 [Tau 伴读隐私政策](/apps/website/content/docs/browser-companion-privacy.md)面向浏览器扩展，不能覆盖手机端行为。
- [AppShell](/apps/mobile/src/app/AppShell.tsx#L114)直接挂载启动编排，[bootstrap](/apps/mobile/src/hooks/useBootstrap.ts#L23)可检查已配置的同步服务；[插件 Provider](/apps/mobile/src/app/plugins/PluginProvider.tsx#L178)在存在中心来源插件时联网核验。这里没有隐私同意状态约束。
- 这能证明缺少统一机制，不能仅凭静态代码断言“全新安装首次启动已经上传笔记”或“采集了 IMEI”。

**整改与验收**

- [ ] 发布公开、稳定、无需登录即可读取的移动端隐私政策，应用内持续提供入口；用户协议说明实际服务、插件与 AI 使用边界。
- [ ] 文档与实际数据流一致，包含个人运营者、联系渠道、处理目的、数据种类、接收方、保留期限、删除与撤回方式、未成年人安排。
- [ ] 首次使用提供清晰的同意与拒绝选项，记录所同意的政策版本；拒绝非必要处理仍可使用基本本地笔记能力。
- [ ] 将需要授权的数据处理接到统一状态；在全新安装、恢复旧设置、有已安装插件、政策升级和撤回后分别检查。
- [ ] 政策更新需要重新授权的范围可判定；撤回能停止相应处理。不要把本地功能或所有非个人数据请求一概视作必须禁止的行为。

依据：[小米隐私自查指引](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=1281)、[苹果隐私要求 §5.1](https://developer.apple.com/app-store/review/guidelines/#privacy)。

### P0-03 为 AI 和第三方处理补明确授权

**现状与证据**

- [引用准备逻辑](/apps/mobile/src/services/aiChat/mentions.ts#L16)会把选中内容放入模型输入；整篇引用允许工具按需读取正文。[对话控制器](/apps/mobile/src/services/aiChat/chatController.ts#L292)直接启动模型运行，没有第三方数据外发确认步骤。
- [AI 服务](/apps/mobile/src/services/ai/index.ts#L35)的 manual 模式确认写入和执行，只读工具不询问。修改笔记前确认，不能代替把笔记发送给模型服务前的授权。
- [语音整理](/apps/mobile/src/services/speechRefinement.ts#L14)在已分配模型时把听写内容传入模型；[图片服务](/apps/mobile/src/services/image-generation.ts#L85)可读参考图，并通过插件执行生成或编辑，结果还会进入配置的资源上传目标。
- [插件授权弹窗](/apps/mobile/src/features/plugins/PluginPermissionPrompt.tsx#L37)已有允许／拒绝及网络风险提示，这是可复用基础；目前提示没有列明实际数据接收方和用途，不能覆盖宿主 AI、全部第三方处理或所有平台要求。

**整改与验收**

- [ ] 在首次向第三方 AI 发送个人数据前，明确展示服务商、实际接收端、数据范围和用途，获得明确许可；自填 API Key 不自动免除产品告知责任。
- [ ] 分别覆盖对话正文、引用笔记、工具读取结果、图片、语音转写／整理、TTS、声音复刻等实际启用路径。
- [ ] 服务商、接收地址或处理目的变化时重新判断授权；用户可撤回且基本本地功能可继续使用。
- [ ] 授权由实际执行入口验证，页面、工具调用和插件路径都不能绕过；操作审批与数据外发许可分别建模。
- [ ] 保留插件授权及撤销能力，按插件列明处理说明和第三方接收方，不用一句“插件可能联网”概括全部处理。

依据：[苹果第三方数据与 AI 共享要求 §5.1.2](https://developer.apple.com/app-store/review/guidelines/#data-use-and-sharing)、[个人信息保护法第二十三条等](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)。

### P0-04 确定国内 AI 范围，完成适用手续与标识

**现状与证据**

- 当前已有通用对话、语音整理、图片生成／编辑和语音合成，并支持自定义服务商与模型；未发现备案号／上线编号展示和国内服务范围控制。
- 检索移动端及公共对话组件，未找到统一生成内容标识机制。[消息操作](/apps/mobile/src/features/aiChat/messageActions.tsx)支持复制和存为卡片；[图片结果保存](/apps/mobile/src/services/image-generation.ts#L137)没有宿主侧标识校验或补充。上游服务可能已含部分标识，因此不能断言所有现有输出都无标识。
- 没有证据显示现有反馈入口已形成针对生成结果的内容举报、定位、响应与处置闭环。

**整改与验收**

- [ ] 列明首发实际提供的 AI、ASR、TTS、图片和复刻能力，对照模型、应用／功能的备案或登记范围；需要属地登记的，通过属地程序核验并办理，适用时公示模型名称及备案号／上线编号。
- [ ] 对自填第三方接口、通用聊天机器人和端侧能力分别确认适用性，不把“只调用已备案模型”或“用户自备 Key”当作当然豁免。
- [ ] 为适用的文本、图片、音频等输出提供显式／隐式标识方案，验证复制、存为卡片、下载、导出及后续发布不丢失必要标识；保留并核验上游标识。
- [ ] 对生成内容提供适当的治理、举报和处理能力，并如实说明年龄与服务限制；仅添加“仅供参考”不能替代整个治理机制。
- [ ] 为每个商店准备是否提供生成合成服务的说明及标识材料。若个人主体暂时无法满足某项服务要求，可选择首发不提供该能力，但须在构建、原生调用、恢复数据、插件安装与服务端分发上落实一致边界；本次不执行功能裁剪。

依据：[网信办生成式服务备案与应用登记公告](https://www.cac.gov.cn/2026-09/14/c_1791136833136332.htm)、[生成合成内容标识办法第四、五、七条](https://www.cac.gov.cn/2025-03/14/c_1743654684782215.htm)。是否需要具体手续由实际服务形态及属地要求决定；接入模型和应用自身的手续应分别核验。

### P0-05 决定 iOS 在线插件的审核路径

**现状与证据**

- [原生插件中心配置](/apps/mobile/src-tauri/src/plugin_center.rs#L78)对 Android 和 iOS 都开放安装；运行时可接入原生网络、业务数据和提供方能力。
- [插件执行器](/packages/plugins/src/rendering.ts#L121)通过 `new Function` 运行下载的 JavaScript，属于实际运行软件能力，不只是静态内容下载。
- 已有中心来源校验、包校验和权限提示，但未找到与苹果在线插件规则对应的完整软件索引 Universal Links、年龄限制和逐软件数据权限审核材料；本轮也未查验 Apple 是否已给特定原生能力开放许可。

**整改与验收**

- [ ] 选择首发方案：一是保留在线插件并逐项满足规则；二是在商店构建中使用随包固定能力、明确限制动态安装和执行。两者涉及的工作与功能范围不同，需要先选定。
- [ ] 若保留在线插件，核验原生能力暴露是否需要且已获 Apple 许可，落实每个软件的数据授权、索引与 Universal Links、年龄控制及内容治理；现有“始终允许”不能未经核对就视为满足全部条件。
- [ ] 若限制动态插件，先记录消费者与保留边界，确保笔记现有正文可读；限制需覆盖 UI、安装命令、已安装包启动、恢复与更新路径，不能仅隐藏中心入口。
- [ ] 提交与实际机制一致的审核说明，不以 TestFlight 内部测试记录代替正式审核结论。

依据：[苹果在线软件与插件要求 §4.7](https://developer.apple.com/app-store/review/guidelines/#mini-apps-mini-games-streaming-games-chatbots-plug-ins-and-game-emulators)。规则允许部分插件形态，因此本报告不认定“动态 JavaScript 一律禁止”，也不认为自有插件中心天然符合要求。

### P0-06 固定商店分发候选包并复验签名

**现状与证据**

- 已有 [iOS 签名与导出手册](/docs/guides/ops-ios-signing.md)及历史内部测试记录，构建脚本也有 `app-store-connect` 导出入口，不需要从零建设签名流程。

- 本地 Android arm64 release APK 为 `0.2.15`／`versionCode=2015`，`apksigner verify` 通过，但不能代表当前所有未提交改动已经进入该包。

**整改与验收**

- [ ] 冻结本次范围及依赖版本，确认哪些当前改动进入候选版本；建立“源码版本／工作区范围—包版本—包摘要”的对应关系。

### P1-02 删除、身份、反馈保留与日志闭环

**证据**：[协作身份](/apps/mobile/src-tauri/src/collaboration.rs#L216)可自动向指定服务器注册设备；本次未发现用户级身份撤销及对应服务端删除闭环。[反馈服务端](/apps/plugin-portal/api/app-feedback.ts#L432)明确永久保留反馈记录和附件，仅清理额度计数。[控制台记录器](/apps/mobile/src/utils/console-logger.ts#L24)与 [日志收集](/apps/mobile/src-tauri/src/logger.rs#L239)主要做序列化、截断、限流和打包，未见统一敏感信息脱敏。已有日志开关且默认关闭，不能描述为自动上传日志。

- [ ] 给本地笔记、AI 会话、协作设备身份、反馈及附件分别定义保留和删除方式；已有内容删除能力继续复用，不要求重新实现所有删除功能。
- [ ] 对服务端个人数据提供用户可行使的删除／撤回渠道；如果构成可创建的服务账号，再按适用要求提供账号删除。没有传统登录页不代表不存在服务端身份。
- [ ] 将反馈、截图和日志的保存期改为有目的、有期限及可执行清理的策略，依法需留存的部分说明例外，避免默认无限期保留全部内容。
- [ ] 在落盘及提交前脱敏 Token、鉴权头、API Key、签名 URL 和用户正文；增加针对错误对象和插件日志的验证。当前仅确认防线缺口，未通过读取真实用户日志来断言发生泄漏。
- [ ] 反馈页面说明接收方和数据用途，允许用户检查或移除附件，验证关闭日志开关时没有日志附件。

依据：[个人信息保护法的最短必要保存与删除要求](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)、[苹果数据保留与删除要求 §5.1.1](https://developer.apple.com/app-store/review/guidelines/#data-collection-and-storage)。

### P1-03 iOS 权限用途与隐私清单

**证据**：[聊天输入](/apps/mobile/src/features/aiChat/ChatComposer.tsx#L319)有 `capture="environment"` 拍照入口，但 [持久 Info 配置](/apps/mobile/src-tauri/Info.ios.plist)和本次检查的 0.2.15 归档没有 `NSCameraUsageDescription`。两处已有麦克风及语音识别用途说明。本次在源码及该归档中都未找到 `PrivacyInfo.xcprivacy`。

- [ ] 为实际相机使用补用途说明，进入最终包后验证拍照、拒绝权限和重新授权；本次未在设备触发，不能宣称已复现闪退。

- [ ] 审计应用、Rust／Swift／第三方依赖使用的 Required Reason APIs 与需申报 SDK，按实际用途添加隐私清单并确保归档携带。

依据：[Apple 相机用途说明](https://developer.apple.com/documentation/bundleresources/information-property-list/nscamerausagedescription)、[Required Reason API 说明](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api)。

## P2 后续加固

### P2-01 凭据、备份与插件隔离

[AI 设置](/apps/mobile/src-tauri/src/ai_settings.rs#L261)把 API Key 写入配置对象，[设置写入](/apps/mobile/src-tauri/src/setting.rs#L317)序列化保存到应用数据目录；Unix 写入模式为 `0600`，已有基础保护，不等于密钥公开暴露。建议进一步评估 Keychain／Keystore、系统备份排除、导出脱敏与本地数据保护。

[Tauri 配置](/apps/mobile/src-tauri/tauri.conf.json)关闭 CSP，下载插件在宿主 JavaScript 环境执行。建议在保持已授权功能的前提下评估最小能力、可控网络目标及隔离方案；现有模块白名单不应被当作完整沙箱。这是架构加固建议，不是本轮证明已经被利用的漏洞。

### P2-02 构建体积与测试告警

本轮 Vite 构建成功，但出现大于 500 kB 分块和部分动态导入不能独立分包的提示；反馈页测试存在 React `act(...)` 告警。建议按性能与测试稳定性安排修复，不把这些提示列为已确认的商店拒审原因。

## 建议执行顺序与放行判据

1. **并行准备个人材料和首发范围**：先核实各商店资格、备案、版权材料，同时决定首发保留哪些 AI 与插件能力。材料办理和渠道资格最容易成为外部等待项。
2. **先做通用隐私闭环**：P0-02、P0-03 与 P1-02、P1-04 一起设计，避免文档、授权和后端删除分别实现后互相矛盾。
3. **落实平台方案**：完成适用的 AI 手续与标识，决定 iOS 插件路径；安卓接入渠道更新，iOS 核验权限与隐私清单。
4. **固定候选与材料**：生成新的商店候选包，完成 P0-06、P1-05、P1-06，再由用户授权实际提交。

放行时，适用的 P0 与 P1 均需有验收证据；“待核验”项目必须明确为已满足、平台明确不适用或已从该渠道发行范围移除。现有自动检查通过，不等于法律合规、设备验收或商店审核通过。
