## 确认的问题

### P1 同一父节点下不同外框的并发操作互相覆盖

位置：[MindUtil.ts](/packages/whiteboard/src/utils/MindUtil.ts#L111)，`addBoundary` 与 `updateBoundary`；协作提交最终经 `WhiteboardModel.set_data` 按属性整体写入。

两个客户端从同一真实 Yjs 文档初始化。A 为 a 添加外框，B 为 b 添加外框，双方交换增量后模型一致，但两个新外框只剩一个。另一个复现从已有两个外框开始，A 修改第一个标题，B 修改第二个标题；合并后仅保留其中一个新标题。

原因是 `boundaries` 作为普通数组存入父节点的单个 data 属性。每次增加、删除和改标题都会替换整个数组，Y.Map 对这个属性的冲突裁决不能合并数组内部的独立操作。任务约定允许同一个短标题并发编辑时后写者胜，但这里互相覆盖的是不同外框，超过了该边界。双方最终模型一致并不能证明内容完整。

建议：为外框提供按稳定 id 的协作粒度，使不同外框的新增、删除、范围和标题修改独立提交；同一个标题仍可保持既定的冲突规则。涉及持久化数据表达与命令边界，需要先确认具体方案，并验证旧数据、局部撤销和二进制重开。

### P1 联系线的端点与折叠查询随节点数和联系线数相乘

位置：[mindRelation.ts](/packages/whiteboard/src/utils/mindRelation.ts#L69) 的 `visibleRelationEnd`，其调用方包括 `mindRelationOpacity` 和 `MindPlugin.getArrowBindPoint`；[ArrowElementComponent](/packages/whiteboard/src/components/ArrowElementComponent/index.tsx#L156) 渲染时求透明度，任一导图节点改变时还会对所有联系线重新求两端。

`visibleRelationEnd` 为单个端点先用 `MindUtil.getRoot` 扫描白板与导图，再从根搜索节点路径；识别联系线本身又多次通过 DFS 找绑定元素。每条线重复上述查询，整批成本约为 O(节点数 × 联系线数)。本轮压力测试每条线只调用一次透明度和两端绑定点查询，没有挂载 React，没有计入样式、文本、路径构造与 DOM 成本。

下表为普通属性对象三次采样的中位数；访问计数另用 getter 插桩运行，计时与计数分开，避免把插桩开销当成产品耗时。

| 普通节点数（另加根节点） | 联系线数 | 普通对象整批查询中位数 ms | 插桩单批 id 读取次数 |
| ------------------------ | -------: | ------------------------: | -------------------: |
| 100                      |       50 |                      2.06 |               60,800 |
| 500                      |      250 |                     41.62 |            1,504,000 |
| 1000                     |      500 |                    175.10 |            6,008,000 |

节点与联系线各增一倍，访问次数约增四倍；小样本也体现相同趋势。500 节点样本已有明显单帧成本。1000 节点样本是本机纯查询工作量，不能用来推定协作文档允许的富文本根规模。这些读数不是实测桌面帧率，也没有进行截图或视觉走查。

建议：每次投影或几何批次构建并共享节点、根、父节点及最近可见祖先索引；随结构和折叠变化失效。用查询访问次数约束复杂度，用门控 benchmark 记录时间；继续保留折叠端点和局部移动行为测试。

### P2 不同范围的概要仍会完全重叠

位置：[ranges.ts](/packages/whiteboard/src/utils/mind-layout/ranges.ts#L184) 的 `placeSummary`。

准备等尺寸的 a、b、c 三个兄弟，先为 a..c 添加概要，再为 b 添加概要。两个范围不同，因此不会触发同范围复用；两个范围的几何中心与外侧边缘相同，最终两个概要正文处于完全相同的位置。四种布局都复现：mind、logic 的两份正文均为 x=288、y=23.795；org 为 x=48、y=230；tree 为 x=188、y≈163.795。两份正文矩形相交断言失败，不依赖截图判断。

现有修复只覆盖完全相同端点的重复概要，未解决包含或交叠区间之间的空间分配。用户能从现有入口正常创建上述不同区间，重叠后难以分别点选和编辑。

建议：明确同父级多个概要的排列规则，对嵌套、交叠和相邻范围分配独立空间，并计算概要子树的尺寸；若产品决定限制组合，则创建入口必须明确约束，不能直接生成重叠正文。

### P2 删除包含导图的画框没有清理联系线

位置：[SelectionActionUtil.ts](/packages/whiteboard/src/utils/SelectionActionUtil.ts#L68)。

在画框里放一个含 a、b 的导图，插入绑定 a→b 的顶层联系线，然后通过真实 `deleteBoardElements` 删除整张画框。a、b 已不存在，联系线仍留在白板里。未挂载箭头渲染器的真实协作文档夹具中，残留箭头的 source/target 仍持有 a/b 的 bindId。

`removedMindIds` 只汇总直接选中的导图根和局部树删除差集，作为 `otherElements` 删除的画框及其后代未纳入统计。即便某个渲染订阅后续解绑箭头，也不满足删除联系线应属于同一操作的契约。

建议：按最终结构的实际删除差集清理联系线，覆盖容器整体删除；不要把移动或解散画框中仍存活的节点算成删除。保留单步撤销、跨导图联系线和未选中箭头的验证。
