# 跨端插件正式接入方案

日期：2026-10-22。基线：`cf90b23f3`（三端可信插件 spike）。本文是正式接入提案，不是已实现架构；本轮仅提交 spike 并完善方案，不实施下述接线，不修改或部署生产插件中心。

文档定位：一次性方案产物，唯一位置为本文件，不由活文档或代码引用。开始实施时将确认后的需求、方案、决策与验收完整写入该实施任务；完成后按实际落地点沉淀，不能把本提案直接当作现状。

## 1. 目标与边界

目标：同一个 SDK、一套作者模板、同一个插件身份，支持桌面、Android、iOS；页面、编辑器内容与业务逻辑尽量共用，交互通过宿主适配或作者的分端视图实现。

本阶段的“正式接入”指接入真实应用壳、正常数据与生命周期，去掉 spike 的固定样本特例；不等于立即开放移动生产分发。生产插件中心保持当前版本时，移动端仅能通过受控开发/测试来源验收，普通用户的中心下载闭环仍有独立上线门槛。

保留四项用户约定：

1. 页面声明与功能入口分离；桌面侧栏、移动“我的”是宿主的呈现选择。
2. SDK 显式提供平台、界面形态、输入能力和 API 可用能力；静态编辑器组件也能读取。
3. 编辑器标准交互由宿主适配，不让每个插件重写拖拽把手、块菜单和插入入口。
4. 作者可拆分复杂的桌面/移动视图，共用节点类型、数据结构、codec 和业务操作。

共同运行范围先限定为可信 Web 插件：生命周期、命令、功能入口、页面、设置、私有 KV、普通正文扩展及其 codec/源码编辑。Node 后台、Shell、本地 stdio MCP、任意系统 API、后台常驻和白板插件不进入移动首版。网络、媒体、业务数据接口按真实消费者逐项开放，不靠占位实现凑齐整个 PluginContext。

## 2. Spike 证明了什么，尚未证明什么

| 已有证据                                              | 可复用结论                                      | 正式接入仍需完成                                                                |
| ----------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------- |
| 三端计数器和 ABC 的 JS/CSS 摘要相同                   | CJS、React、SDK 组件、abc 节点与 codec 可以共用 | 完整作者工具链、平台声明与发布兼容                                              |
| Electron 侧栏、移动功能列表均可打开同一页面           | 页面与功能入口的拆分成立                        | 正式 DesktopPluginRuntime 与移动“我的”接线；spike 桌面用的是验证壳和移动 router |
| ABC 分端源码编辑、撤销/重做、SVG 与 Markdown 往返通过 | 宿主组件可以消化交互差异                        | 正常正文、只读预览、协作、导出/索引与全部编辑入口一致性                         |
| WebView 重载与移动进程重启恢复通过                    | 当前存储/生命周期模型可实现                     | Rust 私有目录、正式数据库、ZIP 事务、损坏恢复、切库隔离                         |
| Android 系统返回实际验证通过                          | 既有返回仲裁可承载插件浮层                      | iOS 真机边缘返回、软键盘、未保存守卫、输入法与手感                              |
| 普通生产构建未包含验证入口                            | 开发载体可隔离                                  | 不把固定样本许可、localStorage 包缓存和本地报告服务搬进正式路径                 |

测试范围为 macOS Electron 43、Android 16 模拟器和 iOS 26.3.1 模拟器，不等于最低系统版本兼容，也不等于 App Store/Google Play 审核通过。现有可信执行模式没有恶意代码沙箱保证。

## 3. 总体结构与单一事实源

| 层                             | 所有者                                                          | 接入原则                                                     |
| ------------------------------ | --------------------------------------------------------------- | ------------------------------------------------------------ |
| 作者 API、能力词表、包兼容判断 | `packages/plugins`                                              | 三端共用契约与纯校验，不引入 app/features 依赖               |
| 作者模板、构建与 SDK 发布      | `scripts/plugins/template`、`scripts/plugins/package-sdk.mjs`   | 一个模板体系，一个公共 SDK 发布包                            |
| 编辑器与 UI 标准交互           | `packages/editor`、`packages/editor-source-view`、`packages/ui` | 定义平台无关注入点；具体平台行为由宿主提供                   |
| 桌面业务与页面承载             | `apps/desktop/src/app/plugins`、对应 feature                    | 使用真实 Page/Sidebar、权限和数据适配器                      |
| 移动业务与页面承载             | `apps/mobile/src` 的插件域与 app 组装                           | 使用既有 router、EditorKit、“我的”和返回仲裁                 |
| 移动包文件与持久化             | `apps/mobile/src-tauri`                                         | Rust 管下载/文件/数据库，不执行插件 JS                       |
| 插件中心                       | 本阶段不变                                                      | 只定义以后需要的兼容契约，不修改 API、D1、审核 UI 或线上数据 |

同一个能力标识、平台声明和包校验逻辑只维护一份。不同宿主共享协议与纯逻辑，不共享依赖 Electron 或 Tauri 的实现；不要把整个桌面 runtime 搬到 mobile，也不要先抽一个没有实际消费者的庞大跨端框架。

## 4. SDK 需要改什么

### S1 环境从固定快照升级为宿主环境源

现有 `context.environment` 和 `usePluginEnvironment()` 保留作者入口，补宿主级 getSnapshot/subscribe：

- platform 和能力配置由宿主明确给定，不由插件解析 User-Agent；平台、layout、touch/finePointer 不合并为一个 isMobile。
- layout/input 响应窗口尺寸、旋转、媒体查询等变化。hook 订阅同一环境源；`context.environment` 读取最新不可变快照，作者长期解构保存的值仍只是当时快照。
- 平台/profile/必需能力在一次插件会话中保持稳定；更换需要重建上下文，不能在输入设备变化时偷偷改兼容性或撤销数据权限。
- 静态编辑器、插件页面、预览分别接 Provider。博客是独立 Web 渲染宿主，应明确表达 web/只读渲染上下文，不能假装成 desktop；这属于环境消费补齐，不扩博客业务能力。
- 正式已接线宿主不应仍返回 unknown；unknown 只用于尚未注入的旧宿主/无场景诊断，不能据此默认开启完整能力。

落点：`packages/plugins/src/environment.tsx`、`contract.ts`、`host.ts`。验收：同一组件在旋转/缩放后更新，不丢草稿；两个作用域不会串环境；不经过 activate 的内容渲染可读取环境。

### S2 功能入口与页面生命周期

延续 `navigation.registerEntry({ id, title, icon, page, params })`，不增加作者指定宿主组件路径的 API。补齐：

- 页面手动注销时，与其绑定的入口一并失效并退出展示；不是等用户点击陈旧入口后才报错。
- 启用失败、停用、切库、窗口关闭和更新会话均回收入口/订阅；同一条目 ID 只能在该插件当前激活范围内唯一。
- 入口的排序、默认分组、高亮由宿主统一处理；不把桌面 sidebar 的拖放子项直接塞进移动入口接口。
- pageContext 的 isActive 同时考虑真实栈顶、应用前后台、实例存活；状态提供器在离开、淘汰和停用后不可继续被读取。
- `registerDismiss` 定义为“注册当前页面浮层退场”，桌面 Esc、移动返回分别接线；不统一成“Esc 也退出页面”。
- 对存在未保存草稿的正式自定义页，补一个有明确返回值和注销语义的离开守卫契约，映射已有宿主守卫；不要复用 registerDismiss 冒充保存确认。

落点：`navigation.ts`、`pages.ts`、`host.ts`；共同生命周期用例放 SDK。导航入口的贡献统计在正式宿主接入时一起补齐，当前 spike 没有扩展正式统计类别。

### S3 可用性、授权、兼容性分别建模

把 spike 自由字符串能力集合收口为版本化词表，例如页面、导航、存储、编辑器源码等能力各有稳定协议版本。客户端配置源于实际适配器，不让作者自行宣称宿主具备能力。

- 必需能力：执行模块前检查，缺失则不可启用。
- 可选能力：作者显式检测，未使用不影响核心功能；调用未实现接口时返回清晰错误，不静默 no-op。
- 权限：继续使用业务数据授权模型；有 data API 不代表用户已经授权。
- 校验：静态依赖检查只能发现一部分误用，不能宣称能够证明任意 JavaScript 不会越界。同环境执行仍是可信模型。

落点：公共词表、`package.ts`、包兼容纯函数、`shared-modules.ts`。模块表采用显式 profile；不能像 spike 只给几个导出后就宣称完整 SDK/UI 可用，也不引入第二份移动 SDK。

### S4 编辑器支持等级与提交保护

正式声明区分“显示”“插入”“编辑”，按目标平台与节点类型表达；包内多个节点可以有不同等级。具体字段属于未发布包协议，本文确定语义，不将其伪装成现有字段。

- 插件保持原节点类型与字段；平台只决定渲染/交互适配，不复制 abc-mobile 之类类型。
- 只显示的节点不开放内部编辑与插入；可编辑正文里的移动/删除等宿主操作仍按文档权限与未知节点保护处理。
- 支持等级不能只控制按钮。节点修改 API 必须同时检查当前文档只读、节点身份、所属插件有效性、编辑等级和提交作用域，避免陈旧回调写入。
- 未安装、不支持或加载失败时保留所有原始数据，不用段落或静态图片覆盖源节点。

落点：`editor.ts`、`editor-fields.ts`、`element.ts`、源码组件宿主桥和内容注册表；保持不开放原始 Slate 包装器的边界。

具体落点：`scripts/plugins/template/src/index.tsx`、`manifest.json`、`build.mjs`、`package.json`、模板 docs、`scripts/plugins/package-sdk.mjs`。不要只更新 workspace exports 而遗漏实际发布器的类型闭包、exports 和文档复制清单。

计数器正式样例要恢复真实模板的设置表单与 `@tau/ui` Dialog，用它验证移动返回与 portal；spike 手写说明层通过，不代表标准 Dialog 已经适配。

## 6. 桌面端需要改什么

| 工作项       | 具体落点与改动                                                                                        | 完成判据                                                                  |
| ------------ | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 宿主环境     | `app/plugins/PluginProvider.tsx`、`runtime.ts` 向 PluginHost 注入真实环境源；页面/内容根注入 Provider | 正式桌面页面和正文不再读到 unknown，切库/关窗正确清理                     |
| 语义入口     | runtime 实现 navigation 适配器，接入已有插件侧栏模型；保留旧 sidebar 专属能力                         | 计数器通过同一个声明出现在正式侧栏，详情页不自动多一个入口                |
| 页面承载     | 复用现有 `plugin-page` definePage 与 PluginPageView；补守卫、失效页面、浮层和状态读取                 | 用真正桌面 Page 验证，而不是继续拿移动 router 的 Electron 壳代替          |
| 贡献统计     | 更新运行时贡献记录与 `features/plugins/model.ts` 的标签等消费方                                       | 功能入口可诊断，与旧 sidebar 不双重计数；这仅属于客户端集成，不改中心后端 |
| 静态内容环境 | 正文、独立内容渲染进程、预览与博客输出消费者逐一接环境/组件 scope                                     | 所有节点渲染调用点可用；纯 codec 不依赖 React hook 或 activate            |
| 包兼容       | 复用现有包读取、加载、安装/升级事务；新包策略由公共校验器提供                                         | 老包继续运行，新 API 插件有正确 minAppVersion，不破坏旧版本安装           |

同步与发布等既有领域能力不作为此轮移动接入一起重写。博客需补足共享内容组件的环境消费与包验证，不能因为只讨论手机而引入桌面发布回归。

旧 sidebar 是不同的桌面专属 API，不是新 navigation 的永久兼容层；按实际作者消费者逐步迁移通用入口，消费者清零后再评估删除，不能把已发布桌面高级侧栏功能直接砍掉。

## 7. 移动端需要改什么

### M1 真实应用启动与插件域

在正常 `AppShell` 的工作区生命周期内建立插件宿主，绑定当前数据库身份；只抽取公共纯逻辑，不引用桌面 runtime/store。新页面在移动 features 的插件域通过 definePage 注册，router 仍零业务依赖。

启动顺序：恢复包事务 → 校验并求值已启用兼容包 → 冻结内容贡献快照 → 创建 EditorKit/codec → 激活页面与命令。单个插件失败必须允许用户进入管理与停用入口；同步死循环无法同线程抢占，需要下次启动跳过插件的恢复路径。

spike 的固定双包、自动下载、自动测试、history 重置与样本 localStorage 不进入正常运行路径。

### M2 “我的”、自定义页面与设置

“我的”实际对应 `features/settings/SettingsPage.tsx` 与 settings Tab，不另外发明一个平行个人中心。通过声明/props/查询适配将已启用插件的语义入口展示在独立插件功能区域；空列表时不造演示入口。

通用插件页复用移动 router 的 single/params 身份、转场、保活、LRU、系统返回与守卫；页面参数只保存允许的 JSON 标量，不放闭包或凭据。页内浮层通过返回仲裁退出，portal 留在当前页或受控浮层作用域，不能挂到 body 后遗留在其他页面。

设置复用 PluginSettings 契约，以移动页面承载；停用后可查看管理资料，但不运行失效的设置组件。网络读取/管理列表沿用 react-query，禁止新增独立 useEffect 拉取体系。

### M3 包文件与私有存储

- Rust 实现应用私有目录的包读取、受控来源下载、ZIP 校验、暂存、提交、取消、备份与恢复；复用桌面事务语义和用例，不能调用 Electron 安装器。
- 档案和启用意图按设备保存；启用、数据授权不因另一台设备同步而自动授予。
- 私有 KV 接既有主库 `plugin_kv`，按实际工作区数据库定位，新增 Rust 命令与 TS 适配器；不要继续把正式数据放 spike localStorage，也不重复建一张带 workspace_id 的 KV 表。
- 插件数据可沿用现有主库同步，但必须验证工作区身份、冲突与安装状态独立性；测试样本没有真实用户迁移需求，不编写从 spike 目录迁移到正式库的路径。
- 切库先失活旧 context；进入提交前复核 signal/工作区，迟到异步不得写入新库。停用保留数据，卸载与清数据沿用明确的宿主语义。
- 如果后续确需更改 schema，必须同步校验脚本、内部 schema 文档，执行 db:schema:build/check；本方案优先复用现有表。

### M4 正文编辑器、预览与派生转换

修改 `services/editorKit.ts`、`editorMarkdown.ts` 与移动工具栏：

- 正常正文与其预览装配同一插件快照；插入面板从 blockPanel/命令贡献生成触摸动作，并在执行前恢复选区。
- Kit 缓存纳入插件会话/快照身份，不能只按相同扩展 ID 命中旧版本；内容插件启停和更新不在已编辑会话中热替换。
- 标准源码容器通过平台适配支持移动编辑，处理软键盘、安全区、只读、取消/提交、返回与撤销；不是把验证 textarea 原封不动移入产品。
- 节点标准菜单先提供触摸动作、移动/删除等有完整数据语义的操作；长按拖拽单独验收，不以“能显示拖拽把手”承诺完成。
- 默认只覆盖普通正文；闪卡、白板、短文本等场景分别声明能力，不自动混入全部扩展。
- 逐一审计 Rust 搜索摘要、索引、导出、协作投影等消费者。显示成功不代表这些路径认识插件节点；需要转换时由受控前端转换服务或现有异步协议提供结果，Rust 不执行插件 JS。不支持的派生结果明确降级，原始正文不能损坏。

### M5 应用生命周期与更新恢复

页面暂停与系统后台是两种状态：系统可挂起/杀进程，不能依赖 deactivate 一定执行，也不能承诺计时器准点或后台 JS 常驻。页面草稿、重要操作与安装事务及时持久化，恢复后重建上下文并刷新数据。

更新先等待正文和页面保存、结束受管调用，再在新的完整插件会话提交快照；不要求 iOS 调用 exit。代码回滚不自动回滚私有数据，作者升级必须给出数据兼容边界；不兼容时拒绝“回退一定成功”的承诺。

## 8. 编辑器/UI 公共包的协同改动

这是四个责任区共同依赖的工作，不能全部算进“移动宿主接几行代码”：

- 在标准源码容器、BlockToolbar、块菜单等位置提供宿主适配点，作者组件名和数据契约保持稳定；具体的页面返回与系统能力留在 app。
- 补 UI 浮层的 platform-neutral dismiss/portal 注入，使真正的 `@tau/ui` Dialog/Drawer 可在移动仲裁链中工作；packages/ui 不 import router/page/features。
- 避免在同一 JavaScript 环境临时替换全局 setter 导致两个编辑器互相影响；固定桥接由当前 Provider/渲染作用域选适配器。
- 保护节点资源声明、提交作用域和只读等级；菜单“隐藏”不能替代写入校验。

## 9. 暂不改生产插件中心时如何推进

### 当前允许做

1. SDK、正式桌面/移动宿主、模板的本地修改与测试。
2. 仓库外生成 SDK/UI tarball、构建真实 ZIP，使用显式开发入口和测试来源注入，验证真实安装事务。
3. 固定测试来源返回与未来中心相同的安装描述结构：插件 ID、版本、目标兼容信息、来源、文件大小、摘要；进入同一安装服务，不另造一套测试安装器。
4. 桌面保持现有中心协议和旧包路径；采用新 API 的桌面包可以在将来正常发布时利用现有 minAppVersion 约束，但本轮不上传、不发布。

### 当前禁止混入

- 不让移动客户端默认接受所有旧 desktop 包，不延用 spike 的双包许可到生产。
- 不把平台声明塞进被旧中心校验器丢弃的未知字段，随后假装中心已经感知兼容性。
- 不新增生产预装、正式 ZIP 侧载、隐藏的远程执行来源或“失败自动换另一个来源”。
- 不修改线上目录、审核、D1、下载协议，不用中心数据“试发一个版本”。

### 后续生产分发必须补齐的协议（本阶段只写规格）

推荐以新包格式表达目标平台、各端最低版本、运行 profile、必需/可选能力与节点支持等级；旧格式 1/2 保持 desktop 含义。先支持同一版本同一 Web ZIP 的三端共同能力，Node 混合多入口留到真实消费者出现后设计。一个插件 ID 的社区/作者身份不拆分。

中心最终需要按平台与能力选择兼容版本，过滤应参与候选集、分页、分类计数与游标。旧客户端视图不被新移动格式污染；直接 releaseId 下载也由客户端重复校验。新协议可采用版本化读接口，具体端点在该独立工作启动时定稿。

**上线闸门：中心兼容分发、平台审核与客户端版本检查没有就绪前，移动生产构建不开放普通用户安装入口。** “客户端已接线”与“移动插件正式可分发”必须作为两个验收结论。

## 10. 实施顺序与交付判据

| 阶段                   | 主要责任                 | 交付与验收                                                                                            |
| ---------------------- | ------------------------ | ----------------------------------------------------------------------------------------------------- |
| A 公共契约与作者闭环   | SDK + 模板               | 环境源、语义入口、能力词表、分级语义和发行闭包；仓库外模板构建能通过，不发布 npm                      |
| B 真实桌面与公共交互   | 桌面 + editor/UI         | 真正 DesktopPluginRuntime/Page/Sidebar 接计数器；标准 Dialog 与内容环境接线，现有桌面插件和博客不回归 |
| C 移动页面与持久化     | 移动 TS/Rust             | 正常 AppShell、“我的”、通用插件页、设置、正式 KV/私有目录与安装事务；切库、退出、重启通过             |
| D 移动编辑器与三端回归 | 移动 + editor + 作者样本 | ABC 进入正常正文/预览、真实标准源码组件与只读保护；同包摘要、数据往返、最低系统版本和真机行为通过     |
| E 独立分发工程         | 后续中心/发布工作        | 另行实施平台感知分发、审核、版本协商与移动上架；未启动，不作为 A–D 的隐藏改动                         |

A–D 的完成定义是“真实客户端接线并通过受控包验收”，不能描述为普通用户已能从生产中心安装。下一步实施从 A 开始，再用 B/C 两个真实宿主验证契约，不继续堆叠验证壳特例。

每阶段结束同步对应当前架构/包文档；只有已落地事实进入 architecture。正式任务按最小闭环逐段推进，保持同一时刻一个进行中单元；需要更新本提案时重新形成明确版本，不把一次性快照变成活文档。

## 11. 必须补的验收矩阵

| 维度       | 关键用例                                                                                                    |
