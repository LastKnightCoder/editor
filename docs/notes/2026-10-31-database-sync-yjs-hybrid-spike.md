# 正文 Yjs 与线性事务混合同步验证

2026 年 10 月 31 日，分支 `codex/database-sync-spike`。目标是在不逐表编写合并器的前提下，让同一篇正文在两端离线修改后，经重启、日志回收和快照补齐仍正确合并，避免旧 JSON 覆盖，并减少用户选择资料库的操作。

新增 21 项专项通过，全套 88 项通过、0 项跳过。常规同篇离线编辑没有产生整库副本，也没有要求选择库。基线不兼容改为保存单篇文档副本；真正无法自动处理的元数据冲突仍保全完整库，但正文先独立确认，主流程继续使用已确认主线，库副本留作主动查看与恢复。

## 分层方案

正文复用当前工作区 `@tau/collaboration` 的协议 2、NodeTree 稳定节点与已有准入校验，不是另造简化的 `Y.Text` 文档。其他业务继续通过原线性事务入口；旧方案的逐表领域门禁不是这条路径的前提。

| 数据                                | 处理                                             |
| ----------------------------------- | ------------------------------------------------ |
| 正文、格式、段落结构及文档标题      | Yjs 增量，按原正文协议校验并合并                 |
| 标签、置顶等独立元数据              | 通用线性事务及读写依赖检查                       |
| 正文 JSON、字数、正文修订与契约投影 | 从经过验证的二进制正文生成，禁止普通 JSON 回写   |
| 不兼容基线或旧库代次的正文          | 保全单篇文档，不覆盖当前正文                     |
| 无法安全接续的真实元数据分支        | 后台保全完整库，继续已确认主线，不强制立即选择库 |

正文编辑提交只包含正文增量和固定文档身份，不夹带任意跨领域写入，因此可以先确认正文，再处理后续元数据事务。真正需要跨域原子性的业务命令仍须通过原宿主的聚合入口，不能任意拆开。

## 真实状态进入主库

实验数据库新增 `_linear_documents`，保存正文 ID、业务 content_id、基线 ID、文档代次、Yjs 完整二进制、摘要与更新时间。它属于同步事实源，不是可随意删除的渲染缓存。

首次初始化只在发布者创建一次真实 CRDT 基线，其他设备复制相同二进制。两份相同 JSON 不能各自建立新 Y.Doc 后冒充共同历史。本轮专门验证了这种伪基线：它没有被强行合并，而是保存为单篇副本。

每次正文编辑先产生不可变增量，通过现有正文模型检查，再在 SQLite 事务内保存二进制、投影、主线提交与未确认 outbox。只有全部提交后才返回成功。源设备准备编辑期间如果库代次改变，不把旧上下文写入新代次。

接收端在隔离候选中合并并校验文档，持久化前重查主线与正文修订。异步准入和快照安装使用串行协调；原文档状态在 SQLite 提交前不被候选替换。

Yjs 状态使用真实二进制保存和恢复，保留原结构身份；日志回收不以 JSON 重建 Y.Doc。实验保留 `gc: false` 的完整状态，没有验证任意长期增长的容量回收方案。

## JSON 只能作为投影

托管正文的 `contents.content`、字数、更新时间，以及 `content_documents` 中的正文契约与修订由正文适配器维护。字数使用现有 `createContentMetrics`，没有另写一套文本统计。

本地普通事务试图改写这些正文事实时回滚并返回 `BODY_WRITE_REQUIRES_YJS`。远端旧 JSON 写包在进入分支处理前被拒绝，不把协议违约当作需要用户选择库的数据冲突。

完整快照携带二进制正文及单篇保全材料。加载时先验证包与真实文档状态，再重新生成 JSON 投影。二进制是新的、JSON 是旧的合法快照会修复投影；包完整性校验失败则拒绝覆盖本机。

重启会验证持久二进制并修复投影缓存。最后确认快照缺失或投影不一致时，改用快照补齐，不用旧 JSON 假造 CRDT 基线。投影的键顺序使用稳定编码，避免两端同义 JSON 的属性顺序不同造成假修订。

## 离线与历史回收

正文提交不传整篇 JSON 前后值，未确认 outbox 保留真实增量及原操作身份。线性日志可以回收，正文当前二进制和未确认更新不能当作缓存清掉。

正文-only 的离线分支即使丢弃了普通主线日志，也能从专用 outbox 重新提交增量。发布者将它合入当前真实状态；若下载端已缺旧主线，则用带真实正文状态的快照对齐。

回执必须在二进制、投影和主线都持久化后发出，不以“连接成功”或“状态向量一样”作为确认。Yjs 删除可能只改变 DeleteSet 而不推进状态向量，本轮验证了这类删除跨离线及快照后仍有效。

正文提交成功但响应丢失时，源端保留 outbox。重发通过原提交身份去重，文字不会重复。快照安装失败或进程在状态写入后退出时，二进制、投影、确认状态与 outbox 一起回滚；重开后继续提交。

## 尽量不让用户选择库

混合同步入口先提交正文，再提交其他事务。即使后面的标签冲突无法自动接续，已确认的正文仍包含两端输入。库副本不会连带替代或撤销已合并正文。

同一真实基线下的普通正文冲突直接合并。文档基线不兼容、旧代输入或重新从 JSON 建立的伪基线，保存为可查看的单篇文档副本，当前正文保持不变。它不触发整库分支选择。

若另一端已删除笔记，新增正文仍保存到该文档的耐久二进制，但不重新创建活动记录。原型可以读取删除状态下保全的正文，尚未接入真实回收站界面与恢复命令。

确实无法处理的其他业务冲突仍保存完整库，返回 `libraryChoiceRequired: false`，意思是继续已确认主线、提供后台副本，不强制用户立即切换整个库。它不表示元数据已经语义合并；用户之后仍可查看副本或主动恢复。实际提示和对比界面尚未制作。

整库副本也包含正文二进制和文档身份，不能只保留 JSON。用户明确选择旧库后会产生新库代次；随后到达的旧代正文只保全为单篇副本，不悄悄覆盖这次选择。

## 验证场景

| 场景                                 | 结果                                         |
| ------------------------------------ | -------------------------------------------- |
| 两端离线在同篇不同位置插字           | 两边输入都保留，状态一致，无库副本           |
| 两端修改后全部重启                   | 基线、二进制及未确认更新保留，继续合并       |
| 两端主线日志回收，确认缓存丢弃       | 快照补齐后继续合并，未从 JSON 初始化         |
| 删除没有推进状态向量                 | DeleteSet 正确传播，不漏删                   |
| 普通旧 JSON 或假修订回写             | 回滚拒绝，不覆盖正文、不生成库冲突           |
| 快照或确认缓存含陈旧 JSON            | 按真实状态重建投影或触发快照补齐             |
| 标题、格式、段落拆分与离线插字       | 使用真实稳定节点模型合并，身份保持           |
| 正文与独立置顶元数据                 | 两者自动处理，不要求选择库                   |
| 正文与真实标签冲突                   | 正文先合并，标签保留确认主线，另一份后台保全 |
| 相同 JSON 重新建立 Y.Doc             | 不冒充旧基线，保全单篇文档                   |
| 远端删除笔记、另端离线继续编辑       | 保存正文，不复活活动记录                     |
| 响应等待期间继续输入                 | 不覆盖新输入，重试保留所有意图               |
| 回执丢失、快照安装中断、进程直接退出 | 未确认材料保留，重启重试不重复应用           |
| 明确选择整库后旧代正文到达           | 只保存单篇副本，不改变新主线                 |
| 非法身份写入或损坏增量               | 不确认、不改当前正文、不要求选择库           |

演示命令输出的正文为 `电脑甲乙手机`。两端重启后清理主线日志到 0、删除确认缓存，再经 HTTP 快照补齐，文档身份保持、二进制摘要相同、outbox 清零；整库副本和单篇副本均为 0。随后手工破坏 JSON 投影，再次重启可从同一二进制恢复正文。

同一位置并发插入的顺序由 CRDT 身份决定，验证要求两端一致且输入都在，不强行指定人为顺序。技术合并不保证句义自然，用户仍可能在笔记内整理文字，这不需要选择整个库。

## 生产接入边界

本轮只改独立实验，没有修改正式 Schema、应用启动或编辑器。首次共同基线建立前已存在的两份 JSON，不会自动还原成共享历史；正式首次接入需要先确定基线并复制真实状态。

还需将真实正文入口、缓存租约、所有数据库替换入口及原生 IPC 接入统一保存协议。资源上传、外部实体关系账与授权仍要调用既有正文流程，本轮只验证正文内容、标题、格式与拆分，没有验收所有插件、附件或跨库引用。

移动端可以沿用已有 TS Yjs 模型，由原生原子保存二进制与投影，不必在 Rust 重写所有业务合并器。但本轮没有实现混合模式的 Rust 适配，也没有进行真机、视觉或后台验收。

普通库事务仍有全库摘要、本地确认快照和候选文档校验开销，没有给出性能或内存承诺。单篇受既有 8 MiB 正文预算约束，完整快照上限 64 MiB、请求上限 16 MiB；大量待发送更新的分批合并与安全回收尚未实现，超预算保留 outbox 并拒绝继续，不宣称任意体量长期离线都已验证。
