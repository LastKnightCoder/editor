# 应用插件系统总入口

本专题的最终目标是建立架构合理、可扩展、安全的应用插件体系。微信读书是验证真实业务能力的一个样本；编辑器、数据库、白板、自定义页面与后台任务共同验证体系的适用范围，任何单一样本都不能决定整个架构。

每个实现提交都必须保留完整可用的应用和受影响功能，不以未接线接口或等待后续修复的状态作为交付。安全模型从架构阶段开始，隔离能力逐步实现；未完成隔离的路径不得开放给不受信任插件。

## 能力阶段总览

1. P0：文档和证据基线。
2. P1：多场景需求、威胁模型、运行边界和契约裁决。
3. P2：最小插件 API、命令、存储与生命周期闭环，先使用可信开发样本。
4. P3：数据、任务、网络和凭证服务，使用真实业务验证。
5. P4：页面、设置、导航与来源贡献，完成跨服务业务样本。
6. P5：编辑器、数据库、白板逐一验证领域扩展和数据保真。
7. P6：开发 SDK、构建、重载，以及第三方安装前所需的隔离和显式授权。
8. P7：升级恢复、分发与第三方开放。

微信读书可在 P3 至 P4 验证组合能力，但完成其迁移不代表插件体系完成。各阶段均有独立的安全验收；第三方发布是最终开放门槛，不是首次考虑安全的时点。接口稳定之前不需要发布公共 npm 包。

实际推荐顺序是：C03 页面与 UI → C04 编辑器样本 → 设置与真实业务服务 → 数据库/白板 → 外部开发工具与第三方开放。页面、UI 属于 P4，编辑器属于 P5；所需最小 P3 服务随页面样本一起实现，不先铺满后台能力。

## 新会话接手

1. 读本入口、阶段计划和执行日志最新条目，确认代码与记录对应的提交。
2. 执行 `git status --short`，保留已有工作；核实相关源码，没有证据不沿用过时结论。
3. 写桌面端代码前全文阅读桌面 03 指南，按该域规范调查直接消费者。
4. 只推进一个有实际消费者的工作单元；遇到结构性取舍先更新决策记录。
5. 按验收规范验证，在同一提交更新现状、进度、日志和必要的桌面指南。
6. 报告提交、完成的行为、验证限制和下一步；本地提交不代表发布或推送。

用户已要求逐步执行、依次提交。后续明确启动某个阶段后，完成该阶段内已授权的工作单元并验证提交，不需要为普通本地提交重复询问；不得将长期路线解释为自动发布、自动调度或立即实施全部阶段。
