## 结论

可行，建议沿用 TTS 的领域提供方模式：宿主规定图片生成与编辑接口，插件负责服务商协议、鉴权、参数转换、轮询和图片下载，宿主继续负责交互、文件解析、资源上传和结果保存。

拆分前已经有 `IImageGenerationProvider.generate/edit` 抽象，但配置、参数、响应以及设置页仍绑定 OpenAI Images，只开放工厂注册不足以完成插件化。本轮已参考 TTS 的实例配置、渲染进程执行、跨窗口转发与取消机制完成图片领域接线，没有直接调用语音专用通道。

建议先将现有 OpenAI 兼容实现完整迁入一个独立插件，再用一个原生非 OpenAI 协议插件验证抽象。改造规模为中等，主要工作在宿主接线与生命周期，第一期不需要数据库 schema 变更或新的插件执行环境。

### 生产消费者

1. 聊天及代理：`openaiImageTools.ts`，提供生成、编辑、多结果上传和专用渲染。`generation-orchestrator.ts` 的 Notebook PPT 提示词通过 `generate_image` 是否启用决定是否提供配图能力，也要回归。
2. 编辑器：`editor-providers/AIImagePanel.tsx`，同时承载 AI 插图与编辑。界面上的“生成”在选择参考图后实际调用 `edit`，两种能力不能只按弹窗标题区分。
3. 白板：`features/shared/whiteboard/components/ImageSelectorModal/imageActions.ts`，只消费文生图，并插入第一张结果。

三个入口都各自处理了服务结果到文件、再上传资源的过程。编辑器和白板目前没有把单次取消信号传入图片请求；聊天工具传给了提供方，但后续输入读取、结果下载和上传尚未贯穿同一信号。

已生成图片保存的是资源地址。展示、复制和播放历史工具结果不需要调用生成服务，插件缺失不应影响这些行为。历史结果上的“编辑”需要当前用户选定的编辑能力。

| 方案                                         | 成本与收益                                                             | 适用判断                                           |

## 最小接口草案

建议使用 `context.images.register`。每个插件注册一个图片提供方，`definition.id` 等于当前插件 ID；同一插件可创建多个账号实例。

```ts
import type { Disposable, JsonValue } from "./contract";

export interface ImageFile {
  name: string;
  mimeType: string;
  content: Uint8Array;
}

export interface ImageOptions {
  size?: string;
  quality?: string;
  outputFormat?: "png" | "jpeg" | "webp";
  background?: string;
  count?: number;
}

export interface ImageGenerateRequest {
  prompt: string;
  options?: ImageOptions;
}

export interface ImageEditRequest extends ImageGenerateRequest {
  images: readonly ImageFile[];
}

export interface GeneratedImage extends ImageFile {
  revisedPrompt?: string;
}

export interface ImageInstance {
  generate?(request: ImageGenerateRequest, signal: AbortSignal): Promise<GeneratedImage[]>;
  edit?(request: ImageEditRequest, signal: AbortSignal): Promise<GeneratedImage[]>;
}

export interface ImageProviderDefinition {
  id: string;
  name: string;
  create(config: JsonValue, modelId: string): ImageInstance;
}

export interface PluginImages {
  register(definition: ImageProviderDefinition): Disposable;
}
```

`generate/edit` 至少实现一个，由宿主在创建实例时校验。这允许只有文生图或只有编辑的模型接入；不要求提供方伪造不支持的方法。宿主内部根据方法是否存在得到 `canGenerate/canEdit`，无需再维护重复的公开能力声明。

`create` 同步创建配置、模型快照，不发网络请求、不读客户端 store。配置的结构及必填校验归插件，宿主只检查 JSON、身份、模型选择及接口完整性，不再要求所有服务都有 API Key 或 baseUrl。涉及网络的鉴权错误在实际调用时返回。

### 参数语义

第一期保留现有五项单次选项，SDK 采用 `outputFormat/count`，避免把 `output_format/n` 固化为图片领域命名。通用聊天工具可以保留现有参数名，在调用宿主服务时完成映射，提供方只处理领域请求。

这些字段统一的是意图，不保证各模型拥有相同取值。`size` 表达明确输出尺寸，`quality` 与 `background` 的支持值由插件验证；不支持且无法等价映射的显式参数应报清楚的错误，不能悄悄丢弃。宿主不补默认值、不做隐式多次调用凑 `count`，也不自动改用别家模型。服务商的特有默认参数可放在插件实例配置中。

第一期不增加任意请求体透传、动态参数表单、模型发现、遮罩编辑、多轮会话、流式预览、统一计费或可恢复任务队列。后续有具体消费者时再扩展；尤其不能把普通参考图编辑声称为已经支持精确局部重绘。

### 输入与输出

宿主将本地路径、file URL、相对路径、远程 URL 和 data URL 解析为图片字节，插件不接收任意本地文件路径，也不负责正文插入。

插件统一返回图片字节和实际 MIME。服务商返回 base64、二进制或临时 URL 时，插件完成解码或下载；下载鉴权由该插件控制，不把生成 API 的 Authorization 头自动带给其他域名。服务商轮询 ID、签名地址与响应体不进入通用结果。

宿主集中实现结果校验、`File` 构造与 `uploadResource(file, signal)`，三个入口共用。第一期沿用当前 PNG/JPEG/WebP 支持范围，保留真实 MIME 和可选修订提示词，不默认所有结果都是 PNG。注册表和桥接增加图片数量、输入及输出总字节上限，并用多图样本验证 IPC 内存开销；字节返回会增加跨进程复制，不能宣称零成本。

图片生成插件不自动承担图床职责。最终图片仍按用户当前资源设置保存到本地或上传提供方；仅在某服务商必须使用公网参考图时，插件可显式调用已有 `context.upload.uploadRemote`，本地模式报错，不自动选远端存储。

## 配置与设置建议

先保留现有“一项配置对应一个模型”和 `imageGeneration.currentProviderId/providers` 容器，避免同时升级为模型目录管理：

```ts
interface ImageProviderSetting {
  id: string;
  name: string;
  pluginId: string;
  modelId: string;
  config: JsonValue;
}
```

宿主管理实例列表、名称与当前选择；插件通过 `settings.register({ target: "images", ... })` 提供自己的凭据表单。增加 `imageConfig: { instanceId, value, modelId, save }`，保存只更新匹配实例 ID 和插件 ID 的配置。可参考 TTS 的保存完成后提交本地值流程，不使用插件级共享 storage 保存所有账号的同一份 Key。

第一期生成、编辑仍使用同一个当前实例。不支持的能力显示不可用；不自动从列表寻找另一个收费账号。若以后需要分别指定生图、修图模型，再增加用途选择，不在这次接口拆分中默认扩张。

插件缺失、停用或配置无效时保留账号与选择，显示对应原因。新增账号先选择已启用并注册图片能力的插件；删除当前账号清空当前选择。新安装不再凭空创建 OpenAI 账号。

## 生命周期与跨窗口

推荐链路为：调用窗口 → 图片宿主服务 → 主进程转发 → 主窗口图片插件实例 → `context.fetch`。主窗口也走统一服务边界，辅助编辑窗口复用同一提供方；插件代码只在主窗口渲染进程执行。

一次任务固定账号 ID、配置、模型、插件激活代次与所属数据库。切换当前账号不影响已经发出的任务；停用、卸载、重载、切库、调用窗口关闭或主动取消会使任务失效。会话关闭通知必须传回调用窗口，避免提供方已返回字节后，旧任务继续上传或写回。

宿主统一传递组合后的信号，覆盖输入解析、生成或编辑、临时结果下载、资源上传以及 UI 或正文写回前的检查。已有 `uploadResource` 支持 signal，可直接接线；本地读取等不可中断步骤在前后检查信号并丢弃迟到结果。取消不承诺撤销远端已经创建的任务、文件或费用。

工具和 UI 的可用性还需独立接线：宿主在当前配置及插件状态变化后，异步取得实例方法信息，再发布不含凭据的能力状态；注册表读取该状态，不能在同步 `isAvailable` 中发网络请求。启动或刷新期间暂按不可用处理，能力状态绑定配置与激活代次，过期回复丢弃。工具执行时仍须重新校验，防止列表已展示但插件刚被停用。

编辑器“生成”选中参考图时必须检查 `canEdit`，只支持文生图时禁用参考图操作；独立编辑操作检查 `canEdit`，白板检查 `canGenerate`。聊天只暴露当前可用的方法，并随能力状态更新工具注册。辅助窗口也必须收到能力变化，不能只订阅本地设置 store。

插件内部可把“提交任务 → 轮询 → 下载结果”封装在同一个 Promise 中。重试分类、轮询间隔与具体超时由插件负责，宿主不叠加自动重试；OpenAI 插件迁移时先保留当前 300 秒请求上限。第一期不承诺应用退出后继续运行或重启恢复任务。

## 不同协议的适配验证

| 协议样本            | 官方文档确认的差异                                                       | 对接口的检验                                                                 |
| ------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| OpenAI Images       | 有生成与编辑接口，编辑支持上传图片和 mask                                | 可保留当前生成与参考图编辑；mask 留待专门交互和契约扩展                      |
| Gemini 原生图片能力 | 文本与图片可组合为输入，输出包含图片数据，尺寸使用自己的比例和分辨率字段 | 原生插件内部转换请求与结果，无需经 OpenAI 兼容网关；特有尺寸默认值归插件配置 |
| Black Forest Labs   | 提交后返回 `polling_url`，轮询到 Ready 后取得结果地址                    | 提交、轮询与结果下载可封装为一次异步调用，不必先增加宿主任务队列             |

来源：[OpenAI 图片指南](https://developers.openai.com/api/docs/guides/image-generation)、[Gemini 图片指南](https://ai.google.dev/gemini-api/docs/image-generation)、[Black Forest Labs 快速开始](https://help.bfl.ai/articles/8446125349-quickstart-guide)。以上适配方式是基于接口差异的设计推论，尚未通过图片插件实测。

第二个验证插件建议选原生 Gemini：它同时覆盖生成和参考图编辑，能检验接口是否真正脱离 OpenAI 请求与响应格式。异步提供方可先以模拟提交、轮询、取消和下载测试检验契约，不要求第一期同时交付所有厂商。

## 升级与退役边界

1. 发布可安装的 OpenAI 兼容图片插件；迁移中可采用 `tau.images-openai` 作为候选 ID，正式名称与插件发布包保持一致。
2. 主进程设置首次加载时先备份，再逐项转换旧配置：保留实例 ID、名称及当前选择，`modelName → modelId`，`baseUrl/apiKey → config`，`providerType: "openai" → pluginId`。不合并同插件的多个账号。
3. 新结构优先；空列表保持为空；未知提供方先保留备份并报错，不猜测映射。转换失败不发布新快照，成功后清除旧字段。
4. 不自动安装、启用插件或调用收费服务。旧配置可转换为“等待安装插件”的账号，并保留选择与凭据。
5. 删除宿主 OpenAI 实现、请求构造、响应解析、默认凭据及服务商校验分支，清零消费者后删除旧工厂；通用图片文件解析保留。
6. 历史工具来源 ID `openai-image-tools` 与结果键 `openai-image-result` 可作为稳定标识继续使用，内部命名和用户文案改为通用图片能力。不为改名重写历史消息或丢失工具开关偏好，也不保留旧服务执行回退。

仅升级设置 JSON，不改图片正文、资源地址、聊天数据库或同步 schema。一次性配置升级入口在用户完成升级后再按项目规范退役。

## 实施阶段与验收

| 阶段 | 最小交付                                                                      | 验收重点                                                                               |
| ---- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| M1   | SDK 图片接口、主窗口注册及跨窗口服务、配置表单、OpenAI 独立插件、三个入口接线 | 生成、参考图编辑、原参数映射、真实 MIME、多账号隔离与辅助窗口调用                      |
| M2   | 原生非 OpenAI 插件，补充能力刷新与异步协议验证                                | 不修改宿主即可新增协议；只生图或只编辑的实例；轮询及下载取消；插件停用后的迟到结果丢弃 |
| M3   | 旧配置一次性升级、宿主旧实现退役、SDK 与作者模板更新                          | 重启恢复、缺包提示、无付费账号自动切换、历史结果保留、独立包构建和安装闭环             |

以上为调研阶段的建议切分；本轮按用户确认的 OpenAI 拆分范围交付，原生非 OpenAI 提供方与正式发布另行推进。

必要验证包括：

- SDK 和宿主：重复注册、归属限制、创建快照、至少一个方法、停用回收、异常与取消不被吞掉。
- 网络适配：JSON、multipart、多图输入、base64、二进制、URL 下载、轮询，以及不支持参数的明确失败。
- 消费者：编辑器参考图走编辑、白板只插入第一张、聊天多结果与历史渲染、Notebook PPT 工具可用性。
- 生命周期：配置中途变化、多窗口并发、切库、主窗口退出、输入读取及上传期间取消、过期能力回复及迟到保存。
- 迁移与保存：多账号不合并、新配置优先、空列表不复活、失效选择不回落、备份或落盘失败不发布。
- 工程检查：SDK 与桌面类型检查、相关行为测试、桌面生产构建、真实插件 ZIP 双窗口验证、作者仓库使用公共 SDK 的干净安装构建；同步桌面 03 指南的插件与设置小节。

首次调研阶段未修改运行代码；随后 OpenAI 拆分已实施，实际范围和验证见本文开头的实施记录。
