## 1. 产品范围与责任

普通用户无需注册即可浏览、下载和本地安装。发布者用 GitHub 登录，平台保存身份与所有权，不另建用户名密码体系；登录成功不等于获得上架资格。首期采用申请或邀请准入。

| 部分        | 用户得到什么                              | 责任边界                                  |
| ----------- | ----------------------------------------- | ----------------------------------------- |
| 插件中心    | 查找、下载已批准且兼容的版本              | 目录元数据决定可分发版本，R2 只保存文件   |
| 插件管理    | 查看来源、权限、启停、更新、移除和故障    | 宿主负责授权及执行，manifest 不能自行提权 |
| GitHub 模板 | 独立开发、文档/API、构建和 ZIP 打包       | 版本化 SDK 与示例真实匹配，不引用宿主源码 |
| 发布入口    | GitHub 登录、提交版本、查看检查和审核意见 | 首期可做独立网页；不要求普通用户登录      |
| 审核后台    | 准入、风险审查、批准、撤回和申诉          | 每版机器检查，人工集中于首发及高风险变化  |

官方目录与本地分发并存。本地包不需要平台审核，但必须通过相同的包校验、兼容检查与用户授权。官方审核不等于无漏洞保证。

## 2. 发布者与版本模型

| 对象             | 关键字段与约束                                                                                                                                      |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 发布者 Publisher | 不可变 publisherId、GitHub 数字用户 ID、准入状态 pending/active/suspended。首期一个所有者，暂不建团队权限系统                                       |
| 插件 Plugin      | 全局唯一且稳定的 pluginId、publisherId、GitHub 数字仓库 ID、所有权代次 ownershipEpoch。显示名称和仓库 URL 可变，不能用来证明所有权                  |
| 提交 Submission  | submissionId、源代码 commit、ZIP 摘要、构建证据、机器检查、人工意见与 policyVersion。重传产物生成新提交，旧检查不沿用                               |
| 版本 Release     | pluginId + SemVer 唯一；固定 manifest、完整文件摘要、ZIP 摘要、源码 commit、SDK/锁文件/构建来源、最低客户端版本、API 版本、平台、执行档位和权限集合 |
| 安装 Install     | 本机安装身份、来源、选定版本与摘要、更新来源、最后可用版本、事务状态；与作者声明分离                                                                |
| 授权 Grant       | 宿主记录安装身份、工作区、所有权代次、能力及范围、适用代码版本。插件不能自行写入或继承其他来源的授权                                                |

版本审核状态为 uploaded → scanning → manual（需要时）→ approved/rejected；分发状态另记 published/yanked/revoked。批准具体版本不等于批准这个插件今后的所有代码。已发布版本不可覆盖，同号修复必须升版本；新版本被拒通常不影响旧的已批准版本。

所有权转移需要双方身份验证和人工处理，递增所有权代次；客户端安装该代次版本前重新确认，不静默沿用旧发布者的授权。GitHub 改名不等于转移，仓库转移必须重新验证绑定。

**生产包建议采用新格式版本 2**，加入必需权限、minAppVersion、执行档位等字段；字段精确语法在 C12/C13 契约验证中确定。API 版本与包格式版本分别管理，不把二者混用。现有格式 1 留在可信开发链路，不自动转换成已授权生产包；旧客户端必须拒绝未知格式。

目录保存每个批准版本的兼容条件，不能只保存 latest。客户端选择满足客户端版本、API、平台和执行档位的最高批准稳定版；首期不做预发布频道。没有兼容版本就明确提示，不尝试加载。

## 3. R2 与发布链

发布元数据服务负责身份、所有权、版本、检查与目录；R2 分为私有待审对象和获准发布对象。服务签发短时、限定对象的上传授权，不向作者提供 R2 密钥；上传后仍由服务核对实际大小和摘要。未批准产物不可经公开下载入口获取。

建议首期官方目录要求公开 GitHub 源码。发布者上传 ZIP 并指定 commit；平台在无生产密钥、隔离网络和资源受限的构建环境中，按锁文件重建并比对规范化文件清单与内容摘要。ZIP 时间戳等容器差异不代替代码差异。无法验证产物来源的提交进入人工处理，不能因为源码看起来安全就批准另一份二进制。依赖安装和构建脚本同样是不可信代码。

批准绑定最终 ZIP 摘要及源 commit，冻结对象，生成平台签名的发布凭据，包含插件/发布者/版本/所有权代次/权限摘要/兼容条件/代码摘要和签名密钥 ID。客户端内置可信公钥并有密钥轮换策略，核对目录和实际产物；具体签名格式在 C15 定稿。R2 地址、manifest 中的作者字段都不是官方身份凭据。

撤回版本停止新安装；安全撤销还进入客户端拒启清单。已知撤销版本不得启用，离线客户端不能声称知道最新撤销结果；下载过的文件和第三方镜像无法远程抹除。目录刷新需防旧清单重放，保存最近可信序列；目录不可用时保留当前可用安装，不静默降级。

## 4. 权限必须如何执行

### 4.1 授权规则

发现、下载、校验和权限展示均不得执行插件顶层代码。首期 manifest 中声明的敏感权限全部是必需权限，拒绝任一项就不启用；暂不引入可选权限和运行中反复弹窗。

纯计算、自己的有界 KV、受控命令与基础界面可作为固有能力；读取用户内容、联网、写公共数据等必须声明并授权。能力名称与范围共同参与比较：网络域名扩大、从选区变成全库读取都算新增权限。权限界面说明“读取内容 + 联网”允许外传获准内容，不只展示技术名称。

### 4.2 受限档：先证明边界，再对外开放

建议验证的结构是：**可单独终止的执行进程 + 无默认文件/网络/Node 能力的 JS 执行器 + 宿主权限代理**。具体引擎尚未选定。独立 Node 进程、Node vm、有限 require、iframe 或 CSP 单独存在，都不足以证明这一边界。

代理在每次调用时根据宿主绑定的通信端点，核对安装身份、代码摘要、工作区、实例代次、授权范围和参数，再调用真实领域服务。不相信消息中自行填写的 pluginId 或 workspaceId。切库、停用、撤权先拒绝新调用，取消在途任务；写入提交点再次校验代次。已经完成的外部副作用不宣称能够回滚。

网络走代理，校验重定向后的目标及实际连接目标，默认拒绝本机、私网和元数据服务；执行器不得有可绕过代理的 fetch、WebSocket、IPC 等。作者网络 API 尽量保留标准 fetch 语义，支持范围经实验确认。C01 中未通过的网络封锁探针必须作为回归反例，不能当成已经完成的隔离。

**受限 UI 建议首期由宿主渲染声明式控件/结果面板**，插件提交经过校验的数据与动作标识，不提交任意 HTML、CSS、DOM 或 React 函数。图片等资源也用受控句柄，不能通过资源 URL 绕过网络权限。

| 能力                            | 受限档首期建议           | 高信任档                                     |
| ------------------------------- | ------------------------ | -------------------------------------------- |
| 命令、私有 KV、异步受控服务     | 支持，经过代理与预算约束 | 复用已有上下文，补生产生命周期               |
| 页面与设置                      | 宿主渲染的受控界面       | 可保留现有 React/@tau/ui 方式                |
| 任意 React 页面、同步编辑器扩展 | 不直接支持               | 已有开发能力可继续适配；生产领域仍需单独验收 |
| 原生系统能力                    | 首期不开放               | 也不因高信任自动开放原生扩展                 |

两个作者入口 `@tau/plugins`、`@tau/ui` 保留，但不能承诺两档具备完全相同的 API。受限 UI 的作者写法须和载体一起验证，未实现能力不提前导出。若产品要求任意 React 页面也有强隔离，需要另行验证隔离 UI 载体；不能暗中放松权限承诺来兼容 G1。

受限档退出门槛包含：同步死循环可终止、内存/消息预算、直接网络及资源旁路被拒、跨插件/工作区伪造被拒、撤权后迟到提交被拒。当前先用内部只读夹具证明执行边界，再接已有命令/私有存储验证真实生命周期；不为证明权限而先新增内容或网络 API。将来开放各类服务时逐项补其权限与提交验收。未通过相关边界就不开放对应能力。

### 4.3 高信任档

manifest 只能申请高信任，宿主必须另外取得用户明确同意。界面说明其可接触应用环境，不能宣称只拥有列出的细粒度权限。授权绑定确切代码摘要，每次版本更新重新确认；拒绝保留旧版本，不能因受限运行失败自动转为高信任。

撤销后阻止再次加载；已经执行的同环境代码可能需要重启才能清除。现有生命周期超时只能限制等待，不能抢占同步代码。高信任不作为解决受限载体失败的默认后门。

## 5. 安装、升级与恢复

### 5.1 两个入口，同一条校验链

当前目录裁决见 PS-033/034：本地主线固定使用 `PathUtil.getAppDir()/plugins/<pluginId>/`（默认 `~/.editor/plugins/<pluginId>/`），用户不选择安装路径。C13-A 已接通启动自动发现、打开目录和刷新列表，现行合同见 [29](29-C13固定目录自动发现.md)。下面“导入后复制到另一快照目录”的早期建议不用于当前阶段，保留为历史方案。

官方中心下载 ZIP；本地用户可自行下载并解压到应用展示的插件导入目录。建议该目录是**导入入口**：发现后静态校验、复制为宿主受管的不可变摘要快照，再授权执行，不直接运行持续可变的外部目录。生产不自动监听代码变化；开发监听继续独立保留。

顺序：发现候选 → 校验路径/文件/摘要/签名与兼容条件 → 建立来源记录 → 展示权限 → 用户同意 → 启用。手工放入默认停用。ZIP 提取拒绝绝对路径、目录穿越、符号链接、重复冲突路径和超限解压，不执行安装脚本；复制也检查链接和复制后的摘要，防止检查与加载读取不同代码。具体资源限额经实测设为宿主政策，不能由插件放宽。

无有效官方发布凭据的包标记为“本地、来源未验证”；即使 pluginId 和作者名与官方一致也不能共享官方授权。经核对与官方批准摘要完全一致的包可显示已验证来源，但切换到官方自动检查更新仍需用户选择。首期同一用户配置中一个 pluginId 只安装一个来源，换源需明确操作，不静默覆盖或移交私有数据。

代码包、安装指针/事务日志、私有数据和授权分开保存。建议包版本按应用用户配置统一管理，启用与授权按工作区管理；G1 按工作区登记开发目录的实现需要改造。删除导入目录不等于卸载已导入的快照；管理界面必须解释并提供打开受管位置与移除入口。

### 5.2 升级

首期提供“检查更新 / 更新”，不默认静默升级。只有批准且兼容的版本进入候选；下载、检查和权限确认失败都不改变旧安装。普通受限更新在发布者未变且权限不扩大的情况下可沿用范围授权，并记录对应新摘要；高信任每个新摘要都重新确认。

建议首期生产升级统一为**暂存完成后重启应用切换**，开发热重载不是生产升级事务。重启前遵守所有窗口的未保存守卫；用户取消则保留旧版，不能先停掉旧实例。启动时通过原子活动指针和事务日志切换，保留最后可用版本；启动未完成或崩溃进入恢复启动，跳过故障插件，再由用户选择恢复旧版或重试，避免无限崩溃循环。

由于代码版本全局统一，新版本所需授权必须覆盖所有已启用工作区；某个工作区未同意时暂不切换，用户可先停用该工作区中的插件。不能让一个工作区同意后，其他工作区自动执行新增权限的版本。首期不增加按工作区锁定不同版本的复杂度。

回滚代码不等于回滚数据。首期要求私有数据演进保持向后兼容；不支持借安装脚本做破坏性迁移。确需破坏性迁移须另行设计数据备份、版本化存储与恢复门槛，不能在本方案中笼统承诺升级失败无损。

| 故障                     | 用户可见行为                                      |
| ------------------------ | ------------------------------------------------- |
| 下载/校验/兼容失败       | 保留旧版，说明失败，不执行候选                    |
| 拒绝新增权限或高信任授权 | 保留旧版；首次安装保持停用                        |
| 重启前取消未保存提示     | 不切换版本，候选保留待处理                        |
| 切换过程中断             | 启动核对事务和摘要，恢复一致指针；不猜测最新目录  |
| 新版启动失败             | 隔离故障插件，提供恢复旧版/重试；不声称数据已回滚 |
| 已知安全撤销             | 拒启该版本，提示选择其他批准兼容版本或移除        |

停用先撤权和回收实例；移除由宿主完成，不执行不可信卸载脚本，默认保留私有数据与已写入的用户内容。删除私有数据是单独明确操作。DEV 安装身份与授权不能继承到生产。

## 6. 审核与单人运营

不要求你手工检查所有普通更新，也不开放匿名无限上传。采用发布者准入、每版机器检查、风险触发人工、目录质量门槛四层控制。

| 事件                                 | 处理建议                                                           |
| ------------------------------------ | ------------------------------------------------------------------ |
| 新发布者、新插件首发                 | 人工确认用途、演示、文档、维护渠道、源码/产物对应及权限合理性      |
| 受限插件普通更新                     | 每版自动检查；无风险变化且全部通过可自动发布                       |
| 新增敏感权限、扩大范围、改变执行档位 | 人工审查变更原因和实际代码，再发布；客户端仍重新授权               |
| 所有权/源码仓库变化、可疑依赖或举报  | 暂停自动发布，人工核实；必要时安全撤销                             |
| 高信任插件                           | 建议首期仅邀请准入，每版人工差异审查；做不到时不扩充官方高信任目录 |
| 新版本不合格                         | 拒绝该版本，给出原因；旧版是否撤回单独判断                         |

机器检查覆盖包格式、兼容声明、权限差异、构建来源、锁文件/依赖风险、静态规则、真实运行与生命周期测试、资源预算。版本号是 patch 不代表低风险，AI 差异摘要不能替代安全结论；通过扫描也不是无恶意证明。

质量规则要求明确用途、可复现演示、安装使用说明与维护联系方式；重复占位、无实际功能、名称冒用、未披露遥测可拒绝。按作者限制待审数量和提交频率，鼓励合并版本；队列超过维护能力可暂停新准入，不自动降低审核门槛。暂不建设评分社交、收费市场或任意外部 updateURL。

审核意见、规则版本、批准摘要与撤销原因可追溯，提供申诉入口；不承诺当前无法承担的审核时限。AI 开发本身不是拒绝理由，验收的是功能、行为和来源。

| 手动重载、完整构建监听                | 继续用于开发，复用失败测试       | 不作为生产更新；不沿用 20 次替换作为产品策略         |
| 页面/设置/命令、编辑器开发台          | 复用宿主适配                     | 受限贡献协议、生产领域接线；数据库/白板未完成        |
| G1 干净作者及 Electron 验收           | 保留回归，扩展 G2 场景           | 恶意包、权限拒绝、断电恢复、来源冲突和云端联调       |
| 发布者、审核服务、R2 分发、插件中心   | 新建                             | 当前没有生产实现，不能只解除 DEV 门禁                |

现有 `formatVersion:1/apiVersion:1`、有限 require 和 integrity 不构成权限系统或官方身份验证。G1 验收也不代表整个应用的生产安装、跨平台或视觉验收。

## 8. 阶段计划与评审重点

| 单元       | 目标与退出门槛                                                                                | 依赖                        |
| ---------- | --------------------------------------------------------------------------------------------- | --------------------------- |
| C11 已交付 | 形成本文及总计划，清楚区分事实/建议；文档交付供审阅                                           | G1                          |
| C12        | 最小权限边界实证 → Electron 运行监督 → 已有命令/私有存储适配；不新增领域 API                  | 当前执行主线，A 的范围见 24 |
| C13        | 生产包契约、本地导入、授权、管理、重启升级和恢复；拒绝/崩溃/来源冲突端到端通过                | C12 安全边界成立            |
| C14        | 本地模板、API/AI 文档和 ZIP 工作流，从干净作者目录完成生产本地完整验收；GitHub 仓库发布可后置 | C13 包契约                  |
| C15        | GitHub 身份、审核、R2 和签名目录                                                              | 暂停，不阻塞本地闭环        |
| C16        | 官方插件中心、发布入口和后台联调                                                              | 暂停，待发布平台恢复        |

这些是阶段目标，不是一次提交或日期承诺。进入每个单元后先调查，再拆成带实际消费者的最小工作片。G3 生产编辑器/数据库/白板及微信读书仍不自动启动。

本轮新增、最值得审阅的工程建议是：受限 UI 首期采用宿主控件；官方高信任插件限量且每版人工；本地目录作为快照导入入口；生产更新首期重启切换且跨工作区统一版本。这些限制换取可验证的权限和可维护的恢复路径，不标记为用户已经逐项确认。
