## 作者接口

所有 Tau 插件 API 从 `@tau/plugins` 导入。插件拿到的 `context.fetch` 类型直接是 `typeof globalThis.fetch`，使用原生 RequestInit、Headers、Request、Response、FormData 与 AbortSignal，不另外导出近似 fetch 的类型。

```ts
const response = await context.fetch(url, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(payload),
  signal,
});
if (!response.ok) {
  await response.body?.cancel();
  throw new Error(`请求失败：${response.status}`);
}
const data = await response.json();
```

非 2xx 正常返回 Response，调用方决定是否报错。取消使用 signal，超时使用 AbortSignal.timeout；请求体、响应读取、重定向等使用标准选项与方法。没有额外的方法枚举、json/query/responseType、连接 ID、固定大小上限或全局 30 秒超时，也没有自定义同源跳转限制。

SDK 只合并插件激活期的取消信号：停用后不能发新请求，在途请求及尚未读完的响应流随信号取消。调用方信号及 Request.signal 保留，init.signal 按标准覆盖输入信号。没有执行器的宿主明确报错。

## 执行环境与跨进程传输

桌面调用者使用 `commands/fetch.ts` 的 desktopFetch；插件宿主注入同一个执行器。Web 预览降级到环境原生 fetch，Electron 通过新的 BACKGROUND fetch 模块调用主进程原生 fetch。原 extra 模块的 node-fetch/abort handler、Axios 请求包装和字段适配全部删除。

主进程执行的是宿主网络环境，不是渲染页面的网络环境：不采用渲染页面的 CORS 和自动会话 Cookie。需要 Cookie/Authorization 的调用方显式提供请求头；认证属于业务配置，不再混入通用 SDK。这一点与“标准 fetch 接口”分开说明，不声称两种执行环境的 Cookie/缓存策略相同。

Request/Response 实例与流不能直接通过普通 IPC 传递，因此内部通道只传元信息与字节：

- 请求由原生 Request 编码，包括 FormData 边界、Blob 和二进制；普通上传按块发送并等待消费，响应头先返回，响应体按 pull 读取，不先整包缓冲。
- 原生 Response 承载响应流，提供 json/text/blob/arrayBuffer/formData、bodyUsed 和 clone；URL、redirected、type 与完整宿主响应头由元信息恢复。
- Chromium 构造 Request/Response 会过滤 Cookie/Set-Cookie。传输层保留调用方显式请求头与主进程完整响应头，以维持 B 站凭证等现有行为；响应头的普通修改方法保持只读。
- signal 在收到响应头后继续作用于响应体；body.cancel、普通窗口销毁/导航也释放执行端资源。控制消息独立于命令取消检查，避免“取消后无法发送取消消息”。
- keepalive 的非流请求体先按原生约束编码为字节；窗口退出后主进程完成并丢弃结果，旧窗口不能重新读取。显式 signal 取消仍优先。
- hasBody 等字段仅为内部 IPC 标记，依据原生 body 是否存在自动生成，不是公开 fetch 选项，不从 @tau/plugins 导出。

网络语义交给原生 fetch，未新增 URL 白名单、重定向计数、认证注入、JSON 编解码或响应大小策略。请求属于发起窗口，不能读取其他窗口的传输；当前仍是显式信任的开发插件，不因此宣称已实现第三方隔离或授权产品。

## 旧调用迁移

| 调用者            | 新写法                                                                                  |
| ----------------- | --------------------------------------------------------------------------------------- |
| 微信读书生产服务  | JSON.stringify 请求体、Response.json、显式检查业务 HTTP 状态                            |
| B 站 API/媒体     | JSON 或 text 显式读取，Response.url，redirect: manual，Headers.getSetCookie，HEAD 的 ok |
| 图片生成/编辑     | 直接使用 Response，原生 FormData，删除 base64 multipart 与伪 Response 组装              |
| 图片/文件读取     | Response.arrayBuffer 与 Headers.get                                                     |
| 网页剪藏/学习资料 | Response.text 与显式状态检查                                                            |
| MCP HTTP 工具     | 标准 RequestInit、AbortSignal.timeout、响应头和文本                                     |
| 主进程下载保存    | 原生 fetch、arrayBuffer 与显式状态检查                                                  |

已有业务超时仍由业务调用方表达，例如图片请求 300 秒和 MCP 参数默认 30 秒，不作为执行器全局限制。不会悄悄将业务失败状态当成成功；无需读取错误正文的调用方主动 cancel 释放流。

独立主进程模块引用的 npm 包 `node-fetch` 不是本次移除的桌面 nodeFetch 函数，不把包名出现误判为兼容层残留。没有保留旧函数、旧 DTO 或旧 IPC 通道。

## 微信读书验证样本

最小流程为：已有账号配置 → 启用「微信读书服务验证」→ 打开「微信读书笔记书单」→ 手动读取、分页、刷新与取消 → 停用/重新启用。

样本只通过 context.fetch 发请求。主进程网络层不知道微信读书；api_name、Skill 版本、分页、HTTP/业务错误属于插件 client。读取的是已有 /user/notebooks 协议，每页 count=100，lastSort 不前进时报错，重复书籍按 bookId 合并。

宿主装配通过 createWeReadPlugin(getApiKey) 将已有微信读书配置读取函数交给这个可信内置样本，插件自行设置 Authorization。该函数是业务依赖，不是新 SDK 凭证 API，也不向其他插件自动注入微信读书凭证。物理凭证存储未迁移；返回前发现账号变化就拒绝旧数据，格式错误的 Key 不交给 Headers 回显。

页面使用独立 React Query 缓存，打开时只读配置状态，不自动请求账号数据。分页失败保留已有页，刷新从第一页开始；隐藏/关闭取消查询，停用释放请求，重新启用不接收旧实例结果。没有写生产书架、笔记、摘录或同步标记。
