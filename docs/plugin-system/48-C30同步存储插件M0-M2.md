## 调研事实

| 层次 | 当前实现 | 必须保留或收口的边界 |
| --- | --- | --- |
| 桌面数据库同步 | `apps/desktop/src/commands/sync.ts`，渲染端编排，调用主进程锁/打包/安装 | 固定任务所属库和目标，不改冲突决策、恢复事务 |

| 资源同步 | `src-electron/main/modules/resource-sync.ts` | 另有四套Adapter；计划、黑名单、重试与状态归宿主 |
| 用量同步 | `src/services/usageSync.ts`、`usageSyncRunner.ts` | 使用同一提供方；保留devices/manifest/分段协议 |
| CLI | `apps/cli/src/utils/sync-providers/*` | 独立四套实现；最终与桌面复用同一Node存储模块 |
| 移动端 | `apps/mobile/src-tauri/src/sync/providers/*` | Rust实现保留现有四种远端协议，不宣称能执行Node插件 |

桌面S3读取与存在检查使用拼接URL请求，CLI使用签名SDK；S3插件应采用经过签名的读取，不直接复制桌面旧实现。实际私有桶行为尚未在本轮执行验证。

目前数据库/会话包经过Uint8Array与IPC，资源适配器也有完整Buffer读取；大文件后台传输是M1/M2需要实接的路径，不能仅把接口改为stream就宣称消除了内存复制。资源取消主要在网络请求前后检查标志，需将signal贯穿实际请求。

## M0发现的架构前置问题（已确认纳入M1）

普通本地插件由 `PluginActivationManager` 通过 `Storage.getItem/setItem` 保存启用意图；`LocalPluginManager` 对普通插件沿用此路径。主进程 `ContentPluginPreferences` 目前只管理静态内容插件，落在 `.editor-enabled.json`。`plugin-local:content-enabled` 明确拒绝非内容插件。桌面PluginProvider随窗口/工作区创建和销毁，CLI无法独立读取普通插件的窗口启用偏好。

同步插件后台加载必须尊重用户的启用状态，不能仅凭“目录存在”或“同步目标已配置”就执行。否则用户在插件管理里停用后，CLI仍可能连接远端；多窗口与退出同步也可能出现不同判断。

不采用以下绕路：

- 为S3增加一份同步专用enabled状态，与插件管理并存。
- 将同步插件标记为editor/whiteboard内容插件以复用现有持久化路径。
- 依赖渲染窗口完成激活，再允许CLI或退出同步借用窗口实例。

**用户已确认把以下改造纳入M1：**

1. 所有已安装的本地插件共用主进程拥有的启用意图存储，窗口只订阅镜像；CLI通过同一Node持久化实现读取。
2. 保留实际运行语义：普通界面插件按既有生命周期启停；内容插件仍按现有启动快照和重启规则装配；后台同步实例由任务持有。
3. 增加通用的后台任务占用检查：有同步任务使用插件时，停用/卸载/替换先拒绝并提示结束任务。任务结束释放占用，不新增S3特判。
4. 迁移现有本地插件偏好时定义优先级、失败重试和完成标记；内容插件已有主进程值优先，普通本地插件从现有窗口偏好一次性转移。旧偏好清除只在新存储确认成功后进行。
5. 内置主题插件和旧开发台夹具不扩入此次改造；它们不作为可供CLI加载的已安装同步插件。后续如果也需要后台运行，必须进入同一协议。

这项改造触及已有插件管理，已在用户确认后开始；范围限于已安装本地插件启用意图，不重构整个插件系统。

曾比较过只收口后台/内容插件的较窄选择，但会保留按能力区分的两条持久化路径。用户选择统一全部已安装本地插件，需覆盖已有普通/内容插件的回归。

## 目标分工

客户端负责快照生成/校验、对象命名、版本链、同步锁、恢复、资源计划、用量合并、任务取消/重试与用户确认。插件负责认证、目标路径映射、远端对象操作、网络错误归一化与配置表单。SDK不向提供方暴露数据库句柄或业务内容写入API。

同步目标配置由宿主在本机应用级持久化，不放在插件当前按工作区隔离的context.storage中。插件定义配置结构与表单；凭证属于配置，不新增通用凭证平台。每次任务捕获目标配置版本、插件版本和工作区，后续修改只作用于新任务。配置、密钥、签名URL不进入日志。

后台模块不依赖React、Electron或窗口API，桌面后台和CLI可加载同一产物。前端仅贡献配置组件。提出manifest增加专用sync入口、模板编译src/sync.ts；必须同步包校验、摘要、ZIP上传检查、安装升级与模板，不能只让本地开发目录绕过校验运行。

接口草案见 [49-C30同步存储接口草案.md](./49-C30同步存储接口草案.md)。

## 阶段与完成标准

### M0：边界与契约

交付：本方案、接口草案、现有消费者清单与验收矩阵。确认后台启用状态的前置方案之后，再将接口从草案推进为实现；当前没有声称已通过任何新增行为测试。

### M1：宿主收口

1. 经确认后，收口本地插件启用意图和后台任务占用；为切库、多窗口、重启与CLI建立行为测试。
2. 增加中性的存储契约及协议适配；已有快照发布函数仍负责版本仲裁，存储层不理解commitId。
3. 固定单次同步目标。数据库、资源、用量与CLI都使用同一对象语义；错误明确传播，不把远端故障当成不存在。
4. 网络与大文件搬运在后台执行，渲染端接收进度与小型结果。沿用现有数据库锁/恢复模块，不在插件内复制同步引擎。

验收：现有服务回归不退化；两个竞争提交只有一个胜者；响应丢失可确认原提交；切换设置不会串目标；权限/网络故障不会触发错误覆盖；取消后旧任务不发布版本；恢复机制仍执行。

其他提供方的旧源码可在尚未迁出时存在，但必须经统一协议接入，不新增另一套S3分支。每个提供方迁出后删除对应旧实现；不把长期双路径视作完成。

### M2：S3插件完整闭环

1. 专用后台入口及其完整包校验；同步配置组件在设置→同步的专用挂载点展示。
2. S3源码归独立作者项目，遵循现有业务插件独立仓库方向；不将业务源码塞进scripts。发布前只做本地作者项目与构建验证，创建GitHub仓库和SDK发布另记实际状态。
3. S3上传、签名下载、stat、分页list、delete、原子仅创建、取消与错误归一化都在插件实现。普通npm依赖打包，宿主不通过专用S3 IPC替插件完成核心逻辑。
4. 桌面数据库/会话、资源、用量及CLI使用同一插件实现。移除已被接管的旧S3同步Provider/Adapter；其他业务仍使用的S3上传/发布接口保留。
5. 同步专属配置一次性迁入宿主目标配置；共享integration凭证不删除，已有远端对象名和协议不变，不重新上传整个库。

验收：干净作者项目构建→ZIP校验→约定目录安装→启用→同步页配置→私有S3测试目标上传/下载→CLI读取同一快照；并发、响应丢失、权限拒绝、取消、恢复、多窗口与启停全部回归。界面视觉由用户验收。

## 测试矩阵与真实环境边界

| 维度 | 必须覆盖 |
| --- | --- |
| 对象协议 | 不存在与无权限分离；分页完整；相对路径；普通覆盖与原子创建分离 |
| 并发 | 同一后继对象最多一位成功；失败响应不能触发覆盖 |
| 完整性 | 数据库/会话配对校验、损坏包拒绝、安装失败恢复 |
| 生命周期 | 窗口隐藏/关闭、切库、重启、CLI独立运行、插件停用/升级 |
| 配置 | 同一任务锁定目标版本；迁移失败保留旧配置；不输出凭证 |
| 大文件 | 真实传输与取消；确认字节没有经渲染端整包复制 |
| 分发 | 后台入口摘要、缺入口/损坏入口、生产包安装与版本切换 |

单测和本地协议服务器不替代真实S3服务验收。真实验收使用明确的隔离前缀，不使用现有生产同步目录；目标服务、凭据和删除权限在执行前明确。对不支持原子条件创建的S3兼容服务明确拒绝，不通过检查后覆盖降级。

M3以后再迁出其余服务；移动端保留现有四种服务的同协议互通，任意第三方存储在移动端执行需另立阶段。同步策略、冲突规则、自动删除远端资源、通用插件沙箱不属于本次。
