## 可行性结论

可以拆分。建议增加独立的发布提供方扩展点 `context.publish.register`，分别交付 `tau.publish-github` 与 `tau.publish-s3`。它们与现有同步、资源上传插件保持独立，因为博客发布需要固定路径、撤下删除、入口切换与整轮提交，现有两个扩展点均不能直接覆盖这些语义。

宿主继续拥有内容选择、模板校验、站点生成、发布计划、增量账本、任务互斥、进度和本地导出。插件拥有账号表单、平台目标配置、连接检查、平台请求及目标解析。本地导出使用同一生成器，直接写用户选择的目录，不注册本地发布插件。

S3 的浏览器侧签名和网络传输已有同类实现，可以沿用模式。GitHub REST 文件上传也能直接迁出；已有 Git Push 则需要额外处理：当前 SDK 没有 Git 服务，不能把 `simple-git` 连同主进程代码直接塞进插件。**建议首期保持现有 REST 与 Git Push 两种方式，新增受控的通用 Git 快照发布服务；Git Data API 批量提交列为可替代方案，不在迁移时静默关闭 Git Push。**

本轮拆分的退场目标应明确为桌面端 GitHub/S3 发布实现与集成入口。移动端仍独立使用这两类集成进行同步和资源上传，全仓退场需要另行替换这些消费者。

## 推荐的提供方协议边界

以下是接口职责草案，不是已经存在的 API；类型名和字段在实施时随行为验证收敛。

| 协议部分   | 输入与输出                                         | 责任                                                               |
| ---------- | -------------------------------------------------- | ------------------------------------------------------------------ |
| 注册       | 所属插件 ID、名称、`create(config)`                | 宿主校验 ID 等于 pluginId；一个插件只注册一个发布提供方            |
| 创建会话   | 固定 JSON 配置、调用方与插件生命周期 signal        | 渲染端创建提供方；主进程只登记身份与任务数据                       |
| 解析目标   | 返回物理目标标识、basePath、可选公开地址、提交方式 | 生成前解析，密钥不进入物理身份或站点数据                           |
| 连接检查   | 返回可读的连接结果或失败                           | 不创建分支、不上传测试文件，不将可读权限等同于部署成功             |
| 文件式提交 | `uploadFile(path, Uint8Array)`、`deleteFile(path)` | S3 与 GitHub Contents API 使用；宿主管理上传、入口、删除和重试顺序 |
| 快照式提交 | 本轮变更文件、删除路径、进度；返回整轮提交结果     | Git Push 使用；只有远端提交确认后才整体记账                        |
| 关闭会话   | 等待在途操作、释放网络及服务资源                   | 停用、切库、窗口关闭后拒绝旧调用及迟到回复                         |

用判别联合表达文件式与快照式两种提交方式，不要求所有提供方实现两套接口。核心按协议方式分流，不按 `tau.publish-github` 或 `tau.publish-s3` 特判。旧发布流程没有调用 `IPublishProvider.listFiles`，首期不需要把远端全量列举暴露到新协议，删除范围继续由宿主账本确定。

字节使用 `Uint8Array`，插件接口不暴露 Node `Buffer`、数据库句柄或任意宿主路径。发布文件已有摘要和入口标记，这些信息应随文件描述一起传递；大站点采用有界批次或任务文件句柄按需读字节，避免把整站内容一次复制到多个进程。

文件式提供方可声明并发上限，由宿主将其与用户上传参数共同收敛为有效并发。GitHub 同分支逐文件写入宜串行，S3 可并发；这个约束通过协议传递，不把平台名称写回核心调度器。认证失败、限流和服务异常须按真实错误处理，不能把获取 SHA 的所有失败都当作文件不存在。

### 配置和页面承载

建议沿用同步、上传的单一当前提供方结构：`publish.active` 为 `local` 或 `plugin`，`publish.plugin` 保存当前插件身份及 `configurations`，`publish.local.basePath`、`publish.site` 保留。首期不引入多站点、多账号管理体系。

GitHub 插件表单负责 Token、仓库、分支、提交者、basePath 与发布方式；S3 插件表单负责 AK/Secret、Endpoint、URL 风格、Bucket、Region、对象前缀与 basePath。配置全部迁出“集成”中的共享账号块。插件配置通过 `publishConfig.value/save` 读写应用级设置，不放进按工作区隔离的 `context.storage`。

插件未安装、未启用或激活失败时保留原选择及配置，明确显示不可用，提供现有插件页入口；不自动选另一个远端，也不静默转成本地导出。提供方列表、连接状态和表单保存需要响应启停与配置变化；新增数据查询按桌面规范使用 react-query。

站点基础字段与模板选择仍由宿主管理。远端凭据不能进入生成器输入、数据 JSON、模板文件、预览返回、错误日志或任务进度。本地导出仅依赖选中的模板和内容插件，不要求安装任一发布插件。

### 目标身份与增量记录

当前 `resolveSiteMeta` 以 `github + repo + branch` 或 `s3 + bucket + pathPrefix + endpoint` 生成物理身份，`statePath` 对其做 SHA-256；相同目标跨窗口和数据库共享发布账本。这个性质必须保持。

物理身份应与密钥、插件版本、模板版本和公开 URL 解耦。更换 Token 不应全量重发；更换分支、Bucket、Endpoint 或对象前缀必须使用另一份账本。建议使用有版本的规范化目标描述，由宿主统一序列化，插件负责平台字段解释。相同物理目标不能因插件更新或提交方式变化绕过互斥。

实现保持原有物理身份序列化规则，因此已有界面配置对应的 `publish-releases/<hash>.json` 无需改名，也不需要额外多文件升级事务。插件升级、Token 与提交方式变化不改变身份；缺少目标账本时完整上传，不借用数据库全局历史进行远端删除。后续若引入身份规范化，必须单独处理旧账本映射与冲突，不能直接换哈希算法。

预览使用与执行相同的目标解析，但只返回路径和数量。一次任务固定配置、目标和插件代次；运行期间修改设置只能影响下一次任务。

## GitHub 发布方式比较

| 方式                                               | 可行性和成本                                                                 | 对现有体验的影响                                        |
| -------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------- |
| 只迁移 Contents API，移除 Git Push                 | 实现成本最低，主要是 HTTP 与字节适配                                         | 丢失现有加速与整轮提交能力，不宜作为默认迁移            |
| 保留双方式，Git Push 经受控宿主服务                | 成本较高，需要通用 Git 服务、任务占用及凭据处理                              | 保留现有用户选择，推荐作为行为等价拆分基线              |
| Git Data API 批量创建 blob/tree/commit，再更新 ref | 无本地 Git 缓存，可由渲染插件经 fetch 实现；需要新的失败恢复与仓库初始化测试 | 仍有 REST 请求和限流，不能未经验证就承诺等价于 Git Push |
| 插件恢复 Node 入口或任意 shell                     | 与既有执行边界冲突                                                           | 不采用                                                  |

### 保留 Git Push 的服务要求

服务可采用 `services.git.publishSnapshot` 一类窄接口，接受 HTTPS 远端、目标分支、提交者、任务文件与删除清单。宿主只执行规定的 Git 流程，插件决定 GitHub 远端及平台配置。服务不接受任意命令、命令拼接、任意 cwd 或任意文件读写，也不包含 GitHub 专属字段或工厂。

原克隆缓存选择需迁为受控目录句柄，默认缓存归宿主管理。保留目标锁和缓存锁、普通分支快进、新分支不带默认分支源码、只暂存本轮拥有的路径、按字面处理特殊文件名、不强推、保留 CNAME 及其他文件等既有约束。

凭据采用任务级认证通道，不把含 Token 的远端持久写入 `.git/config` 或进程参数。失败日志继续脱敏。推送响应丢失时须验证远端提交是否已包含本次结果，再推进本地成功账本；中断和重试不得把未确认提交当作成功。

这增加的是宿主拥有的受控系统能力，插件仍只在渲染进程执行。若选择该方向，须在实施前记录架构裁决，并同步 03 指南的插件服务、发布与任务生命周期小节。

### Git Data API 替代方案的证据和限制

GitHub 官方支持基于已有 `base_tree` 创建包含增删改的新树；已有分支应保留其基准树并只覆盖发布拥有的路径，缺少 `base_tree` 会使未列出的文件在新提交中消失。删除项使用 `sha: null`，不存在的删除目标需要先处理幂等性。[Git Trees API](https://docs.github.com/en/rest/git/trees)

插件可先创建所有资源对象，再创建提交，最后以非强制方式更新分支引用，从而让分支一次切换到完整结果；引用更新失败不能记为成功。官方文档明确 `force: false` 只允许快进，且空仓库不能直接创建引用，因此空仓库初始化与并发分支变更需要专门路径。[Git References API](https://docs.github.com/en/rest/git/refs)

这条路径技术上可行，但改变现有提交实现。官方模板在既有记录中已有数百个资产，首次发布仍需大量对象请求；实施前应验证首次与增量请求量、限流退避、空仓库、保护分支、响应丢失以及大文件和总内存开销，再决定能否替代 Git Push。这里不把 GitHub 文档中“读取 blob 的 100 MB 限制”误当作创建 blob 的上传承诺。

## S3 插件的具体边界

已有独立 `tau-plugin-s3`、`tau-plugin-upload-s3` 工程提供 AWS SDK 浏览器构建与 `createTransport(context.fetch)` 参考；它们不是本轮新增或交付的发布插件。新插件独立打包 AWS SDK，不要求宿主提供 S3 类或签名接口。

保留当前 Endpoint、自定义路径/虚拟主机风格、Region、Bucket、对象前缀、Content-Type 及 Cache-Control 行为。摘要数据、内容插件摘要目录使用不可变缓存，普通模板资产与入口允许同路径更新，不能把所有文件统一设为 immutable。对象前缀与访问 basePath 独立保留，迁移不重新推断用户已配置的路径。

签名后的查询参数、字节及签名覆盖的请求头需由传输层正确保留；现有同步纠偏曾验证过 `content-length` 对签名的影响，不能因为渲染环境而随意删除。[55 的 S3 验证记录](55-插件渲染进程边界纠偏.md)

`HeadBucket` 连接检查不能保证最终 PUT/DELETE 有权限，真实错误仍在发布时上报。上传依赖未全部成功时不得更新入口；入口成功后才按宿主清单删除旧对象，删除失败继续留待重试。S3 不宣称具备整站多对象原子事务，多个入口也不能假定一起切换。

## 生命周期和提交确认

发布桥挂在 `DesktopPluginProvider` 一类常驻壳层，不能挂在发布页或设置抽屉。离开发布页继续运行；切换数据库会重建运行时，关闭发起窗口会失去插件执行者，这些场景需显式中止或判失败，释放目标锁并保留已确认的部分进度。

每轮会话绑定窗口、工作区、插件 ID、激活代次及配置快照；主进程验证调用与回复归属、路径和结果形状。发布占用必须接入启停、卸载、更新、恢复和重启入口，不能仅阻止停用而允许更新替换正在运行的插件。

文件式提交沿用宿主重试、有限保留与 pending 记录。快照式提交只有整轮确认后才落成功记录。请求超时、窗口退出与响应丢失时，不能让迟到回包推进新会话的账本；远端可能已经完成的结果应由后续确认或幂等重试解决。

## 配置迁移与退役清单

### 配置升级顺序

1. 在既有设置加载链中，先让同步和上传迁移消费共享旧凭据，再执行发布迁移；发布迁移对所有旧 GitHub/S3 目标保留配置，包括当前未选中的目标和字段不完整的目标。
2. 备份旧配置，将 `publish.github + integration.github` 合成 `tau.publish-github` 配置，将 `publish.s3 + integration.s3` 合成 `tau.publish-s3` 配置；保留 GitHub 提交者、方式与缓存定位，S3 的 `path` 映射为插件的 `pathPrefix`。
3. 已有插件配置优先，保留当前选择和显式停用意图。插件缺失时等待用户安装启用，不降级为宿主实现。
4. 将旧目标账本映射到新目标身份。多文件升级须有可恢复记录，不能假定分别 rename 就等于整体事务；任一步失败不发布新设置，重启可恢复或重试。
5. 完成桌面生产消费者清零后，删除桌面设置类型、默认值与读取路径中的 `integration.github/s3`、`publish.github/s3`；新写入拒绝旧格式，避免旧窗口快照重新写回这些字段。最后升级的转换代码在完成用户升级后按既有清洁版规则退役，不长期保留双运行路径。

| 对象                                                             | 消费者与用途                                                   | 处理                                                       |
| ---------------------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------- |

| `src/utils/github.ts` 的账号、仓库、分支查询                     | 当前桌面集成与发布表单                                         | 能力迁入插件，删除前复查 barrel 导出及全部引用             |
| 桌面 `@aws-sdk/client-s3`、`mime-types`                          | 当前生产导入位于 S3 发布类                                     | 发布类退出后复核并移除桌面直接依赖，重新生成锁文件         |

| `constants/github.ts`、图床 CDN 设置                             | 历史图片地址转换等                                             | 不随发布凭据删除                                           |

移动端的 `useSyncSettings.ts` 当前通过 Tauri 读写本地设置，并非桌面渲染设置副本；不能推断删除桌面本地字段会立即删除手机凭据。但移动端 `SyncSections.tsx`、`ResourceSections.tsx`、`IntegrationSections.tsx`、`SettingsModulePage.tsx` 与 `src-tauri/src/setting.rs` 都仍有真实消费者。因此本轮可以删除桌面入口与桌面配置，不能宣称 GitHub/S3 已在全仓彻底退役，也不应为了这个目标给移动端恢复插件运行时。

## 实施阶段和验收

| 阶段                 | 工作范围                                                                                  | 完成条件                                                                            |
| -------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 发布契约与双实现原型 | 确定 Git Push 承载；增加发布注册、配置表单目标、文件式/快照式协议；建立两个仓库外作者工程 | 使用正式 PluginHost 验证注册、调用和回收；Git/S3 行为均能表达，未接线接口不作为交付 |

| 内置实现退役         | 两个插件接替发布，按消费者清单删除旧工厂、集成和专属依赖；同步 03、04 与裁决记录          | 桌面生产代码不再消费旧 GitHub/S3 集成，通用 Git/脚本/移动端保留边界有记录           |
| 独立包与完整验证     | 两个作者工程用公开 SDK 干净安装、类型检查、测试、ZIP 构建；正式宿主安装与发布回归         | 本地、REST、Git Push、S3 均通过，包内无宿主源码路径、密钥或本地依赖链接             |

至少覆盖以下行为：

- 无发布插件时本地导出可用；同一模板、同一 basePath 下文件内容保持一致；无模板时明确阻止生成。
- 文件依赖先行、失败不更新入口、增量重试、无变化不轮转保留窗口、撤下与删除失败重试；快照提交失败不写成功记录。
- Token 变化复用同一物理账本，目标变化隔离；多窗口和跨数据库同目标互斥；配置变化不改变在途任务。
- 缺插件、未启用、激活失败、切库、窗口退出、停用/更新/卸载保护、旧回复和网络超时；离开发布页任务继续。
- Git Push 保留特殊文件名、ignore 资源、CNAME、独立新分支、拒绝非快进、推送失败重试；认证不落盘，日志脱敏。
- S3 的自定义 Endpoint、URL 风格、前缀、签名、二进制字节、MIME 与缓存策略；403 和服务错误不得伪装成成功。
- 配置与账本升级幂等、已有配置优先、失败重启恢复、非活动目标保留；多窗口保存不覆盖已退役字段。

实施验证包含 SDK 与桌面类型检查、相关行为测试、Vite 主进程/渲染端构建和独立作者 ZIP 验证。新增“博客发布”分类时同步 SDK 分类、桌面和门户标签及门户校验；公共 SDK 打包入口和作者模板文档也须同步。视觉验收按项目规则由用户完成。
