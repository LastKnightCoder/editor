## C03 桌面页面与内置 UI 接入

归属为 P4 加所需的最小 P3 适配。目标是一个宿主显式登记的可信开发插件，能在真实桌面应用中提供页面，使用内置 UI，并通过应用命令入口打开。

需要完成：

- 明确渲染侧贡献与主进程服务的装配位置、窗口/工作区归属和关闭清理，复用 C02 生命周期；不把 Node 文件适配器直接打进渲染端。
- 页面注册、参数、命名空间、打开、返回/前进和停用处理接入已有 Page，不另建 Router。
- 页面相关公共类型与注册能力从 SDK 根入口提供，注册经插件上下文执行；UI 从 @tau/ui 获取，继承 React、主题和浮层上下文。保持 C02 的无 DOM 运行用例通过。
- 仓库内可信插件先接入；外部包 external/样式产物规则留在 P6。样本本机偏好经注入的浏览器存储适配器按工作区分域，真实业务存储仍按后续 P3 设计。
- 应用命令入口接入插件命令；侧栏贡献按样本需求增加，不能为每个页面硬编码一个壳层分支。
- 提供一个真实桌面样本，不导入应用内部 store 或注册表；不在这一步迁移微信读书全量功能。

验收路径：启用插件 → 从应用命令打开页面 → 使用 UI 并读写自己的偏好 → 返回/前进 → 停用 → 页面与命令按规定退出/降级 → 再启用可恢复。已打开页面、历史条目和未保存状态的处理必须明确，不以 Map.delete 代替完整停用。

修改静态 Page 注册或导航单源约定之前，在桌面 DECISIONS 记录实际选择，并同步 03 指南；框架保持零业务依赖。Agent 做类型、行为、构建和结构检查，视觉仍由用户验收。

C03 的提交切分在调查后决定，每个切片带真实调用路径，不先单独提交一套未实现的 pages API。

## C04 编辑器扩展接入

归属为 P5 的编辑器子项，依赖 C03 的桌面宿主和 UI 基础。内部复用现有 defineExtension 与 EditorKit，以一个小型节点/命令扩展验证插件装配，不重建编辑器插件协议。作者从 @tau/plugins 取得定义函数和公共类型，组件从 @tau/ui 导入，不直接导入 @tau/editor/api；按领域命名避免与白板等导出冲突。当前实现范围、重建取舍和验收见 [13](13-C04编辑器扩展接入.md)。

必须明确安装到哪些编辑场景、每个编辑器实例的生命周期、Markdown 等纯编解码入口，以及已打开文档在启停扩展时如何处理。主进程需要的纯 codec 单独装配，不把 React 组件通过 IPC 传递。

验收覆盖插入、编辑、只读、撤销重做、序列化往返、停用后的未知节点保留和重新启用恢复。不能靠无条件重挂编辑器丢弃正文会话或历史。若某种动态更新需要重开文档，应把限制作为具体取舍说明，不宣称无缝热更新。

C04 成果保留，生产场景另行验收；当前先推进独立插件闭环，不因一个编辑器样本就冻结所有 SDK 接口。

P6 负责统一入口的外部交付：包名、类型声明、宿主模块解析、共享依赖与版本约定。验收时在不依赖仓库源码和未发布内部包的环境构建示例；作者只安装公开 SDK 及声明的生态依赖，不手动拼装多个 Tau 内部包。

## C05 自定义设置接入

C05 补充 P4 设置分区。context.settings.register 从 @tau/plugins 提供，组件使用 @tau/ui；接入现有设置浮层和即时保存模型，数据复用插件私有存储，不新增通用配置数据库。

必须验证注册、打开、保存、关闭/重开、停用与重新启用；包括渲染错误恢复、读写失败重试、迟到结果隔离、切库与宿主重建后持久化。单项注销不得删除已保存值或影响其他插件，失效分区保留不可用提示。实际合同与限制见 [14](14-C05自定义设置接入.md)。

## C01 多场景需求与边界裁决

交付类型：完整设计与证据提交，不改变业务行为。

1. 对照 [目标架构](02-目标架构与能力.md) 的六类样本，补齐直接消费者与反例，分别标记同步调用、异步调用、跨工作区和持久化需求。

3. 比较受限 Chromium 运行环境、独立后台运行载体、受信任界面扩展的能力边界，记录平台限制与成本，不把 Worker 或 Node 进程直接视为安全沙箱。
4. 在决策记录中确定首个支持档位、通信端点身份、撤销机制、数据作用域和入口格式，并给出攻击性测试的预期拒绝结果。
5. 按裁决细化 C02 的精确文件范围和验证命令；若需要改变 Page 等现行架构，先补对应专题决策。

完成条件：每个开放能力能指出执行与校验位置，每类样本能指出可支持的运行档位；未知事项有负责人角色、验证办法和阻塞范围，不把待定选择写成已实现。

历史退出结果：纯文档可回退，随后已实施 C02；当前下一步以页首 C07 计划为准。

## C02 最小插件 API 与流程闭环

交付类型：有实际消费者的基础设施提交。用户已要求优先 API 设计与流程，当前合同改为 [API 与流程闭环](10-C02API与流程闭环.md)。09 保留为后续隔离备忘，不是当前门禁。

范围是一个命令加一个插件私有持久化动作：宿主显式登记可信定义，创建实例、调用命令、停用、重新启用和重建后读取数据。包括注册作用域、失败回收与工作区绑定，不引入跨进程通信和第三方加载器。

验收至少覆盖：公共存储接口按插件和工作区分域，旧上下文不能继续操作，停用后命令和监听器消失，激活及清理失败可恢复，存储重建可读取磁盘数据。这些是正常 API 行为约束，不声称可限制恶意同进程代码。

当前生产业务保持原路径。API 行为验证后逐步接入真实内置业务；不创建未实现的编辑器、数据库、白板接口。隔离证明仍是未来受限第三方开放的前提。

恢复方式：撤回独立开发包与样本，现有业务不依赖它。先提交 C02-A 的内存闭环，再提交 C02-B 的持久化闭环；每个切片有消费者、测试和恢复方法。

## 后续提交如何拆分

进入 P3 以后按一个完整行为切分，而不是“先提交全部类型，再补实现，再接 UI”。可采用以下单元，但进入阶段前须复核依赖：

- 工作区绑定读写：服务、执行端校验、实际调用者、竞态回归一起提交。
- 网络与凭证：受控请求和取消先闭环；凭证物理迁移独立提交并附恢复证据。
- 插件存储：命名空间、分页和限额先闭环；公共领域事务按真实需要增加。
- 动态页面：双注册表、导航接线、页面退出及历史降级一起提交，静态页面照常使用。
- 来源提供器：注册与定位接线、已有 ID 保留、插件缺失显示一起提交。
- 单个领域扩展：一次只接一个领域及一个完整样本，不同时改三套内核。
- 热重载：先实现手动安全重载，再增加文件监听；每次都能独立使用。

微信读书的缓存与摘录原子性是数据协议的压力样本；编辑器输入和白板手势是同步性能压力样本。若两者需求冲突，划分接口和执行档位，不能削弱安全边界去统一形式。

## 每次提交后的完整可用

1. 应用可以启动，已存在的用户路径保持可用。
2. 新增行为已接真实消费者或可运行的开发样本；不暴露死入口和假数据。
3. 类型、行为、构建和结构检查按 [规范](04-开发规范与验收.md) 通过。
4. 数据写入具备一致性、身份与恢复保障。
5. 文档描述实际状态，未完成能力不进入稳定公开承诺。
6. 不需要下一次提交来修复本次已知阻断问题。

阶段未全部完成不影响提交完整性。已知非阻断视觉问题由用户后续验收并记录；数据损坏、越权、死入口和关键功能失效均为阻断问题。
