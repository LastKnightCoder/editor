## 2. 最小数据操作协议

保留现有方法名、Uint8Array及返回形状，避免同时迁移存储实现和重写调用协议。

```ts
interface RemoteFileInfo {
  name: string;
  path: string;
  size: number;
  lastModified?: number;
  hash?: string;
}

interface SyncProvider {
  uploadFile(objectName: string, content: Uint8Array): Promise<boolean>;
  downloadFile(objectName: string): Promise<Uint8Array>;
  fileExists(objectName: string): Promise<boolean>;
  listFiles(prefix?: string): Promise<RemoteFileInfo[]>;
  createFileIfAbsent(objectName: string, content: Uint8Array): Promise<boolean>;
}
```

这是覆盖现有数据库、资源和用量同步的调用集合，不是按S3服务商划分等级的能力体系。四个插件按这一组已有调用分别适配；没有capabilities字段，没有动态能力探测表，没有要求用户勾选能力的设置。

- uploadFile：普通上传，按当前实现执行覆盖/更新，true表示成功；沿用已有false或异常处理路径。没有新增write mode参数。
- downloadFile：读取内容；读取失败沿现有异常路径交给客户端，不用空字节代替失败。
- fileExists：存在性查询；保留其现有实现方式，不强制另做HEAD或返回对象大小。它不能被宿主用来模拟原子的“先查再写”。
- listFiles：资源同步已实际使用，返回当前远端文件信息形状。底层服务分页由插件内部处理，首版不向客户端增加cursor/limit协议。
- createFileIfAbsent：保留现有快照发布函数已经调用的方法。它只表达创建而不覆盖的提交操作，不规定使用某个HTTP头，也不引入“安装前必须通过原子能力认证”。具体后端问题独立核查，不直接推导为整个插件不可用。

现有返回处理并不完全一致：桌面S3/WebDAV/GitHub上传及条件创建的异常多转换为false；AliOSS条件创建和CLI中的若干实现直接抛出异常。publishSnapshot对false和异常都会尝试读取后继记录、核验commitId。迁移阶段保持这条控制流，不将false重新解释为只可能“对象已存在”，不在本轮强推新的结果联合类型或错误码全集。

部分旧listFiles实现会在异常后返回空数组，这是现有行为问题，需要单独登记。不能在协议提取时默默改掉，也不能据此声称网络失败等价于空目录。若后续要调整错误行为，必须显式记录新旧差异与调用方变化。

## 3. 从首版移出的内容

| 移出项                              | 原因                                                                                                  |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------- |
| deleteFile/remove                   | 当前同步主链路没有调用；旧S3/WebDAV/GitHub的deleteFile只是返回false的占位，不据此要求作者补齐删除权限 |
| stat                                | 当前使用fileExists，大小信息来自列表；不新增一次对象元信息查询协议                                    |
| getProviderName                     | 归提供方注册信息的name；CLI状态页/TUI已有调用，宿主用该名称继续提供显示，不删除这一用户行为           |
| ReadableStream、ObjectSource.open   | 首版沿用已有字节接口，流式传输后续按实际需求讨论                                                      |
| 强制AbortSignal、进度回调、dispose  | 不作为这次提取的必填存储方法；沿用宿主已有任务管理，不承诺取消必能撤销远端写入                        |
| capabilities、能力探测/分级         | 不增加，用户只填写服务配置                                                                            |
| target.identity、公开configRevision | 不作为插件额外必填字段；宿主内部固定本次任务的配置，不要求作者实现一套目标身份协议                    |
| 写入探测、删除探测及整套连接认证    | 不作为选择、安装或启用同步插件的前置流程                                                              |

上表不删除既有客户端的冲突校验、备份恢复、包摘要或最低版本检查。这些是已存在的客户端职责；本轮也不增加新的格式、配额或服务商认证门槛。

## 4. 注册、配置与设置页

提供方注册只需要身份、名称、按配置创建适配器的工厂，以及对应的配置组件。四种服务各自一个插件；用户看到S3/阿里云OSS/WebDAV/GitHub，选择后填写相应地址、桶、路径和凭据。

- 插件负责定义、解释自己的配置字段；客户端保存配置并挂载到“设置→同步”，不增加统一凭证服务。
- 后台工厂使用本次任务的配置快照，返回上述SyncProvider；前端配置组件与后台实现通过同一插件身份关联。
- 配置组件只负责编辑/保存，不承载同步引擎。保留客户端的检查远程版本、上传、下载和错误展示入口。
- 不要求用户声明服务端能力，不预设某个S3服务商白名单，也不自动改用AliOSS。
- 用户此前已确认的主进程启用意图收口保留；普通插件即时启停、内容插件重启生效的行为不变。
- 后台运行不能依赖设置页一直打开。已开发的后台入口属于加载实现，不用它反向扩大存储方法集合。
- 后台声明使用defineSyncProvider({id,name,create})；前端通过context.settings.register({id,title,target:"sync",component})挂载，一个插件注册一个同步配置分区。target仅是设置挂载位置，不是能力声明。
- 组件接收PluginSettingsProps.syncConfig：value为已保存的JSON配置，save(value)经主进程保存至应用级sync.plugin.configurations[pluginId]并选中该插件。保存失败由组件展示并保留草稿，不进行远端能力探测。普通插件设置的context不变。
- 后台任务会话由宿主维护，开始时捕获配置，结束时释放。窗口销毁后等待在途调用结束再释放占用；同步期间拒绝停用、卸载、恢复版本和重启，暂存更新仍可进行。会话回收不进入作者五方法协议。

## 5. 条件写入单独核查

createFileIfAbsent不是这次新加的方法，不能为了让协议显得更小而从当前发布路径直接删掉；也不应将某个测试入口的失败上升为所有S3插件的准入规则。

独立记录见 [50-C30 S3新旧实现等价性核查](50-C30S3新旧实现等价性核查.md)。先确认当前S3实现实际发送什么请求、失败后如何恢复，再判断新实现是否引入差异。如果发现原实现的兼容性或正确性问题，另列问题讨论；不在插件拆分中顺手重写冲突策略。
