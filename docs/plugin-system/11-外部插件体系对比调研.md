# 外部插件体系与公共 SDK 边界调研

调研日期：2026-10-13。范围是官方文档和官方示例中的作者 API、UI、贡献注册及共享依赖，重点回答 Button 等组件应与核心 SDK 合包还是分开。本文是研究备忘，建议尚未采纳，不覆盖 PS-014，不改变当前代码或启动 C03。

## 观察结论

这些体系没有统一的物理包数量标准。Obsidian 和 Raycast 的核心入口同时提供产品 API 与部分 UI；Grafana、JupyterLab 则公开多个职责不同的包；VS Code、Figma 的自定义 UI 另有运行环境。判断依据应是 UI 的运行方式、组件职责、依赖与版本合同，而不是只比较 import 行数。

“插件作者不应理解内部目录”与“所有符号只能来自一个包”是两个不同要求。对外提供核心 API 和公共设计系统两个清晰入口，也可以隐藏内部实现拆分。

## 体系对比

| 体系       | 作者侧入口                                                                  | UI 方式                                                        | 贡献与运行方式                                         | 对 Tau 的参考                                 |
| ---------- | --------------------------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------ | --------------------------------------------- |
| Obsidian   | obsidian                                                                    | Setting、Modal、ButtonComponent 等同入口；UI 构造以 DOM 为基础 | Plugin 注册命令、视图、设置和编辑器扩展                | 简单作者入口、资源清理与视图协议              |
| VS Code    | vscode；开发类型通常来自 @types/vscode                                      | 原生视图由宿主 API 构建；自由 HTML UI 使用 Webview             | package.json 的 contributes 加 activate 中的运行时注册 | 声明贡献与运行实现分开，不导出整个 Workbench  |
| Grafana    | @grafana/data、@grafana/runtime、@grafana/ui                                | React 组件，UI 有专门的公共包                                  | Panel/App/DataSource 类型插件及扩展点；共享宿主依赖    | 最接近 Tau 的 React 页面和公共 UI 使用方式    |
| JupyterLab | @jupyterlab/application 等领域包；ui-components/apputils 提供 UI 与辅助能力 | Lumino Widget 与 ReactWidget 集成                              | 插件通过 requires/optional/provides 交换服务           | 内置功能插件化、领域扩展和服务装配            |
| Figma      | figma 全局 API；plugin-typings 提供开发类型                                 | showUI 创建 iframe，自定义 HTML/JS 与主题变量                  | 文档操作与 UI 消息通信                                 | UI 与产品操作的运行上下文分离                 |
| Raycast    | @raycast/api；另有 @raycast/utils                                           | Form、List、Action 等预定义组件                                | 作者以组件与动作描述命令界面                           | 当界面形态由产品严格定义时，UI 可构成核心 API |

上表只概括已阅读的公开面，不代表这些产品所有包、权限或内部架构都已审计。以下链接给出各项事实的直接来源。

## Obsidian

官方 API 与示例从 obsidian 导入插件基类、设置与视图能力；官方设置示例使用 Setting 操作容器，ButtonComponent 也是该 API 的公开类。这证明单入口可同时容纳产品操作与 UI，但这些 UI 接口不是一个 React Button 库。不能因导入路径相同就假设它与 Tau 的组件装配相同。

来源：[API 与插件结构](https://github.com/obsidianmd/obsidian-api)、[官方设置示例](https://github.com/obsidianmd/obsidian-sample-plugin/blob/master/src/settings.ts)、[ButtonComponent](https://docs.obsidian.md/Reference/TypeScript%2BAPI/ButtonComponent)。

适合借鉴：明确的注册点，以及随插件卸载回收事件、计时器等资源。其入口设计是可行方案之一，不足以证明所有 React 组件也应塞进同一个根模块。

## Grafana

官方同一个 QueryEditor 示例分别从 @grafana/ui 导入表单组件、从 @grafana/data 导入类型、从 @grafana/runtime 导入存储 hook。这些是作者直接使用的公共包，不只是内部源码组织。React 面板与应用页面也有各自的插件装配协议。

来源：[官方用户存储示例](https://grafana.com/developers/plugin-tools/how-to-guides/add-user-storage)、[面板插件](https://grafana.com/developers/plugin-tools/tutorials/build-a-panel-plugin)、[应用插件](https://grafana.com/developers/plugin-tools/tutorials/build-an-app-plugin)。

共享库在开发时按 npm 版本使用，运行时链接宿主提供的版本；官方文档说明需要宿主 import map 与构建 external 配合，实际运行版本可能不同于开发安装版本。因此分包并没有消除版本约束，单包也不能替代运行时兼容检查。

来源：[依赖共享](https://grafana.com/developers/plugin-tools/key-concepts/npm-dependencies)、[运行时兼容检查](https://grafana.com/developers/plugin-tools/how-to-guides/runtime-checks)。

对 Tau 的推断：核心插件 API 与公共 UI 分开是成熟且贴近 React 场景的方案，但不必照搬 Grafana 的全部包数量或加载器。当前可以先清晰区分“与应用交互”与“构建界面”。

## JupyterLab

官方将应用描述为核心对象与扩展组成；插件声明 requires、optional、provides，宿主按依赖传入服务。UI 组件由独立包复用，ReactWidget 将 React 组件接入 Widget 生命周期；官方教程通过命令打开主区域 Widget，并单独处理恢复。

来源：[扩展与服务模型](https://jupyterlab.readthedocs.io/en/stable/extension/extension_dev.html)、[公共 UI](https://jupyterlab.readthedocs.io/en/stable/extension/ui_components.html)、[React 集成](https://jupyterlab.readthedocs.io/en/stable/extension/virtualdom.html)、[命令与视图教程](https://jupyterlab.readthedocs.io/en/stable/extension/extension_tutorial.html)。

对 Tau 的推断：应用插件和领域扩展可以共享装配机制而保持不同职责。值得借鉴依赖注入、实例与恢复协议，不必让作者一开始面对同样细的包拆分。requires/optional 是服务可用性，不等于安全授权。

## VS Code 与 Figma

VS Code 的普通扩展通过 vscode API 及贡献声明接入；自定义 Webview 是另外的 HTML/JS 上下文，通过消息与扩展交互。Figma 的文档操作环境和 iframe UI 同样分离。因此它们的“核心 API 入口”不等于通用页面组件库。

来源：[VS Code 扩展结构](https://code.visualstudio.com/api/get-started/extension-anatomy)、[Webview API](https://code.visualstudio.com/api/extension-guides/webview)、[Figma 运行模型](https://developers.figma.com/docs/plugins/how-plugins-run/)、[showUI](https://developers.figma.com/docs/plugins/api/properties/figma-showui/)、[Figma 类型包](https://github.com/figma/plugin-typings)。

版本陷阱：微软原 Webview UI Toolkit 仓库已声明于 2025-01-01 弃用，不能只引用 2021 年发布博客，把它当作当前仍维护的官方组件方案。[官方仓库](https://github.com/microsoft/vscode-webview-ui-toolkit)

对 Tau 的推断：可以参考宿主 API 与视图运行边界，但当前高信任 React 扩展无需照搬其整套 UI 通信模式；UI 拆包与运行隔离是两个独立决定。

## Raycast

官方表单示例从 @raycast/api 导入 Form、ActionPanel、Action、showToast，同时可从 @raycast/utils 导入 useForm。说明“产品 API 包含 UI”本身合理，但它提供的是产品约定的界面形态，且并非全部开发工具都在一个包里。[官方 Form 文档](https://developers.raycast.com/api-reference/user-interface/form)

对 Tau 的推断：如果今后提供某种宿主专用声明式页面控件，可以作为插件 API 的一部分；普通 Button、Input、Dialog 是否如此，应按其是否为通用设计系统组件来判断。

## Tau 的候选方案

| 方案                                    | 作者体验                | 需要承担的约束                                                              | 当前判断                        |
| --------------------------------------- | ----------------------- | --------------------------------------------------------------------------- | ------------------------------- |
| 核心 API 与 UI 全部从 @tau/plugins 导入 | 一个入口，发现方便      | 公共命名、UI 依赖、无 DOM 导入、版本与宿主装配需要统一处理；不能仅 export * | 可行，PS-014 当前记录的方向     |
| @tau/plugins 加 @tau/ui                 | 两个明确职责入口        | UI 要成为真正面向作者的公共设计系统，补组件清单、主题、依赖和兼容承诺       | 基于现有 React 架构，更倾向推荐 |
| @tau/plugins 加 @tau/plugins/ui         | 一个 npm 包、两个子入口 | 可分开加载，但仍需管理 UI peer 与条件导出；不等于一条 import                | 若希望单个 SDK 分发，可作为折中 |

第二种方案并不要求作者知道 @tau/editor/api、内部 service registry 或 feature 路径。页面注册、领域扩展定义和服务类型仍可以通过一个产品 SDK 获取；Button 等通用组件从公共 UI 包取得。React 等生态依赖按公开 peer 约定使用。

现有 @tau/ui 是私有工作区包，不能因为已有这个包名就直接宣称外部作者可以稳定使用全部导出。无论选哪种方案，都需要选定公开组件、提供文档、确认 Provider/主题上下文、处理共享 React，并验证发布类型不依赖私有源码。

不建议为了方便同时从两个入口长期重复导出同一组 UI：除非是有退出计划的兼容迁移，否则会制造两种推荐用法，并模糊依赖边界。这是本次研究建议，不是对现有代码的变更。

## 对当前路线的影响

1. C02 的生命周期、命令与存储成果保留，与 UI 分包选择基本无关。
2. C03 之前重新评审 PS-014 中“UI 必须从根入口导出”这一点；作者不需要理解内部实现的目标仍成立。
3. C03 的真正验收是插件能注册页面并正确使用组件、主题和导航，不能只检查是否减少 import 行数。
4. C04 仍复用编辑器扩展协议，但应明确作者使用的是受支持的公共契约；不因其他产品多包就把内部目录全部开放。
5. P6 再完善外部安装、共享依赖、SDK 发布和兼容测试，不因本次调研提前更换加载器或运行载体。

本次倾向推荐核心 API 与公共 UI 两个入口，依据是 Tau 的 React 设计系统和领域扩展需求更接近 Grafana/JupyterLab 的相关部分。是否采用须结合用户对作者体验的偏好再次确认；本文不自动修改既有决策。
