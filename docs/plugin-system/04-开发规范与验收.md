# 插件体系开发规范与验收

本规范补充仓库 AGENTS.md，不替代桌面、数据库和领域包的现行规则。每次提交同时交付行为、验证证据和文档更新。

## 实施规则

当前按 PS-030 流程优先：生产核心和协议必须使用 TS 并由桌面/测试共用；scripts 仅承担构建、启动、打包和验收编排，不发展第二套生命周期、存储或运行协议。QuickJS 与权限隔离验证暂停；后文安全矩阵保留为未来要求，不阻塞当前可信本地流程。具体模块归属见 [26](26-C12-TS主干与可信流程闭环.md)。

1. 先读直接依赖、类与属性上下文，再用小范围 apply_patch 修改。避免按目录批量搬迁。
2. 每个公开能力必须有实际消费者、执行端实现、输入校验和失败语义；不先铺设未接线 SDK。
3. 插件不得依赖应用内部 store、私有路径或任意 IPC；宿主适配器可以调用内部实现，但不能把内部对象交给插件。
4. 导航框架和设计系统保持零业务依赖。框架新增机制必须通用且有测试，既有 Page 或主题约定变更同步桌面 03 指南及必要的 DECISIONS。
5. 服务依赖、用户权限、运行位置分别声明；不通过 TypeScript 的可见性模拟安全边界。
6. 动态注册归属插件作用域，失败按逆序回收，清理幂等，单个清理异常不阻断其他清理。
7. 数据和事件绑定工作区会话与实例代次；运行时校验不能只依赖调用方自律。
8. 原 ID、公共引用和数据版本保持可解释。迁移失败不放行，不能把删除旧数据当作清理完成。
9. 普通属性、日志、错误、构建和测试夹具均不得包含真实凭证。
10. 注释只解释代码事实；方案取舍、裁决日期和过程记录进入文档。
11. 面向作者的产品/领域 API 从 `@tau/plugins` 导入，UI 组件从 `@tau/ui` 导入（PS-015）；不要求作者导入内部编辑器包。宿主适配与内部业务不受此作者约定限制。

新增根导出时检查支持范围、命名冲突、类型声明和加载副作用；禁止一并导出 PluginHost、Node 文件适配器或内部 store。C03/C04 的作者示例只消费上述两个 Tau 入口，保留 C02 无 DOM 回归；P6 检查发布声明不依赖私有 workspace 路径或未发布包。

C04 的验收限定 workbench 本地文档：贡献变化时逐字段检查正文、选区和历史，普通重绘保持 editor 实例，停用后不得以整页卸载掩盖未知节点问题；同时验证旧命令/提交失效、只读、实例隔离与纯 codec 的 Node 装配。生产协作与 external history 尚未接入，不能将此测试结果登记为整项 P5 或协作验收通过。

C05 设置分区必须在真实设置承载中覆盖注册、保存、停用、重新启用与宿主重建；读写失败不能覆盖旧值或伪报成功。额外覆盖迟到请求、工作区隔离、相同局部 ID、单项注销、渲染错误、关态不挂载和 Portal 清理。当前采用即时保存，不将其验收扩大为草稿守卫或跨窗口同步保障。

统一管理的验收还须通过实际管理按钮执行停用/重新启用，确认宿主详情及启用入口常驻；没有设置贡献的插件也可管理，打开管理详情不得自动激活。多个设置分组仅在插件详情内展示，旧 open 精确定位合同必须保留，开发台不得另建一套启停操作。

C06 标准 fetch 必须验证 RequestInit/Response、非 2xx、bodyUsed/clone、Headers、多种 Body 格式、请求/响应流和 signal；通过真实 Electron IPC 验证，不能只有类型和模拟 Response。旧 nodeFetch 函数/选项/IPC 的消费者必须清零，不保留兼容层。测试应区分本地网络、真实 Electron 与真实账号联调，未运行真实账号不得宣称远端已验证。

## 验证矩阵

本表是最终需覆盖的范围，不是已有测试覆盖声明。近期完成定义以 [16 的 G1 清单](16-框架全局验收与独立插件闭环.md) 为准：G0 内部原型、G1 独立开发闭环、G2 桌面框架首版、G3 领域能力分别登记。独立进程不等于独立包，registerTrusted 不等于安装授权，unregister 不等于卸载，重新启用不等于代码重载。

C07 必须使用仓库外项目、实际 SDK 包产物和真实 Electron 加载，证明类型闭包、React 单例、UI/CSS/资源解析成立。C08 覆盖异步挂起、旧代结果、持久启用意图、重启/切库和移除包；C09 区分构建失败、替换失败与不可恢复副作用，检查完整产物、资源回收和模块缓存。每项保留对应复现命令，不以 mock、源码导入或历史 200 项测试替代新增链路验收。

| 类别       | 必须验证的行为                                                       | 所属阶段            |
| ---------- | -------------------------------------------------------------------- | ------------------- |
| 加载与身份 | 无效 manifest、冲突 ID、非法入口和不兼容版本被拒绝；受限端验证 owner | C07/G1；隔离身份 G2 |
| 权限       | 未声明、未授权、撤销后、间接命令与网络旁路不能越权                   | G2 对外开放前       |
| 生命周期   | 激活失败回收、重复停用、超时、旧回调、监听器残留                     | P2 起               |
| 工作区     | A 切 B、关闭重开同名库、切换期间迟到写入、窗口重复任务               | P3                  |
| 数据       | 幂等、事务回滚、游标提交、分页、引用保留、迁移失败和恢复             | P3 起               |
| 页面       | 双注册表一致、实例退出、历史恢复、未保存守卫、设置卸载               | P4                  |
| 编辑器     | 只读、撤销重做、协作、序列化、未知节点保真                           | P5                  |
| 数据库产品 | 字段与视图缺失、计算错误、查询边界、操作历史                         | P5                  |
| 白板       | 多实例、手势取消、隐藏与销毁、撤销重做、未知元素                     | P5                  |
| 产物与重载 | 产物不完整、模块缓存、CSS 回收、资源定位、重载失败                   | P6                  |

安全测试必须包含直接绕过 SDK 的尝试，不能只测试包装方法返回拒绝。资源泄漏和重载测试检查监听器、任务及注册计数，不以“界面还能点”为通过依据。性能指标在对应阶段开始前记录基线和环境，不能凭空指定通用毫秒目标。

## 命令与执行记录

以下是仓库已有命令或调用方式，执行时按变更范围选择，记录实际退出码与范围：

```sh
git diff --check
pnpm exec prettier --check "docs/plugin-system/*.md"
pnpm check
pnpm --filter desktop exec vitest run <本次相关测试路径>
pnpm --filter desktop build
node scripts/check-database-boundaries.mjs
node scripts/check-whiteboard-boundaries.mjs
```

测试路径必须先从代码中确定，尖括号仅表示调用模板，不能原样执行。修改共享包时检查实际 package.json，追加该包及受影响端的类型、行为和构建命令，不假设所有包都有同名脚本。

桌面运行代码变更须完成类型检查、相关行为测试、构建和必要结构检查。完整 desktop build 包括原生打包步骤，环境或签名缺失导致未通过时必须准确说明，不能把仅前端构建写成完整桌面构建成功。必需门禁未完成不得标为可交付实现。

schema 变化另执行 `pnpm db:schema:build`、`pnpm db:schema:check`，必要时 `pnpm db:schema:prepare`，同步数量断言和内置数据库字段文档，并运行字段对账测试。迁移涉及共享模型时必须验证受影响客户端的读取和拒绝策略。

纯文档提交检查格式、链接、引用路径、状态一致性与 diff；不为文档运行无关业务构建，不把未执行的测试填成通过。Agent 不做视觉走查或截图验证，视觉验收由用户进行，记录不阻断架构清理的外观问题。

## 提交流程

1. 检查工作区和已暂存内容，只纳入本工作单元的文件；保留用户其他修改。
2. 调查后定义本提交的可用行为、验证范围、恢复方式和消费者清理边界。
3. 实现并完成必需检查；新发现的阻断失败先修复，不用下一次提交补救。
4. 同步 README 当前状态、阶段计划、执行日志；行为变化更新现状和相关指南，取舍变化更新决策。
5. 检查最终 diff，使用项目 conventional commit 风格提交，不跳过 hooks，不自动推送。
6. 核实提交和提交后状态，向用户报告提交 ID、结果、验证限制与紧接着的下一步。

执行日志在同一提交中用唯一单元 ID（如 C02）和提交主题定位，不填写自身尚未生成的 hash。后续提交可回填前一条 hash；不为补自身 hash 无限 amend。`git log -- docs/plugin-system` 可追溯实际提交。

## 恢复与数据保护

无持久化变化的提交应能通过 revert 恢复行为；持久化变化必须单独说明恢复前提、备份位置类别、兼容读写范围与必要的前向修复。不要承诺所有 schema 变化都能靠代码回退恢复。

临时适配若确有必要，应记录消费者、退出条件和删除单元；每一步只保留一条有效写入链，不双写两套事实源。消费者清零后同批删除旧实现，不能用永久兼容层掩盖迁移未完成。
