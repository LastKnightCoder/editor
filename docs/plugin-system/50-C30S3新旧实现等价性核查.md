# C30 S3新旧实现等价性核查

本记录与最小协议分开维护。用户确认最小协议后，已执行源码对照、隔离目标实测和接口对齐。没有修改用户同步配置或既有笔记对象。

目标保持S3插件适配，不将它替换成AliOSS插件，也不要求用户为插件声明能力。这里的“旧实现”指当前已有桌面与CLI代码，“新实现”指相邻tau-plugin-s3项目的开发版后台，不是已经发布的插件。

## 1. 现有调用链

数据库同步调用publishSnapshot，后者调用createFileIfAbsent创建后继记录。返回false或抛异常时，会读取该记录并核验commitId及数据库/会话对象名；不能仅根据上传错误判断提交结果。普通版本指针上传失败不撤销已提交的后继记录。

旧桌面S3调用链：

1. src/utils/sync/S3SyncProvider.ts的createFileIfAbsent转到uploadFile(..., true)。
2. uploadFile经commands/s3.ts把ifNoneMatch:"*"传入主进程。
3. src-electron/main/modules/s3.ts构造PutObjectCommand，传入IfNoneMatch。
4. 主进程失败抛出，Provider捕获并返回false；随后由publishSnapshot读取后继对象确认结果。

旧CLI的createFileIfAbsent同样使用PutObjectCommand的IfNoneMatch:"*"，但失败直接抛异常，交同一publishSnapshot处理。

因此“旧S3代码中没有条件写入，是新插件增加的”不符合当前源码；但这也不能证明旧S3在相同目标上的完整运行结果，因为此前没有执行其原始链路的对照测试。

## 2. 对齐前已确认的新旧差异（历史原型）

| 项目          | 旧桌面S3                              | 旧CLI S3                         | 新S3后台                                                               |
| ------------- | ------------------------------------- | -------------------------------- | ---------------------------------------------------------------------- |
| 上传主体      | Uint8Array转Buffer                    | Uint8Array                       | ReadableStream转Node流，显式ContentLength                              |
| 条件创建请求  | IfNoneMatch:"*"                       | IfNoneMatch:"*"                  | create-only映射IfNoneMatch:"*"                                         |
| 上传失败      | Provider捕获后false                   | 抛异常                           | 映射SyncStorageError，条件冲突412返回already-exists                    |
| 读取/存在检查 | 拼URL后fetch GET/HEAD，没有显式签名头 | SDK GetObject/HeadObject签名请求 | SDK签名请求                                                            |
| SDK重试       | 沿用SDK默认                           | 沿用SDK默认                      | 显式maxAttempts=1                                                      |
| 校验和策略    | 沿用SDK默认                           | 沿用SDK默认                      | requestChecksumCalculation/responseChecksumValidation显式WHEN_REQUIRED |
| 列举          | 主进程listObjects聚合后返回           | 当前快照接口不使用               | 向宿主暴露cursor/limit                                                 |
| 删除          | 仅占位返回false，无当前同步调用       | 当前快照接口不使用               | 实现DeleteObject，原方案把它列为必需                                   |
| 取消/进度     | 原方法没有对应参数                    | 原方法没有对应参数               | 每操作signal与流进度                                                   |
| 路径          | 当前Provider使用replaceAll规范前缀    | trim首尾斜线                     | trim前缀并增加对象路径校验                                             |

新后台协议中的流、分页、删除、重试和错误类型都是新增设计，不能称为已经等价迁移。这些差异先记录，按49最小协议修订后再决定代码调整；不能以新实现的额外要求判旧服务不合格。

S3Client共同接收region、endpoint和凭证，urlStyle影响forcePathStyle。对照测试还需固定SDK实际版本、有效请求头、请求体字节与同一隔离前缀，不能仅比较函数名称。

此前协议调研时核对本机已安装包：旧桌面与CLI均为@aws-sdk/client-s3 3.948.0，新原型为3.922.0。当时未修改依赖；本轮对齐已将作者项目固定为3.948.0，见第6节。

## 4. 核查顺序

1. 固定同一配置、同一隔离目标，分别运行旧桌面原始链路、旧CLI链路与修订后的插件链路。
2. 对照普通上传、条件创建、对象已存在、响应丢失后的读取确认、最终提交结果；同时记录有效SDK版本和经过脱敏的请求差异。
3. 如果只有新实现失败，定位并消除新增差异，不通过换后端回避。
4. 如果旧实现也失败，记录可复现的现有兼容性问题，单独讨论修复；不扩大最小协议、不要求用户填写能力表、不自动改用AliOSS。
5. 如果旧实现返回成功而新实现拒绝，核对成功判断是否一致及后继记录实际内容；先给出证据，不擅自改变冲突规则。

本记录不预设核查结论，也不以“更换测试服务商”作为继续定义协议的前提。

## 6. 已对齐的实现与保留差异

- SDK现只提供uploadFile/downloadFile/fileExists/listFiles/createFileIfAbsent；后台注册为id/name/create(config)，加载器直接返回提供方。删除旧stream/open/stat/write协议、额外错误枚举和snapshotStorage适配层，不保留双协议。
- S3以旧桌面为本轮迁移基线：Buffer请求体、SDK 3.948.0、默认重试与默认校验和；上传/列举走SDK，GET/HEAD沿用桌面现有URL请求。条件创建仍返回boolean，失败后由原publishSnapshot确认。
- 列表在插件内部聚合，字段沿用name/path/size/lastModified。旧桌面列举失败返回空数组的行为暂保留，作为既有错误策略问题单独处理。
- 旧CLI保持现有签名读取源码，尚未改用新插件。旧资源同步S3 Adapter也仍在主进程使用签名读取；不能声称本轮已统一全部消费者，更不能静默把这些路径改成匿名读取。
- 对齐后真实请求对照比较了去除隔离前缀后的方法、路径、条件头、校验和头名称、响应状态序列；新插件与旧桌面一致。没有记录认证头、凭据或用户内容，不声称每个请求的签名/随机提交ID完全相同。

## 8. CLI接入和旧实现退役前的行为决策

执行结果：用户已确认统一签名读取。S3插件0.1.1已改为SDK GetObject/HeadObject，CLI与桌面共享该产物；旧同步Provider/Adapter已删除。以下保留当时的决策依据，不代表仍在等待确认。历史对照脚本随旧源码退役，需复跑原始三路对照时使用提交 `3cbec9ede`；当前equivalence.test.ts仅保留真实插件与既有发布协议的行为回归，不复制旧实现。

再次核对源码：旧桌面数据库S3 Provider和当前作者插件的downloadFile/fileExists使用未签名fetch；CLI的S3 Provider使用GetObjectCommand/HeadObjectCommand，桌面资源S3Adapter也使用GetObjectCommand。直接让这些消费者使用当前插件会使原来可用的私有桶读取退化。此前本地HTTP闭环验收只验证接线，不能证明私有桶读取等价；上一轮资源同步接入也受此差异影响。

建议在唯一S3插件中统一SDK签名读取，保留五方法、对象命名、配置字段、条件创建和快照发布/恢复算法。不按调用端分支、不加入匿名模式开关、不通过失败后匿名重试掩盖认证错误。这会改变旧桌面数据库读取的请求认证方式，因此按既定架构约定先讨论，尚未执行。它与服务端条件写入兼容问题相互独立，不要求更换存储服务。
