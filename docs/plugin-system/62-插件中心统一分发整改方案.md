# 插件中心统一分发整改方案（待确认，不实施）

> **方案已撤回，以下保留为调查记录，不得据此实施。** 用户澄清：博客沿用发布时收集插件并上传站点的既有流程；移动端与浏览器扩展不支持通用插件。本稿将代码中的固定渲染装配扩大为建设跨端插件运行机制，超出了任务范围。sandbox/iframe、跨端插件中心及工作区插件依赖同步均不是本次已批准需求，不能作为清理桌面随包安装的前置条件。

## 修正后的任务边界

- 桌面：正式插件从插件中心安装，删除默认随包复制、自动安装及相关产品构建路径。
- 博客：保持发布时收集已安装插件的准确版本、复制main.js/CSS、上传站点并加载的流程；不改为在线访问插件中心。
- 移动端与浏览器扩展：不新增插件安装、管理或动态执行机制。现有代码通过portablePluginBuild静态编入editor:true包，是固定渲染依赖，不能据此宣称产品已支持插件。
- 这条固定渲染依赖目前复用了plugins目录，属于需要单独解耦的遗留实现。先提出保持现有渲染效果的最小处理方式，再明确其归属；不得偷偷改为另一份业务插件随包目录，也不得擅自建设跨端插件系统。
- 原M0至M4计划撤回。本轮没有改运行代码。

## 结论与硬边界

插件中心应是正式插件版本的唯一发布和获取来源。客户端安装包不携带具体插件、不自动给用户安装插件，主仓库不再作为生产插件产物仓库。

同时保留现有同源渲染原则：作者仍提交main.js与可选CSS，编辑器扩展、Markdown codec和预览组件继续复用同一份实现。不引入作者另写render.js，不用静态HTML或图片替代现有交互效果，不把插件代码改名为“内置渲染器”继续装进客户端。

博客发布产物必须保留它实际使用的插件版本快照。这是文章的运行依赖，不是Tau客户端随包安装。若连博客站点都不允许保存插件代码、必须每次在线访问中心，就无法同时保证旧文章版本稳定与中心不可用时的访问；不推荐这种解释。

目前桌面、博客有清晰的整改路径，移动端需要运行时包来源和缓存，浏览器扩展有额外的执行上下文约束，必须先做可行性验证。不能现在承诺把Vite导入换成fetch就能保持所有端效果。

## 推荐的目标链路

### 中心发布与客户端缓存

正式流程保持：作者ZIP → 提交审核 → 批准的不可变版本 → 中心下载 → 客户端本地安装/缓存 → 装配。

桌面已有目录、下载校验、暂存更新、重启生效、上一版恢复、启用意图可以复用。资源缓存不随用户每次打开文档重新下载，不能让内容渲染以中心实时可用为前提。移动端与扩展只先接入内容渲染所需的安装子集，不照搬桌面的同步、AI、MCP等完整插件服务。

本轮“全部走中心”针对正式分发与获取；本地目录仍是安装后的落盘位置，不是另一个分发源。开发调试能力不能借此恢复生产预装。现有用户手工安装的包不擅自删除；是否关闭生产UI的手工ZIP入口，需在安装入口方案中明确，不能夹带成新的安全机制。

### 固定版本与内容依赖

现有正文节点没有普遍携带pluginId/version；同一个节点名也不能推导出处。移动端不能只看到custom-block就猜一个包或下载最新版本。

需要一个随工作区内容快照传递的内容依赖清单，复用现有PluginRenderSelection中的身份、版本、mainHash、stylesHash、nodeTypes，并补充中心releaseId/ZIP摘要。它与对应内容快照一致提交；不在这里创建第二套同步引擎。具体落点及同步信封变更在M1冻结，本轮不改表、不改节点格式。

首期继续“一份工作区内容快照对应一组明确版本”，不假设当前全局ContentPluginRegistry能够同时加载同一插件的多个版本。版本冲突应停在更新/导入确认，不随机选latest；若以后需要逐文档多版本，另做架构设计。

功能插件的启停和具体设备的凭据不跨端同步。内容依赖也不等于授权启用全部插件功能：移动端、扩展和博客只装配该包已有的静态内容贡献，不调用create/activate。用户明确停用渲染时不能偷偷重新启用；原始节点和内容必须保留。

### 博客：保持现有发布快照

1. 从当前已装且可发布的内容插件获得准确版本和摘要。
2. 按节点依赖复制同一包中的main.js/CSS及现有styleSources结果。
3. PublishedPluginRender继续携带runtimeVersion、manifest、入口和节点类型。
4. 站点启动先验摘要、注册扩展/codec和CSS，再挂载现有Editor。

不更改预编译模板为每个插件重新打包；不生成另一份作者渲染入口。发布后中心升级、下架或暂时不可用，不应使已发布文章改用另一版本。缺少依赖时发布失败并保留旧站点，不能生成看似成功的残缺页面。

“全部中心”要求历史使用中的包先有可匹配的审核版本：按ID、版本及代码/CSS摘要核对后关联来源。不同字节不能因版本号相同就认作同一个包；未批准的历史版本不能擅自上传审批、替换或删除，先列出清单处理。已安装且可正常渲染的本地文件在升级过程中保留。

### 移动端：改来源，保留渲染实现

使用中心批准版本建立本地包缓存，由工作区依赖清单选择精确版本，在现有初始化屏障完成校验、装配和CSS加载之后再打开内容。

复用ContentPluginRegistry、createPluginMarkdownProcessor、共享模块映射及source-editor-host；替换virtual:tau-editor-plugins来源，不重写custom-block、不分叉PreviewWithEditor、不复制Markdown转换。

当前manifest.platform为desktop，且桌面minAppVersion为0.59.0、移动应用版本为0.1.0；现有便携编译并未解决这些跨端版本语义。M1必须明确静态内容运行协议与各客户端版本的兼容判断，不能拿移动应用版本套用桌面版本过滤，也不能把desktop简单改成all就声称所有服务可用。

Tauri当前csp:null只是运行时现状，不作为今后分发或上架能力保证。先按实际交付的移动平台验证下载、落盘、重启恢复、离线和渲染效果。

### 浏览器扩展：先做决定性验证

现有扩展把插件代码编为本地JS模块，正是因此能避开运行时eval。下载main.js后调用evaluatePluginPackage会走new Function，不能直接放进当前扩展页面执行。

Chrome官方说明MV3扩展页面的远程JS/WASM执行受限制，另列sandboxed iframe作为特定隔离执行场景。因此推荐先验证：扩展仅携带通用Editor运行时和桥接层；中心包进入本地缓存后，在声明的sandboxed iframe中装配同一份EditorKit、插件main.js/CSS与共享模块。宿主只桥接文档数据、必要编辑事件、主题/资源和现有编译服务，插件代码不进入有扩展权限的sidepanel上下文。

必须验证完整编辑器承载，不能只把自定义块套进iframe后忽略Slate选择、输入法、Portal、拖拽和撤销行为。是否需要完整Editor进入frame、桥接范围以及审核可接受性，均为M0结论项，不是已批准的生产架构。官方允许某类sandbox用法不等于任意插件市场自动获准上架。

若这条路线不能同时满足当前交互/离线要求与目标发布渠道，则“零业务插件随包、任意中心JS动态执行、完全保留原扩展承载方式”不能同时成立。届时必须返回讨论；不能悄悄改成内置渲染子集、远端截图、云端HTML或要求作者另写render.js。Firefox等目标渠道若要支持，另按其规则验证，不由Chrome结果推断。

## 不退化的验收标准

同一文档数据、插件字节、主题、字体和容器尺寸作为前后比较条件；各端使用相同的编辑器扩展和codec。验收包括React交互、PreviewWithEditor、样式源码编译、Markdown往返、嵌套节点，以及当前支持的编辑、复制粘贴、输入法、选择、撤销和资源加载。Agent负责结构/行为测试、类型检查和构建；视觉对照由用户完成。

中心断网或版本下架不影响已有有效缓存与已发布博客。故障占位仅用于保护原始数据，不能算“渲染效果保持”的验收通过；缺少包时不能规范化成普通段落后回写，破坏原节点。

首次离线且从未下载所需包，无法凭空还原插件渲染。对已有用户必须先准备依赖缓存再切换；移动/扩展旧版本只含编译模块而未保存原包，需显式安排一个有限的准备/迁移阶段，或首次在线完成中心安装。没有缓存覆盖证据前不删除旧装配，不能把中间状态作为最终交付；也不把旧插件伪装成“迁移资源”永久留在新安装包。

## 阶段与退出条件

| 阶段              | 达成目标                                                                     | 退出条件                                                           |
| ----------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| M0 事实与可行性   | 核对中心批准版本和历史依赖，验证扩展sandbox路线与移动运行时                  | 已有渲染/交互可复用；无法满足时先讨论，不能进入删除阶段            |
| M1 固定最小契约   | 定稿中心版本定位、内容依赖清单、跨端兼容与缓存事务                           | 锁定版本、不同步凭据、失败保留旧内容；不要求作者双入口             |
| M2 桌面与博客闭环 | 中心安装包接管桌面内容装配及博客发布                                         | 中心安装→启用→编辑→发布→站点加载、回滚、离线均通过；无预装也可运行 |
| M3 移动与扩展替换 | 用中心包/缓存替换构建期插件目录，完成必要迁移                                | 同源渲染、编辑、Markdown、资源、离线恢复和用户视觉验收通过         |
| M4 统一退役       | 删除产品plugins清单/快照、复制脚本、自动安装、便携编译注入及主题示例默认装配 | 清洁构建无业务插件包，生产引用清零；测试夹具独立且不进入发行包     |

M2/M3可以各自开发验证，但最终删除随包目录必须等待所有端替代路径完成。准备版不宣称“全部走中心”已完成；最终版本不长期保留双路径。各阶段只做达到退出条件所需内容，不顺带重构整个插件系统或codec架构。
