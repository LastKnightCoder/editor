## 建议实施顺序

1. 打通一个最小第三方白板元素从公开 SDK → ZIP → 固定插件目录 → 正式白板的完整路径；验证工具创建、属性编辑、撤销、复制和存档。使用临时样本，不增加产品常驻示例。
2. 补齐缩放连接、元信息、手绘与缩略图的通用贡献，以真实火柴人作为验收样本；复用白板现有内核和公开原语。
3. 迁移完整人物实现与测试，保持姿态/配色/翻转/文本/手绘/缩略图/导出一致；接入默认插件分发清单，只验证新格式保存与缺包后重新安装恢复，不验证旧格式兼容。
4. 消费者清零后删除 StickmanPlugin、createStickmanExtension 和各处专用判断；更新 SDK/模板文档并从独立仓库重新打包验收。

默认随应用安装可以沿用 custom-block 的分发方式，但「默认插件」只决定安装来源与默认启用意图，不赋予一套私有白板 API。对第三方同样暴露实际使用的通用能力。

## 仓库组织建议

推荐每个正式插件独立仓库，但暂不把全部插件改为 submodule。独立仓库让作者只能消费公开 SDK，独立构建/发布/版本回退；应用端应以插件 ID、版本、包摘要固定分发产物，不能依赖开发者目录或始终拉最新 main。

submodule 只把外部仓库固定到一个 Git 提交，不负责同步作者模板。它适合必须在一个检出中同时编辑宿主与插件的开发流程；代价是递归克隆、子仓库先提交推送、再提交父仓库指针，以及 CI/权限/新 agent 上手的复杂度。先用火柴人独立仓库验证，再按实际开发频率决定是否加成可选开发入口。现有 distribution.json 目前指向 plugins 下的源码构建目录，不能直接改成外部仓库而假定应用构建不受影响。

模板更新分三类：SDK 通过 pnpm 升级并提交锁文件；通用构建脚本在多个插件重复维护成为实际问题后抽成版本化 npm 工具；模板文档/配置更新通过记录基线后的差异审查或 PR 合入。不能覆盖 src、manifest、README、SKILL.md 和插件自有配置，不自动合并整个模板 main。

GitHub 从模板新建仓库通常从单个新提交开始，没有继承模板历史，不能把它当成 fork 自动合并。当前研究工程保留模板克隆历史只是为了可追溯，不代表已经建立自动更新机制。

参考：[GitHub 模板仓库](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-repository-from-a-template)、[Git submodule](https://git-scm.com/docs/git-submodule)。
