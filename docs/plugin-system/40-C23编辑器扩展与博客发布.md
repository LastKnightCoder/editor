## 兼容与边界

- 发布上下文来自当前启动快照；主进程重新校验包的 ID、版本、JS 与 CSS 摘要。工作区切换不改变该快照，磁盘包改变后需要重启，不用新代码替代当前正在展示的实现。
- 发布 worker 从请求快照装配插件定义和 codec，用于发布搜索内容等转换；不调用 render/create/activate。博客统一加载同一 CJS 入口，React/UI/SDK 由宿主共享；不运行桌面 create/activate。模块顶层必须无环境副作用，codec 为纯转换函数。
- 内容链接悬浮预览读取目标页的依赖清单，按目标页面地址解析资源，独立构造预览 kit，不替换当前页插件。取消或关闭时释放临时样式。
- JS/CSS 需要自包含；通过 styleSources 声明的动态 Tailwind 源码在发布时编译，任意附件目录与移动端用户安装暂不支持。Skill 首版只有随 main.js 打包的单文档。对象存储仍沿用已有逐文件上传流程，不承诺整站原子切换。
- 主进程在 plugin-local 初始化时读取 .editor-enabled.json，从已启用包求值定义并注册 codec；database 依赖 plugin-local，避免先开库索引再装配插件。索引线程通过 workerData 接收同一份包快照，发布线程从发布请求接收包快照。函数及闭包留在原包中，不做函数字符串化，也没有第二份 codec 入口；headless-codecs.ts 已删除。
- 同步了 master 已有 GFM 任务列表修复的过期 Markdown 快照，仅将普通列表改为勾选项及其正确文本位置，没有修改列表转换逻辑。博客行为测试禁用 Tailwind 样式生成插件，生产 Vite 构建仍真实生成 CSS。

## custom-block 维护与本地验收

1. `pnpm --filter @tau/plugin-custom-block build` 构建普通插件包，ZIP 在 `plugins/custom-block/dist/tau.custom-block-1.0.0.zip`。`node scripts/plugins/build-distribution.mjs` 按 plugins/distribution.json 构建并复制分发包到桌面 build/bundled-plugins；桌面 predev/prebuild 自动执行。移动端和扩展端的 Vite 插件消费同一清单与同一产物，无宿主专用 custom-block 注册。
2. 完整重启开发客户端，首次启动安装到 `~/.editor/plugins/tau.custom-block`，无偏好时默认启用。在「插件 → 已安装」查看状态，之后启停/升级均重启生效。首次安装记录在插件根目录 .bundled-installed.json，升级不覆盖用户的插件版本，卸载后不会被下次启动自动恢复。
3. 打开已有 custom-block 文档，验证源码编辑、预览、全屏、主题切换、拖动与段首退格。节点结构和 Markdown 围栏不变，没有数据转换。
4. Skill 页的「插件」分组包含自定义组件块；AI 标识 `tau.custom-block:authoring`，支持自动/手动/停用/复制与读取 SKILL.md。插件停用并重启后从列表退出，个人偏好保留。
5. 使用本次构建的博客模板发布含自定义组件的文章，验证浏览器交互；旧模板缺少 plugin-runtime.json 时会要求更新，不生成缺块页面。HTML/EPUB 等静态导出沿用原来的源码展示，不等同于交互博客。

真实隐藏 Electron 行为验收同时覆盖通用计数样本与实际 custom-block 插件，验证 DOM 一致、交互 3→4、动态 Tailwind 13px、作者目录删除后网站独立运行。人工视觉验收由用户负责。

同一验收还在主进程和真实 index-content.worker 中读取包并执行 codec。当时的扩展边界扫描禁止恢复旧扩展目录、固定 headless codec 表、应用对具体插件的包依赖和生产源码导入；该独立扫描已于 2026-10-20 退役，此处仅保留历史验收范围。

编辑器启用意图的权威存储为 ~/.editor/plugins/.editor-enabled.json，窗口只保留显示镜像，切库不改变它。普通页面插件仍使用原偏好。开发中的旧编辑器 localStorage 意图不作为后台启动事实源；此调整发生于客户端功能正式发版前，不建立长期双源兼容。

跨端分发包装是构建工具对 main.js 的机械封装，以满足浏览器扩展不能 eval 外部包的约束；不是作者第二个渲染实现。增加默认插件只修改产品分发清单，不修改任何宿主 EditorKit。移动端/扩展端没有新增下载管理 UI。

独立作者验收在仓库外安装生成的 npm 压缩包，分别构建通用计数样本与实际 custom-block 源码；后者只依赖公开 SDK 和普通 npm 包，不引用 workspace 编辑器实现。构建脚本使用 .md 的 text loader 将 Skill 正文打入 main.js。

## 代码质量与职责边界

### 本地包 Skill 接线修复

本地包登记阶段只有 manifest 元信息，原包装器直到 activate 内才取到实际定义，导致宿主注册静态 skills 时看到空列表。现由宿主内部 registerDeferred 接收延迟定义解析器，在同一个激活期限与取消信号下先解析定义，再统一创建实例、登记 Skill、执行 activate；加载器只处理包读取与 CSS，不另写技能注册旁路。作者 API、SDK 与 ZIP 格式均不变。

验收覆盖 registerPluginPackage 的普通包和编辑器包，检查列表/AI 读取、停用和再次启用；真实 Electron 验收使用实际 custom-block 产物，确认插件 Skill 进入 useSkillStore。之前直接向宿主登记定义的测试不能替代此包加载链路验收。

修复后 SDK 55 项、桌面插件相关 107 项测试及两端类型检查通过，真实 Electron 验收包含「实际 custom-block 包启用后 Skill 进入用户技能列表」。本次是客户端宿主修复，不需要重新安装插件或发布 npm SDK；完整重启客户端后生效。

### 通用运行时

- ContentPluginRegistry 是唯一的贡献聚合实现，统一校验并原子替换只读快照；各端自行拥有实例，SDK 不保存某个应用的全局注册表。
- 桌面实例位于 shared/content-plugins.ts，主进程、窗口、工作线程各有自己的模块实例，由启动快照传入数据。通用 Markdown、HTML 与编辑器服务不导入 app/plugins 状态，不再通过 typeof document 选择实现。
- app/plugins/content-plugin-state 仅持有窗口的包信息、错误与发布上下文；定义、扩展、codec 均委托公共注册表，不维护平行数组。
- 四端 Markdown 都使用 createPluginMarkdownProcessor，统一处理快照变化与转换器缓存。各端保留自己的内置 codec 清单，避免把不同业务能力强行混合。
- 移动端/扩展端共用 createPortableContentRuntime，各端只提供包加载入口；并发启动去重、失败回滚及重试在同一处实现。
- 作者 API、包格式、启停规则不变。架构边界脚本禁止通用转换服务反向依赖渲染层插件状态；测试覆盖快照隔离、缓存更新、启动幂等和失败回滚。
