# 在线视频提供方插件化

调研与方案日期：2026-10-19。范围为桌面端 Bilibili / YouTube 在线视频的解析、取流、缓存、播放与账号设置，以及编辑器、白板、视频笔记、Vibe Learning 四类消费者。用户确认：两个平台完整迁出为独立插件；第一期不做媒体库浏览（browse）与 HLS；yt-dlp 作为宿主服务开放；移动端、博客、浏览器扩展继续只做降级展示。

### 与旧实现的行为差异

- 原来的「Bilibili」「YouTube」入口改由插件生成：每个启用的插件一项，名称取插件名，自建服务等其他来源同样各占一项；插件未启用时入口不出现。链接属于其他插件时提示改用对应入口。「网络地址」插入不再拦截视频网站链接（插件识别需要异步调用）。
- 界面文案不出现「视频插件」「视频网站」等统称：设置「账号与连接」的分组与缓存筛选叫「在线视频」，移动端和博客的降级提示为「该视频请在桌面端查看」。
- B 站扫码登录的二维码改为插件内本地生成：旧实现把含 `qrcode_key` 的登录链接交给第三方服务 `api.qrserver.com` 渲染，持有该 key 即可轮询换取登录 Cookie。
- B 站解析去掉了网页 HTML 兜底，只走 view 接口；番剧 / 课程仍不支持（旧实现同样不支持）。两份取流实现合并为插件一份，DASH 流 HEAD 探测时尝试备用地址。
- YouTube 由「分别选视频流和音频流」改为按分辨率选清晰度（每档取帧率、码率最高的视频流，搭配最高码率音频），兼容历史数据中格式保存为对象或 ID 字符串。
- 视频笔记转写在视频未缓存时会先下载（旧实现直接失败）。旧平台缓存在升级后清除，已添加的视频首次播放会重新下载一次。

## 结论

沿用 TTS / 图片的领域提供方模式，新增 `context.video.register`。与前两者不同，视频体积大且必须交给 `<video>`，因此插件**不传字节、不返回可播地址**，只返回「播放源描述」（流地址 + 请求头，或交给宿主解析器的页面地址），下载、合并、缓存与播放统一由宿主完成。插件只负责平台知识：识别链接、查询标题与可选清晰度、给出真实流地址与鉴权请求头、账号表单。

插件 ID 直接取存量来源类型 `bilibili` / `youtube`（同摘录 C18 的 `weread` 先例），文档、白板、视频笔记与学习资源中已保存的 `metaInfo.type` / `source_type` 即提供方身份，平台字段由插件解释，**不做数据升级**。只有设置里的 `integration.bilibili/youtube` 需要一次性迁入插件配置。

## 拆分前的实现与耦合

| 环节         | Bilibili                                                             | YouTube                                |
| ------------ | -------------------------------------------------------------------- | -------------------------------------- |
| 链接识别     | `utils/bilibili/parser.ts`（BV/av、番剧、b23 短链）                  | `utils/youtube/parser.ts`，仅判断 host |
| 信息与清晰度 | 渲染进程经 `desktopFetch` 调 view 接口，网页兜底；`getQualityInfo`   | 主进程 `YtDlpService.fetchVideoInfo`   |
| 取流         | DASH 音视频分离；渲染端 `api.ts:341` 与主进程索引队列 `:1430` 各一份 | yt-dlp 选格式                          |
| 下载缓存     | 主进程 `bilibili-cache.ts` 带 Referer 分流下载 + ffmpeg 合并         | 主进程 `youtube-cache.ts` 调 yt-dlp    |
| 账号         | 设置「集成」扫码 / SESSDATA                                          | 设置「集成」代理                       |

`src/` 相对 `apps/desktop/`。两个平台均为「先缓存成本地 mp4 再播放」，不在线流式播放。平台专属代码约 6100 行，平台分支约 53 处分布在 23 个文件；desktop 与 shared 各有一套重复取源 hook；字幕接口已实现但无调用方。

消费者：编辑器视频节点（`editor-providers/videoProviders.tsx`、`App.tsx` 注入）、白板视频元素与选择器、项目视频笔记（取源、转写）、Vibe Learning（添加资源、预览、主进程索引队列）、设置（集成、缓存）。移动端、博客、浏览器扩展只按 `metaInfo.type` 显示「请在桌面端查看」。

## 接口

```ts
/** 插件私有的视频引用：写入文档与数据库，必须可长期保存，不放会过期的直链。 */
export type VideoRef = { readonly [key: string]: JsonValue };

export interface VideoStream {
  url: string;
  /** 下载时附带的请求头（Referer、Cookie 等），只在宿主主进程使用。 */
  headers?: Record<string, string>;
}

export type VideoPlaybackSource =
  | { kind: "file"; stream: VideoStream }
  | { kind: "split"; video: VideoStream; audio: VideoStream }
  | { kind: "extract"; url: string; videoFormat?: string; audioFormat?: string; proxy?: string };

export interface VideoVariant {
  label: string;
  hint?: string;
  ref: VideoRef;
}

export interface ResolvedVideo {
  title: string;
  cover?: string;
  /** 至少一项；选中项的 ref 原样保存。 */
  variants: readonly VideoVariant[];
  defaultVariant?: number;
}

export interface VideoInstance {
  /** 同步识别链接，用于自动选择提供方与「网络地址」插入拦截。 */
  matches(url: string): boolean;
  resolve(url: string, signal: AbortSignal): Promise<ResolvedVideo>;
  /** 稳定缓存身份（含清晰度），已缓存时宿主不再调用 getPlayback，离线可播。 */
  cacheKey(ref: VideoRef): string;
  getPlayback(ref: VideoRef, signal: AbortSignal): Promise<VideoPlaybackSource>;
}

export interface VideoProviderDefinition {
  id: string;
  name: string;
  create(config: JsonValue): VideoInstance;
}
```

- **播放源描述而非字节**：`file` 单流、`split` 音视频分离（宿主下载后 ffmpeg 无损合并）、`extract` 交给宿主 yt-dlp。请求头只在主进程下载时使用，不进入文档、缓存索引与日志。
- **清晰度即引用**：每个可选项自带完整 `ref`，宿主不理解清晰度语义，也不定义公共的 quality 字段，存量 B 站 `quality`、YouTube `videoStream/audioStream` 的布局原样保留。
- **保留键**：宿主在元数据中占用 `type`（提供方 ID）、`title`、`thumbnail`，传给插件的 `ref` 去掉这三个键；插件的引用不得使用它们。
- **宿主统一 UI**：选择弹窗、取源进度、失败提示由宿主按 `resolve` 结果渲染，插件不提供选择 UI；账号流程（如 B 站扫码）走 `settings.register({ target: "video" })`，表单收到 `videoConfig: { value, save }`，每个插件一份配置。
- **视频解析服务**：`context.services.videoExtractor.probe(url, { proxy })` 返回标题、封面与音视频格式列表，插件不能自行启动进程；yt-dlp 二进制的下载、更新与调用归宿主。
- 第一期不做：媒体库浏览、HLS、平台字幕、在线流式播放（全部先缓存）。有具体消费者后再扩展。

## 宿主侧

- **注册表**（主窗口渲染进程）：按插件 ID 登记，调用时读取当前配置 `create(config)`，与插件激活信号、调用方信号合并；插件停用后迟到结果丢弃。
- **跨进程调用**：主进程 `PluginVideoRelay` 只转发请求、回复与取消，调用方可以是任意窗口，也可以是主进程自身（Vibe Learning 索引队列）。提供方列表由主窗口上报、主进程广播，辅助窗口据此显示入口与匹配链接。
- **通用缓存**（主进程 `video-cache` 模块）：按 `提供方 ID + cacheKey` 的摘要命名，三种播放源共用下载、合并、进度事件与索引；设置「缓存」只剩一个在线视频桶。旧 `bilibili-cache`、`youtube-cache` 目录与索引在模块初始化时清除（缓存可重建，不迁移）。
- **统一取源**：`useOnlineVideo(meta)` 替换 desktop / shared 两套 hook：查缓存 → 未缓存时 `getPlayback` → 下载缓存 → 本地地址；视频笔记转写与 Vibe Learning 复用「确保本地文件」同一入口。
- **按插件生成入口**：编辑器、白板、项目视频笔记、学习资料的「添加视频」中，每个启用的插件一项，名称取插件名；弹窗只用该插件解析，`matches` 不通过时若属于其他插件则提示正确入口。
- **缺插件**：已存视频的提供方未安装或未启用时，显示「需要启用 X 插件」并保留原页面链接，不改写数据。

## 配置升级

主进程设置加载链（与 upload / images 迁移同一队列）一次性转换：

- `integration.bilibili.credentials{SESSDATA,bfe_id}` 与 `userInfo` → `onlineVideo.configurations.bilibili`；
- `integration.youtube.proxy` → `onlineVideo.configurations.youtube`；
