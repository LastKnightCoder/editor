## 1. 需求

1. 插件读、写、删卡片、文章、项目文档、待办、日程等业务数据，变更与界面、多窗口和云同步保持一致；定义领域事件，如「卡片更新」。
2. 以 contentId 为单位开放正文：用户自建的自定义页面能读写正文，并自动获得实时协作。思想实验：如果把卡片页做成插件，API 该长什么样。
3. 把 Editor、Database、Whiteboard 作为组件开放给插件。插件作者不用自己组装，就能用上内置扩展和用户已安装的扩展。
4. 权限交互参照浏览器申请麦克风：调用时弹窗，用户可选「仅这次」「始终允许」「拒绝」，并能在插件详情页撤销。

## 3. 总体设计：四层 API

```
ctx.data.*        实体层：卡片/文章/项目/项目文档/待办/日程/数据表的元数据 CRUD
ctx.content.*     正文层：以 ContentRef 为单位读、改、订阅；写入走协作会话
@tau/plugins/components   组件层：<ContentEditor> <DataTable> <Whiteboard> … 宿主注入
ctx.entities.*    插件实体：插件自建、带正文、可被搜索与 @ 引用的业务对象（5.4、14）
ctx.app.*         动作层：打开实体、导出、演示等宿主能力，以动作代替深层组件
ctx.events / onDidChange  事件层：统一信封的领域事件
ctx.permissions   权限：查询 / 申请 / 监听撤销
```

**跨层设计原则**

1. **可序列化、全异步**。除组件层外，所有调用参数和返回值都是纯 JSON，并返回 Promise。插件目前在同上下文运行，但将来迁到 iframe/worker 隔离时 API 不需要改。这是本方案最重要的前瞻约束。
2. **不暴露 SQL、内部 store、Y.Doc、Slate editor**。公开的是领域操作。复用现有命令层，不另写第二套数据路径。
3. **写入一律走宿主现有写路径**。这样多窗口广播、react-query 刷新、协作、索引（doc-tasks、AI 元信息、反链）、云同步都自动生效，插件写入与用户手动操作的行为完全一致。
4. **乐观锁加幂等**。读取返回 `revision`，写入带 `expectedRevision`，冲突时抛 `ConflictError`；写操作接受 `requestId`，重试不会重复执行（沿用 task-assistant 协议）。
5. **来源标记**。每次写入都记录 `origin: { kind: "plugin", pluginId }`，供事件、操作日志和撤销使用，插件也能据此忽略自己触发的事件，避免循环。

## 4. 实体层 `ctx.data`

```ts
interface EntityApi<T, Create, Patch, Query> {
  get(id: string): Promise<T | null>;
  query(q: Query & { cursor?: string; limit?: number }): Promise<{ items: T[]; cursor?: string }>;
  create(input: Create, opts?: WriteOptions): Promise<T>;
  update(id: string, patch: Patch, opts: WriteOptions & { expectedRevision: string }): Promise<T>;
  delete(id: string, opts?: WriteOptions): Promise<{ operationId: string }>;
  onDidChange(listener: (e: EntityChangeEvent<T>) => void, filter?: { ids?: string[] }): Disposable;
}

ctx.data.cards; // { id, contentRef, tags, pinned, createdAt, updatedAt, revision }
ctx.data.articles; // { id, title, contentRef, banner?, deleted, ... }
ctx.data.projects; // 项目树：读取 + tree.move / tree.insert / tree.remove，不暴露 children JSON
ctx.data.documents; // 项目文档（project_item）：{ id, title, kind, contentRef | whiteboardRef, parents }
ctx.data.todos; // 直接映射 task-assistant 的 todo 读写（含 recurrence / occurrence）
ctx.data.calendar; // 日程与日历组：映射 task-assistant 的 calendar 读写
ctx.data.tables; // 数据表：schema / rows / views 的列行操作
ctx.data.tags; // 标签树与重命名（卡片页需要）
```

- **分页是强制的**，`query` 一律走 cursor 加 limit，宿主设上限（例如 200 条）。这遵守「不为展示 N 条全量拉表」的规范。宿主可能需要为此新增聚合或分页命令。
- **ID 对外一律是字符串**（例如 `"card:123"`），内部 id 类型变化不会影响作者。
- **删除可恢复**。文章已有软删；卡片、项目文档的删除进入「操作日志 + 7 天宽限」，与 `content_pending_releases` 的宽限期一致。插件详情页和撤销入口能看到「某插件删除了 N 项」。
- **文档待办**通过 `ctx.data.todos` 修改时，宿主内部仍走 `patchNodes` 回写正文，正文是唯一真相源（DT 方向不变），插件感知不到差别。

## 5. 正文层 `ctx.content`

### 5.1 身份：ContentRef

```ts
type ContentRef = string; // 不透明句柄，内部编码 contentId + createTime，防止 id 复用后误指
```

插件只能从实体（`card.contentRef`）、事件或用户操作（选中、当前文档）拿到 ContentRef，不能凭空构造一个数字 id 去探测全库。这也让「授权到某一篇」成为可能。

### 5.2 读、改、订阅

```ts
ctx.content.read(ref, { format: "markdown" | "nodes" }): Promise<{ revision; markdown?; nodes? }>;
ctx.content.edit(ref, ops: EditOperation[], { expectedRevision, requestId }): Promise<{ revision }>;
ctx.content.replace(ref, value, { expectedRevision }): Promise<{ revision }>;   // 整篇替换，代价最高
ctx.content.onDidChange(ref, listener, { debounceMs?: number }): Disposable;   // 只给 ref + revision，内容按需 read
```

- `EditOperation` 直接沿用 AI 编辑引擎的 `insert / delete / replace` 加定位器（markdown 区间、block path、文本匹配）。**写入经协作会话产生 Y 增量**，所以已打开的编辑器、其他窗口和共享协作者都会实时看到，还能用 Yjs UndoManager 撤销。插件不需要知道 Yjs 的存在。
- 冻结或换源（`frozen/swapping`）期间写入返回 `ContentBusyError`，不排队。
- `nodes` 格式会暴露 Slate 结构，所以必须声明 `nodeSchemaVersion`。markdown 是首选的稳定格式。

### 5.3 为什么不把 Y.Doc 句柄给插件

| 方案                      | 优点                                                   | 代价                                                                                                      |
| ------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| A. 操作级 API（推荐）     | 可序列化、可做权限检查、可迁入隔离、与 AI 编辑同一引擎 | 做不了逐字符的实时自定义编辑器                                                                            |
| B. 暴露 Y.Doc / Awareness | 插件可以自己做实时编辑 UI                              | 需要绑定内部 Slate↔Y 映射（`collabId`、私有块占位），破坏 ER-005 受信任层边界，无法隔离，结构一变插件就坏 |

需要「实时编辑体验」的场景，用组件层的 `<ContentEditor>` 解决，不让插件直接摸 Y.Doc。A 加组件已经覆盖全部需求。

### 5.4 插件自有正文（自定义页面的关键）

自定义页面需要「属于自己」的文档（例如一个看板，每张卡有一段正文）。如果直接裸建 contents，`ref_count` 就没有主人，会泄漏。为此新增**插件实体**：

- 新增表 `plugin_entities(id, plugin_id, kind, key, title, content_id, content_created_at, meta JSON, create_time, update_time)`。由这张表持有 ref_count，同时作为搜索、@ 引用和反链的实体单位（见第 14 节）。
- `ctx.entities.create({ kind, key, title, meta, content? })` 返回 `{ id, contentRef }`；还有 `update/delete/query/get`，删除走 7 天宽限。`kind` 必须先通过 `ctx.entities.registerKind` 声明。
- 卸载插件时，所有实体按延迟回收进入 7 天宽限；在宽限期内重新安装，可以凭 key 找回。
- 插件实体的正文和内置正文一样，享有协作、索引、全文与语义搜索、云同步，因为它们都在主库里。
- 只有插件**自己创建**的正文才算插件实体。插件引用已有卡片或文章时（例如看板里放卡片），存的是实体引用，不重复建实体，也不重复索引。
- 改 schema 时需要同步 `check-schema-parity.mjs` 与 `database-schema.md`（AGENTS.md 规定）。

## 6. 组件层 `@tau/plugins/components`

沿用 `SourceBlockEditor` 的先例：SDK 只导出类型和占位，宿主在共享模块注入真实实现。插件不会打包 Slate、Yjs 或扩展。

```tsx
<ContentEditor contentRef={ref} readonly? placeholder? toolbar?="full|minimal|none" onRevision? />
<ContentPreview contentRef={ref} maxLines? />            // 只读渲染，列表卡片用
<DataTable tableRef={ref} viewId? readonly? />
<Whiteboard whiteboardRef={ref} readonly? />             // 首期只读或嵌入，写入随宿主
<TagPicker value onChange />  <EntityPicker kind="card" onPick />   // 选择器顺带产生「授权到这一项」
```

- `<ContentEditor>` 内部就是桌面端现有的 `ContentEditor` 加 `useContentDocument`，自动带上会话、协作、presence、`createDesktopKit`（内置扩展和已安装扩展）、文档待办状态栏。**插件作者写一行 JSX 就能得到与卡片详情完全相同的编辑器**。
- props 是公开协议，只能少不能多。不透传内部的 `editingContext`、`source` 等。宿主根据 ContentRef 反查实体类型，自动补全这些参数。
- 组件渲染本身也要过权限：挂载 `<ContentEditor>` 需要该 ref 的 `content:write`（readonly 时为 `content:read`），未授权时渲染「请求访问」占位。
- 组件层是**同步 React，依赖同上下文执行**。将来做隔离时，它只能留在高信任档，或改由宿主在插件页面的槽位中代为渲染。这一点在 07 中如实标注。

## 7. 动作层 `ctx.app`

卡片详情页直接 import 了大量宿主内部组件（导出弹窗、演示、播客、沉浸模式、协作控制）。如果全部做成组件开放出去，公开面会失控。规则是：**有自身界面且宿主已有的功能，开放成「动作」，不开放成组件**。

```ts
ctx.app.open(entity | contentRef, { newWindow? })     // 走 navigator，打开宿主详情页
ctx.app.run("content.export", { ref, format })        // 弹宿主导出对话框
ctx.app.run("content.present", { ref })
ctx.app.run("content.share", { ref })                 // 协作共享开关
ctx.app.context(): Promise<{ activeContent?: ContentRef; selection? }>   // 当前焦点文档，用于 activeTab 式授权
```

## 8. 事件层

### 8.1 统一信封

```ts
interface DomainEvent {
  type: "card.created" | "card.updated" | "card.deleted" | "article.*" | "document.*"
      | "project.*" | "todo.*" | "calendar.*" | "table.*" | "content.updated" | "tags.changed";
  entity: { kind: string; id: string };
  revision?: string;
  fields?: string[];          // updated 时哪些字段变化（tags / pinned / title …），不携带值
  origin: { kind: "user" | "plugin" | "ai" | "sync" | "collab"; pluginId?: string };
  at: number;
}
ctx.events.on("card.updated", handler): Disposable;   // 也提供 ctx.data.cards.onDidChange 语法糖
```

### 8.2 实现位置

在主进程的提交点新增 `DomainEventBus`，挂在事务 COMMIT 之后。它把现有零散的 `content:updated`、`card:updated`、`schedule:changed`、`doc-tasks:changed` 归一，再经一个 IPC 通道推到渲染端的插件运行时。

- **事件不带数据，只带引用和 revision**。插件按需 `get/read`，这样事件分发时不必再做数据级权限过滤，只按实体类型权限过滤即可。
- **高频合并**。正文在输入期间每 1 秒投影一次，`content.updated` 默认按 ref 合并（1 秒窗口）。
- **整库替换**（云同步下载、切库）发出 `workspace.reset`，插件应全量刷新，而不是收到几万条 deleted。
- 宿主自己的 react-query 层以后也可以改为消费同一条总线，逐步替换零散广播。这项属于后续收益，不算前置条件。

| 场景              | 如何保证                                                                                                |
| ----------------- | ------------------------------------------------------------------------------------------------------- |
| 宿主界面 / 多窗口 | 写入走原命令，复用既有广播与 react-query 更新                                                           |

## 10. 权限设计

### 10.1 诚实前提

插件与宿主在同一 JS 上下文。**本方案的权限是「正规 API 的闸门加用户知情」，不是安全边界**：恶意插件仍可绕过 SDK 直接调 `window.electron`。界面和文档不得宣称「未授权插件无法访问数据」。真正的强制执行要等隔离载体落地（07/23）。第 3 节「可序列化、全异步」正是为那一天预留的。即便如此，闸门仍有实际价值：防止善意插件越界、让用户知情、留下可审计记录，并把权限协议提前定型。

### 10.2 权限词表

| 权限                                                    | 含义                                                               | 风险提示 |
| ------------------------------------------------------- | ------------------------------------------------------------------ | -------- |
| `cards:read` / `cards:write` / `cards:delete`           | 卡片元数据与正文                                                   | 删除单列 |
| `articles:*`、`documents:*`、`projects:*`               | 同上                                                               |          |
| `todos:read/write/delete`、`calendar:read/write/delete` | 待办与日程                                                         |          |
| `tables:read/write`                                     | 数据表                                                             |          |
| `content:read/write`                                    | 按 ContentRef 访问正文（不经实体，例如自有正文、选择器授予的单篇） |          |
| `events:<kind>`                                         | 不单独设立：订阅某类事件 = 拥有该类 read                           |          |

**范围**有两档：「全部」和「指定项」。指定项来自三种途径：用户通过 `EntityPicker` 选中、通过命令作用于当前文档（类似浏览器的 activeTab，用户主动发起即视为授权该项）、插件自有正文（天然拥有）。

### 10.3 声明与申请

1. **manifest 新增 `permissions: string[]`**，这是插件能申请的上限。未声明的权限调用一律直接拒绝，不弹窗，防止插件运行中不断扩权。
2. **懒申请**：首次调用缺权限的 API 时自动弹窗，等用户答复后才继续执行（类似 `getUserMedia`）。也可以显式调用 `ctx.permissions.request([...])` 一次申请多项。
3. **弹窗选项**：「仅这次」「始终允许」「拒绝」。同一插件同时发起的多项申请合并成一个弹窗；读与联网（`fetch`）同时具备时，额外提示「可将获准数据发送到网络」（07 的组合风险）。
4. **防骚扰**：
   - 后台调用（窗口不在前台，或调用不是由用户动作触发，例如事件回调里）不弹窗，直接失败。插件详情页和侧边栏插件入口出现「待处理的权限请求」角标，用户主动点开再决定。
   - 「拒绝」在本次运行期间记住，不再重复弹。连续拒绝 3 次后转为「已阻止」，只能在详情页解除。
5. **删除类**即使「始终允许」，批量删除超过 N 项（例如 20）时仍会二次确认，并提示可撤销。

### 10.4 授予的存储与生命周期

- 授权记录（Grant）由主进程保存在应用数据目录，键为 `(pluginId, workspace, permission, scope)`。「始终允许」持久化；「仅这次」只存在内存，插件停用、重载、切库或重启后失效。
- 授权与插件 ID 绑定，不绑定版本。但 **manifest 新增的权限不继承**，新版首次调用时重新申请。
- 每次调用在宿主适配层检查授权；写入在提交点再检查一次（防止撤销后迟到的写入）。撤销后立即退订对应事件，之后的调用抛 `PermissionDeniedError`。
- 记录审计日志：插件、权限、时间、读写计数，在详情页显示「最近 7 天读取 23 次 / 修改 4 次 / 删除 0 次」。

### 10.5 插件详情页的「权限」分区

列出 manifest 声明的全部权限及当前状态（始终允许 / 仅这次生效中 / 未授予 / 已阻止），每项都可撤销或重置；提供「全部撤销」；显示审计摘要和「撤销该插件近期操作」入口（基于操作日志）。

### 10.6 与 AI 工具审批的关系

插件通过 `ctx.mcp` 注册的工具在执行时调用数据 API，需要同时满足两条：聊天的工具审批（已有 `risk` 机制）和插件自身的授权。两者不能互相替代。

## 11. 思想实验：卡片页作为插件

```tsx
export default definePlugin({
  activate(ctx) {
    ctx.pages.register({ id: "cards", title: "卡片", component: CardsPage });
  },
});

function CardsPage({ context: ctx }: PluginPageProps) {
  const [filter, setFilter] = useState<{ tag?: string }>({});
  const feed = useInfiniteQuery({
    // 插件自带 react-query 或宿主共享
    queryKey: ["cards", filter],
    queryFn: ({ pageParam }) => ctx.data.cards.query({ ...filter, cursor: pageParam, limit: 50 }),
  });
  useEffect(() => ctx.data.cards.onDidChange(() => feed.refetch()).dispose, []);
  const tags = useTagTree(ctx.data.tags);
  const [active, setActive] = useState<Card>();

  return (
    <SplitView>
      <TagTree tree={tags} onSelect={tag => setFilter({ tag })} />
      <CardList
        items={feed.data}
        render={c => <ContentPreview contentRef={c.contentRef} maxLines={6} />}
      />
      {active && (
        <>
          <ContentEditor contentRef={active.contentRef} /> {/* 协作、扩展、待办全自动 */}
          <TagPicker
            value={active.tags}
            onChange={tags =>
              ctx.data.cards.update(active.id, { tags }, { expectedRevision: active.revision })
            }
          />
          <Menu
            items={[
              {
                label: "导出",
                run: () => ctx.app.run("content.export", { ref: active.contentRef }),
              },
              {
                label: "演示",
                run: () => ctx.app.run("content.present", { ref: active.contentRef }),
              },
            ]}
          />
        </>
      )}
    </SplitView>
  );
}
```

这个实验暴露出的 API 缺口和设计结论：

1. **列表需要分页查询和标签树**。现有 `getScopedCards` 是全量拉取，开放前要补 cursor 查询。
2. **事件要粒度足够、带 revision**，插件才能增量更新缓存，不必每次全量 refetch。现在宿主自己用的是 `card:*` 加 `content:updated` 两路，应合并为统一信封。
3. **编辑器必须是「绑定版」组件**。纯 `@tau/editor` 不认 contentId，让插件自己接会话是不可接受的。
4. **宿主深层功能用动作开放**（导出、演示、共享），避免开放几十个内部组件。
5. **AI 标题、链接等元信息**需要 `card.meta` 只读字段或独立的 `ctx.data.aiMeta`，可以留到有消费者时再做。
6. 如果卡片页真做成插件，权限需要 `cards:*`、`content:*`、`tags:*`。这说明**内置页面也应能用同一套 API 写出来**，这是检验 API 完备性的好标尺，但内置页面本身不需要走权限弹窗。

## 13. 已确认的裁决（PS-042）

1. **「仅这次」= 本次运行期间**：插件停用、重载、切库或应用重启后失效。
2. **正文不开放 Y.Doc 句柄**：只开放操作 API 和 `<ContentEditor>` 组件。
3. **插件做的删除一律可恢复**：记入操作日志，保留 7 天宽限。
4. **插件私有 KV 迁入主库** `plugin_kv`，随云同步。一次性迁移现有 localStorage 数据，完成后删除旧路径（D-091：不长期保留兼容层）。
5. **M1 的消费插件是「每周回顾」页面**，只读。
6. **在隔离落地前上线权限闸门**：界面和作者文档如实说明，它不是安全隔离。

## 14. 搜索接入

### 14.1 现状

- 全局搜索只有一个入口，即命令面板 `features/search/SearchPalette.tsx`，走全文（FTS5 + jieba）与向量的混合检索（`search-core/pipeline.ts`）。AI 的 `search_knowledge` 和 @ 面板复用同一个后端。
- **索引以实体（`type:id`）为单位，不以 contentId 为单位**。类型是写死的联合类型：`card / article / project-item / diary-moment`，以及材料类 `excerpt / pdf-annotation / web-clip`（`types/search.ts:7-9`）。
- 新增一种可搜、可 @ 的类型，要同时改七处：`IndexType` 与 `CONTENT_TYPES`、`searchResultDetails`、全文和向量队列的候选收集、`openEntity`、`ENTITY_REF_KINDS`、MentionPanel、`entity-search` 的 SQL。**没有提供方注册表。**
- 点击结果统一走 `services/open-content.ts` 的 `openEntity(ref, { at })`。`at` 是命中块的位置，由 `ContentEditor/useContentLocation.ts` 负责滚动并闪烁。
- 插件目前唯一能进入搜索的途径是摘录提供方 `ctx.excerpts`。它适合外部材料，但不能被 @，也不进反链。
- **现有缺口**：全文索引只在连库时按 `update_time` 对账（`main-content-fts-index-queue.ts:37`），不订阅 `onContentWritten`，所以正文编辑后要到下次连库才能搜到。这不是插件独有的问题，但插件实体会放大它。

### 14.2 方案：「插件实体」作为第八种索引类型（推荐）

**只改一次写死的分支**：新增一个类型 `plugin-entity`，之后按 kind 交给注册表分发。这样以后每个插件、每种 kind 都不必再改宿主（开闭原则）。

```ts
ctx.entities.registerKind({
  kind: "board-card", // 插件内唯一，宿主内部记为 `<pluginId>/board-card`
  label: "看板卡片", // 搜索结果的类型标签、筛选项名称
  icon: BoardIcon, // 与侧边栏图标同一协议（SVG 组件）
  open: { page: "board", params: e => ({ board: e.meta.boardId, card: e.key }) },
  mentionable: true, // 是否出现在 @ 面板
});
```

| 环节           | 行为                                                                                                                                                                                                                                               |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 索引           | 宿主的全文和向量队列把 `plugin_entities` 也收为候选，`prefixed_id = "plugin-entity:<id>"`，标题取 `title`，正文取 `content_id`，`content_sections` 分节照常生成。**插件不写索引代码**，只要用 `ctx.entities` 写数据就会被搜到                      |
| 结果展示       | 图标和类型标签来自 kind，右侧附插件名作来源标记。标题为空时取正文开头，命中节显示 `› 标题路径`，规则与卡片相同                                                                                                                                     |
| 筛选           | 面板范围里新增「插件内容」一项，展开后按 kind 细分                                                                                                                                                                                                 |
| 点击           | 宿主按声明式的 `open` 计算出 `navigator.push(pluginPageKey, params)`，并自动附上 `at`。插件页面把 `params.at` 传给 `<ContentEditor contentRef at>`，滚动和闪烁就复用现有实现。新窗口打开、最近访问、后退前进全部自动可用                           |
| @ 引用         | `mentionable` 的 kind 会进入 MentionPanel，插入的节点是 `{ contentType: "plugin-entity", refId }`。点击走同一个 `openEntity`。`ref-indexer` 识别该 kind 后，自动生成反链；插件页可以用 `ctx.data.refs.backlinks(entityRef)` 显示「被哪些文档引用」 |
| AI             | `search_knowledge` 自动覆盖，结果附 kind 标签。AI 也能通过 `openEntity` 打开                                                                                                                                                                       |
| 插件停用或卸载 | 结果**仍显示**，标记「插件已停用」。点击时打开宿主的**通用只读查看页**（标题 + 只读 `<ContentEditor>`），因为数据就在 contents 里，宿主始终能渲染。插件专属节点按现有缺扩展策略保留原始数据。卸载超过 7 天宽限后，从索引中清除                     |

**为什么用声明式的 `open`，而不是 `onOpen` 回调**：宿主不运行插件代码就能算出跳转目标，所以新窗口、最近访问记录、深链接（DECISIONS 中的应用内链接）都能直接复用，将来迁入隔离也不受影响。`params` 函数只读取实体的可序列化字段。确有复杂逻辑的场景，再追加可选的 `onOpen(entity, at)`。

### 14.3 不在首期做：联邦搜索提供方

`ctx.search.registerProvider({ search(query) })` 让插件对自己的私有存储或外部服务返回结果。之所以后置，原因有三：

- 排序无法与 RRF 融合，混排质量不可控。
- 每次按键都要调所有插件，需要超时和预算控制，慢插件会拖慢面板。
- 查询词会发给插件，隐私上需要额外的权限。

插件实体已经覆盖「基于 content 的业务」。等出现确实存在于 contents 之外的消费者（例如搜索外部知识库），再单独设计，并在面板里作为「来自插件」的独立分组展示，不与内置结果混排。

### 14.4 插件主动搜索

`ctx.search.query(text, { types?, limit })` 返回 `{ entity, title, snippet, section }[]`。结果只包含插件已获得 `read` 权限的类型；没有权限的类型静默剔除，并在返回值里标出 `omittedTypes`，不触发弹窗。用户的搜索面板总能看到插件实体，因为那是用户自己的数据，不受插件权限影响。

### 14.5 前置修复

**全文索引改为订阅 `onContentWritten`**，按 1 秒窗口合并后增量更新，保留连库对账作为兜底。这项对内置的卡片、文章同样有收益。已在 M1 第一步完成（持续写入最长 5 秒落一次；实体删除与标题变化仍由连库对账处理）。

### 14.6 已确认（2026-10-20，按推荐采用）

1. 插件停用后，结果仍显示，点击打开通用只读页；卸载超过 7 天宽限后才清除索引。
2. `mentionable` 默认关闭，由作者显式开启。
3. 全文索引实时化（14.5）放入 M1。

## 15. M1 实施记录

- **全文索引实时化**：`main-content-fts-index-queue` 订阅正文写入总线，按库合并 1 秒、持续写入最长 5 秒后重建引用这些正文的实体。
- **权限与只读数据（SDK 0.25.0）**：权限词表按 YAGNI 只开放已实现的五项读取权限（`cards/articles/documents/todos/calendar:read`），写入与删除权限随 M2 增加。正文读取不另设 `content:read`，改为要求所属实体的读取权限；插件自有正文（M4）再引入。实体 DTO 暂不带 `revision`，写入接口落地时补齐。调用计数只记读取。
- 宿主侧落点、存储位置与交互规则见桌面 03 指南「插件业务数据与授权（D-176）」。
- **业务事件**：主进程不在每条写路径上埋点，而是在主库连接上用 TEMP 触发器 + 自定义函数捕获全部写入（IPC、协作投影、后台模块），合并后广播；比方案 8.2 设想的「提交点」更早，回滚写入也可能产生事件，因此事件不携带数据。事件信封暂不带 `origin` 与 `fields`，插件写入（M2）落地时补 `origin` 以便忽略自身写入。待办与日程只给集合级事件。
- **消费插件「每周回顾」**：同级独立仓库 `tau-plugin-weekly-review`（本地提交，尚未推送；SDK 发布前依赖仓库内的本地 SDK 包）。按周汇总新卡片、修改过的文章与项目文档、本周截止的待办与日程、常用标签；首次打开先 `permissions.query` 再一次 `request` 尚未决定的权限，避免多次弹窗；被拒绝的分区单独提示「允许读取」；订阅业务事件自动刷新。发布包已固定为集成测试夹具，桌面测试用真实运行时、数据适配、授权代理与弹窗走通「一次授权 → 显示汇总 → 事件刷新」。
- **验证中发现的问题**：`permissions.ts` 经 `package.ts` 被 Node 以仅剥离类型方式直接加载（夹具、CLI 等脚本），TS 参数属性不被支持；已改为显式字段。插件识别权限错误建议按 `error.name` 判断，测试环境不加载 SDK 运行时时同样成立。

## 16. 关联与打开（M3a，排在 M2 之后）

场景：作者做了一个 Excalidraw 页面，要在画布上关联已有的卡片、日记、待办，并且点击后能打开它们。这需要三项能力，原方案放在 M3，现单独提前。

| 能力 | 接口                                                                    | 宿主复用                                                                                                  | 权限                                                                                         |
| ---- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 选择 | `ctx.app.pick({ kinds, multiple?, title? })` → `{ ref, kind, title }[]` | `components/EntityPicker` + `entity:search`                                                               | 不弹窗：用户亲手挑选即授权，插件只得到所选项的引用与标题快照；读取正文仍需读取权限           |
| 打开 | `ctx.app.open(ref, { at?, newWindow? })`                                | `openEntity`（卡片 / 文章 / 项目文档 / 日记）、待办页 `selectedId`、日程页 `eventId`、`whiteboard-detail` | 不需要数据权限；只在用户手势后的短时间内允许（`navigator.userActivation`），防止后台随意跳转 |
| 引用 | `PluginEntityRef = { kind, id }`                                        | 与 `context.data` 的 ID 一致                                                                              | 可序列化，插件存入自己的数据；目标被删除时打开提示「内容不存在」                             |

- `kinds` 为 card / article / document / diary / whiteboard / todo / event；`entity:search` 已补齐待办（独立待办，不含正文勾选项）与日程（不含系统日历的标记）候选。
- 不提供无权限的 `describe(refs)`：数字 ID 可遍历，按 ID 取标题等于绕过读取权限。标题刷新使用 `context.data.get`（需读取权限），或沿用选择时的快照（与白板文档卡的 `title` 快照同一做法）。
- 插件内容被哪些地方引用、插件内容引用了谁，要进脉络「被引用」，依赖 M4 插件实体。
- **实施（M3a）**：`ctx.app.pick` / `ctx.app.open` 已交付；用户手势检查用 `navigator.userActivation.isActive`（Chromium 的瞬时激活约 5 秒，插件在点击后短暂等待数据再打开仍可用）。`open` 不支持 `at` 定位参数，暂无消费者。消费者：「每周回顾」0.3.0 点击条目打开原处（open）；`pick` 目前只有桌面集成测试，真实消费者待自建画布类插件。

## 18. M3 组件与动作实施记录

## 19. M4 插件实体实施记录

- **消费者与范围（2026-10-20 用户确认）**：M4 的消费插件改为「每周回顾」的「周记」（每周一篇插件自建正文，可搜索、可 @、显示被引用）；Excalidraw 画布的场景不是正文，放进「标题 + 正文」的实体模型只能搜到标题，不作为本期消费者。搜索面板暂不新增「插件内容」筛选项，结果与内置内容混排，带类型名与插件来源。分四步：M4a 实体与自有正文，M4b 搜索与打开，M4c @ 与反链，M4d 私有存储入主库。
- **M4a 实体（SDK 0.25.0 同版）**：主库 `plugin_entities(id, plugin_id, kind, key, title, content_id, meta, create_time, update_time, orphaned_time)`，`(plugin_id, kind, key)` 唯一，每项建一份空白正文并持有 1 份引用。`ctx.entities.registerKind / create / get / find / query / update`，类型须先声明，`meta` 为最大 64 KB 的 JSON 对象，revision 为元数据修改时间。插件只读写自己的实体，不需要业务权限；`plugin-data:content` 返回 `pluginOwners`，`content.read / edit`、`ContentEditor` / `ContentPreview` 与 `app.run` 对本插件实体的正文直接放行（协作来源按通用 `content`，不登记 AI 编辑身份）。
- **卸载宽限**：开库维护按 `~/.editor/plugins` 的直接子目录判断插件是否仍安装，不在的实体记 `orphaned_time`；目录重新出现或插件再次读写实体即撤销，超过 7 天删除实体并 `releaseDeferred` 正文（再经正文宽限回收）。读不到插件目录时本次不标记。
- **与方案的偏差**：
  - 不存 `content_created_at`：正文编号经高水位分配不复用，ContentRef 的创建时间取自 `contents`。
  - `create` 不接受初始 Markdown：消费者在编辑器里书写，且主进程 Markdown 转换正在迁往独立内容服务，避免新增依赖；需要时用 `content.edit` 追加。
  - 暂不提供 `delete`：消费者不删除；有消费者时再接入「最近删除」与 7 天恢复（裁决第 3 项）。已在第 20 节补上。
  - `registerKind` 暂不含图标，搜索结果的展示随 M4b 决定。已在第 20 节补上，外观随库保存。
- **M4b 搜索与打开**：单一索引类型 `plugin-entity`（`IndexType`、共享 `ENTITY_REF_KINDS` / `KIND_ALIASES` / 优先级最低、`EntityKind`），全文对账分组与增量 `entityTask`、LIKE 兜底、向量候选 `index-candidates` 与 `MAIN_CONTENT_INDEX_TYPES`、`searchResultDetails`（附 `pluginEntity: { pluginId, kind }`）、`EntitySearchTable` 的 `search` / `locate` / `locateAll` / `resolve`。候选含已停用与宽限期内已卸载插件的内容（裁决 14.6 第 1 项：结果仍显示）。插件运行时把 `registerKind` 登记到宿主表 `services/plugin-entity-kinds.ts`（插件停用即注销）：结果标签取插件声明的类型名，停用时回落「插件内容」；`openEntity` 先 `plugin-entities:locate`，类型已登记则按声明的 `open.page` / `open.params` 推导插件页并附 `at`（定位不参与实例身份），否则打开宿主只读页 `plugin-entity`（标题 + 只读 `ContentEditor`，可回到插件或查看插件详情）。SDK `ContentEditor` 增加 `at`。AI `search_knowledge` 的类型清单加入 `plugin-entity`。
- **M4b 取舍**：搜索面板不新增范围 chip（用户确认），插件内容只出现在「全部」，不计入任何 chip 的命中数；随机漫步不抽插件内容；白板文档卡与创作模式不承载插件内容（`isBoardDocumentRef` 过滤，放到白板的入口对插件内容隐藏）；脉络与 @ 留到 M4c。
- **M4c @ 与反链**：@ 面板的检索类型加入 `plugin-entity`，结果经 `isMentionableResult` 只保留插件正在运行且 `mentionable` 的类型（裁决 14.6 第 2 项默认关闭）；插入的仍是 `content-link`（`contentType: "plugin-entity"`），点击经 `normalizeEntityRefKind` → `openEntity`。共享 `entity-ref` 已认识该类型，引用索引自动收录，`REF_INDEX_VERSION` 升到 6（桌面与移动端 Rust 同步）让已有链接重解析；脉络对插件内容同样给出「被引用」。SDK `ctx.entities.backlinks(id)`：宿主复用 `entity-context:get` 的被引用，按 14.4 的口径只返回插件已获准读取的类型（`cards/articles/documents:read`，只查询不弹窗），日记、其他插件内容与未获准类型计入 `omitted`；方案中的 `ctx.data.refs.backlinks(ref)` 改挂在 `entities` 下，因为目前只有自有内容需要。

- **M4c 限制**：反链沿用脉络的上限（50 个来源），超出部分不计入 `omitted`；移动端不运行插件，引用会被索引但脉络不展示插件内容。

## 20. 插件内容的删除与类型外观

- **范围（2026-10-20 用户确认）**：按「SDK 契约缺口不等消费者」的原则（见 20.3）先补两项：插件内容的删除与恢复，`registerKind` 的图标；同时把插件内容在宿主各处的显示收口为一个抽象，不再在任何地方笼统显示「插件内容」。

### 20.1 删除与恢复

- SDK `ctx.entities.delete(id, { expectedRevision })`，不需要业务权限（只能删自己的内容），revision 过期抛 `PluginConflictError`；宿主不弹确认，需要确认时由插件自己询问。
- 主进程 `plugin-entities:delete`：删除前把整行快照写入 `plugin_operations`（`entity = "plugin-entity"`，与卡片 / 文章同一张表、同一 7 天保留期，登记逻辑抽到 `tables/plugin-operations.ts` 共用），正文 `releaseDeferred` 进入正文宽限。插件详情页「最近删除」显示插件声明的类型名，`plugin-data:restore` 对插件内容按快照原样插回（ID、key、正文不变）、`retain` 正文并重发正文写入事件，让全文与引用索引重新收录，正文中指向它的 @ 链接随之恢复。
- **编号不复用**：`plugin_entities` 的 ID 改为高水位分配（与 `contents`、待办、日程同一机制 `getNextTaskEntityId`）。否则删除后新建的内容可能占到同一 ID，正文里指向旧内容的链接会落到新内容上，恢复也无法沿用原 ID。
- 恢复冲突：同一 ID 已存在、插件已用同一 key 新建了内容、或正文已过宽限被回收时，恢复报错，不覆盖。

### 20.2 类型外观：插件声明，宿主随库保存

- **问题**：M4b 的类型名登记在运行时内存里，插件停用、宽限期内已卸载、或在另一台设备上没装这个插件时，搜索结果、正文里的引用卡片、脉络、漫步统一显示「插件内容」与拼图图标；而正文链接、脉络、漫步只拿得到 `plugin-entity` + ID，连运行中插件的类型名也查不到。
- **抽象**：显示所需的「外观」（类型名 + 图标）与「行为」（打开到哪个页面、能否 @）分开。行为必须执行插件代码，只在插件运行时有效（`services/plugin-entity-kinds.ts` 的运行时登记，不变）；外观是声明式数据，随笔记库保存在新表 `plugin_entity_kinds(plugin_id, kind, label, icon, update_time)`，与内容同步到其他设备，插件不运行时照样可用。
- **图标协议**：SDK 新增通用的 `PluginIcon` / `PluginIconProps`（`PluginSidebarIcon*` 保留为同义名），`registerKind({ icon })` 与侧边栏图标同一写法。宿主在声明时用 `renderToStaticMarkup` 把组件渲染一次（必须是单个 `<svg>`，补齐 `xmlns` 与 24 × 24 尺寸，不超过 16 KB），与类型名一起经 `plugin-entities:declare-kind` 写库，未变化不写。显示时用 CSS `mask-image` 加 `currentColor` 填充：图像上下文不执行脚本、不加载外部资源，因此不需要 HTML 净化，颜色随主题与选中态；代价是只保留形状，多色与渐变图标会变成单色，这与侧边栏图标的线性单色约定一致。
- **宿主侧收口**：`components/EntityKind` 提供 `useEntityKindMeta(ref, fallback)`（只有引用时先经 `plugin-entities:owners` 查所属插件与类型，同一轮渲染的查询合并成一次命令）、`usePluginEntityMetaResolver()`（检索结果已带 `pluginEntity` 时逐项解析）与 `EntityKindIcon` / `EntityKindLabel` 组件。内置类型原样返回各处自己的元数据表，插件内容返回声明的外观，从未声明过才回落 fallback。接入点：搜索面板、@ 面板、正文链接悬浮卡、脉络的连接与来源、漫步卡片 / 岔路 / 足迹、内容选择器、宿主只读页、「最近删除」。外观与归属查询走全局 QueryClient（编辑器内的独立 React 根没有 Provider），声明、删除、恢复后统一失效。类型名优先取运行中登记的最新值，图标取库里保存的声明。
- **清理**：开库维护在删除孤儿内容之后，删除「已卸载且库里已没有其内容」的插件的类型外观；读不到插件目录时不清理。
- **组件之外与批量场景**：卡片数据库连接列在 `useMemo` 里拼文本，用 `useEntityKindMetaResolver(refs)` 一次取齐链接缺文字时的类型名（如「周记 #12」）；AI 工具 `search_knowledge` 用 `loadPluginEntityAppearances(库名)` 读同一份缓存，结果的 `typeName` 报插件声明的类型名，AI 回答与工具卡片据此称呼。
- **未做**：移动端不运行插件，插件内容的引用目前不在移动端展示外观。`tone`（让作者从 tag 色板选色调）未做，所有插件类型仍共用 tag-5。

### 20.3 补充说明与原则

- **反链只返回已获准类型的含义**：每条反链都带来源的标题与引用处前后文字，等于读取了来源，所以按插件已获得的读取权限过滤，否则无 `articles:read` 的插件也能经反链读到文章标题与片段。不弹窗，是因为反链是打开页面时自动发起的查询，用户没有做出「把文章交给插件」的动作，此时弹窗会训练用户无脑允许。插件应据 `omitted` 显示「另有 N 处引用，授权后可见」，由用户点击后调用 `permissions.request`（「每周回顾」0.5.0 即此做法）。
- **SDK 契约缺口不等消费者**：插件由第三方作者编写，作者第一天就需要的通用能力（自有内容的删除、类型图标）不能以「宿主还没有消费者」为由推迟，否则作者只能等宿主发版。YAGNI 只适用于宿主自己的功能（如搜索面板的「插件内容」筛选、Excalidraw 画布插件）。按此重新分类 79 中的后续项：契约缺口为删除、图标（本节已做）、项目文档新建 / 移动 / 删除、事件 `fields`、`open` 的 `newWindow`；宿主功能为搜索筛选与画布插件。
