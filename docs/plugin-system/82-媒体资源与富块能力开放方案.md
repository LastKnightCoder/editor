# 媒体资源与富块能力开放：调研与方案

## 1. 背景与目标

起因是把图片画廊（`image-gallery`）抽成独立插件。已拆出的 ABC、HTML、TikZ、Typst 都是「源码 + 预览」块，SDK 的 `useSourceBlock` / `SourceBlockEditor` 正好覆盖；画廊是第一个富交互媒体块，需要宿主的资源解析、上传、灯箱、属性条、块菜单与节点写入，这些 SDK 都没有开放。

目标不是让画廊插件跑起来，而是开放「媒体资源」与「富交互块」这一类能力：之后第三方做图片对比、音频列表、相册之类的块，不需要再改宿主。判断问句沿用 PS-046：**把画廊删掉，这个接口还说得通吗？**

产品尚未发布，不加载插件的端接受降级（见第 7 节）。

## 2. 设计原则

1. **开放机制，不开放单个动作。** 「远程资源缓存到本地」只是资源解析的一个步骤，是否缓存由用户设置决定，不由插件决定；开放的是解析、上传这一层，组件建在它之上。
2. **默认实现可替换。** 宿主的 Image / Video / Audio 组件作为默认实现开放，作者完全重写也能得到相同的解析结果。
3. **能声明的不写回调。** 节点里有哪些资源是纯数据，宿主在导出、灯箱、协作、CLI 都要用，必须不执行插件代码就能读到（同 PS-046 §2.3）。
4. **不扩大改造范围。** 新能力只给插件块使用，内置块的渲染与交互保持现状；内置节点只补 `resources` 数据声明（协作只认声明的前提，见 4.3）。

## 4. 地基设计

分三层，加两项编辑器通用能力。接口形状为草案，实施时以宿主实现为准。

### 4.1 资源层：解析与上传

```ts
// 渲染作用域 hook：在编辑器内取当前 kit 的服务（协作文档走 binding），编辑器外用宿主默认实现
useResource(url: string, options: { kind: ResourceKind }): {
  src: string | undefined;          // 可直接给 <img>/<video>/<audio> 的地址
  status: "loading" | "ready" | "error";
  retry(): void;
};
useResourceUpload(): ((file: File) => Promise<string>) | undefined;

type ResourceKind = "image" | "video" | "audio" | "file";
```

- 解析遵守用户设置（是否缓存远程图片、CDN 改写），插件不能强制下载。
- 上传按当前作用域：本地库写资源目录，远端模式走用户配置的上传提供方，共享文档走协作 binding。只读编辑器与无上传能力的场景（博客）返回 `undefined`。
- 语义是「解析文档里的资源引用」，不是「把任意路径变成可读地址」。插件目前与宿主同进程，这条边界暂时不硬，但接口不承诺任意路径可读，为以后的隔离留余地。
- 不提供 `pickResource`：宿主没有资源库选择器，插件用文件输入 + `useResourceUpload`。`IMediaSelectors` 删除。
- 实现方式同 `source-editor`：SDK 导出占位，桌面经 `configureMedia` 注入，博客直接并入插件模块。博客的解析为原样返回（发布时资源已改写为公开地址）。
- 桌面的解析抽为 `utils/mediaSource.ts` 的 `resolveMediaSource`，`useResource` 与内置 LocalImage / LocalVideo / LocalAudio 的首轮解析共用；播放器特有的出错换协议重试、流式回退留在组件内。上传没有按类型区分的语义，不带 `kind`。

### 4.2 组件层：默认媒体组件

```ts
MediaImage / MediaVideo / MediaAudio; // 参数沿用 ImageSlotProps / VideoSlotProps / AudioSlotProps
```

- 就是宿主现有插槽组件（桌面为 LocalImage / LocalVideo / LocalAudio，博客为默认实现），加载态、失败态、播放器外观与内置块一致。
- 作者可以只用 `useResource` 完全自绘，得到同样的解析结果。

### 4.3 声明层：节点资源声明

```ts
ElementSpec.resources?: readonly {
  path: string;                 // 字段路径，"url"、"images[].url"
  kind: "image" | "video" | "audio" | "file";
  preview?: string;             // 同一资源的显示版本字段（如裁剪结果），与 path 末段同层
  alt?: string;                 // 替代文字字段，与 path 末段同层
  caption?: string;             // 说明文字字段，与 path 末段同层
}[];
```

- 纯数据，支持读与改写：导出时按 `path` 改写地址，导入时回填。`preview` 指向的显示版本同样参与上传与改写，灯箱优先显示它。
- 类型、内置声明与遍历工具在 `@tau/db-schema/content-resources`：服务端、主进程、CLI、编辑器与 SDK 都依赖这个最底层的纯数据包，协作服务器不需要依赖编辑器。
- 宿主消费者全部改读声明（第 6 节）。内置 image、inline-image、video、audio 也改为声明，删除各处 type switch。`file-attachment` 有 `isLocal` / `localFilePath` 的专门语义，表达不了的保留内置逻辑。
- **随库保存**：主库表 `plugin_element_resources(plugin_id, type, resources, update_time)`。主窗口插件宿主按当前库写入已加载内容插件的声明（插件更新时按类型覆盖，不再声明的类型保留，库里可能还有它的节点）；主进程协作与 CLI 读取「内置 + 库里保存」的合并结果，内置类型不能被插件覆盖。

#### 协作只认声明

共享文档的资源上传改写（主进程 `collaboration/asset-service.ts` 的 `mapResources`）与上传前安全校验（`packages/collaboration/src/document.ts` 的本地路径检查）目前按字段名推断：任意层级里叫 `url`、`src`、`filePath` 等的字符串都当资源。改为只认 `resources` 声明，删除 `RESOURCE_FIELDS`，协作层与节点之间只有协议，不猜字段。

- 资源字段写对是节点声明方的责任。未声明的字段原样同步，不上传、不改写、不校验；插件漏声明导致的裂图或本地路径外泄由插件修复，宿主不兜底。
- 内置节点同样声明（image 的 `url` / `previewUrl`、inline-image、audio、video、file-attachment 等），覆盖现有字段名清单的每一项后再删除推断。
- 文档级字段（如文章题图 `bannerBg`）是宿主自己的数据结构，由宿主按自身类型声明，同样不按字段名识别。
- 声明写在协作文档的 `resources` 映射（节点类型 → 资源字段）。主进程在发起共享、结束共享前，以及共享会话每次投影时，把本机已知、文档里出现但尚未声明的类型补进去；已有的声明不覆盖，避免不同版本的成员来回改写同一项。接收端按随文档的声明下载与改写资源，本机没装对应插件也能正确落地资源。
- 服务端与发布前校验只按文档携带的声明检查资源地址；声明本身形状不对（路径段含 `__proto__` 等、种类未知、项数过多）直接拒绝。
- 主进程不执行插件代码，插件节点的声明从随库保存的数据读取，因此随库保存是这一条的前提。

同一原则下，协作包里还按类型写死了源码字段（`SOURCE_FIELDS`，含已插件化的 abc、html、tikz、typst、custom-block）和 `PRIVATE_BLOCKS`，属于同类问题，另立条目处理，不在本方案交付内。

### 4.4 编辑器：通用元素运行时

```ts
useElement(element): {
  readOnly: boolean;
  selected: boolean;            // 外框里的块是否被点选
  update(patch: Record<string, unknown>): void;
  remove(): void;
  select(): void;
  openMenu(position: { x: number; y: number }): void;   // 需要外框
};
```

- 写入沿用行内源码的提交守卫：只读、节点已被替换或组件卸载后不写入，经提交作用域写入。
- `useInlineSource` 改为它之上的封装。`useSourceBlock` 的 `update` 不加守卫，保持原样：已发布的源码插件在防抖回调里用旧闭包写入，加守卫会静默丢写。
- 不开放 slate / slate-react，插件写入一律经此。

### 4.5 编辑器：void 块外框

外框指 void 块（整块不可在内部输入文字的块，如图片、视频、画廊）四周的公共交互：选中描边、右键菜单、末尾「添加段落」、选中时的 Delete / Enter 键处理。内置块各自在组件里实现这些（约 21 个块组件各自渲染 `AddParagraph`），插件拿不到这些组件。宿主为插件声明的 void 块统一包一层外框，插件只声明：

```ts
ElementSpec.frame?: true | {
  appendParagraph?: boolean;                 // 末尾「添加段落」，默认显示；只读且为最后一块时隐藏
  keys?: Readonly<Record<string, string>>;   // 选中时的按键 → 命令 id，命令收到该元素
}
```

- 外框统一提供：点选与选中描边、点到外面取消、右键打开块菜单（条目与块手柄同源）、选中时 Delete / Backspace 删除并在原位留空段落、Esc 取消。其余按键（如画廊的 Enter 编辑、空格预览）按 `keys` 声明映射到命令，不写回调。
- 声明外框后 `render` 只渲染内容：外框持有 attributes 与 children，`render` 收到空的 attributes 与 null children，照常展开也无害。外框只接受 `kind: "block"` 且 `isVoid` 的元素，否则该扩展不装配。
- 外框只作用于声明了它的块；内置块保持各自实现，不迁移。选中描边类与「块级按键是否该拦」的判定从媒体包移入内核，媒体包改为引用。
- 块属性条以通用名 `BlockToolbar` / `BlockToolbarButton` / `BlockToolbarGap` 开放，由编辑器运行时注入现有 `MediaToolbar` 实现（保留「按下不抢编辑器选区」、上方浮出放不下翻到下方），内置块的引用不改。
- 媒体查看器开放为 `useMediaViewer(element)`，返回 `(index?) => void`：打开时需要当前编辑器，所以是 hook；灯箱按文档中各节点的 `resources` 声明收集（M2a）。

### 4.6 通用原语与外观

- `packages/ui/src/primitives/Sortable`：基于 pointer 事件的列表与网格排序，不依赖 react-dnd；按指针下的项决定落点，手柄获得焦点时方向键前后移动一位，Esc 取消。画廊图片排序、插件设置列表、数据库选项排序都可用。
- 媒体外观默认值经 SDK `useMediaAppearance()` 读取，返回圆角 / 阴影预设（`none` / `sm` / `md` / `lg`），插件按预设映射到主题 token；节点自身的覆盖仍存在节点字段。编辑器没有由 kit 向根节点写 CSS 变量的机制，不为此新增内核能力，改用编辑器服务 `IMediaAppearance`：博客 kit 用发布设置注册（与传给 `createImageExtensions` 的同一份），桌面各处编辑器取同一份用户设置，直接读设置。内置 image 保持现有 `ImageExtensionOptions.appearance`。
- 圆角 / 阴影预设表与布局计算是纯函数，插件自留一份，不进 SDK。

## 7. 不加载插件的端

移动端、浏览器扩展、官网文档站不运行插件。插件节点目前按未知节点保护，只保留数据。

沿用编辑器内核现有的未知节点占位（`core/components/ElementGuard` 的 `UnknownElement`），数据原样保留，不新增移动端渲染。占位文案目前直接露出节点类型（「此处的「image-gallery」内容在当前编辑器中无法显示」），改为不含类型名的通用说法，用户感知不到插件。

## 8. 不做

- 不开放 slate、react-dnd、`@tau/editor/api` 原始组件。
- 不开放任意路径读取、强制缓存、资源库选择器。
- 画廊 Markdown 不补解析器，与现状一致。
- 内置块不迁到外框、不改用新的资源 hook，渲染与交互保持现状。

## 9. 分期

1. **M1 资源与组件（下一版 SDK）**：4.1、4.2、4.6 的外观读取；桌面与博客注入实现（复用现有插槽与资源服务，内置块渲染不改）。代码已完成，见第 11 节。
2. **M2 声明与编辑器能力**：4.3 声明及随库保存、4.4 `useElement`、4.5 外框 / `BlockToolbar` / `openMediaViewer`、`Sortable`；内置节点补 `resources` 声明，第 6 节消费者改读声明；未知节点占位文案去掉类型名。
3. **M3 画廊拆分**：独立仓库与插件，宿主删除第 6 节内容；真实插件包在桌面初始 / 重启 / 停用 / 恢复四阶段与博客发布验证。
4. **回归**：之后再有媒体块插件化或第三方媒体块时，若仍需给 SDK 补专门接口，说明这里的抽象有问题。

每期同步 SDK、作者模板文档、桌面 03 指南与本专题 README / 05。

## 10. 裁决

已确认（2026-10-21，用户）：

1. 按通用能力设计，不为单个功能开口子；开放资源层与默认媒体组件，作者可以完全重写。
2. 方案文档在独立 worktree 编写，与问题管理 SDK 升级分开推进。
3. 协作层只认 `resources` 声明，不按字段名推断；资源字段由节点声明方负责（4.3「协作只认声明」）。由此推出 `resources` 声明必须随库保存，主进程才能在不执行插件代码时读取。

4. 不加载插件的端沿用现有未知节点占位（第 7 节），文案不露出类型名，不新增移动端渲染。
5. 不扩大改造范围：外框等新能力只给插件块用，内置块只补数据声明，本方案只拆画廊。
