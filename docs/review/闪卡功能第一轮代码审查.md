## P0 · 阻断

### 1. `flashcardCardEdit` 路由必填参数过严，主要建卡/编辑入口被静默吞掉

- 位置：`apps/mobile/src/features/flashcard/pages/flashcardCardEdit.page.tsx:22-27`
- `type: paramString()`、`refContentId: paramNumber()`、`refTitle: paramString()` 均为无默认值的必填参数。router 的 `sanitizePageParams` 校验失败时**静默忽略导航**（`RouterProvider.tsx:174-180`，仅 console.warn）。推演各入口：
  - 卡组页「＋ 新建闪卡」→ push `{deckId, cardId: -1}`（缺 type 等 3 项）→ **页面打不开**
  - 卡组页点卡片编辑 → push `{deckId, cardId}`（缺 type）→ **打不开**
  - 建卡选题页选题型 → push `{deckId, cardId: -1, type}`（缺 ref* 2 项）→ **打不开**
  - 全局搜索点闪卡结果 → push 全量参数，其中 `type: "qa"`、`refContentId: -1` 是**绕过校验的假参数**（`search.page.tsx:66-73`）——workaround 坏味道，反向证明 schema 设计错误
- 修复：schema 三参数改 `paramOptional(...)`；`CardEditPage` 的 `type` prop 改可选并给默认题型；删除搜索页 dummy 参数。

## P1 · 高

### 2. `flashcard_review_stats` N+1 查询：统计页一次 364 次查询

- 位置：`flashcard_review.rs:112-154`；调用方 `FlashcardStatsPage.tsx:19,29`（`STATS_DAYS = 364`）
- 对每个 `day_start` 各做一次 prepare + query。统计页打开即触发 364 次查询。
- 修复：单次范围查询拉回 `rating, review_time`，Rust 内按 dayStarts 归桶（时区安全，不受 DST 影响），保持 API 不变。

### 3. `trigger_reconcile` 在事务提交前调用，索引可能漏行且无补救

- 位置：`flashcard_cards.rs:234/295/323`（create/update/delete card 均在 `tx.commit()` **之前**调用）
- `trigger_reconcile` 是 `tauri::async_runtime::spawn`（`reconcile.rs:544-572`），异步任务可能抢在 commit 前执行 `load_indexable_rows`，读到旧数据 → 新建/修改/删除的卡片不进索引；rerun 机制只在「运行中又有新触发」时补跑，此处 commit 后无再次触发，**无补救**。
- 同文件 `flashcard_delete_deck`（`flashcard_decks.rs:126`）是 commit 后调用——正确写法，同批代码两种顺序，属笔误级不一致。
- 修复：三处移到 `tx.commit()` 之后。

### 4. 桌面对照：custom 引用写库口径与桌面不一致（count=0、无 operation 日志）

- 位置：`flashcard_cards.rs:105-118` vs 桌面 `content.ts:203-212`
- 桌面 custom 引用建 contents 行时 `count = getContentLength(content)` 并写 operation 日志（同步管道感知）；移动端裸 INSERT 写 `count=0`、无 operation。
- **缓解因素**：移动端前端只会传 `refType: "content"`（见 `tauri.ts` flashcardCreateCard 类型注释），custom 分支实为不可达死路径 → 归入消融轮删除（删掉后两个问题同时消失），此处记录数据风险。

## P2 · 中

### 5. `parse_card_row` 对可空列无容错，一行 NULL 毒化整个列表/队列

- 位置：`flashcard_common.rs:58-89`；schema 中 difficulty/review_level/ease_factor/review_count/status 均可空（`50_learning.sql:199-218`），桌面端全部有 fallback（`flashcard.ts:436-448`），移动端 `row.get` 遇 NULL 直接 `Err` → 整个命令失败。
- 修复：按桌面口径补默认值（`Option` 读取 + unwrap_or）。

### 6. `flashcard_update_card` 换 deck_id 时不校验目标卡组存在

- 位置：`flashcard_cards.rs:275`；create 有校验（`:199-209`），update 没有——自身不对称，批量移动可能造孤儿卡。
- 修复：deck_id 变更时补同样校验。

### 7. `flashcard_update_card` 对非数组 prompt/detail 静默丢弃

- 位置：`flashcard_cards.rs:250-257`；`Some(非数组)` 时不报错也不写入，用户编辑被静默吞掉；create 是报错的（`:189-191`）——不一致。
- 修复：与 create 对齐，报错。

### 8. `FlashcardDeckPage` 双全量查询

- 位置：`FlashcardDeckPage.tsx:56-71`；`cardsQuery`（带筛选）+ `allCardsQuery`（全量）各拉一份完整卡片列表（含 references + Slate JSON），大卡组翻倍开销。
- 修复：只拉一次全量，筛选/搜索在前端 `useMemo` 完成（数据已在内存，且搜索框本就需要即时反馈）。

### 9. `CardCreatePage` 无卡组时题型仍可点

- 位置：`CardCreatePage.tsx:39-43,85-91`；decks 为空时 `deckId` 保持 -1，点题型带 -1 进编辑页 → 保存时才报「归属卡组不存在」。
- 修复：无卡组时禁用题型区并给出引导。

### 10. `nextIntervalPreview` 与 Rust 调度公式有系统性偏差

- 位置：`constants.ts:75-89`；预览用评分**前**的 ease（仅 clamp），Rust `calculate_schedule` 用评分**后**的新 ease（`flashcard_schedule.rs:62-63`）→ easy 档预览偏短、hard 档偏长。
- 修复：预览公式补 `ease_delta`，与 Rust 同式。

## P3 · 低 / 记录

- **复习队列 limit 语义**：移动端默认 20、clamp(1,100)；桌面不传则全量。移动端 UI 按「20 张一批 + 续批」设计（`FlashcardReviewPage` startNextRound），属产品化差异可接受，但 >100 静默截断无提示——已由续批机制兜底，记录不改。
- `FlashcardDeckStats.lastReviewedTime`：Rust 计算 MAX(last_review_time)，前端从未消费——保留（对齐桌面 stats 结构，成本一行）。
- `mastered` 百分比口径（(total-due-new)/total）把「到期未复习」算作未掌握——产品语义，记录。
- 移动端更严校验（name/title trim+非空、type 枚举、rating 枚举报错）与桌面宽松行为不同——移动端做法更安全，保留。
- 桌面有 `includeUpcoming`/`tag` 过滤参数，移动端未实现——YAGNI，当前无 UI 需要。
- `CardBatchBar` 批量操作逐张串行调用单卡接口（N 次事务）——正确性无虞，交互规模小（多选上限为列表可见量），记录不改。
- references 排序两端不同（移动 `update_time ASC`，桌面自然序）——影响极小，保留移动端确定性排序。

## 消融候选（冗余设计，留待消融轮处理）

1. `cardDraft.ts` 的 `parseTextWithBlanks` / `textToDescendants`：无任何消费者（仅 `genId` 被引用）。注释声称「AI 制卡数据格式互通」，但移动端不存在 AI 制卡链路——纯 YAGNI。
2. `ReviewQueuePayload.statuses`：前端恒传 `null`（`tauri.ts` flashcardGetReviewQueue），Rust 端该过滤分支不可达。
3. `replace_references` 的 custom 分支 + `FlashcardReferenceInput.custom_content`：前端类型层面只会传 content 类型（P1#4）。
4. `flashcardListCards` 的 `limit` 参数：前端所有调用点均不传；且修复 P2#8 后 `statuses`/`search` 服务端过滤也将失去调用方，Rust 端一并瘦身。
5. `MobileEditorBottomToolbar.visibleButtons` 白名单机制（`MobileEditorBottomToolbar.tsx:87-94,224-231`）：实现干净，但需确认是否仅闪卡一处使用；若单场景，可评估更轻的替代——暂保留（对齐「能编辑的就能渲染」约束，设计意图明确）。

## 架构评价

- 分层清晰：`pages/`（路由壳，仅参数解码与导航）→ 特性组件（UI + 本地状态）→ `queries.ts`（react-query 订阅）→ `services/tauri.ts`（IPC）→ Rust 命令层（CRUD/调度/统计分文件）。判分纯函数独立成 `reviewFlow.ts` 并有单测，调度算法在 Rust 侧单点权威且有桌面对照测试，均为正确决策。
- 符合工作区规范：浮层全部使用 `BottomSheet`/`ActionSheet`/`MobileConfirmDialog` 内置返回拦截；复习页 overlay 用 `useBackHandler` 消费返回（页面非容器组件，无需 backDismiss）；无 popstate 直接监听。
- 前向兼容意识好：`RichContent` 未知节点降级纯文本、`parse_rich_text_column` 非 JSON 降级段落、`buildData` 以原卡 data 为底合并防字段清空。

# 第三轮 · 消融实验（删除不必要/不合理的设计）

## 已删除（每项均验证编译 + 测试 + 调用方对齐）

| #   | 删除项                                                      | 理由                                                                                                                                                                                     |
| --- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `cardDraft.ts` 的 `parseTextWithBlanks`/`textToDescendants` | 无任何消费者；注释声称的「AI 制卡互通」在移动端不存在该链路（纯 YAGNI）                                                                                                                  |
| 2   | `ReviewQueuePayload.statuses`                               | 前端恒传 null，过滤分支不可达                                                                                                                                                            |
| 3   | `FlashcardReferenceInput.custom_content` + custom 写入分支  | 前端类型只允许 content 型；顺带消除「custom 引用 count=0/无 operation 日志」与桌面的两处数据口径分歧（P1#4 就此关闭）；桌面存量 custom 引用的读取/展示路径（LEFT JOIN contents）不受影响 |
| 4   | `ListFlashcardsPayload` 的 `statuses`/`search`/`limit`      | Deck 页改前端过滤后无调用方；`deck_id` 收窄为必填                                                                                                                                        |
| 5   | `UpdateFlashcardPayload.references`                         | 前端签名无此字段，update 重写引用在移动端不可达                                                                                                                                          |
| 6   | `UpdateFlashcardPayload.status` + update SQL 的 status 列   | 无调用方传；顺带带来正确性收益——编辑内容不再可能重置调度状态                                                                                                                             |
| 7   | `queries.ts` 的 `localDayStart` 导出                        | 无外部消费者，改模块私有                                                                                                                                                                 |
| 8   | `RichContent` 的 `BlankRenderProps.disabled`                | 无调用方传入                                                                                                                                                                             |
| 9   | `flashcard.rs` 的 `pub use flashcard_types::*` + allow 属性 | 子模块各自精确导入，重导出无人使用（删除后 cargo 0 警告）                                                                                                                                |

## 评估后保留（消融结论）

| 设计                                                | 结论 | 理由                                                                                    |
| --------------------------------------------------- | ---- | --------------------------------------------------------------------------------------- |
| `MobileEditorBottomToolbar.visibleButtons` 白名单   | 保留 | 单场景但替代方案（复制 700 行工具栏）更差；机制 15 行、约束「能编辑的就能渲染」意图明确 |
