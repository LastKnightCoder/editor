## 一、发现并修复的问题总览

### 1. 致命缺陷（P0）

| #    | 问题                                                                                   | 根因                                                                                                                                                                                                                                                                                                                                                                         | 修复                                                                                             |
| ---- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| P0-1 | **范围查询事务未 commit，物化全部回滚**（第 1 轮子 agent 发现）                        | `calendar_event_get_by_date_range` 在 `conn.transaction()` 内执行 ensure/物化/写 operation，函数返回时 tx 被 drop——rusqlite 默认 `DropBehavior::Rollback`。表现为：详情页点开物化事件永远「加载中」、每次查询重复物化且事件 id 永不稳定、纯浏览永远不持久化系统日历、operation 日志丢失导致桌面统计口径分叉。单测自建事务自行 commit，恰好绕过命令层编排，故测试全绿线上必现 | 物化分支后显式 `tx.commit()`（`calendar_events.rs`）                                             |
| P0-2 | **事件 create/update 同线程重入连接锁死锁，冻结全 App 数据层**（第 2 轮子 agent 发现） | `open_active_database` 返回持有全局 `MutexGuard` 的 `ActiveConnection`；`calendar_event_create/update` 尾部直呼 `calendar_event_get_by_id(app, …)`，后者再次 `open_active_database` → 同线程二次 `lock()` 永久挂起，所有 DB 命令排队等锁                                                                                                                                     | 抽 `get_event_by_id_with_conn(&conn, id)` 内部函数，commit 后复用同一连接回读                    |
| P0-3 | **编辑任意日程会静默删除富文本详情**（主 review 发现）                                 | 编辑页 `handleSave` 固定传 `detailContentId: 0` + Rust 全字段覆盖 + 旧内容引用计数回收 → 一次编辑即清空详情并删除 contents 行                                                                                                                                                                                                                                                | 前端 draft 记录并回传 `detailContentId`；Rust `detail_content_id` 为 `None` 时保留旧值（双保险） |

### 2. 数据一致性与两端互通（P1/P2）

## 三、已知接受不修（记录在案）

1. **DST 固定偏移局限**：`tz_offset_minutes` 随调用刷新但单次计算假设每日恒 24 小时；目标用户无夏令时，方案已知。
2. **`calendar_update` 无法把日历移出分组**（`groupId: null` 回退现值）：前端无此功能，桌面同语义，DTO 层留待 P1。
3. **`generate_occurrences_in_window` 从规则 start 逐日迭代**：量级可控，桌面同款；interval 对齐跳步留作真需要时再做。
4. **interval>1 时 weekly/weekdays 与桌面可见性分歧**（桌面 `weekdays` 型忽略 interval、不消费 maxOccurrences）：移动端语义更符合直觉，属「更正确的偏离」，已在方案文档记录。
5. **移动端无 `cleanupOrphanedEvents` 等价例行清理**：当前写路径很难产生孤儿（系统日历不可删），注释已如实描述。
6. **管理页可见性开关（库 `visible`）与主页 chips（localStorage）双轨**：桌面同样 `visible + selectedCalendarIds` 双轨，管理页已加作用范围说明文案。
7. ActionSheet 组件存量 flaky 测试与本次改动无关（基线复现确认）。
