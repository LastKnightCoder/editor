# 用户反馈：独立反馈窗口 + 管理后台

> 状态：V1 已实现（2026-10-20），待用户视觉验收；部署前需先建 R2 桶 `tau-feedback` 并执行 0010 迁移（见门户运维手册）。界面 mockup 见 [mockups/index.html](mockups/index.html)，接口以 `apps/plugin-portal/docs/协议.md`「桌面端用户反馈（0010）」为准。

## 目标

- 桌面端用户提交文字和截图（最多 3 张），不需要登录。
- 管理员在插件门户工作台的「用户反馈」页查看、标记状态、写内部备注、停用滥用身份。
- 截图里可能有用户的笔记正文，所以要**明确由用户选择是否附上、可以预览、可以打码、到期自动删除**。

## 关键结论：图片怎么传、存在哪

「直传 R2」和「base64」是两个不同层面的问题，分开看：

| 问题                           | 选项                                                                   | 结论                                                                                                                                                 |
| ------------------------------ | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **谁先拿到字节**（决定防滥用） | ① 客户端用预签名链接直传 R2 ② 客户端发给 Worker，校验后由 Worker 写 R2 | **②**。预签名链接一旦签发，服务端就看不到上传的内容了，类型、尺寸、图片头都没法校验；而门户现有的 `uploads.ts` 本来就是由 Worker 接收、校验后再写 R2 |
| **最终存在哪**                 | ① D1（base64 / BLOB）② R2 私有 bucket                                  | **②**。D1 单行有 2 MB 上限、整库 10 GB，图片放进去会拖慢查询、备份和 Time Travel；R2 有 10 GB 免费额度，按生命周期自动清理                           |
| **传输编码**                   | ① JSON + base64 ② multipart/form-data                                  | **②**。base64 会多出约 33% 的体积，而且现有的 `body()` 只收 100 KB；Electron 主进程原生支持 `FormData` + `Blob`，复杂度和 base64 一样                |

所以：**用户的担心（被滥用）靠「Worker 当闸门 + 私有 bucket」解决，不靠 base64 解决。**base64 本身也能用：压缩后 3 张图约 0.5–1.2 MB，编码后 1.6 MB 左右，Worker 收得下。只是这样既不省事，也挡不住滥用。

### 体积估算

| 来源                          | 原始    | 客户端压缩后（长边 ≤ 1920，WebP q≈0.8） |
| ----------------------------- | ------- | --------------------------------------- |
| Retina 窗口截图 2880×1800 PNG | 2–5 MB  | 150–400 KB                              |
| 3 张上限                      | 6–15 MB | ≤ 1.2 MB                                |

服务端硬限制：单张 ≤ 1.5 MB，单次请求总大小 ≤ 5 MB（用 `readLimited` 边读边截断），文本 ≤ 4000 字。

## 防滥用（层层兜底）

1. **身份**：复用门户已有的匿名身份 `/v1/visitor-session`。签发时已经按 IP 每小时 60 个限流；令牌只放在桌面主进程（`plugin-center-visitor.ts`），渲染进程拿不到。
2. **频率**：每个匿名身份每天 5 条、每个 IP 每天 20 条（`app_feedback_ip_limits`，加盐哈希分桶，不存原始 IP），**全站每天写入附件累计 1 GiB 熔断**（`app_feedback_daily_bytes`），超出就返回 429，最坏情况下的成本也有上限。
3. **内容校验**：只接受 PNG / JPEG / WebP，**看文件头魔数，不信 Content-Type**；拒收 SVG（防 XSS）。日志必须是 gzip（魔数 1f 8b），各 ≤3 MiB；整个请求 ≤12 MiB，边读边截断。只接受桌面端：带 Origin 的浏览器请求一律 403。
4. **私有存储**：新建 `tau-feedback` bucket，**不绑公开域名、不签发预签名链接**。图片只能通过管理员会话、由 Worker 读出来。这样就算有人恶意上传，这里也没法被当成图床对外分发（这才是公开 bucket 被滥用的主要方式）。
5. **管理端安全展示**：返回附件时带上 `Content-Security-Policy: sandbox`、`X-Content-Type-Options: nosniff`；图片 inline，日志以 `.gz` 下载。门户用带会话的 fetch 取回 Blob，再以 object URL 交给 `<img>`。
6. **处置**：V1 只能在反馈页按匿名身份筛选；停用身份目前要经评论管理（需要该身份有评论），反馈页直接停用留待后续（需要独立的审计记录）。已停用的身份不能再提交反馈。
7. **数据保留**：反馈记录和附件永久保留，不自动删除。定时任务只清理过期的额度计数（`app_feedback_ip_limits` 和 `app_feedback_daily_bytes`）。R2 不配置生命周期规则。如需删除历史数据，应通过独立的管理工具或手动操作完成。

## 隐私

- 默认**不自动附截图**。截图通过「截取窗口」/ 选文件 / 粘贴加入，缩略图可以删除、可以打码，打码直接涂进图片里，原图不上传。
- 环境信息逐项展示、可以整体关闭：版本、架构、系统、当前页面 key、主题、语言。不采集正文。
- 日志默认不勾选，由用户选择是否附带（见下文「日志」）；勾选后提示「日志可能包含文件名和笔记标题」，并提供「在文件夹中查看」。
- 联系方式选填。表单底部只放一行说明：「截图只有开发者能看到」。

## 数据与接口

门户 D1 迁移 `apps/plugin-portal/infra/migrations/0010_app_feedback.sql`：`app_feedback`（正文、类型、联系方式、环境 JSON、状态、内部备注、revision）、`app_feedback_attachments`（kind = image / log / perf，对象键与大小），以及两张额度表。后端在 `api/app-feedback.ts`，契约在 `contracts/index.ts` 的 `APP_FEEDBACK_LIMITS` / `AppFeedback*`，接口细节见协议文档。

> 命名：门户里已有的 `api/feedback.ts` / `submission_feedback` 是插件审核留言。新模块叫 `app-feedback`，路由 `/v1/app-feedback` 与 `/v1/moderation/app-feedback`，避免混淆。

管理页在门户工作台「管理员 › 用户反馈」（`/app-feedback`）：左栏按状态（新反馈 / 处理中 / 已解决 / 已忽略 / 全部，带计数）和类型筛选，右栏看正文、截图（点开大图）、环境、联系方式、日志下载、内部备注，可改状态；版本冲突时提示并保留备注草稿。

## 桌面端落点

### 形态：独立反馈窗口（已定）

反馈表单是一个独立窗口，不是主窗口里的浮层。这样用户可以一边操作主窗口复现问题，一边随时截图。参照快捷卡片窗口（`createQuickCardWindow` + 路由 `/quick-card`）：

- **窗口**：在 `src-electron/main/windows/utility-windows.ts` 加 `createFeedbackWindow({ attachCapture? })`，路由 `/feedback`，440×640，`minWidth 400`，用 `registerWindow` 保持单例（再次唤起时 `focusExisting`，草稿不丢），用 `initialBounds/rememberBounds` 记住位置。首次打开贴在主窗口右侧。
- **置顶**：默认 `alwaysOnTop`，标题栏图钉切换（`setAlwaysOnTop`），不持久化。
- **界面**：`features/feedback/windows/FeedbackWindow.tsx`，标题栏复用 `AuxWindowTitlebar`；表单、标注、成功页都在这个窗口里切换视图。标注时 `setBounds` 加宽到 880，完成后恢复。
- **配色**：整个窗口 `bg-surface`；输入框、环境信息和窗口同底色，只用 `border-line-1` 描边区分，不使用 page / sunken 这类更深的底色。
- **关闭**：有内容时先确认是否丢弃；V1 不跨关闭持久化草稿。

### 入口

`app/navigation.ts` 的 `NAV_FOOTER` 加「反馈」（新增 `opensWindow: "feedback"` 入口类型，不塞进 overlay）；命令面板加「发送反馈」「截取当前窗口并反馈」；托盘菜单加「发送反馈…」。应用没有菜单栏，所以原方案的「帮助 → 发送反馈」改为托盘入口。所有入口都经 `app-feedback:open` 打开反馈窗口，并带上当前页面 key。

### 截图

- 「截取窗口」默认截主窗口，下拉列出已打开的 Tau 窗口（主窗口 / 编辑窗口 / 番茄小窗…，取自 `window-registry`），主进程调用对应窗口的 `webContents.capturePage()`。截的是那个窗口自身的画面，**截不到反馈窗口，也不需要屏幕录制权限**。
- 截别的应用或整个屏幕，就用系统截图后 `⌘V` 粘贴，不自己实现区域截图。
- 「截取当前窗口并反馈」：先截发起入口的那个窗口，再打开反馈窗口，截图作为第一张附件。
- 渲染端用 `OffscreenCanvas` 打码并压缩成 WebP（长边 ≤ 1920），再交给主进程。

### 提交

主进程模块 `modules/app-feedback.ts`（`layer: BACKGROUND`），用 `visitorHeaders(origin, true)` 拿到令牌后，通过 `net.fetch` 发出 multipart 请求；渲染进程只拿得到结果（成功 / 离线 / 限流 / 校验失败）。失败时保留表单，用同一个 `clientRequestId` 重试；第一版不做离线队列（YAGNI）。

## 日志

反馈窗口的「附带日志」有两个独立勾选项，默认都不勾：

- **普通日志**：本次运行的 session 日志尾部 2 MiB，加上次运行的尾部 1 MiB（卡死或崩溃后重开时，问题多在上一份日志里）；跳过轮转产物，gzip 后上传，≤3 MiB。
- **性能日志**：perf-monitor 内存里近 1 小时的诊断数据（与「导出性能快照」同一份 `buildSnapshot()`），gzip 后超限时先去掉启动 CPU 剖析，仍超限就提示取消勾选。

## 错误报告

`components/ErrorState` 在 Electron 下于「技术详情」一行提供「发送错误报告」：一键提交，类型为问题，正文是错误摘要和堆栈（超长截断到 4000 字），附带环境信息和普通日志，不带截图。悬停提示写明会附带哪些内容。同一个错误重试复用请求 ID，不会重复提交。路由级错误页、页面栈每页和局部区域的兜底都用 `ErrorState`，所以三层兜底都自带这个入口；它和普通反馈共用每天 5 条的额度。

## 实现状态与后续

已实现：独立反馈窗口、截取窗口（可选窗口）/ 选文件 / 粘贴、框选与打码标注、环境信息、普通日志与性能日志、错误页一键报告、门户收件箱（状态、备注、按身份筛选）。反馈记录和附件永久保留。
