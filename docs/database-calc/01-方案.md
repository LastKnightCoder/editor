# 数据库汇总与公式 · 方案

## 1. 为什么要做

数据库（`@tau/database`）有 9 类内置字段，但只能存值、不能算值：没有表尾合计，也没有由其他列派生的列。用户要的是 Notion 那两件事——**列相加**（表尾求和 / 平均 / 计数）和 **IF 判断**（按条件派生一列）。

现状（2026-10-08 调研）：

- 全仓零处汇总 / 公式 / rollup 代码与设计；唯一的聚合是看板 / 画廊分组头的 `rows.length`。
- 唯一的派生层是 `core/projection.ts` 的 `projectDatabase`：筛选 → 搜索 → 排序 → 分组，渲染端纯函数，输入是全量行。
- `ColumnDef.type` 是裸 `string`，字段类型由运行时注册的 `CellPlugin` 决定；`CellValue` 含 `| any`，没有任何值类型守卫。
- 存储是 `data_tables.columns` / `rows` 两个 JSON 文本，视图配置在 `data_table_views.config`；SQL 层无法按列聚合。
- 移动端不读数据表，本能力只涉及桌面端。

## 2. 定位

**一句话**：一棵受限的 JSON 表达式树，两个求值范围——整列（表尾汇总）和单行（公式列）；构造器是这棵树的图形投影，AI 产出同一棵树。

- **不定义文本 DSL**：没有词法 / 语法分析，没有文本往返。存储、构造器、AI 输出、校验器都直接面对同一个 JSON 结构。
- 表尾汇总 = 视图上的展示配置；公式列 = 一种新字段类型（`formula` 插件）。两者共用引擎，入口分开。

## 3. 核心规则

1. **AST 是唯一事实源，但只在内部**。构造器只增删改节点，不生成文本；AI 只产出节点。用户只看到槽位、预览与人话提示，看不到 JSON、表达式文本或错误码（DC-013）。
2. **白名单算子**：只有 §6.1 列出的节点种类；无变量绑定、无循环、无自定义函数、无 `eval`。
3. **静态校验先于求值**：列存在性、类型匹配、引用成环、深度上限在保存时检查，不合法不允许保存。
4. **结构化结果**：求值返回 `{ ok: true, value } | { ok: false, error }`。单行出错只影响那一格（显示 `—`，悬停给一句人话原因；错误码只在内部映射文案），不抛异常、不清空整列。
5. **公式值不落库**：渲染时派生，存储只有表达式。
6. **按 columnId 引用**：改列名不影响表达式；删列后引用处报 `missing-column`，不静默改写表达式。
7. **汇总算筛选后的行**（与 Notion 一致，DC-007）。
8. **能推断的不让用户选**：菜单与构造器的可选项由列的值类型推导，必然出错的组合不出现。

## 4. 用户流程

- **表尾汇总**：悬停表格底部出现每列的汇总格 → 点击 → 菜单选「求和」→ 立即显示。菜单按列值类型收窄（文本列没有求和）。末项「公式…」进构造器做组合（如 `求和(小计) × 汇率`）。
- **公式列**：新建列 → 类型选「公式」→ 列编辑弹窗展开构造器 → 选根节点（四则 / IF / 拼接 / 比较）→ 逐槽填列或常量 → 右栏实时预览前几行 → 保存。
- **AI**：构造器顶部输入框写「单价乘数量超过 500 就是高」→ 生成的树回填构造器 → 用户可继续手改 → 保存时走同一个校验器。

## 6. 数据与技术方案

### 6.1 AST

```ts
// packages/database/src/core/formula/types.ts
export type ValueType = "number" | "text" | "boolean" | "date";

export type Expr =
  | { kind: "literal"; value: number | string | boolean | null }
  | { kind: "column"; columnId: string }
  | { kind: "binary"; op: "+" | "-" | "*" | "/"; left: Expr; right: Expr }
  | {
      kind: "compare";
      op: ">" | ">=" | "<" | "<=" | "==" | "!=" | "contains";
      left: Expr;
      right: Expr;
    }
  | { kind: "logic"; op: "and" | "or"; operands: Expr[] }
  | { kind: "not"; operand: Expr }
  | { kind: "if"; test: Expr; then: Expr; else: Expr }
  | { kind: "concat"; parts: Expr[] }
  | { kind: "empty"; operand: Expr }; // 是否为空

export type AggregateOp =
  "sum" | "avg" | "median" | "min" | "max" | "countAll" | "countNonEmpty" | "countEmpty" | "unique";

/** 表尾：单列聚合，或以聚合为叶子的组合表达式 */
export type FooterSpec =
  { kind: "aggregate"; op: AggregateOp } | { kind: "expr"; expr: FooterExpr };

export type FooterExpr =
  Exclude<Expr, { kind: "column" }> | { kind: "aggregate"; op: AggregateOp; columnId: string };
```

- 行内表达式不能含 `aggregate`，表尾表达式不能含 `column`——由类型和校验器双重保证。
- 第一版不含日期运算（DC-009）；`date` 仅参与比较与「是否为空」。

### 6.2 值类型：插件声明，引擎不认识具体字段

`CellPlugin` 增加两个可选成员：

```ts
valueType?: ValueType;
/** 把存储值转为参与运算的标量；缺省按 valueType 直接取值 */
toScalar?: (value: CellValue, column: ColumnDef) => number | string | boolean | null;
/** 数值汇总结果的展示文本（数字列沿用小数位 / 前后缀，进度显示百分比） */
formatScalar?: (value: number, column: ColumnDef) => string;
```

| 插件                                        | valueType           | toScalar                                    |
| ------------------------------------------- | ------------------- | ------------------------------------------- |
| number / star                               | number              | 原值                                        |
| progress                                    | number              | `current / target`（target 为 0 返回 null） |
| text / link                                 | text                | 原值                                        |
| select                                      | text                | 选项 id → 选项名                            |
| multiSelect                                 | text                | 选项名以「, 」连接                          |
| checkbox                                    | boolean             | 原值                                        |
| date                                        | date                | `start`                                     |
| formula                                     | 取自列配置 `output` | 求值结果                                    |
| image / attachment / rich-text / card-links | 不声明              | —                                           |

未声明 `valueType` 的列不出现在构造器与汇总菜单的数值项里；`missingPlugin` 同理。引擎只依赖这两个成员，不 import 任何具体插件（宿主插件也自动接入）。

### 6.3 存储（零 schema 变更）

- **公式列**：`ColumnDef { type: "formula", config: { expr: Expr; output: ValueType; format?: NumberFormat } }`，随 `data_tables.columns` 持久化。`output` 由校验器推导后写入，供排序 / 筛选 / 下游引用直接读取。
- **表尾汇总**：`TableViewConfig.footer?: Record<columnId, FooterSpec>`，按视图存（同一张表不同视图可汇总不同列）。须同步：
  - `packages/shared/src/types/database.ts` 的 `TableViewConfig`；
  - 主进程 `data-table-view.ts` 的 `normalizeConfig`——它是逐键白名单，**不登记会在保存时被静默丢弃**。
- **行数据**：公式列在 `rows` 里没有值。`addColumn` 给存量行补 `null` 的逻辑对 `formula` 类型应跳过，保存路径应剔除派生值（见 §6.5）。
- 版本：`config.expr` 外不加版本号；未知 `kind` 一律 `bad-ref`，旧版本读到新节点只是该列报错，不影响整表。

### 6.4 引擎（`packages/database/src/core/formula/`，纯函数，零 React）

| 文件           | 职责                                                                                                                               |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `types.ts`     | §6.1 类型                                                                                                                          |
| `validate.ts`  | `validateExpr(expr, ctx) → { ok, type } \| { ok: false, errors }`：节点结构、列存在、类型推导与匹配、深度 ≤ 16、公式列依赖成环检测 |
| `evaluate.ts`  | `evaluate(expr, row, ctx) → Result`：受限递归，`and/or` 短路，除 0 返回 `div0`                                                     |
| `aggregate.ts` | `aggregate(op, values) → Result`；`evaluateFooter(spec, rows, ctx)`                                                                |
| `derive.ts`    | `deriveFormulaRows(rows, columns, plugins)`：按依赖拓扑序给每行填公式值，返回新数组；以 `rows` 与公式列配置引用做记忆化            |
| `__tests__/`   | 每个节点、每个错误码、成环、深度、空值语义、记忆化命中                                                                             |

错误码：`type`、`div0`、`missing-column`、`cycle`、`depth`、`bad-ref`。

空值语义：参与四则时空值 → 结果为空（不当 0）；比较时空值只与空值相等；拼接时空值视为空串；聚合忽略空值（`countEmpty` 除外）。

### 6.5 接入投影管线

`projectDatabase` 开头先调用 `deriveFormulaRows`，后续筛选 / 搜索 / 排序 / 分组看到的行已带公式值，**现有插件的 `filters` / `sort` / `search` / `getGroupKey` 无需改动**——formula 插件按 `output` 委托给 number / text / checkbox 插件的同名实现即可。

- 投影产出的派生行只用于展示；store 中的 `rows` 不含公式值，保存路径（`onDataChange` / 行补丁）读的是 store，不会把派生值写进库。实施时用测试守住这一点。
- 表尾汇总输入是 `projection.rows`（筛选后）。分组视图第一版只在表格底部显示全表汇总，不做分组小计（DC-010）。
- 性能：每次投影全量求值 O(行数 × 公式节点数)。行数据本来就在渲染端全量常驻，求值不引入新的数据拉取；`deriveFormulaRows` 记忆化保证编辑无关列、切换视图时不重算。若后续出现万行级卡顿，再按列粒度做脏标记，不提前设计。

### 6.6 formula 插件

`packages/database/src/plugins/FormulaPlugin/`：`editable: false`；`Renderer` 按 `output` 渲染（数字复用 `formatNumber`），错误显示 `—` + tooltip；`sort` / `filters` / `search` / `getGroupKey` 按 `output` 委托；`beforeSave` 恒返回 `undefined`（双保险，不让派生值进库）；列编辑弹窗中由 `FormulaBuilder` 产出 `config`。

### 6.7 AI 入口（宿主能力，组件包不依赖 AI）

- `DatabaseSlots` 增加可选 `formulaAssist?: (input: { prompt: string; columns: ColumnSummary[]; scope: "row" | "footer" }) => Promise<unknown>`。
- `DesktopDatabase` 在用户已配置模型时注入；未配置时不注入，构造器不显示输入框（沿用「配了模型即同意」，不设开关 / 预算 / 隐私提示）。
- 桌面实现：把 AST 的 JSON Schema 与列摘要（id / 名称 / valueType / select 选项名）交给模型，要求结构化输出。具体调用哪个现有模型服务在详细设计时确认。
- 返回值是 `unknown`，**必须经 `validateExpr`**；不通过则在构造器展示错误并保留用户输入，不回填半棵树。
- 不发送行数据，只发送列结构。

## 7. 不做

- 文本公式语法（`prop("单价") * prop("数量")`）及其解析器。
- 跨表 rollup / relation：当前没有关联字段类型，先有关联再谈汇总。
- 公式值落库、公式结果的手动覆盖。
- 自定义函数、正则、日期时区运算、条件格式（按值染色单元格）。
- 分组小计（第一版）。
- 移动端。

## 9. 迭代划分

同一版本内分三步提交，每步可独立测试：

1. **引擎 + 表尾汇总**：`core/formula/*` 与单测；`valueType` / `toScalar` 补到 9 个内置插件（宿主插件不声明，只能计数）；`TableViewConfig.footer` + `normalizeConfig`；表尾行与菜单。
2. **公式列**：formula 插件；`deriveFormulaRows` 接入投影；`FormulaBuilder`；`ColumnEditModal` 的 `includeConfig` 修正；表尾「公式…」组合表达式入口（依赖构造器，自迭代 1 移入）；删列 / 成环 / 派生值不进库的测试。
3. **AI 入口**：`formulaAssist` slot 与桌面实现；校验失败的展示。

每步完成：`npx tsc --noEmit`、`packages/database` 与 `apps/desktop` 相关单测、构建；视觉由用户验收。

## 10. 迭代 1 实施记录（2026-10-08）

- 落位：`packages/database/src/core/formula/`（`types` / `context` / `validate` / `evaluate` / `aggregate`），表尾 `views/TableView/components/FooterRow.tsx`，store `setFooter`；主进程 `data-table-view.ts` 的 `normalizeFooter`。
- 与方案的偏差：
  - 插件契约多一个 `formatScalar`：汇总值需按列格式展示（数字列小数位 / 前后缀、进度百分比），引擎不认识具体插件，只能由插件提供。
  - `FooterSpec` 只实现 `{ kind: "aggregate", op }`；组合表达式随构造器移到迭代 2。主进程只保留该形态的条目。
  - `cycle` 错误码与成环检测随公式列移到迭代 2（迭代 1 不存在列间引用）。
  - 各插件的标量口径：评分 0 星视为未评分（空）；进度取 current / target，插件把缺省值归一为 0%，与单元格显示一致，因而计入平均；复选框为 true / false，不会为空。
  - 删列时同步移除该列的表尾配置。
- 验证：`@tau/database` 类型检查与 83 个测试、边界检查；桌面端 tsc、数据库相关 72 个测试（含主进程 SQLite 往返）、vite build。视觉待用户验收。

## 11. 迭代 2 实施记录（2026-10-08）

- 落位：`core/formula/derive.ts`（依赖排序、成环检测、按源行缓存的派生）、`core/formula/footer.ts`（表尾单列汇总与组合表达式）、`plugins/FormulaPlugin`、`components/FormulaBuilder`（`index.tsx` 槽位与预览、`check.ts` 保存前检查）；`ColumnEditModal` 公式分支、表尾「公式…」弹窗。
- 与方案的偏差：
  - 表达式与 `FormulaColumnConfig`、`FooterSpec` 的组合形态移入 `@tau/shared/database-types`：它们已是存储协议（列配置与视图配置），引擎内仅做短名别名。
  - 插件契约：`valueType` 与 `filters` 都可按列给出（公式列的类型与可用筛选随结果类型变化）；筛选项统一经 `PluginManager.getFilterDefinitions(column)` 读取（原参数为插件类型）。
  - 派生行里公式列的值是 `{ value, error? }`，供渲染显示原因；插件 `toScalar` 拆包，筛选 / 排序 / 搜索 / 分组按结果类型工作，空值排序恒在最后。
  - 引用一个出错的公式列时按空值参与计算，不向下游传播错误。
  - 行详情另行派生显示值；宿主正文组件仍拿存储行，避免派生值被当成补丁写回。
  - 新增公式列不给存量行补 null；其他类型改为公式时删除该列的存储值。
  - 构造器的插入菜单在已有值上选运算时，把原值放进第一个空位（「单价 → 乘 → 数量」）；条件组用「以下全部 / 任一满足」表头，不在每项之间放连接词。
- 验证：`@tau/database` 类型检查、95 个测试（新增派生 / 插件 / 作用域 / 保存前检查 / 构造器组件）、边界检查、`@example/database` 构建；桌面端 tsc、数据库相关 73 个测试（含表尾组合表达式的 SQLite 往返）、vite build。视觉待用户验收。

### 11.1 构造器 v2（2026-10-08，用户验收 mockup 后改写）

- v1 的「空位 + 运算菜单」直接暴露表达式树，用户看不出运算先后，已废弃。v2 按 mockup `apps/desktop/mockups/database-calc/builder-v2.html`：先选意图（计算 / 按条件显示 / 拼接文字），每种对应形状固定的表单。值框可直接输入，▾ 改成某一列；菜单只有一层且不限高；删除按钮常显，每组至少保留 1 个。
- 嵌套：值框 ▾ 菜单底部的「改成计算… / 改成条件…」可在原地展开带边框的小表单（层与层交替底色），「撤销」只保留第一项；根表单下最多 2 层，到上限后菜单项变灰并提示拆列。

## 12. 迭代 3 实施记录（2026-10-08）

- 落位：组件包 `DatabaseSlots.formulaAssist(messages) => Promise<string>`（只负责把消息交给模型并返回文本）；提示词、解析、校验、还原成表单都在 `FormulaBuilder/assist.ts`；构造器顶部输入条 `AssistBar`，宿主未提供能力时不显示。桌面端 `features/shared/database/useFormulaAssist.ts` 用对话模型（`chat` 槽位）注入，用量归属 `formulaAssist`。
- 与方案的偏差：
  - slot 签名从「传结构化请求」改为「传消息、回文本」：只有组件包懂表达式结构，宿主只做模型调用。
  - 复用对话模型槽位，不新增设置项（沿用「配了模型即同意」）。
  - 容忍两类确定偏差：用列名代替列 id、日期写成 `YYYY-MM-DD` 文本；其余交给校验。输出必须通过校验且能还原成表单才回填；不通过时把原因反馈给模型重试一次，仍失败给出原因并保留用户输入。只发送列名、类型与单选选项，不发送行数据。
- 顺带修复：日期列与日期常量（毫秒数）比较被校验误判为「日期不能和数字比较」，构造器里的日期条件此前无法保存；表单往返测试补上校验断言。
- 枚举标签色：改用色相拉开的专用色板（蓝 / 橙 / 绿 / 紫 / 红 / 黄，不用灰），单选色板顺序的红 / 橙 / 黄在部分主题下几乎同色；匹配时忽略首尾空格。
- 验证：`@tau/database` 类型检查、107 个测试（新增 AI 提示词 / 解析 / 容错改写 / 重试 / 输入条交互、标签色区分）、边界检查、示例构建；桌面端 tsc、数据库相关 73 个测试、vite build。视觉与真实模型效果待用户验收。
