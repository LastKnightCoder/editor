# 知识地图万级规模：两项待定决策

2026-09-28 记录。批次 5 的压测与第一轮优化做完后（见 [handoff.md](handoff.md) §7.3），离线计算还剩两个大头，各自对应一项需要拍板的决策。这次没做，这里记下背景、数据与做法，下次直接从这里开始。

**什么时候该回来做**：卡片库到几千张、首次构建或整体重算明显变慢时。674 张时离线全量约 0.65 秒（实机日志），两项都不值得做。

## 现状（第一轮优化之后）

离线全量计算（合成库，Node，含 kNN）：

| 卡片数 | kNN    | 全量   |
| ------ | ------ | ------ |
| 674    | 0.16s  | 1.1s   |
| 5000   | 8.6s   | 20.5s  |
| 20000  | 2.4min | 4.4min |

5000 张的 CPU 剖析：kNN 41%，最后一轮力模拟约 50%（collide 19%、四叉树 visit/get 15%、manyBody 10%），其余不到 10%。两项决策正好对应这两块。

真实库 674 张（实机）：约 650ms。

## 决策一：kNN 换近似近邻（ANN）

### 现在怎么做

`src/knowledge-map/vectors.ts` 的 `knn`：精确暴力，O(n²·d)，d = 1024。已做的优化是只算上三角、向量打包成连续内存、点积 4 路展开，结果与朴素实现逐条一致。每张卡取 k = 8 个近邻，相似度低于 0.35 的不算。

输入是「一张卡一个向量」：索引库 `vec_documents` 里一张卡按分块存多条，`meanPool` 取均值再归一化。

### 为什么当初选精确解

kNN 的结果直接决定 Louvain 分出的主题。近似近邻漏掉几个真近邻、混进几个假近邻，主题边界就会变：边缘上的卡片换主题、同一份数据重算两次结果不同。用户看到的是主题的颜色和名字，边界一抖就是「这张卡上次在 CSS、这次跑到 DOM 了」。

### 要回答的问题

1. **抖动能不能接受？** 这是用户的判断，不是技术问题。要先量化再请用户决定：
   - 用真实库比对精确 kNN 与 ANN 的结果，统计：主题归属变化的卡片比例、主题数与主题名是否变化、每个主题的成员 Jaccard 相似度。
   - 用同一份数据跑两次 ANN（如果算法带随机性），看自身的稳定性。
   - 把两张地图并排给用户看。
2. **确定性**：现在同样的输入必定得到同样的地图（有单测「结果确定」）。ANN 若带随机种子，要固定种子；若依赖插入顺序，要固定顺序。
3. **增量放置要不要跟着换**：`placeIncrementally` 用的是 sqlite-vec 查近邻（`KnowledgeMapTable.neighborsOf`，按分块查、按卡片取最高相似度），和整体重算的 kNN 口径本来就不完全一样（分块 vs 均值池化）。

### 候选做法

| 做法                          | 说明                                                                 | 顾虑                                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **HNSW**（如 `hnswlib-node`） | 业界常用，召回率可调（`ef`），万级构建秒级                           | 原生依赖，要进 Electron 打包与原生模块校验（`scripts/verify-native-runtime.mjs`）；构建有随机性                                                                                                                                                                                                                                                                                                       |
| **用索引库现成的 sqlite-vec** | 不加依赖，向量已经在库里                                             | 仓库用的是 `sqlite-vec@0.1.7-alpha.2`。稳定版的 vec0 是精确暴力扫描（C 实现），快在常数，不在复杂度；上游较新的 alpha 版开始带 ANN 索引（rescore、DiskANN，ivf 还是实验性、默认不启用），见 [releases](https://github.com/asg017/sqlite-vec/releases)，但仍是 alpha。另外库里存的是分块向量，不是均值池化后的卡片向量：要么查 n 次、每次按卡片合并，要么另建一张卡片向量表。先实测 2 万张的总耗时再说 |
| **粗筛再精排**（纯 JS）       | 先降维（随机投影到 64–128 维）或按主题预聚类，只在候选集里算精确点积 | 自己实现，召回率要自己测；但没有新依赖，结果可以做到确定                                                                                                                                                                                                                                                                                                                                              |
| **不换算法，并行化**          | kNN 按行切给多个 worker_threads                                      | 仍是 O(n²)，只是除以核数；结果精确，零抖动                                                                                                                                                                                                                                                                                                                                                            |

倾向：先试「并行化」和「sqlite-vec 实测」这两个零抖动的选项，量出能省多少；只有它们不够时，才带着量化后的抖动数据去问用户要不要上 HNSW。

### 验收

- 2 万张 kNN 的目标耗时（待定，建议 30 秒以内）。
- 真实库上与精确解的主题归属一致率（阈值待与用户确认）。
- 「结果确定」单测仍然通过。

## 决策二：最后一轮力模拟换成一次性解重叠

### 现在怎么做

`src/knowledge-map/compute.ts` 末尾的分层布局：先摆大主题圆盘、再在主题内摆子主题圆盘，最后对全体卡片做一轮 d3-force 松弛，**固定 260 次迭代**，按主题岛分别跑。

每张卡的锚点是它在子主题圆盘内的向日葵螺旋位置（`seedWithinDisc`）。松弛里的力有：

- 语义边和显式链接的弹簧（距离 16/22）；
- 斥力（-14，作用范围 90）；
- 碰撞（半径 + 2，2 轮）；
- 锚点拉力（0.14）。

### 为什么不能直接减迭代次数

实测质量（最近邻间距中位数、间距小于 8 的点对比例）：

| 数据          | 80 次                | 140 次     | 260 次     |
| ------------- | -------------------- | ---------- | ---------- |
| 真实库 674 张 | 中位 12.7，过近 1 对 | 12.9，1 对 | 12.8，1 对 |
| 合成 5000 张  | 中位 6.7，过近 2.6%  | 8.9，1.3%  | 12.5，≈0%  |

真实库 80 次就够了，但合成的密集数据不行。原因是弹簧：螺旋起步时间距是 15.4，80 次后被语义边的弹簧压到 9.3，要靠后面的迭代让斥力和碰撞慢慢推回来。合成库的子主题更大（最大 123 张）、语义边更密，压得更狠。

试过但不行的：

- **去掉斥力**：2000 张 80 次后间距中位从 9.3 掉到 7.3、p10 掉到 3.2。斥力是在干活的。
- **按岛切开跑**：省掉了横跨全图的四叉树，真实库 1.55s → 1.11s；但万级时碰撞和斥力的成本主要随节点数走，帮助有限。

### 这一轮到底在做什么

锚点已经决定了「卡片大致在哪」，这一轮只做两件事：

1. 让有链接的卡片在岛内挨得更近一点（局部结构）；
2. 消除重叠。

第 2 件事不需要迭代：给定位置和半径，可以一次性把重叠推开。第 1 件事可以挪到算锚点的阶段：按链接关系决定卡片在螺旋上的**顺序**，相连的卡片排在相邻的槽位，就不用靠弹簧拉。

### 候选做法

| 做法                             | 说明                                                                                                  | 顾虑                                         |
| -------------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| **网格法解重叠**                 | 按最大直径建均匀网格，每个点只和相邻 9 格比较，把重叠的点对沿连线推开，重复 3–5 遍直到无重叠。O(n)    | 只解重叠，不再有「相连的挨近」；需配合下一项 |
| **螺旋槽位按链接排序**           | 子主题内按链接关系排序（例如按 BFS 序，或按主题内的一维谱嵌入）再依次放进螺旋槽位，相连的卡片天然相邻 | 局部结构的表现力不如力模拟；要看真实库的观感 |
| **保留力模拟，迭代数按收敛判断** | 每 20 次看一次最大位移，小于阈值就停                                                                  | 最省事，但对密集数据仍要跑满                 |
| **保留力模拟，弹簧减弱**         | 语义边的弹簧强度降低，减少压缩                                                                        | 画面会更「散」，要看观感                     |

倾向：螺旋槽位按链接排序，加网格法解重叠，完全去掉这一轮 d3-force。预计这一块从约 50% 降到几个百分点。代价是画面从「力导向的有机感」变成「更规整的一团」，**这是观感问题，要给用户看效果再定**。

### 验收

- 质量指标不劣于现在的 260 次：最近邻间距中位数约 12.5、过近点对约 0%。
- 跨主题连线长度不变差：真实库目前均长 160，不加桥接是 201。
- 岛内链接长度（真实库 p50 26、p90 42）不明显变长：变长说明「相连的挨近」丢了。
- 真实库的截图给用户确认观感。
- 现有单测全部通过，尤其是「同色主题不相邻」（岛间距 > 150）和「结果确定」。

## 压测怎么复现

脚本当时放在 `/tmp/km-bench/`，没进仓库，可能已经被清掉。要点如下，重写不难：

- **合成库**：主题数 `max(4, round(3·log10(n)))`，每个主题占 40 个不重叠的维度（维度总数 1024），子主题再加 20 维偏移 0.05，每维噪声 ±0.05（`(random() - 0.5) * 0.1`）。四成卡片有 1–3 条链接，其中 5% 跨主题。这组参数下相似度中位约 0.62，真实库是 0.68（p10 0.59、p90 0.79），量级对得上。噪声调到 0.3 以上就一个近邻都没有了。
- **真实数据只读**：见 [handoff.md](handoff.md) §5 最后一条（`better-sqlite3` 用 collaboration-server 那份，`{ readonly: true }`，加载 sqlite-vec 扩展）。
- **CPU 剖析**：`npx tsx --cpu-prof --cpu-prof-dir=<目录> 脚本.ts`，再按 `callFrame.functionName` 汇总各函数的自身耗时。
- **渲染帧率**：一定用系统 Chrome（Playwright 的 `channel: "chrome"`、`headless: false`）。无头 chromium 是软件光栅，674 张就只有 11fps，数据作废。
- **布局质量**：最近邻间距中位数，以及间距小于 8 的点对比例。点对用网格找（格宽 24），避免 O(n²)。
