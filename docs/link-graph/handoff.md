# 卡片关联图谱重做 · 转接文档

写给接手的新会话。读完这份就能继续，不需要翻旧对话。
所有路径相对 `apps/desktop/`，除非另注。

## 1. 原始需求

卡片视图里的「关联图谱」原先用 `@antv/g6` 实现：API 难用、难定制、样式丑。用户要自研 canvas 实现，重视**美观与交互感**，后续可能有 3D / 叙事视角。用户提的具体想法：

- 类似 Obsidian，按卡片创建时间做**入场播放**
- 按卡片之间的关系**自下而上形成主题簇**，给用户信息
- 节点交互
- 用户**手动触发** AI，结合主题簇给出建议和洞见（先不接 LLM 起主题名）
- 规模：当前约 700 张卡，**要按万级设计**（用户明确说过：不能只考虑现状、批次不能跳）

离线地图的重算时机：没算过 / embedding 指纹变了 / 一次新增 >10 张卡 / 漂移累计 >15% / 显式 `rebuild`。其余打开图谱时直接读库并对账。
漂移 = 增量放置过的节点 ∪ 重算后编辑过的卡片（`cards.update_time`），按卡片去重，都按行时间戳算，重启后仍准。
编辑不即时重新落位（改错别字不该让卡片在地图上跳；编辑刚保存时向量也还没重算），效果留给整体重算。
分层布局的三步（`compute.ts`）：

1. **摆大主题**：`topicAffinity` 算主题两两亲近度——跨主题边权之和**除以较小一方的规模**（「小主题有多大比例的关系指向对方」），显式链接再乘 `CROSS_LINK_BOOST`（4）；每个主题只留最强的 3 条（`strongestPairs`），`seedByAffinity` 贪心起步摆对，`packDiscs` 力模拟微调。
2. **岛内摆子主题**：`packDiscs` 摆好后 `orientTowardOutside` 整体旋转/镜像，把连向外部主题的子主题转到面向那个主题的一侧（只做刚体变换，不改子主题相对位置）。
3. **全体节点松弛**：锚点力（0.14）把卡片留在子主题圆盘里；**跨主题的显式链接作为弱弹簧**（`BRIDGE_STRENGTH` 0.1，静长 0）加进来，桥接卡片挪到两岛相对的边缘。跨主题的语义边不加（几百条，加了岛就糊了）。

**万级的已知成本**（批次 5 处理）：整体重算的暴力 kNN 是 O(n²·d)，2 万张估计分钟级；「新增 >10 张就重算」在万级太频繁，应改按比例。

## 5. 踩过的坑（别再踩）

- **token 值格式混用**：主题里有 hex、`rgba()`、`hsl()`、`hsla()`。解析器曾漏掉 hsl，强调色整体退化成兜底灰 `#808080`，浅色下肉眼看不出。已加门禁「消费到的 token 全部解析成功」。
- **`ctx.font` 不认 `var()`**：字体栈要在调色板里解析成字面值（`palette.fontFamily`）。
- **LinkGraph 容器不能自带底色**：曾写 `bg-page`，在 surface 卡里挖了个洞。现在透明，底色用 `resolveBackdrop` 从容器向上取。
- **不要等布局收敛才显示**：700 张卡会干等 1 秒 Loading；收敛过程本身就是入场动画。
- **容器 0 宽时不能 fit**：缩放会被压到下限且修不回来（`useGraphEngine` 的 sync 已跳过）。
- **Worker 协议要带簇信息**：批次 3 初版漏传，大图走 Worker 时簇力等于没有。
- **clusterForce 不能在簇对循环里遍历节点**：O(簇²×节点)，已改为先按簇累加再施加。
- **TF-IDF 要用经典 `log(N/df)`**：平滑版让「每个簇都有的 tag」仍有正分。
- **宿主传内联回调会触发重建**：进 effect 依赖的回调用 `useMemoizedFn` 包一层（`onClusters` 已处理）。
- **悬停只显示被指的那一个标签**：连一度邻居一起显示时，枢纽节点周围糊成一片（用户反馈过）。
- **主题名 / 簇名绝不随悬停消失**：旧版悬停时整段跳过主题名，鼠标扫过密集岛时悬停在有/无之间切换 → 整屏闪烁（用户反馈过，很不喜欢）。现在主题名常驻，只有与悬停标题重叠的那一个让位；降淡按 `emphasis` 0..1 做 120ms 渐变（`useGraphEngine` 的 `advanceEmphasis`），淡出期间用 `focusId` 保持降淡中心。
- **知识地图的查询缓存存的是整个 payload（`{ status, map }`），不是裸地图**：批次 5 为了「首开不干等」让缓存带上 status 后，开发悬浮球的「整体重算」还在往里写裸地图，图谱读 `.map` 得到 undefined、退回了按链接跑力布局的链接图谱——点完重算分布与缩放全变，重进页面才恢复（用户差点因此丢弃整批改动）。外部写缓存一律走 `setKnowledgeMapCache`，有单测兜住。
- **筛选命中不能走 `currentCardIds`**：卡片库曾把筛选结果（「全部」时就是全部 674 张）当 `currentCardIds` 传，每张都刷成 accent + 辉光，整张图成了一片蓝雾、主题色全没了（用户截图反馈，「比不选还难看」）。现在分两个口：`currentCardIds` 只给一两张「当前卡片」用（accent + 辉光）；筛选走 `filterCardIds`，命中的保持主题色，未命中的降到 0.2 透明度；没在筛选（「全部」）时传 null，图谱就是平时的样子。
- **悬停标题不能在命中范围之外**：标题画在节点正下方，鼠标挪到标题上就离开了命中圆 → 悬停断开、标题消失 → 鼠标又落回节点 → 标题再出现，来回闪（用户反馈过）。现在渲染器暴露 `hoverLabelBox()`，引擎把「节点中心到标题底部」这片也算作悬停节点的范围。预览面板同理：挂在标题下方而不是光标处（挂在光标处时面板压着标题，一碰就 pointerleave）；指针移进面板不算离开画布，离开面板才收起。
- **按分辨率挑主题数不能只看数量**：批次 3.6 初版只把目标区间改成随规模变化，结果在真实数据上挑到了更粗的一档（TypeScript、包管理器并进 JavaScript，8 个主题）。现在每档先同名合并，再按「多一个主题换来的名字覆盖率」边际收益往细走（`RESOLUTION_MIN_GAIN_PER_TOPIC`）。
- **亲近度 / 桥接力的端到端合成测试钉不住归一化**：合成向量太干净，开关归一化布局不变。所以 `topicAffinity` 抽成纯函数单测；桥接弱力的测试断言「连线 < 中心距的 0.45」，关掉桥接力（只剩岛内朝向，约 0.53）时会失败。改这些常数时要确认测试仍能区分开。
- **只按链接分簇在真实数据上失败**：674 张里只有 269 张有链接，结果是外圈几百个孤点 + 一堆两三张的小簇，每簇一个名字一个颜色 → 满屏彩色碎字（用户截图反馈）。这是做离线语义地图的原因。
- **主题名绝不能用卡片正文**：一句话被截断显示在地图上很难看。名字只从 tag 取，取不到宁可不显示。
- **封顶色槽前先按名字合并**：语义孤岛之间在图上不连通，`capTopics` 找不到合并目标时曾把整个主题置为 -1（丢了 1/3 的卡）。现在先同名合并，再封顶，封顶时图上不连通就退到向量质心余弦；都没有就停手，绝不丢卡。
- **d3-timer 的 tick 走 rAF**：测试里同步断言收不到帧，要 `await` 几十毫秒真实时间。
- **测试里派发指针事件要包 `act`**，否则有 act 告警。
- **showcase 的浏览器 pane 会周期性跳回启动根地址 `/#/shell`**（那是 Electron 入口），验证时每次先检查 `location.pathname` 再导航到 `/showcase.html`；viewport 模拟在回合结束会被清掉。
- **主进程完整构建要大堆**：`NODE_OPTIONS='--max-old-space-size=8092' npx vite build`，否则 OOM。
- **读用户真实数据只能只读**：用 `apps/collaboration-server` 目录下的 better-sqlite3（Node ABI；desktop 那份是 Electron ABI），`{ readonly: true }`，加载 `sqlite-vec` 扩展。库在 `~/.editor/data.db`，索引库 `~/.editor/index/data/data.index.db`；卡片向量是 `vec_documents` 里 `type='card'`，1024 维，按分块存多条。

## 6. 学到的事实（真实数据）

- 674 张卡，全部有向量（891 个分块），269 张有显式链接（含正文内联链接）。
- tag 是分层的：342 个一段、499 个两段、91 个三段；只有 8 张卡无 tag。约一半 tag 只有一段（直接打「JavaScript」），给不出子主题名。
- 离线地图在真实数据上（批次 3.6 之后）：约 1.7 秒，11 个大主题，0 张未归类：JavaScript 181、CSS 103、Python 69、学习方法 67、Linux 59、Canvas 49、经济 44、TypeScript 40、DOM 32、包管理器 18、Git 12（Git 排第 11，复用「经济」的色槽，两岛相距 271，相邻岛约 100）。「经济 / 学习方法」在分辨率那一步就自然分开了，没走拆分；拆分在这份数据上一次也没触发。
- 按分辨率扫描时（同名合并后）的主题数与名字覆盖率：3→0.30、4→0.32、5→0.39、6→0.48、8→0.56、10→0.65、10→0.65。
- 主题摆放（归一亲近度 + 显式链接加权 + 岛内朝向 + 桥接弱力之后）：TypeScript 挨着 JavaScript（岛间隙 10），DOM 落在 CSS 与 JavaScript 之间（与 JS 间隙 25、与 CSS 89）。只用原始边权时 JS↔DOM 间隙 123。
- 跨主题显式链接只有 6 条（显式链接共 324 条）。连线长度：加桥接弱力前 119 / 130 / 174 / 175 / 294 / 316（均 201），加后 92 / 105 / 149 / 153 / 210 / 222（均 155）；岛内链接 p50 23、p90 40 基本不变。`BRIDGE_STRENGTH` 扫过 0.04 / 0.08 / 0.1 / 0.15，0.1 之后收益变小。剩下偏长的两条是 JS→CSS：两岛中心相距约 310，中间隔着 DOM。
- 地图世界坐标约 730×700，最近邻间距中位数 12.6；fit 后缩放约 0.8。渲染器的缩放阈值按此校准。
- sqlite-vec KNN 单次查询约 80ms（增量放置用），所以同步对账限 10 张。
- 桌面端全链路已实机确认（2026-09-27）：首开日志 `rebuilt db=data.db cards=674 topics=10 elapsedMs=1326`，再开秒开。日志在 `~/.editor/logs/session-*.log`。

## 7. 下一步

### 7.1 批次 3.6：主题划分去硬凑（✅ 已完成，以下保留为设计记录）

落地与原方案的差异：拆分门槛是「加权覆盖率至少提高 `SPLIT_MIN_GAIN`（0.15）」；`capTopics` 换成 `mergeStronglyConnected`（小主题连向某一主题的权重占自身总权重 >50% 才并，删掉了向量质心兜底）；`detectTopics` 按覆盖率边际收益挑分辨率（见 §5）。颜色：主题多于 10 个时色槽循环复用，按地图着色的思路避开相邻主题（`topicNeighbors`：圆盘边缘间距 <140 或有连边），分配移到大主题布局之后；**中性色只给未归类的卡片**（用户明确要求：超出 10 个不能变灰）。前 10 个主题的分配与之前完全一致。没有新增颜色。

**现状**（`src/knowledge-map/compute.ts`，没有写死任何主题名，但数量被手调常数约束）：

1. `detectTopics`：7 档分辨率（`RESOLUTIONS`）各跑一次 Louvain，并掉小块后数主题数，挑落在 `TOPIC_TARGET`（6–12，理想 9）里最接近 9 的。真实数据在这步得到 8 个。
2. `capTopics`：超过 `TOPIC_PALETTE_SIZE`（10）就把最小的并进最亲近的主题。
3. `splitIncoherent`：主题名的覆盖率（成员里带该 tag 首段的比例）低于 `TOPIC_COHERENCE`（0.4）就在内部再切，子块各自命名、同名合并，够大（≥ 总数 1.2%）且自身覆盖率 ≥0.4 的提升为新大主题；**额度 = 10 − 当前数**。真实数据用满了 2 个额度：「经济」（111 张，覆盖 27%）拆出「学习方法」（36 张），「包管理器」拆出「Git」。

**问题**（用户认可，要改）：

- 拆分为了用满额度而拆，结果容易总是正好 10 个；「Git」从「包管理器」拆出是否更好有争议。
- 主题数上限 10 来自颜色可辨数（视觉约束），却被当成数据结构的上限，导致 `capTopics` 强行合并不相干的主题。
- 目标区间不随规模变化：50 张和 2 万张都瞄准 9 个大主题。
- 所有门槛只在这一份 674 张的数据上校准过。

**要做的改动**：

1. **拆分只看数据**：只有拆完后名字覆盖率明显提升（例如各子块加权平均覆盖率比原主题高出一个明确幅度，且每个新块本身达标）才拆，去掉「额度 = 10 − 当前数」的驱动；拆分不再受色槽数限制。
2. **主题数与颜色解开**：去掉按色槽数封顶的强制合并（`capTopics` 只在图上确实强连接时才并）。主题超过 10 个时，按规模排序，前 10 个拿色槽，其余小主题用中性色（`palette.nodeFill` 那一档），但**保留名字与独立的岛**。色槽仍按主题名哈希分配，保证加卡片不换色。
3. **目标区间随规模**：理想主题数按卡片数的对数取（例如 `ideal ≈ clamp(round(3·log10(n)), 4, 16)`，700 张约 9，50 张约 5，2 万张约 13），min/max 在 ideal 上下浮动。规模再大时靠子主题层撑（必要时第三层），不要把大主题数拉得很高。
4. **补测试，覆盖多种数据形状**，不能只对真实数据调：小库（~50 张）、没有分层 tag 的库、tag 很少的库、主题数天然 >10 的库（应该得到 >10 个主题、多出的是中性色而不是被并掉）、单一主题的库。断言「不丢卡」「名字只来自 tag」「超出色槽的主题用中性色」。
5. 改完后用真实数据（只读导出，见 §5 最后一条）再跑一次，把主题列表给用户看，对比现在的结果（见 §6）。

渲染层要跟着改的地方：`core/mapScene.ts` 的 `colorSlots` 对无色槽主题不要给值（或给 -1），`useGraphEngine` 的 `rebuildClusterColors` 与 `Canvas2DRenderer` 对无色槽簇回落到 `palette.nodeFill`。`types.ts` 的 `KnowledgeMapTopic.colorSlot` 允许 -1，并同步 `knowledge_map_topics.color_slot` 的读写（schema 本身不用改，它是 INTEGER）。

### 7.2 批次 4：入场播放（✅ 第一版已完成）

落地情况：

- **入口是画布左下角的说明行**（`GraphCaption.tsx`），不是按钮：平时是一行很淡的图例式文字「674 张卡片 · 始于 2021年1月」，悬停变深并露出播放符号，点了就播。播放时这行字本身就是进度（「2022年3月 · 270 张」），播完变回描述。**没有进度条、暂停、倍速**（用户确认过：这是「看自己的积累长出来」，不是查数据，时长已封顶），播放中再点一下或按 Esc 跳到结尾。走过的弯路：左下角浮按钮（突兀）→ 工具栏「播放动画」按钮 + 底部播放条（太工具化，进度条突兀）→ 现在的说明行。倍速也不要用 Segmented（用户嫌丑，想删掉这个组件）。
- **时机**（`features/cards/graphMilestones.ts`，按库记在 localStorage）：这个库第一次进入图谱时自动播一次；之后卡片数跨过里程碑（100 / 300 / 500 / 1000 / 2000 / 5000 / 10000 / 20000，之后按万）时，说明行换成邀请「长到 500 张了 · 看看它是怎么长出来的」，点开才播、点开后才算看过。每 500 张一次太密，用户否决过。每次进入视图只判定一次，视图里新建卡片不会突然弹邀请。
- LinkGraph 的接口：`caption` 打开说明行（不开就没有动画，局部子图不开）、`captionHint` 替换成邀请语、`playbackRef`（`play` / `stop`）给宿主做时机触发、`onPlaybackChange`。
- **时长封顶**：总时长按卡片数取对数封顶（`baseDuration`：50 张约 6 秒、700 张约 12 秒、2 万张封顶 20 秒）。
- `core/timeline.ts`：按排名映射（空窗期不留空白，同一时刻创建的一起出现）；`revealAt` 给出每个节点 0..1 的显现程度，已长满的不进表；`timeAt` 按排名反查真实日期。
- 渲染器只读 `RenderState.reveal`：未出现的不画；正在长的半径走弹簧曲线、不画描边和标题；连线两端都出现后才从先出现的一端画向后出现的一端；主题名 / 子主题名的透明度随该主题已出现的比例上升。播放中未出现的节点不可悬停。
- 卡片集变化（场景重建）时结束播放。

没做的（后续再说）：链接图谱模式下「新节点从邻居附近出现 + 加热布局」（现在两种模式都只是按时间显现，坐标不动）；每个主题的增长曲线；2 万张时远景按主题聚合播放（批次 5 与 WebGL 一起做）。

原方案要点（之前与用户对过）：

- 按 `create_time` 排序逐步加入；**大图上播放的是主题的生长**（远景：主题岛从小到大长出来），近景才是单卡落位。
- 地图模式下坐标是离线定好的，播放只是「按时间显现」，不需要跑物理；链接图谱模式下新节点从已出现的邻居附近出现，给小 alpha 加热。
- 节点显现：弹簧曲线从 0 放大；边从源向目标逐渐画出。
- **时间轴非线性**：卡片有高峰和空窗期，按排名或压缩空白期映射，节奏才均匀。
- 底部可拖动的时间条，拖到哪显示当时的图谱。
- 按创建时间还能叠加：每个主题的增长曲线（批次 6 的洞见素材）。
- 渲染器要能接受「每个节点的显现进度 0..1」，别在渲染器里写时间逻辑——时间轴放 `core/timeline.ts`，渲染器只读状态。
- 规模：2 万张时逐卡动画不可行，远景按主题聚合播放。

### 7.3 批次 5：万级规模（压测已做，见下）

**先压测再动手**（2026-09-28）：造 2 万张合成库（1024 维、主题成团、四成卡片有链接，相似度中位 0.62，真实库是 0.68）实测了整条管线。结论是**瓶颈全在主进程的离线计算，渲染完全不是问题**，所以 WebGL / 边聚合 / minimap 往后放，先修离线。

离线计算（优化前）：

| 卡片数 | kNN    | 全量计算（含 kNN） |
| ------ | ------ | ------------------ |
| 674    | 0.35s  | 1.7s               |
| 2000   | 3s     | 8s                 |
| 5000   | 19s    | 35s                |
| 20000  | 5.3min | **7min**           |

渲染（系统 Chrome，有 GPU；无头 chromium 是软件光栅，674 张就只有 11fps，那组数据作废）：

| 节点数 | 光栅化每帧            | 每帧遍历 | 命中   | 建场景 | 生长动画每帧 |
| ------ | --------------------- | -------- | ------ | ------ | ------------ |
| 674    | 8.3ms（垂直同步上限） | 0.4ms    | 0.09ms | 4ms    | 0.3ms        |
| 5000   | 8.3ms                 | 1.7ms    | 0.55ms | 16ms   | 1.7ms        |
| 20000  | 9.1ms（≈110fps）      | 6.0ms    | 2.46ms | 65ms   | 7.0ms        |
| 50000  | 21ms（47fps）         | —        | —      | —      | —            |
| 100000 | 44ms（22fps）         | —        | —      | —      | —            |

所以 Canvas 2D 的墙在 5 万张以上；2 万张逐卡播放生长动画也跑得动（批次 4 留的「远景按主题聚合播放」暂时不需要）。

CPU 剖析（5000 张，23.8s 采样）：`knn` 35%，**其余 60% 全是最后一轮全体松弛的力模拟**（collide 16%、manyBody 13%、四叉树 visit/get 20%）。

已做的优化（2026-09-28）：

- **kNN 只算上三角 + 向量打包成连续内存 + 点积 4 路展开**（`vectors.ts`）：674 张 0.35s → 0.16s，5000 张 19s → 8.6s，2 万张 5.3min → 2.4min。真实数据上与朴素实现逐条比对，674 张结果完全一致；单测钉住「与每个点独立扫全表的结果一致」。
- **一卡一锚点（向日葵螺旋）**：原来同一子主题的成员共用一个锚点（圆盘中心），最后那轮松弛就是「锚点往里拉、碰撞往外推」的拉锯，画面松不松全看迭代次数。现在每张卡的锚点是它在圆盘内按黄金角铺开的位置（`seedWithinDisc`），起步就不重叠。**螺旋必须铺在圆盘内**——越界会让相邻的岛贴上（有单测兜住）。没分出子主题的卡片铺在主题圆盘里。
- **松弛按主题岛分别跑**：岛之间有 70 的水道、卡片受锚点约束不越界，所以跨岛没有相互作用。切开后省掉横跨全图的四叉树，真实数据 1.55s → 1.11s。**坑**：d3-force 会把 `node.index` 重写成「该节点在本次模拟数组里的位置」，全图一次模拟时恰好与卡片下标相等，切开后就错位（`forceLink` 按 id 找不到节点）；所以 `MapNodeDatum` 的字段改名叫 `card`。
- **跨主题桥接由弹簧改为挪锚点**（`BRIDGE_ANCHOR_SHIFT`）：弹簧要求松弛跨岛进行。改成把桥接卡片的锚点朝对方主题挪一段（上限 `14r+30`），效果接近：跨主题连线均长 160（弹簧版 155，不加桥接 201），岛内链接 p50 始终 26。
- **两个阈值改按规模**（`src/knowledge-map/schedule.ts`，纯计算 + 单测）：`syncPlaceLimit` = max(10, 地图规模 1%)，2 万张时 200 张才触发整体重算；`WAIT_FIRST_BUILD_CARDS` = 1200，超过就**首开不干等**——主进程立刻回 `building` + 空地图，渲染层先画链接图谱（能看能点），`useKnowledgeMap` 按 3 秒轮询等算完再换上地图。

优化后的离线耗时：674 张 1.1s（原 1.7s）、5000 张 20.5s（原 35s）、2 万张 4.4min（原 7min）。

**剩下的瓶颈与判断**：5000 张的剖析现在是 kNN 41%、力模拟约 50%。两项决策（kNN 换近似近邻、力模拟换一次性解重叠）的背景、数据、候选做法与验收标准单独记在 [scale-decisions.md](scale-decisions.md)，下次做时从那里开始。

1. **kNN 仍是最大的单项**（2 万张 2.4min）。要再快只能换近似近邻（HNSW）或直接用索引库里的 sqlite-vec；精确解会让主题边界更稳，换近似前要先确认抖动可接受。
2. **迭代次数不能一刀砍**：真实数据 80 次就达到 260 次的质量（最近邻中位 12.6），但合成的密集数据（子主题 123 张、语义边密）80 次时仍有 2.6% 的点对过近。所以保持 260。要再省得换掉 d3-force 那轮，比如用网格法一次性解重叠。
3. 真需要时才做：WebGL（PixiJS）渲染器、边聚合、minimap——5 万张以上才有必要。

压测脚本在 `/tmp/km-bench/`（未进仓库）：`gen.ts` 造合成库、`offline.ts` 各档离线耗时、`scene.test.ts` 渲染侧 CPU、`web/raster.html` + `web/run.mjs` 浏览器光栅化帧率、`knn-verify.ts` 与朴素实现比对。

之后是批次 6（AI 洞见），见 §2。
