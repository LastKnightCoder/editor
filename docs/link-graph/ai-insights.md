# 卡片 AI 元信息与知识地图洞见 · 需求文档

> 2026-10-01：方向已调整，以 [模块联动与知识闭环](../knowledge-loop/模块联动与知识闭环.md) §4.4 为准（洞见覆盖所有阅读内容、出现在阅读时、产出落到链接与问题）。本文 §3 卡片元信息仍有效，§5、§6 降级为远期的图谱层方案，待重写。

2026-09-28 与用户讨论后整理，对应批次 6（见 [handoff.md](handoff.md) §2）。**产品文档初稿**：只定需求与架构边界，尚未实现；§12 的待确认项留到动手实现时再讨论。洞见的界面与入口要先做 mockup 看效果，这里只列候选。

分两层，下层是上层的基础：

1. **卡片 AI 元信息**（§3）：每张卡读一次原文，生成精简标题、要点、关键概念等结构化数据，作为卡片的元信息存在主库。**全应用受益**，不只是图谱。
2. **知识地图洞见**（§4 起）：建立在元信息之上的建议链接、空白与矛盾、桥接解释。

## 1. 目标

- **元信息**：卡片没有标题字段，全应用 19 处用正文前 N 个字当标题（长度 14 到 26 字不等，见 `getEditorText(card.content, n)` 的调用点），经常不准。LLM 读过内容后给出的精简标题会好得多；既然要读，就顺手产出结构化数据，给以后的功能留扩展。
- **洞见**：图谱已经回答了「我有哪些主题、它们怎么连」。洞见要回答的，是图上看不出、得读内容才知道的东西，而且最好**指向用户可以去做的事**：连一条线、补一张卡、回头看看两张卡谁对。

## 2. 范围

### 要做的三类洞见

| 类型           | 说明                                                                                                               | 用户能做的事             |
| -------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------ |
| **建议链接**   | 两张卡在说相关的事，但没有链接                                                                                     | 一键采纳，变成真链接     |
| **空白与矛盾** | 空白：一个主题里很多卡片都提到某个概念，却没有一张卡专门讲它。矛盾：两张卡的主张互相冲突，常见于早年写的和最近写的 | 补一张卡；回头对比两张卡 |
| **桥接解释**   | 两个主题之间的桥接卡片（图上已算出），解释两个领域在这里怎么联系起来                                               | 理解跨领域的联系         |

### 不单独做的

- **主题概括**：作为分层阅读的中间产物一定会生成（见 §4），但它本身不是一类「洞见」。要不要在界面上展示、在哪展示，留给 mockup。
- **成长回顾**（某主题何时开始、何时密集）：数据现成，但偏「读一段总结」，这次不做。

## 3. 卡片 AI 元信息

### 3.1 用户心智：配了模型就做，不配就不做

用户明确的原则：**心智负担最少**。这个软件没有新用户，用户本人卡片量大，不需要引导流程。

- **唯一的开关就是「配没配模型」。** 设置里新增一个模型用途（候选键 `cardMetadata`，见 §9），用户给它选了模型，后台就开始处理；清空就停止。**不设单独的开 / 关开关，不设「全部 / 只处理以后」的选项**：配上即对全部卡片生效，已有卡片补齐，之后增量跟进。
- **在配置模型的地方讲清楚**会发生什么：会读取全部卡片内容、生成标题等元信息、会消耗 token，并给出按当前卡片数估算的量级（粗估每张卡输入约 500 token：674 张约 34 万 token，2 万张约 1000 万 token）。这是唯一的说明位置。
- **没配模型**：一切照旧，标题仍是正文前 N 个字。
- **隐私提示：不做**（用户决定）。
- **不设每日预算**（用户决定）。
- 有消耗的 AI 处理都要用户同意：**配置模型这个动作本身就是同意**。

### 3.2 精简标题：用户无感知

- **不提供手动修改标题的能力**（用户决定）。标题完全由系统维护，用户感知不到「这是 AI 生成的」，只觉得标题变准了。
- **显示优先级**：AI 标题 → 正文前 N 个字（没配模型、还没处理到、或生成失败时）。
- **全应用统一**：现有 19 处用 `getEditorText(card.content, n)` 当标题的调用点，收敛到一个取卡片标题的函数，先查元信息、再退回前 N 个字。各处原有的长度作为退回时的截断长度保留。
- 不需要新界面：显示位置与现在完全一样。

### 3.3 元信息的内容

| 字段       | 用途                     | 使用者               |
| ---------- | ------------------------ | -------------------- |
| 精简标题   | 替代「前 N 个字」        | 全应用               |
| 一句话要点 | 悬停预览、搜索结果的摘要 | 卡片列表、搜索、洞见 |
| 关键概念   | 找「空白」的原料         | 洞见                 |
| 主要主张   | 找「矛盾」的原料         | 洞见                 |

以后可能加：建议标签（给没打 tag 的卡片补 tag，主题命名间接受益）等。

**可扩展性**：元信息放在一个**带 schema 版本号**的结构里（例如一列 JSON 加版本号）。以后加字段时，只需对版本低于当前的卡片补一次，不必全部重做；已有字段不受影响。

### 3.4 何时生成、何时重新生成

- **新增卡片**：静置一段时间（候选 10 分钟，且向量已重算好）后生成。
- **修改卡片**：按向量相似度判断。用户的判断是**日常编辑理论上都是小改动，不会让相似度掉下阈值**，所以标题基本稳定；只有内容大改才重新生成。阈值待实测（候选 0.98）。
- **删除卡片**：元信息随卡片删除。
- **换了模型**：已有元信息不作废，之后新生成的用新模型。

### 3.5 存储：跟主库走

用户的判断：**元信息不大，应该跟主库一起备份、同步**。索引库不备份，而且每台机器的模型不同、效果也不同，放索引库会导致换一台机器标题就变了。

- 现状：数据库同步是**整个主库文件上传**（`apps/desktop/src/commands/sync.ts` 的 `upload`），索引库不在同步范围内。所以放进主库就自动随备份与同步走，不需要另建文件夹、另做打包。
- 用户提过「单独文件夹、单独打包同步」。讨论后倾向不另拆：同步是按文件整体做的，另起一个文件就要另管版本号、冲突检测和上传顺序，这些主库已经有了。**此项待用户最终确认。**
- 体积估计：每张卡约 300 字节，674 张约 0.2MB，2 万张约 6MB。
- **注意：主库的表结构是桌面端与移动端共用的**（`apps/mobile/src-tauri/src/database/migrator.rs` 直接 `include_str!` 了 `packages/db-schema/schema/main.sql`）。加表要走共享 schema 与迁移流程，移动端至少要能容忍这张表存在；移动端能直接读来显示标题，是额外的收益。
- 草案：新表 `card_ai_meta`（卡片 id、schema 版本、内容哈希、生成时的向量指纹、元信息 JSON、模型信息、生成时间）。

## 4. 洞见：前提与运行方式

- **必须配置 LLM。** 没配置时不提供「只靠向量」的简化版：只靠向量做出来的建议似是而非，体验会让人对这个功能失望（用户明确的判断）。
- **向量只做粗筛，判断交给 LLM。** 向量找候选，不花 token；LLM 只看排名靠前的候选并给出判断和理由。LLM 判断不成立的候选不展示。
- **运行方式与元信息一致：配了模型就在后台做**，不另设开关（同 §3.1）。洞见和元信息共用一个模型用途键还是分开，待定：分开可以给元信息配便宜的模型、给洞见配强的。
- **手动分析单个主题**：原先设想的「没开后台时对单个主题当场分析」，在「配了模型就做」的原则下可能不再需要，待定。
- 隐私提示、每日预算：都不做（同 §3.1）。

## 5. 架构：分层阅读

目标是 AI 不必一次读完全部内容，也能把握全局。做法是顺着知识地图已有的「主题 → 子主题 → 卡片」三层**从下往上只读一遍**：

1. **卡片元信息**（§3）：每张卡读一次原文。这是唯一读原文的一层，也是最贵的一层。
2. **子主题概述**：读该子主题下所有卡片的元信息（不读原文）。
3. **主题概述**：读子主题概述。
4. **全局概述**：读各主题概述。

每次调用的上下文都很小，但全部内容都被读到了。

### 5.1 分工原则：本地只缩小范围，判断全交给 LLM

用户担心「关键决策都是本地粗筛做的，效果可能不好」。对此的原则（2026-09-28 讨论确定）：

- **本地粗筛只负责缩小范围，而且要宽**：任务是「不漏」，不是「选准」。宁可多给 LLM 一些候选，也不能漏掉真正的洞见。
- **凡是需要语义判断的，都交给 LLM**：不用本地的启发式规则（时间间隔、关键词计数之类）去猜「是不是矛盾」「缺了什么」。
- **每类洞见上线前先用真实库评估**（§5.3），不按候选阈值直接上线。

### 5.2 三类洞见的做法

三类洞见都建立在分层阅读的产出上（「元信息」见 §3）：

| 洞见     | 本地做什么（不花 token）                                                                                                         | LLM 做什么                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 建议链接 | 语义近邻、但没有显式链接的卡片对。**候选放宽**到每张卡前 20 到 50 个近邻（依据见下）；**跨主题的候选单独放宽**，不与岛内共用阈值 | 读两张卡的元信息，判断是否真的相关、写一句理由；不成立的丢弃                                             |
| 矛盾     | 只提供语义近邻对作为候选范围，**不用时间间隔筛**（见下）                                                                         | 比较两张卡元信息里的「主要主张」，判断是否冲突                                                           |
| 空白     | **不做本地统计**（见下）                                                                                                         | 读主题概述加上各卡的关键概念，直接判断这个主题缺了什么、建议写什么。这一步本来就在读主题层，只是多问一句 |
| 桥接解释 | 两主题之间的桥接卡片（离线地图已算出）                                                                                           | 读两个主题的概述加这几张桥接卡，解释联系                                                                 |

**建议链接的粗筛靠得住（真实库实测）**：拿用户已建的 324 条显式链接当「确实相关」的标准答案，看每条链接的两张卡在向量相似度排名里能排进多少名（取两端中较好的名次）：

| 候选范围      | 全部 | 岛内（318 条） | 跨主题（6 条） |
| ------------- | ---- | -------------- | -------------- |
| 前 8 个近邻   | 78%  | 78%            | 50%            |
| 前 20 个近邻  | 88%  | 89%            | 50%            |
| 前 50 个近邻  | 97%  | 97%            | 67%            |
| 前 100 个近邻 | 99%  | 99%            | 83%            |

有链接的卡片对相似度中位 0.717（p10 0.602），随机两张卡中位 0.482（p90 0.580）。结论：候选放宽到前 20 到 50 个近邻，真正相关的基本都在里面，选准交给 LLM，代价只是多一些候选、多一些 token。跨主题链接排得明显更靠后，而它恰恰是最有价值的那类建议，所以要单独放宽。跨主题样本只有 6 条，数字只能参考。

**矛盾为什么不用时间间隔筛**：原方案是「语义很近、但创建时间相隔较远」。这个条件站不住：观点一致的两张卡同样语义很近；相隔很近写下的两张卡也可能观点相反。时间间隔只是猜测，不是矛盾的特征。主张已经在元信息里提炼好了，让 LLM 直接比较，成本很低。

**空白为什么不做本地统计**：原方案是「很多卡提到、却没有一张卡以它为要点」。这完全依赖关键概念的抽取质量，而同一个概念不同卡片的写法可能不同（例如「原型链」与「prototype」），本地统计会把它们当成两个概念，既会漏、也会误报。

### 5.3 上线前评估

每类洞见上线前，都先在真实库的只读副本上跑一遍，达标再上：

| 洞见     | 怎么评估                                                                                                    | 看什么                                             |
| -------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 建议链接 | 一、把已有链接当标准答案：藏起一部分链接，看能不能被重新找回（召回率）。二、人工抽查 LLM 给出的前 20 条建议 | 召回率；抽查里用户认为「确实该连」的比例           |
| 矛盾     | 没有现成的标准答案，只能人工抽查                                                                            | 用户认为「确实值得回头看」的比例；误报多了宁可不上 |
| 空白     | 同上，人工抽查若干个主题的结果                                                                              | 用户认为「确实缺了」的比例                         |
| 桥接解释 | 人工抽查                                                                                                    | 解释是否说到了点子上                               |

抽查由用户判断，人工抽查的比例阈值与用户一起定。评估脚本与结果记在本文档或单独的评估记录里，便于换模型、改提示词后复测。

## 6. 动态变化：增删改与主题重划

核心原则：**卡片元信息只和卡片内容有关，和主题怎么划分无关。** 主题的拆、并、重排只影响上层的概述；而上层每个节点的重写，都只是一次读下一层产出的小调用。所以结构变动的代价，是重写受影响的那几个节点，**不需要重读卡片**。

### 6.1 卡片层

规则见 §3.4。往上传的是元信息的变化：元信息重做后，如果要点和主张基本没变，不往上传。

### 6.2 子主题与主题层：按变化量分三档

每个概述存一份**输入快照**：它由哪些子节点、各自哪个版本生成。子节点一变就知道它过时了，但过时不等于要重写：

1. **变化很小**（候选：低于 10%）：保留原概述，只累计变化量。
2. **变化中等**：**增量更新**。把旧概述和变化部分（新增、删除、改过的子节点）交给 LLM 改写，不从头读全部子节点。调用小，前后版本也连贯。
3. **变化较大，或已连续增量更新多次**（候选 3 次）：从子节点完整重写一次，校正增量改写的漂移。

一次编辑最多沿「卡片 → 子主题 → 主题 → 全局」一条链往上走，大多数在第 1 档就停住。

### 6.3 主题本身变了

现状（见 [handoff.md](handoff.md) §3）：两次整体重算之间，新卡按近邻增量挂到已有主题上，主题集合不变，6.2 就够用。整体重算时主题会重新划分，而且**主题编号每次按规模重排，不能当身份用**。

所以概述要有自己的**稳定身份**（自行分配的 id），整体重算后先按**成员重合度**把新旧主题对应起来，再决定继承还是重写：

| 情况     | 判定（阈值待实测）                    | 处理                                              |
| -------- | ------------------------------------- | ------------------------------------------------- |
| 基本不变 | 新旧成员重合度高（候选 ≥ 0.7）        | 继承原概述和身份，当作一次成员变化，走 6.2        |
| 拆分     | 旧主题 A → A1、A2，各自多数成员来自 A | A1、A2 的子主题尽量继承；主题概述由子主题概述重写 |
| 合并     | 多个旧主题 → 一个新主题               | 从子主题概述重写一次                              |
| 新出现   | 对不上任何旧主题                      | 从子节点生成                                      |
| 消失     | 没有新主题对应                        | 删除概述                                          |

子主题用同样的办法对应。整体重算的总代价是「没能直接继承的节点数」次小调用，几十次量级，不是几千张卡。

主题名来自 tag、不是 AI 生成的，改名不影响概述。

### 6.4 洞见的失效

| 洞见           | 何时重新判断                                     |
| -------------- | ------------------------------------------------ |
| 建议链接、矛盾 | 卡片对中任一张的元信息重做了                     |
| 空白           | 所在主题的概述重写了                             |
| 桥接解释       | 任一方主题的概述重写了，或两者之间的桥接卡片变了 |

用户**采纳**或**忽略**过的卡片对要记住，忽略过的不再出现。其中一张卡后来大改时是否重新提出，待定。

### 6.5 调度

- 队列按层级排序：先底层后上层，保证上层读到的是新元信息。用户正在看的主题优先处理。
- 过时的概述照常显示，后台慢慢补。是否标出「基于几天前的内容」留给 mockup。
- 换了模型：已有的元信息与概述不作废，新写的用新模型。

## 7. 写入用户数据

**采纳建议链接**是唯一会修改卡片内容的操作：**一键直接写入，配撤销提示**（用户已同意）。其余洞见都是只读的。元信息（§3）是卡片的附属数据，不改卡片本身。

## 8. 存储

- **卡片元信息**：主库，见 §3.5。
- **概述与洞见**：放哪待定。按 §3.5 同样的理由（换机器、换模型不该让结果变），倾向也放主库；但它们依赖知识地图的主题划分，而主题划分在索引库、每台机器各自重算。另一种做法是留在索引库作为可再生数据，每台机器用同步过来的元信息各自重建（只花上层的小调用）。待与用户确认。
- 现成的参照：知识地图的 `knowledge_map_nodes` / `knowledge_map_topics`（`packages/db-schema/schema/index/40_knowledge_map.sql`）与键值表 `index_meta`（`30_meta.sql`）；视频洞见用内容哈希判断过期（`apps/desktop/src/hooks/video-insights-parser.ts` 的 `computeTranscriptHash`）。

表草案（字段待设计时细化）：

- **卡片元信息** `card_ai_meta`：见 §3.5。
- **概述节点**：稳定 id、层级（子主题 / 主题 / 全局）、当前对应的主题 id、输入快照（子节点 id 与版本）、累计变化量、连续增量次数、正文、模型信息。
- **洞见**：类型、涉及的卡片 / 主题、依赖的输入版本、结论与理由、状态（待看 / 采纳 / 忽略）。
- **处理队列**：可放 `index_meta`。

## 9. 与现有代码的边界

调研结论（2026-09-28，当前分支 `refactor/desktop-refactor`）：

- **LLM 调用只有一条链路**：`chatLLM(providerConfig, modelConfig, messages, options)`（`apps/desktop/src/hooks/useChatLLM.ts`），返回 `Promise<string | null>`。缺配置或请求失败时不抛错，返回 null 并发通知。
- **模型选择**：`useLLMConfig(feature)`（`apps/desktop/src/hooks/useLLMConfig.ts`）按功能键读设置。现有键有 chat、titleSummary、videoSummary 等。**新增键**：元信息候选 `cardMetadata`，洞见候选 `knowledgeInsights`（是否与元信息共用待定，见 §4）。用户给它配了模型即开始处理（§3.1）。注意已有的 `titleSummary` 是给聊天会话起标题用的，不要混用。
- **没有结构化输出**：不支持 `response_format` / json_schema。现有功能靠提示词约束 JSON，再剥代码块、截取 `{…}` 解析（参照 `useAnswerJudgement.ts`、`useVideoInsights.ts`）。洞见也只能这样做，解析失败要能丢弃单条、不影响整批。
- **运行在渲染进程**：`chatLLM` 在渲染进程经 `@tau/agent` 发起，底层通过 IPC `stream-fetch` 由主进程发请求。所以「后台处理」目前意味着**应用开着时在后台跑**，关掉应用就停。以后若要移到主进程，需要在主进程另起一条调用链路，属于单独的决策。另外可能同时开着多个窗口，后台处理只能由一个窗口负责，避免重复调用。
- **本地模型**：LLM 没有 Ollama 等本地模型的预设，只能手填 OpenAI 兼容地址（如 `localhost:11434/v1`），能用但没专门处理过。嵌入向量已支持本地模型（`EmbeddingSection.tsx`）。
- **不重复**：目前没有任何针对卡片集合的 AI 分析。首页回顾只做统计，主题命名明确不用 LLM。

### 聊天重构的冲突面

- 当前分支已包含一次大规模聊天重构（提交 `a0483c89e`，299 个文件），它保留了 `chatLLM` / `chatLLMStream` 的签名。
- 用户提到另有一个分支在大改聊天，本地分支与工作树里没找到，**待用户确认是哪个分支**，确认后再看它是否动了 `chatLLM`、`useLLMConfig` 与模型配置。
- 约定：元信息与洞见模块**只通过一个自己的适配文件**调用 LLM（输入提示词与功能键，输出文本或 null），不依赖任何聊天界面组件（`features/chat`、`components/ChatUI`、`ChatSidebar`）。冲突面收敛到这一个文件加设置里的新功能键。标题替换涉及的 19 处调用点里，聊天相关的界面不在其中。

## 10. 洞见的交互（待 mockup）

方向（用户认可的原则）：沿用生长动画的思路，**不做工具化的按钮和常驻面板，让洞见长在地图上，跟着缩放层级出现**。候选位置如下，要做 mockup 看效果后再定：

- 远景：点主题名，弹出该主题的洞见（空白、矛盾，以及主题概述是否展示）。现在点主题名没有行为。
- 远景：两个岛之间有桥接解释时，水道上出现一个很淡的标记，点开看说明。
- 中近景：建议链接画成两张卡之间很淡的虚线，与真链接区分；悬停看理由，点一下采纳。
- 卡片悬停预览底部加一行「可能相关：…」。
- 左下角说明行在有新洞见时提示（参照里程碑邀请的形式）。
- 主题概述是否在远景直接显示（例如主题名下方一行小字），还是点开主题后才出现。
