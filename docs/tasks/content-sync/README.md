# 桌面与移动正文 Yjs 合并同步方案

状态：方案待评审，尚未实现
目标：复用协同编辑的 Yjs 正文模型，让桌面与移动在云端同步后融合各自编辑，并得到一致正文。

## 需求与同步语义

- 正文合并采用已有的 Yjs 与 NodeTree 协同模型。同一篇不同位置的编辑也参与合并，不再整篇选择最后编辑的版本。
- 正常同步只有一份当前正文，不生成用户需要管理的冲突文章，不将正常并发写入展示为错误。
- 同步偏好保留「自动合并正文」「直接覆盖」「冲突时询问」三选一。
- 本期只接通普通本机正文的协同式同步，不增加实时光标、在场状态、成员权限或共享房间，也不要求新增服务器。已有实时共享正文继续由协作服务负责。
- 业务实体的新建、删除、目录、标签、白板与 AI 对话仍沿用整库同步方向。本期保障两端仍存在、属于同一资料库来源与稳定正文身份的正文。
- 最后编辑时间用于展示，不参与 Yjs 内容胜负判断。同一位置的并发改写按现有协同模型收敛；内容一致不代表系统能判断哪句话更符合作者意图。

本方案取代此前按篇选择最新快照的方案。撤回整篇赢家排序、自建混合逻辑时钟和正文观察向量；Yjs 状态向量及删除信息承担同步职责。

### 并发新建与本机编号碰撞

该场景揭示了当前「只保障已有正文」范围的缺口：两端分别新建卡片或文章，即使整数 `id` 相同，也必须识别为两份不同内容。Yjs 只能合并同一正文的更新，不能替代卡片、文章等业务行的导入。要让合并模式支持正常的双端新建，需要补充下述最小创建同步；具体纳入范围仍待评审，不将其表述为已经实现或已经覆盖。

| 设备 | 本机编号示例         | 稳定身份示例         | 同步含义         |
| ---- | -------------------- | -------------------- | ---------------- |
| A    | card 42、content 108 | entity-A、document-A | 一张独立新卡片   |
| B    | card 42、content 108 | entity-B、document-B | 另一张独立新卡片 |

同步匹配使用 `(sourceId, kind, entityId)` 与 `(sourceId, documentId)`；本机整数仅用于库内查询。目标库可把两张卡片分配为 42 和 43，也可使用其他空闲编号。各设备数字不必相同，稳定身份与引用指向必须一致。

现有 `content_documents.document_id` 已使用 UUID，`entity_identities` 已保存稳定实体身份与本机编号映射；但实体身份存在按需绑定路径。同步接入必须保证新建卡片、文章及其正文在创建事务中建立稳定身份。已有对象的身份应随共同基线分发，不能由各设备独立补随机身份后误认为不同对象。

最小创建导入建议限定卡片、文章和它们持有的正文：

1. 在整库覆盖前保存本机新建对象及正文状态，批次除 Yjs 状态外携带创建时的最小业务记录、稳定实体身份和稳定正文身份。不凭孤立正文猜测它属于卡片还是文章。
2. 接收端按稳定身份查询：已有实体则复用；确实不存在则通过现有分配器创建新的本机编号。相同 UUID 却出现不一致的正文归属属于异常，不能当作普通编号碰撞自动另建一份。
3. 在同一事务导入正文、卡片或文章行、稳定身份映射和持有关系。两种业务入口共用同一正文时，正文按 documentId 只创建一次，业务持有分别登记。
4. 建立以稳定身份为键的目标编号映射，更新 `content_id`、正文与业务活动流水的对象编号、支持的关联和引用。JSON 载荷中的旧编号只通过声明的字段和解析器转换，不能全局替换数字。
5. 重试按稳定身份和事件身份去重，不重复创建业务行或增加引用数。历史已经证明删除的实体不能当成「尚未导入」而复活；导入需识别退役身份及同步基线，无法判定时保留输入，不擅自新建。

自动合并和询问模式下，两份独立的新建对象应同时保留，编号相同不是需要用户选择的冲突。直接覆盖模式仍遵守其明确覆盖语义。已有同一篇正文的编辑继续走 Yjs，不将 document-A 与 document-B 的状态送进同一个 Y.Doc。

两个设备若分别创建了独立资料库，`sourceId` 也不同，即使库名相同也不能直接视为同一同步库；应先完成明确的资料库归属或导入。以上补充不意味着自动合并任意两个独立资料库，也不扩展为项目、白板等全业务实体同步。

### 非卡片正文与引用重映射的安全边界

正文合并以 `contents` 为单位，不能按卡片、文章列表枚举后就宣称覆盖全部正文。当前还包括待办描述 `todo_item.description_content_id`、日程详情 `calendar_event.detail_content_id`、日历说明、待办关联笔记、日记、项目条目、插件实体等使用方；实现前应按 schema 和真实读写入口完成持有及引用清单。

同一份已经存在的待办描述可以走同一 Yjs 合并核心。新增待办、为原来没有描述的待办创建正文，或删除待办时，则还需要维护「哪个待办的哪个字段指向哪份正文」。若两端为同一待办各自新建描述，两个不同 documentId 对应的是同一个描述槽位的关联冲突，不能据此创建两个待办，也不能仅凭数字 ID 自动挑选正文。该类关联变更的同步规则需要一并评审。

现有稳定实体类型清单不包含待办，不能认为已有 UUID 映射已经覆盖全部持有者。待办等入口若进入创建/关联同步，需要补齐其稳定身份或复用经验证的持久身份；只靠标题、自增编号或创建时间猜测同一对象不足以作为导入依据。

编号与引用必须按类型处理。例如目标库已有 `cards.id=1 → contents.id=1`、`todo_item.id=2 → contents.id=2`，另一设备发来一张不同的新卡片且来源编号也是 `card=1/content=1`。目标库可以分配 `cards.id=2 → contents.id=3`；原待办的描述仍指向 `contents.id=2`。卡片 2 与待办 2 可以共存；正文编号由 contents 的分配器避开正文 1 和 2，不按来源编号简单加一。

导入必须满足以下契约：

- 分别建立正文稳定身份到目标 `contents.id`、业务类型及稳定实体身份到目标业务表 ID 的映射，不建立一个不带类型的「旧数字 → 新数字」总表。
- 来源 `contentId` 只用于解析来源包，目标引用从稳定正文身份重新求值。只改写本次导入记录及明确发生的关联变更，不扫描全库替换相同数字。
- 提交前同时核对目标对象的稳定身份、字段指向的对象类型和预期旧关联。外键只证明目标编号存在，不能证明它就是正确正文；不能仅靠外键或行数不变判断未串数据。
- 正文、持有者、身份映射、引用和活动事件按事务提交，失败整批回滚。无法解析的引用不猜测绑定到同号对象。
- 验证覆盖「既有待办描述 contentId=2，新卡片来源 contentId=1 撞号」；导入后既有待办所指正文 UUID、正文内容和归属保持原样，导入卡片指向新正文 UUID；重复导入不增加记录或持有数。

这些约束保护所有正文消费者，不等同于本期自动支持所有业务类型的新建/删除。创建范围确认后，未支持的持有或关联不能被默默改写，也不能对它们宣称无损合并。

## 为什么可行以及现有缺口

项目两端已经使用 `@tau/collaboration` 的 NodeTree、Yjs 正文状态及结构校验；`@tau/editor-collab` 已提供编辑绑定和在既有文档上替换正文的能力。`@tau/collaboration` 与移动端当前固定使用 Yjs 13.6.32。

需要补齐的是跨设备的共同状态与持久化，而不是重新发明合并算法：

| 位置                              | 当前事实                                                        | 需要调整                                                                 |
| --------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 桌面 `content-runtime/open.ts`    | 缓存缺失后从 JSON 建立随机基线；Y.Doc 内正文 ID 使用本机会话 ID | 已启用同步的正文从持久 Yjs 状态恢复，内层使用稳定正文 ID；会话 ID 仍独立 |
| 移动 `useLocalContentDocument.ts` | 使用稳定正文 ID，但缓存缺失后同样建立随机基线                   | 从相同的持久 Yjs 状态恢复，不因下载或库代次变化重新生成正文结构          |
| 桌面本机日志与移动 Rust 缓存      | 已保存 Yjs 检查点、增量和输入草稿                               | 保留其耐久职责，并向可同步的正文状态提交已投影更新                       |
| 主库与整库同步                    | 主要传输正文 JSON/块投影，未共享正文的本机日志不随库传输        | 增加可传输的 Yjs 状态，并与主库投影建立明确的一致性关系                  |
| 冷写与原生业务写入                | 部分入口直接提交完整 JSON，正文没有打开的 Y.Doc                 | 在既有基线上生成更新，或同事务登记可重放的写入意图，发布前补齐 Yjs 状态  |

共同基线要求客户端加载相同的初始 Yjs 二进制结构。相同 `documentId`、相同 `baselineId` 或相同 JSON 本身都不足以证明结构同源；不能在两台设备各自重新插入初始内容后直接汇合，否则可能重复内容或违反节点身份约束。

Yjs 更新允许乱序、重复应用，接收同一组更新后收敛；传输可以交换完整编码状态，也可以根据状态向量计算差量，见 [Yjs 文档更新协议](https://docs.yjs.dev/api/document-updates)。因此对象存储可以承载延迟交换，不依赖实时 WebSocket。

## 三种同步偏好

| 偏好         | 同基线正文的行为                                                                                                                |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| 自动合并正文 | 交换并应用 Yjs 更新，校验完整合并结果，再投影到主库；不同文章与同篇不同位置均自动处理                                           |
| 直接覆盖     | 上传选本机可见正文，下载选云端可见正文；在已观察的合并状态上执行一次有前提的整篇替换，再发布该 Yjs 更新                         |
| 冲突时询问   | 同一正文双方都有尚未互相确认的修改且结果不同，展示 Yjs 合并预览，选择「合并双方修改」「使用本机正文」「使用云端正文」；允许取消 |

询问模式中的冲突是产品层的双端分叉，不是 Yjs 抛错。不同文章不询问；一端尚未接收另一端但自身未编辑时也不询问。预览在隔离候选上生成，选择之前不改变当前正文。

覆盖复用现有条件整篇替换能力：先固定双方观察水位及所选快照，再在当前已知的合并状态上产生一次新的正文编辑。保留原基线，不把旧 JSON 重新种成新 Y.Doc。它覆盖本轮已观察的内容；未被观察到的后续离线输入仍是后续同步要处理的新输入，不承诺永久屏蔽其他设备写入。

存量偏好缺省保持 `overwrite`，界面推荐 `auto`。三个模式都保存并交换合法 Yjs 状态，切换偏好不会重新初始化正文。偏好保存在本机同步目标配置，不从下载主库覆盖本机选择。

## 共用核心与两端分工

| 模块             | 建议位置                                                                 | 职责                                                                 |
| ---------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| Yjs 同步核心     | `packages/collaboration/src/content-sync.ts`                             | 从共同状态构造候选、应用更新、校验、提取正文、生成覆盖更新与选择令牌 |
| 同步编排         | 同包 `content-sync-runner.ts`                                            | 共同准备、读取、预览、发布、安装状态机，经端口执行 I/O               |
| 存储协议与主库表 | `packages/db-schema`                                                     | 文件描述、状态分片、投影修订、待处理写入和事件身份等跨端契约         |
| 桌面适配         | `content-runtime/`、主进程 `modules/content-sync/` 与应用级服务          | 本机日志、SQLite 暂存、保存屏障、文件和插件存储                      |
| 移动适配         | `useLocalContentDocument`、应用级服务与 Rust `sync/content_sync.rs`      | 相同 Yjs 核心、原生阶段命令、维护租约与安装恢复                      |
| 跨端样本         | `packages/collaboration/src/testing/content-sync/` 与 db-schema fixtures | 同一基线、真实更新、删除及结构操作，供两端真实适配器交叉验证         |

合并核心放在已经依赖 Yjs 的 `@tau/collaboration`，不反向给 `@tau/db-schema` 添加 Yjs/编辑器依赖。桌面与移动 WebView 执行同一份核心；Rust 只保存、校验传输摘要及执行事务，不实现另一套 Yjs 算法。

复用 `NodeTree`、`validateNodeDocument`、`readNodeDocument`、现有更新接纳与整篇替换实现。对同步收到的完整候选先在隔离 Y.Doc 集齐依赖，再相对共同的已确认状态做完整校验，不能因到达顺序不同而各自接受不同的前缀。

相同更新集合必须得到相同的正文、契约和结构结果。业务容量或引用校验失败时保留整批待处理状态，不按先到先得丢掉部分更新，不退回整篇最后编辑覆盖来伪装成功。

## Yjs 身份与主库存储

### 身份

跨端来源键为 `(librarySourceId, documentId)`，Yjs 状态同时校验 `baselineId`、`epoch` 与正文协议版本。`content_id`、库路径、窗口 ID、移动库代次只用于本机寻址与迟到写入保护。

桌面需要拆开目前部分入口混用的本机会话 ID 与 Y.Doc 内文档 ID：缓存与 IPC 仍用本机会话 ID，Y.Doc 内使用稳定正文 ID。所有增量接纳、Agent 锚点、历史、草稿与投影检查跟随这一边界调整，不通过修改二进制中的 meta 字段来伪造迁移。

新会话恢复旧结构并生成新的 Yjs clientID，不把安装设备 ID 强行设置为 clientID。保留已存结构身份，不能在缓存清理、整库下载或检查点压缩时重新插入相同文字。clientID 的会话约束见 [Y.Doc API](https://docs.yjs.dev/api/y.doc)。

### 可同步的持久状态

当前已经存在可恢复的 Yjs 状态和历史，不从 JSON 重新制造一套更新：

| 已有记录                 | 位置与用途                                                                                                           | 复用方式                                                           |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 桌面会话检查点与后续更新 | `local-content/content.db` 的 `sessions.state` 与 `updates`，`CollaborationLocalStore.load` 已逐项应用并恢复 `Y.Doc` | 直接恢复当前结构，再导出或计算差量                                 |
| 桌面活跃正文历史         | 同一本机日志库的历史检查点与载荷，随增量接纳事务保存                                                                 | 用完整检查点和后续增量恢复对应历史版本；不按界面历史条数判断完整性 |
| 主库冷写历史             | 主库 `document_history_entries` / `document_history_payloads`，由 `recordClosedContent` 等入口保存                   | 在来源修订匹配时复用；不代表主库已有全部活跃正文历史               |
| 移动本机状态与历史       | 独立 `collaboration.db` 中的缓存及 `local_content_history`                                                           | 复用已经保存的检查点与增量，校验其对应主库修订                     |

现有整库同步主要传主库及 AI 会话文件，不传上述完整本机日志库；因此有编辑历史，不等于云端接收方已经拿到当前可合并的 Yjs 状态。主库冷写历史在原修订接不上时还可能重新建立基线，不能只按正文 ID 把两个历史链拼接。

这些状态已经保存在 SQLite 数据库中，区别是它们不全位于当前上传的那一个资料库文件。同步需要从已有数据库恢复并导出所需正文状态，不是认为现有数据库没有 Yjs 数据，也不是把包含其他本机资料的整个缓存库直接上传。

实现优先从已有检查点与增量恢复 `Y.Doc`，只补齐稳定身份、基线、投影修订和发布水位的对应关系，以及随主库恢复所需的状态载荷。主库可复用现有分片结构；具体新增同步头或映射字段按数据库手册定稿，不预设再建一套重复的编辑历史。

- 常规编辑继续先进入现有耐久日志，再提交主库投影；投影事务同时保存该次已接纳的 Yjs 更新和投影修订。失败时日志保留，保存屏障补投。
- 已启用同步的正文在冷启动时，从主库检查点及更新恢复结构，再处理同源本机日志和草稿。JSON/块表继续供列表、索引和导出读取，不能作为重建新基线的常规路径。
- 主库存储 Yjs 的责任是跨端恢复与同步；现有本机日志的责任是保全尚未投影输入。导出前屏障确保两者已经对齐，不能从可重建缓存是否存在推断正文为空。
- 复制正文仍生成新文档和新节点，实际的新正文允许建立独立基线；原正文下载、重开、计数变化不建立新基线。
- 继承现有 `gc: false` 与节点预算。检查点压缩合并更新、去重编码，保留结构身份与删除信息，不把投影重新种成小文档来压缩。本期不增加任意重置基线或远端垃圾回收。

「完整编码状态」的生成是：载入已有检查点 → 应用该基线之后的全部更新 → 得到当前 `Y.Doc` → 调用 `Y.encodeStateAsUpdate(doc)`。接收端把这个二进制状态作为更新合入自己的文档。载荷包含协同结构身份与删除信息，不是可见正文 JSON，也不要求额外 gzip 压缩。

第一版可先对变更正文交换完整编码状态，减少远端确认水位与增量缺依赖的接入工作。现有历史更新本身也能作为增量来源：若可以可靠确认双方基线、接收水位和全部依赖，便可直接计算或交换缺失更新，并非现有数据做不到。完整状态与差量的区别在传输量和确认协议，合并都由同一 Yjs 模型完成。

状态向量不完整代表删除历史：不能仅因两端状态向量相等就跳过同步。删除也必须进入更新/删除集和确认水位，交叉验证需覆盖仅删除的修改。

### 冷写与原生写入

打开的正文复用现有 Y.Doc 写队列；桌面冷写与移动原生业务写入必须能追溯到同一份 Yjs 结构。

- 能取得正文运行时的写入，复用既有条件替换入口，在原结构上生成增量。
- Rust 等不能运行 Yjs 的原生冷写，在提交 JSON 的同一事务登记有序写入意图，保存稳定身份、原基线、前后快照、原修订与操作身份。原生日记、任务等实际写入不能遗漏。
- 共用 TypeScript 工作器在打开、同步与保存屏障前，按顺序在原 Y.Doc 上重放这些意图。复用现有保留节点身份的快照应用能力，生成并耐久提交 Yjs 更新；输入未变的意图幂等确认。
- 同一正文有尚未投影输入或未重放意图时，不允许直接导出旧 Yjs 状态，也不允许安装新基线掩盖差异。异步重放提交前复核捕获序号，新到意图留给下一批。

这部分是主要接入成本：需要覆盖真实写入口，但不要求在 Rust 引入 JavaScript 引擎或重新实现 Yjs。

## 对象存储与初次建立共同基线

保留现有整库文件传输，增加仅负责正文的不可变记录：

```text
tau-content-yjs-v1/libraries/<sourceId>/
  baselines/<documentId>.json
  states/<sha256>.json
  commits/<deviceId>/<batchId>.json
```

- 首次发布时由一台设备准备一份初始 Yjs 编码状态，再用原子防覆盖创建基线描述；其他设备加载同一份二进制。竞争失败读回赢家，不保留两个独立的初始种子。
- 正文状态按摘要通过现有分块传输保存，批次描述引用状态、基线、协议、编辑来源与正文活动事件；全部载荷准备完成后再原子创建批次描述。
- 每台设备发布独立、不可变的批次。两台设备同时上传互不覆盖；主库固定对象被再次上传也不会删除已发布的正文状态。
- 列举不可变批次并按已读身份增量下载。列举失败不能当作空集；发布结果未知时回读原批次身份，成功确认后才清理待发项。
- 本机发布日志与确认水位按同步目标保存到独立的 `sync-status` 存储，不因下载主库被覆盖。数据库正文与同步状态的安装沿用带日志的阶段恢复。
- 继续使用现有提供方 API、分块和对象请求重试，不要求提供方理解 Yjs。第一版记录随同步批次增长，不引入整库后继版本链或远端历史压缩。

首次启用时，已有独立缓存可在来源与结构身份都可验证时迁入。缓存不可比但投影与已发布基线内容相同时，保全旧缓存后直接采用共同状态。

如果两端在启用前已经各自从 JSON 建立不同结构，而且内容已经分叉，不能还原已经丢失的共同编辑历史。该情况需要一次初始化取舍，或在具有可验证共同旧快照时另行迁入差异；不能把两个随机种子直接合并并承诺无损。协同式自动合并的保障从双方采用共同基线后开始。

参与设备都需升级。旧客户端只会改写 JSON，其编辑不会产生本协议的 Yjs 更新，不能混用旧客户端并承诺正文自动融合。

## 两端执行流程

[共同流程图](flow.html) 继续采用保存的 Diagram Design 默认样式、横向文档尺寸。图只展示主流程和询问分支，以下伪代码包含失败边界。

```text
sync(direction, preference):
  run = native.prepare()                 # 固定库与来源；冻结写入；排空正文、草稿和冷写意图
  local = exportAlignedYjsStates(run)
  remote = readPublishedBaselinesAndStates(run)
  candidate = sharedCore.merge(local, remote)   # 同基线更新合入隔离 Y.Doc
  sharedCore.validate(candidate)          # 依赖、节点身份、契约、预算和可投影性

  if preference == ask and candidate.hasUnacknowledgedBranches:
    releaseEditingBarrier(run)
    return needsChoice(preview, token)    # 固定双方版本；取消不安装、不发布

  if preference == overwrite or choice selects one side:
    candidate = sharedCore.replaceObservedContent(candidate, selectedSnapshot)

  native.stageProjectionAndYjsState(run, candidate)
  uploadImmutableStates(run)
  if direction == upload:
    native.transferBaseDatabaseAndSessions(run)
  receipt = publishOriginalBatch(run)     # 结果未知时按原批次确认
  final = sharedCore.merge(candidate, collectNewPublishedStates(run))
  sharedCore.validate(final)
  if choice inputs changed:
    releaseEditingBarrier(run)
    return needsChoice(newPreview, newToken)
  native.installProjectionAndYjsState(run, final)
  native.acknowledge(run, receipt)
```

### 桌面接入

- 应用级服务统一手动上传、下载、启动与退出自动同步，设置页只提供偏好和选择 UI。
- `content-runtime` 打开、保存、缓存恢复与整篇替换接入可同步 Yjs 状态。整库下载可以撤销旧视图与租约，但重开必须恢复下载后的共同结构，而不是再次从 JSON 初始化。
- 上传前复用现有正文保存屏障与主库投影收尾；合并在暂存副本上进行。安装前备份，主库正文、Yjs 状态、契约、关系与对应修订按事务/安装日志保持一致。
- 退出时处于待选择状态，应停止本次自动退出并显示正常选择界面，不沿用失败分支直接关闭。

### 移动接入

- `useLocalContentDocument` 从同一持久 Yjs 状态恢复；普通正文的协同结构与桌面一致，UI 绑定仍使用 `createNodeTreeDocument`。
- 应用常驻 TypeScript 服务执行共用核心；Rust 提供带 runId 的准备、分页读取、暂存、传输与安装命令，不在原生层决定合并结果。
- 创建 `VACUUM INTO` 快照前排空 WebView 输入、源码草稿、Rust 缓存增量与冷写意图。快照不能代替保存屏障。
- Rust 安装沿用维护租约、数据库与 AI 会话配对日志、库代次失效、索引重建与连库对账。恢复 Yjs 状态时不接受旧代次的迟到投影。
- 离开设置页不取消任务；WebView 暂停或进程终止后，按原生任务日志恢复原批次与阶段，不以生成新种子作为恢复方式。

## operations 与其他联动

- Yjs update 与业务 `operation` 是两种不同记录：前者负责正文状态融合，后者负责活动、统计与订阅，不能把业务流水直接当成 Yjs 更新。
- 为启用后的正文活动事件增加稳定事件身份和稳定正文身份，跨端导入按事件去重，并映射到目标 `content_id`。旧流水随整库基底保留，不根据自增 ID 猜测并集。
- 收到远端更新不伪造新的本机写作活动；保留原事件时间，失效受影响日期的 `operation_daily_counts` 后重算。插件收到工作区刷新，不将历史导入重放为新用户动作。
- 正文投影、节点契约、引用差集、引用数和同步状态一起提交。索引、字数、反链与正文待办根据最终正文维护，不合并两边索引表。
- Yjs 编码必须保留现有合法文档根；业务投影只写正文与契约，标题、封面等业务表仍取整库基底。宿主元信息展示与其 Y.Doc 内字段需要在接线时明确分开，不能用裁剪二进制更新来过滤字段。
- 资源采用规范引用，本机路径映射留在视图/资源适配层，不把解析后的绝对路径写入共同 Yjs 状态。附件未下载沿用独立资源状态，不阻断正文编辑。
- 如果合并正文引用了整库基底不存在的新白板、数据表等实体，不能捏造目标或删节点；保留输入并停止安装。业务实体增删仍不在本期合并范围。
- Yjs 状态同步不自动包含编辑历史的作者、分组和撤销回执。现有历史保留；本期不拼接不同基线的旧增量或承诺完整历史跨端同步。

## 一致性和失败边界

保证的是：同一来源、同一正文基线、相同的已接纳更新集合，在桌面与移动使用相同协议、Yjs 和 NodeTree 实现时，得到相同可见正文、契约与结构。Yjs 编码字节、SQLite 布局、本机编号与图片缓存位置不要求相同。

Yjs 自动融合的是编辑事实，不对文章语义做判断。例如两端对同一句话给出不同改写，融合结果仍可能需要作者继续润色；默认模式不据此报错或生成冲突副本。

| 情况                           | 行为                                                   |
| ------------------------------ | ------------------------------------------------------ |
| 乱序、重复更新                 | 合入一次相同结构，不重复文字、不追加重复活动           |
| 仅删除、同处并发、跨块移动     | 交给现有协同模型，并验证最终结构与删除传播             |
| 缺依赖或基线不一致             | 保留原始输入并补取共同状态；不把 JSON 重种后硬合并     |
| 合并超预算或业务引用不完整     | 整批暂存、不安装；禁止两端因顺序不同各丢一部分更新     |
| 选择期间又有编辑               | 选择令牌绑定双方状态与库代次，重新核对并规划           |
| 发布已成功、本机安装未完成     | 查询原批次继续安装，不再次产生替换操作                 |
| 本轮最后收集后其他设备继续编辑 | 下一轮接收；同步成功只确认本轮更新集合，不宣称实时一致 |

原整库固定对象与正文批次不是一个跨对象事务。任务日志区分正文已发布、整库已传输、本机已安装，所需阶段完成后才显示同步成功。正文的正常并发不报错误；真实传输和结构校验失败不能伪装成功。

## 实施成本与验收

| 批次                | 交付                                               | 量级      |
| ------------------- | -------------------------------------------------- | --------- |
| 共同状态与写入接线  | 稳定正文身份、基线持久化、主库更新与冷写意图恢复   | 2–3 人周  |
| 共用 Yjs 编排和发布 | 隔离合并、共同校验、不可变状态批次、覆盖与选择语义 | 1–2 人周  |
| 桌面与移动适配      | 两端保存屏障、缓存恢复、原生安装、三种偏好 UI      | 2–3 人周  |
| 跨端验证与文档      | 真实双端交叉导入、故障恢复、提供方及官网文档       | 约 1 人周 |

两端已有正文接通初估 6–9 人周。这是对共同基线、全写入口和安装边界的量级估计，不是 Yjs 合并算法本身需要这些时间。并发新建所需的最小创建导入与引用重映射尚未包含在该估算中，应盘点导入边界后另行补充；不能用该估算宣称已涵盖并发新建。原快照选择方案的估算不能直接当作本方案排期。

针对性验证覆盖：

- 从同一编码基线派生两端，分别编辑不同文章、同篇不同段落、同段不同位置及同一位置；任意交换顺序后得到同一结构。
- 单端仅删除、双方删除与插入并发、段落拆分/合并、节点移动、源码字段、格式及未知插件节点，沿用现有 NodeTree 契约。
- 重复接收不重复正文；仅删除的修改不被状态向量相同误跳过；清缓存、退出重开及整库下载后仍保留原结构身份。
- 桌面导出移动导入、移动导出桌面导入，比较可见正文、契约和 Yjs 同步结果，不比较 SQLite 文件或任意编码顺序。
- 冷写连续事务、后台写入、未投影草稿和同步接收一起排空；中断后不重放两次，不漏掉快照与 Yjs 之间的差异。
- 预览不污染原文；覆盖针对已观察更新生成新编辑；已有基线保持不变；旧批次重放不恢复已被覆盖的已知输入。
- 发布响应丢失、并发上传、安装中断、索引/流水事务失败后，按原批次恢复，正文与同步状态不分裂。

新增测试限定在并发状态机、格式解析、事故回归、跨端对账与真实边界，不新增外观快照或覆盖率目标。实现时运行相关现有同步与正文测试、两端类型检查与构建、受影响 Rust 检查，以及数据库 schema build/check/prepare。
