## 一、公开 API 的实际形状

没有 ctx.editorCodec 或 ctx.editorSourceCode，也没有 ctx.dialogs。ctx 只是作者对 PluginContext 参数的命名。

| 实际入口                                             | 含义                                                          | 所属文档领域                     |
| ---------------------------------------------------- | ------------------------------------------------------------- | -------------------------------- |
| definePlugin({ editorExtensions, editorCodecs })     | 静态声明正文节点、行为和文本转换规则                          | 编辑器扩展                       |
| defineEditorExtension / defineEditorElement          | 定义节点渲染、插入动作和编辑行为                              | 编辑器扩展                       |
| SourceBlockEditor / useSourceBlock / useInlineSource | 编辑节点内部的 ABC、HTML 等文本；提供保存、取消和节点更新能力 | 编辑器扩展 → 文本与源码编辑      |
| ctx.editor.register                                  | 当前只用于桌面开发台的动态实验装配                            | 开发诊断附录，不作为普通跨端起点 |
| ctx.pages / ctx.navigation                           | 页面与功能入口分别注册                                        | 页面与导航                       |
| ctx.commands / ctx.settings / ctx.storage            | 命令、通用插件设置、工作区私有数据                            | 对应功能领域                     |
| @tau/ui 的 Dialog / Drawer                           | 对话框、抽屉等公共浮层，宿主接入返回与关闭仲裁                | 公共 UI                          |
| ctx.permissions                                      | 查询或提前申请 SDK 业务数据/宿主 AI 授权                      | 数据访问与授权                   |

editorCodecs 是作者确实需要编写的转换规则，例如 ABC 文本与乐谱节点的往返，不是宿主内置转换表。源码中保留这一静态贡献字段，但在文档中放在编辑器章节下讲解；同名内部依赖标记由工具生成，作者不重复填写。

本方案不另造 ctx.editorCodec、ctx.editorSourceCode、ctx.dialogs，也不为改目录而新增 API 别名。是否把 definePlugin 的静态字段进一步内聚成对象，属于另一次 API 形状决策，本轮不擅自改动。

## 二、五类信息的边界

| 信息               | 回答的问题                                                   | 作者/用户如何接触                                        |
| ------------------ | ------------------------------------------------------------ | -------------------------------------------------------- |
| 功能实现 API       | 插件怎样实现页面、编辑器和数据操作？                         | 作者在对应领域文档中查阅                                 |
| 作者声明           | 支持哪些平台和节点？依赖哪些额外服务？                       | 作者清单中的 targets、editor.elements、requires/optional |
| 内部兼容信息       | 当前宿主是否具备运行这个包所需的实现？                       | 构建器生成，中心选版与宿主加载检查；原始值仅进开发诊断   |
| 数据访问授权       | 是否允许插件经 SDK 读取或修改指定业务数据、使用特定宿主 AI？ | 必要时声明 permissions，用户在相关操作中授权             |
| 产品介绍与支持结果 | 能做什么？当前设备能装哪版、支持到什么程度？                 | 作者介绍、平台信息、节点支持聚合、安装状态               |

内部依赖表是机器判断的集合，不是作者 API 的顶层目录，也不是权限列表。editor 是节点装配，editorCodecs 是文本转换协议，sourceEditor 是标准编辑工具，dialogs 是公共 UI 接入；它们不能平铺成一组消费者功能标签。

功能检查保留，中心的 required/optional 原始字段保留给选版和诊断。仅调整信息组织和展示，不用删掉检查来隐藏不兼容，不增加版本映射或协议翻译层。

## 三、权限为什么存在，哪些插件不需要声明

### 3.1 必需服务与权限分别处理

- requires: ["sourceEditor"] 表示宿主需要提供标准源码编辑工具，缺少时不能运行；这是自动兼容检查，不向用户弹授权框。
- permissions: ["cards:read"] 表示插件可能通过 SDK 读取卡片数据；声明是申请范围，不是已获授权，也不表示安装时自动授予。
- Android/iOS 的相册、相机等系统授权属于原生平台操作，不等于上述两个字段。本方案不把系统权限塞进插件能力表。

### 3.2 普通插件不必为了使用 SDK 填权限

| 行为                                                | 是否因此需要声明业务数据权限                                         |
| --------------------------------------------------- | -------------------------------------------------------------------- |
| 注册页面、功能入口、命令、设置或显示 Dialog         | 不需要                                                               |
| 读写本插件的私有 KV                                 | 不需要                                                               |
| 渲染宿主交给插件的节点，通过节点 hook 修改当前节点  | 不需要因此申请 cards:write；仍遵守文档只读、节点归属与提交有效性检查 |
| 编写节点的 Markdown 转换规则、编辑其内部源码        | 不需要                                                               |
| 在宿主允许的文档作用域使用媒体服务                  | 不因使用 media 名称而增加业务数据权限；是否能上传仍取决于当前作用域  |
| 通过 SDK 查询卡片库、读取其他文章、修改用户已有内容 | 按实际调用声明相应 read/write/delete 范围                            |
| 调用需要授权的宿主 AI 能力                          | 按对应 AI 接口的授权约定处理，不泛化为“所有 AI 都申请同一权限”       |

当前计数器模板和六个编辑器的作者清单均没有 permissions。当前官方插件中，问题管理显式声明了读取/修改卡片、文章等范围；这是数据操作需求，不是“它是页面插件所以要权限”。这些现有声明不天然代表最小必要集合，后续应按真实调用核对，发现多声明时缩减。

普通作者不必先调用 ctx.permissions.request 再重复调用数据接口。现有数据接口会在需要时由宿主申请授权；作者处理拒绝、取消与错误即可。只有确实要提前解释、批量申请或展示当前授权状态时才直接使用 ctx.permissions。

### 3.3 权限的实际保证

保留必要的数据授权，用来限定 SDK 接口的访问范围、处理用户拒绝和撤销。可信插件与宿主共享执行环境，这不是恶意代码安全沙箱；permissions 为空不能展示成“无法访问任何数据”“零风险”或“已安全隔离”。

移动业务数据授权尚未接入，含移动目标且声明非空 permissions 的包当前会被拒绝。展示改造不能把这个限制改成“点确认即可安装”。网页也无法代表用户完成客户端授权。

本方案不删除现有数据授权，不新增权限类别，不增加审核者实测、授权代办或验证记录要求。作者负责真实功能声明，用户负责必要的数据授权，宿主负责执行检查。

## 四、作者文档按功能领域组织

| 领域               | 主线内容                                                     | 支持说明                                          |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------------- |
| 快速开始与生命周期 | definePlugin、作者清单、构建、启停、取消和资源回收           | 先跑通公共页面，不先讲内部能力词表                |
| 页面与导航         | pages、navigation、参数、离开守卫                            | 桌面侧栏与移动功能列表由宿主呈现                  |
| 编辑器扩展         | 节点与数据、渲染/插入/编辑、编解码、源码编辑、只读与提交保护 | editorCodecs 和 sourceEditor 都在本领域下解释     |
| 公共 UI            | Dialog/Drawer、按钮、主题、容器布局、输入方式                | Dialog 是组件，不是独立产品功能或权限             |
| 私有数据与媒体     | storage、媒体解析与上传、资源字段                            | 区分私有存储、文档作用域与业务数据 API            |
| 业务数据与授权     | data/content、实体与事务、必要的数据访问声明                 | 明确桌面已接、移动未接的边界                      |
| AI 与领域扩展      | AI、MCP、同步/上传/发布等提供方、后台与白板                  | 各领域单列真实宿主范围，不从 SDK 类型存在推断支持 |
| 开发诊断附录       | 内部依赖、发行格式、兼容失败、包摘要与日志                   | 不作为初学者入口，不要求作者逐项填写基础依赖      |

每个领域按“能做什么 → 最小写法 → 平台差异 → 错误与生命周期”组织；平台差异主要引用支持矩阵，不复制多份容易漂移的事实。清单说明里仍解释 sourceEditor/media/runtimeStyles 等额外依赖的用途，但不将其画成与 editor 并列的 SDK 命名空间。

例如编辑器入口仍写静态贡献：

```tsx
export default definePlugin({
  ...__PLUGIN_META__,
  editorExtensions: [abcExtension],
  editorCodecs: [abcCodec],
});
```

这是领域内的定义字段，不是新增 ctx 服务。API 不因文档分组调整而改名，SDK 0.37.0 不重新发布覆盖。

## 五、展示内容从哪里来

| 展示信息                         | 权威数据                                          | 展示规则                                            |
| -------------------------------- | ------------------------------------------------- | --------------------------------------------------- |
| 名称、简介、分类                 | 插件资料中的 name/description/categories          | 简介是作者介绍；分类不是运行时认证                  |
| 声明平台、最低版本               | 当前展示版本的 targets                            | 省略的平台显示“未声明支持”；不推断平板已验收        |
| 最新、可安装、已安装、待生效版本 | latest、真实 host 的 resolve、当前/待生效安装记录 | 分别标注，不把不同版本的字段拼成一份详情            |
| 正文扩展支持                     | 当前平台的 elements 支持表                        | 聚合为用户可理解的编辑/查看范围，不展示节点技术标识 |
| 安装是否可用及原因               | 真实兼容结果、分发开关、撤回状态                  | 隐藏内部依赖不改变实际安装判据                      |
| 数据访问声明                     | 当前选中发布包的 permissions                      | 与功能支持分区；不当作已获授权                      |
| 内部排障信息                     | releaseId、原始 targets、host、reason、摘要和版本 | 仅放开发诊断，不作为用户功能列表                    |

不能从 required 包含 pages 就推断插件提供了页面：构建器会给编辑器包同样添加公共基础要求。也不能从 media 推断一定能上传图片，从 sourceEditor 推断一定有代码运行能力。页面等业务功能的具体描述先使用作者简介/README；现有结构化数据不足时不编造功能标签。

当前中心没有节点的人类可读名称，只有技术 type。第一阶段按支持等级聚合数量，不在宿主硬编码 abc、html-block 等插件类型到中文的映射，也不在商店执行插件 JS 来提取名称。以后确需逐项命名，再讨论作者提供并校验的元数据，本次不加字段。

## 六、移动端具体展示

以下版本和插件用于说明呈现方式，不表示候选插件已经上架；真实页面必须使用当前选中发布记录和设备结果。

### 6.1 商店卡片

以兼容且可安装的 ABC 版本为例：

> ABC 乐谱  
> 在文档中插入、编辑和预览乐谱。  
> Android · 支持编辑  
> 可安装 v0.1.7  
> 按钮：安装 v0.1.7

有已装版本时只在兼容版本更高时显示“更新至 vX”。没有更高版本则显示“已安装 vX”；待生效单独显示“vY 待生效”，不能冒充当前运行版本。卡片不显示 required/optional、Dialog、codec、profile、权限空表或节点 type。

### 6.2 详情页

> ABC 乐谱  
> 当前版本：v0.1.7  
> Android：声明支持 · 需要 Tau 0.2.3 或更高版本  
> 正文功能：支持编辑  
> 其他声明平台：桌面、iOS  
> 功能介绍：作者提供的简介与正文介绍  
> 版本记录：最新／本机可安装／已安装／当前选择

平台声明是作者信息，不能标成“官方实测通过”。当前设备是否能安装使用真实 host 结果；不因为列出了 Android 就给出可安装结论。

### 6.3 安装确认

没有业务权限声明的计数器/编辑器，不再放一个大块的“需要的权限：无”。保留插件身份、准确版本、实际包大小、来源和生效时机，例如：

> 安装 ABC 乐谱 v0.1.7  
> 下载大小：发布记录中的实际大小  
> 安装后将在下次打开应用时生效。  
> 按钮：取消／安装

确有权限声明时，使用标题“可能申请的数据访问”，逐项写“读取卡片”“新建和修改文章”等准确文案。说明“安装不会自动授予这些访问；使用相关功能时由应用询问”。当前移动端不支持的此类包应在进入可安装确认前被实际兼容检查阻止，不新增一个假授权按钮。

更新包有新增访问声明时，标出真实新增项；没有完整的旧声明数据时不猜测“无新增”。不在这里显示 sourceEditor/media/dialogs，因为它们不是数据权限。

## 七、网页插件中心具体展示

- 平台筛选继续显示声明平台的插件数量，含义仍是目录数量，不是当前电脑的可安装数量。
- 卡片展示名称、简介、分类、声明平台和版本；浏览者仅筛选 Android、但没有客户端版本与能力信息时，显示“声明支持 Android”，不显示“你的设备可安装”。
- 详情的三个平台分栏均明确属于同一个选中版本；每栏显示平台、最低 Tau 版本、正文功能支持摘要。取消默认“必需能力／可选能力／节点等级”技术列表。
- 最新版本和本机可安装版本不同时，分别标出“最新 vX”和“本机可安装 vY”；选择 vY 后，最低版本、支持范围、大小与权限全部随 vY 更新。
- 普通详情的“功能介绍”使用作者资料；非编辑器插件不显示空的正文支持表。含业务权限声明时展示“可能申请的数据访问”；空声明不显示权限大区块，也不宣称绝对安全。
- 网页商店不执行插件，不把博客 web 渲染环境列成应用可安装平台。作者工作台和审核页可查看技术详情，但不新增审核者测试任务或确认项。

### 正文支持摘要的统一规则

| 当前平台的节点声明         | 普通文案                                                                 |
| -------------------------- | ------------------------------------------------------------------------ |
| 全部为 edit                | 支持编辑                                                                 |
| 全部为 render              | 支持查看，不能在此平台插入或编辑                                         |
| edit/render 混合           | 部分内容可编辑；例如“1 类可编辑，1 类仅可查看”                           |
| 含 none 且仍有支持项       | 部分内容不支持；同时给出可编辑、仅查看、不支持的真实数量                 |
| 全部为 none                | 此平台不支持该插件的正文内容；不冒充整包不支持，因为插件可能还有页面功能 |
| 非编辑器包                 | 不显示正文支持区                                                         |
| 已声明编辑器但支持数据缺失 | 未提供完整支持信息；由实际包/兼容校验处理，不默认显示支持                |

edit 表示作者声明该平台具备编辑实现，不取消当前文档的只读限制。中心现有元数据无法判断每个节点是否有独立插入入口，因此通用摘要只承诺声明的编辑等级；具体插入方式使用作者介绍，不靠计数推断。

### 不可安装与降级文案

| 实际原因             | 普通文案                             | 开发诊断                             |
| -------------------- | ------------------------------------ | ------------------------------------ |
| 最低版本不满足       | 需要 Tau X 或更高版本                | APP_VERSION_TOO_LOW、实际/最低版本   |
| 当前平台未声明       | 此版本未声明支持 Android/iOS/桌面    | PLATFORM_UNSUPPORTED、原始 targets   |
| 协议或必需实现不支持 | 当前应用暂不支持此版本，无法安装     | 原始原因码、缺失依赖、格式或 profile |
| 分发未开放           | 此平台暂未开放插件安装               | DISTRIBUTION_UNAVAILABLE、实际开关   |
| 已撤回或禁用         | 此版本已撤回／该插件已停止提供       | releaseId、状态与服务端原因          |
| 可选样式增强缺失     | 部分样式增强不可用，基础功能仍可使用 | missingOptional 的完整原值           |
| 未知可选增强缺失     | 部分增强功能不可用                   | 完整未知标识；不猜测具体业务影响     |
| 无真实 host          | 未检查客户端兼容性                   | unchecked，不能显示 compatible       |

“升级即可解决”只用于已知最低版本不足，不拿它解释所有缺失实现。原始技术错误保留用于排障，不直接拼接英文标识到普通用户提示里。

## 八、开发诊断与实现边界

开发诊断展示插件/发布身份、实际选中版本、宿主平台与版本、原始 required/optional、原始节点 type 和等级、格式/profile、兼容原因码与包摘要。它属于开发信息呈现，不是新的 SDK 权限或命名空间。

移动端在开发构建/开发诊断入口查看；普通生产商店不平铺技术字段。网页开发诊断与普通详情分开，作者工作台/审核技术详情可复用。显示入口不是安全访问控制，公开发行元数据本身不是秘密，不新造“诊断权限”。

两端共用展示摘要的纯数据规则：产出状态、支持数量及原因类别，不依赖 React，不识别具体插件 ID。中文标签由展示层统一维护。诊断继续消费完整字段；普通展示隐藏字段不改变 /v2 分发事实，也不生成另一套兼容协议。

现有 normalizeCenterHost 的名称检查仍使用只含小写的规则，会拒绝 sourceEditor、runtimeStyles 等当前稳定名称。实施时需将能力名称校验与运行 profile 校验按真实契约分开，并用当前宿主完整能力集合验证目录/选版请求；本轮仅记录，不能通过展示过滤掉依赖来绕过这个问题。
