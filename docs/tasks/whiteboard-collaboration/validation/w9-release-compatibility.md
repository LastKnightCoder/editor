# W9 正式版本兼容核对

核对日期：2026-10-25。目标：确认白板协作的 SDK、桌面端、作者插件和协作服务最低组合，区分源码验证与正式发行证据。本轮只做只读发行查询、隔离包检查、本地验证和文档更新；UI 接线由另一会话负责，不执行真实迁移、发布或部署。

后续授权的火柴人本地适配与组合验收见 [火柴人候选组合验收](w9-stickman-compatibility.md)。下文保留本次正式发行核对证据；本地候选通过不改变线上 SDK、插件与服务的发行状态。

## 结论与最低组合

**目前没有可确认全部满足新白板协作契约的正式发行组合。** 正式 SDK 已确认不兼容，桌面公开更新源尚未交付本轮能力，现有正式白板插件仍为旧声明，线上服务版本与本轮协议实现尚未建立对应证据。

| 组件     | 当前正式证据                                                              | 新协作白板最低要求                                                                                                      | 可采用的候选与限制                                                                                                       |
| -------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 作者 SDK | npm latest 为 `@xiongtao.xt/tau-plugins@0.44.0`；正式包不含新白板契约     | 必须采用包含稳定身份命令、`dataVersion`、文本绑定和受控写入口的新发行物                                                 | 版本必须高于已占用的 0.44.0；可提议 0.45.0，但本轮不分配或修改版本。不能写成“0.44.0 及以上已支持”                        |
| 桌面宿主 | macOS/Windows 公开更新源均为 0.59.0；本地源码为 0.59.5                    | 首个同时包含公共编辑器契约、白板宿主及产品接线并通过验收的正式桌面版本                                                  | 0.59.5 仅为当前源码候选。只有最终确以该版本发行且验收通过，插件才能把最低版本定为 0.59.5；若实际发行号变化，清单同步调整 |
| 作者插件 | 当前 v2 白板分类仅返回火柴人 0.1.10，仍使用旧声明                         | 插件逐 ID 适配并以新版本发行；显式 desktop 最低宿主版本、正确数据契约、文本与资源声明、受控命令和宿主历史               | 火柴人需高于 0.1.10 的适配版本；0.1.11 可作候选编号，但仅升版本或重打包不构成适配。不同插件没有统一最低包版本            |
| 协作服务 | 活动 Worker 版本可识别，但缺少本轮源码/构建映射；健康状态不列文档协议能力 | 服务构建必须实际支持白板文档协议 3、契约格式 2、`whiteboard-w1-v1`、身份/epoch、因果依赖、操作及迁移/发布回执、资源保留 | 以经过联验的具体构建摘要/Worker version ID 固定版本。Node 包 0.1.0、Worker 包 0.0.0 都不足以定义最低服务版本             |

因此，最低**能力组合**是：新版 SDK + 首个完整支持的桌面发行版 + 已适配的插件版本（或无插件时的保真占位）+ 经验证的协议 3 服务构建。当前本地候选组合仅证明模型、作者接口和门禁；不能视为正式发行承诺，也不能外推任意更高版本都兼容。

没有安装某个插件时，宿主可以按文档契约保留其数据并提供已有的整体移动/删除等操作；插件专属渲染、创建和编辑仍需要匹配插件。纯内置白板不要求用户安装第三方插件或 npm SDK。

## 正式产物核对证据

### SDK：同号源码与发行物确实不同

读取 [npm latest 元数据](https://registry.npmjs.org/@xiongtao.xt/tau-plugins/latest)，下载其指定的 [0.44.0 tarball](https://registry.npmjs.org/@xiongtao.xt/tau-plugins/-/tau-plugins-0.44.0.tgz)，未执行包内代码。下载字节的 SHA-512 与注册表 integrity 一致。

| 检查对象                        | SHA-256                                                            | 冻结作者夹具结果                  |
| ------------------------------- | ------------------------------------------------------------------ | --------------------------------- |
| 正式 0.44.0                     | `305b418f993873d8499858baab34acbce8833e0b101bfac4ccf3db0dfa798c7d` | TypeScript 退出 2，预期不兼容     |
| 本轮源码本地打包，仍标为 0.44.0 | `f8d582d1b2a43b022865a7515fbcd107b7b76397abc0daf890ee25778c42acbc` | TypeScript 退出 0；仅候选，不上传 |

两者使用同一份 [作者类型夹具](whiteboard-sdk.fixture.tsx)，在仓库外目录解析 tarball 声明，未通过 workspace alias 偷换为源码 SDK。公开类型依赖复用本机已安装依赖；这是 SDK 接口对照，不是全部依赖的全新安装认证。候选包生成 475 个声明文件、8 个公开类型依赖；之前 W9 的 472 个声明属于当时源码，不将两个产物混为一份。

正式包的实质差异：

- `submit` 接受路径 `Operation[]`，仍公开 `apply`，快照不是当前稳定身份投影。
- 元素定义有 `schemaVersion/migrate`，没有当前作者定义的 `dataVersion/previousVersions/migrations`。
- 没有 `getTextBinding` 与当前 `updateElementData`。
- 编译出现 `TS2353: dataVersion` 不存在、`TS2339: getTextBinding` 不存在，以及旧接口使若干负向断言不再成立。不是仅由 tarball 时间戳或压缩摘要差异推断不兼容。

SDK 主要提供作者类型，运行时实现由桌面宿主提供。因此替换 npm 依赖不会升级用户桌面的运行时；只升级桌面也不会自动改写旧插件。

### 桌面：正式更新源尚不是源码候选

[macOS 更新源](https://dl.taunote.app/desktop/latest-mac.yml) 和 [Windows 更新源](https://dl.taunote.app/desktop/latest.yml) 均返回 0.59.0，发布日期分别为 2026-10-22T14:16:17.237Z 和 2026-10-22T12:32:18.461Z。这里只确认公开自动更新通道，不据此断言其他渠道绝无更高版本。

本地 `v0.59.0` tag 指向 `1b5e07473d9d3d3841a6a6e652861d340f30634f`；该 tag 的白板作者定义仍是路径操作和 `schemaVersion/migrate`。没有下载或运行正式桌面安装包，不把 tag 检查冒充安装包字节对账。当前工作区 0.59.5 包含未提交的多任务改动，尚不是固定发行提交；也没有相应的 0.59.5 发布说明文件。

### 插件：可安装不等于新协作契约兼容

通过 [v2 发行记录](https://plugins-api.taunote.app/v2/plugins/taunote.stickman/releases?platform=desktop) 读取火柴人 0.1.10，并下载正式 ZIP 静态检查，没有安装或执行插件：

- release ID：`87b0db02-6acf-4c73-8a16-cf1bfd18ba68`；提交：`9338aff3679a57845eb786d630176c80abb8b384`。
- ZIP SHA-256：`4ba41d62b1bec7532437fbac5700cb95768e3040bf85d3b5cd6edd4087abcc47`，与中心记录一致。
- 清单为 `formatVersion: 3`、`apiVersion: 1`、`profile: web-v1`、`targets.desktop.minAppVersion: 0.59.4`。
- `main.js` 仍有 `schemaVersion`，没有 `dataVersion` 或 `updateElementData`；当前插件仓库也仍依赖 SDK 0.42.0。正式 ZIP 是主要判据，本地依赖声明仅为补充。
- 正式包 README 写最低 0.59.0，与清单 0.59.4 不一致；选版以清单为准，后续适配版须同步说明，不修改历史发行物。

向公开只读 `POST /v2/catalog/query` 提供桌面 0.59.5、API 1、格式 1/2/3、`web-v1`，白板分类返回 0.1.10 为 compatible，且无下一页。这说明中心的安装检查通过；它不检查插件是否具备新白板数据契约。v1 目录会返回历史 0.1.6，不能拿 v1 结果当作格式 3 的最新发行记录。

源码 [ContentPluginRegistry](/packages/plugins/src/content.ts) 准备白板契约时排除没有 `dataVersion` 的定义；[协作目录](/packages/whiteboard/src/collaboration/catalog.ts) 要求显式版本，并按精确契约摘要分发。旧插件即便可安装，也不能因此获得新协作元素的编辑能力。旧创建载荷的 `schemaVersion` 亦不符合当前作者创建外壳约束。此处是静态核对和公共门禁验证，未宣称执行过该正式插件的完整 UI 流程。

### 服务端：已定位线上版本，仍不能认定支持本轮契约

只读查询 [ready](https://collab.taunote.app/health/ready) 与 [live](https://collab.taunote.app/health/live)，均返回 HTTP 200、`prototype: false`、`instance: production-v1`、`build: production-v1`。`/health` 不是这两个健康端点，探测得到 401 不作为不可用证据。

只读执行 `wrangler deployments list` 和 `wrangler versions view`，未执行 deploy/upload/迁移：

- 最新部署：`4942d08d-96a6-4f51-972c-c8fe2a639523`，2026-10-24T01:38:28.026429Z。
- 100% 流量版本：`2dde1000-d02e-4f6f-b050-5ceee3f0255e`（版本号 15）。
- script etag：`755c340266b1460d236f7c7131af06b8eda99372eee354950db766d9b9ce997e`。
- 版本注解只有上传来源，未提供可对应本轮已验证提交的 revision；未下载线上脚本，也未向生产创建测试房间或发送测试更新。

故当前判定为“协议 3 支持未确认”，不能仅凭部署时间推断它必然支持或必然不支持。健康返回中的 build 是通用实例标签；Node `/health/live` 中的 version 来自旧 `COLLABORATION_VERSION = 1`，同样不是新白板能力清单。不要把 `/v1` 路径或该数字误当白板协议版本。

## 兼容门禁与混用边界

| 层次       | 必须满足的条件                                                | 不满足时的边界                                                                            |
| ---------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 插件分发   | API 1、支持的包格式/profile、desktop target 和最低宿主版本    | 拒绝不匹配安装；检查不证明白板数据语义兼容                                                |
| 作者运行时 | 当前身份命令与字段接口；写入来自有效可写宿主作用域            | 不开放旧路径写入或通过原始模型绕过；安装 SDK 不提供运行时                                 |
| 元素数据   | 契约格式 2；owner/domain/type/dataVersion 和完整契约摘要匹配  | 同 type、同版本但摘要不同仍不复用渲染/编辑；历史 access 分 read/edit/none；缺失则保真占位 |
| 白板文档   | 文档协议 3、`whiteboard-w1-v1`，正文节点使用公共契约          | 协议 1/2 客户端不能按旧快照或票据通道接入白板房间；正文协议 2 不是白板协议 3              |
| 会话与操作 | documentId、baselineId、epoch、operationId/摘要和因果依赖一致 | 旧代次拒绝、原分支留在旧日志；缺依赖不确认；超时查原回执                                  |
| 迁移与替换 | 现有条件替换、发布/迁移回执和分存储安装校验                   | 只有显式迁移可更换基线；不自动降级、跨代次合并或新增恢复包                                |

插件包版本只说明作者发行顺序；`dataVersion` 说明元素结构，不能用包 SemVer 替代；epoch 是文档代次，不能用它代替 SDK 或服务器版本。`web-v1` 是插件运行配置，`whiteboard-w1-v1` 是白板数据 profile，两者也不可混用。

现有门禁已验证“新服务拒绝旧客户端进入新白板房间”；这不等于证明任意旧服务都会正确拒绝新协议。正式服务缺少构建对应和协议验收时，不能安排新白板写入生产。

| 缺口                                           | 影响                                                    | 后续完成条件 / 归属                                                                                                        |
| ---------------------------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| SDK 版本仍占用已发布旧号                       | 作者按正式依赖无法编译新接口，工作区 alias 可能掩盖问题 | 发行负责人固定新版本；在仓库外以实际新 tarball 编译作者夹具和示例，并保存完整性摘要。本轮不改版本或发布                    |

| 正式火柴人仍旧 API，安装兼容检查过宽于数据能力 | 可安装但无法据此承诺新白板的创建与编辑                  | 作者适配新契约、受控命令与创建载荷，保留历史数据转换边界，发行新插件版本；核验缺失/旧版占位和升级，不自动迁数据            |
| 服务活动版本缺源码/构建映射和协议 3 线上证据   | ready 不证明能接纳、回执或换代新白板                    | 先固定本地已验收服务构建，记录提交/摘要与 Worker version ID 对应。需要真实部署或隔离远端演练时另行授权；不向生产写测试数据 |
| 跨发行物组合尚未联验                           | 单个源码测试不能证明最终分发组合                        | 使用固定 SDK tarball、桌面构建、插件 ZIP 和服务构建重跑旧端拒绝、缺插件、因果/epoch、回执与迁移重试                        |
| 目标设备体验未验收                             | 无法承诺高负载、中文输入和长会话体验                    | 用户完成目标设备手工验收；不以自动化或版本号代替                                                                           |

不新增能力标签或第二套版本协商协议来填补以上发布证据缺口。先使用已有 target/minAppVersion、契约摘要和服务门禁，并固定真实产物；如后续发现必须修改协议，另行明确范围。
