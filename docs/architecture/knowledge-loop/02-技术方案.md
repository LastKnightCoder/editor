# 模块联动与知识闭环 · 技术方案

2026-10-01 与用户讨论后整理。对应产品文档 `01-模块联动与知识闭环.md`（下称「01」）。本文定架构、数据归属、关键接口与迭代划分；每个迭代动手前再细化到任务与测试。路径相对仓库根目录，`D` = `apps/desktop`。

## 1. 已定的技术决策

| #   | 决策                                                                                                                                                                                                                      | 理由                                                                                        |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| T1  | **引用索引放索引库**，作为可从正文重算的派生数据                                                                                                                                                                          | 不改主库 schema、移动端零改动、不受同步冲突影响；代价是移动端暂时没有反向链接               |
| T2  | **地址分三层，段落锚点与 `collabId` 解耦**（KL-013、KL-017，取代原「复用 `collabId`」）：实体引用为默认；系统内部用引述锚点（引文 + 前后文）；只有用户主动「引用这一段」才生成独立的 `anchorId`，整篇替换时按内容匹配迁回 | `collabId` 的生命周期由协作协议决定，绑在一起会让协作层的改动悄悄破坏引用；按需生成不用回填 |
| T3  | **从文章抽段落成卡片 = 复制 + 谱系**，不做多处同步的块引用                                                                                                                                                                | 简单可靠；与现有「整篇转卡片 = 投影（共用正文）」并存，界面文案区分                         |
| T4  | **AI 后台处理全部在主进程**                                                                                                                                                                                               | 主进程单例，无多窗口重复；已有 `PiAiRuntimeModule.complete` 与按功能键取模型的能力          |

此外沿用的约束：主进程新模块一律 `layer: BACKGROUND`（`D/src-electron/main/module-init/module-config.ts`）；渲染端数据一律 react-query；主库 schema 变更遵守根目录 AGENTS.md 的「数据库 Schema 维护规则」（同步 `scripts/db/check-schema-parity.mjs`、`database-schema.md` 与移动端）。

## 2. 总体架构

```
L3 界面   脉络面板 · 知识地图页 · 阅读时标记 · 「转为问题 / 以此立项」
            │  context:get(EntityRef) 等少量 IPC → react-query
L2 服务   关系查询服务 · 引用索引器 · 知识地图（泛化节点）· AI 队列 · 对话信号
            │  全部为主进程 BACKGROUND 模块
L1 关系   引用索引（索引库，可重算）· 谱系（主库）· 摘录（主库）· 问题材料（主库，已有）
            │
L0 底座   统一实体地址 EntityRef · 内容写入总线 · 引述锚点 / 按需 anchorId（迭代 6）
```

原则：

- **能推导的不存**：投影关系（多个实体共用一份正文）、闪卡来源、正文里的引用都能从现有数据推导，查询时算或进可重算的索引；只把**推导不出来的事实**（复制、摘自、升级为……）写进主库。
- **弱引用 + 缺失降级**：关系表不持有 `ref_count`。目标不存在时显示「已删除」，段落锚点失效时退化为整篇引用。现有 `question_link` 的 `resolveMaterials` 就是这种写法。
- **派生数据双保险**：写入总线做增量，数据库连接时整库对账兜底。

## 3. L0 底座

### 3.1 统一实体地址 `EntityRef`

```ts
// D/src/types/entity-ref.ts（主进程与渲染端共用）
type EntityKind =
  | "card"
  | "article"
  | "project-item"
  | "diary"
  | "question"
  | "answer"
  | "excerpt"
  | "pdf-annotation"
  | "web-clip"
  | "flashcard"
  | "vl-project"
  | "vl-note"
  | "chat-session";

interface EntityRef {
  kind: EntityKind;
  id: number | string; // chat-session 的 id 是字符串
  anchor?: { blockId?: string; messageId?: string };
}
```

- 现有的多套写法统一映射到它：问题材料的 `target_type`（`project_item`）、`EntityPicker` 的 kind、内联引用的 `contentType`（`project-item`）、向量的 `prefixed_id` 前缀（`project-item`）、日记的 `diary-daily`。提供一个 `normalizeKind()` 收口命名差异，**存储层逐步统一为 `EntityKind` 的写法**，新表只用新写法。
- 打开实体统一走 `openEntity(ref)`（在现有 `D/src/services/open-content.ts` 上扩展；目前不支持日记，要补）。
- 一份正文可能被多个实体共用（卡片、文章、项目文档投影同一个 `content_id`）。现有 `entity-search.ts` 的 `locate` 只返回第一个，改为 `locateAll(contentId): EntityRef[]`。`cards`、`articles`、`project_item` 的 `content_id` 目前没有索引，要补（主库索引变更，见 §8）。

### 3.2 内容写入总线

现状：正文的写入分散在多条路径，日常打字还绕过了 IPC 与 `onDatabaseWrite`：

| 路径                                                                                           | 位置                                                                                        |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 本机与共享正文的契约投影                                                                       | `D/src-electron/main/modules/collaboration/content-sessions.ts` 的 `projectContractContent` |
| `content:create/update/delete` 与直接调用 `ContentTable`（日记、每日笔记、剪藏、AI 工具、MCP） | `D/src-electron/main/modules/tables/content.ts`                                             |
| 迁移代码                                                                                       | `tables/content.ts` 内的迁移函数                                                            |

方案：

- 新增主进程模块 `content-events`（electron-free，便于测试），提供 `emitContentWritten({ dbName, contentId, kind: "create" | "update" | "delete" })` 与 `onContentWritten(cb)`。
- 在上表前三类写入点调用 `emit`；迁移代码不接，由对账覆盖。
- 订阅方自行防抖。投影每秒一次，引用索引器按 `contentId` 防抖 2 秒；AI 队列按静置时间（候选 10 分钟）。
- **对账**：订阅方在 `databaseModule.onDatabaseConnected` 时整库比对一次（FTS 已是这个模式，见 `main-content-fts-index-queue.ts`），按 `contents.update_time` 与派生数据记录的时间判断。它兜住移动端写入、同步下载、迁移和总线漏掉的路径。

### 3.3 地址与语义单元（KL-016、KL-017）

**地址分三层**：

| 层         | 是什么                                        | 谁用                          | 改不改正文               |
| ---------- | --------------------------------------------- | ----------------------------- | ------------------------ |
| 实体引用   | `EntityRef`，指向整张卡 / 整篇文章            | 所有人，默认                  | 不改                     |
| 引述锚点   | 引文 + 前后各约 32 字；原文变了做模糊匹配找回 | 系统内部：谱系、摘录、AI 标记 | 不改                     |
| `anchorId` | 段落上的独立属性，与 `collabId` 无关          | 用户主动「引用这一段」        | 改（只改被引用的那一段） |

- 引述锚点找不回时，显示保存的引文，并提示「原文已修改」。
- AI 标记是即时计算的，内容一改就重算，本身不需要稳定锚点；引述锚点只用来在当前版本里定位。
- `anchorId` 留到 6b，本次不改正文结构，其编辑规则和 Markdown 往返另行实施。

**语义单元（6a 已实现）**：卡片整张；长文取重复最高级标题分节，1200 字再切、80 字短节向后合并。嵌入文本为「实体标题 › 标题路径 + 本节 Markdown」，content_sections 保存顶层块区间，向量 / 全文保留 chunk_index。MAIN_CHUNK_VERSION 拼入主内容指纹，静默重嵌且不阻断全文检索。SearchResult.section 供命令面板、AI 检索与定位共用。引述锚点为 32 字上下文、2000 字上限、0.75 模糊阈值，实测见 11 §11.3。

## 4. L1 关系数据

### 4.1 引用索引（索引库）（迭代 1 已实现）

表结构以 `packages/db-schema/schema/index/50_entity_refs.sql` 为准：

- `entity_refs`：src_content_id（引用正文）、src_block（来源顶层块序号）、dst_kind / dst_id（目标实体）、dst_content_id（目标正文）、snippet_before / snippet_label / snippet_after（前文、文字、后文，两侧各 70 字）。REF_INDEX_VERSION=4，旧索引补列并全量重解析。
- `entity_ref_sources`：每份正文最后一次解析时的 `contents.update_time`，对账用。

要点：

- 只收正文里的 `content-link`。显式链接 `cards.links` **不进索引**，查询时读主库（KL-014）。
- 反向链接按 `dst_content_id` 查，自然覆盖共用正文；老节点缺 `contentId` 时按 `dst_kind` / `dst_id` 兜底。
- 片段存成三段，界面据此点亮被引用的标题。
- 解析函数 `D/src/entity/inline-refs.ts`，原来两份 `getInlineLinks` 已收敛到它。
- 不含 `content-link` 的正文由 SQL 过滤，不解析 JSON。本机真实库 4413 份正文首次对账 73 ms。
- 每台机器各自重建，连接时对账。被引用经 at 打开来源块，日记保留 moment 身份；段落级目标 anchorId 留到 6b。

### 4.2 谱系（主库）

6a 选区 / 整节抽卡为复制：去掉 collabId，分类永久，文章 / 项目文档 → 卡片记 derived，src_anchor.quote 存引文及上下文。来源按锚点定位；找不回时保留引文和「原文已修改」。选区转问题不记谱系，独立存 question_link.anchor，材料仍指向整个实体。

```sql
-- packages/db-schema/schema/main/ 新增
CREATE TABLE IF NOT EXISTS entity_lineage (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  src_kind    TEXT NOT NULL,
  src_id      TEXT NOT NULL,
  src_anchor  TEXT,                 -- JSON：{ messageIds?, quote? }
  dst_kind    TEXT NOT NULL,
  dst_id      TEXT NOT NULL,
  relation    TEXT NOT NULL,        -- 见下表
  create_time INTEGER NOT NULL,
  UNIQUE (src_kind, src_id, dst_kind, dst_id, relation)
);
-- 索引：(dst_kind, dst_id)、(src_kind, src_id)
```

| relation       | 含义                      | 写入点                                                                                                       |
| -------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `derived`      | 复制出来，之后各自演化    | 抽段落成卡片（新）；`InsertNoteToTreeModal` 的 copy 分支（VL 笔记、插件笔记插入项目）                        |
| `excerpt_of`   | 由某条摘录 / PDF 标注写成 | 微信读书单书页、PDF 标注列表的「转为卡片」（迭代 4 已实现）                                                  |
| `saved_from`   | 由对话中的某条消息存成    | Notebook 对话存为产物；以后若经 MCP 让 AI 总结生成卡片等（04 待定），`src_anchor.messageIds`                 |
| `upgraded_to`  | 问题升级为课题            | 「以此立项」（迭代 5 已实现，`question` → `vl-project`）                                                     |
| `discussed_in` | 从该实体发起了一次对话    | 问题「围绕它聊」（迭代 5 已实现）；脉络、阅读时标记、知识地图的「继续聊」（迭代 7），`dst` 为 `chat-session` |
| `clipped_from` | 剪藏自网页条目            | 迁移自现有 `content_link`                                                                                    |

**不写入谱系、查询时推导的关系**：

- 投影：同一 `content_id` 的多个实体（`buildCardFromContent`、`createCardFromProjectItem`、`buildArticleFromContent` 都是共用正文）。按 `create_time` 判断谁先谁后。
- 闪卡来源：`flashcard_references.content_id`。
- 问题材料：`question_link`。
- Notebook 引用的笔记：`vibe_learning_resources` 的 `source_type = note`。

**`content_link` 的去留**：它目前只记录「项目条目 → 剪藏」。把数据迁入 `entity_lineage`（`clipped_from`），改造 `D/src/services/webClipTaskRunner.ts` 等调用方后删除该表；主进程那套旧的剪藏实现（`D/src-electron/main/modules/web-clip.ts`）一并确认是否还在用，不在用就删。按 D-091 不保留兼容层。

**命令签名**：新增的「把 A 存成 B」类操作，参数里带来源；不改现有投影类函数的语义。从自己写的正文抽成卡片不做（KL-052）。

**约定（迭代 3 定）**：任何「把 A 的内容复制 / 存成 B」的新入口——界面按钮或 AI 工具——都要写谱系；投影类（共用正文）不写。端点类型 `LineageNode` 比 `EntityRef` 宽（含对话、Notebook 笔记、剪藏解析文档、闪卡），id 统一存文本，弱引用不级联删除（KL-028，详见 08 §2）。

### 4.3 摘录（主库）（迭代 4 已实现，详见 09）

原则：**来源已经是主库里的行，就直接指向它；不是行的，才落成摘录。** 三类外部材料（摘录、PDF 标注、剪藏）合称 `MaterialRef`，由谱系端点 `LineageNode` 收纳，不扩 `EntityRefKind`（KL-031）。

| 来源           | 处理                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------ |
| PDF 标注       | 直接作为 `pdf-annotation`（`pdf_annotations.id`）被指向；撤销删除保留原 id（KL-036）                               |
| 微信读书划线   | 保存书时在同一事务里展开成摘录，按外部 id diff，源端删除软删除；存量连库回填；书架同步顺带拉划线（KL-033、KL-034） |
| 浏览器插件划线 | 插件 background 按页发快照 `excerpt.syncPage`，桌面按页 diff，删除随快照传来（KL-035）                             |
| 剪藏网页       | 直接作为 `web-clip`（`web_clip.id`）被指向；只有仍挂在网页条目上的进索引                                           |
| 视频高亮       | 暂不处理                                                                                                           |

表结构以 `packages/db-schema/schema/main/50_learning.sql` 为准：`excerpt(source_type, source_key, source_title, external_id, quote, note, anchor, color, source_time, …, is_deleted)`，唯一键 `(source_type, external_id)`，微信读书 `external_id = bookId:bookmarkId` / `bookId:review:reviewId`（KL-032）。`anchor` 只存来源原生定位，`quote` 即引述锚点的 `exact`（KL-038）。

摘录、PDF 标注、剪藏进入主库向量与全文索引，嵌入文本带来源上下文（KL-037）。打开统一经 `openMaterial` 到原处（单书页划线、PDF 标注、浏览器里的划线、网页条目的解析文档）。

### 5.4 AI 队列 `content-ai-queue`

- 主进程 BACKGROUND 模块，依赖 `database`、`pi-ai`、`content-events`。样板是 Notebook 的 `vibe-learning-index-queue.ts`：**扫库推导待办 + 内存串行 + 切库作废（generation）+ 有限重试**，只在 `index_meta` 存游标与上一轮摘要。
- LLM：`PiAiRuntimeModule.complete`（`D/src-electron/main/modules/pi-ai-runtime.ts`），模型按功能槽 `resolveUsageSlot`（`llm-usage-slot.ts`）取。
- 功能槽：元信息用 `contentMetadata`（覆盖所有「我的思考」，不再叫 `cardMetadata`）；洞见是否单独一个槽，迭代 7 再定。新增槽要改：`D/src/stores/useSettingStore.ts`（类型与默认值）、`D/src/features/settings/sections/LLMSection.tsx`（设置分组与说明文案）、用量页文案、`D/src/hooks/useLLMConfig.ts` 的联合类型（它已经漏了 `vibeLearningImageDescription`，顺手补齐）。
- 元信息存主库 `content_ai_meta`，**按 `content_id` 为键**：投影共用一份正文，也就共用一份标题与要点。字段沿用 ai-insights §3.5 的草案（schema 版本、内容哈希、元信息 JSON、模型信息、生成时间）。
- 正文转文本用 `entity/text-digest.ts` 的 `contentPlainText`（按块纯文本，代码块读 `code`），主进程与渲染端共用；不用渲染端的 `getEditorText`。
- **已实现（迭代 7a，13 §11.3、14）**：
  - 范围：卡片、未删文章、`document` 型项目文档的正文（`count > 0`），按 `content_id` 去重；不含日记与外部材料。
  - 对账：连库时清孤儿行，找出没有元信息、`schema_ver` 过低、或 `contents.update_time` 晚于元信息 `update_time`（最后一次生成或核对）的正文，按更新时间倒序；增量由 `onContentWritten` 记最后写入时间，静置 10 分钟再判断。
  - 重算：正文纯文本字符 bigram MinHash（128 个），与生成时指纹的估计 Jaccard 低于 **0.7** 才调模型（真实编辑样本校准，14 §1）；否则只记核对时间，指纹保留生成时的版本。换模型不作废。
  - 调用：`thinking: "off"`，单次 JSON 输出（标题 ≤ 24 显示宽度、要点 ≤ 60 字、概念 3–8 个、主张 0–3 条）；卡片给正文，长文给标题 + 大纲 + 前 6000 字。串行；单份失败重试 2 次后跳过，失败列表记 `index_meta.content_ai_failures`；连续 5 份失败停本轮；切库 / 换槽 / 清空槽作废并中止请求。
  - 写入后节流 2 秒，`notifyExternalWrite("content-ai-meta:changed")`（脉络写事件白名单）并带 `contentIds` 广播给渲染端。
  - 取标题：主进程 `contentTitles` / `contentTitle`（`tables/content-ai-meta.ts`，按批 LEFT JOIN）；卡片表查询带 `aiTitle`；渲染端 `utils/card-title.ts` 的 `cardTitle`，只替换「当作卡片标题」的 6 处调用点；变更通知后经 `content-ai:titles` 原地补进卡片缓存。
  - **AI 洞见（7b，D-101）**：主进程 `content-insights.ts`，用户点击时分析一篇——本文每个文字 ≥ 80 字的节查近邻（k = 200 块、随机块对 p95 以上、排除已有关系但不排除同项目、按对方正文去重取前 15），一次模型调用（槽 `contentInsights`），输出的原文片段逐字核对后存主库 `content_ai_insights`；渲染端 `features/insights` 把结果画在正文上（洞见视图）。
  - 规模（2 万卡 + 3000 长文，14 §4）：无变化的对账 25 ms，全部改过的核对轮 4.4 s（后台逐份让出），2 万张卡标题批量 21 ms，列表轻表 182 ms。
  - **主题与全局层（7c，D-102，17）**：主进程 `topic-insights`（BACKGROUND）后台按知识地图「子主题 → 主题 → 全局」只读元信息分层生成；结果按成员快照（Jaccard ≥ 0.7）对回当前主题，变化量三档（< 10% / 10%–40% 增量 / ≥ 40% 或连续增量 3 次完整），全局后台每 6 小时最多一次；元信息覆盖率 ≥ 80% 才跑，地图过时先 `ensureFresh`。本地候选：组内相近对、跨主题呼应对（排除概念重合 > 0.4 的同一份内容）、问了但没写的提问组、项目外可能属于某一支的笔记；模型输出里的编号回填成标题，长文片段逐字核对。结果存主库 `knowledge_ai_insights`（含项目回顾）。复用槽 `contentInsights`。

### 5.5 对话信号

- 应用对话存于 `~/.editor/sessions/<库名>/*.jsonl`，随库同步；每条消息有 id（`D/src-electron/main/modules/pi-session-files.ts`）。浏览器插件对话在 `~/.editor/browser-sessions/`，不随库同步，不参与。
- 「从体系发起对话」：会话记录发起实体。`chat_session` 已有 `scope` + `domain_ref`，但它表达的是「归属」（PDF 对话、Notebook 对话），语义不同；发起来源改为写谱系（`src` = 实体，`dst` = `chat-session`，relation `discussed_in`），不复用 `domain_ref`。
- 「问了但没写」：把**用户消息**写入索引库（向量 `type = 'chat-prompt'`，`prefixed_id` 为 `chat-prompt:<sessionId>#<messageId>`），AI 回答不入。**已实现（7c，KL-064）**：只取 `scope = 'main-chat'`，短于 6 字跳过，作为主库向量队列的候选来源（会话按 `update_time` 缓存解析），不进全文、检索结果与覆盖率统计；候选为离笔记都不近（< 随机块对 p95 + 0.05）、彼此相近（≥ p95 + 0.1）的提问组。

## 9. 风险与待实测

- **写入点漏接**：总线漏掉的路径会让派生数据漂移。靠对账兜底，并为总线写一条测试：枚举 `contents` 的写入函数，确认都会 emit。
- **`anchorId` 迁回的阈值**：整篇替换时按内容匹配迁回被引用段落的锚点，相似度阈值与对齐算法要用真实的 AI 编辑样本测，统计锚点保留率（迭代 6）。
- **回填迁移的体量**：全部正文重写一遍 JSON，库文件变化大，同步会整库上传一次。
- **知识地图**：长文向量聚合方式、tag 覆盖率、节点数增加后的计算耗时，都要在真实库副本上实测。
- **摘录同步**：微信读书整列覆盖写、源端删除、插件 XPath 锚定脆弱，摘录要以外部 id 为准，原文定位失败时只显示引文。
- **现有缺陷**（已另开任务）：知识地图漂移统计漏算正文编辑；闪卡引用的正文引用计数只增不减。
