## 3. 独立审查（agent 评审）结果与修复

派发独立 agent 以桌面端源码为金标准做全量审查，结论「数据层质量高，需修复后合入」，发现问题 24 项，已修复 21 项：

**P0（1/1 修复）**：编辑页返回手势绕过未保存守卫——系统返回/边缘侧滑直接弹栈丢表单。修复：`useBackHandler` 与顶栏返回走同一 `requestExit` 守卫。

**P1（5/5 修复）**：

1. 编辑保存静默清除桌面写入的 `data` 字段（hint/referenceNotes）→ `buildData` 改为以原卡 data 为底合并。
2. 筛选 chips 计数基于筛选后数据（切档后其余档归零）→ 计数改用并列的全量查询。
3. 主页掌握度公式 `total - due - new` 重复扣减新卡可出负数（新卡 due_time=创建时间恒已包含在 due 内）→ 改 `total - due` 并加注释。
4. dirty 语义是"有任何内容"而非"有改动"（零修改也弹确认）→ 改为加载快照 diff。
5. 查询失败被渲染成空列表诱导新建 → 补 isError 分支 + 重试按钮（主页与卡组详情）。

**P2（8 项修复 7 项）**：LIMIT 拼接改参数绑定（对齐全库惯例）；间隔预览补 ease 增量（原系统性低估）；`canSubmitAnswer` 注释与桌面事实不符已更正；cloze 逐空判分两处重复实现收敛为 `isBlankCorrect`；建卡校验卡组存在（防同步删除后建出孤儿卡）；`replace_references` 的 ref_count 泄漏加"对齐桌面存量缺陷"注释；两处硬编码 `#fff8ef` 改令牌。未修：复习队列一批 20 张无续批（完成页文案与续批留给 P1 统计迭代）。

**P3（8 项修复 6 项）**：确认框打开时返回先关确认框；队列加载 catch 补 cancelled 守卫；测试注释数学笔误；`crypto.randomUUID` 统一为带 fallback 的 `genId`；卡片滑动加 `touch-action: pan-y` 防纵向滚动劫持；填空输入框改固定宽度（原按答案长度计算会泄露提示）。未修：update 未传 prompt 时回写解析降级后的 Value（功能等价，桌面行为一致）；suspended 无筛选档（桌面亦无入口）。

**审查确认无问题的维度**：调度算法逐字段一致（含 round 语义、状态翻转规则、桌面死分支的等价省略）、SQL 全参数绑定无注入、事务边界完整（含并发互斥）、serde↔前端类型映射、判分语义与桌面一致（single-choice 补防御属合理改进）、Hooks 合规、复习页返回手势符合《移动端页面栈与返回策略》、浮层全走通用容器、令牌使用合规、无 YAGNI 违例、未触发 db-schema parity 规则。

## 4. 消融实验

对全部新代码逐项审视"是否有当前消费者"，删除 6 处无消费者/无收益设计（删后全量回归全绿）：

| 删除项                                                                              | 理由                                                                                                  |
| ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `flashcard_get_deck` 命令 + payload + lib.rs 注册 + tauri 封装                      | 前端零调用——主页与卡组详情均从 `list_decks`（含内联 stats）取数，独立 get 是对桌面 IPC 的机械映射     |
| `flashcard_list_cards` 的 `search` 参数（Rust LIKE 条件 + payload 字段 + 前端参数） | P0 无搜索 UI；P1 接入统一搜索（走 `search.rs` jieba 索引）时按需加回，LIKE 预埋无消费者               |
| `FlashcardReviewPage` 的 `cardRef`                                                  | 只声明挂载、从未读取                                                                                  |
| `CardEditPage` 编辑态加载 `promptText`                                              | 编辑态题干只读渲染走 `card.prompt`（保护桌面富文本），state 里的纯文本无 UI 消费，且是 dirty 误报来源 |
| `FlashcardDeckPage` 的 `useMemo(cards)`                                             | 无稳定引用需求（不传 memo 子组件），`?? []` 包 memo 是无收益代码                                      |
| 类型层若干预留字段（userText 等）                                                   | 迭代中被接口重构取代，已随最终接口清理                                                                |

**保留的边界决策**（有当前消费者或明确低成本回补路径，不算预埋）：

- Rust `references` 写入链路（含 custom 类型建 contents、ref_count 递增）：桌面同步数据带引用，复习页参考资料查看依赖它，属数据层完备性而非预埋。
- `flashcard_reviews` 历史只写不读：与桌面一致，为 P1 统计留数据（已在方案 §9 风险表声明）。
- 前端 `nextIntervalPreview` 复刻调度常量：评分按钮间隔预览有真实 UI，Rust 是权威、前端仅展示，两处已注释互指同步义务。

**消融结论**：最终交付 Rust 1094 行 / 前端 3066 行（含 162 行测试），对比方案预估无膨胀；所有保留代码均有当下消费者或在文档中显式声明为已知边界。

## 9. P2 迭代交付记录：统一搜索 FTS 索引接入（2026-09-14 第三轮）

P1 遗留的「全局统一搜索接入闪卡」按正解完成——flashcards 纳入 reconcile 增量索引，闪卡进入全局搜索的 FTS 主链路（jieba 分词命中），LIKE 兜底同步覆盖。

**机制结论（决定接入方式）**：reconcile 是「全量扫源表 + 逐行 update_time 对比 upsert + stale 清扫」的后台对账（异步协程、运行中合并触发），`index_schema_version/hash` 从不参与变更判定——因此**新增索引源无需 bump 任何版本**，老用户下次启动 `bootstrap_app` 触发 reconcile 即自动补齐 flashcards 索引。

**改动面**：

| 层           | 改动                                                                                                                                                                                                                                                                                           |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| reconcile.rs | `load_indexable_rows` 新增 flashcards 源：题干（Slate JSON，复用 `extract_plain_text`）为主文本、详情提纯 + tags 进 extra、`prefixed_id=flashcard:{id}`；卡组名不进索引文本（hydrate 现查，改组名无需重索引）                                                                                  |
| search.rs    | ① `SEARCH_TYPES` 加 `flashcard`（FTS 与 LIKE 的 `type IN` 过滤同源生效）；② `hydrate_unified_result` 新增分支：题干提纯首行为 title、120 字摘要、`container_id=deck_id` + LEFT JOIN 卡组名（对齐 project-item 的容器语义）；③ `unified_like_sql` 新增 UNION 段（prompt/detail/tags 三列 LIKE） |
| 闪卡写路径   | `create/update/delete card`、`delete deck`（级联删整组）在事务提交后 `common::trigger_reconcile`；`submit_review` **不触发**——只改调度字段不改索引文本，代价是下次全局 reconcile 会重分词已复习卡片（与 cards 更新 category 的现状一致，可接受冗余）                                           |
| 测试         | 现有 LIKE/FTS 两用例扩展：主库补 flashcards/decks 建表与数据，断言 flashcard 结果的 title/容器字段（FTS 用例经真实 jieba 分词行验证端到端）                                                                                                                                                    |
| 前端         | `UnifiedSearchResultType` 联合类型、搜索页类型标签「闪卡」、`openResult` 分发到 `flashcardCardEdit`（编辑态以卡片数据为准，占位参数即刻覆盖）                                                                                                                                                  |

**索引时效性**：卡组删除立即触发（避免整批 stale 行残留到下次全局触发）；新卡/改卡即时可搜；复习评分对可搜性无影响。

验证：`cargo test --lib` 34/34（含扩展用例）、`tsc --noEmit`、`pnpm lint` 0 error、前端 vitest 8/8。

**P2 余量**：AI 制卡/答案评判、卡片批量操作；另记录 reconcile 的既有性能隐患（每次触发对全部行做 jieba 分词、逐行 MAX(update_time) 对比无索引）供未来治理，本次未动。

### P2 第三批：卡片批量操作（2026-09-14 第五轮）

### P2 第三批：富文本建卡（2026-09-14 第五轮）

移动端闪卡编辑能力与桌面端对齐，编辑态题干不再只读（P0 时"富文本题干请在桌面端编辑"的降级方案退役）。
