## 0. 目标与范围

**一句话**：让「问题」成为闭环的枢纽（01 §2.7）：外部材料与对话能挂到问题上，阅读和对话时产生的疑惑一步变成问题，问题攒够了材料能升级为 Notebook（VL）课题。

```
 划线 / PDF 标注 / 剪藏 / 对话 ──挂成材料──▶ 问题 ──以此立项──▶ Notebook 课题
        │                                   ▲                    │
        └────────── 转为问题 ────────────────┘                    └── 材料作为资源带入
```

**数据层（属于迭代 5 的定义，只需确认结构，见 §12.1）**：

- `question_link` 扩类型（摘录、PDF 标注、剪藏）；
- 新表 `question_chat`：问题与对话的关联（§2.2）；
- 谱系新增端点 `question`、`vl-project`，新增关系 `upgraded_to`、`discussed_in`；
- Notebook 资源新增 `material` 来源类型；
- 答案转卡片后的反查口径。

**用户可见入口（每个都要确认，见 §8、§12.2）**：各处「转为问题」、问题「关联已有」能选材料与对话、「以此立项」、从问题发起对话，以及几处展示。

**本迭代不做**：

- 选中一段正文转为问题、段落级地址（迭代 6，需要引述锚点）；
- AI 发现矛盾 / 空白后生成问题、立项提示、对实体「继续聊」（迭代 7）；
- AI 生成卡片 / 文章 / 闪卡（04 待定）；
- 移动端展示。

## 1. 现状调研

### 1.1 表

问题模块共 4 张表（`packages/db-schema/schema/main/20_content.sql:31-66`），**没有独立的答案表**：独立答案就是 `contents` 里的一行，经 `question_link(target_type = 'answer')` 挂到问题上。

| 表 | 关键列 | 说明 |
| -- | ------ | ---- |
| `question_group` | `title`、`color`、`is_default` | 分组；删除分组时其下问题先迁走 |
| `questions` | `question_content`（标题，纯文本）、`description`（背景，Slate JSON）、`status`（`not_started` / `in_progress` / `resolved`）、`answers`（JSON 数组，content id 缓存） | `answers` 只是缓存，每次关联变动都由 `syncAnswersCache` 重写，留给 CLI 等旧消费者读 |
| `question_link` | `question_id`、`target_type`（TEXT）、`target_id`（**INTEGER**）、`content_id`、`sort_index` | 多态材料表；`content_id` 是这条关联持有引用计数的正文（卡片 / 文章 / 项目文档 / 答案有值，项目、白板为 NULL） |
| `question_event` | `type`（`create` / `status` / `link` / `unlink` / `note`）、`payload`（JSON） | 探究轨迹 |

索引：`question_link` 有 `UNIQUE(question_id, target_type, target_id)` 和 `(target_type, target_id)`（`90_indexes.sql:26-27`）。全部表没有外键。

`target_type` 现有 6 种：`card`、`article`、`project_item`、`project`、`white_board`、`answer`（`D/src/types/question.ts:31`）。`answer` 的 `target_id` 是 `contents.id`，其余是各实体表主键。

### 1.3 答案转卡片

- 入口在答案编辑弹窗顶部 `AnswerMetaBar` 的「创建为 ▾」（卡片 / 文章 / 项目文档）。
- 是**投影**：`build-card-from-content` 新建一行卡片指向同一份正文并加引用；这份正文已是卡片就返回已有那张（`tables/card.ts:499-522`）。
- 转换后 `question_link` 仍是 `answer:contentId`。问题详情里它仍在「我的答案」，标签是「独立答案」。
- **脉络已经能反查到**：迭代 1 的 `questionsOf`（`entity-context/context-query.ts:191-228`）先按自身与共用正文的全部身份查 `card` / `article` / `project_item`，再查 `target_type = 'answer' AND target_id IN (自身 content_ids)`。所以卡片、文章、项目文档的「相关问题」分区已经包含「我是哪个问题的答案」。
- 之后在卡片库删掉这张卡片，问题持有的引用还在，答案不会消失。

结论：02 §4.4 说的「按卡片反查不到」只对 `listQuestionsByTarget` 成立，而它没有调用方。见 §5。

### 1.4 Notebook（VL）

- 表：`vibe_learning_project(title, desc, archived, …)`（`desc` 是 Slate JSON 的目标描述，**不进对话提示词**）、`vibe_learning_resources(project_id, name, source_type, source_meta_info, …)`、`vl_note`、测验三张表；对话在 `chat_session`（scope `vibe-learning-chat`，`domain_ref` = 项目 id）。

### 1.8 移动端与 CLI

- 移动端**不读写** `questions`、`question_link`、`question_event` 与 VL 表；只有旧迁移改写过 JSON 列。
- CLI 只读 `questions`（答案从 `questions.answers` 缓存解析），不读 `question_link`，没有写入。
- 问题本身不进向量、全文索引与知识地图。

### 1.9 设计口径（KL-029）

按结构推规模：一个问题的材料通常几条到几十条，`question_link` 按 `(target_type, target_id)` 有索引，反查与解析都是小查询。规模压力只在两处：

- **「关联已有」搜索材料**：摘录可能几万条（09 §1.1），PDF 标注的原文在 `annotation_payload` JSON 里。必须 `LIMIT`，并用规模夹具实测（§11）。
- **立项带入材料**：一次几十条，生成一份 Markdown，不构成压力。

## 2. 类型层

### 2.1 问题材料类型

```ts
// D/src/types/question.ts
export type QuestionLinkTargetType =
  | "card" | "article" | "project_item" | "project" | "white_board" | "answer"
  | MaterialKind;         // "excerpt" | "pdf-annotation" | "web-clip"，直接复用迭代 4 的类型

export interface QuestionLinkTarget {
  targetType: QuestionLinkTargetType;
  targetId: number;             // 仍然只有数字 id；对话不进这张表，见 §2.2
}
```

- 新值按 02 §3.1「新增只用新写法」，用连字符（与 `MaterialKind`、`LineageNode` 一致），存量 `project_item` / `white_board` 不改。
- 材料**不持有引用计数**，`content_id` 为 NULL（与项目、白板相同）。剪藏的解析文档生命周期跟着 `web_clip` 行走，不由问题持有。
- 删除材料不级联清理 `question_link`，解析时降级（弱引用，与现有做法一致）。

### 2.2 问题与对话：新表 `question_chat`

`question_link.target_id` 是 INTEGER，会话 id 是 UUID 字符串。曾比较四个方案：

| 方案 | 做法 | 结论 |
| ---- | ---- | ---- |
| A | 不改表，UUID 以 TEXT 存进 INTEGER 列（SQLite 类型亲和性允许） | **否决**。① 任何 `CAST(target_id AS INTEGER)` 会把 UUID 静默截成开头的数字（实测 `'8f3a1c2e-…'` → `8`），可能撞上真实 id，仓库里已有 `CAST(l.src_id AS INTEGER)` 的写法；② 按 `i64` 读取的代码（移动端 rusqlite）遇到文本直接报错；③ `target_id` 的 TS 类型变成 `number \| string`，现有 `===` 比较埋隐患；④ AI 按表结构说明读到的是整数列。都不会马上出错，出错时也不报错 |
| B | 重建 `question_link`，`target_id` 改 TEXT | 否决。改存量格式，要共享幂等迁移 + 桌面三入口 + Rust 实现（D-091）；存量数字 id 全变字符串，波及面最大 |
| C | 问题与对话的关联记谱系 | 否决。谱系是不可变的来源事实，「解除关联」要删谱系行，语义不对 |
| **D（采用）** | 新表 `question_chat` | 类型干净；只加表，共用 schema 在桌面与移动端自动建出（同迭代 4 的 `excerpt`），不需要迁移函数与 Rust 实现 |

```sql
-- packages/db-schema/schema/main/20_content.sql（question_link 之后）
-- 问题的探究对话：session_id = chat_session.id（pi 会话 UUID）；message_ids 为 JSON 数组，
-- 记录问题从哪几条消息转来（可空）。弱引用：对话被删不级联，解析时降级。
CREATE TABLE IF NOT EXISTS question_chat (
  id          INTEGER PRIMARY KEY,
  question_id INTEGER NOT NULL,
  session_id  TEXT NOT NULL,
  message_ids TEXT,
  create_time INTEGER NOT NULL
);
-- 90_indexes.sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_question_chat_unique ON question_chat(question_id, session_id);
CREATE INDEX IF NOT EXISTS idx_question_chat_session ON question_chat(session_id);
```

- 主库 64 → **65 表**，108 → **110 索引**。
- 不设 `sort_index`：分区按关联时间倒序，不做手动排序（YAGNI）。
- `message_ids`：从对话转为问题（Q3）时记那条用户消息的 pi entry id。本迭代打开对话仍从头显示；定位到消息与迭代 6 一起做，但数据从现在起就记下。
- 删除问题时一并删除它的 `question_chat` 行（与 `question_link`、`question_event` 同一事务）。
- 关联与解除也记 `question_event`（`link` / `unlink`，payload 标明 `chat-session`、会话标题），关联时问题若仍「待探究」同样自动转「探究中」。

## 3. 解析与打开

### 3.1 `resolveMaterials` 扩展

主进程 `question-link.ts` 的 `resolveMaterials` 按类型分派：

| 类型 | 解析 | `missing` |
| ---- | ---- | --------- |
| 现有 6 类 | 不变 | 不变 |
| `excerpt` / `pdf-annotation` / `web-clip` | 批量调 `MaterialTable.resolve`（迭代 4）：标题、出处 `meta`、引文作摘要、想法 | 行不存在；软删除的摘录不算缺失，带 `deleted` 显示原文与「原划线已删除」，不可打开 |

`QuestionMaterial` 增加可选的 `material?: MaterialInfo`，渲染端据此打开，不再自己猜。

对话另由 `QuestionChatTable.list(questionId)` 解析：读 `chat_session` 的标题、scope、消息数、更新时间；行不存在时 `missing`；只有主对话 `openable`。问题详情 `question:get-detail` 一并返回 `chats` 字段，不多一次请求。

### 3.2 `MaterialList` 与打开

- `TARGET_META` 补 3 类：划线（`excerpt`）、PDF 标注、剪藏；图标沿用命令面板「摘录」范围的图标。
- 打开：材料经 `openMaterial`（迭代 4）。
- 材料行的「编辑」只对正文类显示；材料只有「打开」与「解除关联」。

### 3.3 「探究对话」分区

问题详情在「探究材料」之后新增「探究对话」分区（无对话时不渲染）：

- 每行：对话标题、场景（PDF / 视频笔记 / Notebook 对话标注来源，主对话不标）、消息数、最后更新时间；从问题发起的对话（有 `discussed_in`）标「由此发起」。
- 悬停操作：「打开」（只主对话，`navigator.push("chat", { id })`）、「解除关联」（5 秒可撤销，沿用材料行的延迟落库）。
- 对话已删除：灰显「对话已删除」，只能解除关联。

### 3.4 写事件

- 材料：`question:link-targets`、`question:unlink-target` 已在脉络白名单，新增类型走同一 IPC。
- 对话：新增 IPC `question:link-chat`、`question:unlink-chat`。脉络不读 `question_chat`（问题与对话都不是脉络宿主），不进脉络白名单；渲染端经问题 mutation 事件失效查询，与现有问题写操作一致。
- 立项与发起对话的谱系经 `lineage:record`，已在白名单。

## 4. 「转为问题」的统一做法

所有「转为问题」入口共用一套流程，入口只负责给出**来源**和**默认标题**：

```ts
// D/src/services/question-capture.ts（新增，services 层，不属于任何 feature）
export type QuestionCaptureSource =
  | { kind: "material"; target: QuestionLinkTarget }               // 成为第一条探究材料
  | { kind: "chat"; sessionId: string; messageIds: string[] };     // 成为第一条探究对话
export interface QuestionCaptureDraft {
  source: QuestionCaptureSource;
  sourceLabel: string;          // 来源 chip 的文字，如「《书名》· 划线」「对话：xxx」
  defaultTitle?: string;        // 对话的用户提问可直接作标题；划线不预填
}
export function requestQuestionCapture(draft: QuestionCaptureDraft): void;
```

**交互（推荐）：复用命令面板的「记问题」模式**。

- `requestQuestionCapture` 打开命令面板，进入记问题模式；输入框上方显示来源 chip，输入框预填 `defaultTitle`（可为空）。
- 回车：`captureQuestion(title, groupHint)` → 材料走 `linkQuestionTargets`，对话走 `linkQuestionChat`；toast「已收集到「分组」」，带「查看」。
- 背景（`description`）**不预填引文**：材料列表已经显示引文，再抄一份是重复。
- 失败（如材料已不存在）只提示，不创建半截问题：先校验来源可解析，再创建。

**为什么不新做一个弹窗**：命令面板已有「记问题」模式与 `#分组` 解析，用户在别处已经用过；它由壳层挂载（D-003），任何 feature 都能经 services 层的桥打开，不违反「feature 之间不 import 彼此的 store」。桥的实现：`question-capture.ts` 持有一个极小的订阅点，`SearchPalette` 订阅它；面板的 store 不对外暴露。

备选：独立的「转为问题」小弹窗（标题输入 + 分组 + 来源预览）。好处是能显示完整引文，代价是又一套问题创建界面。

## 6. 以此立项

### 6.1 流程

问题详情 →「以此立项」→ 确认弹窗（显示将带入的材料与不能带入的条目数）→ 创建 Notebook → 跳转到 Notebook 详情。

渲染端服务 `D/src/services/question-to-notebook.ts` 编排现有命令（与 `material-to-card.ts` 同一层）：

1. `createVibeLearningProject({ title: 问题标题, desc: 问题背景 })`。
2. 按 §6.2 逐类建资源，逐个 `addVLIndexTask`。
3. `recordLineage({ src: question, dst: vl-project, relation: "upgraded_to" })`。
4. 问题还是「待探究」就转「探究中」（与 `linkTargets` 的自动转换一致）。
5. 跳转 `vibe-learning-detail { id }`。

第 2 步部分失败不回滚项目：已建的保留，toast 说明几条没带入。项目建好而资源全失败，用户仍可手动添加资源。

### 6.2 材料怎么带入

| 问题材料 | 带入为 | 说明 |
| -------- | ------ | ---- |
| 卡片、文章、项目文档 | `note` 资源（`ensureVLNoteResource`，按 `contentId` 去重） | 现有能力 |
| 答案 | `note` 资源，`type = "answer"` | `NoteSourceMeta.type` 是自由字符串，索引只用 `contentId`；资源列表与打开要认识 `answer`（打开到问题） |
| 摘录、PDF 标注 | **合并成一份** `material` 资源：「《问题》的摘录（N 条）」 | 每条一个资源会把资源列表撑满；合并后一份 Markdown，每条为「引文 + 想法 + 出处」 |
| 剪藏 | 每条一份 `material` 资源 | 解析文档是整篇长文，单独成资源 |
| 项目、白板、对话 | 不带入 | 没有对应资源类型；确认弹窗里列出「N 项不会带入」 |

**新资源类型 `material`**（§12.1 待确认）：

```ts
// D/src/types/vibe-learning.ts
export interface MaterialSourceMeta { title: string; refs: MaterialRef[] }
```

- 索引队列新增 `processMaterialResource`：经 `MaterialTable.resolve` 取引文、想法、出处拼 Markdown；剪藏取解析文档 `getMarkdown`。与 `note` 一样是**索引时快照**。
- 表结构不变（`source_type` 是 TEXT，`source_meta_info` 是 JSON）；移动端不读写 VL，不受影响。
- 备选：不新增类型，把摘录拼成一份新正文写进 `contents` 再作为 `note` 资源。代价是产生一份不属于任何实体的孤儿正文，不推荐。

### 6.3 立项之后

- **不自动同步**：立项后问题新增的材料不会进 Notebook。材料带入是一次性的「出发行李」，之后探究在 Notebook 里进行；需要时在 Notebook 里手动添加资源。
- 问题详情头部显示一行「已立项 · Notebook「X」」，可点开；「以此立项」变为「打开 Notebook」。Notebook 被删后谱系降级（KL-026），按钮恢复为「以此立项」。
- 一个问题只对应一个 Notebook（已立项就不再显示立项按钮）。多个问题合并立项不做。
- Notebook 一侧显示「由问题「X」立项」，列入 §8 的 Q7。
- Notebook 的目标描述 `desc` 目前不进对话提示词（§1.4）。是否让 Notebook 对话知道「这个课题要回答什么问题」，属于 Notebook 自身的改动，不在本迭代，记入 §12.4。

## 7. 对话与问题

### 7.1 关系的存储

| 关系 | 存在哪 | 理由 |
| ---- | ------ | ---- |
| 对话是问题的探究对话（手动关联、从对话转为问题、从问题发起） | `question_chat`（§2.2） | 用户可解除；问题详情单独成「探究对话」分区（§3.3） |
| 对话是从问题发起的 | 谱系 `discussed_in`（问题 → 对话），只在 §7.3 写 | KL-007：发起来源记谱系。它是不可变的历史；材料关联可以被用户解除，解除后发起来源仍在 |

两者在「从问题发起」时会同时写，但表达的是两件事，不算重复存储（KL-008 只排除能推导的关系）。

### 7.2 从对话生成问题

对话里**用户消息**的悬浮条加「转为问题」：`defaultTitle` = 这条提问的文字（截断到 200 字），来源 = 这次对话与这条消息的 pi entry id（`question_chat.message_ids`）。

- 只做用户消息：提问本身就是疑问（01 §3.2「我的提问 = 思考方向」）。AI 回答是材料，不是疑问。
- 消息 id 记下，但本迭代打开对话仍从头显示；定位到消息与迭代 6 一起做。
- 只有主对话可打开；PDF / 视频笔记 / Notebook 里的对话不加这个按钮（关联后也打不开，体验不完整）。

### 7.3 从问题发起对话（若做 Q6）

问题详情动作区「围绕它聊」：

- 打开对话页的新草稿，页面参数加 `seed?: { kind: "question"; id: number }`；输入框上方显示「围绕问题：X」chip（`composerAccessory`，PDF 对话样板）。
- 首条消息发送时，经 `prepareUserContent` 把问题标题、背景与材料清单（标题 + 出处，不展开全文）作为上下文附上；AI 需要材料全文时用已有的检索工具。
- 首轮发送、会话登记后：写 `question_chat` 与谱系 `discussed_in`。
- 这套「对话页带种子上下文」的能力，迭代 7 的「继续聊」（从脉络、知识地图发起）可直接复用，届时种子扩展为 `LineageNode`。

### 7.4 问题关联已有对话

问题详情「关联已有」的选择器能选对话（§8 Q4）。对话一侧不显示关联的问题（§8 Q14 不做）。

### 11.3 实现与设计的差异

- **「关联已有」的类型切换**：类型共 9 种，分段放不下，`EntityPicker` 在类型超过 5 种时改用「按钮 + 菜单」（不新增 Segmented 用法），其他调用方仍是分段。对话候选没有整数主键，`EntityCandidate` 加可选 `sessionId`（`id` 为 0），`entityKey` 按 `sessionId` 区分。
- **来源 chip 的文字**：材料取 `MaterialTable.resolve` 的出处（如「微信读书 · 《书名》 · 章节」「PDF · 文件名 · 第 N 页」），统一经 `requestMaterialQuestionCapture`；对话为「对话：标题」。
- **Q8 的实现**：问题详情解析答案时经 `locateAll` 带出共用正文的卡片 / 文章 / 项目文档（`QuestionMaterial.projections`），答案行显示「也是卡片」可点开；不含日记。
- **问题详情一次返回**：`question:get-detail` 增加 `chats`（探究对话）与 `notebook`（已立项的 Notebook）；Notebook 一侧经 `question:source-of-notebook` 查来源问题。
- **立项后的状态**：问题若仍「待探究」，经普通的改状态命令转为「探究中」（轨迹是一条手动状态事件，不是 auto）。
- **材料资源**：`originalPath` 为 `material://<项目 id>/<名称>`（没有原件，阅读区与目录不提供「用默认程序打开」）；转卡片与材料资源共用 `src/entity/material-markdown.ts` 的引文格式，资源里源端删除的摘录在出处后标「（原划线已删除）」。
- **围绕它聊**：对话页参数 `seedQuestion`，只对新对话草稿生效；问题上下文以引用块前置到首条消息（用户在气泡里看得到带了什么），chip 可移除；`navigator.push("chat", { seedQuestion })` 复用对话页当前的新对话草稿。
- **写事件**：`question:link-chat` / `unlink-chat` 不进脉络白名单（问题与对话都不是脉络宿主），渲染端经问题 mutation 事件失效。
- **实测**：规模夹具（`entity-search-scale.eval.test.ts`，`KL_PICKER_SCALE=1` 才跑）5 万条摘录：最近 3.7 ms、命中 9.9 ms、未命中（全表扫）9.9 ms；5000 条 PDF 标注命中 1.0 ms。真实库副本（`context.eval.test.ts`）：206 个问题的列表摘要 1 ms，详情解析平均 0.10 ms、p95 0.20 ms；脉络查询平均 0.19 ms、p95 0.35 ms，与迭代 4 持平。

### 12.1 技术与结构（已写入 04）

- **KL-042 谱系新增端点 `question`、`vl-project` 与关系 `upgraded_to`、`discussed_in`**；「转为问题」不写谱系，`question_link` 即这条关系。（§2.3）
- **KL-043 「转为问题」统一走命令面板的记问题模式**：services 层 `requestQuestionCapture` 桥接，来源 chip + 可选默认标题；来源作为第一条材料，背景不预填引文。备选：独立小弹窗。（§4）

- **KL-045 对话与问题的关系**：关联存 `question_chat`；从问题发起的对话另记谱系 `discussed_in`（问题 → 对话）作发起来源（KL-007）；从对话转为问题只在主对话的用户消息上，记下消息 id，打开定位留到迭代 6。（§7）
