# 06 · 迭代 1 详细设计：底座 + 反向链接 + 脉络面板 v1

2026-10-01。对应 [03-迭代计划.md](03-迭代计划.md) §迭代 1、[02-技术方案.md](02-技术方案.md) §3–§6。路径相对仓库根目录，`D` = `apps/desktop`。

## 0. 目标与范围

**用户可见**：打开任何卡片、文章、项目文档、日记，能看到：

1. **被引用**：哪些笔记在正文里引用了它，以及引用所在那一段的原文片段；
2. **共用正文**：同一份正文的其他身份（例如这张卡也是项目 X 里的一篇文档）；
3. **相关问题**：它是哪些问题的材料。

**本迭代不做**：谱系、摘录、段落级引用目标（`dst_block_id`）、点击后滚动到原段落、移动端展示、知识地图改造。

## 1. 真实库统计（2026-10-01，本机 `data.db` 只读副本）

| 项                                           | 数量          |
| -------------------------------------------- | ------------- |
| contents                                     | 4413          |
| 其中**没有 `collabId`**                      | 4190（95%），合计 6.3 MB |
| 其中含 `content-link`                        | 135           |
| 卡片 / 未删文章 / 项目文档 / 日记段落        | 674 / 76 / 761 / 865 |
| 卡片与项目文档共用正文                       | 22            |
| 有显式 `links` 的卡片                        | 178           |
| `question_link`                              | 173           |

`collabId` 机制 2026-09-06 引入（`bc0f3b5dc`），有 id 的正文更新时间全部晚于这一天；之前写的、之后没打开过的正文都没有 id。

**由此带来的设计调整**（KL-013，已确认）：迭代 1 **不引入任何块 id**。反向链接用「引用所在段落的文本片段」展示上下文。

- 段落锚点与 `collabId` **解耦**：`collabId` 是协作同步的节点身份，生命周期由协作协议决定；段落锚点是用户引用关系的身份，应由产品语义决定。迭代 6 采用独立的 `anchorId`，**只在段落第一次被引用时按需生成**，不回填、不依赖 `collabId`。
- 「从被引用处跳回原段落」不需要块 id：来源文档里指向我的那个 content-link 节点本身就是定位点。
- Markdown：应用内部往返（AI 编辑、源码视图）保留 `anchorId`；**导出分享时剥离**，对方没有这些段落引用。

## 3. 主进程：一份正文对应哪些实体

`D/src-electron/main/modules/tables/entity-search.ts` 新增 `locateAll(db, contentId): EntityRef[]`，以及批量版 `locateAllMany(db, contentIds)`（反向链接要一次解析很多来源）：

```sql
SELECT 'card' AS kind, id FROM cards WHERE content_id IN (…)
UNION ALL SELECT 'article', id FROM articles WHERE content_id IN (…) AND is_delete = 0
UNION ALL SELECT 'project-item', id FROM project_item WHERE content_id IN (…)
UNION ALL SELECT 'diary', d.id FROM diary_segments s JOIN diary_entries d ON d.id = s.diary_id WHERE s.content_id IN (…)
```

返回值带 `contentId` 与展示用的标题（卡片取正文前 N 字，文章与项目文档取 `title`，日记取日期）。现有 `locate`（单个、命中即返回）保留给待办，不动。

**主库索引**（`packages/db-schema/schema/main/90_indexes.sql`）：

```sql
CREATE INDEX IF NOT EXISTS idx_cards_content_id ON cards(content_id);
CREATE INDEX IF NOT EXISTS idx_articles_content_id ON articles(content_id);
CREATE INDEX IF NOT EXISTS idx_project_item_content_id ON project_item(content_id);
```

`diary_segments.content_id` 是否已有索引，实现时核对。按 AGENTS.md 同步 `scripts/db/check-schema-parity.mjs` 的索引数量，执行 `pnpm db:schema:build`、`pnpm db:schema:check`。移动端共用 schema，自动建索引。

## 5. 引用索引

### 5.1 表（索引库）

新分片 `packages/db-schema/schema/index/50_entity_refs.sql`：

```sql
-- 正文里的内联引用（content-link），可从主库正文重算
CREATE TABLE IF NOT EXISTS entity_refs (
  src_content_id INTEGER NOT NULL,  -- 引用所在的正文
  snippet        TEXT NOT NULL,     -- 引用所在段落的纯文本，截断到 160 字
  dst_kind       TEXT NOT NULL,     -- EntityKind
  dst_id         INTEGER NOT NULL,
  dst_content_id INTEGER            -- content-link 节点上的 contentId
);
CREATE INDEX IF NOT EXISTS idx_entity_refs_dst_content ON entity_refs(dst_content_id);
CREATE INDEX IF NOT EXISTS idx_entity_refs_dst ON entity_refs(dst_kind, dst_id);
CREATE INDEX IF NOT EXISTS idx_entity_refs_src ON entity_refs(src_content_id);

-- 每份正文最后一次被解析时的 update_time，用于对账
CREATE TABLE IF NOT EXISTS entity_ref_sources (
  content_id  INTEGER PRIMARY KEY,
  update_time INTEGER NOT NULL
);
```

同步：`scripts/db/build-schema-bundles.mjs` 的 `indexSegments`、`scripts/db/check-schema-parity.mjs` 的 `INDEX_CORE_TABLES`、重新生成 `schema/index.sql`。

**与 02 §4.1 的差异**（实现后回写 02）：

- **显式链接 `cards.links` 不进 `entity_refs`**。它是双向写入的，查询时直接读主库即可（KL-008「能推导的不存」）。
- **增加 `dst_content_id` 与 `snippet`**。按 `dst_content_id` 查反向链接，能自然覆盖共用正文：引用了项目文档 P 的笔记，也会出现在与 P 共用正文的卡片 C 的脉络里。

### 5.2 解析：`D/src/entity/inline-refs.ts`

```ts
export interface InlineRef {
  dst: EntityRef;
  dstContentId: number | null;
  snippet: string;          // 该块的纯文本
}
export function extractInlineRefs(content: unknown): InlineRef[];
```

- 递归遍历全部 `children`；content-link 只出现在 paragraph 里，但 paragraph 可嵌在列表、引用、callout、表格、tabs 等容器中。
- 「块级祖先」取 content-link 的直接父元素（paragraph）；它的纯文本拼接所有文本叶子，content-link 用其 `contentTitle` 代入。
- `refId` 不是数字、`contentType` 不认识的丢弃；同一块内对同一目标的重复引用合并。
- 替换 `D/src/utils/card.ts` 的 `getInlineLinks`（注意它现在值导入了含 React 的 `@/editor-extensions/content-link`，主进程不能用）与 `D/src-electron/main/modules/tables/knowledge-map.ts` 里的副本。`getInlineLinks` 保留为薄包装（只取 card），调用方不改。

### 5.3 索引器模块 `entity-context`

新主进程模块 `D/src-electron/main/modules/entity-context/`，在 `module-config.ts` 注册为 `layer: BACKGROUND`，依赖 `database`：

```
entity-context/
  index.ts          模块：订阅事件、注册 IPC、调度
  ref-indexer.ts    增量与对账（纯函数为主，接收 mainDb、indexDb）
  context-query.ts  context:get 的查询组装
  __tests__/
```

**对账**（`databaseModule.onDatabaseConnected` 触发，仿 `main-content-fts-index-queue.ts`）：

1. `generation` 自增；`ensureIndexDatabaseReady` 返回 null 则跳过。
2. 读主库 `SELECT id, update_time FROM contents` 与索引库 `entity_ref_sources`，得到三类：新增或变更（主库时间更新）、已删除（只在索引里）、未变。
3. 已删除：删 `entity_refs` 与 `entity_ref_sources` 中对应行。
4. 新增或变更：分批（每批 50）读正文。**SQL 先用 `instr(content, '"content-link"') > 0` 过滤**，不含引用的正文只更新 `entity_ref_sources`、清空旧引用，不解析 JSON。含引用的走 §5.2 解析，事务内「删旧插新」。
5. 每批之后检查 `generation`，切库即停；批间 `setImmediate` 让出事件循环。

首次全量：4413 份正文中只有 135 份需要解析，代价很小。

**增量**：`onContentWritten` 按 `(dbName, contentId)` 收集，2 秒防抖后对这批正文执行第 4 步（delete 事件执行第 3 步）。目标库不是当前已连接的库时忽略，由下次连接时的对账处理。

**通知渲染端**：一批处理完、确有引用变化时，`broadcastDatabaseChange("entity-context:changed", dbName)`（`D/src-electron/main/modules/database-notifications.ts`）。另外订阅 `databaseModule.onDatabaseWrite`，事件名属于下列集合时也广播（这些变化会影响脉络的其他分区）：

- 卡片：`cards:patch-scoped`、`update-card`、`create-card`、`create-card-from-project-item`、`build-card-from-content`、`delete-card`
- 文章、项目文档的增删与改标题
- 问题材料：`question_link` 相关的全部写事件

具体事件名实现时从各 `tables/*.ts` 的注册表里取全，并写一条测试防止遗漏。

## 6. `context:get`

### 6.1 接口

```ts
// IPC "entity-context:get"，只读
interface ContextRequest { ref: EntityRef }

interface ContextEntity {
  ref: EntityRef;
  title: string;
}

interface EntityContext {
  self: ContextEntity & { contentId: number };
  /** 共用同一份正文的其他身份 */
  projections: ContextEntity[];
  /** 谁在正文里引用了我；同一来源的多处引用合并，按来源最近更新排序 */
  backlinks: Array<{ source: ContextEntity; snippets: string[] }>;
  /** 我是哪些问题的材料 */
  questions: Array<{ id: number; title: string; status: QuestionStatus }>;
}
```

### 6.2 组装

1. 由 `ref` 查 `content_id`（四张表各自的主键查询）。
2. `projections = locateAll(contentId)` 去掉自身。
3. `backlinks`：索引库按 `dst_content_id = contentId` 查（再并上 `dst_kind/dst_id` 命中但 `dst_content_id` 为空的老节点），得到 `src_content_id` 集合，`locateAllMany` 解析成实体；**排除 self 与 projections**；一份来源正文对应多个实体时，按 卡片 > 文章 > 项目文档 > 日记 取一个展示。
5. `questions`：对 self 与全部 projections，调 `QuestionLinkTable.listByTarget`（kind 映射回 `project_item`），再并上 `target_type='answer' AND target_id = contentId` 的情况，去重。
6. 每个分区最多返回 50 条，并返回总数（v1 不做分页）。

### 6.3 渲染端

- 命令：`D/src/commands/entity-context.ts`，契约放 `D/src/commands/contracts/`。
- 查询：`useEntityContext(ref)`，key `["entity-context", databaseName, kind, id]`，`refetchOnWindowFocus: true`。
- 失效：模块顶层 `on("entity-context:changed", …)`，按库名失效 `["entity-context", databaseName]`（仿 `D/src/features/vibe-learning/quizQueries.ts`）。

## 7. 脉络 v1：元信息行入口 + 浮层（KL-015）

mockup：`apps/desktop/mockups/context-panel/index.html` 的 D。原则是**克制**：正文区域不增加任何东西，关联收在元信息行的一个计数里。

### 7.1 形态

```
  重排与重绘
  ● 知识 · 2026-08-02 创建 · 212 字 · ⟡ 4 处关联                ⋯
                                        ┌──────────────────────────────┐
                                        │ 被引用                        │
                                        │  ▤ 浏览器是怎样把一页画出来的  │
                                        │   ……就会触发「重排与重绘」……   │
                                        │ 也出现在                      │
                                        │  ▦ 前端体系 · 渲染篇           │
                                        │ 相关问题                      │
                                        │  ? 为什么 transform 动画…  探究中│
                                        └──────────────────────────────┘
```

- **入口**：元信息行末尾（`⋯` 菜单之前）一个计数「N 处关联」，N = 被引用来源数 + 共用正文数 + 相关问题数。**N 为 0 时不渲染**，新卡片看不到任何东西。
- **浮层**：点击计数打开，锚定在计数下方，宽约 380px，最大高约 460px，内部滚动。分区：被引用（来源 + 片段，标题在句中点亮）、也出现在、相关问题（带状态）。**不含「引用了」**：出链在正文里本来就看得见，卡片还有「连接」区。
- **交互**：点击条目打开对应实体并关闭浮层；点浮层外或按 Esc 关闭。浮层经 `useOverlayDismiss` 接入 Esc 仲裁（AGENTS.md「全局浮层」规则），业务代码不自行监听 Esc。
- **视觉重点**只有一处：被引用片段里点亮自己的标题（`--tau-accent-soft` 底部高亮）。其余元素压低到 `ink-2` / `ink-3`。
- 已知代价：最容易被忽略。先这样上线，观察使用后再决定是否需要「有新的被引用」之类的弱提示，不预先做。

- 不做视觉走查；面板形态由用户验收。

## 11. 风险

- **写入点漏接**：靠护栏测试与连接时对账兜底。
- **`contents.update_time` 未被某条写入路径更新**：对账会漏。实现时核对 4 个收口点与迁移代码都更新了 `update_time`（`projectLocalContent` 已确认会更新）。
- **`diary-daily` 的 `refId` 语义**：未核实，见 §2.3。
- **content-link 的 `contentId` 可能过期**（目标实体的正文被替换过）：按 `dst_kind/dst_id` 再查一次兜底（§6.2 第 3 步）。
