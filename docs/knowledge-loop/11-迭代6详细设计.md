## 0. 目标与范围

**一句话**：让长文（文章、项目文档）里的一节成为一个观点单元——能被检索命中到节、能被定位打开、能被抽成卡片并记住出处；最后再给用户一个「引用这一段」的稳定地址。

迭代 6 在 03 里列了五件事，它们的依赖与代价差别很大：

| 部分 | 内容 | 依赖 | 代价 |
| ---- | ---- | ---- | ---- |
| A 引述锚点 | 引文 + 前后文；在当前正文里找回位置，找不回降级 | 无 | 纯函数 + 谱系锚点字段 |
| B 节级语义单元 | 长文按节切块、嵌入带标题路径；命中能回到节 | 无 | 索引库结构变化 + **全库重新嵌入一次** |
| C 打开到位置 | 卡片 / 文章 / 项目文档详情页能滚到某一节、某一段 | A 或 B | 页面参数 + 编辑器定位 |
| D 抽一节 / 一段成卡片 | 复制 + 谱系 `derived`，来源记引述锚点（KL-011） | A、C | 入口 + 服务 |
| E `anchorId` 段落引用 | 用户主动「引用这一段」；内联引用带 `blockId` | C | **改正文结构**：编辑规则、Markdown 编解码、AI 改写迁回、移动端 / 博客 |

**推荐分两段**（§12.3 待确认）：本次实现 A–D（6a），E 单独成 6b，等 6a 验收、看到「段落级地址」的真实需求后再开工。理由见 §7.1。

**本迭代不做**：知识地图细化到节级节点（01 §8 待定，规模另评估）；AI 洞见、阅读时标记（迭代 7）；移动端展示。

## 1. 现状调研

### 1.1 切块与向量索引

- **切块**（`D/src-electron/main/utils/smart-chunk.ts`）：按长度切，标题只是「高分断点」（`#` 100、`##` 90…），不是硬分节；默认 500–2000 字、无重叠。`smartChunkWithRanges` 能给出起止偏移与行号，但**主库向量与全文都用只返回文本的 `smartChunk`**，位置被丢掉。Notebook 的索引队列用带位置的版本，并有 `chunk_index`、行号列，可作参照。
- **嵌入文本不带标题**：块原文直接嵌入（`tables/vec-document.ts:242`），不带实体标题，也不带所在章节。
- **存储**：索引库 `vec_documents`（vec0 虚表：`prefixed_id`、`update_time`、`content`（块原文）、`type`、向量）。一个实体多块共用 `prefixed_id = type:id`，**没有块序号、没有位置**。全文 `content_fts` 有 `title`、`chunk_index` 列，但**从未写入**。
- **重建机制**：只有嵌入指纹（模型、维度等）变化时整表重建；增量只比 `update_time`。**切块规则变了不会触发重建**，没有口径版本（引用索引有 `REF_INDEX_VERSION`，可参照）。
- **本地模型的长度**：bge-m3 每 480 token 一窗、多窗向量取平均（05「补 `<s>` + 分窗」）。一块 2000 字约 3–4 窗，块内语义已被平均稀释。

### 1.2 检索结果

- 向量按块召回，再按实体去重（取最高相似度）；`SearchResult` 只带整篇正文，**命中块文本被丢弃**。
- 混合检索的 snippet 是全文里第一个词面命中周围 220 字；纯语义命中时与命中块无关。命令面板显示的是整篇正文前 90 字。
- AI 工具 `search_knowledge` 给模型的是**整篇正文**（不截断、不含命中块），长文多时既费 token 又不聚焦。
- 知识地图把实体所有块向量取平均（`src/knowledge-map/vectors.ts`）。

### 1.3 正文结构与 Markdown

- Slate 顶层块；标题元素 `type: "header"`、`level` 1–6。演示模式已有「取出现两次以上的最高级标题作为分节级别」的逻辑（`D/src/components/PresentationMode/sections.ts`）。
- `getMarkdown` 按顶层块逐个拼接，块 ↔ Markdown 偏移容易恢复；另有 `getMarkdownWithPositions`。
- **段落的 Markdown 只输出文字**（`packages/editor/src/extensions/paragraph/markdown.ts:16`），块上的其他字段在 Markdown 往返中丢失。content-link 的 Markdown 是 `:content-link[文字]{refId contentId contentType title}`（`D/src/utils/markdown-codecs.ts`），与移动端、插件共用 `@tau/shared` 的指令解析。
- **AI 编辑写回是整篇重新导入**：`services/content-editing/persist.ts` 把改后的 Markdown 经 `importFromMarkdownWithPositions` 生成新正文。源码视图同理。
- 协作层按整个节点保存块字段（`packages/collaboration/src/document.ts`），移动端、博客与桌面共用 `@tau/editor`，正常编辑不丢未知字段。
- `collabId` 不稳定（KL-013）：AI 编辑、Markdown 往返、整篇替换会换新；95% 的老正文没有。

### 1.4 定位与打开

- 卡片、文章详情页参数只有 `id`；项目详情有 `itemId`，没有块位置。
- 文章目录已能「按标题序号 → 编辑器实时节点 → DOM」定位（`resolveEditorHeaderAnchor`，`ContentOutline`），可以复用来滚到某一节。
- 对话页能 `scrollToIndex` 到某条消息（会话树跳转在用，`ChatContainer.tsx:1421`）；问题的探究对话已存 `message_ids`（迭代 5），只差打开参数。
- 脉络「被引用」点击只打开来源实体，不滚到引用所在段落（迭代 1 明确未做）。

### 1.5 可复用的匹配工具

- `D/src/utils/review-merged-content.ts`：按块的 LCS 对齐 + 相似度打分（AI 修订审阅在用）。
- `fast-diff`（`packages/collaboration`、`editor-collab` 已依赖）。
- 谱系 `entity_lineage.src_anchor` 是 JSON 文本，目前只有 `{ messageIds }`，加字段不改表。

### 1.6 设计口径（KL-029）

按结构推规模，不按本机数据：

- **向量条数**：节通常几百字。重度用户上万篇长文、每篇十几节，节级切块后向量条数可达十万到二十万量级（现在按 500–2000 字切约少 2–3 倍）。vec0 是精确 KNN，十几万条 1024 维仍在百毫秒内；知识地图的 `neighborsOf` 按块查近邻，耗时随块数线性增长，要实测。
- **重新嵌入一次**：切块规则一变，全库每块都要重嵌。远程模型按 token 计费，总量≈全库正文 + 标题路径前缀（约多 5%）；本地模型串行，耗时与全库文本量成正比，首次需要后台跑一段时间。只做一次，用口径版本触发。
- **锚点找回**：在一份正文里找一段引文，正文最长几万字，按块滑动比对是毫秒级；只在打开定位、显示来源时做，不批量做。

## 2. 引述锚点（A）

### 2.1 结构

```ts
// D/src/entity/quote-anchor.ts（纯 TS，主进程与渲染端共用）
export interface QuoteAnchor {
  exact: string;      // 引文（纯文本，最长 2000 字，超出截断并记 truncated）
  prefix: string;     // 引文前约 32 字
  suffix: string;     // 引文后约 32 字
  heading?: string;   // 所在节的标题路径「一级 › 二级」，找回失败时用于展示与粗定位
  truncated?: boolean;
}

// D/src/entity/lineage.ts
export interface LineageAnchor {
  messageIds?: string[];
  quote?: QuoteAnchor;   // 新增
}
```

- 与 W3C Web Annotation 的 TextQuoteSelector 同构（KL-017）。摘录的 `quote` 就是 `exact`（KL-038），外部材料不加 prefix / suffix（打不开原文去匹配），不受本节影响。
- 存储：谱系 `src_anchor`（JSON 文本），不改表。

### 2.2 生成

`buildQuoteAnchor(content: Descendant[], range: { start: Point; end: Point })`：把正文按顶层块转纯文本（块之间换行），在拼接文本上取选区文字与前后各 32 字；同时记所在节的标题路径。抽一整节时，`exact` 是整节文本（截断到 2000 字），`heading` 是该节标题路径。

### 2.3 找回

`resolveQuoteAnchor(content, anchor) → { status: "exact" | "fuzzy" | "lost", blockStart, blockEnd, score }`：

1. **精确**：在拼接文本里找 `exact` 的所有出现；只有一处直接命中；多处时按 prefix / suffix 的匹配长度选最佳。
2. **模糊**：精确找不到时，用 `fast-diff` 按块窗口比对，算 `exact` 与候选窗口的相似度（共同字符 / 较长者长度），并用 prefix / suffix、`heading` 加权；高于阈值（候选 0.75，实现时用编辑样本校准）算 `fuzzy`。
3. **找不回**：`lost`。界面显示保存的引文与「原文已修改」，打开时退到 `heading` 所在节；节也找不到就打开到文首。

结果映射到顶层块区间，供 §4 打开定位与高亮。

## 3. 节级语义单元（B）

### 3.1 分节

`splitSections(content, title)`（纯函数，主进程用）：

- **分节标题级别**：取正文里出现两次以上的最高级标题（与演示模式同一规则）；没有标题的短文、卡片整篇一节（KL-016：卡片整张嵌入）。
- 每节 = 标题块 + 到下一个同级或更高级标题前的所有块；记 `blockStart`、`blockEnd`（顶层块序号）与标题路径（各级祖先标题 › 本节标题）。
- **长节再切**：一节超过约 1200 字时，用 `smartChunkWithRanges` 在节内按段落切，子块继承同一标题路径并记块区间；短于约 80 字的节与下一节合并（避免只有标题的节）。
- 嵌入文本：`实体标题 › 标题路径\n\n本节 Markdown`（KL-016）。全文索引同样按节写，补写 `title`、`chunk_index`。

### 3.2 存储（索引库，可重建）

| 方案 | 做法 | 取舍 |
| ---- | ---- | ---- |
| **a（推荐）** | `vec_documents` 加元数据列 `chunk_index`；新表 `content_sections(prefixed_id, chunk_index, heading_path, block_start, block_end, char_count)`，主键 `(prefixed_id, chunk_index)` | 向量表本就随口径版本整表重建，加列不需迁移；节信息在普通表里便于 JOIN、调试 |
| b | 节信息全部塞进 `vec_documents` 的元数据列 | vec0 元数据列类型与查询有限制，文本列多了检索时整行读出 |

- 新增**主库正文的切块口径版本** `MAIN_CHUNK_VERSION`，并入嵌入指纹；版本变化即整表重建（与模型变化同一条路径）。本迭代升到 1 触发一次全量重嵌。
- 索引库核心表 10 → **11 张**（`content_sections`），同步 `check-schema-parity.mjs` 的 `INDEX_CORE_TABLES`。主库不变。
- 外部材料（摘录、PDF 标注）本来就是一条一块，不分节；剪藏解析文档按节切（它也是长文）。

### 3.3 检索结果带出命中的节

- 向量检索去重时保留最佳块的 `chunk_index`；`SearchResult` 增加 `section?: { chunkIndex, headingPath, text, blockStart, blockEnd }`。
- 混合检索的 snippet 优先用命中节文本（修正现在纯语义命中时 snippet 与命中无关的问题）。
- 知识地图仍按实体聚合（平均所有节向量），节级节点不在本迭代。

## 5. 抽一节 / 一段成卡片（D）

- **复制 + 谱系**（KL-011）：新卡片的正文 = 选中块的深拷贝（去掉 `collabId`，保留格式与内联引用）；谱系 `derived`（文章 / 项目文档 → 卡片），`src_anchor.quote` 记引述锚点。

## 7. 段落引用 `anchorId`（E，推荐另起 6b）

### 7.1 为什么推荐推迟

- **用户可见的收益是「@ 引用到某一段，点了跳到那一段」**。A–D 做完后，被引用跳回原处（S5）已经能定位到引用发生的位置；「引用别人的某一段」目前没有观察到的需求。
- **它是唯一改正文结构的部分**，牵动面最大：
  1. 编辑规则：Slate 拆分段落时新段落会复制旧段落的全部字段（两段同一个 `anchorId`），粘贴会复制，合并会丢掉第二段的字段——都要在 normalize 里处理；
  2. Markdown：段落目前只输出文字，`anchorId` 要在 Markdown 里有载体（如段尾 `{#a-xxxx}` 或 HTML 注释），否则 AI 编辑、源码视图一次就全丢；同时导出、复制为 Markdown、发布博客时要剥离；
  3. AI 改写写回是整篇导入（§1.3），要按 KL-010 在写回前按内容把锚点迁回，阈值要用真实 AI 编辑样本测；
  4. content-link 加 `blockId` 属性，`@tau/shared` 指令解析、移动端渲染与点击、博客都要认识；
  5. 引用索引 `entity_refs` 加 `dst_block` 列并升 `REF_INDEX_VERSION`。
- A 的引述锚点已经覆盖了系统内部的所有段落定位需求（抽卡、问题材料、AI 标记），`anchorId` 只服务「用户手动段落引用」这一个场景（KL-017）。

### 7.2 若现在做的草案（供比较）

- 「引用这一段」：段落悬浮条 / 选区工具条一个按钮，生成 `anchorId`（短 id）写进该块，复制一个 `content-link{blockId}` 到剪贴板或插入当前编辑处。
- normalize：同一正文内 `anchorId` 去重（保留文档序靠前的）；拆分时后半段去掉；合并时第一段没有就继承第二段的。
- Markdown：段尾 `{#anchor}` 属性（内部往返保留，导出剥离）；AI 写回前按 `review-merged-content` 的块对齐迁回，迁不回的锚点从引用降级为整篇引用，引用处显示「原段落已修改」。
- 移动端、博客：认识 `blockId` 但只按整篇打开（降级），不提供生成入口。

## 12. 决策（用户 2026-10-02 确认：全部按推荐）

### 12.1 技术与结构（已写入 04）

- **KL-046 引述锚点结构**：`{ exact, prefix, suffix, heading?, truncated? }`（TextQuoteSelector 同构），存谱系 `src_anchor.quote`；找回顺序精确 → 模糊（`fast-diff` 按块窗口，阈值实测后定，候选 0.75）→ 丢失降级为显示引文、打开到所在节或文首。（§2）
- **KL-047 分节规则**：分节级别 = 出现两次以上的最高级标题；超过约 1200 字的节在节内再切，短于约 80 字的节并入下一节；卡片与无标题短文整篇一节；嵌入文本 = 「实体标题 › 标题路径 + 本节」。（§3.1）
- **KL-048 节信息存索引库**：新表 `content_sections` + `vec_documents.chunk_index`，主库不变；切块口径版本并入嵌入指纹，**本次触发全库重新嵌入一次**。（§3.2、§9.3）
- **KL-049 打开到位置**：详情页可选参数 `at`（块序号或引述锚点），`openEntity` 统一；定位失败停在文首。（§4）
- **KL-050 抽成卡片 = 复制 + `derived` + 引述锚点**（KL-011），新卡片去掉 `collabId`；原文正文不加标记。新卡片分类：推荐「永久」（来自我的思考，不是文献）。（§5）
- **KL-051（若做 S4）`question_link` 加可空列 `anchor`**，材料仍指向整个实体，锚点只负责定位与显示引文。（§6）
