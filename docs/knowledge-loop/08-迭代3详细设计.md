# 08 · 迭代 3 详细设计：谱系 + 脉络补「被使用」

2026-10-02。对应 [03-迭代计划.md](03-迭代计划.md) §迭代 3、[01](01-模块联动与知识闭环.md) §4.2 与 §5、[02](02-技术方案.md) §4.2。路径相对仓库根目录，`D` = `apps/desktop`。

## 0. 目标与范围

**用户可见**：

1. 脉络浮层多出「来源」「衍生」：从对话存下来的卡片知道自己来自哪段对话；卡片能看到由它生成的闪卡；从 Notebook 复制进项目的文档知道自己来自哪篇笔记。
2. 脉络浮层多出「被使用」：这张卡被放进了哪些白板（含思维导图节点关联的笔记）、被哪些待办关联、被哪些 Notebook 当作资源（用户 2026-10-02 提出）。
3. 补齐两个断掉的入口：AI 回答「存为卡片 / 文章」、「生成闪卡」。

**本迭代不做**：摘录与插件划线（迭代 4，插件笔记的来源 URL 一并放到那里）；问题升级为课题、答案转卡片后的材料迁移（迭代 5）；抽段落成卡片与引述锚点（迭代 6）；移动端展示脉络。

## 1. 现状调研

### 1.1 设计口径

**技术决策按数据结构与可能的规模推导，不按本机库的数量下结论**：本机某个功能用得少（如白板只有十几页、待办关联为 0），不代表别人也少。本机统计只用来做实测与回归对照（实现后在 05 记录耗时）。

据此：

- 反查走**已有索引**的（待办关联 `todo_note_link(content_id)`、闪卡引用 `flashcard_references(content_id)`），查询时直接查。
- 反查要**解析大块 JSON** 的（白板画布，可能含大量元素甚至内嵌图片数据），不在查询时扫，建派生索引（§4.4），与引用索引 `entity_refs` 同一套做法（KL-009）。

### 1.2 「转为 / 存为 / 生成」入口盘点

| 入口                                                                                           | 投影 / 复制        | 现在记了什么                      | 本迭代                                      |
| ---------------------------------------------------------------------------------------------- | ------------------ | --------------------------------- | ------------------------------------------- |

| 插入笔记弹窗 shared-content（答案、白板文本 → 项目文档）                                       | 投影               | `refType="content"`               | 不动                                        |

| 卡片 / 文章 / 项目文档「生成闪卡」                                                             | 闪卡引用正文       | `flashcard_references.content_id` | 不写谱系，查询时推导（KL-008）              |

| Notebook 对话里的 `vibe_learning_save_note`（把对话内容存为产物）                              | **新建**           | 无                                | 写 `saved_from`（对话 → Notebook 笔记）     |
| 白板「复制一页」                                                                               | 复制画布           | 无                                | 不做（不是笔记）                            |

其他事实：

- **对话里目前没有创建卡片、文章、闪卡的工具**：`a0483c89e` 之前有 `create_card_and_activate_tab`、`create_article_and_activate_tab`、`generate_flashcards_from_conversation`，那次重构一起删了。所以「存为卡片 / 生成闪卡」只能由界面入口承担（§3.1、§3.2）。以后若恢复这类工具，必须同样写 `saved_from`（`srcAnchor` 记 `toolCallId` 所在消息），见 §2.3 的约定。
- Notebook 生成任务（从资源生成笔记、大纲等）不写谱系：资源与笔记的关系是「Notebook 用了这篇笔记」，查询时由资源表推导（§4.4），不是一对一的派生。
- 主进程 `D/src-electron/main/modules/web-clip.ts` 是死代码：经 `ModuleInitManager` 用 WebSocket RPC 注册 `web-clip:start/cancel/status`，全仓库没有调用方；逻辑与渲染端 `webClipTaskRunner.ts` 重复。
- `ConversationFlashcardDialog` 仍挂在 `App.tsx`，但唯一的调用方（MCP 工具）在 `a0483c89e` 被删；参数里的 `chatGroupId` 是旧的数字 id，与现在 `chat_session.id`（TEXT）对不上。
- 一条 AI 回答由多个 pi entry 组成，渲染端消息上带 `piEntryIds`（`packages/shared/src/chat-core/messages.ts`）；「会话 id + piEntryIds」可以唯一定位一条回答。
- 主库没有版本号；表的增删与数据迁移写成共享幂等函数，挂到桌面开库、下载校验、CLI 三个入口（样板 `packages/db-schema/src/feature-table-retirement.ts`）；移动端共用 `main.sql`，新表自动补建，**删表与数据迁移要在 Rust 写同口径实现**（样板 `apps/mobile/src-tauri/src/database/main_upgrade.rs`、`audio_note_retirement.rs`）。

## 2. 谱系表 `entity_lineage`（主库）

### 2.1 表

```sql
-- packages/db-schema/schema/main/40_resource.sql（替换 content_link 的位置）
CREATE TABLE IF NOT EXISTS entity_lineage (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  src_kind    TEXT NOT NULL,
  src_id      TEXT NOT NULL,     -- 统一存文本：对话 id 是字符串
  src_anchor  TEXT,              -- JSON：{ messageIds?: string[] }；迭代 6 再加 quote
  dst_kind    TEXT NOT NULL,
  dst_id      TEXT NOT NULL,
  relation    TEXT NOT NULL,
  create_time INTEGER NOT NULL
);
-- 90_indexes.sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_entity_lineage_unique ON entity_lineage(src_kind, src_id, dst_kind, dst_id, relation);
CREATE INDEX IF NOT EXISTS idx_entity_lineage_dst ON entity_lineage(dst_kind, dst_id);
```

- 唯一索引的前缀已覆盖按 `src` 查，不再单建 `(src_kind, src_id)`。主库索引数 107 − 3（`content_link`）+ 2 = **106**，表数不变 63。
- 弱引用：不持有 `ref_count`，两端删除时**不级联删谱系行**；查询时解析不到的端点按 §5.3 降级。理由同 KL-008：删除路径遍布桌面、移动端、CLI，逐一接级联成本高且易漏；残留行很小。
- 移动端不写入，只随 schema 建表。

### 2.2 端点类型

谱系的端点比 `EntityRef`（四类正文实体，`id: number`）宽：

```ts
// D/src/entity/lineage.ts（纯 TS，主进程与渲染端共用）
export type LineageNode =
  | EntityRef // card / article / project-item / diary
  | { kind: "chat-session"; id: string }
  | { kind: "vl-note"; id: number }
  | { kind: "web-clip"; id: number }
  | { kind: "flashcard"; id: number };

export type LineageRelation = "derived" | "saved_from" | "clipped_from";
```

- **不扩 `EntityRefKind`**：`EntityRef` 被引用索引、知识地图、`openEntity` 广泛使用，且假设 id 是数字；谱系另起一个联合类型，`EntityRef` 是它的子集。
- 存储层统一文本，读出时按 kind 还原数字 id。
- 关系只实现本迭代用到的三种；`excerpt_of`、`upgraded_to`、`discussed_in` 随迭代 4、5、7 再加（02 §4.2 表保留）。

### 2.3 写入

主进程表模块 `D/src-electron/main/modules/tables/entity-lineage.ts`：

| IPC                | 作用                                                                |
| ------------------ | ------------------------------------------------------------------- |
| `lineage:record`   | `INSERT OR IGNORE`，幂等；参数 `{ src, dst, relation, srcAnchor? }` |
| `lineage:find-dst` | 按 `src + relation` 查衍生（剪藏用：网页条目 → 解析文档）           |

- 渲染端 `D/src/commands/lineage.ts`。写入是「先建实体、再记谱系」两步 IPC，**谱系写失败只记日志、不回滚实体**：它是附加信息，丢一条不影响主功能。
- `lineage:record` 进 `CONTEXT_WRITE_EVENTS`，写完脉络自动刷新。
- **约定**：今后任何「把 A 的内容复制 / 存成 B」的新入口（界面按钮或 AI 工具）都要写谱系；投影类（共用正文）不写。这条写进 02 §4.2。

## 3. 写入点

### 3.1 AI 回答存为卡片 / 文章（新入口）

- 位置：`D/src/components/ChatUI/MessageView.tsx` 的 `hoverActions`，**只在 AI 回答上**加一个「存为…」按钮（lucide `BookmarkPlus`），点开 `Menu`：存为卡片 / 存为文章 / 生成闪卡（§3.2）。三项共用一个按钮，避免悬浮条变长。
- 内容：该回答的**最终文本**（不含思考、工具调用过程），Markdown 经 `importFromMarkdown` 转正文。文章标题取回答的第一个标题，没有则取对话标题。
- 新建正文（复制，不是投影：回答在 JSONL 里，不在 `contents`），然后 `lineage:record({ src: { kind: "chat-session", id: sessionId }, dst: card/article, relation: "saved_from", srcAnchor: { messageIds: piEntryIds } })`。
- 完成后 toast「已存为卡片」，带「打开」。
- 回调经 `ChatContainer` 往下传（同 `onCreateBranch`），`MessageView` 不直接依赖卡片 / 文章命令。

### 3.2 对话生成闪卡（补入口）

- 入口：§3.1 菜单的「生成闪卡」。素材是**这条回答及其对应的提问**，不是整段对话：粒度与「存为卡片」一致，生成更聚焦；整段对话的入口等有需要再加。
- `useConversationFlashcardStore.openGenerationModal` 的 `chatGroupId: number` 改为 `sessionId: string` 与 `messageIds: string[]`；保存后对每张新闪卡 `lineage:record({ src: chat-session, dst: { kind: "flashcard", id }, relation: "saved_from" })`。
- 闪卡没有脉络入口，这些谱系现在无人展示；照记，因为来源事后推导不出来（01 §4.2「零成本、完全准确」）。

### 3.3 Notebook 笔记复制进项目

- `InsertNoteToTreeModal` copy 分支新增可选 prop `source?: LineageNode`；建出项目文档后 `lineage:record({ src: { kind: "vl-note", id }, dst: project-item, relation: "derived" })`。
- 只有 `NoteEditorView` 传 `source`；插件笔记（`ExtNoteInsertModal`）的来源是网页 URL，等迭代 4 网页 / 摘录成为实体后再接。
- 顺手删掉弹窗里无调用方的 `webview`、`video-note` 两个分支。

### 3.3.1 Notebook 对话「存为产物」

`vibe_learning_save_note`（`D/src/features/vibe-learning/views/VibeLearningView/chat/productTools.ts`）建出 `vl_note` 后，写 `lineage:record({ src: chat-session, dst: { kind: "vl-note", id }, relation: "saved_from", srcAnchor: { messageIds } })`。工具执行上下文里有会话 key 与 `toolCallId`，消息 id 取工具调用所在的 entry。之后这篇笔记转成卡片（投影），卡片经「也出现在」能看到 Notebook 笔记，Notebook 笔记的来源是对话。

### 3.4 `content_link` 迁入谱系并删表

- 迁移函数 `packages/db-schema/src/content-link-retirement.ts`（不依赖 electron）：表不存在就直接返回；否则 `VACUUM INTO` 备份 → `BEGIN IMMEDIATE` → 确保 `entity_lineage` 存在 → `INSERT OR IGNORE INTO entity_lineage SELECT 'project-item', source_id, NULL, 'web-clip', target_id, 'clipped_from', create_time FROM content_link WHERE source_type='project_item' AND target_type='web_clip'` → 其余行（类型不符）存在则失败不放行 → `DROP TABLE content_link` → 提交。失败抛 `CONTENT_LINK_RETIREMENT_FAILED:`，开库失败（D-091）。

- 移动端：`apps/mobile/src-tauri/src/database/content_link_retirement.rs` 同口径实现，同样排在知识库迁移之后；跨端 fixture 放 `packages/db-schema/fixtures/`。

## 4. 脉络查询（`entity-context:get` 扩展）

### 4.1 返回体

`D/src/types/entity-context.ts` 的 `EntityContext` 新增：

```ts
sources: ContextLineageItem[];    // 我从哪来
derived: ContextLineageItem[];    // 我产生了什么
usages: ContextUsage[];           // 被白板使用、关联待办、Notebook 资源

interface ContextLineageItem {
  node: LineageNode;
  relation: LineageRelation;
  title: string;                  // 解析不到时为空串，missing = true
  meta: string;                   // 「对话」「Notebook · 项目名」「闪卡 · 卡组名」
  missing: boolean;
}
type ContextUsage =
  | { kind: "whiteboard"; pageId: number; title: string; meta: string; open: WhiteboardOpenTarget }
  | { kind: "todo"; todoId: number; title: string; completed: boolean }
  | { kind: "notebook"; projectId: number; title: string };
// 白板页的归属三种：独立白板 / 项目里的白板条目 / 文档里嵌入的白板块
type WhiteboardOpenTarget =
  | { page: "whiteboard-detail"; id: number; pageId: number }
  | { page: "project-item"; projectId: number; itemId: number }
  | { page: "entity"; ref: EntityRef };
```

各分区仍截断 50 条。

### 4.2 来源与衍生

- `sources`：`entity_lineage WHERE dst_kind = self.kind AND dst_id = self.id`，**并对共用正文的各个身份一起查**（同一份正文是卡片也是项目文档时，来源对两者都成立）。
- `derived`：`entity_lineage WHERE src = self（及共用正文的身份）` ∪ **闪卡推导**：`flashcard_references.content_id IN contentIds` → 闪卡（标题取 `prompt` 纯文本，meta 为卡组名）。
- 端点解析：四类正文实体复用 `EntitySearchTable.resolve`；`chat-session` 读 `chat_session.title`；`vl-note` 读 `vl_note` 与项目名；`flashcard` 读 `flashcards` 与卡组。

### 4.3 「也出现在」补 Notebook 笔记

Notebook 笔记「转为卡片 / 文章」是投影，`vl_note.content_id` 与卡片共用。`locateAll` 目前只认卡片 / 文章 / 项目文档 / 日记，卡片的「也出现在」看不到这篇 Notebook 笔记。脉络的 `projections` 额外查 `vl_note.content_id IN contentIds`，作为 `vl-note` 行显示（不改 `locateAll`，避免影响知识地图与引用索引）。数据库单元格投影不做（打开位置无法定位到行）。

### 4.4 被使用

- **白板**：索引库派生索引，见 §4.5。查询时按 `cardId` / `articleId` / `contentIds` 命中页，再解析页的归属：
  - 独立白板：`white_boards.white_board_content_ids` 经 `json_each` 反查（只解析 id 数组这一短列，代价随白板数线性、与画布大小无关）；
  - 项目里的白板：`project_item.white_board_content_id`；
  - 文档里嵌入的白板块：§4.5 的 `whiteboard_embeds`（由引用索引器顺带维护），归属是那篇文档。
  - 三处都找不到（孤儿页、`ref_count <= 0`）不显示。按页去重，标题用白板名或宿主文档名，meta 为页名。

- **待办**：

  ```sql
  SELECT t.id, t.title, t.is_completed FROM todo_note_link l JOIN todo_item t ON t.id = l.todo_id
  WHERE l.content_id IN (:contentIds) AND t.is_archived = 0
  ORDER BY t.is_completed, t.update_time DESC
  ```

- **Notebook 资源**：笔记作为 Notebook 资源时，`vibe_learning_resources.source_type = 'note'`、`original_path = 'note://<contentId>'`。按 `original_path IN (...)` 查，归到 Notebook 项目。这一列没有索引，资源表是窄表、比较的是短字符串，规模到上万行仍是毫秒级；实测若慢再补 `(source_type, original_path)` 索引。

- **刷新**：待办关联、Notebook 资源的写事件加入 `CONTEXT_WRITE_EVENTS`；白板由 §4.5 的索引器在索引变化时广播 `entity-context:changed`，**只在某页引用的笔记集合真的变了才广播**（画布每 400 ms 保存一次，拖动元素不会触发失效）。

### 4.5 白板引用索引（索引库）

```sql
-- packages/db-schema/schema/index/60_whiteboard_refs.sql
CREATE TABLE IF NOT EXISTS whiteboard_refs (
  page_id   INTEGER NOT NULL,   -- white_board_contents.id
  dst_kind  TEXT NOT NULL,      -- card | article | content
  dst_id    INTEGER NOT NULL,
  via       TEXT NOT NULL,      -- card | richtext | mind-node | inline
  PRIMARY KEY (page_id, dst_kind, dst_id, via)
);
CREATE INDEX IF NOT EXISTS idx_whiteboard_refs_dst ON whiteboard_refs(dst_kind, dst_id);
CREATE TABLE IF NOT EXISTS whiteboard_ref_sources (page_id INTEGER PRIMARY KEY, update_time INTEGER NOT NULL);
-- 文档里嵌入的白板块：宿主正文 → 白板页
CREATE TABLE IF NOT EXISTS whiteboard_embeds (
  host_content_id INTEGER NOT NULL,
  page_id         INTEGER NOT NULL,
  PRIMARY KEY (host_content_id, page_id)
);
CREATE INDEX IF NOT EXISTS idx_whiteboard_embeds_page ON whiteboard_embeds(page_id);
```

**解析按元素类型走，不做通用 JSON 扫描**（纯函数 `D/src/entity/whiteboard-refs.ts`）：

| 元素                           | 记录                                                                                                     |
| ------------------------------ | -------------------------------------------------------------------------------------------------------- |
| `card`                         | `cardId` → `card`                                                                                        |
| `richtext`                     | `contentId` → `content`；`linkedCardId` → `card`；`linkedArticleId` → `article`                          |
| `mind-node`（递归 `children`） | 每个节点的 `contentId`（关联笔记）→ `content`；节点 `text` 里的内联引用经 `extractInlineRefs` → `inline` |
| `whiteboard`（嵌套白板）       | 不记（它指向白板，不是笔记）                                                                             |
| 其他                           | 递归进 `children`，只认上面几种类型                                                                      |

- 只认元素类型，是为了避开 Slate 正文里 content-link 节点也带 `contentId` 造成的误判（例如文本块缓存的 `content`）。
- 文本块（`richtext`）正文里的内联引用已在 `entity_refs` 里（它的正文在 `contents`），但来源正文解析不到身份，目前被丢弃；现在经 `whiteboard_refs` 的 `richtext` 行反查到白板，**归入「被使用 · 白板」**，不进「被引用」。规则统一为：**来自白板的关系（放入、关联、白板文字里的引用）都显示为「被白板使用」**。
- 增量：`white-board-content:create/update/delete` 与子白板增删改事件 → 按页防抖 2 秒重解析，结果集合有变化才写库并广播。
- 对账：连接数据库时比对 `white_board_contents.update_time` 与 `whiteboard_ref_sources`，同 `entity_refs`。
- `whiteboard_embeds` 由现有引用索引器维护：它的 SQL 预筛从「含 `content-link`」扩为「含 `content-link` 或 `whiteBoardContentId`」，解析时顺带取白板块。
- 索引库表可重建，不涉及主库与移动端。

## 5. 脉络浮层

### 5.1 分区与顺序

```
  来源        ← 对话「CSS 层叠上下文怎么理解」
  连接 / 引用了   （现有）
  被引用          （现有）
  也出现在        （现有，补 Notebook 笔记）
  衍生        → 3 张闪卡 · 项目文档「渲染篇」
  被使用      ▣ 白板「前端知识图」 · ☐ 待办「整理渲染笔记」 · Notebook「浏览器原理」
  相关问题        （现有）
```

- 「被使用」的行：白板（▣，标题为白板名或宿主文档名）、待办（☐，带完成态）、Notebook（Notebook 图标）。
- **「来源」置顶**：它回答「我从哪来」，是看一条笔记时最先想知道的；条数通常只有 0 或 1，不占地方。
- 「被使用」一个分区装白板与待办，行首图标区分；不拆两个分区，免得浮层分区太多。
- 计数「N 处关联」把来源、衍生、被使用都计入。

### 5.2 打开

| 端点          | 行为                                                                          |
| ------------- | ----------------------------------------------------------------------------- |
| 对话          | `openPage("chat", { id: sessionId })`（不定位到消息，见 §8）                  |
| Notebook 笔记 | `openPage("vibe-learning-detail", { id: projectId })`                         |
| 闪卡          | `openPage("review", { deckId })`                                              |
| 白板          | 按归属：`whiteboard-detail`（定位到页）/ 打开项目条目 / `openEntity` 宿主文档 |
| Notebook      | `openPage("vibe-learning-detail", { id: projectId })`                         |
| 待办          | `openPage("todos", { selectedId })`                                           |
| 四类正文实体  | `openEntity`                                                                  |

`openEntity` 不扩展；上表在脉络域 `features/context/open.ts` 收口。

### 5.3 缺失降级

- 来源已删除（如对话被删）：保留一行，灰显「来源已删除」，不可点。来源是事实，删了也值得知道「它曾经来自别处」。
- 衍生已删除：不显示，也不计数。

## 8.5 实现与设计的差异

- `content_link` 退役排在知识库迁移之后，`knowledge-migration` 的守卫保留（§3.4）。
- Notebook 投影单独一个字段 `notebookProjections`，浮层里并入「也出现在」；被使用的打开目标统一为 `ContextOpenTarget`（§4.1）。
- 引用索引的解析口径加版本号（`index_meta` 的 `entity-refs:version`），加白板块后升到 2，触发一次全量重解析（§4.5）。
- 对话来源按 `chat_session.scope` 区分：主对话可点开；PDF / 视频笔记 / Notebook 里的对话只展示、不可点（§5.2）。
- Notebook 对话 `save_note` 的谱系只记会话，不带消息 id：工具执行上下文拿不到所在消息的 entry id（§3.3.1）。
- 插入笔记弹窗删掉了无调用方的网页 / 视频笔记分支（§3.3）。
- 实测数据见 05「迭代 3：存为卡片 / 闪卡入口……」一条。
