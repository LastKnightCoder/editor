## 0. 目标与范围

**一句话**：把「外部材料」里的划线与标注变成主库里**可被指向**的行，并进入向量与全文索引。这是迭代 5（问题材料扩类型）和迭代 7（AI 洞见覆盖所有阅读内容）的前提。

**原则**（02 §4.3）：**来源已经是主库里的行，就直接指向它；不是行的，才落成摘录。**

| 来源           | 是不是行                                       | 本迭代                                   |
| -------------- | ---------------------------------------------- | ---------------------------------------- |
| 微信读书划线   | 不是：`weread_notebook.chapter_highlights` 整列 JSON | 落成 `excerpt` 行（§4.1）               |
| 浏览器插件划线 | 不是：只在插件 `chrome.storage.local`           | 落成 `excerpt` 行（§4.2）               |
| PDF 标注       | 是：`pdf_annotations`                           | 直接指向；修正撤销删除换 id（§4.3）      |
| 剪藏网页       | 是：`web_clip`（解析文档在 `contents`）         | 直接指向（§4.4）                         |
| 视频高亮       | `video_notes.highlights`，由 AI 生成            | 不处理                                   |

**数据层（不需要单独确认，属于迭代 4 的定义）**：材料类型层、`excerpt` 表、微信读书与插件写入、PDF 标注 id 稳定、向量与全文索引覆盖三类材料。

**用户可见入口（每个都要确认，见 §7、§12.2）**：全局搜索能搜到材料、AI 对话检索覆盖材料、打开到原处、划线「转为卡片」、`@` 引用摘录、摘录自身的脉络、全部摘录页、插件笔记记来源网页。

**本迭代不做**：问题材料扩类型、「转为问题」（迭代 5）；引述锚点的模糊找回、段落级地址（迭代 6）；AI 生成卡片 / 闪卡（04 待定）；移动端展示。

## 1. 现状调研

### 1.1 设计口径

技术决策按数据结构与可能规模推导（KL-029）。本机库几乎没有这几类数据：593 本书只有 1 本存了划线 JSON，而且里面没有划线；PDF 标注 0 条；剪藏 7 条。所以**本机数据不能用来判断规模**。按结构推：

- 微信读书 `/book/bookmarklist` **不分页**，一本书的划线一次返回、整列存进一个 TEXT。重度用户可能有上千本书、几万条划线。
- 插件划线没有任何上限，受 `chrome.storage.local` 默认配额（约 10 MB）约束，每次改动都整页重写。
- PDF 标注一份 PDF 可以有几百条，`pdf_annotations` 连 `pdf_id` 索引都没有。

据此，写入一律做**增量 diff**，不做「每次整库重展开」；向量按条建文档。

### 1.2 微信读书

- **表**：只有 `weread_notebook`（一本书一行，`50_learning.sql:133`）和键值表 `weread_config`。划线在 `chapter_highlights`（`ChapterHighlightReview[]`），想法在 `chapter_highlights[].chapterReviews` 与 `book_review` 两处冗余存放。类型定义见 `D/src/types/weread.ts:254`（`Highlight`）、`:281`（`Review`）。
- **划线与想法没有 id 关联**：解析时（`D/src/services/weread/parser.ts:51-56`）按 `range + chapterUid` 匹配，把想法正文复制进 `Highlight.reviewContent`，不记 `reviewId`。只有想法、没有划线的条目在展示时用 `abstract` 当原文（`D/src/features/weread/model.ts:195-245`）。
- **原文已被改写**：`markText` 入库前经 `addIndentToParagraphs`（`parser.ts:256`）在第二段起每段前加 3 个空格。
- **静默丢数据**：`parseChapterHighlightReview` 只遍历章节列表（`parser.ts:121-150`），`chapterUid` 不在列表里的划线会被丢掉。
- **同步**：网络请求全在渲染端（`D/src/services/weread/index.ts`），主进程只落库（`D/src-electron/main/modules/weread.ts`、`tables/weread-notebook.ts`）。
  - 书架同步（进入书架页、手动同步）**只同步元数据**；划线和想法只在**打开某本书**时整本拉取，然后整列覆盖写（`queries.ts:201-243`）。
  - `removed` 被写死成空数组（`index.ts:484-486`、`:555`），synckey 恒为 0，没有任何增量。
  - 唯一的保护是 `preferNonEmpty`：新拉回来是空、旧缓存有内容时保留旧内容。
  - 书从书架移除时，整行删除（`queries.ts:155`）。
- **界面**：书架页 `weread`、单书页 `weread-book`（参数只有 `bookId`）。每条划线只有「复制」，没有 DOM 锚点，不能定位到单条。
- **移动端、CLI 都不读写这两张表**，只随整库快照携带。AI 可经 `sql_query` 读到整列 JSON。

### 1.3 浏览器插件

- **数据**（`E/content/types.ts`）：`Highlight { id: uuidv4, range: { startXPath, startOffset, endXPath, endOffset, text }, style, color, createdAt }`；批注 `Annotation { highlightId, text, updatedAt }`，一条划线最多一条；按页存在 `tau-highlights:<去 hash 的 url>` → `PageHighlights { url, highlights, annotations, version: 1 }`。
- **XPath 不稳定**：路径是相对于「已插入之前划线的 `<mark>`」的页面结构算的，删除划线时 `normalize()` 会让后面的划线失效；恢复时文字对不上就静默跳过。**引文才是主数据**，XPath 只当提示。
- **删除是硬删除、没有墓碑**；改颜色 / 样式不更新任何时间戳；没有离线队列。
- **通信**：主进程在固定端口 24678 起 WebSocket 中转；`D/src/services/aiServer.ts` 跑在**渲染端**，以服务端身份接入，写库再经 IPC 进主进程。参数基本不校验，**整个端口没有鉴权**（任何本地进程或网页都能调 `content.create`）。content script 不连 WS，background 只有 4 行。
- **插件笔记**存在插件本地，用户操作时经 `content.create` 写入 `contents`，**不传 URL**；`ExtNoteInsertModal` 不传 `source`，所以插件笔记复制进项目不记谱系（08 §3.3 留到本迭代）。
- 插件有「当前页面划线」侧栏列表，没有「全部划线」页；页面内能滚到某条划线，但没有「打开 URL 后滚到某条」的入口。

### 1.4 PDF 标注

- `pdf_annotations(id, pdf_id, page_num, annotation_payload, color, notes, type, area_data, …)`（`10_core.sql:76`），没有任何索引。原文在 `annotation_payload.custom.text`，旧数据在 `contents`；取法已有 `annotationModel.ts:174-179`。批注在 `notes`（Slate JSON，只用第一条）。
- 类型：高亮、下划线（新建只有这两种）、波浪线、删除线（旧数据）都有原文；**区域截图 `area` 没有原文**，只有图片。PDF 文件自带的标注不落库。
- 写入经 IPC `add/update/delete-pdf-annotation`，会触发 `onDatabaseWrite`，但向量编排与脉络的事件白名单都不认识这几个事件。
- **撤销删除会换 id**：`restore`（`D/src/features/pdfs/reader/data.ts:197-210`）走 `addPdfAnnotation` 新插一行，主键变了，引擎里的 uuid 不变。按主键指向的话，撤销后引用会断。
- 阅读页 `pdf-detail` 参数只有 `pdfId`；阅读器内部已有 `jumpToRecord(record)`（`ReaderLayout.tsx:292`），只是没有对外参数。

### 1.5 剪藏网页

- `web_clip(id, content_id, url, title, …)`，解析文档在 `contents`。与网页条目（`project_item`，`ref_type = 'web-link'`）只靠谱系 `clipped_from`（project-item → web-clip）关联；`LineageNode` 里 `web-clip` 的 id 是 `web_clip.id`。
- **没有独立详情页**，解析文档只在网页条目视图的「文档」分段里显示。
- 编辑解析文档只更新 `contents.update_time`，不更新 `web_clip.update_time`。
- `web-clip:delete` 没有调用方：删网页条目后 `web_clip`、正文和谱系都成孤儿。

### 1.6 向量与全文索引

- `MAIN_CONTENT_INDEX_TYPES = ["card", "article", "project-item", "diary-daily"]`（`main-content-vec-index-queue.ts:27`），同一组类型还在 `IndexType`（`D/src/types/search.ts:4`）、`EmbeddingIndexContentType`、`knowledgeSearchTool` 各写了一份。
- 候选扫描 `forEachCandidate` 按四张表硬编码；`prefixed_id = type:id`，id 必须是数字。全文 `main-content-fts-index-queue.ts` 同样硬编码四类。
- 检索结果 `SearchResult` 要求 `contentId` 与 `content: Descendant[]`，三处解析都是硬编码 switch。
- **全局搜索面板**未选范围时不过滤类型；新类型一入库就会出现在结果里，而 `CONTENT_TYPES[r.type].icon` 没有对应项会**直接崩溃**（`SearchPalette.tsx:372`）。面板点击内容结果目前只跳到模块列表页。
- **知识地图**有自己的白名单 `VECTOR_TYPES`（`tables/knowledge-map.ts:26`），新类型不会变成节点。
- **已有缺陷**：卡片 / 文章 / 项目文档删除时清理索引传的是主库连接（`card.ts:351` 等），实际不删；队列也不清理已删实体的向量，只在解析结果时丢弃。

### 1.7 实体层

- `EntityRef`（`D/src/entity/ref.ts`）只有四类正文实体，`id: number`，被引用索引、知识地图、`openEntity`、`entity-context:get` 的入参共用。
- `LineageNode`（`D/src/entity/lineage.ts`）= `EntityRef` ∪ 对话、Notebook 笔记、剪藏、闪卡（KL-028）。
- 内联引用 content-link 的 `contentType` 是任意字符串，但悬停预览要 `contentId`，点击走 `openContent`（未知类型抛错），引用索引只认 `EntityRef`；移动端与 blog 各有一份实现。

### 2.2 为什么另立一层，而不扩 `EntityRefKind`

| 依据 | 说明 |
| ---- | ---- |
| 数据形状不同 | `EntityRef` 的四类都有 `content_id`（一份 Slate 正文），引用索引、投影（`locateAll`）、悬停预览都依赖它；摘录、PDF 标注没有正文。 |
| 角色不同 | 01 §2.6：卡片、文章、项目文档是「我的思考」，是知识地图节点和脉络入口的宿主；划线、标注、剪藏是「外部材料」，挂在体系边上（KL-002）。扩进 `EntityRefKind` 会让知识地图、`ContextBadge`、引用索引默认接纳材料，每处都得再排除。 |
| 消费方一致 | 向量 `prefixed_id` 的 type、谱系端点、迭代 5 的 `question_link.target_type` 都用同一组字符串；有一个具名类型，迭代 5 直接复用。 |
| 先例 | 迭代 3 已经为对话、闪卡另立 `LineageNode`（KL-028），本迭代是把其中「材料」这一类具名化。 |

**材料不进知识地图、不挂脉络入口**：前者沿用 KL-002 / 01 §2.6，`VECTOR_TYPES` 不改；后者见 §7 的 E6。

## 3. 摘录表 `excerpt`（主库）

### 3.1 表

```sql
-- packages/db-schema/schema/main/50_learning.sql（weread 之后）
CREATE TABLE IF NOT EXISTS excerpt (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  source_type   TEXT NOT NULL,              -- weread | web
  source_key    TEXT NOT NULL,              -- weread: bookId；web: 去掉 hash 的 URL
  source_title  TEXT NOT NULL DEFAULT '',   -- 书名 / 网页标题（来源被删后仍能显示）
  external_id   TEXT NOT NULL,              -- 见 3.2
  quote         TEXT NOT NULL,              -- 原文（引文）
  note          TEXT NOT NULL DEFAULT '',   -- 划线上的想法 / 批注，纯文本
  anchor        TEXT,                       -- JSON，来源原生定位，见 3.3
  color         TEXT,                       -- 来源原生取值（微信读书 colorStyle / 插件颜色名）
  source_time   INTEGER,                    -- 来源里的创建时间（毫秒）
  create_time   INTEGER NOT NULL,
  update_time   INTEGER NOT NULL,
  is_deleted    INTEGER NOT NULL DEFAULT 0
);
-- 90_indexes.sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_excerpt_external ON excerpt(source_type, external_id);
CREATE INDEX IF NOT EXISTS idx_excerpt_source ON excerpt(source_type, source_key);
```

- 主库 63 → **64 表**，106 → **108 索引**。
- 与 02 草案的差异：唯一键由 `(source_type, source_key, external_id)` 改为 `(source_type, external_id)`；新增 `source_title`；`note` 改为非空默认空串。

### 3.2 唯一键

| 来源 | `external_id` | 理由 |
| ---- | ------------- | ---- |
| 微信读书划线 | `<bookId>:<bookmarkId>` | `bookmarkId` 是否全局唯一没有文档保证，带上 bookId 一定唯一 |
| 微信读书「只有想法」的条目 | `<bookId>:review:<reviewId>` | 原文取想法的 `abstract` |
| 插件划线 | 划线 uuid | 本身全局唯一 |

不把 URL 放进唯一键：插件、桌面 `web_link`、插件笔记三处对 URL 的规范化各不相同，URL 规则一变就会产生重复行。`source_key` 只用来按书 / 按页分组和打开。

### 3.3 `anchor` 与引述锚点（KL-017）的关系

- `anchor` 只存**来源的原生定位**，用来打开到原处：
  - 微信读书 `{ chapterUid, chapterIdx, chapterTitle, range }`；
  - 插件 `{ startXPath, startOffset, endXPath, endOffset }`。
- `quote` 就是 KL-017 引述锚点（TextQuoteSelector）里的 `exact`。本迭代**不做**前后文与模糊找回：原文在外部（书、网页），我们打不开原文去匹配，打开到原处时定位失败就只显示引文（§6）。
- 迭代 6 的引述锚点针对的是**我们自己的正文**（文章段落 → 卡片）。若届时摘录也需要前后文，在 `anchor` 里加 `prefix` / `suffix` 即可，不改表。

### 3.4 删除与生命周期

- **源端删除 → 软删除**（`is_deleted = 1`），保留引文。摘录被谱系或（迭代 5 的）问题材料指向时，删了也要能显示「原划线已删除」和原文（与 KL-026「来源被删保留一行」一致）。
- 同一 `external_id` 再次出现（如微信读书里恢复划线）→ `is_deleted` 复位为 0。
- **不清理**软删除行：每行很小，判断「是否还被引用」要扫谱系与问题材料，不值得（YAGNI）。
- 软删除的摘录不进向量与全文索引（§5）。

### 3.5 微信读书摘录为什么存行，而不是查询时从 JSON 推导

微信读书的划线**能**从 `weread_notebook.chapter_highlights` 推导出来，按 KL-008 / KL-009 似乎应放索引库。不这样做的理由：

1. `chapter_highlights` 是远端的**缓存**，每次打开书都会被整列覆盖。源端删掉的划线会直接从 JSON 里消失，被指向的摘录就丢了原文。摘录需要比缓存更长的生命周期（§3.4）。
2. 谱系、问题材料都在主库，需要一个随库同步、跨设备稳定的 id。索引库每台机器各自重建，自增 id 不稳定；改用 `bookId:bookmarkId` 字符串 id 又会让谱系、向量 `prefixed_id`（要求数字 id）两套写法并存。
3. 插件划线**必须**存行（推导不出来）。微信读书也存行，摘录就只有一套读写与查询。

代价：同一份划线在主库存两份（JSON 缓存 + 行），只占文本体积。把单书页改为读 `excerpt` 行、去掉 `chapter_highlights` 列属于另一项重构，本迭代不做。

## 4. 写入点

### 4.1 微信读书

**展开（纯函数）** `D/src/entity/excerpt/weread.ts`：`expandWeReadExcerpts(bookId, title, chapterHighlights, bookReview) → ExcerptInput[]`。

- 划线：`external_id = bookId:bookmarkId`，`quote` = `markText` **去掉 `addIndentToParagraphs` 加的缩进**（第二段起每段开头的 3 个空格；纯函数里还原，单书页的展示不动），`note` = `reviewContent`，`source_time` = `created * 1000`。
- 只有想法、没有同 `range` 划线、且有 `abstract` 的想法：`external_id = bookId:review:reviewId`，`quote = abstract`，`note = content`。
- 没有原文的章节想法、整书书评（`type = 4`）**不是摘录**，跳过。
- 顺手修复解析器：`chapterUid` 不在章节列表里的划线不再丢弃，归入「其他」章节（`parser.ts:121-150`）。

**写入（主进程，同一事务）** `D/src-electron/main/modules/tables/weread-notebook.ts`：

- `upsert` 时在同一事务里比较新旧 `chapter_highlights` / `book_review` 文本，**有变化才展开**并调用 `ExcerptTable.syncSource(db, "weread", bookId, title, inputs)`：
  - 按 `external_id` diff：新增插入，内容（quote / note / color / anchor）变了更新 `update_time`，不在新集合里的软删除，重新出现的复位。
  - 书架同步的 `mergeMetadata` 会带着旧划线整行 upsert，文本没变就不展开，避免每次同步都解析几百本书的 JSON。
- 删除一本书（移出书架）时，同一事务里把这本书的摘录全部软删除。
- `preferNonEmpty` 的边界照旧：源端把一本书的划线**全部**删掉时，新拉回来是空，旧缓存保留，摘录也不会被删。接受这个限制，在 05 记录。

**存量回填**：桌面连库时，`excerpt` 后台模块检查 `weread_config` 的 `excerpt_expand_version`，低于当前版本就把所有有划线的书展开一遍（diff 写入，幂等），然后写入版本号。展开规则变化时升版本号，与派生索引同样的做法（05 踩坑）。

- 这不是数据格式迁移，而是从已有数据填充新表：失败只记日志、下次连库重试，**不阻塞开库**，不适用 D-091 的「失败不放行」。
- 因此不写成 `packages/db-schema/src/` 的共享迁移函数，移动端和 CLI 也不实现：移动端不读写微信读书；桌面下次连库时自然补上。

**补全划线的来源（行为变化，见 KL-034）**：目前只有打开过的书才有划线，大部分书的摘录会是空的。建议书架同步时，对「笔记指纹变化且有笔记」的书只拉划线与想法两个接口（不拉详情与章节，章节标题已在划线里），并发 2；升级后第一次同步会补拉所有有笔记的书，进度沿用书架同步的提示。笔记指纹取 `/user/notebooks` 返回的每本书的 `sort` 与笔记数，实现时先核实这两个字段在新增划线时是否变化。

### 4.2 浏览器插件

**改 02 草案的逐条 `excerpt.upsert` 为按页快照 `excerpt.syncPage`**。理由：插件删除是硬删除、没有墓碑；插件本来就是整页存、整页写。发送整页快照，由桌面按页 diff，删除就自然传了过来，插件数据模型不用加墓碑。

**RPC（渲染端 `aiServer.ts` 注册 → IPC `excerpt:sync-web-page` → 主进程事务）**：

```ts
// 参数
{ url: string; title: string; highlights: Array<{
    id: string; text: string; note: string; color: string; createdAt: number;
    anchor: { startXPath: string; startOffset: number; endXPath: string; endOffset: number };
} > }
// 返回 { inserted, updated, deleted }
```

- handler **显式校验**：类型、URL 只接受 http(s)、单页最多 5000 条、单条原文最多 20000 字，超出拒绝。端口没有鉴权是全局问题，另开任务处理（§12.4）。
- 主进程 `ExcerptTable.syncSource(db, "web", url, title, inputs)`，与微信读书同一套 diff。

**插件改动**：

1. `PageHighlights` 加可选 `title`：content script 每次保存时写入 `document.title`（background 拿不到页面标题）。
2. **同步引擎放在 background**（content script 不连 WS，侧栏在桌面断开时整个不可用）：
   - 触发：`storage.onChanged` 里 `tau-highlights:*` 变化（防抖 2 秒）、`runtime.onStartup`、`chrome.alarms` 每 5 分钟重试一次。
   - 脏页判断：按库记已同步指纹 `tau-excerpt-sync:<库名>` → `{ [url]: 快照哈希 }`；库名经 `settings.getCurrentDatabase` 取。哈希变了才发，成功后更新指纹；失败（桌面未启动、中转回 `no server`）保持脏，等下次触发。
   - 首次（或换库后）所有页都是脏的，逐页发送。
   - manifest 增加 `alarms` 权限（不会弹权限提示）。
3. **进入哪个库**：划线是插件全局的，没有「属于哪个库」。按上面的指纹设计，划线进入**当前打开的库**；切到另一个库后，也会全部同步进新库。这是产品行为，列入 §12.2 的 E9 确认。

### 4.3 PDF 标注

- 直接以 `pdf_annotations.id` 作为 `pdf-annotation` 的 id。
- **修正撤销删除换 id**：`restore` 改为带原 id 回插（主进程 `addPdfAnnotation` 接受可选 id）。保持数字主键，不改用引擎 uuid（那样 `prefixed_id` 就不是数字了）。
- 只有带原文的标注（高亮、下划线、波浪线、删除线）、或带批注的区域截图进向量（§5）。区域截图可以被谱系指向，但没有原文时不进索引。
- `add/update/delete-pdf-annotation` 加入向量编排的写事件白名单。

### 4.4 剪藏网页

- 直接以 `web_clip.id` 作为 `web-clip` 的 id（与迭代 3 谱系一致）。
- **只索引仍挂在网页条目上的剪藏**：候选 = 有 `clipped_from` 入边、且网页条目未删除的 `web_clip`。孤儿剪藏不进索引；孤儿清理（`web-clip:delete` 无调用方）不在本迭代范围，另记待办。
- 更新时间取 `MAX(web_clip.update_time, contents.update_time)`，编辑解析文档后也会重新索引。

## 5. 向量与全文索引

### 5.1 候选与嵌入文本

| 类型 | 候选 | 嵌入 / 全文文本 | `update_time` |
| ---- | ---- | --------------- | ------------- |
| `excerpt` | `is_deleted = 0` | 微信读书：`《书名》 › 章节标题` + 引文 + 想法；网页：`网页标题（域名）` + 引文 + 想法 | `excerpt.update_time` |
| `pdf-annotation` | 有原文或批注 | `文件名 · 第 N 页` + 原文 + 批注纯文本 | `pdf_annotations.update_time` |
| `web-clip` | 见 §4.4 | 标题 + `getMarkdown(解析文档)`，按现有 `smartChunk` 切块 | 两者取大 |

- 摘录、标注很短，单独嵌入语义太薄；带上来源上下文，与 KL-016「嵌入带标题路径」同一思路。
- 每条摘录 / 标注一个向量文档（`prefixed_id = excerpt:<id>`）；剪藏按块，共用一个 `prefixed_id`，与正文一致。
- 规模：几万条短摘录的嵌入，远程模型成本很低，本地模型首次需要一段时间；沿用 AI 零配置，配了嵌入模型即索引，不另设开关。

### 5.2 改动点

1. 类型：`MAIN_CONTENT_INDEX_TYPES`、`IndexType`、`EmbeddingIndexContentType` 三处收敛为从 `MaterialKind` 与正文类型拼出的一份常量，避免再各写一份。
2. 候选：`forEachCandidate` 与全文队列各加三类分支；设置页覆盖率标签 `TYPE_LABELS` 补三类。
3. 写事件：`MAIN_CONTENT_WRITE_EVENTS` 加入微信读书保存与删除、`excerpt:sync-web-page`、PDF 标注三个事件、剪藏创建与更新。
4. **对账清理**：`collectTasks` 发现索引里有、候选里已没有的 `prefixed_id`（实体已删、摘录软删、剪藏变孤儿），删除其向量与全文行。这样也顺带修复了旧四类删除后向量残留的缺陷（§1.6）。
5. 检索结果：`SearchResult` 增加区分字段（正文结果带 `contentId`，材料结果带 `material: MaterialRef` 与纯文本摘要），三处解析 switch 补三类。
6. 知识地图 `VECTOR_TYPES` 不改，材料不成为节点。
7. 在第 5 步之前，全局搜索面板必须能识别或过滤材料类型，否则会崩溃（§1.6）。是否展示由 E1 决定。

## 6. 打开到原处

`openMaterial(ref)`（§2.3）的目标：

| 材料 | 打开 | 定位到单条需要的改动 |
| ---- | ---- | -------------------- |
| 微信读书摘录 | `weread-book { bookId, bookmark? }` | 单书页加可选参数 `bookmark`（`external_id` 后半段），每条划线渲染 `data-bookmark`，加载后滚动并闪烁；找不到就停在书首 |
| 网页摘录 | 系统浏览器打开 `url#tau-hl=<uuid>` | 插件 content script 恢复高亮后，读取这个 hash 参数，滚到该划线（复用 `TAU_SCROLL_TO_HIGHLIGHT` 的逻辑）；划线恢复失败就只打开页面 |
| PDF 标注 | `pdf-detail { pdfId, annotation? }` | 页面参数加 `annotation`；阅读器等标注加载、布局完成后调 `jumpToRecord`；同一 PDF 已打开时，参数原位更新也要响应 |
| 剪藏 | 经 `clipped_from` 反查网页条目 → `project-detail { id, itemId, webTab: "parsed" }` | 网页条目视图接受打开到「文档」分段的参数 |
| 已软删除的摘录 | 不可点，显示原文与「原划线已删除」 | — |

`ContextOpenTarget` 相应增加 `weread-book`、`pdf-detail`、`external-url`，以及带 `webTab` 的项目条目这几种目标。

这一节是 E1、E2、E4 的共同前提：只要有任何一个入口会把材料展示给用户，就需要它。如果 E1、E2、E4 都不做，本节也不做。

## 11.5 实现与设计的差异

- **剪藏打开不加页面参数**：已剪藏的网页条目本来就默认打开到「文档」分段，`project-web-clip` 直接 `openEntity(project-item)`，没给项目详情页加 `webTab`（§6）。
- **材料展示信息收口主进程**：`tables/material.ts` 的 `MaterialTable.resolve`（IPC `material:resolve`）给出标题、出处、引文与想法、打开目标；脉络来源、检索结果、`openMaterial` 都用它。
- **检索结果详情收口**：向量、全文、全量列出原来各写一份按类型的 switch，收敛到 `search-details.ts`；材料结果带 `SearchResult.material`，正文给引文与想法两段，现有的摘要展示不用改。
- **微信读书的写事件**：微信读书走自有 IPC（不经 `eventAndHandlers`），摘录有变化时经新增的 `databaseModule.notifyExternalWrite` 补发 `weread:excerpts-changed`，向量编排与脉络据此刷新。回填挂在已有的 `weread` 模块上（依赖加 `database`），没有新建后台模块。
- **笔记指纹存在 `synckey_highlights` / `synckey_reviews`**：这两列原本一直是 0；分别存笔记本概览的 `sort` 与笔记总数（划线 + 想法）。新增划线时这两个字段会不会变，要等用户真实同步时确认；不变的话，「全量重新同步」仍会全部重拉。
- **插件快照的参数校验放在主进程**（`ExcerptTable.syncWebPage`），渲染端 RPC 只转发：IPC 本身也是入口。
- **全文索引只在连库时对账**（现状如此），新摘录要下次连库才进全文；向量在空闲（本地模型）或手动索引时补。
- **已知限制**：网页摘录打开带 `#tau-hl=<id>`，用 hash 路由的单页应用可能把它当路由；划线恢复失败时只打开页面。
- **实测**（`tables/__tests__/excerpt-scale.eval.test.ts`，`KL_EXCERPT_SCALE=1` 才跑）：1000 本书 × 50 条划线首次保存 272 ms、原样写回 113 ms、连库回填 221 ms；插件单页 2000 条首次同步 8 ms、删一条重发 3 ms；5 万条材料的索引候选 103 ms。真实库副本（`context.eval.test.ts`）：回填 3 ms 得 1 条摘录，剪藏 7 条里 5 条挂在网页条目上进索引，脉络查询耗时与迭代 3 持平（平均 0.18 ms，p95 0.35 ms）。

## 12. 决策（用户 2026-10-02 确认按推荐执行）

### 12.1 技术与结构（推荐方案，确认后写入 04）

- **KL-031 材料类型层 `MaterialRef`**（`excerpt` / `pdf-annotation` / `web-clip`）由 `LineageNode` 收纳，不扩 `EntityRefKind`；材料不进知识地图。（§2）
- **KL-032 `excerpt` 表**：唯一键 `(source_type, external_id)`，微信读书 `external_id = bookId:bookmarkId` / `bookId:review:reviewId`；加 `source_title`；源端删除即软删除，保留引文，不清理。（§3）
- **KL-033 微信读书摘录在主库存行**，虽然能从 JSON 推导，理由见 §3.5；在保存书的同一事务里按文本变化做 diff；存量由桌面连库时按版本号回填，失败不阻塞开库，移动端与 CLI 不实现。（§3.5、§4.1）
- **KL-034 书架同步顺带拉划线**：对笔记指纹变化且有笔记的书，只请求划线与想法两个接口，并发 2；升级后第一次同步会补拉所有有笔记的书。这会增加同步时的请求数。（§4.1）
- **KL-035 插件划线按页快照同步**（`excerpt.syncPage`，取代 02 的逐条 `excerpt.upsert`）：由插件 background 发起，按库记指纹，失败保持脏、5 分钟重试。（§4.2）
- **KL-036 PDF 标注以 `pdf_annotations.id` 为地址**，撤销删除改为保留原 id；只有带原文或批注的标注进索引。（§4.3）
- **KL-037 索引**：三类材料进向量与全文；嵌入文本带来源上下文；对账时删除已不存在的候选（顺带修旧类型的向量残留）；剪藏只索引仍挂在网页条目上的。（§5）
- **KL-038 摘录的 `anchor` 只存来源原生定位**，`quote` 即引述锚点的 `exact`；不做模糊找回，定位失败只显示引文；迭代 6 需要时在 `anchor` 加前后文，不改表。（§3.3）
