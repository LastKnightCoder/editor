## 0. 目标与范围

**一句话**：AI 在后台读一遍「我的思考」，生成每份正文的元信息（标题、要点、概念、主张），以此为底座在**审视**环节给出洞见——让用户发现连接、生出新疑问（KL-001、KL-052）。

03 里迭代 7 列了 6 件事，依赖和风险差别很大：

| 部分 | 内容 | 依赖 | 风险 |
| ---- | ---- | ---- | ---- |
| A 元信息底座 | 主库 `content_ai_meta`、主进程队列、功能槽 | 无 | token 成本（首轮读全库一次） |
| B AI 标题 | 卡片标题全应用统一，用户无感知（ai-insights §3.2） | A | 标题质量；19 处取标题收敛 |
| C 脉络「相关」 | 语义相近但还没连接的内容 | 节级向量（迭代 6） | 噪音：给得不准就是打扰 |
| D 阅读时标记 | 读到某一段旁边出现淡标记，点开就地展开 | A、C | **最打扰**；01 §4.4 要求先出「不打扰 + 可关闭」设计 |
| E 回顾 | 结项回顾、生长回顾、体系项目「可能属于这里」 | A | 需要新界面形态 |
| F 雷达 | 对话信号「问了但没写」、知识地图主题级洞见与立项提示 | A、对话入索引 | 需要新界面形态；评估难 |

**推荐分三段**（§12.3 待确认）：本次 **7a = A + B + C**（底座 + 两个不打扰的落点）；D 先出 mockup 再定（7b）；E、F 各自出设计后再做（7c）。理由：A 是所有洞见的原料、成本最高、一旦生成就随库同步；B、C 不需要新界面形态就能验证元信息与近邻的质量，验证过了再往 D–F 走。

**本迭代不做**：AI 生成卡片 / 文章 / 闪卡（04 待定）；从输出转为问题（KL-052）；移动端展示（移动端可读到表，但不消费）。

### 1.5 设计口径（KL-029）

- 重度用户：2 万张卡片 + 数千篇长文。首轮元信息每张卡输入约 500 token，合计约 1000 万 token（ai-insights §3.1）；长文截断输入后每篇约 2000 token。远程模型按量计费一次；本地模型（若用户配本地 LLM）耗时以天计，必须可中断、可续跑。
- 元信息每份约 300–600 字节，2 万份约 6–12 MB，随主库同步。

## 2. 元信息（A）

### 2.1 表（主库）

```sql
-- packages/db-schema/schema/main/ 新增
CREATE TABLE IF NOT EXISTS content_ai_meta (
  content_id    INTEGER PRIMARY KEY,   -- 共用正文的投影共用一份（02 §5.4）
  schema_ver    INTEGER NOT NULL,      -- 元信息结构版本，加字段时只补低版本
  text_digest   TEXT NOT NULL,         -- 生成时正文的指纹（见 §2.3）
  meta          TEXT NOT NULL,         -- JSON：{ title, summary, concepts[], claims[] }
  model         TEXT NOT NULL,         -- providerId/modelId
  create_time   INTEGER NOT NULL,
  update_time   INTEGER NOT NULL
);
```

- 主库 65 → **66 表**，索引不增加（主键即查询键）。
- 放主库的理由沿用 ai-insights §3.5：随库备份同步，换机器标题不变；索引库每台机器各自重建、模型可能不同。
- 正文删除（引用计数归零）时删元信息：在 `ContentTable.deleteContent` 的同一事务里删，另由连库对账兜底删孤儿行。
- 移动端：共用 schema 自动建表，不读写；CLI 不涉及。

### 2.2 内容

| 字段 | 用途 | 本迭代消费者 |
| ---- | ---- | ------------ |
| `title` | 卡片精简标题（≤ 24 字） | B |
| `summary` | 一句话要点（≤ 60 字） | C 的相关理由、悬停预览（§8 I5） |
| `concepts` | 关键概念（3–8 个） | 7c 空白 / 雷达 |
| `claims` | 主要主张（0–3 条） | 7c 矛盾 |

**一次生成全部字段**（§12.1 待确认）：成本主要在读正文（输入 token），多输出两个字段的增量很小；以后再补字段就要把全库再读一遍。代价是 `concepts` / `claims` 本迭代没有消费者，质量要到 7c 才验证。

### 2.3 范围、时机与重算

- **范围**：卡片、文章、项目文档的正文（按 `content_id` 去重）。不含日记（04 待定「日记是否进知识地图」，日记标题是日期）、外部材料（不是我的思考）。
- **长文输入**：标题路径（各级标题）+ 正文前约 6000 字；长文的标题不用 AI 的，只用要点与概念。
- **触发**：
  - 连库对账：找出没有元信息、或 `schema_ver` 低于当前、或正文已大改的正文，按更新时间倒序入队（最近写的先有标题）；
  - 增量：`onContentWritten` 后**静置 10 分钟**再判断（ai-insights §3.4），日常打字不触发。
- **大改才重算**（标题稳定）：`text_digest` 存正文纯文本的字符 bigram 指纹（MinHash，128 个整数），当前正文与之的估计 Jaccard 相似度低于阈值（候选 0.8，用真实编辑样本校准）才重算。不用向量判断：远程用户的向量不一定是最新的，且换嵌入模型会让所有判断失效。
- **换模型**：已有元信息不作废，之后新生成的用新模型（ai-insights §3.4）。
- **队列**：主进程 BACKGROUND 模块 `content-ai-queue`，串行、每次一份正文；切库作废；单份失败重试 2 次后跳过，记 `index_meta`，下次连库再试；槽未配置时不运行，配上即开始（零配置，§12.1）。

### 2.4 提示词与输出

- 单次调用，要求 JSON 输出；解析失败按失败处理。正文语言即输出语言。
- 标题规则：概括观点而不是复述开头；不加引号、句号；不超过 24 字。
- `source.feature = "contentMetadata"`，用量页可见。

## 4. AI 标题（B）

- **显示优先级**：AI 标题 → 正文前 N 字（没配模型、还没处理到、失败时）。不提供手动改标题（ai-insights §3.2，已定）。
- **收敛取标题**：
  - 主进程：新增 `contentTitle(db, contentId, fallbackLength)`，`EntitySearchTable.resolve` 的卡片分支、`question-link.ts`、知识地图卡片节点标题、`search-details.ts` 的卡片标题都经它（LEFT JOIN `content_ai_meta`，一次查询，不逐条请求）；
  - 渲染端：卡片查询结果带 `aiTitle?: string`（列表轻表与详情都带），新增 `cardTitle(card, fallbackLength)`；15 处 `getEditorText` 中**作为卡片标题用的**（面包屑、`CardDetailLinks`、`CardsView`、编辑器窗口标题、`CardDatabaseView`）改用它。作为摘要 / 预览文字用的（`ItemCard` 描述、项目条目 `previewText`、白板笔记）不改。
- 写事件：元信息写入后经 `databaseModule.notifyExternalWrite("content-ai-meta:changed")` 广播，渲染端失效卡片与脉络查询（进脉络写事件白名单）。
- 不加任何新界面；用户只会觉得标题变准了。

## 5. 脉络「相关」（C）

### 5.1 取数（不调 LLM）

1. 取实体的节向量均值，查前 50 个近邻（已有 `neighborsOf` 口径）。
2. 去掉已经有关系的：显式链接、引用了 / 被引用、共用正文、谱系两端、同一问题的材料。
3. 相似度阈值：高于「随机对 p90」（ai-insights 实测 0.580，换嵌入模型后会变）——**按当前库实测动态取**：连库时抽样 1000 个随机对，取 p95 作阈值存 `index_meta`。
4. 最多显示 5 条，按相似度排序。

### 5.2 展示

- 浮层末尾一个「相关」分区（KL-023 的分区顺序之后），每行：标题 + 一句话要点（有元信息时）；**不显示相似度数字**。
- 「相关」**不计入元信息行的关联数**（否则所有卡片都会显示有关联，脉络入口失去「有就显示」的意义，KL-015）。
- 行上一个动作：卡片之间「添加连接」（复用 KL-018 的连接）；文章 / 项目文档不给动作，点开即可。
- 单条「不相关」：本迭代**不做**（要存忽略记录，等使用后看是否需要）。

### 5.3 为什么不让 LLM 判定

01 §4.4 的「相关」本意是 LLM 确认后给理由。但每打开一次浮层就调一次 LLM 成本不可控；预先为每个实体判定又是 2 万 × 20 次调用。7a 先用纯近邻 + 要点，评估（§11）达标就上，不达标再考虑 LLM 复核。

- `pnpm db:schema:*`；桌面 `tsc`、lint、`vite build`；移动端 `cargo test database::`。视觉由你验收。

### 11.3 实现与设计的差异

实测数字与评估结果统一记在 [14-迭代7a验证记录.md](14-迭代7a验证记录.md)。

- **重算阈值取 0.7**（候选 0.8）：真实编辑样本下 0.7 的小改误重算 4.7%、大改漏重算 1.0%，0.8 为 8.6% / 0%；按「标题稳定优先」取 0.7。短卡片（<100 字）bigram 少，0.7 下仍有约 20% 的小改会重算，本迭代不另设规则（14 §1）。
- **`update_time` = 最后一次生成或核对的时间**：正文改动没到重算条件时只更新 `update_time`，`text_digest` 保留生成时的指纹。这样对账只需比较 `contents.update_time > content_ai_meta.update_time` 就能跳过未改动的正文，不必每次连库给全库算指纹；小改累积到阈值以下仍会重算。
- **`ContentTable.deleteContent` 整体包进事务**：原实现没有事务，「同一事务里删元信息」需要先把引用计数递减、白板与问题释放、正文删除收进一个事务。

## 12. 决策（用户 2026-10-03 确认：全部按推荐）

### 12.1 技术与结构（已写入 04）

- **KL-053 元信息存主库 `content_ai_meta`，按 `content_id`**，一次生成标题、要点、概念、主张四个字段，带结构版本；范围为卡片、文章、项目文档，不含日记与外部材料。（§2）
- **KL-054 重算条件**：静置 10 分钟后，正文纯文本 MinHash 相似度低于阈值（候选 0.8，实测校准）才重算；不用向量判断；换模型不作废已有元信息。（§2.3）
- **KL-055 新功能槽 `contentMetadata`「笔记元信息」**，配上即处理全部、清空即停止，说明文案给出 token 估算；不复用 `titleSummary`。（§3）
- **KL-056 AI 标题只用于卡片**，显示优先级 AI 标题 → 正文前 N 字；主进程与渲染端各一个取标题函数，只替换作为「卡片标题」的调用点。（§4）
- **KL-057 脉络「相关」= 本地近邻（不调 LLM）**：排除已有关系、阈值按当前库随机对 p95 动态取、最多 5 条、不计入关联数，卡片之间可「添加连接」。（§5）
