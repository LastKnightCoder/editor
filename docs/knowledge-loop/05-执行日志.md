## 踩坑

### 工程与协作

- **嵌套 worktree 里 pre-commit 必挂** → `.claude/worktrees/*` 下 eslint 会同时加载 worktree 与主仓库的 `.eslintrc.cjs`，`react-refresh` 插件重复 → 在 `apps/desktop` 下手动跑 `npx eslint --no-eslintrc -c ../../.eslintrc.cjs <文件>`，再跑 tsc 与相关测试，全部通过后用 `--no-verify` 提交。
- **新 worktree 里 vitest 报找不到 `vitest-canvas-mock`** → worktree 没装依赖，解析到主仓库的 `node_modules` → 在 worktree 根目录执行 `pnpm install --frozen-lockfile`。合入 master 后依赖有变化，要再装一次。
- **任务分支的基线不一定是当前分支** → 用 spawn 开出的任务会话可能从 master 切出；直接合并会把整条 master 带进来（曾出现 31 个文件冲突，原因是移动端日历与闪卡迁移在两条线上各有一份 SHA 不同的版本） → 合并前先 `git merge-base` 确认基线；不是同一条线就只 cherry-pick 修复提交。
- **本会话限定在自己的 worktree** → git 命令不能指向其他 worktree（`git -C`、循环里的复杂 git 命令会被拒绝）；主仓库检出的分支（如 master）也无法从这里快进 → 拆成简单命令；需要动主仓库时，给用户命令让其执行。
- **`flashcard.ts` 原本就有大量未按 prettier 格式化的行** → 修改时不要整文件格式化，避免 diff 混入无关改动。

### 代码事实（调研所得，设计时注意）

- **日常编辑不经过 `content:update`，也不触发 `onDatabaseWrite`**：正文由协作层每秒投影直接 `UPDATE contents`（`collaboration/content-sessions.ts` 的 `projectLocalContent`）。派生数据不能只挂 IPC 写事件。（02 §3.2）
- **`collabId` 不稳定的场景**：AI 编辑、Markdown 往返、整篇替换会让全部块换新 id；合并块时被并入的 id 消失；从未打开过的老正文没有 id。（02 §3.3）
- **「转为卡片 / 文章」是投影，不是复制**：共用同一行 `contents`，一处改处处变。（02 §4.2）
- **一个 `content_id` 可能对应多个实体**，`entity-search.ts` 的 `locate` 只返回第一个；`cards` / `articles` / `project_item` 的 `content_id` 没有索引。
- **主库已有 `content_link` 表**，但只用于「项目条目 → 剪藏」，新表不要重名（计划在迭代 3 迁移后删除）。
- **向量 `prefixed_id` 是 `type:实体id`，多块共用，没有块序号**；`content_fts.chunk_index` 有列但从未写入；切块基于 Markdown，不保留与 Slate 块的对应。
- **LLM 调用已全部在主进程**（pi-ai 运行时）。ai-insights §9 说的 `chatLLM` / `stream-fetch` 已不存在。
- **`useLLMConfig.ts` 的功能键联合类型已与设置脱节**（缺 `vibeLearningImageDescription`），新增功能槽时顺手补齐。
- **知识地图从表到渲染器都写死卡片**：`knowledge_map_nodes` 以 `card_id` 为主键，读向量过滤 `type='card'`，`LinkGraph` 的 props 全是 `ICard`。
- **大部分正文没有 `collabId`**：机制 2026-09-06 才引入，之前写的、之后没打开过的正文都没有（本机 95%）。不要假设块 id 存在。
- **真实库副本是 WAL 模式**：`sqlite3 -readonly` 打不开（要建 `-shm`），复制到 `/tmp` 后用普通模式打开副本，用完删除。
- **`openContent` 不支持日记**，content-link 点日记会报错；`project_item` 与 `project-item` 两种写法并存。
- **`listQuestionsByTarget` 接口已存在但没有调用方**；答案转卡片后 `question_link` 仍指向 `answer:contentId`。
