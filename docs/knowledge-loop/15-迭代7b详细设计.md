# 15 · 迭代 7b 详细设计：文档的 AI 洞见

## 0. 目标、分段与范围

**一句话**：打开一篇文档（文章、项目文档、卡片）时，AI 站在你整个知识库的角度读它，指出平时遗漏、忘记的东西，并帮你延伸：哪一处可以连到哪里、哪里和以前写的重复或矛盾、哪个结论还可以追问、哪个概念还没展开。**AI 只提议，连接和问题都由你确认后才落地**（KL-001：促成发现连接，产出落到链接或问题）。

**迭代 7 的分段（没有迭代 8）**：

| 段 | 层 | 内容 |
| -- | -- | ---- |
| 7a ✅ | 原料 | 元信息（标题、要点、概念、主张）、卡片 AI 标题、脉络「相关」 |
| **7b（本文）** | **文档层** | 一篇文档（或一张卡）的 AI 洞见：可建立的行内连接、重复、矛盾、追问、空白、延伸；节首淡点（用户选定的 A 形态）+ 文档的「AI 洞见」侧栏 |
| 7c | 主题与全局层 | 分层阅读（子主题 / 主题概述）→ 模式梳理、体系生长、主题间的呼应；AI 主动的落点（今日页、知识地图）；结项 / 生长回顾、问了但没写 |

7b 先做，是因为它离日常使用最近（你正在读、正在写的那篇），而且能直接产生连接和问题；7c 的主题概述会读 7b 的结果，反过来不需要。

**本迭代不做**：主题级的模式与回顾（7c）；AI 生成卡片 / 文章 / 闪卡（04 待定）；自动建立连接（必须用户确认）；外部材料（剪藏、PDF）的洞见。

## 1. 用户决策（2026-10-03 讨论）

- **连接一律由用户确认**；AI 推荐「哪一处可以建立行内连接」及理由，确认后在那一处直接生成 `content-link`（把那几个字包成链接，不另插 `@` 文字）。
- **重复与矛盾在文档层就能看出来**，放进文档的 AI 洞见里，不必等全局。
- **洞见单独一个功能槽「AI 洞见」**（04 待定项的结论）。
- **卡片也要 AI 洞见，但要主动**（用户主动或 AI 主动），不放在脉络浮层里。
- 形态从用户选定的 mockup A（节首淡点）出发；AI 主动的落点（今日页、知识地图、详情页顶部）都可以接受，主题层的放到 7c。
- **延伸可以带入 AI 自己的知识**（以看法与问题的形式，§3）。
- 「模式」只要能帮用户、帮知识体系生长都算：主题关注点的变化、反复使用的思路、论证链缺环都要；放在 7c 的主题层。

## 2. 洞见类型

| 类型 | 你在意的 | AI 写出来的样子 | 依据 | 动作 |
| ---- | -------- | --------------- | ---- | ---- |
| **连接** | 遗漏 | 「『强制同步布局』这里，就是《列表滚动掉帧的排查》那次的原因」 | 向量候选的要点 + 对方那一节原文 | 预览、**建立连接**（确认后把那几个字包成 content-link） |
| **重复** | 忘记 | 「这一节和《浏览器渲染流程》› 布局 讲的几乎是同一件事，那边更完整」 | 候选的要点与节文本 | 预览、建立连接、忽略 |
| **矛盾** | 忘记 | 「这里说 transform 不触发重排；你在《动画性能笔记》里写过改 transform-origin 会触发，哪个条件下成立？」 | 7a 元信息的「主张」 | 预览、**记为问题** |
| **追问** | 延伸 | 「这里断言 CSS 阻塞渲染，但没写为什么不阻塞 DOM 解析」 | 只读本文 | **记为问题** |
| **空白** | 延伸 | 「多次提到合成层，但没写它是怎么划分的」 | 只读本文（本文内反复出现、未展开的概念） | 记为问题 |
| **延伸** | 延伸 | 「合成层通常由 will-change、3D 变换、视频等触发；可以补一节触发条件」 | AI 自己的知识，**标明「AI 的补充」** | 记为问题；展开看 AI 的看法 |

- **默认给引子与问题**（KL-001）：每条先一句话；展开后才是 AI 的看法（≤ 120 字）。
- **延伸只给看法与问题，不生成正文**：不提供「写进文档 / 生成卡片」（04 待定「AI 生成卡片」）。
- 「记为问题」走命令面板记问题模式（KL-043），来源 chip 为本文档，这是审视环节产生的问题（KL-052 允许）。

## 3. 一次分析怎么做

**一篇文档一次调用**（卡片同样一次）：

1. **本地候选（宽，不花 token）**：每个有文字的节（去掉代码、图片、链接后 ≥ 80 字）查向量近邻，排除已有关系（同「相关」：自身与共用正文、链接、引用了 / 被引用、谱系、同一问题的材料），同一项目的文档**不排除**（重复与矛盾恰恰常在同一项目里）。阈值放宽到**随机块对 p95**（判断交给 AI，ai-insights §5.1「本地只负责不漏」）。全文合并去重，按相似度取前 **15 个候选**；每个候选带：标题 › 命中的节、AI 要点、主张、命中节的前 300 字。
2. **AI 调用**（槽 `contentInsights`）：输入为本文（标题 + 大纲 + 正文前约 6000 字，各节标号）+ 候选列表；要求 JSON 输出最多 **8 条**洞见，每条：`type`、`section`（节号）、`anchor`（**本文里的原文片段**，连接类必填，用于包成链接，2–20 字）、`target`（候选编号，连接 / 重复 / 矛盾必填）、`hint`（一句话引子）、`detail`（AI 的看法）。
3. **校验**：`anchor` 必须是该节某一块里的原文子串，`target` 必须在候选里；不满足的丢弃（防止 AI 编造位置与目标）。连接类再检查 `anchor` 不在已有链接里。
4. **存储**：结果写主库 `content_ai_insights`（§7），带生成时的正文指纹与模型。

**token 估算**：输入约本文 3600 + 候选 15 × 200 + 提示 500 ≈ 7000，输出约 800；一张卡约 2500 / 500。按 deepseek-flash 实测单价量级，一篇长文不到 1 分钱。

## 4. 什么时候分析（主动）

| 谁主动 | 触发 | 范围 |
| ------ | ---- | ---- |
| **你** | 文档元信息行「AI 洞见」按钮；没有结果或结果已过期时点开即分析，侧栏里有「重新分析」 | 任意卡片 / 文章 / 项目文档 |
| **AI** | 后台：你**最近 30 天写过**的文档，编辑静置后（与元信息同一静置，且元信息已生成）自动分析一次；正文大改（指纹相似度 < 0.7）后重新分析 | 只限最近写过的，不扫全库 |

- AI 主动的结果在你下次打开文档时出现（节首淡点 + 按钮上的数字），不弹窗、不通知。
- **不做全库首轮**：重度库 3000 篇长文 + 2 万张卡全分析约 1.2 亿输入 token，而大多数旧文档不会再打开。旧文档在你打开并点「AI 洞见」时才分析。
- 估算日常量：每天写 5–20 份 → 每天约 5–15 万 token。
- 槽未配置：按钮与淡点都不出现（零配置：配了模型即同意，§9）。

## 5. 形态（mockup v2）

**入口**：详情页元信息行一个按钮「✦ AI 洞见」，有未处理的洞见时带数字（如「AI 洞见 3」）。卡片、文章、项目文档都有。不进脉络浮层，不计入「N 处关联」。

**节首淡点（A，只在长文）**：有洞见的节，标题右侧页边一个淡点，悬停显示第一条洞见的引子；点击打开侧栏并定位到这一节的洞见。每篇最多 3 个点（按洞见优先级：矛盾 > 连接 > 重复 > 追问 / 空白 / 延伸）；正在输入时隐藏，停下约 2 秒后淡入。卡片只有按钮，没有淡点（卡片短，整张一节）。

**侧栏「AI 洞见」**（`Drawer` 非模态，伴随正文、不遮挡编辑）：

- 顶部一行：分析时间 · 模型 ·「重新分析」；结果过期时提示「正文已改动，重新分析？」。
- 按类型分组：**可以建立的连接** / 重复与矛盾 / 可以追问的 / AI 的补充。
- **连接卡**：本文那几个字（引文样式）→ 对方标题 › 节 + 理由；动作：
  - **预览**：悬停对方标题，复用 content-link 的悬停预览（`AnchoredPanel` + `Content`）；
  - **定位**：点引文，正文滚到那一处并闪一下高亮（「打开到位置」已有）；
  - **建立连接**：确认后在正文那一处把这几个字包成 `content-link`（`wrapContentLink` 的选区包裹分支），这条洞见标为「已连接」并移出列表；原文已改、找不到这几个字时提示「原文已改动」并作废这条。
- 其他卡：引子 + 展开看 AI 的看法；动作「记为问题」「预览」（有对方时）「忽略」。
- 「忽略」只对这一条；已连接 / 已记为问题 / 已忽略的折叠在底部「已处理 N 条」，可恢复。

**设置**：功能槽「AI 洞见」（说明：会在后台分析你最近 30 天写过的文档，打开其他文档时可手动分析；按日常写作量估算每天约 X 万 token）。另一个开关「阅读时显示洞见淡点」，默认开——只管淡点的视觉打扰，不影响按钮与侧栏。

## 6. 与「相关」的关系

- 「相关」（7a，脉络浮层末尾）仍是**本地近邻、不调 AI、不计数**，回答「还有哪些相近的内容」；
- 「AI 洞见」是**AI 判断后的、可操作的**提议，回答「哪里该连、哪里该想一想」。
- 两者的候选同源（向量近邻 + 同一套排除规则），洞见的候选更宽（p95，且不排除同项目）。

## 7. 存储

**主库新表 `content_ai_insights`**（理由同元信息 ai-insights §3.5：花 token 生成的结果随库同步，换机器不重算、不重复收费；用户的「已忽略 / 已连接」也要跟着走）：

```sql
CREATE TABLE IF NOT EXISTS content_ai_insights (
  content_id   INTEGER PRIMARY KEY,
  schema_ver   INTEGER NOT NULL,
  text_digest  TEXT NOT NULL,     -- 分析时的正文指纹（同 content_ai_meta）
  insights     TEXT NOT NULL,     -- JSON：[{ id, type, section, anchor, target{kind,id,section}, hint, detail, status }]
  model        TEXT NOT NULL,
  create_time  INTEGER NOT NULL,
  update_time  INTEGER NOT NULL
);
```

- `status`：`open` / `linked` / `questioned` / `dismissed`。重新分析时保留已处理的（按 `type + target + anchor` 匹配），不让忽略过的重新出现。
- 删除：同 `content_ai_meta`，正文引用计数归零时同事务删除，连库对账清孤儿。
- 主库 66 → **67 表**，索引不变；只加表，移动端不读写。

## 9. 零配置与成本

- 配上「AI 洞见」槽即同意后台分析最近写过的文档；清空即停止，按钮与淡点消失，已有结果保留不删。
- 不另设预算、隐私提示（沿用既有约束）。用量页按 `source.feature = "contentInsights"` 可见。
- 7a 元信息是洞见的前提：候选的要点与主张来自 `content_ai_meta`；元信息槽没配时，洞见只给追问 / 空白 / 延伸，连接 / 重复 / 矛盾缺依据会显著变差——**两个槽都配才有完整效果**，设置说明写清。

## 11. 任务拆分（确认后）

1. 主库 `content_ai_insights` 与表模块（读写、状态合并、删除、孤儿清理）；schema 三件套。

3. **提示词与评估（停下等用户反馈）**：真实库副本（重建向量）上分析 15 篇长文 + 15 张卡，导出洞见表（类型 / 位置原文 / 对方 / 引子 / 看法），用户逐条标「有用 / 没用 / 错」。不达标改提示词再测。
4. 渲染端：元信息行按钮、节首淡点、侧栏与各动作（建立连接走编辑器 `wrapContentLink`）；设置槽与开关。
5. 实测与文档回写（规模：重度库单篇候选与调用耗时；03 架构指南、DECISIONS、02、本文 §11.3）。

## 附录 A：本地候选的数据（第一版评估）

真实库副本（本地 bge-m3 修复管线重建，1425 个实体），270 篇 ≥ 3 节长文（平均 8.6 节），脚本 `D/src-electron/main/modules/entity-context/__tests__/reading-marks.eval.test.ts`。随机块对分位：p95 0.643、p98 0.687、p99 0.721。

| 口径 | 阈值 | 有候选的长文 | 每篇候选中位 / p90 |
| ---- | ---- | ------------ | ------------------ |
| 节与目标文字 ≥ 80 字 | p95 | 99% | 58 / 151 |
| 同上 | p99 | 89% | 5 / 31 |
| 同上 + 同项目互不推荐 | p99 | 69% | 2 / 29 |

结论：只靠本地阈值，p99 下仍有大量「同一件事别处也写过」与代码节、主题相邻的噪音，所以本版把判断交给 AI；本地按 p95 放宽、取前 15 个候选，保证不漏。重复与矛盾常在同一项目内，候选不再排除同项目。
