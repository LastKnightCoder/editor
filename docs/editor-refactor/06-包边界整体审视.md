## 1. 结论

已有拆分多数有真实职责与消费者依据，不需要整体推倒。但拆包过程中混用了三种目标：领域归属、重依赖隔离、清空内核目录；这些目标不能互相替代。05 提供了分组与批次，却仍把默认文档规则、复制片段和标记贡献留为候选协议。在这些边界未落实时继续搬目录，会把内部耦合变成跨包 API 和宿主装配负担。

建议保留已有明确领域包，暂停新增小包。下一步先确定内核与基础文档规则的边界、显式装配方式；基础领域优先一个包内按职责分入口，再迁媒体领域。包数量不作为完成指标。

## 2. 判断是否需要独立包

先划清模块职责，再选择目录、子入口或独立包：

1. 职责能否独立说清，元素、命令、codec、类型、样式是否能一起归属？
2. 是否存在真实独立消费者，或不同的运行环境、依赖及装配需求？
3. 拆出后能否通过少量稳定接口协作，避免反向引用、内部路径和临时宿主注入？
4. 是否有可验证的收益，足以承担 manifest、出口、类型配置、四端接线与测试成本？

独立入口足以隔离的，不必独立建包。共享第三方库不意味着共享领域；两个包依赖 KaTeX 或 emoji-mart 本身不构成错误。生产体积与首屏收益须由构建验证，不能从包名或 import 数量推断。

## 4. 当前未收口的具体边界

### 4.1 默认功能仍由内核隐式装配

`packages/editor/src/kit/EditorKit.ts` 直接导入 `startExtensions`；`createEditorKit()` 自动补齐内置功能，只有 `createBareEditorKit()` 使用显式列表。`extensions/index.ts` 仍聚合基础、列表、表格、容器与媒体。四端同时手工补已迁扩展和预览菜单，形成“部分自动、部分显式”的双重装配规则。

建议最终由宿主场景显式选组合，内核只装配传入的贡献。通用领域可以导出稳定的扩展组；宿主业务服务和场景选择留宿主。不要为了少写四份 import 马上新增一个含四端业务的总装配包，也不能在工厂切换时改变现有场景覆盖或 Kit 实例稳定性。

### 4.2 段落与标记是运行规则，不只是几个文件

`plugins/withNormalize.ts`、`utils/normalizeEditorContent.ts` 固定补 `paragraph`/`formatted`；`utils/insertElement.ts`、`utils/nodeOperations.ts` 也有段落规则。`api/index.ts` 公开的 AddParagraph 与段落判断已有迁移桥说明。根编辑器直接渲染 `components/FormattedText`，其中固化粗体、代码、高亮、颜色和渐变等。

建议先列出空文档、删除最后一块、void 后追加、方向键落点、源码退出与标记渲染的消费者，确定最小默认文档规则和贡献方式。只把这些规则封成核心中的通用函数，仍没有移走领域所有权；反过来，为彻底抽象一次性设计任意 schema/第三方生命周期也超出需要。

### 4.3 列表、表格和容器尚未独立

`plugins/withNormalizedCopy.ts` 知道 list-item、table-row/cell 和多种容器；`menu/defaultMenu.tsx` 固定转换源、容器名单与目标；`utils/nodeOperations.ts` 承担具体转换。只迁 `extensions/list-*` 或 `extensions/table` 会留下半个领域在内核。

建议通用复制遍历/隔离留核心，具体片段修复由领域负责；通用移动、剪贴、删除留机制，类型转换规则和菜单归基础领域。先验证现有贡献点是否足够，再用真实列表/表格行为证明缺口，不凭文件数量新增协议。

### 4.4 服务应按语义归属，不能按“解耦”统一往 shared 搬

| 内容                                                             | 建议归属                                                                                         |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Registry、作用域、服务派生、通知/错误/主题消费、编辑器浮层适配桥 | editor；实现维持当前语义，不另建 DI/浮层包                                                       |
| Typst 编译契约                                                   | diagram/services；宿主提供实现                                                                   |
| HTML/custom-block 共用运行时样式契约                             | 现有 shared/runtime-style 纯入口                                                                 |
| 媒体插入来源、provider、动作、选择器与媒体插槽                   | 未来媒体领域；不能仍叫通用 EditorSlots 掩盖媒体语义                                              |
| 文件、资源、打开链接                                             | 先完整调查编辑器外消费者；确有共用时采用明确纯子入口，否则随真实领域；本轮不照旧候选名单批量迁出 |
| Page/router、Electron/Tauri/RPC 的具体实现                       | 宿主                                                                                             |

现有 OverlayBackDismiss 的 React Layer 需要当前 Page 上下文，只登记关闭回调，不渲染浮层或创建第二套仲裁。保留当前归属，不抽通用 overlay 包；已接源码全屏与行内公式，不能宣称覆盖所有浮层。

### 4.5 通用媒体组件不等于编辑器媒体扩展

shared 的 VideoPlayer 被桌面视频笔记直接消费，AudioPlayer/VideoPlayer 被移动端 LocalAudio/LocalVideo 包装使用，图库也被编辑器多个布局消费。因此未来迁 `editor-media` 时，只应拥有文档元素、ingest、回填、编辑动作与媒体契约；不能把所有播放器/裁剪器直接塞进该包，迫使非编辑器页面反向依赖 editor。

通用媒体 UI 先保留明确入口；若独立包收益不足，不另建 media-ui。平台视频下载、缓存与业务数据处理仍归宿主适配。

## 5. 后续分组建议与方案比较

| 方案                                                             | 收益                                                         | 成本/风险                                                           | 建议                                   |
| ---------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------- | -------------------------------------- |
| 继续按 05 为 basic/list/table/containers 分别建包                | 每域 manifest 独立                                           | 当前共享段落、复制和转换规则未分离，容易形成交叉依赖与大量迁移桥    | 先不执行；后续有独立使用与维护证据再拆 |
| 一个 `editor-basic`，内部按基础文本/列表/表格/容器分模块和子入口 | 先把基础文档语义从核心移出，保留按场景组合能力，减少包间协议 | 包内仍须守住方向；不能通过根入口自动装全部，也不能变成第二个 shared | **推荐作为下一阶段的候选边界**         |
| 所有新功能重新合并为一个 extensions 包                           | 包数量少                                                     | 现有源码预览、重依赖、独立运行入口重新混合，迁移成本高              | 不推荐整体回并                         |

这里的 `editor-basic` 对应 05 中 basic/list/table/containers 的职责集合，不是要求四域成为同一个扩展对象；包内仍按能力独立导出，codec 和类型使用各自纯入口。现有 emoji 可保留；如果未来实际装配证明没有独立价值，再单独评估合入，避免本轮来回搬运。

`editor-media` 是下一项较明确的候选独立包：image、inline-image、gallery、audio、video 共享上传/回填/插槽与交互语义。暂不继续拆 image/audio/video 三包；先明确通用媒体 UI 与宿主业务能力的边界。

## 6. 恢复实施时的顺序与验收

以下是讨论用顺序，不是当前待自动执行清单：

1. **确认归属和场景矩阵**：列四端现有 Kit、扩展集合、codec、服务和预览菜单，逐项标注核心/领域/宿主；确认基础领域合包建议，不改变产品能力。
2. **收口默认装配与最小规则**：明确默认可编辑块、复制片段、标记渲染的真实缺口，形成具体接口与回归用例；避免先建包再倒推接口。
3. **基础领域整体迁移**：扩展、类型、codec、插入/转换、复制修复、菜单、标记与样式按归属同步迁移；迁完收回对应段落桥及深引。
4. **媒体领域单独迁移**：在宿主/通用媒体 UI 边界确定后迁媒体扩展与专属服务；完整检查移动工具栏、协作资源覆盖和四端插入链路。

每步独立收尾：依赖方向与公开入口、Node/headless、场景覆盖、文档往返、光标/复制/删除、只读/服务派生/协作稳定性通过相应验证；涉及样式与重依赖再检查生产资源。视觉由用户验收。一个包是否独立，以职责和使用证据判断，不以测试全绿代替设计评审。
