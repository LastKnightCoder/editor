# 02 · 阶段计划

每个阶段都要**独立可合并**：做完一个阶段，应用能正常运行，测试全绿，再开始下一个阶段。阶段内按任务粒度提交。

通用验证（每个阶段收尾都要跑）：

```bash
pnpm check                                   # desktop tsc
pnpm --filter @tau/ui check
pnpm --filter @tau/themes test          # P1 起
pnpm --filter @tau/editor test            # editor 单测
pnpm --filter @tau/editor-collab test   # P7 起
pnpm --filter @tau/collaboration test
pnpm --filter blog test
pnpm --filter mobile test
pnpm --filter browser-extension test
pnpm lint
pnpm check:editor-refactor               # 基线只许降；阶段完成后 --update 下调
```

涉及视觉的阶段还要在 desktop showcase（`pnpm showcase`）里做明暗 × 至少两套主题的截图对比，截图结论记进 04。

第一块（错误隔离 + 未知节点）落地形态：

- 渲染：`components/ElementGuard` 的 `ElementErrorBoundary` 包每个元素，出错显示「X 渲染失败」占位（保留 `attributes` / `children`），节点数据变化后重试；扩展 render 在函数子组件里调用，允许直接用 hook。
- 行为：`kit/extensionGuard.ts` 按扩展逐组应用插件，只包该组改写过的行为方法（`insertBreak` / `deleteBackward` / `insertData` / `normalizeNode` 等，schema 判定 `isVoid` / `isInline` 与 `apply` 不拦）；出错回退上一层实现，已产生操作则不回退（防止一次按键执行两遍）。快捷键 action 同样隔离。10 秒内同一扩展出错 3 次即熔断，停用其行为与快捷键。渲染错误只上报不计入熔断。
- 上报：新服务 `IExtensionErrorReporter`，未注册时写控制台；宿主接提示 / 日志留给后续（目前各端都没接）。
- 未知节点：`withUnknownElements` 把没注册的 type 当 void、跳过其子树规范化；`UnknownElement` 渲染只读说明块。
- Markdown：`@tau/markdown/src/unknownNode.ts`，语法见 ER-006。
- 守护测试：`packages/editor/src/__tests__/extension-isolation.test.tsx`（4 例）、`packages/markdown/src/__tests__/unknown-node.test.ts`（7 例），都做过「去掉实现即失败」的反向验证。

第二块（`defineExtension` + `@tau/editor/api` + 适配器）落地形态：

- 声明：`src/api/extension.ts` 的 `defineExtension({ id, elements, blockPanel, toolbar, behaviorsFor, plugins })`，`apiVersion` 自动补齐并冻结；`defineElement<E>()` 只做类型收窄。元素声明 `{ type, kind, isVoid, render, behaviors }`，`render` 是组件（可 `lazy()`，加载期间渲染保留结构的空壳）。
- 行为：`insertBreak` / `deleteBackward` / `insertText` / `normalize`，签名 `(editor, [node, path], ...) => boolean`，从选区所在的最内层元素往外找，返回 `true` 即停，都不处理再交给插件链与默认行为；每个 handler 按扩展隔离与熔断。`behaviorsFor` 给「在别的元素里触发、产出本元素」的场景（快捷语法），挂在目标类型上与其自身行为一起分发。
