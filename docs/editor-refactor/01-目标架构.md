# 01 · 目标架构

这里描述**终态**。各阶段怎么一步步到达，见 [02-阶段计划.md](02-阶段计划.md)。决策出处用 `ER-xxx` 编号，见 [03-决策记录.md](03-决策记录.md)。

## 1. 核心原则

1. **内核只放机制，功能都是扩展。** 内置扩展和（将来的）第三方插件走同一套公开 API，不许走后门（ER-001）。
2. **依赖只能往下。** Editor 依赖契约（主题 token、服务接口），不依赖宿主实现。
3. **文档比插件活得久。** 插件缺失或出错时，它的节点必须能无损保存和往返（ER-006）。
4. **Token 是 API，类名不是 API。** 主题定制和插件取色都只走 CSS 变量和 ThemeService（ER-003）。

## 2. 分层与依赖方向

```
apps/desktop · blog · mobile · browser-extension     组装：选扩展、注册服务、注入主题
        ↓
平台层（desktop 的 editor-extensions / services 等）    服务实现、插槽（LocalImage…）、业务扩展
        ↓
扩展包   editor 内置扩展（basic）│ editor-diagram │ editor-custom-block │ editor-webview │ editor-collab …
        ↓
@tau/editor（内核）                                     机制（React / DOM）
        ↓
@tau/markdown（纯函数，无 DOM）   @tau/themes（主题契约，纯数据）   @tau/shared
```

`@tau/markdown` 和每个扩展的 `schema.ts` / `markdown.ts` 属于 **headless 层**：不依赖 React、DOM，可以在 Electron 主进程、Node 脚本、MCP 里直接用（见 §8）。

**headless 包的「Node 可直接加载」约束**（`@tau/themes` 根入口首先落地）：不经构建，Node 以包名原生加载 TS 源码（type stripping）。所以：相对导入写 `.ts` 扩展名；tsconfig 开 `allowImportingTsExtensions`、`erasableSyntaxOnly`、`verbatimModuleSyntax`，lib 不含 DOM；包内放一个 `node-import.test.ts`，用子进程真实加载。

硬约束：

- `@tau/editor` 不得 import 任何 `apps/*`，也不得 import `@tau/ui`（组件库属于宿主）。
- 扩展只能 import `@tau/editor` 的公开入口（终态为 `@tau/editor/api`），不得深引 `@tau/editor/src/...` 内部路径。P8 起用 ESLint `no-restricted-imports` 强制。
- `@tau/themes` 是主题的唯一归属，没有中间转出层。根入口只放数据和纯函数（token 词汇表、`defineTheme`、内置主题、偏好解析与首帧脚本生成），node 可跑；DOM 应用放 `@tau/themes/dom`，React 运行时（zustand store）放 `@tau/themes/react`；CSS 分为 `tokens.css`（变量）和 `tailwind.css`（语义类映射）。Editor 只用根入口的类型和 CSS 变量。

## 3. 内核（`@tau/editor`）负责什么

| 模块          | 职责                                                                              |
| ------------- | --------------------------------------------------------------------------------- |
| 文档模型      | 元素类型注册、schema 校验、未知节点保护（ER-006）                                 |
| 扩展宿主      | 扩展注册、冲突检测、生命周期（activate/dispose）、按类型分发、错误隔离            |
| 命令与快捷键  | 命令注册表；快捷键只绑定命令 id                                                   |
| UI 挂载点     | BlockPanel、HoveringToolbar、右键菜单、拖拽手柄；**只提供挂载点**，条目由扩展贡献 |
| 服务注册表    | 现有 `ServiceRegistry` 保留：服务接口 + 插槽（`EditorSlots`）                     |
| 主题消费层    | `editor.css` 定义 `--ed-*` 组件 token；`ThemeService` 接口                        |
| 文档源        | `EditorDocument` 接口：普通值或 Yjs 绑定；文档源切换时无缝交接（§7）              |
| Markdown 接入 | 调用 `@tau/markdown` 做粘贴导入等；框架本身在 `@tau/markdown`（§8）               |

**不属于内核**：任何具体元素类型（包括段落），任何重依赖（mermaid、katex、shiki、codemirror、abcjs、echarts 等），任何平台能力的实现。

## 4. EditorKit（替代 EditorProvider）

每个宿主创建一次，显式传给 `<Editor>`：

```ts
const kit = createEditorKit({
  extensions: [...basicExtensions(), diagramExtensions(), customBlock(), ...desktopExtensions],
  services: [desktopServices],        // ServiceRegistration[]，沿用现有注册方式
  theme: desktopThemeService,         // ThemeService
});

<Editor kit={kit} initValue={value} onChange={...} />
```

- kit 创建时完成冲突检测和预计算（替代 `PluginOptimizer` 的缓存职责），同一个 kit 可给多个编辑器复用。
- 嵌套编辑器（预览、白板卡片里的编辑器）默认继承父编辑器的 kit：用**内核私有**的 Context 传递，不对宿主暴露。
- 单个编辑器实例需要差异时用 `kit.extend({ extensions, services })` 派生，不做隐式合并。
- kit 按**场景**划分，一个场景一个，命名说场景不说程度（`getMarkdownFileKit()` / `getFlashcardKit()` / `getChatInputKit()`…），见 ER-016；每个 kit 只注册该场景需要的扩展，不要求全量覆盖，见 ER-017。各端 kit 可以不同（服务与组件实现有平台差异），但元素类型的覆盖要按内容实际会包含什么来补齐，否则同一份内容换端就渲染不出来。
- 现在 `EditorConfig` 里的字段去向（ER-004）：

| 现字段                                       | 去向                                                                        |
| -------------------------------------------- | --------------------------------------------------------------------------- |
| `theme.mode`                                 | `ThemeService.mode`                                                         |
| `theme.colors`（Tailwind 类名）              | **删除**，改用 `--ed-*` / `--tau-*`                                         |
| `appearance.image`                           | image 扩展参数：`createImageExtensions({ appearance })`                     |
| `openUrl`                                    | 服务 `IOpenerService`                                                       |
| `formatDate`                                 | **删除**，不设服务：没有宿主使用，也没有平台差异                            |
| `plantumlServer` / `plantumlDarkTheme`       | plantuml 扩展参数                                                           |
| `<Editor theme>` prop、`EditorContext.theme` | 删除，统一由 ThemeService；局部强制明暗用 `<EditorThemeOverride>`（ER-014） |
| `features.disableHeaderCollapse`             | header 扩展参数                                                             |

## 5. 扩展 API v2

### 5.1 形态

```ts
export default defineExtension({
  id: "tau.custom-block",          // 全局唯一；内置用 tau.*，第三方将来用作者命名空间
  apiVersion: 1,
  elements: [
    {
      type: "custom-block",        // 内置类型保持现有 type 名，不加前缀（兼容已有文档）
      kind: "block",               // block | inline
      isVoid: true,
      schema,                      // 校验函数；不合法时交给 normalize 修复
      render: lazy(() => import("./CustomBlock")),
      markdown: customBlockCodec,    // 来自 ./markdown.ts（纯函数文件）
      behaviors: { onKeyDown, deleteBackward, insertBreak, normalize, onPaste },
    },
  ],
  commands: [{ id: "tau.custom-block.insert", run }],
  hotkeys: [{ key: "mod+alt+c", command: "tau.custom-block.insert" }],
  blockPanel: [...],
  toolbar: [...],
  contextMenu: [...],
  services: { requires: [], optional: [IFileService] },
  activate(ctx) { return () => {} },   // 返回 dispose
});
```

- `ctx` 提供：`editor`（受限的编辑器 API）、`services`、`theme`（ThemeService）、`log`、`subscribe`。
- `behaviors` 只在选区或目标节点属于该类型时由宿主调用，不再全局改写 `editor.insertBreak`。
- **受信任层**：`plugins: Plugin[]`（原始 `(editor) => editor`）保留，只给内核内置扩展用。它在类型上标记为 `@internal`；将来开放第三方时不进公开 API。原因：少量能力（列表、表格的跨节点 normalize，协作）用声明式表达不了，硬塞进公开 API 会冻结内部实现（ER-005）。
- 过渡期：旧 `IExtension` 由适配器 `fromLegacyExtension()` 包成 v2，逐个迁移，不要求一次性改完。

### 5.2 隔离与容错

| 层面     | 机制                                                                                                                                   |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 渲染     | 每个元素外包 `ElementErrorBoundary`：出错显示「扩展 X 渲染失败」占位，保留 `attributes` / `children` 让 Slate 不丢选区，数据不动       |
| 行为     | 宿主调用每个 handler 时 try/catch，出错则回退默认行为并记日志；同一扩展短时间内连续出错达到阈值就停用该扩展的 behaviors，并提示用户    |
| 冲突     | 元素 type 在 kit 创建时检测，重复直接报错，显式 `override: true` 才允许替换（P6 已落地）；命令 id 与快捷键的检测随 P8 的命令注册表补齐 |
| 未知节点 | 找不到扩展的节点渲染为只读占位（显示类型名），序列化时原样保留（ER-006）                                                               |
| 性能     | `render` 和重依赖一律懒加载；首屏不因扩展数量变慢                                                                                      |
| 协作     | 元素数据必须可 JSON 序列化（schema 保证），这样才能走 yjs                                                                              |

### 5.3 Markdown 归属

- 每个元素自带 Markdown 编解码（codec），但 codec 写在扩展的独立文件 `markdown.ts` 里，**不写在 `defineExtension` 的 UI 模块里**，否则主进程引入 codec 会连带引入 React 组件。`defineExtension` 只引用它。详见 §8。
- 未知节点兜底：序列化为 `:::tau-node{type="x"}` 加 JSON 代码围栏（具体语法 P8 定，写进 ER），解析时还原，保证往返无损。

### 5.4 为第三方预留（本期不实现）

本期不做，但以下设计**不能被本期实现堵死**：

- 扩展以 `id + apiVersion` 标识，公开入口只有 `@tau/editor/api`。
- react、slate 等由宿主提供单例（将来作为 externals 注入），扩展包不能各自打包一份。
- 扩展不能直接访问 `window` 上的宿主对象，只能通过 `ctx.services` 访问。
- 扩展元数据（id、名称、版本、依赖服务）可以脱离代码读取，为将来的市场和授权清单留口。

## 6. 主题

### 6.1 三层 token

```
palette（主题作者自由组织）
   → 语义 token  --tau-*   （@tau/themes 契约，所有宿主一致）
   → 组件 token  --ed-*    （@tau/editor 自己定义，默认从 --tau-* 派生）
```

- `--tau-*` 的词汇表就是原 `packages/ui/src/theme/tokenContract.ts` 定义的那套，P1 整体迁到 `@tau/themes`（ER-002、ER-011）。
- Editor 自带 `editor.css`，在 `.tau-editor` 作用域下定义组件 token，例如：

```css
.tau-editor {
  --ed-text: var(--tau-ink-1);
  --ed-text-muted: var(--tau-ink-2);
  --ed-border: var(--tau-line-1);
  --ed-hover-bg: var(--tau-bg-hover);
  --ed-accent: var(--tau-accent);
  --ed-code-bg: var(--tau-bg-sunken);
  --ed-callout-tip-bg: var(--tau-ok-soft);
  --ed-callout-tip-border: var(--tau-ok);
  --ed-selection: var(--tau-accent-soft);
  --ed-font-mono: var(--tau-font-mono);
}
```

- 组件优先写 `--ed-*`；只有语义明确对应的地方才直接写 `--tau-*`。
- 明暗依赖 `html[data-mode]`（兼容期同时保留 `.dark` 类，因为 Tailwind 的 `dark:` 变体在用）。组件里不再根据 `isDark` 拼类名；非 CSS 渲染器通过 ThemeService 取值。

### 6.2 ThemeService

```ts
interface ThemeService {
  readonly mode: "light" | "dark";
  /** 读取计算后的 token 实际值，给 mermaid、canvas、echarts、shiki 用 */
  token(word: TokenWord | EditorTokenWord): string;
  subscribe(listener: () => void): () => void;
}
```

- 内核提供 `createDomThemeService(root = document.documentElement)` 默认实现：监听 `data-theme` / `data-mode` 变化，读 `getComputedStyle`。多数宿主直接用它。
- React 侧用 `useEditorTheme()`（基于 `useSyncExternalStore`）。

### 6.3 给主题作者和插件作者

- **自定义主题**：沿用 `defineTheme`（全键约束，漏键编译不过）；可额外覆盖 `--ed-*` 做编辑器细调（callout 配色、代码高亮）。
- **插件作者**拿到三样东西：CSS 变量 `--tau-*` / `--ed-*`、`ctx.theme`、少量 UI 原语（见下）。
- **UI 原语**：Editor 现在 43 个文件直接用 antd。终态由 `@tau/editor/api` 导出少量原语（Button、Menu、Popover、Input、Tooltip），底层可以继续用 antd，但插件作者不绑定 antd。antd 主题由 `--tau-*` 生成 ConfigProvider token。原语清单 P8 定。

### 6.4 custom-block 的主题

custom-block 模板和编辑器运行在同一个页面上下文（ER-007），通过 `hooks` 注入 `useEditorTheme`，模板作者写 `var(--tau-*)` 即可跟随主题。现在的 `renderWithTheme(isDark)` 机制在 P3 改为订阅 ThemeService。

## 7. 协作：文档源 + 协作扩展

### 7.1 现状与闪烁的根因

- desktop 所有内容编辑都经 `apps/desktop/src/components/ContentEditor`（12 个调用点）。**本机编辑也是 Yjs**：主进程为每篇内容建一个 `mode: "local"` 的协作会话，渲染进程经 IPC 订阅。
- 发起共享时，主进程用当前内容**新建**一个 Y.Doc（`createSharedDocument`），documentId 换成服务端 id。渲染进程这边接连发生三件事：
  1. `useCollaborationDocument` 在 documentId 变化时先把 binding 置空，ContentEditor 退回 fallback/转圈；
  2. 新 binding 就绪后，`<Editor key={contentId:documentId}>` 的 key 变了，整个编辑器卸载重建；
  3. 重建时所有块组件（mermaid、codemirror 等）重新初始化。
- 结束共享、移动端连接失败回落本地（`CollaborativeEditor` 返回 null 由宿主换成本地编辑器）也是同样的路径。
- 此外 `CollaborationServices` 靠嵌套 `EditorProvider` 覆盖资源服务和媒体插槽；内核里 `withCollaboration`、光标、私有块占位（SafeElement）都是 `collaboration` prop 的特判，内核因此硬依赖 yjs。

结论：闪烁不是渲染性能问题，而是**「换文档」和「换同步方式」被混成了一件事**。共享只改变了同步方式，内容并没变，不应该换文档。

### 7.2 模型

协作不是普通的内容扩展：它改变了内容的事实来源（Y.Doc 而不是 Slate value），接管了撤销历史，而且必须从第一帧就生效。所以拆成两部分：

- **文档源（EditorDocument）**：内核新增的一等概念，回答「内容从哪来、改动往哪去、谁管撤销」。普通值和 Yjs 绑定是两种实现。
- **协作扩展（`@tau/editor-collab`）**：协作光标、私有块占位、共享模式下的资源上传/解析服务。走扩展 API 的受信任层（ER-005）。

```ts
/** 内核接口（示意，P0 协作 spike 后定稿） */
interface EditorDocument {
  /** 内容谱系：同一篇内容在本机/共享之间切换时保持不变 */
  readonly lineage: string;
  /** "external" 表示由文档源自己管撤销（Yjs UndoManager），内核不装 withHistory */
  readonly history: "slate" | "external";
  /** 挂到编辑器上：同步初始内容、开始监听；返回卸载函数 */
  attach(editor: Editor): () => void;
  /** 该文档源需要覆盖的服务（如共享模式的资源上传），挂在本编辑器实例上 */
  readonly services?: ServiceRegistration;
  readonly readonly: boolean;
  subscribe(listener: () => void): () => void;
}

<Editor kit={kit} document={doc} />
```

落地形态（P6 定接口，P7 接入协作）：接口如上（另有 `initialValue`、可选 `onChange`），
`createValueDocument(initValue, onChange)` 由内核提供。`initValue` / `onChange` 仍是各宿主的
主路径，未改写为内部转文档源（见 02 P6 说明）。

- `createValueDocument(initValue, onChange)`：内核自带，给 blog、预览、只读场景。
- `createYjsDocument(binding, { lineage, cursors, onChange })`：`@tau/editor-collab` 提供。
- 内核不再有 `collaboration`、`collaborationCursors` prop，也不再依赖 yjs / slate-yjs。

接管内容与撤销的文档源（目前只有协作）经 `document.binding` 改写编辑器，这是受信任层
（ER-005，标 `@internal`，不进公开 API）。内核在这几个点上让路，别处不认识协作：

| `EditorDocumentBinding`  | 内核何时调用               | 协作的实现                                                  |
| ------------------------ | -------------------------- | ----------------------------------------------------------- |
| `install(editor)`        | 创建编辑器时一次           | `withCollaboration`（withYjs + withYHistory + withCursors） |
| `connect` / `disconnect` | 挂载 / 卸载，换源时成对    | `YjsEditor.connect`；断开前 flush 未发出的本地改动          |
| `rebind(editor)`         | 同谱系换源（§7.3 第 3 层） | 换 sharedRoot、重建 UndoManager、结构共享                   |
| `renderElement`          | 每个元素渲染前             | 私有块：作者渲染真身，远端渲染占位                          |
| `renderOverlay`          | 编辑区之上                 | 协作光标层                                                  |
| `wrap`                   | 包住编辑器子树             | 提供 `useCollaboration` 的上下文                            |

`history: "external"` 时内核不装 `withHistory`；`binding` 存在时 `setEditorValue` 不接受整体覆盖
（内容归文档源管）。`renderOverlay` / `wrap` 用函数而不是组件：换源时组件类型一变，React 会重挂载整棵子树。

### 7.3 无缝切换的三层保证

1. **主进程：共享是会话升级，不是换文档（desktop）。** 发起共享时，把本机会话的 Y.Doc 状态发布到服务端，继续用**同一个 Y.Doc**；私有块转占位、资源 URL 改写、`meta.mode` 切换都作为这个 Y.Doc 上的普通编辑发生，经 IPC 像平常的更新一样同步到渲染进程。渲染进程订阅的是稳定的内容会话键，documentId 变化只在主进程内部映射。这一层做完，desktop 的发起/结束共享就根本不需要换文档。
2. **宿主：先准备好再切换，中间不出现转圈。** `useContentDocument(contentId)` 返回一个稳定句柄；底层文档源要换时，旧的继续显示和编辑，新的就绪后在同一帧切换。首次打开仍可用只读快照作占位（现有 `fallback` 的做法）。
3. **内核：同谱系的文档源切换不重建编辑器。** `document` 换了但 `lineage` 相同，就在同一个 Slate editor 上 detach 旧源、attach 新源；新内容与当前内容相同就保留现有节点对象，块组件不会重新挂载，选区也保留。`lineage` 不同才视为换了一篇文档。

第 3 层主要服务移动端「连接失败回落本地 → 恢复后接回协作」这类确实要换源的情况。

### 7.4 desktop 的 ContentEditor

保留一个薄的宿主组件是合理的（「编辑器 + 业务数据源」本来就是宿主的职责），但它只做一件事：

```tsx
function ContentEditor({ contentId, ...props }) {
  const document = useContentDocument(contentId); // 稳定句柄，内部处理会话、升级、回落
  return <Editor kit={desktopKit} document={document} {...props} />;
}
```

没有 key、没有嵌套 Provider、就绪前不换组件；只读、冻结、在线状态由文档源的 `readonly` 和 `subscribe` 提供。

### 7.5 已验证的可行性（P0 spike，2026-09-28）

- **会话升级（S1）可行**。在同一个 Y.Doc 上做最小编辑：私有块换成占位，删除 `LOCAL_FIELDS`，`meta.mode` 切为 shared，资源 URL 改写。结果如下：
  - 与私有块无关的块仍是同一个 `Y.XmlText`；
  - 读出的内容与新建共享文档一致，并通过 `validateDocument`；
  - 私有块数据（包括升级前 50 轮编辑的历史）和原本地资源路径都不会出现在编码状态里。
  - **前提是 Y.Doc 开启 gc**（Yjs 默认开启）。关掉 gc 后历史会残留，spike 里有对照用例。正式实现要在主进程加断言，或在发布前检查编码内容，把这条隐私边界锁死。
  - 升级必须是最小编辑。不能用 `replaceSharedContent` 整体替换正文，否则渲染端还是会整体重建节点。
  - 体积：50 轮编辑后，升级文档约 2.1 KB，新建文档约 1.2 KB，可以接受。
- **同谱系换源（S2）可行**。`rebind` 的步骤：disconnect → 改 `sharedRoot` → 重建 UndoManager → connect → 结构共享（新树中与旧树深度相等的子树换回旧对象）→ 恢复选区。结果如下：
  - 内容相同时元素组件零重挂载，选区保留；只有一段不同时只重建那一段；
  - 写入和远端更新都只走新文档，撤销只作用于新文档。
  - 对照组：不做结构共享时，所有元素都会重新挂载。这说明闪烁的根源在节点对象身份，而不在 `key`。
  - 正式实现还要处理（spike 没覆盖）：`withCursors` 的 awareness 切换、`withCollaboration` 的 fields 监听和 hydrate 重绑；结构共享要按 `collabId` 匹配而不是按位置，避免在差异段之后的段落上失效。

## 8. Markdown：headless 层

### 8.1 现状

同一件事现在有三份实现：

| 位置                                                                                                                | 内容                               | 使用方                                                          |
| ------------------------------------------------------------------------------------------------------------------- | ---------------------------------- | --------------------------------------------------------------- |
| `apps/desktop/src/utils/markdown.ts` + `markdownSerializerRegistry.ts` + `markdown-helper.ts` + `positionMapper.ts` | 导入导出、双向位置映射，约 3800 行 | desktop 渲染进程、Electron 主进程（web-clip、search-core）、MCP |
| `packages/editor/src/utils/markdownImport.ts`                                                                       | 只有导入，约 1170 行               | editor 粘贴导入、mobile、browser-extension                      |
| `packages/slate-markdown`                                                                                           | 导出注册表，约 930 行              | **没有使用方**                                                  |

desktop 这份还硬编码了 desktop 自己的扩展类型（file-attachment），并由 `markdown-node-import.test.ts` 守护「无 DOM 环境可导入」。

### 8.2 目标

- 合并为一个包 `@tau/markdown`（沿用 `packages/slate-markdown` 目录改名），**headless**：只依赖 unified/remark 生态、`slate`（核心包本身不碰 DOM）和元素类型。
- 对外：

```ts
const md = createMarkdownProcessor({ codecs: desktopMarkdownCodecs });

md.importFromMarkdown(markdown, ignoreTypes?, { customDirectives? }); // → Descendant[]
md.importFromMarkdownWithPositions(markdown); // → { content, positionMap }
md.getMarkdown(value); // → string
md.getMarkdownWithPositions(value); // → { markdown, positionMap }
```

包入口另外导出一组只含内置类型的同名函数（`importFromMarkdown` 等），mobile / browser-extension / 编辑器粘贴导入用它。
方法名沿用迁移前的 `importFromMarkdown` / `getMarkdown`，没有改成 `parse` / `stringify`——约 70 个使用方，改名的收益不足以抵消改动面。

- **codec 按扩展归属**：每个扩展的 `markdown.ts` 导出 codec（纯函数，只 import 类型和 `@tau/markdown`）。扩展包用独立的 headless 入口（如 `@tau/editor-diagram/markdown`）导出 codec 列表。宿主只定义一次 codec 列表，kit 和主进程共用，避免两边漂移。
  - P5 落地形态：`MarkdownCodec = { type, directives?, serializer?, isVoid?, inlineWrapperDirective? }`，`isVoid` 对导入、导出两个方向同时生效。内置类型仍在包内处理（拆成按扩展归属留给 P8/P9）；desktop 的业务类型集中在 `apps/desktop/src/utils/markdown-codecs.ts`。
- **双向位置映射是框架能力**，不让每个 codec 各自实现：
  - 块级映射由框架根据 mdast `position` 自动生成；
  - 行内格式文本的字符级映射（前后缀长度）由框架统一处理；
  - void 元素的属性级映射（如 code-block 的 `code` 对应源码里哪一段）由 codec 通过上下文声明，不声明就只有块级映射；
  - 现有 `positionMapper.test.ts` 的用例全部迁移并保持通过。
- 未知节点兜底语法（ER-006）在这一层实现。

### 8.3 「不依赖 DOM」怎么强制

只靠约定守不住，用三道机制：

1. `packages/markdown/tsconfig.json` 的 `lib` 不含 `DOM`，用了 `document`、`window`、`HTMLElement` 直接编译不过；
2. 包内测试跑在 vitest `environment: "node"`；
3. ESLint `no-restricted-imports`：`packages/markdown/**` 和各扩展的 `schema.ts` / `markdown.ts` 禁止 import `react`、`slate-react`、`slate-dom`、`antd`、`@tau/editor`（内核入口）。元素类型按文件深路径 `import type`（`@tau/editor/src/types/element/*.ts`）。
4. `node-import.test.ts`：子进程用 `node -e` 以包名加载并做一次往返，同时验证「Node 可直接加载」与「无 DOM」。

HTML 剪贴板转 Markdown 这类需要 `DOMParser` 的逻辑不进 `@tau/markdown`，留在编辑器粘贴扩展里。
