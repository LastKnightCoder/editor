- 第一版把分类做成了 store 的第二个数组 `libraryBlockExtensions`，被用户质疑「为什么又多一个概念」后退回。问题有三个：装载器不该承担策略分类；名字说「库内块」而真实判据是「有没有 serializer」，名不对实；手抄了一份 codec 表已有的事实，加新扩展放错桶没人拦。改为 store 只管装载（单一 `extensions`），清单 `BLOCKS_LOST_IN_MARKDOWN` 放在执行它的 `editorKit.ts`，并加单测钉住判据——清单里每个类型在 `desktopMarkdownCodecs` 里都不能有 serializer。给白板临时加个 serializer 验证过该用例会失败。
- 也试过「按有无 serializer 自动过滤」，不成立：`inline-ai-assistant` 同样没有 codec 条目，但它是临时 UI 标记元素、没有内容要存，自动过滤会顺手砍掉内联 AI。所以这条策略只能明写，代价用自检单测补。
- 动态导入保留，并把原因写进了 store 的注释：一是白板 / 数据库会拉进整个白板引擎与数据库视图；二是静态引入会成环（`editorKit → editor-extensions → whiteboard → components/WhiteBoard → DOMSizeMeasurer → editorKit`），而 `new WhiteboardExtension()` 在模块初始化期求值，正是「服务 hook 与 kit 的循环引用」那条坑的同一形状。
- 加了装载守卫：`initialized` 为假时建 kit 直接抛错。kit 只建一次，少拿了扩展不会报错、整个应用静默少几种块——与 AGENTS.md 里 D-014 同一类失效，所以宁可响亮地失败。三个入口（`main.tsx`、showcase、协作 e2e）统一在渲染前 await；后两个此前根本没调用过 `initExtensions()`，showcase 的富文本档案因此一直缺宿主块，这次一并修掉。

## 踩坑

### 共享工作区里按目录 git add 会圈进并发会话的中间态

- 现象：提交 ingest 时 pre-commit 基线钩子报 isDark 27/22 超标；stash 验证 HEAD 持平，说明超标来自未提交改动——而我的 ingest 改动不含任何 isDark。
- 原因：`git add packages/editor` 把目录下**所有**工作区改动都暂存，其中混着并发 editor 会话未提交的中间态（+5 个 isDark 文件）；基线钩子对整个工作区检查，被别人的半成品挡住。暂存区里还同时有对方 stage 的文件，对方 commit 有带走我文件的风险（本例对方只提交了自己的单个文件，侥幸）。
- 解法：共享工作区**一律按文件白名单 add**，绝不用目录通配；提交前 `diff --cached` 逐文件核对；钩子被他人中间态误伤时，确认自己零违规后 --no-verify 并在提交信息注明原因。
- 相关：efc892bbe。

### 脚本批量改 CSS 结构会留下悬空括号

- 现象：用脚本删 `&.dark { ... }` 块时，嵌套规则的收尾 `}` 被留下，less 编译报「Unrecognised input」，两处。
- 原因：按行匹配的删除逻辑没有正确跟踪嵌套深度。
- 解法：批量只做「值替换」，删除结构块改用精确编辑；每批都跑一遍 less 编译检查（`/tmp/lesscheck.cjs` 那种一次性脚本即可）。

### 计算样式快照比对的假差异：CSS transition

- 现象：blog 迁移后 doc、article 两个页面深色快照与基线不一致，逐元素看是一部分文字颜色处于中间色（如 `rgb(214,221,227)`，目标是 `rgb(230,237,243)`）。
- 原因：页面元素带 `transition-colors`。基线采样时刚切到深色，颜色还在过渡中途；两次采样的时机不同，所以哈希不同。和改动无关。
- 解法：采样前注入 `*{transition:none!important;animation:none!important}`；并且先 `git stash` 掉改动，在同一个 dev server 上采集基线，再恢复改动采集对比，两次口径完全一致。

### 用正则处理数 MB 的构建 CSS 会卡死

- 现象：对 5 MB 的 sidepanel CSS 用 `[^{}]*\{\s*\}` 反复替换来删空规则，两次都超时（回溯爆炸）。
- 解法：改用仓库已有的 lightningcss（`transform` + `visitor` 删掉 `--tau-*` 声明）做结构化比对，几秒就能出结果。

### `@tau/themes/testing` 解析器最初把 `@import` 并进下一条规则

- 现象：desktop 覆盖测试里 paper · light 报 41 个词全部缺失。
- 原因：`tokens.css` 开头的 `@import "./scale.css";` 没有花括号，被规则正则当成下一个选择器的前缀，于是 `[data-theme="paper"][data-mode="light"]` 这个选择器没有登记上。
- 解法：先剥掉 `@xxx ...;` 语句再匹配规则，并补回归用例。

### Node 侧以包名导入 workspace 的 TS 源码包失败（已根治）

- 现象：`vite.config.*.mts` 里 `import { createThemeBootstrapScript } from "@tau/themes"` 启动报 `ERR_MODULE_NOT_FOUND: .../packages/themes/src/register`。
- 原因：vite 打包配置文件时把包名导入外置，交给 Node 原生 ESM 加载。Node 24 能对 workspace 符号链接（真实路径不在 node_modules 下）做 type stripping，但 ESM 不补扩展名，TS 源码里的 `./register` 找不到。
- 最初的绕法：配置里改用相对路径。用户要求根治，不绕。
- 解法：headless 包（Node 也要用的）遵守「Node 可直接加载」约束：
  1. 相对导入写 `.ts` 扩展名；
  2. tsconfig 开 `allowImportingTsExtensions`、`erasableSyntaxOnly`（禁 enum、namespace、参数属性等不可擦除语法）、`verbatimModuleSyntax`（类型导入必须写 `import type`）；
  3. 包内加 `node-import.test.ts`：子进程用 `node -e 'import("@tau/themes")'` 真实加载。已验证：把任一导入改回无扩展名，这个测试就会失败。
  - 消费方的 tsconfig 也要开 `allowImportingTsExtensions`（desktop、blog、mobile、extension、editor 早就开了，这次给 `@tau/ui` 补上）。
- 相关：P5 `@tau/markdown` 按同一约束建包，Electron 主进程和脚本就能直接以包名导入。约束写进了 01 §2。

- 原因：历史上只用 `@tau/themes/light.less` 这类深路径，两边刚好都能解析。

### 局部强制明暗只管 token，不管正文色

- 现象：内容导出预览选深色主题，代码块、行内代码是深色（正确），正文却是深色字，几乎看不见。
- 原因：`EditorThemeOverride` / 根节点的 `data-mode` 只让 `--tau-*` / `--ed-*` 在子树重算；编辑器正文是 `color: inherit`（`c9251a458` 起，为了让导图节点决定字色），会一路继承到应用 `body` 的字色，也就是应用当前明暗的字色。导出预览的容器没设 `color`。
- 解法：用局部强制明暗时，**容器必须同时设正文色**（导图节点设 `textColor`，导出预览按主题设 `#fff` / `#000`）。验证时要读正文叶子节点的 computed `color`，不能只看根节点的 `data-mode`。
- 另：blog 的 `global.css` 给 `h1–h6` 设了 `color: var(--color-text-primary)`，标题不继承容器色；blog 目前没有局部强制明暗的场景，未改动。

### prettier 改写了往返基准夹具

- 现象：往返基准提交后，在**同一份提交**上重跑就有 1 处位置映射不一致（表格后一行文本的 `mdCh` 9 → 11）。
- 原因：lint-staged 对 `*.md` 跑 prettier，把夹具里的表格补齐成等宽列；快照是按格式化前的夹具生成的。
- 解法：`.prettierignore` 加 `**/__fixtures__/*.md`；在旧实现的临时 worktree 上用未格式化的夹具重新生成快照再拷回。教训：基准类快照提交后要在干净 checkout 上重跑一次。

### 服务 hook 与 kit 的循环引用

- 现象：把 `services/hooks.ts` 里的 `useRegistry` 写成 `const useRegistry = useCompatibleRegistry`（别名赋值）后，13 个用例报 `useRegistry is not a function`。
- 原因：`services/hooks.ts` → kit 兼容模块 → `kit/EditorKit.ts` → `extensions/index.ts` → 各扩展组件 → 回到 `services/hooks.ts`，成环。别名在模块初始化时求值，那一刻被引用的导出还是 undefined。
- 解法：①需要被服务 hook 依赖的部分（读注册表）单独放 `kit/providerBridge.ts`，**不引内置扩展**，从结构上断掉环；②跨环引用写成函数声明、调用时才取值，不要用别名赋值。
- 相关：提交「引入 EditorKit」。

### `git checkout -- <path>` 会连自己刚写的改动一起冲掉（第二次踩）

- 现象：脚本批量改错后想回滚脚本的改动，跑了 `git checkout -- apps/desktop/src`，把同一目录下手写的 kit / store / 入口改动也一起没了。
- 原因：这条命令按路径回滚，不区分改动是谁做的；下文已有同名条目，但当时没想起来。
- 解法：批量脚本跑之前先 `git add -A`（或 `git stash --keep-index`）把手写改动收进暂存区，回滚时用 `git checkout-index` / `git restore --worktree` 只回工作区；或者先提交手写部分再跑脚本。
- 相关：提交「desktop 宿主扩展收进 kit」。

### 按属性名批量删 JSX 属性会误伤同名的实例特有值

- 现象：写脚本删 `extensions={extensions}` / `extensions={dynamicExtensions}`，结果把闪卡填空、视频时间戳、项目卡片列表这些**实例特有**扩展的传参也删了——它们的变量恰好也叫 `extensions`。
- 原因：判断依据是属性名与变量名，不是值的来源。
- 解法：先解析出「本文件里直接取自 store 的标识符」（`const x = useDynamicExtensionsStore(...)`），只删值为这些标识符的属性；其余逐个人工判断。跨组件传递的部分另外单独处理。教训：透传清理的判据必须是数据来源，不是名字。
- 相关：提交「desktop 宿主扩展收进 kit」。

### 只覆盖服务的派生 kit 会让编辑器整个重建

- 现象：发起协作时正文明显抖一下（块组件重挂载），而换源逻辑本身是对的。
- 原因：`kit.extend({ services })` 里新建了 `ExtensionAssembly`，`assembly.plugins` 成了等价但全新的数组；内核创建 editor 的依赖里有它，于是重建。
- 解法：装配只取决于扩展集合——扩展集合没变时派生 kit 复用父 kit 的 assembly。给内核加依赖时要问一句「这个值在等价输入下是否保持同一个引用」。
- 相关：提交「派生 kit 复用装配」。

### 别名表在「升级后又降级」时会把当前 id 指回作废的 id

- 现象：一篇内容发起共享（本机 id → 服务器 id）后又结束共享（服务器 id → 同一个本机 id），此后用当前的本机 id 查会话，解析到的却是已经作废的服务器 id。
- 原因：两次换身份各写了一条别名，形成环。
- 解法：`rekeySession` 在写新别名前先 `aliases.delete(nextId)`；解析函数另外带跳数上限与已访问集合防环。
- 相关：提交「发起 / 结束共享改为会话升级与降级」。

### 会话换身份后，创建时捕获的 documentId 会把更新写错会话

- 现象（改造中发现，未流出）：`restore()` 里 `doc.on("update")` 的闭包捕获了创建时的 `info.id`，用于 `store.append` 与广播。会话升级换掉 documentId 之后，更新仍按旧 id 落盘与广播，渲染端收不到、本地缓存也写进了已删除的行。
- 解法：这类长生命周期闭包一律读 `session.info.id`（可变），不捕获创建时的值。IPC 侧同理。
- 相关：提交「发起 / 结束共享改为会话升级与降级」。

### 换源时换掉 localOrigin，本地编辑会静默不再写回 Y.Doc

- 现象：rebind 之后编辑器里输入的字显示正常，但 `flushLocal()` 后新文档的内容没有变化，旧文档也没有。改动凭空消失。
- 原因：slate-yjs 用 `ORIGIN` WeakMap 记最近一次 `withOrigin` 的 origin，`isLocal()` 拿它与 `editor.localOrigin` 比较。`withOrigin` 结束时会把 ORIGIN 恢复成调用前的值（也就是旧的 localOrigin），于是 connect 时的一次 hydrate 就让 ORIGIN 永久停在旧 origin 上。此时若把 `localOrigin` 换成新绑定的 origin，两者不再相等，本地操作不再进入 `LOCAL_CHANGES`，flush 也就没有东西可写。
- 解法：`localOrigin` 在编辑器生命周期内保持不变，rebind 让新绑定沿用它（`next.origin = target.localOrigin`）。undoManager 的 `trackedOrigins` 也用它，否则换源后撤销失效。
- 相关：提交「同谱系换源」。

### 用 onInit 判断「编辑器有没有重建」会得到错误结论

- 现象：断言 lineage 变化后编辑器重建，测试却报「是同一个 editor」。
- 原因：`onInit` 有 `isInit` 状态守卫，只在组件首次挂载时回调一次；编辑器实例换了但组件没卸载，它不会再触发，测试拿到的还是旧引用。
- 解法：测试经 `ref.current.getEditor()` 读当前实例。
- 相关：提交「同谱系换源」。

### 包内没有 tsconfig 时 vitest 不会用 automatic JSX

- 现象：editor-collab 新增的测试报 `React is not defined`，同目录下先前那个 JSX 测试却是好的。
- 原因：esbuild 的 JSX 模式读包内 tsconfig 的 `jsx` 字段。该包故意不放 tsconfig（类型检查随 desktop 的 `pnpm check`），先前那个测试恰好因为缓存没暴露问题。
- 解法：vitest 配置里显式写 `esbuild: { jsx: "automatic" }`。
- 相关：提交「同谱系换源」。

### 新包跑「渲染真实编辑器」的测试要借 editor 的依赖解析

- 现象：`packages/editor-collab` 里 `import { DndProvider } from "react-dnd"` 报 Failed to resolve import，随后又报 `ResizeObserver is not defined`。
- 原因：编辑器的重依赖（react-dnd、codemirror 等）装在 `packages/editor` 下，新包的 node_modules 里没有；协作光标的定位 hook 还要 ResizeObserver，jsdom 没有。
- 解法：vitest 配置加一个 `enforce: "pre"` 的 resolveId 插件，本包解析不到的裸包名改以 `packages/editor/src/index.ts` 为 importer 再解析一次；setup 文件转引 editor 的 setup 并补 ResizeObserver 桩。不要把这些依赖在新包里再声明一遍——版本会漂移，而 slate / react 必须是同一份实例。
- 相关：提交「建 @tau/editor-collab」。

### `git stash` 取基线时新包目录不会被收走

- 现象：为了确认某个 mobile 测试是不是既有失败，`git stash` 掉改动后重跑，报的却是 `Failed to resolve import "@slate-yjs/core"`——和要查的问题无关。
- 原因：`git stash` 默认不动未跟踪文件，新建的 `packages/editor-collab` 留在原地；而 node_modules 已经按改动后的 package.json 链接过了，于是得到一个半新半旧的状态。
- 解法：要取基线就用 `git worktree add /tmp/xxx HEAD` 另开一份干净检出，在那里 `pnpm install` 后再跑。
- 相关：提交「建 @tau/editor-collab」。

### 测试 mock 用 Proxy 会让 vitest 永久挂起

- 现象：想让 `vi.mock("@/services/editorKit", () => new Proxy({}, { get: () => () => ({}) }))` 对任意 kit 名都返回桩，结果该测试文件一直不结束。
- 原因：Proxy 对 `then` 也返回函数，vitest `await` 工厂返回值时把它当成 thenable，调用后永远等不到 resolve。
- 解法：显式列出导出。新增场景 kit 时同步更新各测试的 mock（目前 9 个文件）。
- 相关：提交「desktop kit 按场景拆分」。

### 触发器自己 toggle 的 Popover 迁移后点一下开了又关

- 现象：antd Popover 的触发元素上原本就有 `onClick={() => setOpen(!open)}`（受控）。迁到 `@tau/ui` 的 Popover 后，点击时它克隆注入的 onClick 先调调用方的 handler（翻成 true），再按自己看到的 `open` 翻一次（翻回 false）。
- 原因：`@tau/ui` 的 Popover 自己在触发器 click 上 toggle；antd 受控模式下触发器的 click 不会被 Popover 再处理一遍。
- 解法：触发器的 handler 只留 `stopPropagation`（挡住 Slate 把点击当成移动选区），开合交给 Popover。迁移时搜一下触发器上有没有 `setOpen(!` 之类的写法。
- 相关：批注 `Annotation`、列表 `ListItem` 圆点。

### 反向验证时 vitest 缓存让改坏的实现照样全绿

- 现象：临时把 `useSheetBackDismiss(open && …)` 改成 `false && …` 验证测试会失败，结果仍全部通过；新加的测试文件也一度没出现在总数里。
- 原因：vitest 复用了上一次的模块转换 / 结果缓存，没有重新读取刚改过的文件。
- 解法：反向验证一律 `npx vitest run --no-cache <文件>`，并用 `--reporter=verbose` 按用例名确认新测试真的跑了，不要只看总数。

### 用脚本批量改代码，用户看不到改了什么

- 现象：用 Python 脚本批量替换 import / 调用，工具输出只剩一行「改了几处」，用户无从审阅。
- 原因：脚本把改动藏在了执行里，而 Edit 工具的每处修改用户都能看到。
- 解法：改代码一律用 Edit 逐处修改；改动多时打开 diff 面板给用户看。脚本只用于只读的统计与探查。

### Tailwind 命名 group 隔离不了同名嵌套

- 现象：块外层加 `group/block`、手柄写 `group-hover/block:opacity-100`，鼠标放在高亮块里的某个段落上，高亮块和里面所有段落的手柄全亮。
- 原因：`group-hover/block` 编译为 `:where(.group\/block):hover *`，匹配的是「**任意**同名祖先被悬停」，不是最近的那个。命名只能区分不同名字的 group；块嵌套块时名字必然相同。
- 解法：用 CSS `@scope` 取最内层被悬停的块作根、嵌套块作下边界：`@scope (.ed-block:hover:not(:has(.ed-block:hover))) to (.ed-block) { [data-block-reveal] { opacity: 1 } }`，写在不分层的 `editor.css` 里以压过 utilities 层的 `opacity-0`。需要 Chromium 118+（Electron 43 满足）。
- 另：在页面里读 computed opacity 验证时要先注入 `*{transition:none!important}`，否则读到过渡起点的 0，会误以为规则没生效。
- 相关：`components/BlockDrag`、`theme/editor.css`。

### 新包里写 Tailwind 类，宿主不生成

- 现象：editor-webview 的 less 转成 Tailwind 类后，类名在 DOM 上，样式却不生效。
- 原因：Tailwind v4 只扫描入口 CSS 里 `@source` 列出的目录；四个宿主（desktop / mobile / blog / browser-extension）都只 `@source` 了 editor、shared、ui，没有 editor-webview。
- 解法：各宿主入口补 `@source .../packages/editor-webview/src`。以后新建含 Tailwind 类的包（P9 拆包时会有），同步检查四个宿主的 `@source`。
- 相关：`apps/desktop/src/tailwind.css`、`apps/mobile/src/styles.css`、`apps/blog/src/styles/global.css`、`apps/browser-extension/src/entrypoints/sidepanel/style.css`。

### 测试里整模块 mock `@tau/editor/src` 会漏掉新导出

- 现象：desktop `ProjectListSlate` 的导航测试报 `No "BLOCK_DRAG_GROUP" export is defined on the "@tau/editor/src" mock`。
- 原因：`vi.mock` 工厂只返回了 `AddParagraph` / `useDragAndDrop`，组件改用 `BlockDrag` 后读到的是 undefined。
- 解法：纯展示件用 `vi.importActual` 取真实实现并展开，只桩依赖编辑器上下文的部分。

### 共享工作区里 git add 是追加，commit 会带走整个暂存区

- 现象：只 `git add` 了自己的两个文件后 commit，提交里混进另一个并发会话的 3 个文件重命名——对方已 stage 未 commit，暂存区不是空的。
- 原因：`git add <path>` 只往暂存区追加；`git commit` 提交的是整个暂存区，不区分是谁暂存的。
- 解法：共享工作区里提交前必须先 `git diff --cached --name-only` 核对暂存区只有自己的文件。混入了就 `git reset --soft HEAD~1` + `git restore --staged <对方路径>`（新旧路径都要）后重新提交；对方的物理改动不受影响，重新 stage 即可。

### 子代理被打断后，以工作区为准逐文件核对

- 现象：并行的五个迁移子代理有三个没跑完（会话结束 / API 余额报错），没有任何汇报。
- 解法：不要假设它们做完或没做。用「仍 import 已删 less 的文件」「改过但残留 `styles.` 的文件」两条查询定位半成品，再逐个续做；tsc 能兜住 import 缺失，兜不住「less 删了但类名还是 `styles.xxx`（undefined）」，所以第二条必须查。

### 本机 node 版本回退让 Node 子进程测试与桌面构建静默变红

- 现象：`node-import.test.ts` 报 `ERR_UNKNOWN_FILE_EXTENSION: Unknown file extension ".ts"`；desktop `vite build` 在加载 `vite.config.mts` 时对 `@tau/themes` 报同样错误；`pi-sync-process.test.ts` 的子进程同样炸。全部在 HEAD 的干净 worktree 上复现——不是改动引入的。
- 原因：机器当前激活的 node 是 22.13.1（nvm4w），type stripping 在 22.6–23.5 需要 `--experimental-strip-types` 显式开启；之前会话记录里测试与构建通过时用的是 Node 24（默认开启）。
- 解法：子进程测试统一加 `--experimental-strip-types --no-warnings`；桌面构建用 `NODE_OPTIONS="--experimental-strip-types --max-old-space-size=8192"`（后者是主进程打包的堆）。环境类的既有失败先用 worktree 在 HEAD 上复现定性，再决定是修测试还是修环境。

### core.autocrlf 把往返基准夹具检成 CRLF

- 现象：`markdown-roundtrip-baseline.test.ts` 的 import mappings 快照差一处 `slateLength` 9 → 10；探查发现 blockquote 文本值是 `"引用一行\r\n引用两行"`，`\r` 进了文本节点。HEAD 上同样失败。
- 原因：仓库 `core.autocrlf=true`，夹具在索引里是 LF、工作区被检成 CRLF；mdast 的文本值会原样保留 `\r\n`（micromark 只在行尾结构处理上归一，不经 `\r` 剥离保证）。快照是 LF 夹具时生成的。
- 解法：基准测试读取夹具时 `.replace(/\r\n/g, "\n")` 统一 LF（夹具语义就是 LF）。教训：对换行敏感的快照测试，读入时显式归一，不要依赖 checkout 配置。

### 等价迁移的断言不能凭「应该是什么」写，要以 HEAD 实测为准

- 原因：旧实现 `delete` 后空文档先被 Slate 默认规范化补一个空段落，`insertNodes` 再插一个——注释描述与实际行为从来就不符，只是之前没有测试盯着。
- 解法：`git stash push -- <迁移涉及的路径>`（路径限定，共享工作区安全）收起改动，对 HEAD 跑同一场景确认旧行为也是 2 个，断言改成与 HEAD 一致；既有瑕疵不修（迁移零漂移），要修另立提交。
- 相关：define-extension.test.tsx callout 用例、extensions/callout/behaviors.ts

### 裸 editor + 单插件装配测不到 v2 的行为分发

- 现象：header 的旧插件单测 `plugin(createEditor())` 直接测改写后的方法；迁 v2 后同样的装配方式测不到任何东西（行为不再走插件链）。

- 解法：等价测试一律用真实 kit 挂载（`createEditorKit` + `<Editor>`，参考 define-extension.test.tsx 的 mount 模式），断言原样保留；后续扩展迁移照此办理。
- 相关：extensions/header/**tests**/ 两个迁移后的测试

### v2 行为 handler 里拿不到「原链实现」

- 现象：header「回车拆行、拆出的后半变段落」需要先执行默认 insertBreak 再 setNodes，行为 handler 里没有原链引用。

- 相关：extensions/header/behaviors.ts insertBreak
