## 2026-09-29 · P6.5 完成：desktop 宿主扩展收进 kit

一次提交。`getDesktopKit()` 自带宿主扩展，业务代码不再自行取 `useDynamicExtensionsStore`（明细与验收见 02 P6.5）。

- 分两档（ER-015，**当日即被推翻**，见上一条）：`getDesktopKit()` 带全部宿主扩展；`getDesktopFileKit()` 按 `BLOCKS_LOST_IN_MARKDOWN` 滤掉存不回 `.md` 的块。用户先裁决「全量统一」，随后指出 Markdown 文件不该支持白板 / 数据库；核对 codec 表确认这是正确性问题（`database` 无条目、`whiteboard` 只有 `isVoid` 没有 serializer，导出即丢数据），于是按存储边界切出第二档。
- 第一版把分类做成了 store 的第二个数组 `libraryBlockExtensions`，被用户质疑「为什么又多一个概念」后退回。问题有三个：装载器不该承担策略分类；名字说「库内块」而真实判据是「有没有 serializer」，名不对实；手抄了一份 codec 表已有的事实，加新扩展放错桶没人拦。改为 store 只管装载（单一 `extensions`），清单 `BLOCKS_LOST_IN_MARKDOWN` 放在执行它的 `editorKit.ts`，并加单测钉住判据——清单里每个类型在 `desktopMarkdownCodecs` 里都不能有 serializer。给白板临时加个 serializer 验证过该用例会失败。
- 也试过「按有无 serializer 自动过滤」，不成立：`inline-ai-assistant` 同样没有 codec 条目，但它是临时 UI 标记元素、没有内容要存，自动过滤会顺手砍掉内联 AI。所以这条策略只能明写，代价用自检单测补。
- 动态导入保留，并把原因写进了 store 的注释：一是白板 / 数据库会拉进整个白板引擎与数据库视图；二是静态引入会成环（`editorKit → editor-extensions → whiteboard → components/WhiteBoard → DOMSizeMeasurer → editorKit`），而 `new WhiteboardExtension()` 在模块初始化期求值，正是「服务 hook 与 kit 的循环引用」那条坑的同一形状。
- 加了装载守卫：`initialized` 为假时建 kit 直接抛错。kit 只建一次，少拿了扩展不会报错、整个应用静默少几种块——与 AGENTS.md 里 D-014 同一类失效，所以宁可响亮地失败。三个入口（`main.tsx`、showcase、协作 e2e）统一在渲染前 await；后两个此前根本没调用过 `initExtensions()`，showcase 的富文本档案因此一直缺宿主块，这次一并修掉。
- 前置调查漏了两类消费者，用 TS AST 全量扫描才找齐：7 个中间组件（`ContentSelector`、`AnswerModal` 等）声明 `extensions` prop 只为转手；`MentionPanel → List` 的 `extensions` 传到底却从未使用（死 prop）；还有第三个装载器 `hooks/useDynamicExtensions.ts`（只有闪卡参考编辑器在用，已随之删除）。教训：这类「prop 沿组件树透传」的清理不能只 grep JSX 属性，要连中间层一起查。
- 唯一一处判断错了又改回：`ImmersiveEditorMode` 不是纯转手，项目文档要通过它传实例特有的 `project-card-list`，prop 恢复为可选。是 `pnpm check` 报出来的。
- 行为变化（有意）：12 处此前没传扩展的编辑器现在带宿主扩展，其中 7 处可编辑（EditRecordModal、PdfEmbed 正文、日程备注、QuickTimeRecord、card-list CreateCard、白板 Geometry 文本、SkillEditView），会多出附件 / 白板 / 数据库的块面板入口与内容链接 / 内联 AI 的悬浮条；只读的 5 处无影响（这些贡献点在只读态不出现）。
- 基线新增 `desktop.hostExtensionConsumers`，钉住「业务代码不再读 store」，已清零。
- 验证：desktop 4167 例通过（新增 kit 单测 3 例），`pnpm check` 通过，`pnpm lint` 0 error，`vite build` 三个产物都通过且白板 / 数据库仍独立分块。
- 未验证：实机观感——含宿主块的编辑器要打开看块能否正常显示；那 7 处新获得宿主扩展的轻量编辑器是否顺眼。

## 踩坑

### 脚本批量改 CSS 结构会留下悬空括号

- 现象：用脚本删 `&.dark { ... }` 块时，嵌套规则的收尾 `}` 被留下，less 编译报「Unrecognised input」，两处。
- 原因：按行匹配的删除逻辑没有正确跟踪嵌套深度。
- 解法：批量只做「值替换」，删除结构块改用精确编辑；每批都跑一遍 less 编译检查（`/tmp/lesscheck.cjs` 那种一次性脚本即可）。

### 计算样式快照比对的假差异：CSS transition

- 现象：blog 迁移后 doc、article 两个页面深色快照与基线不一致，逐元素看是一部分文字颜色处于中间色（如 `rgb(214,221,227)`，目标是 `rgb(230,237,243)`）。
- 原因：页面元素带 `transition-colors`。基线采样时刚切到深色，颜色还在过渡中途；两次采样的时机不同，所以哈希不同。和改动无关。
- 解法：采样前注入 `*{transition:none!important;animation:none!important}`；并且先 `git stash` 掉改动，在同一个 dev server 上采集基线，再恢复改动采集对比，两次口径完全一致。

### 用正则处理数 MB 的构建 CSS 会卡死

- 现象：对 5 MB 的 sidepanel CSS 用 `[^{}]*\{\s*\}` 反复替换来删空规则，两次都超时（回溯爆炸）。
- 解法：改用仓库已有的 lightningcss（`transform` + `visitor` 删掉 `--tau-*` 声明）做结构化比对，几秒就能出结果。

### `@tau/themes/testing` 解析器最初把 `@import` 并进下一条规则

- 现象：desktop 覆盖测试里 paper · light 报 41 个词全部缺失。
- 原因：`tokens.css` 开头的 `@import "./scale.css";` 没有花括号，被规则正则当成下一个选择器的前缀，于是 `[data-theme="paper"][data-mode="light"]` 这个选择器没有登记上。
- 解法：先剥掉 `@xxx ...;` 语句再匹配规则，并补回归用例。

### Node 侧以包名导入 workspace 的 TS 源码包失败（已根治）

- 现象：`vite.config.*.mts` 里 `import { createThemeBootstrapScript } from "@tau/themes"` 启动报 `ERR_MODULE_NOT_FOUND: .../packages/themes/src/register`。
- 原因：vite 打包配置文件时把包名导入外置，交给 Node 原生 ESM 加载。Node 24 能对 workspace 符号链接（真实路径不在 node_modules 下）做 type stripping，但 ESM 不补扩展名，TS 源码里的 `./register` 找不到。
- 最初的绕法：配置里改用相对路径。用户要求根治，不绕。
- 解法：headless 包（Node 也要用的）遵守「Node 可直接加载」约束：
  1. 相对导入写 `.ts` 扩展名；
  2. tsconfig 开 `allowImportingTsExtensions`、`erasableSyntaxOnly`（禁 enum、namespace、参数属性等不可擦除语法）、`verbatimModuleSyntax`（类型导入必须写 `import type`）；
  3. 包内加 `node-import.test.ts`：子进程用 `node -e 'import("@tau/themes")'` 真实加载。已验证：把任一导入改回无扩展名，这个测试就会失败。
  - 消费方的 tsconfig 也要开 `allowImportingTsExtensions`（desktop、blog、mobile、extension、editor 早就开了，这次给 `@tau/ui` 补上）。
- 相关：P5 `@tau/markdown` 按同一约束建包，Electron 主进程和脚本就能直接以包名导入。约束写进了 01 §2。

### `git checkout -- <file>` 会冲掉未提交的改动

- 现象：验证 DOM 护栏时往 `bootstrap.ts` 追加一行，再用 `git checkout` 还原，结果 `./themes` → `./register` 的改动也一起丢了。
- 解法：还原临时探针要精确删除追加的那一行，不要用 `git checkout`。

### 手工 grep 统计漏掉 less 文件

- 现象：立项时手工统计旧 CSS 变量为 51 种，脚本统计为 62 种。
- 原因：手工用 `grep --include` 在 zsh 下展开失败，只扫到了 ts/tsx。
- 解法：统计一律用 `scripts/editor-refactor-baseline.mjs`，不再手工 grep。

### 升级共享的隐私边界依赖 Y.Doc gc

- 现象：S1 的对照用例显示，`new Y.Doc({ gc: false })` 时私有块旧数据会残留在编码状态里。
- 原因：Yjs 关闭 gc 后会保留已删除内容的结构和值。
- 解法：P7 正式实现时，主进程在升级前断言 `doc.gc === true`，或在发布前扫描编码内容，确认没有私有块数据。

### desktop 对 `@tau/themes` 的两处别名指向不一致（P1 前已存在）

- 现象：`apps/desktop/tsconfig.json` 把 `@tau/themes` 指向 `packages/themes/src`，`vite.config.mts` 却指向 `packages/themes`。
- 原因：历史上只用 `@tau/themes/light.less` 这类深路径，两边刚好都能解析。
- 解法：P1 删除手写别名，改为 workspace 依赖 + package `exports`。未验证：保留别名时 `@tau/themes/react` 这类子路径在 tsc 和 vite 下能否一致解析；直接删掉别名，就不用去验证了。

### 局部强制明暗只管 token，不管正文色

- 现象：内容导出预览选深色主题，代码块、行内代码是深色（正确），正文却是深色字，几乎看不见。
- 原因：`EditorThemeOverride` / 根节点的 `data-mode` 只让 `--tau-*` / `--ed-*` 在子树重算；编辑器正文是 `color: inherit`（`c9251a458` 起，为了让导图节点决定字色），会一路继承到应用 `body` 的字色，也就是应用当前明暗的字色。导出预览的容器没设 `color`。
- 解法：用局部强制明暗时，**容器必须同时设正文色**（导图节点设 `textColor`，导出预览按主题设 `#fff` / `#000`）。验证时要读正文叶子节点的 computed `color`，不能只看根节点的 `data-mode`。
- 另：blog 的 `global.css` 给 `h1–h6` 设了 `color: var(--color-text-primary)`，标题不继承容器色；blog 目前没有局部强制明暗的场景，未改动。

### prettier 改写了往返基准夹具

- 现象：往返基准提交后，在**同一份提交**上重跑就有 1 处位置映射不一致（表格后一行文本的 `mdCh` 9 → 11）。
- 原因：lint-staged 对 `*.md` 跑 prettier，把夹具里的表格补齐成等宽列；快照是按格式化前的夹具生成的。
- 解法：`.prettierignore` 加 `**/__fixtures__/*.md`；在旧实现的临时 worktree 上用未格式化的夹具重新生成快照再拷回。教训：基准类快照提交后要在干净 checkout 上重跑一次。

### 服务 hook 与 kit 的循环引用

- 现象：把 `services/hooks.ts` 里的 `useRegistry` 写成 `const useRegistry = useCompatibleRegistry`（别名赋值）后，13 个用例报 `useRegistry is not a function`。
- 原因：`services/hooks.ts` → kit 兼容模块 → `kit/EditorKit.ts` → `extensions/index.ts` → 各扩展组件 → 回到 `services/hooks.ts`，成环。别名在模块初始化时求值，那一刻被引用的导出还是 undefined。
- 解法：①需要被服务 hook 依赖的部分（读注册表）单独放 `kit/providerBridge.ts`，**不引内置扩展**，从结构上断掉环；②跨环引用写成函数声明、调用时才取值，不要用别名赋值。
- 相关：提交「引入 EditorKit」。

### `git checkout -- <path>` 会连自己刚写的改动一起冲掉（第二次踩）

- 现象：脚本批量改错后想回滚脚本的改动，跑了 `git checkout -- apps/desktop/src`，把同一目录下手写的 kit / store / 入口改动也一起没了。
- 原因：这条命令按路径回滚，不区分改动是谁做的；下文已有同名条目，但当时没想起来。
- 解法：批量脚本跑之前先 `git add -A`（或 `git stash --keep-index`）把手写改动收进暂存区，回滚时用 `git checkout-index` / `git restore --worktree` 只回工作区；或者先提交手写部分再跑脚本。
- 相关：提交「desktop 宿主扩展收进 kit」。

### 按属性名批量删 JSX 属性会误伤同名的实例特有值

- 现象：写脚本删 `extensions={extensions}` / `extensions={dynamicExtensions}`，结果把闪卡填空、视频时间戳、项目卡片列表这些**实例特有**扩展的传参也删了——它们的变量恰好也叫 `extensions`。
- 原因：判断依据是属性名与变量名，不是值的来源。
- 解法：先解析出「本文件里直接取自 store 的标识符」（`const x = useDynamicExtensionsStore(...)`），只删值为这些标识符的属性；其余逐个人工判断。跨组件传递的部分另外单独处理。教训：透传清理的判据必须是数据来源，不是名字。
- 相关：提交「desktop 宿主扩展收进 kit」。

### 测试 mock 用 Proxy 会让 vitest 永久挂起

- 现象：想让 `vi.mock("@/services/editorKit", () => new Proxy({}, { get: () => () => ({}) }))` 对任意 kit 名都返回桩，结果该测试文件一直不结束。
- 原因：Proxy 对 `then` 也返回函数，vitest `await` 工厂返回值时把它当成 thenable，调用后永远等不到 resolve。
- 解法：显式列出导出。新增场景 kit 时同步更新各测试的 mock（目前 9 个文件）。
- 相关：提交「desktop kit 按场景拆分」。
