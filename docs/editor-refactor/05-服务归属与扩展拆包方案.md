# 服务归属与扩展拆包方案

日期：2026-09-30。代码基线：`ceb8b8045983fb37af948bf06db5fecb956482f3`。
状态：建议方案，供评审；本文不代表下列 API、包和服务已经实现。

## 1. 当前结论与本次范围

当前 P9 已拆出 custom-block 和五种图表，四端接线、headless codec、依赖护栏均已落地。剩余问题是服务契约和部分领域逻辑仍归 editor：实现目录迁出，不代表职责已经全部迁出。

后续目标是让 `@tau/editor` 只提供装配、行为/命令分发、错误隔离、未知节点保护、文档绑定、导航/拖拽/菜单挂载和服务作用域。具体元素、渲染/编译实现、领域服务、插入和类型转换规则由相应模块持有。

边界保持：

- 只使用现有 v2 扩展体系，不恢复 Base / IExtension / fromLegacyExtension。
- 不恢复 chart、graphviz、multi-column、inline-ai-assistant 或代码块全屏。
- custom-block 保留文档内 JS 执行；不引入沙箱、市场、第三方加载或远期生命周期 API。
- 不改文档 type、字段名、已有命令 ID、Markdown 语法和位置映射。
- 场景扩展覆盖、嵌套继承、服务覆盖、实例稳定性、协作换源与未知节点保护保持原有行为。
- agent 负责代码与自动化检查；视觉和实机确认由用户完成。

## 2. 编译链路的实际归属

| 消费者                        | 当前执行链路                     | 是否消费 ICompilerService | 后续归属                                        |
| ----------------------------- | -------------------------------- | ------------------------- | ----------------------------------------------- |
| TikZ                          | 包内 tikzjax / WASM              | 否                        | editor-diagram 的本地渲染实现，无需虚构宿主服务 |
| Mermaid                       | 包内 mermaid                     | 否                        | editor-diagram                                  |
| ABC                           | 包内 abcjs                       | 否                        | editor-diagram                                  |
| PlantUML                      | 编码后生成服务器图片地址         | 否                        | editor-diagram 的参数与渲染实现                 |
| Typst                         | desktop 主进程，浏览器扩展经 RPC | 是：typst                 | editor-diagram 的编译契约，宿主提供实现         |
| custom-block JSX / JS         | 包内 Babel 编译并执行            | 否                        | editor-custom-block/runtime                     |
| custom-block 样式             | 宿主生成 Tailwind CSS            | 是：tailwindRuntime       | 共用运行时样式契约                              |
| html-block / html-inline 样式 | 宿主生成 Tailwind CSS            | 是：tailwindRuntime       | 同一共用样式契约，HTML 扩展消费                 |

`CompilerService { typst, tailwindRuntime }` 混合了不同输入、输出、消费者和平台支持情况，应拆除。Typst 返回当前渲染器消费的 HTML；不能继续用“SVG 或 PDF”这类与实际调用不符的注释定义契约。

样式链路还有一个明确缺口：`useTailwindRuntimeCss(content, extension, service)` 接受 `extension`，却不把它传入服务；desktop 的实现统一使用 `tsx`。新契约应显式携带 `html | tsx`，迁移时先验证同一源码的 CSS 输出，再改变调用，不能将参数补齐当作无行为变化的搬运。

## 3. 服务体系：保留机制，重新归属契约

### 3.1 内核保留什么

以下职责已经服务于内核本身，应保留：

- ServiceRegistry：获取、可选获取、延迟实例化、实例缓存、循环依赖检测、父子作用域。
- EditorKit 的服务注入与 `kit.extend({ services })`；仅覆盖服务时复用 assembly，避免重建 editor。
- React 的 `useService/useOptionalService` 与非 React 的 `editor.getService/tryGetService`。
- ThemeService、EditorNotifier、ExtensionErrorReporter：内核直接消费的能力。

不把 registry 扩大为插件启动器、对象生命周期容器或自动依赖重算系统。

### 3.2 契约归属表

| 当前项                                       | 建议归属                    | 处理方式                                               |
| -------------------------------------------- | --------------------------- | ------------------------------------------------------ |
| ServiceIdentifier / createServiceId          | 纯服务契约入口              | 与 React、Editor、具体 token 分离                      |
| ICompilerService.typst                       | editor-diagram/services     | 独立 TypstCompiler token 与类型                        |
| ICompilerService.tailwindRuntime             | 共用宿主样式契约            | custom-block、HTML 与导出消费同一语义                  |
| IResourceService                             | 共用宿主资源契约            | 保留上传/解析语义，collab 可覆盖实现                   |
| IFileService                                 | 共用宿主文件契约            | 选择/读取/宿主路径能力；basename 回到纯工具            |
| IOpenerService                               | 共用宿主打开链接契约        | link 等扩展消费，内核不解释链接业务                    |
| IMediaInsertSources / IVideoContentProviders | editor-media/services       | 插入来源、平台视频接管归媒体领域                       |
| IMediaActions / IMediaSelectors              | editor-media/services       | 有内容操作与素材选择归媒体领域                         |
| IEditorSlots                                 | editor-media 的媒体插槽契约 | 当前只有 Image / Video / Audio，不冒充通用 Editor 插槽 |

服务契约由定义语义的模块持有，宿主注册具体实现，editor 负责当前实例的服务作用域。媒体扩展迁出时，`mediaInsert.ts`、媒体弹窗、上传 hook 和默认媒体插槽也要调查并一起归属，不能保留为内核里的隐形媒体层。

### 3.3 共用契约放在哪里

三个选择：

| 方案                     | 成本与问题                                                     | 建议                         |
| ------------------------ | -------------------------------------------------------------- | ---------------------------- |
| 全部继续放 editor        | 改动最小，但核心继续拥有 Typst、Tailwind、媒体等知识           | 仅作为现有迁移起点           |
| 一个小的 shared 纯子入口 | 不新增包，已有多个真实消费者；必须避开 shared 根入口的 UI 依赖 | 当前推荐                     |
| 新建通用服务/平台包      | 物理边界更强，但当前会增加包与出口维护成本                     | 有独立使用或发布需求后再评估 |

推荐在既有 `@tau/shared` 增加职责清楚的纯子入口，如 `service-contract`、`runtime-style`、`resource-capabilities`、`file-capabilities`、`opener-capability`。这里只放协议、token 和极小的标识符工厂，不放 Electron/Tauri/RPC 实现，也不通过 shared 根入口转出。

`@tau/contracts` 当前承担跨端命令/RPC channel，不把编辑器 DI 和各种宿主接口塞进这个包。既有 RPC wire 名称也不因为服务 token 改名而变化。

文件/资源接口当前使用浏览器 File 类型。迁移归属时保留该类型和调用语义；这些是浏览器适配契约，不伪称为无 DOM 类型的纯数据模型。DI 标识符、文本编译与 codec 则必须通过不含 DOM 的类型检查。所有纯契约入口在运行时都不得加载 React/DOM 实现。

### 3.4 headless 服务入口与依赖方向

目前 `@tau/editor/api` 重导出预览容器及其他 React 代码。将 token 搬到外包、再从此入口导入 `createServiceId`，仍可能把 UI 带进宿主契约入口。

建议新增 `@tau/editor/api/services`，只导出纯 ServiceIdentifier、createServiceId 和 registry 所需的类型；实际纯定义可来自 shared 的 service-contract。registry 实现仍属于 editor，通用宿主契约不依赖 editor。

依赖关系：

```text
宿主 → 扩展 /services → 纯服务契约
扩展渲染代码 → editor/api + 扩展 /services
editor 的 registry → 纯服务标识符定义
editor 不引用扩展 token 或领域接口
纯服务契约不引用 editor 或 shared 根入口
```

这是新增公开子入口的建议，需要同步调整当前“仅允许 editor/api”的护栏，并记录对 ER-008/ER-020 的补充；不是允许扩展深引 src。

### 3.5 编译契约建议

以下为设计示意，不是当前可直接调用的 API：

```ts
interface TypstCompiler {
  compile(code: string): Promise<string>; // 返回当前渲染协议需要的 HTML
}

interface RuntimeStyleCompiler {
  compile(request: { source: string; language: "html" | "tsx" }): Promise<string>; // 返回 CSS
}
```

TypstCompiler 的 token 属于 diagram；RuntimeStyleCompiler 的 token 属于共用样式契约。统一使用有命名空间的 ID，例如 `tau.diagram.typst-compiler` 与 `tau.host.runtime-style-compiler`。

宿主支持什么就注册什么。不支持 Typst 时不注册该 token，扩展保留已有缓存/不支持提示；不支持运行时 CSS 时样式消费者降级为空 CSS，custom-block 的 JS 能力仍可使用。真实编译失败与“能力未注册”分开处理，不为凑齐大接口注册假实现。

永久不支持与暂时不可用分开：浏览器 RPC 暂时未连接、服务正在初始化等情况通过现有服务返回状态/错误，不随连接状态反复增删 token、创建新 Kit。服务集合按场景确定，瞬时可用性由实现表达。

### 3.6 registry 需要明确的行为边界

- 当前同层重复注册 ID 会覆盖。首先使用命名空间并调查实际覆盖调用；保留有意覆盖，不在搬运中直接改成抛错。必要时后续引入显式 override，单独提交。
- 函数注册值当前被解释为工厂。服务能力用对象承载，避免将普通函数误作工厂；不急于增加新的注册 DSL。
- 子级覆盖 B 不会重新求值父级已经创建、依赖 B 的 A。维持当前词义和测试；需要子级依赖关系时在子级显式注册 A，不暗改父子作用域。
- token 被定义不代表每个 Kit 必须注册。必选/可选由具体消费者及场景决定，纯文本 Kit 不应为了通过检查注册编译或媒体服务。

终态所有具体内容元素都离开核心，包括 paragraph；不是一个元素对应一个包。

## 5. 源码预览与代码块必须分清

当前代码块的主要编辑实现是 textarea＋Shiki overlay；CodeMirror 5 由 PreviewWithEditor 及 editor 根入口的 mode/CSS 导入承担。不能把拆代码块误写成“把 CodeMirror 搬到 code-block”，也不在拆包中统一两套输入器。

source-view 首先原样接管 PreviewWithEditor。diagram、custom-block、HTML 和块级公式消费它；code-block 保持自己的 overlay、控制器与更新逻辑。

内核保留泛化的块导航、命令分发、焦点和插入机制。source-view 通过最小公开 API 注册内部输入器的起止焦点、触发相邻块导航；可以按实际需要公开现有 registerBlockNavigation / focusPreviousBlock / focusNextBlock 等窄能力，不重导出整个 utils 或内部 store。

预览“编辑/全屏”命令与动作注册表归 source-view。宿主只组合一次预览贡献扩展，避免多个使用方重复注册同一命令 ID。source-view 不 import 业务扩展，也不由核心反向 import。

完成全部消费者迁移后删除核心 PreviewWithEditor 实现和 API 转出；需要调整 ER-020。source-view 的预览全屏保持原有能力，已删除的代码块全屏不恢复。

## 6. 内核中的隐性领域逻辑

迁移目录时必须调查并归属以下文件，不能仅看 extensions 下的目录：

| 当前位置                      | 已发现的领域知识                       | 后续处理                                                     |
| ----------------------------- | -------------------------------------- | ------------------------------------------------------------ |
| utils/insertElement.ts        | 插入、段落替换、链接/公式/下划线等包裹 | 具体动词迁扩展；泛插入机制与段落规则分离                     |
| utils/element.ts              | 按具体 type 判断空态、行内性           | 优先消费已注册的 kind/isVoid/isEmpty；领域判断迁包           |
| utils/table.ts                | 网格、行列、单元格导航                 | 随 table 迁出                                                |
| plugins/withNormalizedCopy.ts | 列表项、表格等复制片段修复             | 框架保留遍历/隔离，类型修复由实际拥有方贡献                  |
| menu/defaultMenu.tsx          | 转换源名单、容器类别、目标集合         | 通用移动/剪切/复制/删除留机制；转换菜单和行为迁基础/容器模块 |
| types/custom-element.ts       | BuiltinElementMap 的完整具体类型名单   | 各包自增强登记；核心不进口各扩展类型                         |
| components/FormattedText      | 具体标记渲染与调色                     | 基础模块接管渲染策略，核心保留 leaf 属性/子树组合与保护      |
| kit/EditorKit.ts              | 默认补齐 startExtensions               | 最终改为宿主显式组合，不能反向 import editor-basic           |
| editor 根 CSS/mode 入口       | CodeMirror 全量导入与元素专属样式      | 模式/CSS 归实际包；保留变量名与既有视觉                      |

内核里仍需要创建空段落、识别退出/可编辑落点等行为时，应由 Kit 提供当前文档 schema 的具体规则。不能将 `type === "paragraph"` 改成另一份集中名单后宣称类型知识已经消除。

## 7. 最小 API 补充策略

现有 behaviors / commands / menu / drag / ingest / isEmpty / 文档 binding 可以表达的行为继续使用，不增加平行协议。

以下仅为通过当前消费者调查确定的候选缺口，实施时逐项用真实扩展证明：

- headless 服务标识符公开入口，避免 /services 引入 UI。
- 源码输入器的块导航/焦点注册，替代深引内核 controller/store。
- 文档 schema 的默认可编辑块创建规则，替代内核固定创建 paragraph。
- 复制片段的规范化贡献：已有 normalize 行为是否足够，先用列表/表格验证；不足才补遍历与隔离明确的小接口。
- leaf/标记渲染贡献：当前 v2 只有元素 render，迁 FormattedText 前需要真实标记的组合点，保留 Slate attributes、children、未知标记数据和错误隔离。

候选 API 不先一次性实现。类型空态已经有 isEmpty，不能再创建一个意思相同的通用能力。新增协议需说明真实消费者、错误回退、覆盖顺序、实例稳定性和至少一个反向验证；远期 activate/dispose 等仍不实现。

## 8. 渐进实施批次

| 批次               | 交付                                                             | 退出条件                                                                                 |
| ------------------ | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 服务与 HTML        | 纯 DI/共用样式入口、Typst 独立契约、两种 HTML 拆包、宿主注册迁移 | ICompilerService 无消费者后删除；跨端缺能力降级与 CSS 输出回归通过                       |
| 源码视图与代码块   | source-view、code-block、预览贡献组合与重依赖迁移                | 内核不再 import CodeMirror / Shiki / magic-move 或深引控制器，源码键盘/焦点与 codec 通过 |
| 数学与表情         | math、emoji 及 shared 的相关消费边界                             | 根与实际运行时加载图不再把已迁重依赖带回内核                                             |
| 媒体               | 五类元素、媒体契约、插槽、ingest、媒体 UI 与宿主适配             | 上传异步路径、取消/失败/目标删除、多文件、服务覆盖与 codec 通过                          |
| 基础领域与核心收口 | basic/list/table/containers、leaf/schema/复制贡献，显式 Kit      | 核心没有具体类型注册/判定名单、默认元素导入或领域转换；四端场景快照一致                  |

每个批次内部保持“小机制补充 → 单包试点 → 宿主接线 → 回归 → 清旧入口”的顺序，可形成多个独立提交。不在首批跨越所有包；列表、表格和基础标记承担跨节点语义，必须分别验证。

当前 createEditorKit 会自动注入剩余内置扩展。迁移中不得直接切为空集合，使旧调用点静默少能力。先调查并迁完 createEditorKit / createBareEditorKit / createEditorKitFromRegistry 及所有中间场景工厂；最后一个批次才删除自动补齐。前后同一用途的 elementTypes 与 codec 覆盖由快照和 parity 测试担保。

## 9. 每个包的标准迁移单

1. 调查渲染、行为、命令、快捷键、插入、类型、服务、codec、CSS、依赖、全部消费者与宿主适配。
2. 记录迁移前的场景类型集合、插入菜单、命令顺序、Markdown/位置映射样本和模块加载图；数字按包迁移后的总集合对账，不用旧包测试数硬断言。
3. 将公开类型与 /markdown、/services 分离，带 .ts 相对扩展名；需要的 UI 继续用 @tau/ui，运行时单例由宿主提供。
4. 补最小公开机制并验证，再迁实现；不加入 src 深路径白名单。
5. 四端按原场景组装稳定实例，检查嵌套、服务覆盖、协作派生与组件外测高。
6. 宿主只合成一次 codec，desktop 主进程与渲染端共用；样式扫描新包。涉及 mobile 自建浮层时接统一返回仲裁，不引入新的业务返回监听。
7. 消费者清零后删除旧入口、实现、重导出、依赖与锁文件冗余；不能用 shim 把迁走的渲染器重新接回内核。
8. 完成相应代码检查和文档更新后提交；保留原工作区隔离约束，不合并或推送。

## 10. 代码验收门

### 依赖与 headless

- 两道图检查：工作区 dependencies/peerDependencies 与实际打包模块图；仅 package.json 清理不算完成。
- 核心不得引用扩展根入口、实现、renderer 或扩展类型；shared 不能反向引用 editor/扩展包来恢复默认功能。
- 核心机制允许的 API 与纯服务入口列为明确清单，深路径禁止；反向放入一次非法 import，确认护栏失败。
- codec、纯类型、DI 和编译契约分别在 Node 子进程加载，拒绝 React、DOM 和重渲染器；DI/文本编译入口做无 DOM 类型检查。
- Node 只加载 codec 不应初始化 SourceEditor、CSS、renderer、编译 worker 或宿主 IPC。

### 行为与稳定性

- 原场景 type/codec 集合、嵌套 Kit 继承、服务覆盖、同参缓存与 editor 实例稳定性。
- 缺失可选服务：显示明确已有降级，不熔断整个编辑器，不丢失缓存或内容；真实服务失败按当前反馈语义处理。
- 源码：编辑回写、外部内容更新、代码焦点、跨块移动、空态删除、退出保存；保留代码块现有 diff/高亮行行为。
- 媒体：pathRef/uuid 异步定位、失败与取消、删除目标、多文件、行内/块级落位。
- 基础：列表缩进与换行、表格跨单元格删除保护、容器退出、类型转换、叶标记组合和复制修复。
- 未知节点无损与协作换源：原有完整测试保持，特别是光标发送开关、节点缓存失效、剪切失败保护。
- Markdown 普通和带位置两个方向往返，宿主往返快照不漂移；做关键路径的反向验证。
