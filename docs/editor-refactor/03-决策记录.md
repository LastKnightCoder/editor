## ER-001 内核只放机制，内置扩展与第三方同一套 API（2026-09-28，已定）

2026-09-30 修订：下方“不含具体元素类型”的绝对限制由 ER-026 修正，paragraph 与文本作为核心基础模型；内外扩展使用同一公开 API 的原则继续有效。旧结论保留用于追溯。

- 结论：`@tau/editor` 内核不含具体元素类型；内置扩展只能用公开 API，不许走后门。
- 依据：内置扩展能不能只靠公开 API 写出来，是检验 API 是否够用的唯一可靠办法；custom-block 能否干净拆包作为验收标准（P9）。
- 排除：「内核带一组基础元素、第三方用另一套 API」——两套 API 会让第三方 API 长期不够用。
- 例外：见 ER-005 受信任层。

## ER-002 主题契约下沉到 `@tau/themes`，所有平台统一 `--tau-*`（2026-09-28，已定）

- 结论：token 词汇表、`defineTheme`、内置主题、tokens.css 放进纯数据包 `@tau/themes`；desktop、mobile、blog、browser-extension 都注入 `--tau-*`。
- 依据：Editor 要只依赖契约，就必须每个宿主都提供同一套契约；否则 Editor 得给每个平台写兜底。用户确认统一接入。
- 排除：Editor 直接依赖 `@tau/ui`——组件库属于宿主，依赖方向会再次反掉。

## ER-003 Token 是 API，类名不是 API（2026-09-28，已定）

- 结论：主题定制、插件取色只通过 `--tau-*`、`--ed-*` 和 ThemeService；删除宿主传入 Tailwind 类名的 `ThemeColors` 机制。
- 依据：类名一旦被外部覆盖就成了事实 API，组件改结构就破坏主题（Obsidian CSS 片段的常见问题）。
- 排除：保留 `ThemeColors` 作为兼容——它正是依赖反向的来源。

## ER-004 删除 EditorProvider，改为显式 EditorKit（2026-09-28，已定）

- 结论：宿主用 `createEditorKit()` 创建一次，作为 `<Editor kit>` 传入；嵌套编辑器用内核私有 Context 继承；`EditorConfig` 字段拆到服务或扩展参数（字段去向见 01 §4）。
- 依据：Provider 的隐式继承让「这个编辑器到底由什么组成」不可见；config 是杂物袋，互不相关的设置耦合在一起。
- 排除：保留 Provider 只精简字段——宿主根上包一层的用法和隐式继承问题仍在。

## ER-005 原始 Slate plugin 作为受信任层保留，不进公开 API（2026-09-28，已定）

- 结论：`plugins: (editor) => editor` 保留给内核内置扩展（列表、表格、协作等跨节点逻辑），类型上标 `@internal`；公开 API 只暴露声明式 `behaviors`。
- 依据：部分能力声明式表达不了；但把 monkeypatch 能力开放给第三方会冻结内部实现，并且没法做错误隔离。
- 排除：完全去掉原始 plugin（做不到）；向第三方开放原始 plugin（不可隔离）。

## ER-006 未知节点必须无损往返（2026-09-28，已定）

- 结论：扩展缺失或加载失败时，节点渲染为只读占位，序列化原样保留。
- 依据：文档寿命比插件长；插件停用导致内容丢失是不可接受的。
- 渲染层（P8 落地）：kit 没注册的 type 按 void 处理、整棵子树不参与规范化，渲染为只读占位；行内 / 块级按所在位置判断（父元素含文本子节点即行内）。内容以 JSON 存库，所以渲染层不动它就不会丢。
- Markdown 兜底语法（2026-09-29 定稿，取代待定项 ER-P3）：触发条件是「该 type 没有 Markdown codec」，与 kit 有没有渲染器无关——`@tau/markdown` 是 headless 的，主进程也在用，它只知道 codec。整节点（含 children）原样存 JSON，导入时还原：
  - 块级：`:::tau-node{type="x"}` 容器内一段 `json` 代码围栏；JSON 里有反引号串时围栏自动加长。
  - 行内（代码围栏放不下）：`:tau-node[正文]{type="x" json="…"}`，方括号里的正文只供阅读，还原以 json 为准。
  - 代价（已知并接受）：有渲染器但没有 codec 的类型（tabs、分栏、comment、graphviz、白板、数据库等）在 `.md`、全文索引、AI 上下文里从「只剩正文」或「空」变成一段 JSON；换来的是 Markdown 文件保存它们不再丢内容。补上 codec 的类型自动退出兜底。
  - 排除：①子节点照常序列化、属性放 base64 属性——用户选了 JSON 围栏；②HTML 注释包裹——与 html-block 导入纠缠；③只兜底「编辑器也不认识」的类型——headless 层拿不到 kit 的注册信息。

## ER-007 custom-block 保留文档内执行 JS，暂不做沙箱（2026-09-28，已定）

- 结论：维持现有「模板里写 JS、主进程内编译执行」的能力；沙箱（iframe/worker）放到远期。
- 依据：用户确认先保留能力、安全后续考虑。
- 约束：P3 / P8 改造 custom-block 时不要引入会阻碍将来放进 iframe 的设计。例如模板与宿主的交互只经 `components` / `hooks` 注入对象，不让模板直接拿到宿主全局对象。

## ER-008 第三方插件本期只做内部模块化（2026-09-28，已定）

- 结论：本期不做第三方加载和市场；公开 API 以 `id + apiVersion` 标识，单一入口 `@tau/editor/api`，为将来开放预留（01 §5.4）。
- 依据：用户确认后做，但要求将来开放时不大改。

## ER-009 协作拆为「文档源」与「协作扩展」，并纳入本次重构（2026-09-28，已定）

- 结论：内核新增 `EditorDocument` 概念（普通值 / Yjs 两种实现），协作光标、私有块占位、共享资源服务放进 `@tau/editor-collab`；内核不再依赖 yjs。desktop 发起共享改为升级本机会话、复用同一个 Y.Doc；内核支持同谱系文档源无缝切换。详见 01 §7。
- 依据：闪烁的根因是「换同步方式」被实现成了「换文档」（documentId 变、binding 置空、`<Editor key>` 重建）。协作改变的是内容的事实来源和撤销历史，比普通扩展更底层，不能只当作 UI 扩展处理。用户要求和本次重构一起解决。
- 排除：①只把 `collaboration` prop 包装成扩展——换源时仍要重建编辑器，不解决闪烁；②保留 key 重建，只用快照占位掩盖——块组件仍会重新挂载，mermaid、codemirror 状态丢失。
- 风险：slate-yjs 的 sharedRoot 重绑、升级时私有块数据的隐私边界，P0 spike 先验证；验证不通过就修订本条。

## ER-010 Markdown 合并为 headless 的 `@tau/markdown`（2026-09-28，已定）

- 结论：三份 Markdown 实现合并为一份，保留源码 ↔ 富文本双向位置映射作为框架能力；包内禁止 DOM，由 tsconfig lib、node 测试环境、ESLint 三道机制强制。codec 按扩展归属，但写在扩展的独立纯函数文件里。详见 01 §8。
- 依据：Electron 主进程（web-clip、search-core）和 MCP 在用 Markdown 导入导出；三份实现已经出现能力分叉（位置映射只在 desktop，`ImportFromMarkdownOptions` 只在 editor）。

## ER-011 主题整体迁入 `@tau/themes`，不保留 `@tau/ui/theme` 转出层（2026-09-28，已定）

- 结论：`packages/ui/src/theme/` 全部迁到 `@tau/themes`，按依赖分为根入口（纯数据 + 纯函数，含首帧脚本生成）、`/dom`、`/react`、`/tokens.css`、`/tailwind.css`。P1 已落地。使用方直接从 `@tau/themes` 导入，`@tau/ui` 删除全部 theme exports，ESLint 禁止旧路径。
- 依据：用户要求彻底迁移，不做没有实际作用的中间层。转出层会让「主题归谁」出现两个答案，后续也总有人从旧路径导入。
- 排除：①`@tau/ui/theme` 从 `@tau/themes` 转出以保证 desktop 零改动——多出一层没有意义；②运行时代码留在 `@tau/ui`——mobile、blog 为了用主题运行时就得依赖整个组件库。
- 取代：待定项 ER-P1。

## ER-012 P2 各平台以「桥接」接入 `--tau-*`，外观不变（2026-09-28，已定）

- 结论：mobile / blog / browser-extension 保留自己的主题、变量与运行时，在各自的 `tau-tokens.css` 里把 `--tau-*` 全键映射到现有变量；运行时补写 `data-mode`；覆盖测试逐套主题检查全键齐全。自带主题的宿主只引 `@tau/themes/scale.css`，不引主题数据块。
- 依据：P2 的目标是让 Editor 只依赖 `--tau-*`，不是统一各平台的视觉。mobile 有 1714 处自有语义类，而且与 `@tau/themes` 的 page / surface / accent 等类名重名，一起统一的风险和工作量都与本次重构无关。用户选定。
- 排除：①三个平台全面改用 `@tau/themes` 主题族——外观会变，mobile 类名冲突要同时处理，另立迭代再说；②混合（mobile 桥接、blog/扩展改用主题族）——blog 与扩展的外观也会变。
- 后续：各平台是否改用 `@tau/themes` 主题族，另行决定，不在本次重构范围内。

## ER-013 `--ed-*` 组件 token 清单与 isDark 的保留边界（2026-09-28，已定）

- 结论：编辑器组件 token 共 58 个（`packages/editor/src/theme/editor.css`）：文字 4、表面 6、描边 3、强调 5、状态 8、浮层 3、排版 1、选中 1、标签 1、下划线 1、批注 4、代码块 6、callout 15。全部从 `--tau-*` 派生，主题作者可覆盖。
- 结论：`isDark` 保留两类用法，不追求清零——①用户自选色的明暗变体（内容数据）；②第三方渲染器的主题入参。需要具体色值的渲染器改从 `ThemeService.token()` 读。
- 依据：把用户选的「红色文字」也说成主题耦合会改变语义；第三方渲染器要的是色值或自己的主题名，CSS 变量传不进去。
- 取代：待定项 ER-P2。

## ER-014 局部强制明暗用 `<EditorThemeOverride>`，不在 `<Editor>` 上设 prop（2026-09-29，已定）

- 结论：删除 `<Editor theme>`。需要让编辑器按固定明暗渲染的地方（深底的思维导图节点、导出预览等），宿主用 `<EditorThemeOverride mode>` 包住编辑器；它提供一个「固定明暗、其余沿用外层」的 ThemeService。编辑器发现生效明暗与 `<html>` 不同时，在根节点补 `data-theme` + `data-mode`，让 `--tau-*` 数据块在子树重算。`mode` 缺省时不覆盖，嵌套编辑器经同一个 Context 继承。
- 依据：明暗只有 ThemeService 一个来源（01 §4 字段表）。25 处 `theme` prop 里 20 处传的就是全局明暗，属于冗余；剩下 5 处是「这块区域的背景是深色」，属于宿主的布局语义，用包裹组件表达比每个编辑器各传一个 prop 更贴切，也覆盖了编辑器内部的嵌套编辑器。
- 排除：①保留 `<Editor theme>`，内部转成服务——明暗又有了两个入口；②让宿主为每个局部区域注册子注册表覆盖 `IThemeService`——写法太重，5 处都要 `createChildRegistry` 加 Provider。

## ER-015 desktop 的 kit 分两档，边界是「能不能存回 Markdown」（2026-09-29，已推翻）

- 原结论：`getDesktopKit()` 给库内内容带全部宿主扩展，`getDesktopFileKit()` 给 Markdown 文件编辑、不含白板与数据库块（清单 `BLOCKS_LOST_IN_MARKDOWN`，判据有单测自检）。
- 推翻原因（2026-09-29，同日）：机制错了。「白板 / 数据库存不回 `.md`」是**插入入口**的问题，却用**不注册扩展**去解决，结果连渲染也没了——同一份内容从别处进来就渲染成「无法识别的类型 whiteboard」，方向与「各端扩展覆盖应当一致」相反。「档」这个词本身也把设计带歪了，见 ER-016。
- 保留的事实（仍然成立，已由 P6.6 的 `getMarkdownFileKit()` 处理）：`database` 在 desktop codec 表里没有条目，`whiteboard` 只有 `isVoid: true` 没有 serializer，在 Markdown 文件里插入这两种块保存后会丢内容。所以 Markdown 文件的 kit 不应提供这两个插入入口。
- 同时作废：ER-015 里「那些轻量编辑器按全量统一归第一档」的裁决，由 ER-016 的按场景划分取代。
- 代码已回滚：`getDesktopFileKit`、`BLOCKS_LOST_IN_MARKDOWN` 与对应单测删除，Markdown 窗口回到应用 kit。

## ER-016 kit 按场景划分，一个场景一个 kit，命名按场景（2026-09-29，已定）

- 结论：kit 的粒度是「这是什么内容 / 什么场景」，不是「一个应用一份」，也不是「第几档」。desktop 会有若干命名 kit：`getMarkdownFileKit()`、`getFlashcardKit()`、`getChatInputKit()`、描述输入、视频笔记等；blog / mobile / browser-extension 各有自己的。命名一律说场景，不用「档」「lite」「bare」这类程度词。
- 依据：不同场景需要的能力差别是真实的——描述输入可能只要段落和无序列表；能创建卡片 / 关联卡片的地方要全量。用程度词命名会邀请「再切一档」，ER-015 就是这么歪的。
- 多数场景共用同一份通用扩展声明；某端要自己的实现就写一份、把通用那份替换掉。通用那份当初是照 desktop 写的，不一定适合 mobile。
- 命名取仓库既有的领域词，不自造：这类内容在代码里就叫 content（`contents` 表、`IContent`、`contentId`、`ContentEditor`），所以是 `getContentKit()`。曾叫 `getLibraryContentKit()`，"library" 全仓搜不到，已改。
- **「拆」与「齐」是两件事，不矛盾**：拆的是同一端内不同用途（content 正文 / 描述输入 / Markdown 文件…），齐的是同一用途跨端的元素类型覆盖。描述输入存在业务记录的 JSON 列里、不会同步到其他端，所以收窄它不影响跨端渲染；跨端必须对齐的只有 content 正文这一档。
- 排除：①一个应用一个 kit（现状 `getDesktopKit()`）——把差异挤到每个调用点的 `extensions` 透传，就是 P6.5 清掉的那种形态；②按能力命名（`getFullKit` / `getInlineOnlyKit`）——调用方要反推「我这个场景算哪一种」。

## ER-017 扩展按场景按需注册，不要求全量覆盖（2026-09-29，已定）

- 结论：kit 只注册该场景需要的扩展，不要求每个 kit 都能渲染所有元素类型。判断依据是「这个场景的内容实际会包含什么」——闪卡正文要把基础能力补齐再加闪卡自己的，闪卡背面不会出现白板，就不装。按已有能力来，不为假想需求预留。
- 依据：场景能产生的内容是受约束的；为「万一」给每个 kit 装全套违反 YAGNI，也会把重依赖拖进轻量场景。
- 排除：「kit 必须能渲染所有元素类型，窄的只是能插入什么」——这条是把 ER-015 的教训过度泛化，代价是每个窄场景都要背全部扩展。
- 不抽「通用底座扩展」共享包（2026-09-29 裁决）：四端底座已经是共享工厂——`WebviewExtension` 本身是独立包，`createImageExtensions` / `createMarkdownPasteImportExtension` 是 `@tau/editor` 的工厂，各端只是调用它们三行，差异（`importFromMarkdown`、`imageAppearance`）都是真参数。而 `@tau/editor` 依赖 `@tau/shared`，共享 helper 放 shared 会反向成环，新开一个包为去重 3 行不值得。防漂移由 `CONTENT_ELEMENT_TYPES` 与四端 parity 测试担保。
- 残留风险（已知并接受）：内容可以从别处进来（从卡片复制粘贴、旧数据同步、格式转换），窄 kit 遇到没注册的类型只能显示通用说明块。P8 之前露出的是字面「无法识别的类型 X」，P8 第一块已落地 ER-006 只读占位，风险降级为「显示一个说明块、内容原样保留」。

## ER-019 旧扩展适配层（IExtension/Base/fromLegacyExtension）随三端迁移完成而删除（2026-09-30，已定）

- 背景：P8 的 `fromLegacyExtension` 让旧 `IExtension` 类扩展零改动混入 v2 kit（「v2 与旧扩展可以在同一个 kit 里混用」是过渡承诺，非长期 API）。
- 删除：blog / mobile / browser-extension / desktop VideoNotePanel 系的旧扩展全部迁 v2 后，删除 `extensions/base.ts`（Base 类）、`IExtension` 接口、`fromLegacyExtension` 适配器与装配层的 legacy 收集分支；热键双通道收窄为「扩展命令热键 + 宿主 prop 场景热键（IHotKeyConfig 直通）」——**hotkeyConfigs prop 是 `<Editor>` 的宿主 API，与旧扩展体系无关，保留**。
- 保留：`AnyExtension` 作为 `EditorExtension` 的别名（全仓标注自然更替后再收）；`IExtensionBaseProps`（元素组件旧 props 命名）；`IHotKeyConfig`（宿主 prop 热键形状）；`Plugin` 类型与 `applyPlugin`（受信任层的原始 Slate 插件，ER-005）。
- 漏网教训：VideoNotePanel 的三个扩展只 `implements IExtension` 不 `extends Base`，按「extends Base」盘点漏掉——删接口后 tsc 才暴露。删除公共接口前应按**接口名**全仓 grep 消费者。

## ER-018 编辑器移除 antd，UI 直接用 `@tau/ui`（2026-09-29，已定）

- 结论：`@tau/editor` 与 `@tau/editor-webview` 不再依赖 `antd` / `@ant-design/icons`；浮层与控件直接 import `@tau/ui`（Popover、Tooltip、Input、Button、Spinner、Tabs、FileDropZone、LoadingOverlay），图标用 lucide。取代待定项 ER-P4。
- 推翻：01 §2「`@tau/editor` 不得 import `@tau/ui`（组件库属于宿主）」。理由：用户要求以当前主题语言和设计为准，`@tau/ui` 就是这套设计语言的实现；在编辑器里另写一套外观相同的原语是重复。
- 边界：`@tau/editor/api` **不**转出 UI 组件，扩展（含内置扩展）直接 import `@tau/ui`。将来开放第三方时再决定扩展可用哪些 UI，届时改一轮 import（用户裁决：现在不为此预留）。
- 编辑器自留两件：`ui/Tooltip`（层级抬到 z 10200，否则被悬浮工具条 z 9999 盖住）、`ui/CaretRight`（折叠用实心三角，lucide 没有）。通用的 Tabs / FileDropZone / LoadingOverlay 进 `@tau/ui`。
- 轻提示与确认走服务 `IEditorNotifier`，默认实现是 `@tau/ui` 的 toast 与 `@tau/ui` 的 ConfirmDialog（由编辑器内的 `ConfirmHost` 渲染，宿主不必挂载）；有自己提示体系的宿主（mobile）注册自己的实现。**禁止** `window.confirm` 之类的浏览器原生对话框（用户裁决：UI 美观是底线），`editor-notifier.test.tsx` 守护。不直接 import toast 的原因：只有 desktop 挂了 `ToastHost`；mobile 的确认框必须接返回手势（AGENTS.md 移动端浮层规范）。
- 各宿主为此在样式入口引入 `@tau/themes/tailwind.css` 并 `@source` 扫描 `packages/ui`，否则 `@tau/ui` 的语义类在 mobile / blog / 插件不生效。mobile 自有的同名类（`bg-surface`、`text-ink-2`…）后声明，以 mobile 为准。
- custom-block：不再向模板注入 `components.antd` / `antdIcons`，也不再包 antd 的 `App` / `ConfigProvider`。旧模板访问 `antd` 时抛出带说明的错误，由本块自带的错误边界显示，不波及页面。存量模板的迁移不做进软件（只有用户本人在用），见 04 遗留问题。
- 排除：①编辑器内自写一套原语、外观对齐 `@tau/ui`——重复实现，两边漂移；②`@tau/editor/api` 转出 UI 组件——第三方不排期，这层转出只增加绕路；③新建 headless 原语包供两者共用——要迁移 `@tau/ui` 现有组件，范围超出本次。

## ER-049 内核的单行输入框也交给宿主：`IEditorNotifier.prompt`（2026-09-30，已定）

- 结论：`EditorNotifier` 增 `prompt(options): Promise<string | null>`，与 `confirm` 对称（提交得到去首尾空白的值，取消得到 null）。默认实现是编辑器内的 `PromptHost`（`@tau/ui` Dialog + Input）；mobile 在 AppShell 挂 `EditorPromptHost`（`BottomSheet` + 输入框），返回手势、遮罩、下拉都等同取消。`MediaUrlInputModal` 与 `useMediaUrlInputStore` 删除，「插入网络图片 / 视频 / 音频」改为 `openMediaUrlInput` 调 `notifierOf(editor).prompt`。
- 起因：内核的网络地址弹窗在 mobile 上不响应 Android 返回键与边缘侧滑，违反 AGENTS.md「移动端浮层与返回手势规范」；内核又不能 import mobile 的 `useSheetBackDismiss`。ER-018 已经为确认框确立了「内核只表达意图，浮层由宿主提供」的做法，输入框照搬。
- 校验：`options.validate(value)` 返回错误文案则输入框保持打开、在输入框下方显示（两端都这样，mobile 的 toast 可能被键盘遮住）。约定 `validate` 必须是纯判断，副作用放在 resolve 之后，所以「当前选区能否插入」抽成 `canSetOrInsertNode(editor)`，与 `setOrInsertNode` 共用同一个锚点查找。`inputMode` 可选，媒体地址传 `url`，手机上弹网址键盘。
- 实现：确认与输入的默认渲染点共用 `createHostedRequestStore` / `useHostedRequestLeader`，也就是原来 `useConfirmStore` 的逻辑：同页多个编辑器只由队首渲染，编辑器全部卸载时未决的请求按取消结算。`PromptHost` 常驻挂载，和 `ConfirmHost` 一样，不再按 `readonly` 条件挂载。
- 排除：①注入一个「返回拦截 hook」服务，内核 Dialog 调它——改动最小，但 mobile 仍是桌面风格的居中弹窗，而且「把 hook 当服务注入」是新造的模式；②媒体专用的 `requestMediaUrl`——下一个需要输入的内核功能还要再开一个接口；③`onSubmit` 带副作用的回调——输入框会重复提交，副作用难以推断，纯 `validate` 已经能覆盖现有的三种失败情况。

## ER-054 源码类块统一用卡片悬停档做底，源码预览块改为「卡片展开」（2026-10-01，desktop 分支原 ER-021，合并后编号）

- 依据：`bg-page` 是窗口最底层的颜色，压在 surface 正文上，标题行加源码区就成了一大块深色带；聊天代码块整块同色、被描边框住，所以不显深。surface-hover 只比正文深半档，三处一致后文档里只有一种「源码」底色。
